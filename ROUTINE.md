# Routine — produce the next topic

This is the procedure an automated session follows when a domain's routine fires. There are **two routines per domain**, a draft routine and a review routine, each told its domain and role in its prompt and firing **every 4 hours**, the domains at different minutes. **Chapters go in sequence, topics in parallel.** A chapter starts with its plan: one run writes the chapter's `CHAPTER.md` (section 1A), every topic's scope, outcomes, concepts, bridge and handoff, built on the chapter before as it really is, and pushes it to `main`. Then every topic of that chapter is built at the same time, each by its own run, each to its part of the plan, so continuity is fixed by the plan instead of by waiting. The next chapter is planned once every topic of this one is **content-final** (written, reviewed and checked; only narration and shipping left, section 6). A dispatcher starts one run per free job every hour, besides the hourly routine (section 0, "Who starts the runs"). Narration, the slowest part, comes last (section 7), so it never holds anything up; topics finished out of order ship held and are released in order (section 1). **Three stages, decoupled (owner decision 2026-10-13).** *Draft* runs (`.claude/skills/draft-chapter`, role `draft`) plan a chapter and write every topic's first draft: research, content plan, fact-check, coverage map, and every file including the narration script in the professor's voice (sections 1A, 2, 3); each draft is pushed as a topic branch and handed over (`claim.mjs drafted`), and the draft run goes on to the next topic until the chapter is drafted. *Review* runs (`.claude/skills/review-topic`, role `review`, the domain routines) take one drafted topic each: content review, checks, looks review, fixes, content-final, and ship it **held** without audio (sections 4, 5, 6, 8). The owner's PC narrates and releases (`.claude/skills/narrate`). Chapter N+1 is planned and drafted as soon as chapter N is fully drafted, while chapter N is still being reviewed. A review run makes **one topic** ready, to the same standard as a hand-made topic. The rules live in [PROJECT_PLAN.md](PROJECT_PLAN.md) and [QUALITY.md](QUALITY.md), the house style in [DESIGN.md](DESIGN.md); this file is the order of work. If anything here conflicts with the plan, the plan wins.

## 0. Ground rules

- **One domain per run:** only the domain named in the prompt. Never touch another domain's topics.
- **One role per run.** A run is a draft run or a review run, as its prompt says, and asks for its job with that role: `node scripts/claim.mjs next "<domain>" --role draft` (jobs `plan`, `draft`) or `--role review` (job `review`). A draft run may take several draft jobs in a row (section 1, `draft`); a review run takes exactly one.
- **No narration on the cloud; park the topic (owner decision 2026-10-13).** Narration is generated on the owner's PC, on a GPU, in bulk, with the `.claude/skills/narrate` skill, which also releases the narrated topics. A routine run builds everything else, ships the topic **held** without audio (section 7), and never runs `site/narration/setup.sh` or `narrate.sh`. `scripts/claim-settings.json` → `"narration": "pc"` is the switch: while it is set, `claim.mjs` hands out no `release` job to a routine (the PC releases with `CLAIM_RELEASE=1`). A held topic without audio is normal and expected; `npm run test:narration` lists it as a warning, which is the PC's to-do list.
- **Skipped topics are not jobs.** A syllabus topic marked *(skipped)* (owner decision; `syllabus/review-notes/de-cuts.md`) stays in the curriculum but gets no reel: `claim.mjs` leaves it out of the order, a chapter plan does not plan it, and the topic after it bridges from the last topic that is not skipped. Never build one; a reel for a skipped topic fails the build.
- **Scope of a run: one job, the one it claimed.** `scripts/claim.mjs` hands each run its job (section 1): plan a chapter, make a topic, resume one whose run stopped, or release finished ones. Do it, report, and stop: don't take a second job in the same run, even with time left. Never touch a topic another run has claimed, its branch or its folder. A topic takes about 4–6 hours for a refresher and 8–12 hours for a full topic, including narration; time is not a constraint, quality is.
- **Live reels are locked.** A live topic is signed off: never change anything it is made of, which is its folder, its audio, its registry entry, any file its reel imports (a chapter's shared `refreshers.tsx`, for example), or the shared player, layouts, pages and styles (`scripts/check-locked.mjs`, run by `check-all` and CI). If your topic needs a change there, don't make it: build around it, and say what you needed in the report. Only the owner unlocks a live reel (a commit line `Unlock: <topic-id>` or `Unlock: shared`, written when they asked for that change); a run never writes one, with one exception the owner approved on 2026-10-12: the Basics backfill (section 1B) changes a live topic's `prerequisites.mdx` only, and its commit carries `Unlock: <topic-id>`.
- **Parallel runs, one at most per job.** At most four runs of a domain (`CLAIM_MAX_PARALLEL`) and eight of all domains together (`CLAIM_MAX_TOTAL`) work at once: every run shares one account's usage limit with its owner's own sessions; a run that finds no free job stops at once. The owner's switches are in `scripts/claim-settings.json`: `finishOnly` (runs only resume or release started topics; nothing new is planned or started) and `maxTotal`.
- **Who starts the runs.** A routine session can't start other runs (it has no `fire_trigger` tool), so it never tries. Each domain's draft routine and review routine fire every 4 hours; a draft run keeps taking draft jobs until its domain has none, so one firing drafts a chapter; a review run takes one topic per firing. `node scripts/claim.mjs open` counts the jobs free right now per domain without claiming any, for the owner (or a dispatcher session, if one is scheduled) to fire a routine more often. Keep the claim alive: start `node scripts/claim.mjs keepalive` in the background right after claiming (a heartbeat every 15 minutes while the run works). Before every push, run `node scripts/claim.mjs mine`; if it fails, another run has taken the topic over after this one went quiet: stop at once, push nothing, and say so in the report. A claim without a heartbeat for 90 minutes is free for the next run to resume.
- **Never publish anything half-done.** All work happens on a branch `topic/<topic-id>`. `main` (which deploys the live site) only receives a topic after every check passes (section 8). Checkpoint: commit and push the branch at the end of every section from 2 on (a message like "WIP <id>: content review done"), with `OUTLINE.md` → "Progress" saying what is done and what comes next.
- **If the run can't finish** (a usage limit is near, or a problem it can't fix): push the branch with "Progress" up to date, then `node scripts/claim.mjs stop "<what stopped it>"`, which hands the topic straight to the next run (the reason goes with it). A topic whose runs stop three times (or vanish six times without a word, as when a usage limit ends them) is blocked for a human instead of being retried; a run that gets `wait` with `blocked` says so at the top of its report.
- **Measure the run, and put it on record.** At the start of each numbered section below run `node scripts/run-metrics.mjs mark <section name>` and `node scripts/claim.mjs beat` (a heartbeat in case the background one failed; if it says the claim was taken over, stop at once). At the very end of every run that claimed a job (a chapter plan, or a topic shipped, held, released, resumed or stopped), after the report is drafted, run `node scripts/run-metrics.mjs finish <domain> <topic-id or chapter-NN> <planned|shipped|held|released|stopped> --checks "<which checks passed, which failed>" --issues "<what went wrong in this run and why, or none>"`. It writes the run's tokens per model, time and stages to `metrics/runs.jsonl` and a two-line entry to [LEDGER.md](LEDGER.md), and pushes both straight to `main` itself (don't commit them with the topic). Be exact in `--issues`: the daily audit ([AUDIT.md](AUDIT.md)) and the owner read the ledger to find what the pipeline gets wrong. A run that only got `wait` writes nothing. If it says no transcript was found, carry on: never invent numbers.
- **Models: Sonnet, and Opus for five judgment jobs.** The run and every agent it launches run on Sonnet, except the five jobs marked **Opus** in the table below, which run on Opus (the owner's choice, 2026-10-12: Opus where a mistake spreads to everything after it, Sonnet for the reading, building and fixing that are most of the tokens). Launch every agent with the Agent tool's `model` set as the table says (`sonnet` or `opus`), and `effort: high` for the jobs in bold. Never Fable or Haiku, and never Opus for any other job. If Opus is unavailable (refused or rate-limited), run that job on Sonnet with effort `high` and say so in `--issues`. Judgment stays independent by giving it to **fresh** agents: the agent that checks something has not written it and starts without the writer's reasoning, only the files.

  | Job | Who | Why |
  |---|---|---|
  | Claim, choose sources, coverage map assembly, merging, shipping, report | the run | mechanical, and checked by scripts |
  | Read each primary source: verbatim quotes and its contents item by item (2.1) | Sonnet agents, one per source | reading is most of the tokens, so it stays out of the run's own context; the fact-check re-reads the sources |
  | **Chapter plan** (1A.2) | **Opus**, effort `high` | everything the chapter's topics share: the biggest lever on flow |
  | **Chapter plan review** (1A.3) | a fresh **Opus** agent, effort `high` | checks the plan without having written it |
  | **Content plan and storyboard** (2.2) | **Opus**, effort `high` | decides what is taught and how every step looks: the biggest lever on quality, and where pacing is set (one idea per step, captions short enough for a reel) |
  | **Fact-check, currency and red team** (2.3) | a fresh **Opus** agent, effort `high` | correctness the scripts can't check (QUALITY.md #7–9), by an agent that didn't plan |
  | **Blind expert list** (2.4) | a fresh Sonnet agent | what an expert must know; short, no repo reading; independent of the plan |
  | **Build**: examples and every file of the topic, until build and examples pass (3) | one Sonnet builder agent | long and iterative: a fresh agent keeps the run's own context small |
  | **Content review: flow, gaps, expert reader** (4) | a fresh **Opus** agent, effort `high` | one agent reads the finished topic once for all three |
  | **Looks and learning review** of the screenshots (5) | a fresh Sonnet agent, effort `high` | judges beauty, clarity and pacing at both sizes (Rule #4) |
  | Fixing a batch of review findings or check failures (4, 5, 8) | a fresh Sonnet fix agent per batch | same reason as the builder |
  | Narration (7) | the owner's PC, later (`.claude/skills/narrate`) | parked on the cloud: no audio is generated in a routine run |

  Each planning and review agent (the ones in bold) runs **once** per topic. Run it again only for a finding marked *major* that needed a new or redesigned step or section, and then give it only its earlier findings and the changed files. The run checks smaller fixes itself.
- **Keep the run's own context small.** Every call re-reads the whole conversation, so a long run pays for everything it ever read on every later call. Brief agents with file paths, not pasted contents; agents write long results to files in the topic folder and return a short summary. Read the parts of files you need, never a file you just wrote, and only the tail or failures of long logs. Look only at the screenshots of steps you changed; the looks review sees the rest.
- **Reviews are written down.** Every review agent appends its findings to the topic's `REVIEW.md` (a section per review: reviewer, date, numbered findings with where, what, evidence, fix, severity), and the run marks each finding fixed or why not. The next topic's planner reads it, so the same mistake isn't made twice; a kind of finding that keeps coming back becomes a QUALITY.md row and, where possible, an automatic check.
- **Never end your turn while anything is running.** A routine session that goes idle is shut down, and everything it started dies with it (QUALITY.md #40: a run lost two and a half hours of narration that way). So:
  - **Agents run in the foreground.** Launch independent agents together in one message (they run in parallel and the call returns when all are done); never with `run_in_background`.
  - **Long jobs** (`setup.sh`, `narrate.sh`, `check-all.mjs`): start them in the background, note the PID, and wait in the foreground in chunks under ten minutes: `timeout 540 tail --pid=<pid> -f /dev/null`, repeated until the job exits (each wait costs almost nothing). Look at the log's last lines only every few chunks, and do other work of this topic between chunks where there is some.
  - End the turn only when the run is finished or stopped.
- **Privacy.** Never put personal information (names, email addresses, account details) in any web request, header or query, yourself or in any agent you launch.
- **No vendors for the voice.** Narration is generated locally with the frozen voice in `site/narration/voice.json`. Never change the voice, their settings or the pipeline.
- **Everything needed is in the repo.** A fresh session has nothing installed: `site/narration/setup.sh` builds the narration tools, `npm ci` the site. If a tool, script or step you need isn't in the repo, that is a bug to fix in the repo (and record in `QUALITY.md`), not something to work around locally.
- **No pull requests.** Merge finished topics into `main` yourself and push.
- **A failing check is this run's job.** If the build or any check fails, find the cause and fix it in this run: missing content gets written, a wrong claim corrected, a broken page repaired. Never skip, loosen or delete a check, never hold a topic back or drop content just to get green, and never merge into `main` while anything is red. If the failure is in `main` itself, caused by another domain's work, fix that minimal cause too (`main` must never stay red) and say so in the report. Only if the fix can't be finished inside the run's budget: push the branch, don't merge, and report exactly what fails and why.
- **Don't guess.** Any claim about how a real system behaves is verified by running it, or against the current primary source. If something can't be verified, leave it out.
- **Read sources as they are.** WebFetch returns a small model's summary of a page, not the page: use it (and web search) only to find sources, never to quote or check them. Fetch every source you rely on with `node scripts/sources.mjs fetch <url> <topic>/sources/<name>.txt` and read that text; quotes go into `SOURCES.md` exactly as they appear there, and `node scripts/sources.mjs check <topic-folder>` proves every quote word for word (it also runs in `check-all`). Tell every agent the same.
- **One procedure per run.** Follow the ROUTINE.md you read at the start, even if `main` changes it while you work (merging `main` into your branch brings the new file; keep going by the one you started with). The next run follows the new one; a resumed topic picks up under the current procedure from its "Progress" note.

## 1. Claim the topic

1. **First thing in the run, before reading anything else:** `node scripts/claim.mjs next "<domain>"` (it needs nothing installed and reads the syllabus and registry the way the build does). It walks the syllabus in order, skips live topics and topics another run is working on, and prints the job as JSON:
   - `wait`: nothing to do now (the domain's or the account's run limit is reached, every topic of the planned chapter is taken and the next chapter isn't due yet, or a job is `blocked`). **Stop at once** with a one-line report of the reason (a `blocked` topic first, word for word). Don't read the plan or the repo.
   - `draft` (draft runs): write a topic's first draft, sections 2 and 3, then hand it over. New topic: use the id and folder in `topic.use` (they keep a chapter in one folder even when several runs work in it), then `node scripts/claim.mjs set <topic-id> <folder>`, `git fetch origin`, and create `topic/<topic-id>` from `origin/main` (never from a local `main`, which may be stale). With `resumed: true` (a draft run stopped; `previousRunStopped` says why): check out `topic.branch` (if it has none, start as new) and continue at the first unfinished step, `OUTLINE.md` → "Progress"; deal with the reason it stopped first. When the draft is pushed (section 3, "Hand over"), run `node scripts/claim.mjs drafted`, then ask for the next job (`next --role draft`) and continue in the same run while it returns `draft` or `plan`; stop at `wait`.
   - `review` (review runs): a drafted topic, on `topic.branch`. Check it out, read `OUTLINE.md` → "Progress" (a first review starts at section 4; a stopped review continues at its first unfinished step; `contentFinal: true` means only section 8 is left) and do sections 4, 5, 6 and 8. One topic per run.
   - `plan`: plan the chapter in `chapter` (section 1A), then stop. Make no topic in that run.
   - `release` (the PC only, `CLAIM_RELEASE=1`; a routine never gets it while narration is parked): held topics (`topics`, in order) whose earlier topics are all live now: release them as one chain, in order. Merge `origin/main` into a branch `release/<first-topic-id>`, set each one's `status: 'live'`, and check each seam: launch the content review (section 4) on each topic's previous topic (final reel, Deep dive, registry entry) against its bridge, Prerequisites and `uses`, and fix what it finds. A topic held longer than 14 days also gets the full release check: refresh facts against current sources, coverage map and gap review. Add the Basics section (section 1B) to every topic in the chain that `site/src/topics/basics-backlog.json` still lists. Generate narration where it is missing, stale or out of standard (`npm run test:narration` warns about held reels; section 7), then ship (section 8). Make nothing new in that run.

   Then start the heartbeat in the background (`node scripts/claim.mjs keepalive`). Do not start the narration setup: narration is parked (section 7).
2. **The chapter plan is the contract.** For `draft` and `review`, `topic.chapter.plan` is the chapter's `CHAPTER.md` on `main`: this topic's entry there (scope, outcomes, concepts it introduces and uses, bridge, handoff, Prerequisites) is what it must deliver, and the neighbouring entries are what the topics around it deliver, being built at the same time. Never edit `CHAPTER.md`; if this topic truly can't keep to its entry, keep as close as it can, record why under `OUTLINE.md` → "Changes from the chapter plan", and say so in the report (the release seam check and the audit look for it). The JSON also describes the **previous** and **next** topics (status, id, branch, folder): read what exists of them (on `main`, or on their branch with `git show origin/<branch>:<folder>/<file>`) to match their style and wording, but build to the plan, not to their progress.
3. Read before writing anything (the parts, not whole files you won't use: the plan's named sections by heading, not all of `PROJECT_PLAN.md`; the previous topic's reel step titles, registry entry and post-notes headings rather than every file in full): the plan's Core Rules (#1–#6), Learning design, Narration and Definition of Done; all of `QUALITY.md`; `DESIGN.md`; `CHAPTER.md` (all of it); the previous chapter's last topic and the topics of this chapter that already exist (registry entry, reel step titles, post-notes headings, `REVIEW.md`); and the next topic's syllabus line.

## 1A. Plan a chapter (job `plan`)

A chapter plan lets every topic of the chapter be built at once without losing the thread, so it decides everything topics share and nothing they can decide alone. **The plan is pushed the moment it exists**, to its own branch `chapter.branch` (`plan/<domain-prefix>-ch<NN>`), and again after every change, so a run that dies (a usage limit) loses nothing: the next run continues from the branch. Only the reviewed plan goes to `main`, because topic runs start from what is on `main`.

0. **Start or continue.** `git fetch origin && git ls-remote --exit-code origin refs/heads/<chapter.branch>`. If the branch exists (a stopped run's draft), check it out (`git checkout -B <chapter.branch> origin/<chapter.branch>`) and continue: a last commit "reviewed" goes straight to step 4, any other to step 3. Otherwise `git checkout -B <chapter.branch> origin/main`.

1. **Inputs.** The JSON's `chapter` (number, title, the `plan` path, and every topic with its index, status, id and folder: use these ids and folders), the syllabus lines of the chapter's topics and of the first topic of the next chapter, `previousChapter.plan` and the previous chapter's topics as they really are (registry entries, reel step titles, post-notes headings, `REVIEW.md`: all content-final by now), the plan's Core Rules, Learning design and Narration sections, `DESIGN.md`, and `QUALITY.md`. Topics of this chapter that are already live, held or in progress are fixed: plan around them (read their files or their branch's `OUTLINE.md`).
2. **Plan (Opus agent, effort high)** writes `CHAPTER.md` at `chapter.plan` and, **the moment the file is written, commits and pushes it** (`git add <plan> && git commit -m "Chapter <N> plan: draft" && node scripts/claim.mjs mine && git push -f origin HEAD:refs/heads/<chapter.branch>`; tell the agent exactly this; if `mine` fails, another run has taken the plan over: stop), then again after any later change. The plan:
   - **The chapter:** the problem it solves for the learner, the order of ideas and why, the notation, terms and running example every topic shares, and the one visual language the chapter's reels use.
   - **Each topic, in syllabus order:** title, id, folder, kind (full or refresher); **scope** (what it covers, clause by clause from its syllabus line, and what it leaves to which other topic: no overlap, no gap); learning outcomes; concepts it `introduces` and `uses` (ids, as the registry ledger uses them; a concept is used only after the topic or chapter that introduces it); its `bridge` from the topic before and `handoff` to the topic after (the last one hands off to the next chapter's first topic); its Prerequisites, starting with the Basics terms its panel opens with (every notation and term the reel will use); its visual idea in a line; the primary sources it should start from.
3. **Plan review (a fresh Opus agent, effort high)** checks it and lists every problem: a syllabus clause assigned to no topic or to two; a concept used before it is introduced (within the chapter and against the chapters before); a bridge that doesn't answer the handoff before it; scopes that overlap; inconsistent notation; anything an expert would find thin or wrong. Fix them all (the reviewer edits the file itself), then commit "Chapter <N> plan: reviewed" and push it to the branch at once, as in step 2.
4. **Publish.** Put the reviewed file on `main`: `git fetch origin && git checkout -B publish origin/main && git checkout <chapter.branch> -- <plan>`, commit "Plan <domain> chapter <N>: <title>", `node scripts/claim.mjs mine`, then `git push origin HEAD:main` (if rejected, `git pull --rebase origin main` and push again; it is a new file, so there is nothing to conflict). Then delete the branch (`git push origin --delete <chapter.branch>`) and `node scripts/claim.mjs done`.
5. **Continue.** The chapter's topics are now draft jobs: ask for the next one (`node scripts/claim.mjs next "<domain>" --role draft`) and draft it (sections 2, 3, 3H); other draft runs take the rest in parallel. At `wait`, finish the run (`run-metrics.mjs finish <domain> chapter-<NN> planned …`) and report.

## 1B. Basics backlog (retired)

The Basics backfill is finished: every topic has `pre-notes.md` (2026-10-17) and `basics-backlog.json` no longer exists. New topics write their pre-notes as part of section 3.

## 2. Research and plan

1. Run the state-of-the-art scan and pick the primary sources (official docs, papers, source code, specs; the current version of each). Launch one Sonnet agent per source (all in one message, so they run in parallel) to fetch it with `scripts/sources.mjs fetch` and write its section of `SOURCES.md` in the format described at the top of that script: URL, version, every passage the topic could rely on as **verbatim quotes** copied from the fetched text, and the source's contents item by item (for the coverage map). Then run `node scripts/sources.mjs check <topic-folder>`; every quote must pass before planning starts. A source that can't be fetched (blocked, paywalled) is replaced by one that can, or its claims are dropped.
2. **Content plan (Opus agent, effort high).** Launch an Opus agent to plan the topic before anything is written. Give it the syllabus line, `SOURCES.md`, the plan's Core Rules, Learning design and Narration sections, `QUALITY.md`, `DESIGN.md`, the drawing kit (`site/src/reels/kit.tsx`), the previous topic's registry entry, reel, post-notes headings and `REVIEW.md` (this topic must pick up exactly where its handoff leaves off, use only concepts it or earlier topics introduce, and not repeat the mistakes its reviews found), and the next topic's syllabus line. It may read a source itself where `SOURCES.md` is thin. It writes `OUTLINE.md` in the topic folder: the learning outcomes; the reel's steps in order, each with a **storyboard** to `DESIGN.md` (title; the visual idea for this concept and why it makes it click; what is on screen and where, in portrait first and then landscape; what moves on which beat; the real values shown; the final frame; the caption's point; every predict question with its answer and wrong options; **and the narrator's line of thought for the step: what she explains beyond the description** (the why, what to watch, the wrong intuition she corrects, the question she asks before the reveal), in the MIT-professor persona of the plan (Narration → The narrator's persona), since the narration teaches and never reads the description); the post-notes headings with what each covers; the examples to execute and what each must assert; the bridge and handoff; the concept ledger (`introduces` / `uses`); and **the claims list**, every factual claim the topic will make with its source. Writing follows `OUTLINE.md`; a change of plan during writing is made in `OUTLINE.md` first, with the reason.
3. Launch an adversarial fact-check agent (a fresh Opus agent, effort high) on `OUTLINE.md` against the primary sources themselves (their fetched texts in `<topic>/sources/`, and further sources it fetches the same way), not only `SOURCES.md` (as in `site/src/topics/.../io-cost-model/FACT-CHECK.md`). It re-derives every claim from its source (a source it could not open doesn't count: find one it can open, or drop the claim; a book may be cited for framing next to an opened source), checks that each quote in `SOURCES.md` really supports the claim it is cited for (that the quotes are word for word is already proven by `sources.mjs check`), flags anything outdated, renamed or superseded (current version, quoted), and as red team tries to break each explanation and predict question with edge cases and counter-examples. Apply every correction, to `OUTLINE.md` too. It saves its result as the topic's `FACT-CHECK.md`.
4. **Coverage map** (plan, Rule #6), in the topic folder as `coverage.json` (follow the existing topics' maps; the format is described at the top of `site/src/lib/coverage.ts`):
   - `syllabus`: the topic's syllabus line split into clauses, copied word for word, together covering the whole line.
   - `sources`: the contents of at least two primary sources, item by item (from `SOURCES.md`).
   - `expert`: launch an independent Sonnet agent (in parallel with the content plan; it needs nothing from it) that has **not** seen your draft (forbid it from reading `site/`) to write a "what an expert must know" list for the syllabus line, each item with a primary source it has opened (`scripts/sources.mjs fetch`; never one cited from memory) and a placement (here / a named later syllabus topic / out of scope). Copy its items in.
   - Map every item to a planned reel step title, post-notes heading, or another syllabus topic with a quote from its line that shows it covers it. Source and expert items may be marked `out` only with a reason. Anything that belongs here and isn't planned yet goes into `OUTLINE.md`.

## 3. Build the topic

Launch one **builder agent** (Sonnet) with the topic folder, `OUTLINE.md`, `FACT-CHECK.md`, `coverage.json`, `DESIGN.md`, `site/src/reels/kit.tsx` and the previous topic's folder as the pattern. It writes every file below, runs `npm run build` until it passes, commits, and returns a short summary (what it wrote, anything it couldn't follow in the plan and why). The folder and id are the ones `claim.mjs` gave in section 1 (`m<N>-<short-name>/ch<NN>-<short-name>/<topic-slug>` under `site/src/topics/<domain>/`); topic ids are permanent and prefixed by domain: `de.` Data Engineering, `dsa.` Data Structures & Algorithms, `rust.` Rust.

- `examples.py` or `examples.sh`: everything about real software behaviour, with asserts for every number and output the reel shows (the build checks that every number on screen appears in `examples.py`; running the examples is optional since 2026-10-18, `npm run test:examples` by hand).
- `reel.tsx` + `scenes.tsx`: the steps and their animations, every animation a pure function of time, built from the drawing kit and the shared components (`site/src/reels/`) to `DESIGN.md`. Refreshers: about 5 minutes, fast recap, at least one predict question, a recap step. Full topics: the plan's learning-design layers 1–4 and "Prove it" in the reel.
- `post-notes.md`: the Deep dive for after the reel (outcomes, internals, lab, production, frontier, and a closing "Where this goes next"), plain Markdown with `<section data-section="…">` wrappers. `references.md`: the sources actually used, a list with "Last verified: <date>" (and "Expert sign-off: pending").
- `pre-notes.md`: **only what must be known before watching** (owner decision 2026-10-17): the prerequisite vocabulary the reel takes for granted, never a term the reel itself teaches. 4–14 bullets, each `- **Term**: definition in our own words. *Where you meet it:* scenario.`, under 400 words, no links, plain Markdown. The build checks it (`site/src/lib/notes-rules.ts`, the same code the in-page editor runs).
- `prerequisites.mdx`: links only: a heading per thing the learner must already know and its resources. On-site reels use `<Resource kind="reel" host={props.host} …>`. Every outside link and its title, author and length is verified (YouTube via oEmbed, pages for a 200 and a matching title); unverified metadata is left out. No prose around the links.
- `narration.json`: the spoken script, one line per sentence or phrase, written to be heard (see the plan's Narration section); an `answer` clip for every predict step; code and names spelled the way they are said. **It teaches in the voice of an MIT professor; it does not read the description** (plan, Narration → The narrator's persona; the writing brief with examples is `.claude/skills/narrate/teacher-pass.md`; owner rule 2026-10-13): for each step, explain the picture (why it looks like that, what to watch as it moves, the wrong intuition and what goes wrong with it, the reason behind the rule), say a number only when the number is the point, and never repeat a description sentence. The build fails a step whose narration is its description read aloud (`topic-checks.ts`, check 5).
- The registry entry in `site/src/topics/registry.ts`: `kind`, `introduces` / `uses` / `declared` (the concept ledger), a real `bridge` from the previous topic and `handoff` to the next, `status: 'live'`, or `'held'` if an earlier topic isn't live yet (normal when the topic before it is still being narrated or shipped by another run; a later run releases it).

### 3H. Hand over the draft (draft runs end a topic here)

The draft is complete when every file of section 3 exists, `npm run build` passes, `node scripts/narration-teaches.mjs <folder>` shows no flag, and `node scripts/sources.mjs check <folder>` passes. Write `OUTLINE.md` → "Progress": `drafted <date>; next: review (ROUTINE.md section 4)`, commit `Draft: <topic-id>`, `node scripts/claim.mjs mine`, push the branch, then `node scripts/claim.mjs drafted`: the topic is now a review job. Do not review, do not run the looks review, do not set the registry status (it stays `'held'`), do not touch `main`. Then `node scripts/claim.mjs next "<domain>" --role draft` for the next draft or plan job; at `wait`, finish the run (`run-metrics.mjs finish`, section 9).

## 4. Content review (review runs start here)

A review run has checked out `topic.branch` and read `OUTLINE.md` (the storyboard, the claims list, "Progress"), `FACT-CHECK.md`, `coverage.json` and `SOURCES.md`, and runs `npm run build` once to confirm the draft builds before reviewing it. Everything the draft run did is on the branch; nothing is redone unless a review finds it wrong.

Launch one **content review** agent (a fresh Opus agent, effort high) that has not written anything in this topic. Give it the previous topic (on `main`, or content-final on its branch), this topic's files (reel and scenes, narration, Deep dive, Prerequisites, registry entry, `coverage.json`, `SOURCES.md`, `FACT-CHECK.md`) and the next syllabus topic's line. It reads them in sequence once and appends to `REVIEW.md`, in three parts:

- **Flow:** anything abrupt, anything used before it is taught, any prerequisite that sits later in the syllabus.
- **Pre-notes:** `pre-notes.md` holds only vocabulary the reel assumes (nothing the reel teaches), each definition is correct and in our own words, and it stays a primer (a line or two per term with a scenario, no links).
- **Gap hunt:** everything missing, too thin, or wrongly marked as covered elsewhere, against the syllabus line, the sources and the expert list.
- **Expert reader:** anything imprecise, hand-wavy, or not at the depth the plan's Learning design asks for, as a sceptical senior engineer would judge it.
- **Narration teaches, in the professor's voice:** step by step, would an MIT professor say this about the picture (the why before the rule, what to watch, the wrong intuition corrected, the question before the reveal, the connection to the step before), or is it the description read aloud or paraphrased? Name every step that reads the screen or merely restates; the build's check is only the floor. The brief is `.claude/skills/narrate/teacher-pass.md`.

Fix everything it finds (with a fix agent for a large batch). A prerequisite later in the syllabus is a syllabus bug: reorder and log it in `syllabus/review-notes/`, but **never move a topic that is live, held or claimed** (`node scripts/claim.mjs status "<domain>"`): other runs are building on the order around it. If the fix needs that, log it for a human in `syllabus/review-notes/` and teach the missing piece here (`introduces`) meanwhile. Fill every real gap (or record why an item is out of scope), then record the review in `coverage.json` → `gapReview` (date, who, `open: []`). The build's flow and coverage checks must pass.

## 5. Checks and the looks review

From the repo root, run every check except narration (cheapest first, a timing summary at the end; it starts and stops `astro preview` itself):

```sh
node scripts/check-all.mjs --skip narration --changed     # docs, examples, sources, build, and the reels and links this branch affects
node scripts/check-all.mjs --only reels --topic <topic-slug>   # while fixing: just this topic's reel
```

`--changed` limits the reel and link checks to what the branch can affect against `origin/main` (`scripts/affected.mjs`): this topic, plus every reel when the branch touches shared code. Change shared code (`site/src/reels/`, `site/src/lib/`, components, tests) only when this topic truly needs it, keep it working for every existing topic, and expect the full reel test. It runs the same commands as CI, so nothing is weaker: `npm run build` (includes the flow, coverage, syllabus and topic-file checks), `npm run test:examples`, `npm run test:reels`, `npm run check:links`, `node scripts/check-docs.mjs`. The reel test also fails on text in a drawing that is clipped, overlaps or runs into other text, or is too small to read. A coverage failure means content is missing: write it, or point to the topic whose syllabus line truly covers it; never weaken the map to make it pass.

Then the **looks and learning review**: once the reels test is green, launch a fresh Sonnet agent (effort high) on this topic's screenshots in `site/test-results/` (every step, desktop and phone), with `OUTLINE.md`, `narration.json` and `DESIGN.md`. It judges each step as a demanding designer and teacher would, by the checklist in `DESIGN.md` → "The looks review checks", and appends its findings to `REVIEW.md`. Fix every finding (a fix agent for a large batch), re-run the affected checks, and look at the changed steps' new screenshots yourself. All of this section is green before going on.

## 6. Content final (review runs)

Commit and push the branch, then run `node scripts/claim.mjs final`. From here the run no longer counts against the run limits (shipping uses few tokens). Once every topic of the chapter is content-final, the next run (started by the dispatcher or the hourly schedule) plans the next chapter. **The content is now final:** change it only when a check or the narration forces it, and then add a line under `OUTLINE.md` → "Changes after final" (what changed and why) and push it, so the release seam check and the next chapter's plan can follow.

## 7. Narration: parked for the PC (nothing to do in a routine run)

Narration is **not** generated on the cloud (owner decision 2026-10-13; ground rules). The topic ships without audio, `held`, with its final `narration.json` (checked by the build: one entry per step, speakable lines, at most 50 words a line) as the script the PC will voice. Do not run `site/narration/setup.sh` or `narrate.sh`, do not generate or commit audio, and do not treat the missing audio as a failure: `npm run test:narration` reports a held topic without audio as a warning, and that warning is the PC's work list.

The PC side is `.claude/skills/narrate/SKILL.md`: it pulls `main`, narrates every held topic the test lists, in bulk on the GPU with the voice frozen in `site/narration/voice.json`, fits the clips to each topic (`manifest.json`, captions timing), runs the full checks, and releases the chains that are complete, in order (the `release` job, section 1, with `CLAIM_RELEASE=1`). Until then the topic is finished content, parked.

The old cloud procedure (`narrate.sh`, the take cache on the `narration-cache` branch, the transcript check) still exists and still works; it is just not run by a routine.

## 8. Ship (then report and stop)

1. Go through `QUALITY.md` → "Before shipping any topic". If this run hit a new kind of problem, add a row with its fix and a guard (an automatic check where possible).
2. Other runs (this domain's and others') merge into `main` at the same time. So: `git fetch origin && git merge origin/main` into the topic branch, resolve conflicts (in `site/src/topics/registry.ts` keep **both** sides' entries).
3. **Continuity.** Check this topic still matches its `CHAPTER.md` entry (bridge, handoff, concepts, scope), and, where the previous topic exists, its real handoff and concepts (on `main`, or its branch's `OUTLINE.md` → "Changes after final" and "Changes from the chapter plan"); bring this topic's bridge, Prerequisites and `uses` in line. Set **`status: 'held'`**, always: a topic without narration cannot be live (`test:narration` fails a live reel without audio), and narration is parked for the PC (section 7). The PC releases it, in order, after narrating, and checks every seam again against the real topics on both sides.
4. Run `node scripts/check-all.mjs --changed`: every check, all green, on the merged branch (the narration check passes with a warning for this held topic: expected).
5. Run `node scripts/claim.mjs mine`, then merge into `main`, push, and confirm the CI run for your push succeeds (on `main` every push gets its own run, testing the reels it affects) and that the site deployed (a Deploy run for your push, or a newer one that includes it, succeeded). If the push is rejected because `main` moved, repeat from step 2. If CI fails, fix it on the branch and push again; never leave `main` red.
6. Delete the topic branch and run `node scripts/claim.mjs done`.

## 9. Report

End the run with a short report for the owner:

- the domain and chapter, and the topic shipped (or resumed, or planned) this run: it shipped **held, parked for narration on the PC** (say so), and which earlier topics it also waits for, if any; how much of the chapter remains;
- what was verified and how (fact-check corrections, executed examples, measured results), and the main review findings;
- the run's ledger entry (what `run-metrics.mjs finish` printed: time, tokens per model, agents, checks, issues), and the stage that used the most;
- anything that needs a human: the narration to generate on the PC (the topic id), and the expert sign-off still pending;
- if the run stopped early: the branch, the step it stopped at, and what remains.
