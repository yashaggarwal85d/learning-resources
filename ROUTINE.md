# Routine — produce the next topic

This is the procedure an automated session follows when a domain's routine fires. There is **one routine per domain**, each told its domain in its prompt and firing **every hour**, the domains at different minutes. **Chapters go in sequence, topics in parallel.** A chapter starts with its plan: one run writes the chapter's `CHAPTER.md` (section 1A), every topic's scope, outcomes, concepts, bridge and handoff, built on the chapter before as it really is, and pushes it to `main`. Then every topic of that chapter is built at the same time, each by its own run, each to its part of the plan, so continuity is fixed by the plan instead of by waiting. The next chapter is planned once every topic of this one is **content-final** (written, reviewed and checked; only narration and shipping left, section 6). A dispatcher starts one run per free job every hour, besides the hourly routine (section 0, "Who starts the runs"). Narration, the slowest part, comes last (section 7), so it never holds anything up; topics finished out of order ship held and are released in order (section 1). A run makes **one topic**, finished and shipped, to the same standard as a hand-made topic. The rules live in [PROJECT_PLAN.md](PROJECT_PLAN.md) and [QUALITY.md](QUALITY.md), the house style in [DESIGN.md](DESIGN.md); this file is the order of work. If anything here conflicts with the plan, the plan wins.

## 0. Ground rules

- **One domain per run:** only the domain named in the prompt. Never touch another domain's topics.
- **Scope of a run: one job, the one it claimed.** `scripts/claim.mjs` hands each run its job (section 1): plan a chapter, make a topic, resume one whose run stopped, or release finished ones. Do it, report, and stop: don't take a second job in the same run, even with time left. Never touch a topic another run has claimed, its branch or its folder. A topic takes about 4–6 hours for a refresher and 8–12 hours for a full topic, including narration; time is not a constraint, quality is.
- **Live reels are locked.** A live topic is signed off: never change anything it is made of, which is its folder, its audio, its registry entry, any file its reel imports (a chapter's shared `refreshers.tsx`, for example), or the shared player, layouts, pages and styles (`scripts/check-locked.mjs`, run by `check-all` and CI). If your topic needs a change there, don't make it: build around it, and say what you needed in the report. Only the owner unlocks a live reel (a commit line `Unlock: <topic-id>` or `Unlock: shared`, written when they asked for that change); a run never writes one.
- **Parallel runs, one at most per job.** At most four runs of a domain (`CLAIM_MAX_PARALLEL`) and eight of all domains together (`CLAIM_MAX_TOTAL`) work at once: every run shares one account's usage limit with its owner's own sessions; a run that finds no free job stops at once.
- **Who starts the runs.** A routine session can't start other runs (it has no `fire_trigger` tool), so it never tries. Runs are started two ways: each domain's routine fires every hour, and a dispatcher session (scheduled hourly, outside the routines) runs `node scripts/claim.mjs open`, which counts the jobs free right now per domain without claiming any, and fires each domain's routine that many times. So a newly planned chapter, or a topic made content-final, gets its next runs within the hour. Keep the claim alive: start `node scripts/claim.mjs keepalive` in the background right after claiming (a heartbeat every 15 minutes while the run works). Before every push, run `node scripts/claim.mjs mine`; if it fails, another run has taken the topic over after this one went quiet: stop at once, push nothing, and say so in the report. A claim without a heartbeat for 90 minutes is free for the next run to resume.
- **Never publish anything half-done.** All work happens on a branch `topic/<topic-id>`. `main` (which deploys the live site) only receives a topic after every check passes (section 8). Checkpoint: commit and push the branch at the end of every section from 2 on (a message like "WIP <id>: content review done"), with `OUTLINE.md` → "Progress" saying what is done and what comes next.
- **If the run can't finish** (a usage limit is near, or a problem it can't fix): push the branch with "Progress" up to date, then `node scripts/claim.mjs stop "<what stopped it>"`, which hands the topic straight to the next run (the reason goes with it). A topic whose runs stop three times (or vanish six times without a word, as when a usage limit ends them) is blocked for a human instead of being retried; a run that gets `wait` with `blocked` says so at the top of its report.
- **Measure the run, and put it on record.** At the start of each numbered section below run `node scripts/run-metrics.mjs mark <section name>` and `node scripts/claim.mjs beat` (a heartbeat in case the background one failed; if it says the claim was taken over, stop at once). At the very end of every run that claimed a job (a chapter plan, or a topic shipped, held, released, resumed or stopped), after the report is drafted, run `node scripts/run-metrics.mjs finish <domain> <topic-id or chapter-NN> <planned|shipped|held|released|stopped> --checks "<which checks passed, which failed>" --issues "<what went wrong in this run and why, or none>"`. It writes the run's tokens per model, time and stages to `metrics/runs.jsonl` and a two-line entry to [LEDGER.md](LEDGER.md), and pushes both straight to `main` itself (don't commit them with the topic). Be exact in `--issues`: the daily audit ([AUDIT.md](AUDIT.md)) and the owner read the ledger to find what the pipeline gets wrong. A run that only got `wait` writes nothing. If it says no transcript was found, carry on: never invent numbers.
- **Models: Fable and Opus judge, Sonnet does everything else.** The run itself is Sonnet (the routine pins it). Judgment on what to teach, how it should look and whether it is right goes to Fable or Opus, split so that each has a share of the work (they have separate usage limits) and so that **what one of them writes, the other checks**: Fable designs (the chapter plan, the content plan and storyboard) and reads the finished topic as a whole; Opus checks the facts, writes the blind expert list, reviews the chapter plan and judges the looks. Reading sources, building against a plan and fixing, where the checks catch mistakes, go to Sonnet. Nothing runs on a smaller model. Launch agents with the Agent tool's `model` (`fable`, `opus`, `sonnet`) and `effort` where given:

  | Job | Who | Why |
  |---|---|---|
  | Claim, choose sources, coverage map assembly, merging, shipping, report | the run | mechanical, and checked by scripts |
  | Read each primary source: verbatim quotes and its contents item by item (2.1) | Sonnet agents, one per source | reading is most of the tokens, so it stays out of the run's own context; the fact-check re-reads the sources |
  | **Chapter plan** (1A.2) | Fable, effort `high` | everything the chapter's topics share: the biggest lever on flow |
  | **Chapter plan review** (1A.3) | Opus, effort `high` | a different model checks what Fable planned |
  | **Content plan and storyboard** (2.2) | Fable, effort `high` | decides what is taught and how every step looks: the biggest lever on quality |
  | **Fact-check, currency and red team** (2.3) | Opus, effort `high` | correctness the scripts can't check (QUALITY.md #7–9), by a different model than the plan's |
  | **Blind expert list** (2.4) | Opus | what an expert must know; short, no repo reading; independent of the plan |
  | **Build**: examples and every file of the topic, until build and examples pass (3) | one Sonnet builder agent | long and iterative: a fresh agent keeps the run's own context small |
  | **Content review: flow, gaps, expert reader** (4) | Fable, effort `high` | one agent reads the finished topic once for all three |
  | **Looks and learning review** of the screenshots (5) | Opus | judges beauty, clarity and pacing at both sizes (Rule #4) |
  | Fixing a batch of review findings or check failures (4, 5, 8) | a fresh Sonnet fix agent per batch | same reason as the builder |
  | Narration (7) | the run | scripted; mostly waiting |

  **If Fable is unavailable** (its weekly limit is reached, or the Agent tool rejects it): run that agent on Opus at the same effort, as before Fable was added, and carry on; everything else stays as it is. Say so in the report and in `--issues` (for example "Fable unavailable: content plan on Opus"). If Opus is unavailable, use Fable for its jobs the same way. If neither is available, stop the run (section 0, stopping) rather than judge with Sonnet. For any other option that isn't available, use a stronger one, never a weaker one, and say so in the report.

  Each Fable or Opus agent runs **once** per topic. Run it again only for a finding marked *major* that needed a new or redesigned step or section, and then give it only its earlier findings and the changed files. The run checks smaller fixes itself.
- **Keep the run's own context small.** Every call re-reads the whole conversation, so a long run pays for everything it ever read on every later call. Brief agents with file paths, not pasted contents; agents write long results to files in the topic folder and return a short summary. Read the parts of files you need, never a file you just wrote, and only the tail or failures of long logs. Look only at the screenshots of steps you changed; the looks review sees the rest.
- **Reviews are written down.** Every review agent appends its findings to the topic's `REVIEW.md` (a section per review: reviewer, date, numbered findings with where, what, evidence, fix, severity), and the run marks each finding fixed or why not. The next topic's planner reads it, so the same mistake isn't made twice; a kind of finding that keeps coming back becomes a QUALITY.md row and, where possible, an automatic check.
- **Never end your turn while anything is running.** A routine session that goes idle is shut down, and everything it started dies with it (QUALITY.md #40: a run lost two and a half hours of narration that way). So:
  - **Agents run in the foreground.** Launch independent agents together in one message (they run in parallel and the call returns when all are done); never with `run_in_background`.
  - **Long jobs** (`setup.sh`, `narrate.sh`, `check-all.mjs`): start them in the background, note the PID, and wait in the foreground in chunks under ten minutes: `timeout 540 tail --pid=<pid> -f /dev/null`, repeated until the job exits (each wait costs almost nothing). Look at the log's last lines only every few chunks, and do other work of this topic between chunks where there is some.
  - End the turn only when the run is finished or stopped.
- **Privacy.** Never put personal information (names, email addresses, account details) in any web request, header or query, yourself or in any agent you launch.
- **No vendors for the voice.** Narration is generated locally with the frozen voice in `site/narration/voice.json`. Never change the voice, their settings or the pipeline.
- **Everything needed is in the repo.** A fresh session has nothing installed: `site/narration/setup.sh` builds the narration tools, `npm ci` the site. If a tool, script or step you need isn't in the repo, that is a bug to fix in the repo (and record in `QUALITY.md`), not something to work around locally.
- **No pull requests.** Merge finished topics into `main` yourself and push.
- **A failing check is this run's job.** If the build or any check fails, find the cause and fix it in this run: missing content gets written, a wrong claim corrected, a broken page repaired. Never skip, loosen or delete a check, never hold a topic back or drop content just to get green, and never merge into `main` while anything is red. If the failure is in `main` itself, caused by another domain's work, fix that minimal cause too (`main` must never stay red) and say so in the report. Only if the fix can't be finished inside the run's budget: push the branch, don't merge, and report exactly what fails and why.
- **Don't guess.** Any claim about how a real system behaves is verified by running it, or against the current primary source. If something can't be verified, leave it out.
- **Read sources as they are.** WebFetch returns a small model's summary of a page, not the page: use it (and web search) only to find sources, never to quote or check them. Fetch every source you rely on with `node scripts/sources.mjs fetch <url> <topic>/sources/<name>.txt` and read that text; quotes go into `SOURCES.md` exactly as they appear there, and `node scripts/sources.mjs check <topic-folder>` proves every quote word for word (it also runs in `check-all`). Tell every agent the same.
- **One procedure per run.** Follow the ROUTINE.md you read at the start, even if `main` changes it while you work (merging `main` into your branch brings the new file; keep going by the one you started with). The next run follows the new one; a resumed topic picks up under the current procedure from its "Progress" note.

## 1. Claim the topic

1. **First thing in the run, before reading anything else:** `node scripts/claim.mjs next "<domain>"` (it needs nothing installed and reads the syllabus and registry the way the build does). It walks the syllabus in order, skips live topics and topics another run is working on, and prints the job as JSON:
   - `wait`: nothing to do now (the domain's or the account's run limit is reached, every topic of the planned chapter is taken and the next chapter isn't due yet, or a job is `blocked`). **Stop at once** with a one-line report of the reason (a `blocked` topic first, word for word). Don't read the plan or the repo.
   - `make`: a new topic. Use the id and folder in `topic.use` (they keep a chapter in one folder even when several runs work in it), then `node scripts/claim.mjs set <topic-id> <folder>`, `git fetch origin`, and create `topic/<topic-id>` from `origin/main` (never from a local `main`, which may be stale).
   - `resume`: a topic whose run stopped (`previousRunStopped` says why, when that run could say). Check out its branch (`topic.branch`; if it has none, start the topic as `make`) and start at its first unfinished step: `OUTLINE.md` → "Progress" says where it stopped. Deal with the reason it stopped before anything else. A branch without `OUTLINE.md` gets one first, written by the content-plan agent (2.2) from the branch's files and sources. A branch whose content was already final when its run stopped goes straight on to section 7.
   - `plan`: plan the chapter in `chapter` (section 1A), then stop. Make no topic in that run.
   - `release`: held topics (`topics`, in order) whose earlier topics are all live now: release them as one chain, in order. Merge `origin/main` into a branch `release/<first-topic-id>`, set each one's `status: 'live'`, and check each seam: launch the content review (section 4) on each topic's previous topic (final reel, Deep dive, registry entry) against its bridge, Prerequisites and `uses`, and fix what it finds. A topic held longer than 14 days also gets the full release check: refresh facts against current sources, coverage map and gap review. Generate narration where it is missing or stale (section 7), then ship (section 8). Make nothing new in that run.

   Then start the heartbeat in the background (`node scripts/claim.mjs keepalive`) and, for `make` and `resume`, the narration setup (`bash site/narration/setup.sh`, in the background; it takes a while and is needed only in section 7).
2. **The chapter plan is the contract.** For `make` and `resume`, `topic.chapter.plan` is the chapter's `CHAPTER.md` on `main`: this topic's entry there (scope, outcomes, concepts it introduces and uses, bridge, handoff, Prerequisites) is what it must deliver, and the neighbouring entries are what the topics around it deliver, being built at the same time. Never edit `CHAPTER.md`; if this topic truly can't keep to its entry, keep as close as it can, record why under `OUTLINE.md` → "Changes from the chapter plan", and say so in the report (the release seam check and the audit look for it). The JSON also describes the **previous** and **next** topics (status, id, branch, folder): read what exists of them (on `main`, or on their branch with `git show origin/<branch>:<folder>/<file>`) to match their style and wording, but build to the plan, not to their progress.
3. Read before writing anything (the parts, not whole files you won't use: the plan's named sections by heading, not all of `PROJECT_PLAN.md`; the previous topic's reel step titles, registry entry and Deep dive headings rather than every file in full): the plan's Core Rules (#1–#6), Learning design, Narration and Definition of Done; all of `QUALITY.md`; `DESIGN.md`; `CHAPTER.md` (all of it); the previous chapter's last topic and the topics of this chapter that already exist (registry entry, reel step titles, Deep dive headings, `REVIEW.md`); and the next topic's syllabus line.

## 1A. Plan a chapter (job `plan`)

A chapter plan lets every topic of the chapter be built at once without losing the thread, so it decides everything topics share and nothing they can decide alone. **The plan is pushed the moment it exists**, to its own branch `chapter.branch` (`plan/<domain-prefix>-ch<NN>`), and again after every change, so a run that dies (a usage limit) loses nothing: the next run continues from the branch. Only the reviewed plan goes to `main`, because topic runs start from what is on `main`.

0. **Start or continue.** `git fetch origin && git ls-remote --exit-code origin refs/heads/<chapter.branch>`. If the branch exists (a stopped run's draft), check it out (`git checkout -B <chapter.branch> origin/<chapter.branch>`) and continue: a last commit "reviewed" goes straight to step 4, any other to step 3. Otherwise `git checkout -B <chapter.branch> origin/main`.

1. **Inputs.** The JSON's `chapter` (number, title, the `plan` path, and every topic with its index, status, id and folder: use these ids and folders), the syllabus lines of the chapter's topics and of the first topic of the next chapter, `previousChapter.plan` and the previous chapter's topics as they really are (registry entries, reel step titles, Deep dive headings, `REVIEW.md`: all content-final by now), the plan's Core Rules, Learning design and Narration sections, `DESIGN.md`, and `QUALITY.md`. Topics of this chapter that are already live, held or in progress are fixed: plan around them (read their files or their branch's `OUTLINE.md`).
2. **Plan (Fable agent, effort high)** writes `CHAPTER.md` at `chapter.plan` and, **the moment the file is written, commits and pushes it** (`git add <plan> && git commit -m "Chapter <N> plan: draft" && node scripts/claim.mjs mine && git push -f origin HEAD:refs/heads/<chapter.branch>`; tell the agent exactly this; if `mine` fails, another run has taken the plan over: stop), then again after any later change. The plan:
   - **The chapter:** the problem it solves for the learner, the order of ideas and why, the notation, terms and running example every topic shares, and the one visual language the chapter's reels use.
   - **Each topic, in syllabus order:** title, id, folder, kind (full or refresher); **scope** (what it covers, clause by clause from its syllabus line, and what it leaves to which other topic: no overlap, no gap); learning outcomes; concepts it `introduces` and `uses` (ids, as the registry ledger uses them; a concept is used only after the topic or chapter that introduces it); its `bridge` from the topic before and `handoff` to the topic after (the last one hands off to the next chapter's first topic); its Prerequisites; its visual idea in a line; the primary sources it should start from.
3. **Plan review (an Opus agent, effort high)** checks it and lists every problem: a syllabus clause assigned to no topic or to two; a concept used before it is introduced (within the chapter and against the chapters before); a bridge that doesn't answer the handoff before it; scopes that overlap; inconsistent notation; anything an expert would find thin or wrong. Fix them all (the reviewer edits the file itself), then commit "Chapter <N> plan: reviewed" and push it to the branch at once, as in step 2.
4. **Publish.** Put the reviewed file on `main`: `git fetch origin && git checkout -B publish origin/main && git checkout <chapter.branch> -- <plan>`, commit "Plan <domain> chapter <N>: <title>", `node scripts/claim.mjs mine`, then `git push origin HEAD:main` (if rejected, `git pull --rebase origin main` and push again; it is a new file, so there is nothing to conflict). Then delete the branch (`git push origin --delete <chapter.branch>`) and `node scripts/claim.mjs done`.
5. **Finish.** The dispatcher starts the chapter's topics (ground rules, "Who starts the runs"). Finish the run (`run-metrics.mjs finish <domain> chapter-<NN> planned …`) and report.

## 2. Research and plan

1. Run the state-of-the-art scan and pick the primary sources (official docs, papers, source code, specs; the current version of each). Launch one Sonnet agent per source (all in one message, so they run in parallel) to fetch it with `scripts/sources.mjs fetch` and write its section of `SOURCES.md` in the format described at the top of that script: URL, version, every passage the topic could rely on as **verbatim quotes** copied from the fetched text, and the source's contents item by item (for the coverage map). Then run `node scripts/sources.mjs check <topic-folder>`; every quote must pass before planning starts. A source that can't be fetched (blocked, paywalled) is replaced by one that can, or its claims are dropped.
2. **Content plan (Fable agent, effort high).** Launch a Fable agent to plan the topic before anything is written. Give it the syllabus line, `SOURCES.md`, the plan's Core Rules, Learning design and Narration sections, `QUALITY.md`, `DESIGN.md`, the drawing kit (`site/src/reels/kit.tsx`), the previous topic's registry entry, reel, Deep dive headings and `REVIEW.md` (this topic must pick up exactly where its handoff leaves off, use only concepts it or earlier topics introduce, and not repeat the mistakes its reviews found), and the next topic's syllabus line. It may read a source itself where `SOURCES.md` is thin. It writes `OUTLINE.md` in the topic folder: the learning outcomes; the reel's steps in order, each with a **storyboard** to `DESIGN.md` (title; the visual idea for this concept and why it makes it click; what is on screen and where, in portrait first and then landscape; what moves on which beat; the real values shown; the final frame; the caption's point; every predict question with its answer and wrong options); the Deep dive headings with what each covers; the examples to execute and what each must assert; the bridge and handoff; the concept ledger (`introduces` / `uses`); and **the claims list**, every factual claim the topic will make with its source. Writing follows `OUTLINE.md`; a change of plan during writing is made in `OUTLINE.md` first, with the reason.
3. Launch an adversarial fact-check agent (Opus, effort high) on `OUTLINE.md` against the primary sources themselves (their fetched texts in `<topic>/sources/`, and further sources it fetches the same way), not only `SOURCES.md` (as in `site/src/topics/.../io-cost-model/FACT-CHECK.md`). It re-derives every claim from its source (a source it could not open doesn't count: find one it can open, or drop the claim; a book may be cited for framing next to an opened source), checks that each quote in `SOURCES.md` really supports the claim it is cited for (that the quotes are word for word is already proven by `sources.mjs check`), flags anything outdated, renamed or superseded (current version, quoted), and as red team tries to break each explanation and predict question with edge cases and counter-examples. Apply every correction, to `OUTLINE.md` too. It saves its result as the topic's `FACT-CHECK.md`.
4. **Coverage map** (plan, Rule #6), in the topic folder as `coverage.json` (follow the existing topics' maps; the format is described at the top of `site/src/lib/coverage.ts`):
   - `syllabus`: the topic's syllabus line split into clauses, copied word for word, together covering the whole line.
   - `sources`: the contents of at least two primary sources, item by item (from `SOURCES.md`).
   - `expert`: launch an independent Opus agent (in parallel with the content plan; it needs nothing from it) that has **not** seen your draft (forbid it from reading `site/`) to write a "what an expert must know" list for the syllabus line, each item with a primary source it has opened (`scripts/sources.mjs fetch`; never one cited from memory) and a placement (here / a named later syllabus topic / out of scope). Copy its items in.
   - Map every item to a planned reel step title, Deep dive heading, or another syllabus topic with a quote from its line that shows it covers it. Source and expert items may be marked `out` only with a reason. Anything that belongs here and isn't planned yet goes into `OUTLINE.md`.

## 3. Build the topic

Launch one **builder agent** (Sonnet) with the topic folder, `OUTLINE.md`, `FACT-CHECK.md`, `coverage.json`, `DESIGN.md`, `site/src/reels/kit.tsx` and the previous topic's folder as the pattern. It writes every file below, runs `npm run build` and `npm run test:examples` until both pass, commits, and returns a short summary (what it wrote, anything it couldn't follow in the plan and why). The folder and id are the ones `claim.mjs` gave in section 1 (`m<N>-<short-name>/ch<NN>-<short-name>/<topic-slug>` under `site/src/topics/<domain>/`); topic ids are permanent and prefixed by domain: `de.` Data Engineering, `dsa.` Data Structures & Algorithms, `rust.` Rust.

- `examples.py` or `examples.sh`: everything about real software behaviour, **executed**, with asserts for every number and output the reel shows.
- `reel.tsx` + `scenes.tsx`: the steps and their animations, every animation a pure function of time, built from the drawing kit and the shared components (`site/src/reels/`) to `DESIGN.md`. Refreshers: about 5 minutes, fast recap, at least one predict question, a recap step. Full topics: the plan's learning-design layers 1–4 and "Prove it" in the reel.
- `index.mdx`: the Deep dive (outcomes, internals, lab, production, frontier, sources with "last verified" and "Expert sign-off: pending").
- `prerequisites.mdx`: what the learner must already know, each item explained briefly with a self-check, plus resources. On-site reels use `<Resource kind="reel" host={props.host} …>`. Every outside link and its title, author and length is verified (YouTube via oEmbed, pages for a 200 and a matching title); unverified metadata is left out.
- `narration.json`: the spoken script, one line per sentence or phrase, written to be heard (see the plan's Narration section); an `answer` clip for every predict step; code and names spelled the way they are said.
- The registry entry in `site/src/topics/registry.ts`: `kind`, `introduces` / `uses` / `declared` (the concept ledger), a real `bridge` from the previous topic and `handoff` to the next, `status: 'live'`, or `'held'` if an earlier topic isn't live yet (normal when the topic before it is still being narrated or shipped by another run; a later run releases it).

## 4. Content review

Launch one **content review** agent (Fable, effort high) that has not written anything in this topic. Give it the previous topic (on `main`, or content-final on its branch), this topic's files (reel and scenes, narration, Deep dive, Prerequisites, registry entry, `coverage.json`, `SOURCES.md`, `FACT-CHECK.md`) and the next syllabus topic's line. It reads them in sequence once and appends to `REVIEW.md`, in three parts:

- **Flow:** anything abrupt, anything used before it is taught, any prerequisite that sits later in the syllabus.
- **Gap hunt:** everything missing, too thin, or wrongly marked as covered elsewhere, against the syllabus line, the sources and the expert list.
- **Expert reader:** anything imprecise, hand-wavy, or not at the depth the plan's Learning design asks for, as a sceptical senior engineer would judge it.

Fix everything it finds (with a fix agent for a large batch). A prerequisite later in the syllabus is a syllabus bug: reorder and log it in `syllabus/review-notes/`, but **never move a topic that is live, held or claimed** (`node scripts/claim.mjs status "<domain>"`): other runs are building on the order around it. If the fix needs that, log it for a human in `syllabus/review-notes/` and teach the missing piece here (`introduces`) meanwhile. Fill every real gap (or record why an item is out of scope), then record the review in `coverage.json` → `gapReview` (date, who, `open: []`). The build's flow and coverage checks must pass.

## 5. Checks and the looks review

From the repo root, run every check except narration (cheapest first, a timing summary at the end; it starts and stops `astro preview` itself):

```sh
node scripts/check-all.mjs --skip narration --changed     # docs, examples, sources, build, and the reels and links this branch affects
node scripts/check-all.mjs --only reels --topic <topic-slug>   # while fixing: just this topic's reel
```

`--changed` limits the reel and link checks to what the branch can affect against `origin/main` (`scripts/affected.mjs`): this topic, plus every reel when the branch touches shared code. Change shared code (`site/src/reels/`, `site/src/lib/`, components, tests) only when this topic truly needs it, keep it working for every existing topic, and expect the full reel test. It runs the same commands as CI, so nothing is weaker: `npm run build` (includes the flow, coverage, syllabus and topic-file checks), `npm run test:examples`, `npm run test:reels`, `npm run check:links`, `node scripts/check-docs.mjs`. The reel test also fails on text in a drawing that is clipped, overlaps or runs into other text, or is too small to read. A coverage failure means content is missing: write it, or point to the topic whose syllabus line truly covers it; never weaken the map to make it pass.

Then the **looks and learning review**: once the reels test is green, launch an Opus agent on this topic's screenshots in `site/test-results/` (every step, desktop and phone), with `OUTLINE.md`, `narration.json` and `DESIGN.md`. It judges each step as a demanding designer and teacher would, by the checklist in `DESIGN.md` → "The looks review checks", and appends its findings to `REVIEW.md`. Fix every finding (a fix agent for a large batch), re-run the affected checks, and look at the changed steps' new screenshots yourself. All of this section is green before going on.

## 6. Content final

Commit and push the branch, then run `node scripts/claim.mjs final`. Once every topic of the chapter is content-final, the next run (started by the dispatcher or the hourly schedule) plans the next chapter. **The content is now final:** change it only when a check or the narration forces it, and then add a line under `OUTLINE.md` → "Changes after final" (what changed and why) and push it, so the release seam check and the next chapter's plan can follow.

## 7. Narration (last)

Wait for the narration setup started in section 1 to finish (or run `site/narration/setup.sh` now; re-running skips what's done). Then from `site/`:

```sh
narration/narrate.sh src/topics/<domain>/<milestone>/<chapter>/<topic>
```

It restores the take cache from the `narration-cache` branch when it starts and saves it when it stops, so takes survive a fresh session or an interrupted run. Expect about 40–70 seconds per take on 4 CPU cores (a refresher is about 2 hours); wait for it as the ground rules say, never with the turn ended. If a line never passes the transcript check, rewrite the line (simpler words, spelled-out names), not the check; a rewritten line is a "Change after final" only if it changes what is taught.

As soon as it finishes, commit and push the audio (`site/public/audio/<topic-id>/`) with `narration.json`, then run `node scripts/check-all.mjs --only narration`.

## 8. Ship (then report and stop)

1. Go through `QUALITY.md` → "Before shipping any topic". If this run hit a new kind of problem, add a row with its fix and a guard (an automatic check where possible).
2. Other runs (this domain's and others') merge into `main` at the same time. So: `git fetch origin && git merge origin/main` into the topic branch, resolve conflicts (in `site/src/topics/registry.ts` keep **both** sides' entries).
3. **Continuity.** Check this topic still matches its `CHAPTER.md` entry (bridge, handoff, concepts, scope), and, where the previous topic exists, its real handoff and concepts (on `main`, or its branch's `OUTLINE.md` → "Changes after final" and "Changes from the chapter plan"); bring this topic's bridge, Prerequisites and `uses` in line. Set `status: 'live'` only if every earlier topic is live on `main`; otherwise `'held'` (the build's flow check enforces this; with topics built in parallel, most ship held). A held topic is released by a later run, which checks every seam again against the real topics on both sides.
4. Run `node scripts/check-all.mjs --changed`: every check, narration included, all green, on the merged branch.
5. Run `node scripts/claim.mjs mine`, then merge into `main`, push, and confirm the CI run for your push succeeds (on `main` every push gets its own run, testing the reels it affects) and that the site deployed (a Deploy run for your push, or a newer one that includes it, succeeded). If the push is rejected because `main` moved, repeat from step 2. If CI fails, fix it on the branch and push again; never leave `main` red.
6. Delete the topic branch and run `node scripts/claim.mjs done`.

## 9. Report

End the run with a short report for the owner:

- the domain and chapter, and the topic shipped (or resumed, or released) this run, with its live link, or, if it shipped held, which topic it waits for; how much of the chapter remains;
- what was verified and how (fact-check corrections, executed examples, measured results), and the main review findings;
- the run's ledger entry (what `run-metrics.mjs finish` printed: time, tokens per model, agents, checks, issues), and the stage that used the most;
- anything that needs a human: the narration to listen to (name two or three clips), and the expert sign-off still pending;
- if the run stopped early: the branch, the step it stopped at, and what remains.
