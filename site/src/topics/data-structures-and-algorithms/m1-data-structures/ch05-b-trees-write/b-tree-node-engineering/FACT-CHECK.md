## Red team

- **Edge case: does suffix truncation ever need to keep the whole key?** Yes, re-derived from the source's own statement — if no shorter prefix distinguishes the two split halves (e.g. the last left key and first right key share every attribute but the very last one), truncation keeps attributes up to and including the first point of difference; the README's own wording ("the remaining attributes must distinguish...") makes this the floor, not an optional shortcut. The reel's step 4 states this correctly as "keep only what still distinguishes," not "always drop to one byte."
- **Edge case: is suffix truncation ever applied to an inner-node split?** The source explicitly says it is *not*: "While it's not possible to correctly perform suffix truncation during internal page splits..." This topic's own claims list and reel are careful to scope suffix truncation to leaf splits only, matching the source precisely rather than over-generalizing to every split.
- **Predict-question distractor check (step 3, suffix truncation):** "the full key, unchanged" is the natural assumption from topic 26's own split mechanism, which never mentioned truncation; "nothing, routing entries store no key at all" overcorrects, since a routing entry still needs *some* key to route by; "a hash of the key" imports a different, unrelated technique (hashing breaks the ordering routing depends on).
- **Predict-question distractor check (step 6, bulk loading):** "insert one at a time" is the naive, slow baseline the source explicitly contrasts against; "build every level at once in parallel" overstates what the algorithm actually does (levels above the leaf are still built incrementally, just cheaply, as leaf pages fill); "it can't be done faster" is directly contradicted by the source's own claim.
- **Counter-example tried: is the bulk-load's right-most-path property still true after many splits at different levels?** Re-derived in `examples.py`: every split recorded during the bulk-load run is checked against the current rightmost node at its own level at the moment of the split, confirmed true for every split in the run, not just the first few.

## Claims not made (restated from OUTLINE.md, confirmed still out of scope)

- Bayer and Unterauer's full 1977 algorithm is named as suffix truncation's origin, not re-derived from the original 1977 paper itself (not fetched; PostgreSQL's own README is the primary source actually read and quoted).
- Posting-list compression is explicitly declined by PostgreSQL's own README for concurrency reasons; named in post-notes only, not claimed as how PostgreSQL's deduplication actually works.
- Unique-index deduplication (a separate section of the same README, with different goals from non-unique-index deduplication) is out of scope; only the non-unique-index case the syllabus names is covered.
