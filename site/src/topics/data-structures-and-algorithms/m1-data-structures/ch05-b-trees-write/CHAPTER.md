## The chapter

### The problem it solves

Chapter 1 named the cost that matters once data outgrows memory — not comparisons, but blocks moved — and stated the bound a good structure should hit: Θ(log_B N) I/Os per search. Chapter 4 built a tree that is optimal in *comparisons* but says nothing about *blocks*: a red-black tree's nodes are scattered across memory by pointer, so a single search can cost one disk I/O per edge, and its height is Θ(log₂ N) — fine in RAM, ruinous once N is "every row in the table" and B is "one 8 KB page." This chapter asks a different question: build a tree whose own node *is* a disk page, so one I/O reads not one key but B of them, and the tree's height — and so its I/O count — shrinks to Θ(log_B N), not Θ(log₂ N). A B-tree does this by construction (topic 26), but construction alone leaves bytes on the table — a slotted layout, prefix truncation and bulk loading (topic 27) are what make a real B+-tree's fanout B actually large instead of merely nonzero. The second half of the chapter asks what happens when the workload itself changes the trade-off: a B-tree pays its I/O cost on every write, in place, immediately; an LSM-tree defers that cost by never updating in place at all, writing sequentially and paying the cost back later, on its own schedule, as compaction (topics 28–29). The thread through this chapter is **the page, not the pointer**: every topic's mechanism exists because random access to a block is expensive and sequential access to many is cheap, and each topic is a different way of spending that one asymmetry.

### Order of ideas, and why

1. **§5.1 B-trees (26–27).** B-tree and B+-tree mechanics (26: fanout, splits, merges, all keys in the leaves with sibling links, the Θ(log_B N) bound itself) → B-tree node engineering (27: what it actually takes to make a real page hold a large, cache-friendly B — prefix/suffix truncation, key normalization, a slotted layout, fill factor, bulk loading, deduplication). 26 before 27 because 27's every technique is a refinement of a page that 26 must first define: you can't truncate a prefix or normalize a key before you know what a B-tree node holds and why its size is bounded by a disk page. Copy-on-write B-trees and the Linux maple tree are both skipped (see "Skipped in this chapter" below); the chapter keeps the mechanics every on-disk B+-tree needs regardless of its update strategy.
2. **§5.2 Write-optimized structures (28–29).** LSM-tree write and read paths (28: the WAL, the memtable, flushing to immutable sorted runs, and the read path that must now check several runs, newest first, with Bloom filters and fence pointers to avoid paying for most of them) → LSM compaction and amplification (29: what happens once those runs pile up — the compaction policies that bound how many runs a read must check, and the three amplification numbers, read/write/space, that every compaction policy is really trading against each other). 28 before 29 because 29's entire subject, compaction, exists only to fix a problem 28's own write path creates (ever-more immutable runs) — there is nothing to compact, or to measure amplification on, before 28 defines what gets written and in what shape. Bε-trees/fractal trees and learned indexes are both skipped; the chapter keeps the two-structure contrast (B-tree vs. LSM-tree) the syllabus's own Lab asks for, without the research-tier structures that generalize past it.
3. **Handoff to Chapter 6.** Topic 29 ends on the RUM trade-off — every write-optimized design trades read, write and space amplification against each other, and no policy minimizes all three — as the chapter's last word on "the page, not the pointer." Chapter 6 opens with binary heaps, a refresher: a much narrower structure, answering one question (what's smallest right now) with no claim at all about where its data physically sits.

### Shared notation and terms

- **Block / page / node, one thing:** this chapter's tree and LSM structures are built from disk pages, and a node *is* a page — defined once in topic 26, assumed by every topic after.
- **Fanout B:** the number of children a B-tree node can have (bounded by page size, not by a constant like a binary tree's 2) — defined in topic 26, the quantity topic 27's node-engineering techniques exist to make as large as possible without growing the page.
- **Height vs. I/O count:** Chapter 4 measured cost in comparisons; this chapter measures it in I/Os, one per block touched — carried over from `dsa.external-memory-i-o` (Ch.1 §1.3) and restated concretely for a B-tree's own height in topic 26.
- **In-place vs. log-structured update:** a B-tree updates a page in place, paying its I/O cost immediately on every write; an LSM-tree never updates in place, writing sequentially and deferring the cost to compaction — the one design choice topics 26–27 and 28–29 sit on opposite sides of, named explicitly in topic 28.
- **Amplification (write/read/space):** the three costs any write-optimized design trades against each other, named together once in topic 29 as the RUM trade-off, not assumed from memory of any one paper's own numbers.
- **Spoken numbers:** narration has no digits, symbols or code names (automatic check); say "order log base B of N", "fanout B", "write amplification", and add new terms the first time each appears (`fanout`, `split`, `merge`, `memtable`, `compaction`, `tombstone`, QUALITY.md #29).

The chapter builds from `site/src/reels/kit.tsx` and `DESIGN.md`'s briefing theme (PROJECT_PLAN.md, "Theme — briefing"): black and white carry everything, colour is rare and means something. On top of that this chapter shares one grammar:

- **Colour:** `crema` a page's own stored keys, as they are; `latte` secondary labels (a page's fill level, a run's sequence number, a filter's false-positive rate); `taupe` an empty slot or an unallocated page; `caramel` **the thing to look at**: the page about to split or merge, the run being compacted, the key range a fence pointer rules out; `cinnamon` (rare) **the alternative being compared**, always the same side of each pair: a B-tree's I/O count against Chapter 4's pointer-tree's comparison count (26), a B-tree's in-place write against an LSM-tree's sequential one (28); `cherry` with `cherryText` **the bad outcome**: a page overflowing before the split that should have already happened (26), a read that must check every run because no filter or fence pointer narrowed it (28), a compaction policy left to run unbounded until read amplification is unbounded too (29).

- **Write/read paths (28, 29):** a short vertical pipeline (WAL → memtable → flushed run → compacted run), with a read drawn as a `caramel` path that stops as soon as a Bloom filter or fence pointer rules a run out, shown as a short beat, not skipped.

### 26. B-tree and B+-tree mechanics (`dsa.b-tree-b-tree`): full, §5.1

### 27. B-tree node engineering (`dsa.b-tree-node-engineering`): full, §5.1

- **Folder:** `b-tree-node-engineering`. About 12 min.
- **Scope (syllabus clause → what it delivers):**
  - "prefix and suffix truncation, key normalization": storing only the part of a key that distinguishes it from its neighbours in a sorted node (prefix truncation) or from the node's own boundaries (suffix truncation), and converting a key to a byte-comparable fixed form so comparisons are cheap memcmp calls (normalization) — each verified against a current primary source (a database's own internals documentation or source).
  - "slotted node layout, fill factor": a page laid out as a slot directory (fixed-size pointers/offsets) pointing into a variable-length data area growing from the other end, letting keys and payloads vary in size without shifting every later entry on each insert; fill factor as the fraction of a page's capacity a build or rebalance target leaves used, trading some wasted space now for fewer splits later.
  - "bulk loading from sorted input, and deduplication of duplicate keys (PostgreSQL 13+)": building a B-tree bottom-up from already-sorted data in one pass instead of one-at-a-time inserts, far cheaper in I/Os; and the specific, dated optimization of deduplicating repeated keys within a leaf page rather than storing each occurrence in full, verified against PostgreSQL's own release notes or source at the stated version.
  - Leaves the tree's own split/merge mechanics to topic 26; this topic is entirely about what fits inside one node once the shape is already decided.
- **Outcomes:**
  - Explain prefix/suffix truncation and key normalization, and show the byte savings each gives on a real key set.
  - Lay out a page as a slot directory with a variable-length data area, and explain why this avoids shifting every entry on insert.
  - Bulk-load a B+-tree from sorted input and show it costs fewer I/Os than one-at-a-time insertion; explain PostgreSQL's duplicate-key deduplication and the version it shipped in.
- **Introduces:** `prefix-suffix-truncation`, `slotted-page-layout`, `bulk-loading`, `key-deduplication`. **Uses:** `b-tree`, `b-plus-tree`, `node-split-merge` (topic 26). **Declared:** `node-split-merge` (topic 26, restated as the operation bulk loading and deduplication are measured against).
- **Bridge:** "A B+-tree's height is bounded, but only if its nodes are actually full of keys, not full of wasted bytes. Node engineering: what it takes to make a real page hold as many keys as the hardware allows."
- **Handoff:** "Every technique so far still updates a page in place, paying its I/O cost immediately on every write. The next structure refuses that trade entirely: never update in place, write sequentially, and pay the cost back later, on its own schedule. LSM-trees, next."
- **Prerequisites panel:** topic 26 (Before this: what a B+-tree node holds and why its size is bounded by a disk page). On-site: none new.
- **Visual idea:** one page's slots shown twice, side by side — keys stored naively in `cinnamon`, the same keys with prefix truncation and normalization applied in `crema` with the bytes saved labelled in `latte`; a slot directory drawn as pointers into a growing data area; a bulk-load building a tree bottom-up in one pass next to a one-at-a-time insertion building the same tree, with an I/O-count comparison.

### 28. LSM-tree write and read paths (`dsa.lsm-tree-write-read`): full, §5.2

- **Folder:** `lsm-tree-write-read`. About 13 min.
- **Scope (syllabus clause → what it delivers):**
  - "WAL + memtable": every write appended to a write-ahead log for crash recovery, then applied to an in-memory sorted structure (the memtable) that serves recent reads and writes directly, verified against a current, well-documented LSM implementation's own design docs.
  - "flush to immutable sorted runs (SSTables)": once the memtable reaches a size threshold, it is written out as one immutable, sorted, on-disk run (an SSTable) and a fresh memtable takes over — no run, once flushed, is ever modified again.
  - "newest-first reads with Bloom filters and fence pointers, tombstones": a read must check the memtable, then each on-disk run from newest to oldest until it finds the key (newest wins, since a later write or delete shadows an earlier one); a Bloom filter per run lets most reads skip a run entirely without a false negative, and fence pointers (the key range, or a sparse index of boundary keys, each run stores) narrow which block of a run to check; a delete recorded as a tombstone marker rather than removing anything in place, since the run holding the old value is immutable.
  - Leaves what happens once runs accumulate — compaction, and the three amplification numbers that trade against each other — to topic 29.
- **Outcomes:**
  - Trace a write through the WAL, the memtable, and a flush to an immutable sorted run.
  - Trace a read that must check several runs newest-first, and show how a Bloom filter and a fence pointer each let it skip work.
  - Explain why a delete is recorded as a tombstone rather than an in-place removal, and what that implies until compaction runs.
- **Introduces:** `write-ahead-log`, `memtable`, `sstable`, `bloom-filter-pruning`, `fence-pointer`, `tombstone`. **Uses:** `b-tree`, `node-split-merge` (topic 26, as the in-place alternative this structure explicitly avoids). **Declared:** none new beyond its own.
- **Bridge:** word for word, topic 27's own handoff above ("Every technique so far still updates a page in place... LSM-trees, next.").
- **Handoff:** "Flushing a full memtable to its own run solves the write problem, but only by deferring it: every run flushed is one more run every read has to check, and one more copy of every key compaction will eventually have to rewrite. Compaction and amplification, next: what it costs to clean this up, and why no policy makes that cost disappear."
- **Prerequisites panel:** topic 26 (Before this: the in-place, page-based alternative this structure is built to avoid). On-site: none new.
- **Visual idea:** the log's on-disk index redrawn as a short vertical pipeline — writes landing in a WAL and a memtable, a flush sealing a shaded SSTable block below it; a read drawn as a `caramel` path checking the memtable, then each run newest-first, stopping early at a run a Bloom filter or fence pointer rules out (`cherry`-flagged near-miss where neither is available); a delete shown as a tombstone marker sitting over an unmodified older run.
- **Sources to start from:** a current, well-documented LSM-based storage engine's own design documentation (e.g. a current key-value store's or wide-column database's own internals docs) for the WAL/memtable/SSTable write path and the Bloom-filter/fence-pointer/tombstone read path, verified at research time.

### 29. LSM compaction and amplification (`dsa.lsm-compaction-amplification`): full, §5.2

- **Folder:** `lsm-compaction-amplification`. About 14 min.
- **Scope (syllabus clause → what it delivers):**
  - "leveled vs tiered vs hybrid compaction": the major compaction families — leveled (each level holds non-overlapping runs, merged into the next level once full, bounding read amplification tightly at the cost of more write amplification), tiered (several overlapping runs per level, merged together once a threshold count is reached, the opposite trade), and hybrid schemes combining both — each verified against a current primary source's own description, not a folklore summary.
  - "read, write and space amplification and the RUM trade-off (Athanassoulis et al., EDBT 2016)": the three costs defined precisely (read amplification: extra reads beyond the one logical read; write amplification: extra bytes written beyond the one logical write; space amplification: extra on-disk bytes beyond the live data's own size) and the RUM conjecture's own claim, verified against the cited paper directly, that no access method minimizes all three for every workload at once.
  - "Monkey (SIGMOD 2017) per-level filter sizing and Dostoevsky (SIGMOD 2018) lazy leveling": two specific, named research results that improve on naive leveled/tiered compaction — Monkey's result that a uniform Bloom-filter false-positive rate across levels is suboptimal and sizing filters per level by workload lowers read amplification at the same memory budget; Dostoevsky's lazy-leveling hybrid that tunes where on the tiered/leveled spectrum a system sits per workload — each verified against the cited paper's own stated result, not restated from a blog's paraphrase.
  - Closes the chapter: measures the three amplification numbers on one real compaction run, satisfying the syllabus's own Lab bullet's measurement requirement for the structures topics 26–28 already built.
- **Outcomes:**
  - Explain leveled, tiered and hybrid compaction and the read/write-amplification trade each one makes.
  - Define read, write and space amplification precisely and state the RUM trade-off's own claim.
  - Name Monkey's per-level filter-sizing result and Dostoevsky's lazy-leveling result, and what workload assumption each depends on.
- **Introduces:** `compaction-policy`, `read-write-space-amplification`, `rum-tradeoff`, `per-level-filter-sizing`. **Uses:** `sstable`, `bloom-filter-pruning`, `tombstone` (topic 28). **Declared:** `sstable` (topic 28, restated as the unit compaction merges and rewrites).
- **Bridge:** word for word, topic 28's own handoff above ("Flushing a full memtable to its own run solves the write problem, but only by deferring it... Compaction and amplification, next.").
- **Handoff:** "Every structure in this chapter optimized where data physically sits — on a page, in a run, across a level — to make a block of I/O count for as much work as possible. The next chapter asks a narrower question, answered the same way regardless of where anything sits: of everything not yet processed, which one is smallest, right now. Binary heaps, next."
- **Prerequisites panel:** topic 28 (Before this: the write path that creates the runs this topic compacts, and the read path whose cost compaction exists to bound). On-site: none new.
- **Visual idea:** several overlapping runs (tiered) merging into one wider, non-overlapping run one level down (leveled), drawn as the chapter's two-or-more-blocks-sweeping-together move; a three-bar chart (read/write/space amplification) measured on one real compaction run in `examples.py`, with the RUM triangle drawn as the shape no single point on it minimizes; a `latte`-labelled per-level filter size next to a flat, uniform one in `cinnamon` for the Monkey contrast.
- **Sources to start from:** a current, well-documented LSM-based storage engine's own documentation for leveled/tiered/hybrid compaction (verified at research time); Athanassoulis et al.'s RUM conjecture paper (EDBT 2016), the Monkey paper (SIGMOD 2017) and the Dostoevsky paper (SIGMOD 2018) directly, each quoted from the actual paper text, not a secondary summary.
