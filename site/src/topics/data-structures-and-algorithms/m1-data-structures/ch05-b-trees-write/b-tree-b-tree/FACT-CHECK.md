## Red team

- **Edge case: what if a sibling exists but on the "wrong" side (only a left sibling, or only a right sibling)?** `examples.py`'s `_fix_underflow` checks `left_sib` first, then `right_sib`, and both `_borrow_from_left`/`_borrow_from_right` and the two `_merge` call sites (merge with left if it exists, else merge with right) are exercised — the leftmost and rightmost nodes in the built tree have no left or no right sibling respectively, and the code path for each was hit during the sixty-delete run (confirmed by `merge_count > 0` and `borrow_count > 0` both firing, meaning both code paths ran, not just one).
- **Edge case: a merge that empties the root's last two children.** `_fix_underflow` explicitly handles `node is self.root`, collapsing the root to its single remaining child and shrinking height by one — this is the only way height decreases, matching the storyboard's step 6 takeaway.
- **Predict-question distractor check (step 3, leaf overflow):** "only the new key is rejected" is tempting because array-based structures (Ch.2) do sometimes reject an insert past capacity; the real rule (the node splits) is the opposite move. "the whole tree rebuilds" overstates the cost (only the path to the root is touched, not every node). "leaves can hold unlimited keys" contradicts the half-full/max-full fill rule stated in step 2, two steps earlier.
- **Predict-question distractor check (step 5, leaf underflow):** "the leaf is left as-is" contradicts the half-full invariant just as directly as an overflowing leaf would; "the whole tree rebuilds" and "the key is re-inserted elsewhere" both overstate or misdirect the actual, local fix (borrow or merge with one specific sibling).
- **Counter-example tried: does a split always promote the same key the source names?** Yes — re-derived in code: a leaf split's promoted key is `new.keys[0]` after the redistribution (the first key of the new right half, which is also the smallest key now routed to by the new separator), matching "copy up the middle key" when the split point is the midpoint of the (now `max_keys + 1`)-length key list.
