## The chapter

### The problem it solves

A search engine, an OLAP engine and a graph store all hold one kind of data in enormous quantities: **sets of integers** (the ids of the rows that match a predicate; the documents that contain a term; a vertex's neighbours). A set of 10⁶ ids drawn from a universe of 2³² costs 512 MiB as a plain bitmap and 4 MB as a plain sorted array, and neither is right for every list: the bitmap is wasteful for a sparse set and unbeatable for a dense one; the array is the reverse. The queries are intersections and unions of several such sets, and the time budget is the memory bandwidth. This chapter keeps the syllabus's two practical answers and drops its theory (persistence, succinct rank/select, Elias–Fano, wavelet trees, succinct trees are all marked *(skipped)*, and the chapter's own title promises them: see the note at the end). **Compressed bitmaps: Roaring** (topic 43) answers "which representation, for which part of the set?" by choosing **per chunk of 65,536 values** between a sorted array, a bitmap and runs, so the set is never bigger than its densest honest encoding and intersection is chunk-by-chunk. **Integer compression** (topic 44) answers the other half: given a sorted list of integers that *is* the representation (a posting list, a column page, an SSTable index), how few bits per integer can it take, and how fast can it be decoded: varint, delta and frame-of-reference coding, patching, SIMD bit-packing and Stream VByte. The thread is **bits per integer against decode speed**, and the lesson (both topics prove it, from different directions) is that the winner is the one that spends the fewest *instructions* per integer, not the fewest bytes.

### Order of ideas, and why

1. **§13.2 Compressed bitmaps: Roaring (43).** First, because the structure is the clearer one: it shows the whole trade (dense versus sparse versus clustered) with three containers, and it returns to the chapter's question from Chapter 12's handoff: an *exact* set, no false answers, fast set algebra. Its array container is a sorted list of integers, which is topic 44's subject.
2. **§13.2 Integer compression (44).** Second, because it goes inside the sorted list: varint, then the delta and frame-of-reference ideas that shrink a list of ids to a list of small numbers, then patching, SIMD packing and Stream VByte as the same ideas made fast. It closes with the one comparison the syllabus's lab asks for (bits per element, intersection speed, random access), which needs topic 43's Roaring to compare against.
3. **Handoff to Chapter 14.** Topic 44 ends on an observation that is true of every structure in this chapter: a compressed posting list is *immutable*, which is why many readers can decode it at once with no coordination at all. That is the exception. The first time two threads write the same structure, the question stops being speed and becomes what "correct" means. Chapter 14 opens with progress guarantees and linearizability.

### One running example: a log's own posting lists

Earlier chapters used the log's own records. This chapter treats the log as a **table of N records with a 32-bit row id each**, and each *predicate* (`level = ERROR`, `service = auth`, `hour = 13`) as the **set of row ids that match it**. Topic 43 intersects three such sets (the query `level = ERROR AND service = auth AND hour = 13`); topic 44 compresses one such set stored as a sorted list (a posting list). Every number on screen is computed or asserted in each topic's own `examples.py`; the values below are planning values (arithmetic was done at planning time with Python), and a builder who finds one wrong fixes it there and records it in `REVIEW.md`.

### Shared notation and terms

- **Set of integers, universe u, cardinality n; chunk, container, key** (Roaring's names, written as the Roaring papers write them). **Run** (maximal sequence of consecutive values) and **run length**; **gap** (difference between consecutive sorted ids; the survey and papers call it a delta); **bits per integer** (the unit of every size in topic 44), written `bits/int`.
- **Block** (a fixed group of integers coded together, 128 in the papers' fastest scheme) and **bit width** b (bits used per value in a block). **Frame of reference** (FOR), **patched FOR** (PFOR), **exception** (a value too large for the block's bit width, stored aside), **control stream** and **data stream** (Stream VByte's two byte streams). Written as the papers write them.
- **Decode speed** is reported as nanoseconds per integer or integers per second *on the recorded machine*, never as a bare ratio; the machine is named in `OUTLINE.md` (CPU, SIMD level, compiler flags).
- **Spoken numbers:** narration has no digits, symbols or code names (automatic check). Say "sixty five thousand five hundred and thirty six", "four thousand and ninety six", "bits per integer", "variable byte", "frame of reference", "patched frame of reference", "continuation bit", "control byte"; speak every number in words (QUALITY.md #29). Library and class names (CRoaring, RoaringBitmap, FastPFor) are not spoken.

### 43. Compressed bitmaps: Roaring (`dsa.compressed-bitmaps-roaring`): full, §13.2

### 44. Integer compression (`dsa.integer-compression`): full, §13.2

- **Folder:** `integer-compression`. About 15 min. Hosts the chapter's lab.
- **Scope (syllabus clause → what it delivers):**
  - "varint/LEB128": the variable-byte idea: 7 payload bits per byte and the most significant bit as a continuation flag, least-significant group first (Protocol Buffers' varint, with the documentation's worked example: 1 is the single byte `01`, 150 is `96 01`; the WebAssembly specification's LEB128 for integers, "in either unsigned or signed variant", with the constraint that a u*N* value takes at most ceil(N/7) bytes, both read at planning time); the sizes (1 byte below 128, 2 below 16,384, …); the decode loop and its cost (a data-dependent branch per byte: Chapter 1's branch misprediction); the signed variant named, and how a signed value is mapped (the zigzag mapping in Protobuf's "Signed Integers" section is **to verify** before it is said).
  - "frame-of-reference": delta coding first: a sorted list becomes gaps (non-negative integers, "typically much smaller than the original" as the SIMD paper puts it), decoded by a prefix sum (Chapter 8's prefix-sum idea), with the stated cost that the prefix sum is a serial dependency and the usual remedy of partitioning a large array into blocks (Lemire and Boytsov); then frame of reference: partition into blocks, store the block's minimum (or the range) once and each value as an offset in ⌈log₂(range)⌉ bits (the paper's example: values in [1000, 1127] take 7 bits each), the idea attributed to Goldstein, Ramakrishnan and Shaft, "Compressing relations and indexes" (ICDE 1998, as the SIMD paper cites it); why one outlier forces the whole block to a wide width.
  - "PFOR": patching: pick a small bit width b for the block, store the values that do not fit (**exceptions**) in a separate location, and patch them back after unpacking; attributed to Zukowski, Héman, Nes and Boncz, "Super-scalar RAM-CPU cache compression" (ICDE 2006: title and venue checked, the paper's own text **not read**: attribute only what the Lemire–Boytsov paper says it proposed); the variants NewPFD and OptPFD (Yan et al. 2009, named as the SIMD paper names them) and what patching buys (the paper's table for the GOV2 collection: binary packing at 5.5 bits/int, SIMD-BP128 at 6.3, OptPFD at 4.5, read at planning time; the topic recomputes its own on the chapter's list and treats the paper's as context, with the dataset named).
  - "SIMD bit-packing": pack and unpack blocks of integers at a fixed bit width with vector instructions: SIMD-BP128 ("nearly twice as fast as the previously fastest schemes on desktop processors (varint-G8IU and PFOR)" and "saves up to 2 bits per integer", blocks of 128 integers, from Lemire and Boytsov, *Software: Practice and Experience* 45(1), 2015), SIMD-FastPFOR ("a compression ratio within 10% of a state-of-the-art scheme"); the layout that lets one instruction handle several lanes at once is **to verify in the paper** before it is drawn; the FastPFor library's own statement that SIMD compression does not need very large blocks (its fastest scheme works over blocks of 128 integers, read from its README).
  - "Stream VByte": the idea in two steps: Varint-GB (Google) groups four integers under one control byte holding four 2-bit byte lengths, so one control byte is processed per four integers and "this block-based design can reduce the number of branch mispredictions by a factor of four" (the Stream VByte paper); Stream VByte moves **all** control bytes into a separate **control stream** so the data stream is read without interleaved control bytes, which suits SIMD (paper: "separates the control stream from the encoded data", "up to twice as fast as VARINT-G8IU decoding over real data sets", and on a 3.4 GHz Haswell it "decodes more than 4 billion differentially-coded integers per second from RAM to L1 cache": the machine is part of the quotation); the decode mechanism (a shuffle driven by the control byte) is **to verify in the paper** before it is drawn; Amazon's varint-G8IU is named as the previous fastest byte-oriented scheme (the paper says it is patented; the topic repeats nothing about patents beyond the paper's own sentence).
  - "decode speed vs ratio for posting lists and columnar pages": the measured table on the chapter's list: bits per integer for varint on gaps, a Varint-GB-style grouped byte code, bit-packed FOR, and patched FOR (all computable exactly in `examples.py`, in pure Python, with the floor from the counting bound beside them); decode **speed** is the one number pure Python cannot give honestly (interpreter overhead hides the instruction counts the topic is about): it is shown only from a compiled micro-benchmark whose output `examples.py` records (the machine, compiler and flags named, the library versions pinned) or from the papers' own tables with their hardware, never from a Python timing. Real instances: Lucene's postings format as the posting-list case (the codec's own documentation, read at planning time for the 9.x `Lucene99PostingsFormat`: postings in packed blocks of integers "encoded with the same bit width", block size "currently 128", with variable-length VInt blocks for the tail, the frequency blocks "uses patching" and the document-delta blocks "does not use patching": the current version is re-read at research time, since the name changes with each Lucene format) and Parquet's `DELTA_BINARY_PACKED` and RLE/bit-packing hybrid (Parquet's `Encodings.md`, read at planning time for the encoding names and which types they apply to) as the columnar-page case.

- **Hook:** a posting list of 2²⁰ (about a million) document ids, in order, is four mebibytes as 32-bit integers. The ids are on average 4,096 apart in a universe of four billion, and the counting floor for the whole list is 13.4 bits per id (computed exactly: 13.44), so no encoding can average fewer, over all such lists. Plain varint on gaps with that mean (drawn at random, as the planning run did: exponential gaps of mean 4,096) spends about 15.9 bits per id, because it rounds every gap up to whole bytes; packing blocks of 128 at the widest gap in each block spends about 15 (planning values, rechecked by the builder on its own list). Which of these decodes fastest? Not necessarily the smallest: decoders are bounded by instructions and branches per integer, not by bytes. Predict how many bits per integer plain varint spends, and whether the fastest scheme is the smallest.
