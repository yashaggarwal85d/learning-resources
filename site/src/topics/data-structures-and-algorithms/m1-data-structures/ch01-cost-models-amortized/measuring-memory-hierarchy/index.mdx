## After this topic you can

- Build a pointer-chasing benchmark that really measures load latency, and read the size of each cache level and the DRAM latency off its staircase.
- Find the cache-line size and the TLB reach with a strided-access benchmark, and say why a prefetcher can hide the knee you are looking for.
- Tell prefetching apart from a cache hit in a measurement, by comparing a sequential walk against a random one.
- Map a measured plateau and its knee back to the **M** and **B** of the I/O and ideal-cache models at that level.
- Reconcile a measured growth or shrink policy with its potential-function proof, and explain exactly where wall-clock time and the count of element copies disagree.

## Into the internals

### Why the models need a ruler

The last two topics took the two numbers of a memory level as given: **M**, the items that fit in the fast level, and **B**, the items in one block. The external-memory model charged one block transfer of B items; the ideal-cache model let an algorithm be optimal for every unknown B and M at once. Both are hypotheses about a machine. This topic measures the machine, so that the models stand on numbers you have seen rather than numbers you were told.

A real core has not one fast level but a staircase of them: a few register files, an L1 data cache, an L2 cache, usually a shared L3, main memory (DRAM), and, through virtual memory, a cache of address translations (the TLB). Each level is larger and slower than the one above it. The chapter's running example — **the vector** of 64-bit keys, **w = 64**, universe **U = 2⁶⁴** — is just a contiguous array of items, so where its working set lands on that staircase decides what a single `a[i]` load costs, anywhere from under a nanosecond to a trip across the whole hierarchy. The word-RAM charged one unit for that load (topic 2 named the gap; here we price it).

We measure two things and read a third from them:

| What | Microbenchmark | What it exposes |
|---|---|---|
| Load latency vs working-set size | pointer chasing | the capacity of each cache level, and the latency plateau of each level and of DRAM |
| Cost vs access stride | strided access | the cache-line size B, the TLB reach, and the prefetchers |
| The latency staircase | reading the two curves together | M and B at every level of this machine |

Every number a build puts on screen is one measured run on one named machine (CPU model, compiler, flags and date recorded with it); the **shape** of the staircase transfers to other machines, the **numbers do not**. Order-of-magnitude anchors below are cited; machine-specific values are marked **(measure in build)**.

### The pointer-chasing benchmark

To measure the latency of *one* load — the time from issuing it to having its result — you must stop the core from doing anything else in the meantime. A modern out-of-order core will happily run dozens of independent loads at once, so a loop over `sum += a[i]` measures throughput, not latency: the misses overlap. The fix, which goes back to lmbench's memory-latency benchmark (McVoy and Staelin, 1996), is to make each load depend on the result of the last:

```c
// A working set of `n` slots, each holding the index of the next slot to visit.
// The loop cannot start load k+1 until load k has returned: no overlap.
size_t p = 0;
for (long i = 0; i < iters; i++)
    p = next[p];
sink = p;               // keep the compiler from deleting the chain
```

lmbench calls the quantity this measures the **back-to-back-load latency**: "the time that each load takes, assuming that the instructions before and after are also cache-missing loads." Divide the loop's wall time by `iters` and you have nanoseconds per dependent load at that working-set size. Sweep the size from a few kilobytes to several times the last-level cache and the curve is the **latency staircase**.

Five details are the difference between measuring memory and measuring a mistake:

- **Dependence.** `p = next[p]` carries a true data dependency, so load *k + 1* cannot be issued until load *k* retires. Without it the core overlaps misses and you measure bandwidth.
- **A single cycle.** The `next` array must be *one* permutation cycle of length `n`, visiting every slot exactly once before returning to the start. If it split into several short cycles the walk would revisit a small set that fits in cache and under-report latency. Build the cycle with **Sattolo's algorithm** (Sattolo, 1986), a one-line variant of Fisher–Yates whose only change — drawing each swap partner from strictly *below* the current index — guarantees a single cycle of full length:

  ```c
  // Sattolo: produce one cycle of length n in `next` (indices 0..n-1).
  for (size_t i = 0; i < n; i++) next[i] = i;
  for (size_t i = n - 1; i > 0; i--) {
      size_t j = rand_below(i);     // 0 <= j < i   (strictly below i)
      swap(&next[i], &next[j]);
  }
  ```

- **A random order.** A cycle laid out in address order would let the hardware prefetcher predict the next load and hide the latency (that is exactly the effect we measure separately, below). A random single cycle defeats prediction, so each load that misses pays the full latency of its level.
- **Enough iterations and a warm-up.** Run the chain long enough to dwarf the loop overhead and to let the clock settle; discard a warm-up pass so the first (cold) traversal does not pollute the steady-state figure.
- **A fixed frequency.** Turn off frequency scaling and turbo for the run (or report the governor), because nanoseconds per load are meaningless if the clock is moving under you.

Read down the curve and each flat run is a level whose working set still fits:

| Working-set regime | Typical latency, order of magnitude | What the plateau is |
|---|---|---|
| ≲ L1 data cache | ~1 ns (a few cycles) | L1 hit |
| ≲ L2 cache | a few ns | L2 hit |
| ≲ L3 cache | ~10 ns | L3 hit |
| > L3 (DRAM) | ~50–100 ns | DRAM access |

The DRAM anchor (~50–100 ns) and the sub-nanosecond L1 anchor are the widely used order-of-magnitude figures (Drepper, 2007; Norvig's latency table); the exact plateau heights and the working-set size at each knee are **(measure in build)**. The capacity of a cache level is read off the staircase as the working-set size at which the latency climbs to the next plateau.

### The strided-access benchmark

The pointer chase finds the *capacities*; a strided sweep finds the *block size*. Walk a working set larger than the cache, touching one item every `stride` bytes, and measure the average cost per access as you grow the stride. The method is Saavedra and Smith's (1995). The reasoning is pure I/O model:

- When the stride is **smaller than a cache line** (B bytes), several of your accesses fall inside the same line, so one line transfer serves them all and the amortised cost per access is low.
- Once the stride **reaches the line size**, every access touches a fresh line — one transfer per access — and the cost per access stops rising.

So the cost-per-access curve climbs and then flattens, and **the stride at the knee is the cache-line size B.** For the running example a 64-byte line holds **B = 8 keys** (eight 8-byte words); that is the value topics 8 and 9 used at the cache level, and the measurement is how you confirm it on a given machine rather than assuming it.

**The caveat you must show, not hide.** On current cores a hardware prefetcher can flatten or move this knee. Intel cores, for instance, run several prefetchers; the *spatial* (adjacent-cache-line) prefetcher pulls in the 128-byte-aligned pair of the line you touched, which can make the line look 128 bytes wide in a naive stride sweep (Intel 64 and IA-32 Architectures Optimization Reference Manual; Agner Fog's microarchitecture guide). Two honest responses:

- Visit the strided addresses in a **random order** (a Sattolo cycle again) so the prefetcher cannot predict the stream, which recovers the true line size; or
- Report the knee **with the caveat**, naming which prefetchers the recorded CPU documents.

Which prefetchers a given CPU has, and whether they can be disabled, is cited from that CPU vendor's documentation — not assumed.

### The TLB and TLB reach

Virtual memory hands each process its own address space, carved into fixed-size **pages** (4 KiB on x86-64 by default). Every memory access first translates its virtual page to a physical one, and that translation is itself cached, in the **translation lookaside buffer (TLB)** — a small, fast cache of recent page translations. A TLB miss is a second kind of miss, independent of the data caches: the data can be in L1 while its translation is not in the TLB.

The quantity that matters is the **TLB reach**: the amount of memory the TLB can map without a miss,

> TLB reach = (number of TLB entries) × (page size).

Extend the strided sweep to **page-sized strides over many pages** and a second staircase appears: once the working set spans more pages than the TLB has entries, each access pays a TLB miss (a page walk) on top of its data-cache cost, and the latency steps up again. Larger pages trade granularity for reach: a 2 MiB huge page, the common huge-page size x86-64 Linux supports (the kernel documentation notes valid and default huge-page sizes are architecture- and configuration-dependent, not fixed at 2 MiB everywhere), is 512× a 4 KiB page, so the same number of TLB entries reaches 512× as much memory — which is why huge pages often help pointer-heavy, large-footprint workloads. The entry counts (and separate instruction/data and multi-level TLBs) are machine-specific and read from the vendor's documentation; the *reach* step in the staircase is **(measure in build)**.

### Prefetchers, told apart from cache hits

A prefetcher brings a line into cache *before* the program asks for it, by predicting the access pattern. In a latency curve a prefetched line looks exactly like a cache hit — low latency — even though the data was in DRAM. The way to tell them apart is to measure the same working set two ways:

- **Sequential order** (addresses increasing by one line): the stream prefetcher learns the pattern and the latency stays low even when the working set is far larger than the last-level cache.
- **Random order** (the Sattolo single cycle): the prefetcher cannot predict the next line, so the latency climbs the full staircase.

Drawn together, the sequential curve stays flat and low where the random curve climbs: the gap between them *is* the prefetcher's contribution, and nothing else. A finer test pits a **constant stride the prefetcher can learn** against **a stride (or a random cycle) it cannot**: the learnable one is served ahead of time, the other pays in full. This is also the honest reason the latency benchmark must use a random cycle: a sequential chain would measure the prefetcher, not the memory.

### Reading the latency staircase

Put the pieces together and the random-order curve, plotted with the working-set size on a log₂ axis (4 KiB … 1 GiB) and latency on a log axis with decade ticks, is a staircase:

- **Plateaus** are levels: L1, L2, L3, DRAM, each flat run a level whose working set still fits.
- **Knees** are capacities: the working-set size where latency climbs is that level's size M.
- **The TLB step** appears where the footprint outgrows the TLB reach, independent of the data-cache knees.
- **Knees are soft, not sharp.** Set associativity means a level fills before its nominal capacity; a shared L3 is contended by other cores; other processes and the operating system perturb the run. Report a distribution, not a single number, and quote tail percentiles — **p50, p99, p99.9** (topic 7) — because the tail is what a latency-sensitive service feels.

Mapping back to the models closes the chapter: each plateau's capacity is an **M** and each line size is a **B**, and the fact that one cache-oblivious algorithm is optimal at *every* one of these levels at once (**multilevel-optimality**, topic 9) is why the model was worth stating before the staircase was measured.

### Where the number of copies and the clock disagree

Topics 5 and 6 counted the vector's cost in **element writes**: an append without a resize costs 1; an append that resizes a vector holding n elements costs n + 1; the amortized bound is O(1) per append for the doubling rule. Those proofs are about *counts*. The staircase is about *time*. The last section of the lab reconciles them, and the interesting part is where they disagree:

- The count of copies for a million appends with **g = 2** is **2²⁰ − 1 = 1,048,575** (20 resizes, the last copying 524,288), so **≈ 1.05 copies per append**, not 2 — the amortized bound g/(g − 1) = 2 is only reached just after a resize (the sawtooth of topic 5).
- But each resize copies a *contiguous* run, which the prefetcher streams at bandwidth, so its **time per element** is far below a random pointer chase at the same footprint. A resize that spills from one cache level to the next shows up as a step in time-per-append even though the copy count is smooth. That step is the staircase reasserting itself inside the amortized proof — the count is right, and the clock adds the hierarchy the count ignores.

## Build, break, measure

This is the chapter's one human lab (syllabus §1.3). It runs locally in one sitting. Measured numbers vary by machine; the **shape** of each result is the thing to reproduce. Record the machine, CPU model, compiler and flags, and the date with the data. Parts 2 and 3 use the growth and shrink rules exactly as the chapter's running example defines them, and reconcile against the predictions from topics 5 and 6 (their `examples.py` count the element writes for each policy).

### Part 1 · Plot latency vs working-set size (pointer chasing)

A small C program. Allocate a working set of `n` 8-byte slots; fill `next` with **one** random cycle using Sattolo's algorithm; walk `p = next[p]` for enough iterations; divide wall time by iterations. Sweep `n` so the footprint runs from **4 KiB to at least 4× the last-level cache** (through 1 GiB on a typical desktop), doubling each step. Pin the frequency, discard a warm-up pass, and record ns per load.

- **Expected shape:** a staircase — flat at ~1 ns inside L1, stepping up at each cache capacity, reaching the DRAM plateau (~50–100 ns order of magnitude) beyond the last-level cache. The working-set size at each knee is that level's size.
- **Then the strided sweep:** touch one item every `stride` bytes over a set larger than the cache; grow the stride; the cost-per-access curve climbs and flattens at the **cache-line size** (expect 64 bytes = **B = 8 keys**, to confirm). Extend to page-sized strides over many pages to find the **TLB-reach** step.

**Break it.** Walk the cycle in **sequential** address order instead of random: the staircase collapses toward the L1 plateau because the prefetcher now predicts every load — proof that the random cycle was doing real work. Then disable turbo versus leaving it on, and watch the plateaus shift: a reminder that nanoseconds are meaningless without a fixed clock.

### Part 2 · Doubling vs 1.5× dynamic array

Append `n` keys (up to the large vector, **n = 1,000,000**) to a vector that grows by **g = 2** and to one that grows by **g = 1.5**. Record total element copies and time per append.

- **Prediction (topic 5):** copies per append are bounded by about **g/(g − 1)** — 2 for g = 2, 3 for g = 1.5 — and reached only just after a resize; just before one they fall to about **1/(g − 1)**. For a million appends with g = 2 the total is **1,048,575** copies (**≈ 1.05 per append**), over 20 resizes, the last copying 524,288.
- **Expected shape:** the measured copy count matches the prediction to the element; time per append is a flat line with spikes at the 20 (resp. ~34 for g = 1.5) resizes, each spike's height set by how far down the staircase its copy reached.

**Break it.** `reserve` the final capacity up front: all copies vanish and time per append drops to the no-resize floor — isolating the resize cost from the write cost.

### Part 3 · Shrink-at-½ vs shrink-at-¼ under the adversarial sequence

Run the chapter's adversarial push/pop sequence: fill the vector until **n = cap = C** (a power of two; C = 16 in the reel, larger here), push once, then repeat **(pop, pop, push, push)**. Run it under **shrink-at-½** (halve when a pop leaves it < ½ full) and under **shrink-at-¼** (halve when a pop leaves it < ¼ full). Record copies and time per operation.

- **Prediction (topic 6):** under shrink-at-½ every second operation of the repeat resizes and copies about C elements; when C grows with the number of operations n (fill with ~n/2 pushes first) the whole sequence is **Θ(n²)** — the thrash. Under shrink-at-¼ nothing resizes after the first grow, because the vector is about half full just after every resize, so Ω(cap) operations must pass before the next: **O(1) amortized** per operation (**resize hysteresis**). Note that strict push/pop *alternation* does **not** thrash under the strict "less than half" rule.
- **Expected shape:** shrink-at-½ draws a row of cherry spikes, one every second operation; shrink-at-¼ is flat.

### Part 4 · Reconcile with the potential-function proof

Take topic 6's potential for the expand/contract table (Φ built from the load factor **α = n / cap**, charging distance from α = ½; Φ(D₀) = 0, Φ ≥ 0). Sum the amortized costs **Σĉᵢ = Σcᵢ + Φ(D_last) − Φ(D₀)** and compare against the **measured** total element copies **Σcᵢ**.

- The copy count must agree with Σcᵢ exactly (the proof is about counts).
- Where **wall-clock time** diverges from the copy count, explain it with Part 1's staircase: a resize that spills into a slower level costs more nanoseconds per copied element than one that stays in cache, even though every copy counts as 1 in the proof. The potential method bounds the *work*; the staircase prices it.

## In production

A review checklist for anyone who puts a memory-latency number in a design doc or a benchmark:

- **Did the latency benchmark actually serialise the loads?** If each load does not depend on the last (`p = next[p]`), you measured bandwidth, not latency, and the number is too low by the core's memory-level parallelism (often 10× or more).
- **Is the walk one random cycle?** Multiple short cycles revisit a cache-resident set and under-report; a sequential cycle measures the prefetcher. Use Sattolo's algorithm and verify the cycle length is `n`.
- **Was the clock pinned?** Turbo and frequency scaling move the plateaus. Report the governor and frequency, or disable scaling for the run.
- **Are you reporting a distribution?** Caches are shared and associative, and the OS schedules other work; a single mean hides the tail. Quote p50, p99 and p99.9, and say how many samples.
- **Did a prefetcher flatten the knee you report?** If a stride sweep says the line is 128 bytes, suspect the adjacent-line prefetcher; re-run in random order or name the prefetcher and its documentation.
- **Did you separate the TLB from the data caches?** A footprint that fits in L3 can still miss the TLB. If latency steps up where the data should fit, test page-sized strides and consider huge pages.
- **When you cite copies, cite time too.** Amortized O(1) is a count; a service feels nanoseconds. A doubling array's ~1.05 copies per append at a million elements can still stall a request on the one resize that copies half a million elements into cold memory — which is why topic 7 deamortizes it.
- **The shape transfers; the numbers do not.** Re-measure on the target hardware before trusting any absolute figure in a capacity plan.
