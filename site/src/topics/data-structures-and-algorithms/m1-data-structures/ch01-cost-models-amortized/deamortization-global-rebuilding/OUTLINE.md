- **Percentiles (introduced here):** nearest rank. Said in the reel as "the cost that 99 of every 100 stay at or under".
- **The incremental vector (the design every number below uses; builder: implement exactly this):**
  - State: `buf` (current buffer, capacity `cap`), `old` (the previous buffer, or none), `m` (how many old keys must move), `k` (the **frontier**: old indices `< k` have moved), `n`.
  - **Append x:** if `n == cap`: if `cap == 0`, allocate 1 slot (no migration); else start a migration: `old = buf`, `m = n`, `k = 0`, `buf =` a new buffer of `2·cap` slots, `cap = 2·cap`. Then `buf[n] = x`, `n += 1`, then **move up to 2**: while fewer than 2 moved and `k < min(m, n)`: `buf[k] = old[k]`, `k += 1`. When `k ≥ min(m, n)` the migration ends and `old` is freed.
  - **Read get(i) / write set(i, x)** (0 ≤ i < n): the old buffer if a migration is running and `k ≤ i < m`, else `buf`. (`set` must follow the same rule, or a later move overwrites the new value.)
  - **Pop:** `n −= 1`; if migrating, `m = min(m, n)` (popped old keys need not move); move up to 2. Then, if no migration is running and `n < cap/4` (shrink-at-¼): if `n == 0` free the buffer (cap 0), else start a migration into a buffer of `cap/2` slots (`m = n`, `k = 0`) and move up to 2.
  - **Cost:** 1 + keys moved: at most **3 writes per operation**, always. Proved in the Deep dive and checked exhaustively (every state reachable from empty up to capacity 256: 17,570 states) and on random sequences: no grow or shrink is ever triggered while a migration runs, so at most two buffers exist.
  - **Space:** during a migration both buffers are alive: at the last resize of a million appends (c = 524,288) that is 524,288 + 1,048,576 = 1,572,864 slots, 12 MiB of 8-byte keys, for 262,144 appends. The plain vector also holds both (3c slots) while it copies, but only during that one append.

## Learning outcomes

As CHAPTER.md lists them, made concrete:

1. **Deamortize a doubling array with incremental copying and state its worst-case cost and space overhead:** two buffers and a frontier k; every append writes its key and moves 2 old keys, so the copy of c keys finishes after c/2 appends, at n = 1.5c, with a quarter of the new buffer to spare; every append costs at most 3 writes (with pops and shrink-at-¼ too); reads pick the buffer by `k ≤ i < m`; the total work is unchanged (31 writes for 16 appends, 2,048,575 for a million), the median append rises from 1 to 3, both buffers stay alive for c/2 appends (12 MiB for 262,144 appends at c = 524,288), and the O(1) worst case assumes O(1) allocation. For growth factor g, at least 1/(g − 1) keys per append.
2. **Explain global rebuilding and how to run it in the background:** let a structure degrade for Θ(n) updates, then rebuild all of it in f(n), for O(f(n)/n) amortized extra (the tombstone vector: rebuild when half the slots are tombstones; the doubling vector is itself one); in the background: start early (at a quarter), keep serving from the old copy, build the new one 8 slots of work per update, log the updates that hit already-copied keys and replay them, then swap; every delete then costs at most 9 writes at any size, and the old copy never passes 39% tombstones.
3. **Explain a scapegoat tree's partial rebuild and its amortized cost:** no balance data in nodes, only size and max-size at the root; α between ½ and 1; a node deeper than h_α(n) = ⌊log_{1/α} n⌋ triggers a climb to the first ancestor with a child holding more than α of its subtree (the scapegoat), whose subtree is rebuilt perfectly balanced in time proportional to its size and O(log n) extra space; a potential (|left size − right size| per node) pays for it, so inserts and deletes are O(log n) amortized and searches O(log n) worst case; deletes trigger a global rebuild when size < α·max-size; a single insert can still rebuild most of the tree (751,332 nodes for one of a million sorted inserts).
4. **Decide when a service needs a worst-case bound instead of an amortized one:** from the size of the spike (Θ(n) against a constant) and the requests behind it (131,072 arrive during the last copy; 349,515 of 1,000,000 wait behind some resize; request p99 494,289 ticks against append p99 1), multiplied by fan-out (63% of requests slow at 100 servers in Dean and Barroso's example), weighed against the price (the same total work, a worse median, memory held longer, more complex reads). A batch job judged on total time does not need it.

## The problem (opened in step 1, closed in step 17)

"Each request to a service appends one key to the vector. A request arrives every 4 ticks; one tick is one element write. Append 524,289 copies 524,288 keys, and 131,072 requests arrive while it runs. Every append is O(1) amortized. Is the service fast?" It is not: the appends' own p99 is 1 write (only 20 of a million resize), but the requests' p99 is 494,289 ticks, because 349,515 requests (35%) queue behind a resize. Closed in step 17: with incremental copying no append exceeds 3 writes, so no request ever waits (each arrives 4 ticks after the last); p99 and max request latency are 3 ticks; the total work is the same 2,048,575 writes; the price is a median of 3 instead of 1 and two buffers alive for a while.

  - `### Incremental copying, exactly`: the design from this file's header, as pseudo-code (append, get, set, pop, the migration start and end); the invariant (**work left ≤ 2 × operations left before the next possible resize**) and its proof: after a grow at capacity c (n = c), the copy of at most c keys needs at most c/2 operations; a further grow needs c more appends, a shrink needs n < c/2, at least c/2 pops, and every operation during the migration reduces the keys left by 2 (a pop of an unmoved key by up to 3); after a shrink (n = cap/4 − 1 into cap/2) the copy needs at most cap/8 operations, a grow needs over cap/4 appends and the next shrink at least cap/8 pops; so no resize starts during a migration, at most two buffers exist, and every operation costs ≤ 3 writes (exhaustive check to capacity 256: 17,570 states; 300 seeded random sequences of 4,000 operations with reads compared against a plain list; the adversarial pop, pop, push, push sequence of the last reel costs ≤ 3 per operation as well). The 16-append trace and the million (2,048,575 writes; max 3; 524,287 appends cost 3; p50 3). **Growth factor g:** the copy of c keys must finish within the (g − 1)c appends before the new buffer fills, so move at least 1/(g − 1) per append; with the chapter's rounding (⌈1.5·cap⌉, at least cap + 1), 2 per append works for g = 1.5 (it finishes exactly as the buffer fills at 8 → 12: zero slack; asserted for every capacity to 10⁶). **Space:** peak 3c slots for both vectors (the plain one during its single copy; Tarjan and Zwick: "two arrays need to stored together"), held for c/2 appends by the incremental one; 12 MiB at c = 524,288. **Reads:** one extra comparison; a migration-aware iterator must do the same. **Allocation:** the O(1) worst case holds if allocating a buffer is O(1); Tarjan and Zwick assume constant-time allocation and note their amortized bounds survive O(N) allocation, and Brodnik et al.'s worst-case bound is stated "assuming that memory allocation takes O(1) worst-case time" (both via Tarjan–Zwick); what a real allocator does is not claimed here (measured in "Measuring the memory hierarchy"). **The name:** Tarjan and Zwick call this "a standard background-rebuilding technique": resizing "can be made O(1) worst-case" that way.
  - `### Deamortizing as a recipe`: (1) prove the amortized bound with credits or a potential; (2) find the expensive job and the deadline before which it must finish (here: before the new buffer fills); (3) charge each operation a fixed slice of the job, at least work ÷ operations to the deadline; (4) keep the old structure answering until the job is done (dsbook: "we must keep the old structures until the construction finishes"); (5) check that no second job can start before the first ends. The price list (step 9) applies to every instance: a larger constant on cheap operations, memory held, more complex reads, more code (dsbook: "for the price that the resulting ... structure will be more complicated"; Tarjan and Zwick on the HAT: "the resulting data structure becomes more complicated"). Topic 5's counter has a deamortized cousin: Ehrlich's 1973 Gray-code algorithm, which Erickson presents as maintaining "a Gray code counter in constant worst-case time per increment".
  - `### Global rebuilding`: rebuild after Θ(n) updates; f(n) to build ⇒ O(f(n)/n) amortized extra, "given that n does not change asymptotically between the rebuilds" (dsbook); its examples: the array that doubles, the y-fast trie rebuilt when n changes by a constant factor (named only), tombstones with a rebuild at n/2; Erickson's hash table "global rebuilding rules" (grow when more than ¾ full, shrink when less than ¼): the last reel's table under another name. The tombstone vector at scale: the delete that makes half of 1,048,576 slots tombstones copies 524,288 keys. Binary search over tombstones: a tombstone keeps its key and a deleted mark, so order is preserved and a search lands on it and steps to the nearest live key (to the left, for a predecessor). Attribution: the term and technique are credited to Overmars (CHAPTER.md: *The Design of Dynamic Data Structures*, LNCS 156, 1983, a book not opened); **to verify** in Okasaki's thesis §5.2 or another opened source before the name appears; dsbook's chapter is the opened source for the technique.
  - `### Global rebuilding in the background`: the tombstone design exactly: trigger at a quarter of the slots, 8 units of work per delete (a unit = one old slot scanned, live or not, or one log entry replayed), deletes during the rebuild tombstone the old copy (which keeps serving), a delete behind the scan is logged and replayed as a tombstone in the new copy, swap when the scan and the log are done. Proof: work ≤ S + d for S slots and d deletes during the rebuild, so 8d ≥ S + d after d ≤ S/7 deletes; the old copy then has at most S/4 + S/7 = 11S/28 tombstones (39%, under ½); the new copy has at least S − 11S/28 = 17S/28 slots and at most S/7 tombstones, at most 4/17 < ¼, so it starts below its own trigger; at most two copies at a time; at most 1 + 8 = 9 writes per delete. Executed at 1,048,576 keys for three deletion orders. **Why the budget counts slots scanned, not keys copied:** with a budget of 8 copies, a delete may scan a long run of tombstones for free: a write budget is not a time budget (`examples.py` measures the longest scan one delete makes under that broken budget). The general form: dsbook's worst-case semi-dynamization (blocks built a few steps per insertion, "at most three finished blocks and at most one block in construction" per rank) and Tarjan and Zwick's background rebuilding; buffering updates during the rebuild and replaying them before the swap is the standard pattern (Okasaki §5.2; **to verify** before citing).
  - `### Scapegoat trees, exactly`: Galperin and Rivest (SODA 1993). Nodes hold key, left, right; the tree holds size[T] and max-size[T]. α-weight-balanced: size(left[x]) ≤ α·size(x) and size(right[x]) ≤ α·size(x), with ½ ≤ α < 1; α-height-balanced: h(T) ≤ h_α(n), with h_α(n) = ⌊log_{1/α} n⌋ (**to verify**: the formula is garbled in the extracted text; its Figure 1 values, α = 0.57 with h_α(17) = h_α(18) = 5, fit it); scapegoat trees are only *loosely* α-height-balanced, h(T) ≤ h_α(n) + 1. Insert: as in a BST, size and max-size updated; if the new node is deeper than h_α(n), climb and stop at the first ancestor that is not α-weight-balanced (one must exist: Lemma 5.1); sizes are computed on the way up with size(x_{j+1}) = size(x_j) + size(brother(x_j)) + 1, so finding the scapegoat costs O(size of its subtree) (Lemma 5.3); rebuild it ½-weight-balanced. The alternative scapegoat rule (the deepest ancestor x_i with i > h_α(size(x_i))), which their experiments preferred. Rebuild: FLATTEN (in-order into a list linked through right pointers) and BUILD-TREE, O(size) time and space proportional to the height; a non-recursive in-place version with two logarithmic stacks, 25–30% faster in their experiments. Delete: as in a BST, then if size[T] < α·max-size[T] rebuild the whole tree and set max-size[T] = size[T] (the inequality is garbled in the extraction: **to verify**). Analysis: potential Δ(x) = |size(left) − size(right)| when ≥ 2, else 0, "an accounting fiction"; insertions raise it by O(1) per node passed; an unbalanced node holds Θ(size), enough to find and rebuild; the rebuilt subtree has potential 0. Theorem 5.2 (inserts and searches) and Theorem 5.3 (with deletes): O(log n) amortized per insert or delete, O(log k) worst-case search. Searches never restructure (unlike splay trees, Ch.4 "Splay trees"). The small example (step 12–14) and the million (sorted: 28.24 per insert, max 751,333; seeded random order: 1.04 per insert, max 191, p99 1). **Choosing α (measured in our unit, not the paper's timings):** 100,000 sorted inserts: α = 0.55: 55.74 writes per insert, height 19, average depth 15.76; α = 2/3: 22.81, 27, 20.09; α = 0.75: 17.04, 40, 27.09: a larger α allows deeper trees and rebuilds less. The paper's own timing sentence about α ("as the value of α is increased the SEARCH and DELETE operations perform faster, while the INSERTS become slower") reads the other way: **to verify** against its Figures 4–5 before anything about measured timings is said; the reel says nothing about it. Galperin and Rivest compare: red-black trees store one extra bit per node for worst-case O(log n) updates (Ch.4 "Red-black trees", Goes deeper later); scapegoat trees store nothing per node and pay with amortized updates.
  - `### Spreading a partial rebuild out`: no opened source gives a worst-case scapegoat tree, so this is the recipe applied, labelled as such: build the balanced copy of the scapegoat's subtree in installments while the old subtree keeps serving, buffer the inserts and deletes that land in it, replay, swap; the difficulty is that a second scapegoat can appear inside or above the one being rebuilt before it finishes, so the schedule must account for nesting.
