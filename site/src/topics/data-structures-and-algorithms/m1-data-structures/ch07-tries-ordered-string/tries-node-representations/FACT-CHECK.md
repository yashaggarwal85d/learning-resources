## Red team

1. **Is "sorted-list children searched by binary search" (the chapter plan's own fourth representation) actually the same thing as UW's "BST-based implementation"?** No, and this is flagged directly in `SOURCES.md` and `OUTLINE.md`'s own "Claims not made": a sorted list searched by binary search and a binary search tree are related but distinct structures (one is a flat array with an implicit search path, the other is an explicit tree of nodes). No source fetched describes a plain sorted-array-with-binary-search child representation as its own separately named trie variant. `examples.py` implements the sorted-list representation directly — a Python list kept sorted by character, searched with `bisect` — as a direct, uncontroversial application of binary search (the technique this course has used since Chapter 1), and this topic does not claim a dedicated primary source for that specific implementation beyond the general technique and UW's closest documented analogue.

2. **Does the measured memory ratio match Princeton's own "1035 vs. 155 null links" example?** No, and it shouldn't be expected to: that is Princeton's own specific count on its own key set (a dictionary of ~34 three-letter words shown in the slide). `examples.py` measures its own, different 21-word dictionary and finds the array representation uses 4.48x the TST's total memory, with 96.3% of the array's own child slots null. The direction (array wastes far more than TST) and the general shape (the overwhelming majority of array slots are empty) both match the source; the exact ratio does not, and is not claimed to. This topic reports its own measured number, not the source's number restated as if it were measured here.

3. **Is the O(key length) lookup bound actually verified, or just asserted from the source?** Verified directly: `examples.py` counts real per-character lookup steps for the array, hash, and sorted-list representations and asserts the count equals `len(key)` for every tested key, across keys of different lengths, confirming the cost tracks key length and nothing else (dictionary size is held fixed, but the claim itself — that cost depends on L, not n — is the source's own stated argument: each step consumes one character and advances to exactly one child, which is a structural fact independent of how many other keys share the trie).

4. **Predict-step distractor check** (`CostPredict`, step 3): "depends on how many keys are stored" is ruled out because the source's own stated reason (one character consumed, one child followed, per step) never references n; "logarithmically, like a balanced tree" is ruled out because it would make a trie just a dressed-up balanced tree, which contradicts the entire point of this chapter (position in a string, not a comparison between whole keys); "depends on the alphabet size" is ruled out because R only affects a node's own child-storage width, never how many steps a lookup takes.

5. **Predict-step distractor check** (`ArrayPredict`, step 5): "most fill up eventually" is ruled out directly by the measured result (96.3% null on this dictionary); "exactly half, on average, for any alphabet" is ruled out because the real fraction depends on the dictionary's own branching factor at each node, not a fixed universal constant; "none stay empty, because a trie only allocates a slot when it's used" describes the hash representation, not the array one — the array's own defining trade-off is that it allocates every slot up front, used or not.

6. **Predict-step distractor check** (`TSTPredict`, step 8): "saving memory always costs an extra traversal step per character" is ruled out because the TST's own lo/hi comparisons happen without advancing the string position — only the equal child advances, so the number of character positions consumed is unchanged; "three child pointers always cost more than one array" is ruled out directly by the measured result (three references beats 26 slots on this dictionary); "giving up the O(key length) bound" is ruled out because the TST's own recursive lookup still terminates in a number of steps bounded by the key's own length (it can take more total pointer-follows than L due to lo/hi comparisons at a single character position, but it never revisits a position already resolved — `tst_lookup`'s own step counter, not assumed, confirms this stays proportional to the key, not to n).

7. **Does the hash-children representation actually reuse Chapter 3's separate-chaining mechanism, or just "a hash table" in name only?** Checked against the chapter plan's own stated seam (`CHAPTER.md`, "Seams to check at release"): the reuse claimed is the general hashing mechanism (a hash table keyed by character, mapping to child nodes), the same mechanism Chapter 3 introduced for arbitrary keys — not a claim that Chapter 3's own code is literally reinvoked. `examples.py`'s own `HashNode` uses Python's built-in dict, which is the same open-addressing-family hash table this course has treated as the canonical hash table since Chapter 3; no new hashing mechanism is introduced here.

8. **Does the ternary-search-tree representation actually reuse Chapter 4's binary-search-tree shape, or just share a name?** Checked: a TST node's own lo/hi comparison at one character position is structurally identical to a single binary-search-tree node's own left/right comparison — the only addition is the third ("equal") child that advances to the next character position, which has no BST analogue. The reuse claimed in `CHAPTER.md` ("one BST per node's children") is accurate at the level of the lo/hi comparison discipline, not a claim that Chapter 4's own rotation or balancing logic is reinvoked here (a TST is not self-balancing, and this topic makes no claim that it is).

9. **Bridge/handoff text check:** topic 32's own "Bridge" is quoted word for word from `CHAPTER.md`'s own Chapter 6 handoff text, verified by direct comparison against `tournament-loser-trees/registry.ts` entry's own `handoff` field in an earlier session (recorded in project memory) — unchanged since. This topic's own "Handoff" to Chapter 8 is quoted word for word from `CHAPTER.md`'s own topic-32 entry, verbatim, with no paraphrase.

10. **Are Radix/Patricia trees, longest-prefix-match, ART, and finite-state transducers actually absent from any claim in this topic?** Checked directly against `OUTLINE.md`'s own "Claims not made": all four are named only once, in the Frontier post-note and the ProveIt step's own body text, as the destination this topic's own measured memory blow-up motivates — never described mechanically, never assigned a specific number or bound of their own.
