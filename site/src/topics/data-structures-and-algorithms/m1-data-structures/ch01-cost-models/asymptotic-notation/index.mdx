<section data-section="outcomes">

## After this refresher you can

- State O, Ω, Θ, o and ω with their quantifiers, produce witnesses for a bound, and say why 2<sup>2n</sup> is not O(2<sup>n</sup>).
- Separate the two questions inside any complexity claim: which function (best, average, worst, expected case) and which inequality (O, Ω, Θ).
- Say what an average-case, an expected-time, a with-high-probability and an amortized bound each promise, and which of them a latency target needs.
- Name both resources in a time-space trade-off and what is counted, and spot a bound stated in the value of a number instead of its length.

## A little deeper

### Definitions

- **The notation as sets.** O(g) is the set of functions f for which there are constants c > 0 and n₀ with 0 ≤ f(n) ≤ c·g(n) for all n ≥ n₀; Ω(g) reverses the inequality and Θ(g) = O(g) ∩ Ω(g). The order of the quantifiers matters: c and n₀ are chosen first and must not depend on n (CLRS 4th ed., §3.2).
- **Strict versions.** f ∈ o(g) needs the inequality f < c·g for *every* c > 0 (with n₀ allowed to depend on c); equivalently f/g → 0 when the ratio has a limit. ω is the mirror. So f is never in o(f), and 3n² + 10n is Θ(n²) but not o(n²).
- **The limit test is one-directional.** If f/g has a limit, 0 means o, a positive constant means Θ and infinity means ω. If the limit does not exist the test says nothing: n and n·(2 + sin n) are Θ of each other and their ratio oscillates.
- **Equals signs lie.** "f(n) = O(g(n))" reads "is a member of", so it is not symmetric: n = O(n²) does not allow n² = O(n). Inside a formula, 2n² + 3n = 2n² + O(n) means "for some function in O(n)" (Knuth 1976 objects to the one-way equality but the convention won).
- **Two meanings of Ω.** Knuth's and CLRS's Ω needs the inequality for all large n. The older Hardy–Littlewood Ω, still used in number theory, means "not o": the inequality holds for infinitely many n. A function that is n on odd n and 0 on even n is Ω(n) in the second sense and not in the first; check which a source means.
- **Several variables.** A bound such as O(V + E) is not covered by the one-variable definition. Textbooks either leave it undefined or define it in incompatible ways (Howell 2008 found a flaw in one; Rutanen 2013 surveys them). State the domain: for all large V *and* E, or for all pairs outside a bounded set.
- **Rules to know cold.** O(f + g) = O(max(f, g)); a polynomial of degree k is Θ(n<sup>k</sup>); logarithm bases differ by a constant factor; exponentials with different bases do not (4<sup>n</sup> is not O(2<sup>n</sup>)); n! is not O(2<sup>n</sup>).

### Cases and randomness

- **A case chooses a function.** Worst case is the maximum over inputs of size n; best case the minimum; average case an expectation over an *assumed* input distribution, so it is only as good as the assumption. Each is an ordinary function of n and has its own O, Ω and Θ. "Quicksort's worst case is Ω(n²)" and "insertion sort's best case is O(n)" are both well-formed.
- **Expected time uses the algorithm's coins.** A randomized algorithm's expected running time is a maximum over inputs of an expectation over its random bits, so a hostile input cannot help. For quicksort with a uniform random pivot and distinct keys, the expected number of key-versus-pivot comparisons is 2(n+1)Hₙ − 4n (solving C(n) = n − 1 + (2/n)·ΣC(k)), about 1.39·n·log₂ n; the example file solves the recurrence exactly and checks the closed form.
- **Expectation is not a tail bound.** Markov's inequality gives only Pr[T ≥ k·E[T]] ≤ 1/k. A with-high-probability bound says the failure probability is at most 1/n<sup>c</sup> for a constant c the analyst may pick, usually at the price of a larger constant in the bound; it is a statement about a tail, neither an expectation nor a worst case. In the reel's 2,000 runs the slowest run was 1.42 times the mean.
- **Amortized is neither.** An amortized bound is a worst-case bound on a *sequence* divided by its length: no probability, but individual operations can still be slow. It gets its own topic (§1.2).

### Resources, size and reality

- **Space has the same notation.** Say whether the input is counted (auxiliary versus total space) and count recursion depth: a quicksort that always recurses into the larger side can use Θ(n) stack, one that recurses into the smaller side O(log n).
- **Trade-offs name both resources.** Memoization, hash tables and lookup tables buy time with space; recomputation, streaming and in-place algorithms buy space with time. The reel's duplicate search measured 499,500 pair comparisons with no extra values, 17,830 heapsort comparisons with none, and 1,000 hash-set steps with 1,000 stored values.
- **Input size is length, not value.** A cost polynomial in the number's value but exponential in its bit length is pseudo-polynomial (the O(nW) knapsack dynamic program, trial division). Doubling a prime's bit width from 32 to 64 took trial division from 65,534 steps to over four billion.
- **The RAM model is an assumption.** Unit-cost operations ignore the memory hierarchy and big-integer arithmetic. That is the next topic.
- **Constants and sizes are real.** 100n is slower than n² below n = 100. By comparison count alone merge sort's average already beats insertion sort's from n = 4 (measured in the example file), so the small-input cut-offs in sort libraries come from per-step overhead and cache effects, not comparison counts. Use the doubling test: if T(2n)/T(n) → 2<sup>b</sup>, the cost grows like n<sup>b</sup>.

## In code review

- "It's O(n log n)" with no case and no input model: ask which case, and whether the input can be adversarial (a fixed pivot on sorted data is quadratic).
- An average-case bound used for a latency target: averages hide the tail; ask for a percentile or a w.h.p. statement.
- A loop over a number's *value* where its bit length is the input size: pseudo-polynomial costs that explode with wider keys.
- Space ignored: a hash set that makes the time linear but holds every key in memory.
- "O(1)" for an operation that is amortized O(1): a single call can still take Θ(n).
- Choosing the asymptotically better algorithm for tiny inputs, or ignoring a 100× constant at the sizes the system really sees.
