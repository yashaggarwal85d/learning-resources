<section data-section="outcomes">

## After this refresher you can

- State O, Ω, Θ, o and ω with their quantifiers, produce witnesses for a bound, and say why 2<sup>2n</sup> is not O(2<sup>n</sup>).
- Separate the two questions inside any complexity claim: which function (best, average, worst, expected case) and which inequality (O, Ω, Θ).
- Say what an average-case, an expected-time and a with-high-probability bound each promise, which of them a latency target needs, and recognise an amortized bound (§1.2) as a third kind of promise.
- Name both resources in a time-space trade-off and what is counted, and spot a bound stated in the value of a number instead of its length.

## A little deeper

### Definitions

- **The notation as sets.** O(g) is the set of functions f for which there are constants c > 0 and n₀ with 0 ≤ f(n) ≤ c·g(n) for all n ≥ n₀; Ω(g) reverses the inequality and Θ(g) = O(g) ∩ Ω(g). The order of the quantifiers matters: c and n₀ are chosen first and must not depend on n (CLRS 4th ed., chapter 3).
- **Strict versions.** f ∈ o(g) needs the inequality f < c·g for *every* c > 0 (with n₀ allowed to depend on c); for g eventually positive this is exactly f/g → 0, and ω is the mirror (f/g → ∞), so for o and ω the limit always exists. So f is never in o(f), and 3n² + 10n is Θ(n²) but not o(n²).
- **The limit test is one-directional.** If f/g has a limit, 0 means o, a positive constant means Θ and infinity means ω. If the limit does not exist the test says nothing, and only Θ, O and Ω can hold without one: n and n·(2 + sin n) are Θ of each other and their ratio oscillates.
- **Equals signs lie.** "f(n) = O(g(n))" reads "is a member of", so it is not symmetric: n = O(n²) does not allow n² = O(n). Inside a formula, 2n² + 3n = 2n² + O(n) means "for some function in O(n)" (Knuth 1976 spells out the set reading and why the one-way equals is tolerable; the convention is entrenched).
- **Two meanings of Ω.** Knuth's and CLRS's Ω needs the inequality for all large n. The older Hardy–Littlewood Ω, still used in number theory, means "not o": the inequality holds for infinitely many n. A function that is n on odd n and 0 on even n is Ω(n) in the second sense and not in the first; check which a source means.
- **Several variables.** A bound such as O(V + E) is not covered by the one-variable definition. Most textbooks define O for one variable only; the only two books Rutanen found that define it for several (the 2nd and 3rd editions of CLRS) give different definitions, and Howell (2008) showed a flaw in the first of them (asymptotic linear dominance). State the domain: for all large V *and* E, or for all pairs outside a bounded set.
- **Rules to know cold.** O(f + g) = O(max(f, g)); O(f)·O(g) = O(f·g); a polynomial of degree k is Θ(n<sup>k</sup>); logarithm bases differ by a constant factor (log₂ n = log₂ 10 · log₁₀ n), so O(log n) needs no base, but not inside an exponent (2<sup>log₂ n</sup> = n while 2<sup>log₄ n</sup> = √n); exponentials with different bases do not (4<sup>n</sup> is not O(2<sup>n</sup>)); for every ε > 0, log<sup>k</sup> n = o(n<sup>ε</sup>) and n<sup>k</sup> = o(2<sup>n</sup>); log n! = Θ(n log n); n! is not O(2<sup>n</sup>). Θ is an equivalence relation and O a preorder, but not all pairs compare: n and n<sup>1+sin n</sup> are neither O nor Ω of each other.

### Cases and randomness

- **A case chooses a function.** Worst case is the maximum over inputs of size n; best case the minimum; average case an expectation over an *assumed* input distribution, so it is only as good as the assumption. Each is an ordinary function of n and has its own O, Ω and Θ. "Quicksort's worst case is Ω(n²)" and "insertion sort's best case is O(n)" are both well-formed. An algorithm has a single Θ only if best and worst agree, so “insertion sort is Θ(n²)” is false as stated; say “worst case Θ(n²)”. “At least O(n²)” is meaningless: O is an upper bound, and a lower bound needs Ω.
- **Expected time uses the algorithm's coins.** A randomized algorithm's expected running time is a maximum over inputs of an expectation over its random bits, so a hostile input cannot help. For quicksort with a uniform random pivot and distinct keys, the expected number of key-versus-pivot comparisons is 2(n+1)Hₙ − 4n (solving C(n) = n − 1 + (2/n)·ΣC(k)), asymptotically about 1.39·n·log₂ n (the lower-order terms still matter at n = 1,000: 10,986, against 13,816 for 2n ln n alone); the example file solves the recurrence exactly and checks the closed form.
- **Expectation is not a tail bound.** Markov's inequality gives only Pr[T ≥ k·E[T]] ≤ 1/k. A with-high-probability bound says: for every constant c there is a constant d such that the bound d·n·log n fails with probability at most 1/n<sup>c</sup> (Har-Peled proves it in this form for quicksort's recursion depth, d·ln n, which caps the comparisons at d·n·ln n), so a larger c costs a larger d. It is a statement about a tail, neither an expectation nor a worst case. Here the output is always correct and only the running time is random; a w.h.p. *correctness* guarantee is a different promise (Las Vegas against Monte Carlo, Ch.29). Neither kind of bound implies the other: E[T] = O(n log n) allows a heavy tail (Markov gives only 1/k), and a w.h.p. bound says nothing about the failure branch unless the worst case is capped. If T ≤ n<sup>d</sup> always and T = O(n log n) with probability at least 1 − 1/n<sup>d+1</sup>, then E[T] = O(n log n). In the reel's 2,000 runs the slowest run was 1.42 times the mean.
- **Amortized is neither.** An amortized bound is a worst-case bound on a *sequence* divided by its length: no probability, but individual operations can still be slow. It gets its own topic (§1.2).

### Resources, size and reality

- **Space has the same notation.** Say whether the input is counted (auxiliary versus total space) and count recursion depth: a quicksort that recurses on both sides can use Θ(n) stack on bad splits; one that recurses into the smaller side and loops on the larger uses O(log n).
- **Trade-offs name both resources.** Memoization, hash tables and lookup tables buy time with space; recomputation, streaming and in-place algorithms buy space with time. The reel's duplicate search measured 499,500 pair comparisons with no extra values, 17,830 comparisons for heapsort plus the final scan with O(1) auxiliary space (it permutes the input), and 1,000 hash-set lookups with 1,000 stored values; the hash set's linear time is itself an expected bound, and colliding keys make it quadratic.
- **Input size is length, not value.** A cost polynomial in the number's value but exponential in its bit length is pseudo-polynomial (the O(nW) knapsack dynamic program; Garey and Johnson's formal definition is polynomial in the input length and its largest number). Trial division is O(√v) divisions for value v, which is 2<sup>b/2</sup> for b bits. Doubling a prime's bit width from 32 to 64 took trial division from 65,534 steps to over four billion.
- **The RAM model is an assumption.** Unit-cost operations ignore the memory hierarchy, and adding two b-bit numbers costs Θ(b) bit operations, not O(1); the trial-division example already assumes O(1) division of 64-bit values. The model is the next topic. In practice log₂ n ≤ 64 for anything that fits in memory, so a log factor is “nearly constant” and a large constant on an O(1) can still lose to it.
- **Constants and sizes are real.** 100n is slower than n² below n = 100. By comparison count alone, top-down merge sort's average is below insertion sort's for every n from 4 to 8 (equal at 2 and 3; checked by enumeration in the example file), so when libstdc++'s `std::sort` stops partitioning ranges of 16 or fewer elements and finishes with plain insertion sort, the gain is low per-step overhead, not fewer comparisons. CPython's timsort weighs it the other way: there a comparison costs far more than moving a pointer, so it extends short runs with *binary* insertion sort to cut the comparisons. Use the doubling test: if T(n) ~ a·n<sup>b</sup> then T(2n)/T(n) → 2<sup>b</sup>, so a measured ratio estimates b. It cannot see log factors: n log n also gives a ratio tending to 2 (2.07 from 10⁹ to 2·10⁹).

## In code review

- "It's O(n log n)" with no case and no input model: ask which case, and whether the input can be adversarial (a fixed pivot on sorted data is quadratic).
- An average-case bound used for a latency target: averages hide the tail; ask for a percentile or a w.h.p. statement.
- A loop over a number's *value* where its bit length is the input size: pseudo-polynomial costs that explode with wider keys.
- Space ignored: a hash set that makes the time linear but holds every key in memory.
- "O(1)" for an operation that is amortized O(1): a single call can still take Θ(n).
- "Hash lookups are O(1)": expected O(1), under assumptions about the hash function and the keys. Keys chosen to collide make every lookup slow; hash flooding and per-process random seeds are §3.1.
- Choosing the asymptotically better algorithm for tiny inputs, or ignoring a 100× constant at the sizes the system really sees.

</section>

<section data-section="frontier">

## The frontier

- **Beyond worst case.** Worst-case analysis can be too pessimistic, and average-case analysis rests on an assumed input distribution and can favour algorithms tailored to it, so newer models sit between them. Smoothed analysis "measure[s] the maximum over inputs of the expected performance of an algorithm under small random perturbations of that input" (Spielman and Teng); it showed that the simplex method (with the shadow-vertex pivot rule) has polynomial smoothed complexity. Roughgarden's edited book surveys the other alternatives: parameterized analysis, instance optimality, resource augmentation and semi-random models.
- **Algorithms with predictions.** A newer line gives an algorithm a machine-learned prediction about its input and asks for two bounds at once: near-optimal when the prediction is good, and no worse than the prediction-free worst case when it is bad (Mitzenmacher and Vassilvitskii). The guarantee is again a pair of cases, stated separately.
