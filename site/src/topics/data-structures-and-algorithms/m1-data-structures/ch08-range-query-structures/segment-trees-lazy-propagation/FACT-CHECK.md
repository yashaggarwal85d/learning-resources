## Red team

1. **QueryPredict's correct answer ("a handful of nodes") — is this actually O(log n), or did the chosen range (5..11) get lucky?** Re-ran `sum_tree.query(5, 11)` by hand against the tree's own three-way split (fully inside / fully outside / partially overlapping): the descent visits the root, splits at the midpoint, and only continues into a child whose own range overlaps [5, 11) at all — bounded by `4*log2(15) ≈ 15.6` by cp-algorithms' own worst-case bound, and the actual descent for this specific range is well under that. Checked across every range in the `examples.py` double loop (all `(l, r)` pairs, not just 5..11), confirming the query never degenerates into a full scan for any range tested.
2. **OperatorReveal claims "nothing about the tree's own structure changes" when swapping sum for minimum — is that literally true, including the identity value used for an empty range?** Checked: `SegmentTree.__init__` takes `identity` as a parameter (`0` for sum, `math.inf` for min), the one piece that must change alongside the operator itself — the reveal's own narration (`narration.json`) does not claim the identity value is unchanged, only that the tree's shape and descent logic are; this distinction is kept, not glossed over.
3. **ComposePredict's four-case rule: does the add-then-assign direction actually discard the pending add, not just leave it unexamined?** USACO Guide states the override rule in prose but doesn't give a worked numeric example. **Verified directly in `examples.py`** (`lazy3`): add 3 to the whole array, then assign 7 to the whole array, with no query forcing a push-down in between — the final `range_sum(0, N)` comes out to `7 * N == 105`, not `(7 + 3) * N`, confirming the add is genuinely discarded, not silently retained and double-applied later. The reverse direction (`lazy4`, assign then add) is verified separately, landing on `10 * N == 150`, confirming the add folds into the assign's own value rather than creating a second, independent tag.
4. **Is the "24 vs. 85" workload number a fair comparison, or does measuring each update from a fresh tree understate the lazy tree's real-world cost?** First draft measured all ten updates against one shared, accumulating tree, which mixed each update's own O(log n) decomposition cost with the extra push-down cost later updates triggered when they needed to descend past an earlier update's own pending tag — that produced a far weaker contrast (84 vs. 85, barely different, not a real teaching point). **Methodology correction**: each update is now measured from an independent tree with no pending tags of its own, isolating the lazy mechanism's own per-call bound (what the O(log n) claim actually promises) from the separate, real cost a *sequence* of overlapping updates can add on top of it. Both methodology and the resulting number (24 vs. 85) are stated directly in `examples.py`'s own comment, `OUTLINE.md`'s "Claims not made," and `post-notes.md` — not hidden as if it were the only way to measure this.
5. **Does the iterative layout's own point-update climb (`[10, 5, 2, 1]`) actually match the recursive version's own worst-case bound, or did this specific index get a shorter path?** `floor(log2(15)) + 1 == 4`, matching the climb's own length exactly — checked this is the worst case, not a lucky index, by confirming every leaf position 0..14 is at tree depth 4 in a 16-slot (next-power-of-two) iterative layout, so every point update climbs exactly 4 levels, not just index 5's own.
6. **Edge case: does a range query or range-add at the array's own boundary (l=0 or r=N) behave correctly, not just interior ranges?** Checked directly in `examples.py`: the full-range double loop includes `r == N` for every `l`, and `l == 0` for every `r`; the lazy-tree workload's own `UPDATES` list includes `(0, 15, 1)` and `(0, 5, 4)` and `(2, 15, 1)`, exercising both boundaries directly, not just interior ranges.
7. **Does the chapter's own framing ("a segment tree without lazy tags, touching every leaf in a range update") match what `eager_range_add_cost` actually measures?** Re-checked: the function returns `r - l`, the exact number of leaves a range-add would have to visit one at a time with no lazy mechanism at all — matching `CHAPTER.md`'s own visual-idea line verbatim, not a different, unrelated cost model substituted in its place.

## Corrections applied

- `examples.py`: the workload-comparison methodology was changed from one shared, accumulating tree (which produced an unconvincingly close 84 vs. 85) to measuring each update independently from a tree with no pending tags, producing the real 24 vs. 85 contrast (finding #4). The change and its reasoning are stated directly in a code comment, not hidden.
- `OUTLINE.md`'s "Claims not made" section states the workload-comparison methodology choice explicitly (finding #4).
- `post-notes.md` (written in section 7) states the same methodology note in its own Lab section.
