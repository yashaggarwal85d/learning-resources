## Red team

1. **UpdatePredict's correct answer (3 slots touched updating minute 5) — is 3 actually right, or did the worked example get lucky?** Re-ran `Fenwick(15).add(5, 0)` by hand: 5 (0101) → +1 → 6 (0110) → +2 → 8 (1000) → +8 → 16 > 15, stop. Three slots: 5, 6, 8. Confirmed independently of the code, by hand.
2. **QueryPredict frames the query's jump count as matching the update's (3 = 3) — does this risk teaching "update and query always take the same number of jumps"?** That's false in general (an update at index 1 touches log2(n) slots forward; a query at index 1 touches exactly one slot, itself, going backward — very different counts). Checked: for this topic's own chosen pair (update at 5, query at 11), both happen to take 3 jumps, which is a coincidence of these two specific indices, not a general law. **Fix applied to `narration.json`**: the narrator explicitly says "three jumps again — not because update and query always match, but because these two particular indices do," so the reel does not imply a false general rule.
3. **Does "A point update walks forward by its own lowest set bit" (step 4 takeaway) hold for every index, or only 5?** Re-checked against every index 1–15 in `examples.py`'s own max-jump-count loop (the `max_jumps_seen` computation covers all 15 update indices and all 15 query indices) — every index's own jump sequence adds/subtracts its current lowest set bit at each step; 5→6→8 is a representative instance, not a cherry-picked exception.
4. **The naive-vs-Fenwick workload comparison (step 10): is 97 vs. 47 the real cost, or an inflated worst case?** First draft of `examples.py` charged a flat N=15 touches per update regardless of which index was updated — that overstates the naive cost for updates near the end of the array (updating minute 14 only needs to rebuild minutes 14–15, two slots, not fifteen). **Corrected** to charge `N - idx + 1` per update, the real number of cached prefix-sum slots that shift after that specific index — dropping the comparison from a flat 160 to the honest 97, still a real ~2x contrast, not an inflated one.
5. **TwoDPredict: "the same arithmetic nested" — does the 2D Fenwick tree actually preserve O(log n) per axis, or does nesting cost more?** Both sources' own code nests one update/query loop inside the other (`for i: for j:`), each loop independently bounded by O(log n) index jumps along its own axis — O(log n) × O(log n) = O(log² n) total per 2D operation, not O(log n) overall. **Correction**: step 9's own reveal text says "jumping in two dimensions at once," which is accurate to the mechanism (one nested loop per axis) but must not claim the 2D operation is still O(log n) overall — post-notes' own Internals section states the real O(log² n) bound explicitly rather than leaving it implied as O(log n).
6. **Edge case on the two-Fenwick-tree range update: what if r+1 exceeds n?** cp-algorithms' own pseudocode doesn't guard this explicitly in the snippet shown; `examples.py`'s `RangeFenwick.range_add` guards it directly (`if r + 1 <= self.n else None`) since this topic's own array is finite (n=15) and a range ending at the last index must not index past the array. Verified: the workload's own range-add (minutes 5–11, well inside 1–15) never exercises this guard, so a second, explicit check was added confirming no index error is raised when r == n is tried directly.
7. **Does the "exactly two prefix-sum queries" claim (step 7) hold for every range, including l=1?** Checked: `range_sum(1, r)` calls `prefix_sum(r) - prefix_sum(0)`, and `prefix_sum(0)` correctly returns 0 (the while-loop condition `idx > 0` never executes) — still two queries, one of which is a trivial zero. Confirmed in `examples.py`'s own full-range check (`for i in range(1, N+1): prefix_sum(i)` against the naive scan, which exercises l=1 implicitly).
