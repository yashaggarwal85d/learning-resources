# Fact-check — Tournament and loser trees

## Claims table

| # | Claim | Status | Source |
|---|---|---|---|
| 1 | A naive scan of all k current heads costs Θ(k) comparisons per output | Confirmed | `sources/wikipedia-kway-merge.txt`: "A straightforward implementation would scan all k arrays to determine the minimum. This straightforward implementation results in a running time of Θ(kn)." |
| 2 | A heap-based k-way merge costs roughly 2·log(k) comparisons per output, because a sift-down compares both children at every level | Confirmed | `sources/wikipedia-kway-merge.txt`: "A heap uses approximately 2*log(k) comparisons in each step because it handles the tree from the root down to the bottom and needs to compare both children of each node." |
| 3 | A tournament tree is a single-elimination bracket: two elements compete per game, the smaller is promoted, forming a binary tree of games | Confirmed | `sources/wikipedia-kway-merge.txt`: "The Tournament Tree... is based on an elimination tournament, as in sports competitions. In each game, two of the input elements compete. The winner is promoted to the next round." |
| 4 | A tournament tree costs only log(k) comparisons per output, one comparison per layer | Confirmed | `sources/wikipedia-kway-merge.txt`: "a tournament tree only needs log(k) comparisons because it starts on the bottom of the tree and works up to the root, only making a single comparison in each layer." |
| 5 | A loser tree stores each game's loser; repair touches only the leaf-to-root path | Confirmed | `sources/wikipedia-kway-merge.txt`: "it is more efficient to only store the loser of each game... When one of the leaves is updated, all games from the leaf to the root are replayed." / `sources/tutorialspoint-tournament-trees.txt`: "it is sufficient to examine node on the path from leaf to root rather than the sibling of the nodes on this path." |
| 6 | k-way merges are the second stage of external sorting; a wider merge needs fewer passes | Confirmed | `sources/wikipedia-kway-merge.txt`: "k-way merge algorithms usually take place in the second stage of external sorting algorithms..." / "If there are 6 runs that need be merged then a binary merge would need to take 3 merge passes, as opposed to a 6-way merge's single merge pass." |

## Red team

1. **Is the precise "⌈log₂ k⌉" bound actually in either source?** No — both sources state it informally ("log(k)", "Θ(log k)"), never with ceiling notation. Checked directly: the ceiling form follows from the sources' own balanced-tree construction (sentinel-padded runs to the next power of two keeps every leaf at the same depth, ⌈log₂ k⌉), and `examples.py` verifies it by counting real comparisons at k=4 (a power of two) and k=6 (not), confirming the bound holds in both cases rather than assuming it from the informal phrasing.
2. **Does the loser tree's "only the path is replayed" claim hold even though the heap also only touches one path (sift-down)?** Checked: both structures are single-path repairs after an output — the difference isn't which nodes move, it's how many comparisons each visited node costs (a heap's sift-down compares two children per level; a tournament/loser tree's repair makes one comparison per level). `examples.py`'s own counters track comparisons, not nodes touched, specifically to make this distinction visible rather than conflating it with "single path."
3. **Predict-step distractor check** (`HeapPredict`, step 3): "the same k−1 comparisons" is ruled out because a heap's own structure is exactly what improves on a linear scan, per the source's own O(log k) claim; "exactly log₂(k)" is the tournament tree's own cost, not the heap's — the distinction between the two structures' costs is the entire point of the next predict step; "zero comparisons" is ruled out because every source describes an active repair step, never a free lookup.
4. **Predict-step distractor check** (`TournamentPredict`, step 5): "no — log₂(k) rounds either way" conflates depth with comparison count, which the previous reveal (step 4) already distinguished; "yes, but unsafely" is ruled out because the source describes the tournament tree's bound as a direct structural consequence (one comparison per layer, not a shortcut that skips a needed check); "no — a bracket needs more rounds" is ruled out because both structures are balanced binary trees of the same depth over the same k elements.
5. **Does this topic claim a dedicated source ties loser trees specifically to LSM compaction?** No — checked directly: no such source was found during research, and none is cited as if it existed. The LSM-compaction connection in step 8 rests on topic 29's own already-fact-checked content (each compaction step merges several runs), not on a new claim about loser trees appearing by name in an LSM paper or RocksDB's own documentation.
6. **Does the heap-vs-loser-tree gap actually measure out to the source's own rough "2x" estimate?** No, and this matters: `examples.py` measured a heap/loser-tree ratio of 1.45x (k=8) and 1.19x (k=6), not 2x. The source's "approximately 2*log(k)" describes a full root-to-bottom sift-down's worst-case per-operation comparison count; a real k-way merge mostly replaces a removed head with a nearby value from the same sorted run, so the sift-down often stops before reaching the bottom, costing fewer comparisons than the worst case. The topic reports the real measured ratio in "Prove it" rather than restating the source's rough estimate as if it were the measured result — the loser tree still wins on every run measured, which is the claim that actually matters.
7. **Does "6 runs, 3 binary passes vs. 1 six-way pass" actually check out?** Checked by direct arithmetic: pairing 6 runs two at a time gives 3 merges in one pass (6 runs → 3 runs); pairing those 3 runs needs an uneven pass (one pair merges, one run waits) giving 2 runs; a final pass merges those 2 into 1 — three passes total, matching ⌈log₂ 6⌉ = 3. A single 6-way merge is one pass by definition. The qualitative claim (a wider merge needs fewer passes) also follows directly from the k-way merge's own definition, independent of this one worked example.
