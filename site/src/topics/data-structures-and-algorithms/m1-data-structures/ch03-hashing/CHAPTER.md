## The chapter

### The problem it solves

Chapters 1 and 2 built sequences: structures where "where is element i" is answered by arithmetic on a position. Hashing answers a different question: "where is the element whose key is k," for a key that has no natural position at all. Every topic in this chapter is a different way of turning that question into O(1) expected work, and a different way of paying for the two things that make it hard: a key can hash to the same slot as another key (collision), and the table can run out of slots (growth) — and, once hashing is exposed to anyone outside your own program, an adversary can choose keys that make every slot collide on purpose (HashDoS). The thread through all seven topics is **the same three questions asked of every hashing scheme**: what happens when two keys land in the same place, what happens when the table is full, and what happens when the keys are chosen by someone who wants your table to perform badly. Topics 16–20 answer these for a single machine's hash table; topics 21–22 ask the first question again at the scale of many machines or many files, where "the same place" means "the same server" or "the same subtree," and collision becomes the question of how little has to move when a machine joins or leaves, or how little has to be re-verified when one byte changes. Later chapters build on this directly: separate chaining's bucket-of-entries idea is a linked list (Ch.2 topic 2) used as the collision answer; hash tables under memory pressure (topic 20) reuse the amortized-resizing argument Ch.1 and Ch.2 topic 1 already proved and this chapter only has to adapt; B-trees and LSM trees (Ch.5) hash-partition their own merges; graph representations (Ch.8 onward) use a hash set for "visited"; Bloom filters (Ch.12) are k hash functions reused as a different data structure entirely; consistent hashing (21) is cited directly by *Data Engineering* §5.3 for sharding, and Merkle trees (22) are cited by replicated-storage anti-entropy and by Git and certificate transparency outside the syllabus's own two domains.

### Order of ideas, and why

1. **§3.1 Hash functions (16).** The mechanism every later topic in this chapter treats as a black box: turning a key into a number. Comes first because topics 17–20 all need "a hash function" as a given, and because the chapter's own HashDoS thread — an adversary choosing keys — has to be named before any hash table is built, so the learner judges every collision-handling scheme that follows against "does this scheme also need a keyed hash to be safe," not just "is this scheme fast."
2. **§3.2 Hash tables, by collision answer (17–20).** Separate chaining (17, the refresher: the oldest and simplest answer, a linked list per bucket) → linear probing and open addressing (18, the harder but more cache-friendly answer: no second allocation, but clustering) → SIMD group-probing tables (19, open addressing taken as far as 2017-era hardware allows: Swiss Tables, the scheme three major language runtimes converged on) → resizing and incremental rehashing (20, the question every one of 17–19 has deferred: what happens when the table in front of you is full). 17 before 18 because chaining is the simpler mental model and the refresher; 18 before 19 because Swiss Tables is open addressing with one specific, fast way of answering "which slot," not a different idea; 20 last in this group because every earlier topic in it built a table at a fixed capacity and this one is the only topic whose whole subject is what happens when that capacity runs out — it needs 17–19's tables as the things being resized, not the other way around.
3. **§3.3 Distributed and authenticated hashing (21–22).** Consistent hashing rings (21), where "hashing" now places a *machine*, not a slot in one array, and the chapter's growth-and-shrink question becomes "a node joins or leaves" → Merkle trees (22), where hashing moves from locating data to proving two copies of it agree without transferring either copy whole. 21 before 22 because 21 is still answering this chapter's collision-and-resize questions one level up (now about machines, not slots), while 22 answers a question this chapter hasn't asked yet — not "where is it" but "has it changed" — and is better placed last, as the chapter's turn toward verification.
4. **Handoff to Chapter 4.** Topic 22 ends on Merkle trees proving equality without comparing whole datasets; Chapter 4 opens with "BST operations and rotations," a different answer to "where is it" — one that keeps keys in order, which no hash table in this chapter does or tries to.

### Shared notation and terms

- **Load factor α:** entries ÷ capacity, defined once in topic 17 and used by name afterward (18, 19, 20).
- **Collision:** two distinct keys hashing to the same slot (or bucket) — defined once in topic 16 as a fact about any hash function with a finite range (pigeonhole), given its real consequence (a lookup can't stop at the first candidate slot) only once a table exists to show it, in topic 17.
- **Open addressing vs chaining:** `chaining` = each slot holds a pointer to a structure of all entries that hashed there (Ch.2's linked list, reused); `open addressing` = every entry lives directly in the table's own array, and a collision is resolved by trying another slot. Named once in topic 17 (chaining) and topic 18 (open addressing), used as the chapter's recurring axis in 18–20.
- **Probe sequence:** the order of slots an open-addressing scheme tries for a given key, defined in topic 18 and reused by name in 19.
- **Tombstone:** a marker left where a deleted entry used to live, so a probe sequence doesn't stop early at a now-empty slot that used to hold a collision; defined in topic 18, declared again wherever a scheme's delete behaviour is shown (19, 20).
- **Keyed vs unkeyed hash:** an unkeyed hash is the same function for everyone and its collisions are public once found (topic 16's HashDoS thread); a keyed hash includes a per-process secret, so an attacker who doesn't know the key can't find colliding inputs in advance. Named once in topic 16, used wherever a scheme's safety against adversarial keys is discussed (declared again in 17–19 as "this scheme still needs a keyed hash to be safe against the keys it's handed").
- **Resizing idiom:** this chapter's resize cost is the same amortized argument Ch.1/Ch.2 topic 1 already proved for a growable array, now applied to a table of slots instead of a row of records (topic 20 says this explicitly, once, and does not re-derive the bound); **incremental rehashing** is the chapter's one genuinely new resizing idea — migrating across two live tables instead of stopping the world for one doubling — and is introduced in topic 20 only.
- **Ring placement / virtual nodes:** topic 21's vocabulary, used only there; **Merkle proof / root hash:** topic 22's vocabulary, used only there. Neither borrows from the single-machine hash-table vocabulary above beyond "hash function" itself.
- **Spoken numbers:** narration has no digits, symbols or code names (automatic check); say "load factor zero point seven five", "big O of one expected", "SIMD", "sixteen slots", and add new terms the first time each appears (`load factor`, `collision`, `probe sequence`, `tombstone`, `keyed hash`, `control byte`, `virtual node`, `root hash`, QUALITY.md #29).

### One visual language for the chapter's reels

The chapter builds from `site/src/reels/kit.tsx` and `DESIGN.md`'s briefing theme (PROJECT_PLAN.md, "Theme — briefing"): black and white carry everything, colour is rare and means something. On top of that this chapter shares one grammar:

- **Colour:** `crema` keys and entries as they are; `latte` secondary labels (bucket indices, hash values); `taupe` empty slots, quiet axes; `caramel` **the thing to look at**: the slot a probe sequence is currently testing, the bucket being migrated, the node a key is routed to, the hash path being recomputed; `cinnamon` (rare) **the alternative being compared**, always the same side of each pair: chaining against open addressing (17 vs 18), doubling against incremental migration (20), a ring's naive placement against one with virtual nodes (21); `cherry` with `cherryText` **the bad outcome**: a collision cascade under an unkeyed hash flooded with adversarial keys (16, 17), primary clustering (18), every key moving on a naive resize or a naive ring join (20, 21), a mismatched hash proving two copies of a file disagree (22).
- **The table is drawn the same way in every single-machine topic (16–20):** a row of labelled slots, `taupe`-outlined when empty, `crema`-filled with a key's short label when occupied. A chain (17) draws a small linked list (Ch.2's own link-and-arrow drawing) hanging below an occupied slot. A probe sequence (18, 19) is a dotted `caramel` path hopping slot to slot until it lands; a `cherry` flash marks a slot a probe tests and rejects because it's occupied by a different key (a true collision cascade), never on its first successful landing.
- **SIMD matching (19):** the same slot row gains a second row of one control byte per slot, drawn as a small tag; the chapter's one 16-wide match is shown landing on all sixteen control bytes in a single `caramel` highlight sweep, in one frame, not sixteen sequential frames — the frame itself is the argument that this is one instruction, not sixteen.
- **Resizing (20):** doubling draws a second, longer row below the first exactly as Ch.2 topic 1's reallocation does, with `caramel` arrows moving every entry at once; incremental migration draws the two tables side by side with a `caramel` marker that advances through the old table a few slots at a time across several frames, while new inserts land directly in the new table — the two pictures are given equal screen time so "not amortized the same way" is seen, not asserted.
- **The ring (21):** drawn as an actual circle (reusing Ch.2 topic 5's ring motif, now with machines instead of buffer slots), keys landing clockwise at the first machine encountered; a join or leave is a `caramel` arc showing exactly which keys move, with every other key's arc left undrawn — the visible absence of movement is the point.
- **Merkle trees (22):** a binary tree of hash boxes, leaves `crema` (a segment's own hash), internal nodes `latte` (hash of the two children below), drawn growing upward; changing one leaf flips a `cherry` path from that leaf to the root, and the reel's proof is exactly that path, nothing else, lit `caramel`.
- **Reel shape.** Topic 17 is this chapter's only refresher (about 6 minutes). Full topics (16, 18, 19, 20, 21, 22) open on a problem drawn from the log's keys (or, for 21–22, the log sharded or verified across machines), ask a predict question in the first three steps, show the mechanism, then "Prove it." About 10–14 minutes, 2–4 predict questions.

### 16. Practical hash functions and HashDoS (`dsa.practical-hash-functions-hashdos`): full, §3.1

- **Folder:** `practical-hash-functions-hashdos`. About 12 min.
- **Scope (syllabus clause → what it delivers):**
  - "fast non-cryptographic hashes (xxHash3, wyhash, FxHash)": what makes a hash function fast when it doesn't need to resist a deliberate attack — few instructions per byte, good avalanche (a one-bit input change flips about half the output bits), verified against each named hash's own specification or reference implementation, not a secondary summary; named only the ones actually verified at research time.
  - "vs keyed hashes (SipHash, Rust's default `HashMap` hasher)": a keyed hash folds in a per-process secret so the function an attacker sees behaving one way today behaves differently on a different run; SipHash specifically, and the fact that Rust's standard `HashMap` uses a SipHash-family default for exactly this reason, verified from Rust's own standard-library documentation or source at research time.
  - "vs cryptographic hashes (SHA-256, BLAKE3)": built to resist a much stronger attacker (finding *any* collision at all, or reversing the hash) at a real speed cost per byte — named as the next tier up, with one verified current benchmark figure showing the cost difference against the non-cryptographic hashes above, not asserted from memory.
  - "collision-flooding attacks and per-process random seeds": the actual HashDoS mechanism — if a server hashes attacker-controlled keys (form fields, JSON keys, URL parameters) with a known, unkeyed hash, the attacker can precompute a large batch of keys that all land in the same bucket, turning a hash table's expected O(1) into a worst-case O(n) and a service into a target; a per-process random seed (what a keyed hash needs one of) defeats precomputation because the attacker can't know the seed in advance; cited to a real disclosed incident or advisory (verified at research time, not assumed) that this chapter's later topics will refer back to.
  - Leaves every collision-handling scheme itself (chaining, probing, SIMD matching) to topics 17–19; leaves what a weak hash's actual cascade looks like inside a table to topic 17, which builds the table this topic only threatens.
- **Outcomes:**
  - Name the cost/safety trade-off across non-cryptographic, keyed and cryptographic hashes, with one real example of each.
  - Explain the HashDoS mechanism: why an unkeyed hash over attacker-controlled keys is a real denial-of-service vector.
  - Explain why a per-process random seed defeats precomputed collision attacks, and say which named hash uses one by default.
- **Introduces:** `hash-function`, `avalanche-property`, `non-cryptographic-hash`, `keyed-hash`, `cryptographic-hash`, `hashdos`, `per-process-seed`. **Uses:** none from earlier chapters directly (this topic is the chapter's own foundation). **Declared:** none new beyond its own.

- **Handoff:** "A hash function turns any key into a number. It says nothing yet about what happens when two different keys turn into the same one. Next: the oldest answer, and the one every language's standard library still ships."
- **Prerequisites panel:** Ch.2 topic 6 (Before this: strings as the thing being hashed). On-site: none new.

### 18. Linear probing and open addressing (`dsa.linear-probing-open-addressing`): full, §3.2

- **Folder:** `linear-probing-open-addressing`. About 13 min.
- **Scope (syllabus clause → what it delivers):**
  - "primary clustering and Knuth's expected-probe analysis": linear probing's specific failure mode — once a short run of occupied slots forms, any key hashing anywhere inside that run makes the run longer, so runs tend to merge into longer runs at high α; Knuth's expected-probe-count result (cited from his own derivation, verified against the primary text rather than a paraphrase) quantifies how much worse this gets as α approaches 1.
  - "quadratic probing and double hashing": the two classic fixes to clustering — quadratic probing (probe offsets grow as i² instead of i, scattering a run's overflow rather than extending it, with its own caveat about which table sizes guarantee every slot is reachable) and double hashing (a second hash function sets the probe step itself, so two keys that start at the same slot diverge immediately instead of following the same sequence) — named and contrasted with plain linear probing on the same picture, not built as three separate mechanisms.
  - "tombstones vs backward-shift deletion": deleting an entry can't simply empty its slot, because a later probe sequence passing through would stop early and miss entries placed beyond it; a tombstone marks "deleted, keep probing past me" at the cost of a slot that's occupied forever until a rehash; backward-shift deletion instead shifts a later entry in the same probe run back into the freed slot, immediately, at the cost of a bounded extra scan — named as the two real answers, with one correctness subtlety each, not asserted as equivalent.
  - Leaves the table-is-full question to topic 20; leaves Robin Hood's and cuckoo hashing's own, more elaborate probe-sequence designs out of scope (skipped in the syllabus) — this topic's "Prove it" section may name them as "what you'd reach for next" with no mechanism.
- **Outcomes:**
  - Explain primary clustering and state (not re-derive) Knuth's expected-probe result's shape as α rises.
  - Contrast quadratic probing and double hashing against plain linear probing as two real fixes for clustering.
  - Explain tombstones and backward-shift deletion as two different correct answers to "can you delete from an open-addressed table," and name the cost each one pays.
- **Introduces:** `open-addressing`, `probe-sequence`, `primary-clustering`, `quadratic-probing`, `double-hashing`, `tombstone`, `backward-shift-deletion`. **Uses:** `load-factor`, `collision`, `hash-function`. **Declared:** `collision` (topic 17 already introduces it; restated as the thing a probe sequence resolves instead of a chain).

- **Handoff:** "Open addressing keeps every entry in the array itself, one cache line at a time — but still walks a probe sequence one slot at a go. The next scheme tests many candidate slots in a single instruction."
- **Prerequisites panel:** topics 16 and 17 (Before this). On-site: none new.

### 19. SIMD group-probing tables (Swiss Tables) (`dsa.simd-group-probing-tables`): full, §3.2

- **Folder:** `simd-group-probing-tables`. About 13 min.
- **Scope (syllabus clause → what it delivers):**
  - "Abseil's `flat_hash_map` design (2017)": the forcing problem — a node-per-entry chained table wastes memory (a pointer and allocation overhead per entry) and misses the cache on almost every probe; Abseil's answer, verified against Google's own Abseil documentation or the CppCon talk's own slides/transcript, not a secondary retelling.
  - "H1/H2 hash split": one hash value split into H1 (which group of slots to start probing) and H2 (a cheap one-byte fingerprint stored per slot, not the whole key), so most false candidates are rejected by comparing one byte before ever touching the actual key.
  - "one control byte per slot": every slot has a control byte recording empty, deleted (a tombstone, topic 18's term reused) or H2's fingerprint for an occupied slot — the control-byte array is what actually gets matched, not the entries themselves.
  - "matching 16 slots per SIMD instruction": a single SIMD compare instruction checks a whole group's control bytes against the query's H2 byte at once, turning what would be up to sixteen sequential probes into one hardware instruction plus a cheap bitmask of which lanes matched — the chapter's one frame-is-the-argument picture (see visual language above).
  - "adopted by Rust's `hashbrown` (std `HashMap`) and Go's built-in map since Go 1.24": named and verified at research time against each project's own source or release notes, not assumed from an older or remembered version — Go 1.24's switch specifically needs a current, dated source, since this is a recent change.
  - Leaves the full capacity-and-growth mechanics of resizing such a table to topic 20 (this topic may preview, in one frame, that the table resizes, without building the resize); leaves Robin Hood's and cuckoo hashing's alternative probe-sequence designs out of scope (skipped in the syllabus).
- **Outcomes:**
  - Explain the forcing problem Swiss Tables solves and name the design (H1/H2 split, one control byte per slot) that solves it.
  - Explain why one SIMD instruction can test sixteen slots at once, and what makes most of them rejectable by one byte instead of the whole key.
  - Name the three real languages/runtimes that converged on this design, as verified at research time.
- **Introduces:** `swiss-table`, `control-byte`, `h1-h2-split`, `simd-group-match`. **Uses:** `open-addressing`, `probe-sequence`, `tombstone`, `cache-lines`, `cache-miss`. **Declared:** `tombstone` (topic 18 already introduces it; restated as one of three control-byte states).
- **Bridge:** "Open addressing keeps every entry in the array itself, one cache line at a time — but still walks a probe sequence one slot at a go. Swiss Tables test many candidate slots in a single instruction, by not looking at the entries at all until one byte says it's worth it."
- **Handoff:** "Every scheme so far has worked inside a table of fixed size. None of them has yet said what happens when that table fills up. Next: resizing, and the two real ways to pay for it."
- **Prerequisites panel:** topics 16 and 18 (Before this); SIMD/vector instructions at a basic level (declared, with a self-check: how many bytes fit in a 128-bit register?). On-site: none new.
- **Visual idea:** the same 16-slot table from topic 18, now with a control-byte row beneath it; a query's H2 byte compared against all sixteen control bytes in one `caramel` highlight sweep across the whole row in a single frame, with the matching lane(s) kept lit and the rest fading, versus topic 18's probe sequence redrawn beside it hopping slot to slot for comparison.
- **Sources to start from:** Abseil's own `flat_hash_map`/Swiss Tables design documentation and Matt Kulukundis's CppCon 2017 talk (primary, read/watched in full); Rust's `hashbrown` crate's own documentation or source describing its adoption of the design; Go's official 1.24 release notes for the built-in map change (a dated, verifiable source, since this is recent).

### 20. Resizing and incremental rehashing (`dsa.resizing-incremental-rehashing`): full, §3.2

- **Folder:** `resizing-incremental-rehashing`. About 12 min.
- **Scope (syllabus clause → what it delivers):**
  - "doubling with amortized cost": the question every earlier topic in this section deferred — once α rises past a scheme's workable range, the table must grow; this topic states explicitly that the amortized argument is the same one Ch.1 and Ch.2 topic 1 already proved for a growable array (not re-derived here), now applied to a table of slots that must all be rehashed into new positions, because a key's slot depends on the table's own capacity.
  - "vs incremental migration across two tables (Redis `dict`)": the real cost doubling pays that a growable array doesn't — rehashing every entry at once is a single long pause, which a latency-sensitive server can't always afford; Redis's `dict` structure, verified against Redis's own source, instead keeps the old and new tables both live and migrates a bounded number of entries on every operation that touches the table, so no single operation pays for the whole migration.

  - Leaves the per-scheme resizing details (what a chained table's rehash looks like vs an open-addressed one's) to a single unified treatment, since the amortized argument and the two migration strategies don't depend on which collision scheme topics 17–19 built.

### 21. Consistent hashing rings (`dsa.consistent-hashing-rings`): full, §3.3

- **Folder:** `consistent-hashing-rings`. About 13 min.
- **Scope (syllabus clause → what it delivers):**
  - "ring placement": hash both keys and machines onto the same circular range; a key belongs to the first machine found going clockwise from the key's own position — the mechanism that makes this chapter's earlier "where does this key live" question meaningful at the scale of many machines instead of many slots in one array.
  - "virtual nodes for balance": a single physical machine hashed to one point on the ring gets an unpredictable, often lopsided share of the ring's keys by chance; hashing each machine to many points (virtual nodes) instead spreads its share evenly across the ring, verified against a primary source's own reasoning for why this specific fix works (not just asserted that it does).
  - "minimal remapping on join/leave": the chapter's resizing question, one level up — when a machine joins or leaves, only the keys between its ring position and its clockwise neighbour's move, not the whole key space; this is the property the "ring" visual language exists to make visible as a near-empty arc, in contrast to topic 20's resize, where every key moved.
  - "consistent hashing with bounded loads (Mirrokni, Thorup, Zadimoghaddam, SODA 2018)": the real extension that caps how much any one machine can be overloaded relative to the average, even under an adversarial key distribution, by redirecting excess load to the next machine on the ring instead of letting one machine absorb an unbounded share — named and cited directly to its own paper, with the bound it actually proves stated as the paper states it, not simplified past correctness.
  - "→ *Data Engineering* §5.3": named as the cross-domain cite this syllabus clause specifies; this topic does not re-teach what that chapter covers, only hands off to it.
  - Leaves rendezvous, jump and Maglev hashing's own mechanisms out of scope (skipped in the syllabus), but the syllabus's *Lab* bullet's "key movement when growing 10 → 11 nodes" measurement is kept for this ring scheme alone (see "Notes for the release run").
- **Outcomes:**
  - Explain ring placement and why a key's owning machine is found by walking clockwise from the key's hash.
  - Explain virtual nodes as the fix for a single ring point's unpredictable load share.
  - State the minimal-remapping property and measure it directly for a join or leave.
  - Name the bounded-loads extension and the real guarantee it adds over plain consistent hashing.
- **Introduces:** `consistent-hashing`, `ring-placement`, `virtual-node`, `minimal-remapping`, `bounded-load-hashing`. **Uses:** `hash-function`, `hash-table-resize` (as the single-machine question this answers one level up). **Declared:** none new beyond its own.
- **Bridge:** "A single machine's table can always grow to fit more keys. Consistent hashing asks the same question one level up: when a machine itself joins or leaves, how many keys have to move?"
- **Handoff:** "Consistent hashing answers where a piece of data lives, and how little moves when the set of machines changes. It says nothing about whether two copies of that data actually agree. Next: proving they do, without comparing either one whole."
- **Prerequisites panel:** topic 20 (Before this: what a resize costs on one machine, as the contrast); topic 16 (Before this: a hash function, now hashing machines too). *Data Engineering* §5.3 as "Goes deeper later".
- **Visual idea:** a ring of a handful of machines, the log's keys landing clockwise at `caramel` dots; one machine added, with only the short `caramel` arc of keys between it and its clockwise neighbour redrawn moving, every other key's position left untouched; a second picture, same ring, one machine hashed to several virtual points instead of one, with the per-machine key count visibly more even across a bar chart beneath.
- **Sources to start from:** Karger et al.'s original consistent-hashing paper (the primary source for ring placement and virtual nodes, read directly, not from a secondary summary); Mirrokni, Thorup and Zadimoghaddam's "Consistent Hashing with Bounded Loads" (SODA 2018), read in full for its actual stated guarantee; a primary engineering write-up from a system that uses consistent hashing with virtual nodes in production (e.g. a current, citable design document), for a real verified virtual-node count.

### 22. Merkle trees (`dsa.merkle-trees`): full, §3.3

- **Folder:** `merkle-trees`. About 12 min.
- **Scope (syllabus clause → what it delivers):**
  - "hash trees for verifying and diffing large datasets in O(log n)": a binary tree where every leaf is the hash of one chunk of data and every internal node is the hash of its two children; comparing two datasets' root hashes answers "do these agree at all" in O(1), and walking down from a mismatched root toward the one or few leaves whose hashes actually differ costs O(log n) instead of comparing every chunk.
  - "anti-entropy repair in Dynamo/Cassandra": named and verified against each system's own documentation or source at research time — how a Merkle tree over a node's key range lets two replicas find exactly which key ranges disagree without exchanging every key.
  - "Git objects": Git's own object store, verified against Git's own documentation/source, as a Merkle structure in practice — a commit's hash depends on its tree's hash, which depends on every blob's hash beneath it, so two repositories' histories can be compared, and two commits proven identical or not, by comparing hashes alone.
  - "certificate transparency": named and verified against the Certificate Transparency RFC or project documentation — a public, append-only Merkle tree of issued certificates, letting anyone verify a certificate was logged without downloading the whole log, and a log operator prove they haven't silently rewritten history.
  - "content-defined variants (prolly trees) for diffable indexes": named with one verified current source — a Merkle tree whose chunk boundaries are set by the data's own content (a rolling hash crossing a threshold) rather than fixed offsets, so inserting or deleting data near the start doesn't shift every later chunk boundary and therefore doesn't invalidate every later hash the way a fixed-offset chunking would.
  - Leaves the chapter's resizing/collision thread fully behind; this topic's subject is verification, not location, and says so once, explicitly, as the chapter's turn.
- **Outcomes:**
  - Build a Merkle tree over a batch of data and explain why comparing root hashes answers "do these agree" in O(1).
  - Find which leaf(ves) differ between two trees in O(log n) by walking down from a root mismatch.
  - Name at least two real production uses (anti-entropy repair, Git, certificate transparency) and what each one proves without transferring the whole dataset.
  - Explain why content-defined chunking (prolly trees) avoids invalidating every later chunk's hash on a small edit, where fixed-offset chunking would not.
- **Introduces:** `merkle-tree`, `root-hash`, `merkle-proof`, `anti-entropy-repair`, `content-defined-chunking`. **Uses:** `hash-function`, `cryptographic-hash` (topic 16). **Declared:** none new beyond its own.
- **Bridge:** "Consistent hashing answers where a piece of data lives, and how little moves when the set of machines changes. It says nothing about whether two copies of that data actually agree. Merkle trees prove they do, without comparing either one whole."
- **Handoff:** "Every structure in this chapter answered 'where is the key' or 'do these two copies agree' by turning data into a number. The next chapter asks a question hashing can't answer at all: keep the keys in order, so you can ask for the smallest, the largest, or everything between two bounds. Binary search trees, next, and the rotations that keep one balanced."
- **Prerequisites panel:** topic 16 (Before this: a cryptographic hash, strong enough that two different inputs practically never share a hash); topic 21 (Before this, as the contrast: locating data vs verifying it). On-site: none new.
- **Visual idea:** a handful of the log's own segment files as leaves of a small binary tree, each leaf's hash rising into its parent's, up to one root hash at the top; one segment edited, its leaf hash changing `cherry`, and exactly the path from that leaf to the root re-lit `caramel` while every sibling path stays untouched — the proof the reel ends on.
- **Sources to start from:** Ralph Merkle's original patent/paper describing the hash-tree structure (the primary source, read directly if accessible, or a current, careful secondary treatment if the original is not practically readable, noted as such in `SOURCES.md`); Amazon's Dynamo paper (DeCandia et al., SOSP 2007) or Cassandra's own documentation for anti-entropy repair; Git's own documentation (`gitformat-objects` or current equivalent) for its object-hashing structure; the Certificate Transparency RFC (RFC 6962 or its current successor) for the public-log use; a primary source describing content-defined chunking / prolly trees (e.g. Dolt's or a comparable project's own design write-up), verified at research time.
