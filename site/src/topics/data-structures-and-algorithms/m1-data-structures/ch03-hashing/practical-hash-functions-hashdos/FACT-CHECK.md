## Red team: both predict questions

**Step 3 (FloodPredict).** Distractors tested against the real mechanism:
- "Nothing changes" — tempting if a learner conflates "hash function speed" (a property of the function alone) with "hash table performance" (a property of the function *and* the key distribution). Explicitly separated in the reveal.
- "A little slower, proportional to collisions" — the genuinely hardest distractor, since it's *true* for ordinary, incidental collisions. The reveal has to say why a crafted multicollision is qualitatively different (every key in one bucket, not a few), not just quantitatively worse. `examples.py`'s own measured ratio (not "a little") is the proof.
- "Only matters if attacker knows table size" — tested against the actual mechanism: the attack constructs keys colliding under the *hash function itself* (mod any table size that's a power of two sharing the colliding bits, or simply colliding under the full hash value), so a reasonable range of table sizes doesn't save the defender. Confirmed wrong, kept as a distractor because it's a real objection a learner might raise.

**Step 5 (SeedPredict).** This is the pair the correction (claim 9) exists to teach, so it was red-teamed hardest:
- Option 1 ("yes, attacker can't predict collisions, flood fails") is not a strawman — it is the literal fix multiple real systems shipped in 2011–2012, per the SipHash paper's own account ("We comment that many of the hash-flooding defenses proposed since December 2011 are vulnerable to the same attack"). Marking it simply "wrong" without this context would be unfair to the learner's reasoning; the explain text names it as "the actual industry response," not a dumb guess.
- Option 4 ("as long as the seed is ≥128 bits") was added deliberately to test whether a learner conflates "seed length" (an entropy/brute-force question) with "hash family structure" (the actual vulnerability, which is about linearity, not key length — SipHash's own key is also 128 bits, but that's not why SipHash resists the attack this step is about). Confirmed as a genuine distractor, not reducible to the correct answer by a different route.
- Option 3 ("no, random seeds don't help at all") was checked against claim 9's own scope: the paper's attack needs the attacker to *query and time* the server adaptively. Against a precomputed, offline attacker (the original Klink & Wälde threat model), a random seed genuinely does work — this is why option 3 is wrong, not option 2's milder claim. The explain text preserves this nuance rather than overcorrecting into "seeds are useless."

## Currency notes

- wyhash's own README states its project has moved on to rapidhash; this topic names wyhash only because the syllabus names it, and says so in `references.md` rather than presenting wyhash as current best practice.
- Rust's `std::HashMap` docs state the default algorithm "is subject to change at any point in the future" — the reel names SipHash 1-3 as "currently" the default, matching the docs' own hedge, not as a permanent guarantee.
- `rustc-hash`'s README states its 2.x hasher's underlying algorithm has already changed once while keeping the `FxHasher` name; the reel's claim is about the *design decision* (speed over DoS resistance), which hasn't changed, not about one specific formula.

## Claims not made

- No claim about *which* tier (non-crypto, keyed, crypto) is "best" in the abstract — the reel's own recap (step 9) frames it as a fork on one question (are the keys adversarial?), matching the chapter plan's and `DESIGN.md`'s no-ranking stance used elsewhere (e.g. the strings topic's Go-vs-Rust framing).
- No claim that this topic's from-scratch SipHash-2-4 implementation in `examples.py` is suitable for production use, is constant-time, or resists side-channel attacks in a real deployment — it exists only to verify the mechanism against a published test vector and to drive step 7's pipeline diagram, never for timing (see row 14).
- No claim about MurmurHash2/3's current status beyond what the AppSec slides state (their role as the *previous* generation's randomization-only patch, later also shown insufficient) — this topic does not re-derive the differential-cryptanalysis attack on MurmurHash3 the slides sketch; it is out of scope and not needed for this topic's own claims.
