## The chapter

### The problem it solves

A set of a billion keys is too big to keep in memory and, in an LSM tree, too slow to consult on disk for every read that finds nothing. Chapter 5 gave the answer's *use* (a filter per run says "definitely not here" or "maybe", and almost every read skips almost every run) and measured it. It did not say why a filter with ten bits per key makes a mistake about one time in a hundred, why seven hash functions and not four or fourteen, or whether that is as good as any filter could be. This chapter is the mathematics under that measurement, for the one structure the syllabus builds in full (the Bloom filter), taught as a mechanism you can derive from a single line: **each of the m bits is still zero after n·k random settings with probability e^(−kn/m)**. From that one line come the false-positive rate, the best k, the bits per key, the proof that no filter can do much better, the trick that replaces k hash functions with two, and the one thing the structure cannot do (delete). The thread is **a one-sided error priced in bits**: every answer "no" is certain, every answer "yes" is a bet whose odds you choose by choosing the memory. The syllabus's other filters (blocked and partitioned Bloom, cuckoo, quotient, xor/binary fuse/ribbon, range) are all marked *(skipped)* and get no reel; they are what this one topic's limits motivate, and each is named once in its post-notes.

### Order of ideas, and why

1. **§12.1 Bloom filters and false-positive math (42).** One topic, because everything the syllabus line asks is one derivation: the mechanism (k hash functions over m bits, set on insert, test on query), the rate (the one-line probability above, giving (1 − e^(−kn/m))^k), the optimum (k = (m/n) ln 2, which makes exactly half the bits ones and the rate (1/2)^k), the bound (m ≥ n·log₂(1/ε) for any filter with no false negatives and rate ε, against the Bloom filter's n·log₂(e)·log₂(1/ε) ≈ 1.44·n·log₂(1/ε)), the probe trick (two hashes simulate k), and the limit (no deletes). Splitting it would put the formula in one reel and its use in another.
2. **Handoff to Chapter 13.** The chapter's last word is what a Bloom filter cannot give: it holds a set but cannot list its members, and every answer about a *specific* key carries an error. Chapter 13 opens with the exact counterpart: a set of integers stored as a bitmap, compressed, with fast intersection and union and no errors at all (Roaring).

**Skipped in this chapter** (stay in the curriculum, get no reel, per `syllabus/review-notes/dsa-cuts.md`, "Chapter 12 — Filters and Approximate Membership (2 of 6)" and "(3 of 6)"): Blocked and partitioned Bloom filters, Cuckoo filters (§12.1); Quotient filters (§12.1); Xor, binary fuse and ribbon filters, Range filters (§12.2). That is all of §12.2 and four of the five §12.1 topics. Each is named once, in topic 42's post-notes "Where this goes next", with only the facts read from a primary source at research time; none is built. The syllabus's own *Lab* names several of them; see "Notes for the release run".

### Shared notation and terms

- **m** the number of bits, **n** the number of keys inserted, **k** the number of hash functions (probes per key), **ε** (written `ε`, said "epsilon") the target false-positive rate, **f** the rate actually achieved, **b = m/n** the bits per key. Written as the Broder–Mitzenmacher survey and the syllabus write them, so a reader of either recognises them. The fraction of bits that are one is called **fill** on screen and in captions (no Greek letter, so it cannot be mistaken for the survey's own symbol for the proportion of zero bits).
- **False positive / false negative:** a *false positive* is "maybe present" for a key never inserted; a *false negative* is "absent" for a key that was inserted. A Bloom filter has none of the second kind and the topic keeps the two words apart in every caption.
- **Spoken numbers:** narration has no digits, symbols or code names (automatic check). Say "bits per key", "hash functions", "false-positive rate", "optimal number of hash functions", "natural log of two", "one point four four", "one in a hundred"; speak every number in words (QUALITY.md #29). Names (Bloom, Kirsch, Mitzenmacher) are checked against `site/narration/voice.json` aliases and added by the builder when missing. **Known clash:** `voice.json` already holds the alias `"bloom": "blum"` (added for Manuel Blum in Chapter 1's potential-method topic, so the speech check accepts "bloom" as a transcription of "Blum"). This topic says "Bloom filter" in nearly every line, so before narrating, the builder reads how `narration/match.py` applies aliases and makes sure the two uses cannot mask a real mishearing in either direction; the fix is to the lexicon or the line, never to the check.

### 42. Bloom filters and false-positive math (`dsa.bloom-filters-false-positive`): full, §12.1

- **Folder:** `bloom-filters-false-positive`. About 15 min.
- **Scope (syllabus clause → what it delivers):**
  - "k hash functions over m bits": the structure and its two operations: insert sets k bits, query reports "maybe present" only if all k are set and "absent" at the first zero; one-sided error, no false negatives ever, and why (a bit once set is never cleared); the structure holds no keys, so it cannot list its members. The reading of Chapter 5's per-run filter (an immutable run's filter is built once from the run's keys, so it never needs to change) closes the loop with topic 28. LevelDB's `util/bloom.cc` as the real small instance (read at planning time: `k_ = bits_per_key * 0.69`, clamped to 1…30; a minimum filter size of 64 bits; k stored in the filter's last byte so a reader uses the writer's k).
  - "FPR ≈ (1 − e^{−kn/m})^k": the derivation, line by line. After n·k independent settings a given bit is still zero with probability (1 − 1/m)^(kn) ≈ e^(−kn/m); a false positive needs k bits all one, each with probability 1 − e^(−kn/m), so f ≈ (1 − e^(−kn/m))^k. The two approximations named and sized (the Broder–Mitzenmacher survey: p = e^(−kn/m) is "very close (within O(1/m))" to the exact probability, and the fill concentrates with high probability around its mean, both read at planning time); the formula is an approximation, and **Bose, Guo, Kranakis, Maheshwari et al., "On the false-positive rate of Bloom filters" (Information Processing Letters 108(4), 2008, pp. 210–213; citation checked, abstract not read) is cited for the claim that the textbook formula is not exact; its exact statement is to verify at research time and is not asserted from this plan**. Measured against absent keys in `examples.py`.
  - "optimal k = (m/n) ln 2": set the derivative of k·ln(1 − e^(−kn/m)) to zero; the solution is k = (m/n) ln 2 ≈ 0.693·b; at it, exactly half of the bits are one and f = (1/2)^k, so for a target rate ε the number of hash functions is log₂(1/ε) (checked: k = 7 at ε ≈ 1% is 6.64 rounded up, and the table above); the optimum is flat (planning table), which is why implementations round k down to save probes (LevelDB's 0.69 and its integer truncation; the rate at k = 6 against k = 7 for 10 bits per key is 0.84% against 0.82%).
  - "~1.44 log₂(1/ε) bits per key": substituting the optimum, m = n·log₂(1/ε)·log₂ e = n·ln(1/ε)/(ln 2)² ≈ 1.44·n·log₂(1/ε) bits; the lower bound by counting (the Broder–Mitzenmacher survey's argument: a representation must give each of the (u choose n) possible sets an m-bit string, and a string that is to accept only a fraction ε of the universe can stand for few sets, so m ≥ n·log₂(1/ε); this is the Chapter 1 information-theoretic bound applied to a new object, a point the topic makes aloud); therefore a Bloom filter is within a factor log₂ e ≈ 1.44 of the best possible filter (survey: "within a factor of log₂ e ≈ 1.44 of the (asymptotic) lower bound"), and at equal space the optimal Bloom rate is about 0.6185^j against the bound's 0.5^j for j bits per key. What the bound does not say: that 1.44 is achievable by other means (the skipped xor, binary-fuse and ribbon filters sit closer to it; RocksDB's wiki states its ribbon filter "saving about 30% of Bloom filter space" at 3–4× the filter CPU, read at planning time, named in the post-notes only).
  - "double hashing to derive k probes": compute two hash values h₁(x), h₂(x) and probe positions g_i(x) = h₁(x) + i·h₂(x) mod m for i = 0…k−1; Kirsch and Mitzenmacher (Random Structures & Algorithms 33(2), 2008, pp. 187–218; "Less hashing, same performance") prove that this loses nothing in the asymptotic false-positive rate (abstract read at planning time: "only two hash functions are necessary to effectively implement a Bloom filter without any loss in the asymptotic false positive probability"); LevelDB's code is the instance, with a rotate-by-17-bits as the second hash and its comment citing the paper. The measured agreement in the planning table. **This is the same arithmetic as Chapter 3's double hashing** (`double-hashing`, a probe sequence for open addressing): the topic says so in one sentence and names what differs (there the sequence resolves a collision, here it spreads k probes). The topic does not claim the guarantee holds for any hash functions (the paper's conditions are quoted at research time).
  - "no deletes": clearing a key's k bits can erase bits that other keys also set, producing false negatives, the one thing the structure promises never to do (the planning table's search demonstrates it on a small filter); the counting variant (a small counter per cell instead of a bit, at several times the space) named, with its cost to verify against a source before any figure is stated; why an LSM run does not care (immutable, so the filter is never edited, and a deleted key lives on as a tombstone in a newer run, as topic 28 taught); and why the practical answer to "I need deletes" is another structure (cuckoo and quotient filters, both skipped and named once).
  - "→ Data Engineering §5.6": the practitioner's view (sizing from a target rate, where filters sit in LSM reads, Parquet column filters, join pruning and runtime filters, cuckoo/xor/ribbon in production) is Data Engineering's topic "Bloom, cuckoo and xor filters" (planned there, not live when this was written); this topic gives the mathematics and points there by name.
  - The syllabus *Lab* names blocked Bloom, cuckoo and ribbon or binary-fuse structures, all of them skipped: this topic's post-notes lab implements the standard Bloom filter only, measures FPR and queries per second at 8, 12 and 16 bits per key, and leaves the rest as a sourced extension (see "Notes for the release run").
- **Outcomes:**
  - Derive the false-positive rate, the optimal number of hash functions and the bits per key from the one probability e^(−kn/m), and check each against a measured filter.
  - Size a filter for a target rate and key count (bits, k, bytes), and say what each extra bit per key buys.
  - Explain why 1.44 is the gap to the best possible filter, how two hashes replace k, and why a Bloom filter cannot delete.

- **Hook:** a read for a key that is not in the database would open every run of the LSM tree. Chapter 5's filter makes that read nearly free, at about ten bits per key. How wrong is it allowed to be? At ten bits per key, with seven hash functions, one absent key in a hundred slips through; to get one in a million you do not need a million times the memory, you need about nineteen more bits per key. Predict how many bits per key a one-in-a-million filter needs, and whether it needs more hash functions or fewer.
- **Visual idea:** a row of bit cells; a key's seven probes draw out of it and the cells flip on one beat; an absent key's probes land, six on ones and one on a zero (`caramel` on the deciding zero) and then, in a second try, all seven on ones (`cherry`, the false positive); a counter on the side shows the fill climbing toward one half.
