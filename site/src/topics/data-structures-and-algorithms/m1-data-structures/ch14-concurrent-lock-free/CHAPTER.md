## The chapter

### The problem it solves

Every structure in Chapters 1–13 was analysed as if one thread touched it. A server has dozens, and the first thing they all want is the same few structures: a queue between stages, a map from key to state, a counter. The obvious fix, one lock around the structure, is correct and is the baseline everything here is measured against; its cost is invisible in a single-threaded benchmark and appears as soon as threads contend for the lock or one of them is descheduled while holding it. This chapter answers three questions in the order a practitioner meets them. **What do we even mean by "correct" and "fast enough" for a shared structure?** (topic 45): a *correctness criterion*, linearizability, which says a concurrent execution must look like one of the sequential ones, and a *ladder of progress guarantees* (blocking, obstruction-free, lock-free, wait-free) that says what happens to the other threads when one stops. **How is a queue built when the producers and consumers are many and the capacity is fixed?** (topic 46): per-slot sequence numbers, so each slot says whose turn it is, and the padding that keeps two threads' counters off one cache line. **How is a hash map built when it must also grow?** (topic 47): lock striping, a map whose bins are locked or compare-and-swapped one at a time, a resize that every thread helps with, the lock-free alternative that sorts the whole table into one list, and the sharded map a Rust programmer reaches for. The thread through all three is **what a thread that stalls does to everyone else**, and the lesson is the one the syllabus's chapter heading states: *a concurrent structure needs a concurrent argument*. A picture of a correct sequential structure is never a proof of a concurrent one, so each topic shows one interleaving that breaks the naive version before it shows the one that works. The memory-model detail (what an acquire or a release means) lives in the Rust track (Chapter 7) and is used here only as a one-sentence contract; the seven topics the owner cut (Treiber stacks and ABA, safe memory reclamation, Michael–Scott queues, concurrent skip lists, B-link and optimistic lock coupling, Bw-trees, and testing concurrent structures) are named, not built.

### One running example: three shared structures of a log pipeline

Chapter 13 treated the log as a table with row ids. This chapter lets the log **arrive from several threads**. Three shared structures carry the whole chapter, one per topic, each small enough to draw: **a counter** of events seen (topic 45: the smallest shared object, used to show lost updates, a lock, a retry loop and a hardware add), **a bounded queue of log records** from several producer threads to several consumer threads (topic 46), and **a map from request id to a running count** updated by many threads and growing as new ids arrive (topic 47). Every interleaving drawn is a *numbered, replayable schedule* (thread A step 1, thread B step 1, …), so a picture never relies on a race that happened to occur. Every number on screen is computed or asserted in each topic's own `examples.py`, and the examples **replay schedules deterministically in a single-threaded model** (the way a model checker would) rather than relying on real threads racing: a pure-Python thread benchmark would be dominated by the interpreter's global lock and would show nothing about lock-free scaling. Any throughput or latency figure comes only from a compiled helper whose machine, compiler and flags are recorded in `OUTLINE.md`, or from a source's own table with its hardware named. ### Shared notation and terms

- **Operation, invocation, response, history, pending operation, complete operation:** Herlihy and Wing's terms, used exactly: a history is the sequence of invocation and response events; an operation is *pending* when its invocation has no response yet; "A precedes B" means A's response comes before B's invocation; operations that do not precede each other are *concurrent*. A history is drawn as lanes of intervals, one lane per thread.
- **Progress, per operation:** *blocking* (a stalled thread can prevent others finishing), *obstruction-free* (a thread that runs alone for long enough finishes), *lock-free* (some thread always finishes: the system as a whole makes progress), *wait-free* (every thread finishes in a bounded or at least finite number of its own steps). Said as four words and drawn as one ladder, strongest at the top; each topic lights the rung its structure sits on.
- **Compare-and-swap, written CAS(address, expected, new):** atomically, if the value at the address equals expected, store new and report success; otherwise report failure and change nothing. Said "compare and swap" always, never the abbreviation as a word.
- **Spoken numbers:** narration has no digits, symbols or code names (automatic check). Say "compare and swap", "lock free", "wait free", "linearization point", "sequence number", "cache line", "lock striping"; speak every number in words (QUALITY.md #29). Class and crate names (ConcurrentHashMap, dashmap, crossbeam) are not spoken.
- **Not used:** the word "thread-safe" as a claim. Every structure is described by its progress guarantee and its correctness criterion, never by "thread-safe", which is not a property with a definition.

### One visual language for the chapter's reels

The chapter builds from `site/src/reels/kit.tsx` and `DESIGN.md`'s briefing theme: black and white carry everything, colour is rare and means something. On top of that this chapter shares one grammar:

- **Colour:** `crema` a value, a node, a slot's contents; `latte` secondary labels (a thread name, a sequence number, a step number); `taupe` a slot or bin nobody is touching, a thread that is waiting; `caramel` **the thing to look at**: the step being executed, the linearization point, the atomic instruction that decides the outcome; `cinnamon` (rare) **the alternative being compared**, always the same side of each pair: the lock-based version against the lock-free one, padded against unpadded; `cherry` with `cherryText` **the bad outcome**: a lost update, a thread blocked behind a suspended one, an operation that returns a result no sequential order allows.
- **A concurrent execution is drawn as lanes:** one horizontal lane per thread, time left to right, an operation as a bar from its invocation to its response (`Draw`), the instant it "takes effect" (its linearization point) a `caramel` tick inside the bar; a stalled thread is a lane that stops (`taupe`) while the others continue. The same lane picture is used for a numbered schedule in topics 45–47, so a reader moves between them without relearning it.
- **A structure is drawn as what it is in memory:** a queue as a row of cells with a sequence number beside each cell and two counters (enqueue position, dequeue position) on separate lines; a hash map as a bin array with a chain per bin and the first node marked as the lock; the 64-byte cache lines drawn as framed groups of cells so false sharing is visible as two counters in one frame.
- **Reel shape.** All three topics are full topics (no refresher): about 14–16 minutes each, 2–4 predict questions, the first within the first four steps; open on the problem named in each topic's hook, then one interleaving that breaks the naive version, then the mechanism that survives it, the measured number, then "Prove it". Every "interleaving" step is a **predict** step wherever the learner can reason it out ("which value does the dequeue return?").

### 45. Progress guarantees and linearizability (`dsa.progress-guarantees-linearizability`): full, §14.1

- **Folder:** `progress-guarantees-linearizability`. About 15 min.
- **Scope (syllabus clause → what it delivers):**
  - "blocking vs obstruction-, lock- and wait-free progress": the problem first (a shared counter; the lost-update schedules above; a lock fixes it and creates a new failure: the thread holding it is preempted, or crashes, and every other thread waits); then the four rungs, each defined from its source and shown on one schedule. *Blocking*: a mutual-exclusion lock; a suspended lock holder stops all others. *Obstruction-free*: Herlihy, Luchangco and Moir (ICDCS 2003): "guarantees progress for any thread that eventually executes in isolation", a thread being in isolation "as long as the other threads do not take any steps" (read at planning time); it is weaker than lock-freedom and wait-freedom, and can livelock under contention (the paper's own remark is to be quoted at research time before the topic says how it is cured). *Lock-free*: "ensures only that some thread always makes progress" (the same paper's wording, read), so an individual thread can starve; shown by the CAS retry loop on the counter in a schedule where one thread fails every time. *Wait-free*: Herlihy, "Wait-free synchronization" (TOPLAS 13(1), 1991, pp. 124–149): each operation completes "in a finite number of steps, regardless of the relative execution speeds of the other processes" (the paper's definition, read at planning time; the paper also defines *bounded* wait-free, with a bound N on the steps); shown by an atomic add on the counter. The hierarchy is stated and each implication argued in one line: wait-free implies lock-free, and lock-free implies obstruction-free (the topic checks each against the sources' wording: the paper calls obstruction-freedom weaker than both); a blocking implementation sits below the ladder and guarantees nothing to a thread whose peer has stopped. What the topic does **not** claim: that an instruction called "atomic add" is wait-free on every machine (how a hardware add is built is the architecture's, so the claim is made only for the operation as the source defines it and is **to verify** before any statement about a particular CPU); that lock-free is always faster than a lock (the topic says the measured answer depends on contention and shows the planning schedule where it is not).
  - "compare-and-swap" (not in the syllabus line, but the one primitive the progress examples and the next two topics use, and no earlier DSA topic teaches it): CAS(address, expected, new) and its failure semantics; the retry loop; the counter built from it; why a CAS loop is lock-free and not wait-free; the classic ABA hazard **named in one sentence** as the reason a CAS success can lie (the skipped "Treiber stacks and the ABA problem" owns the mechanism and its fixes, named in the post-notes only). The hardware primitive's memory-ordering contract is Rust Systems Engineering Chapter 7's (live there: "Atomicity versus ordering", "Acquire/Release publication and SeqCst"); this topic says "a CAS is atomic and, for this chapter, ordered", and points there. The Rust track's "CAS loops and the ABA problem" is itself marked *(skipped)*, so this topic is the only place in the site that teaches the CAS retry loop as a progress argument.
  - "linearizability as the correctness criterion (Herlihy & Wing, TOPLAS 1990)": Herlihy and Wing, "Linearizability: a correctness condition for concurrent objects" (TOPLAS 12(3), 1990, pp. 463–492): a history is linearizable if it can be extended (by appending responses to some pending operations) to a history whose complete part is equivalent to a legal sequential history that preserves the real-time precedence order (their conditions L1 and L2, read at planning time: "complete(H′) is equivalent to some legal sequential history S" and the precedence order of H is contained in that of S); the plain version: every operation appears to take effect instantaneously at some point between its invocation and its response (its **linearization point**); pending operations may or may not have taken effect. Worked by hand on four-operation queue histories (the linearizable one and the planning history that is not, with the argument for why no legal order exists). How a checker finds a linearization (try orders, prune by real time) and that checking is expensive in general are named; **the NP-completeness result is cited, not proved, and its exact statement and its source (Gibbons and Korach, "Testing shared memories", SIAM J. Comput. 26(4), 1997, citation checked, abstract not read) are to verify at research time**. A small brute-force checker in `examples.py` is the topic's tool and the one the next topic reuses.
  - "and why it composes": locality: Herlihy and Wing's theorem that a history of several objects is linearizable if and only if each object's sub-history is ("a local property: a system is linearizable if each individual object is linearizable", read at planning time), so objects can be built and verified independently; the same paper's remark that linearizability is also a **nonblocking** property ("processes invoking totally-defined operations are never forced to wait", read), meaning the definition itself never makes a pending operation block another; why that matters (a queue and a map in one program can each be reasoned about alone). The contrast with serializability (a multi-object transaction property that is **not** local) is named once, from the same paper's remark that linearizability "can be viewed as a special case of strict serializability where transactions are restricted to consist of a single operation applied to a single object" (read at planning time), and left to Data Engineering.
  - "→ Rust Systems Engineering Ch.7": the pointer to the memory-model track, by name (Chapter 7 is live there); this topic builds nothing of it.
  - **Overlap with Data Engineering, by design:** Data Engineering Chapter 14 (planned there, topic 5, `de.linearizability`, not live when this was written) teaches linearizability for *replicated registers across machines*, Attiya–Welch cost bounds, "read from the leader" and a checker over simulated histories. This topic teaches the *shared-memory, many-threads-in-one-process* version that a data structure needs: the same definition, applied to a counter, a queue and a map, with CAS as the mechanism. Neither depends on the other (the ledgers are per domain); each names the other once. This topic never uses the replication examples.

### 46. Bounded MPMC ring queues (`dsa.bounded-mpmc-ring-queues`): full, §14.2

- **Folder:** `bounded-mpmc-ring-queues`. About 16 min. Hosts the chapter lab.
- **Scope (syllabus clause → what it delivers):**
  - "per-slot sequence numbers (Vyukov's bounded queue)": the problem (many producers and many consumers share a ring of fixed capacity; Chapter 2's ring used two indices that one producer and one consumer own; with many of each, the indices must be claimed atomically and a slot must say whether it holds data); then the design as the code on Dmitry Vyukov's 1024cores page gives it (the live page now serves unrelated content, so the topic cites the archived copy read at planning time, and crossbeam's `ArrayQueue`, whose source states "The implementation is based on Dmitry Vyukov's bounded MPMC queue"): a power-of-two ring of cells, each cell holding a **sequence number** and the data, two shared counters (`enqueue_pos`, `dequeue_pos`); a cell's sequence number starts at its index; **enqueue**: read `enqueue_pos`, look at the cell it maps to (`pos & mask`, Chapter 2's masking), compare the cell's sequence number with `pos`: equal means the cell is free for this turn, so CAS `enqueue_pos` from `pos` to `pos + 1`, write the data, then store `pos + 1` into the cell's sequence number (the release that publishes it); less means the cell still holds an unconsumed item from the previous lap, so the queue is full; greater means another producer already took this turn, so reload `enqueue_pos` and retry; **dequeue** symmetrically compares with `pos + 1`, and after reading the data stores `pos + capacity` (the next lap's free marker). The sequence number is therefore a lap counter that tells each side whose turn the cell is, with **no lock and one CAS per operation** (Vyukov's page: "The cost of enqueue/dequeue is 1 CAS per operation. No amortization, just 1 CAS", and a benchmark of 75 cycles on a dual-core laptop, which the topic quotes only with its hardware, as a historical figure). The sequence numbers after each operation of a capacity-4 trace are the topic's asserted numbers.
  - the property the page itself states and the topic must make precise: Vyukov classifies it "MPMC, array-based, fails on overflow, does not require GC, w/o priorities, causal FIFO, blocking producers and consumers", and says it is "not lockfree in the official meaning, just implemented by means of atomic RMW operations w/o mutexes". Chapter 14 topic 45's ladder makes that exact: **a producer that claims a slot and is suspended before publishing blocks the consumer waiting on that slot, so the queue is blocking, not lock-free**. The planning replay (the stalled producer above) also shows that a dequeue can return "empty" while an enqueue that completed before it began has put an item in a *later* slot; by the definition of topic 45 that history is **not linearizable** (the dequeue should have returned x). ### 47. Concurrent hash maps (`dsa.concurrent-hash-maps`): full, §14.2

- **Folder:** `concurrent-hash-maps`. About 16 min.
- **Scope (syllabus clause → what it delivers):**
  - "lock striping": the baseline first: one lock around a Chapter 3 table is correct and serializes everyone (the contention picture from topic 45); then split the table into S independently locked **stripes** (segments) and pick a stripe by hash, so threads on different stripes never meet; what it buys (S-fold less contention when keys are uniformly spread) and what it costs (an operation that needs the whole table, such as the size or a resize, must take every lock; the stripe count is fixed at construction); its real instance: Java's `ConcurrentHashMap` before the Java 8 rewrite was built from segments (the JDK 21 source still carries the `concurrencyLevel` constructor argument "solely for compatibility with previous versions", a `DEFAULT_CONCURRENCY_LEVEL` of 16 and an unused `Segment` class "instantiated in minimal form only when serializing", read at planning time; **the older segment design itself is to be read in a JDK 7 source or documentation at research time before any detail of it is stated**).
  - "Java `ConcurrentHashMap` (CAS on bins, treeified bins)": the JDK 21 design as its source comments state it (read at planning time; the version and the file are recorded at research time): a table of bins, each a list of nodes; **inserting the first node of an empty bin is a single CAS** ("by far the most common case for put operations under most key/hash distributions"); other updates take a lock on the **first node of the bin** ("we do not want to waste the space required to associate a distinct lock object with each bin, so instead use the first node of a bin list itself as a lock", using built-in `synchronized`), after validating that the node is still first; **reads do not lock** ("Retrieval operations (including get) generally do not block"; `get` is a plain traversal of volatile reads, read in the source); the cost the source names itself (other updates on the same bin stall behind a slow `equals` or mapping function, and under random hashes "not a common problem": the Poisson table in the comment, parameter about 0.5 at the 0.75 resize threshold, bin lengths 0 to 8 with probabilities 0.607, 0.303, 0.076, 0.013, 0.0016, 0.00016, 0.000013, 0.0000009, 0.00000006, computed and checked in `examples.py`); the size is kept in a **striped counter** (`baseCount` plus `CounterCell`s, the idea of `LongAdder`), which is why `size()` is an estimate under concurrent updates ("typically useful only when a map is not undergoing concurrent updates"); no null keys or values (the source's `NullPointerException` documentation; the value rule to be read before it is stated). **Treeified bins**: when an insert walks a chain whose node count reaches `TREEIFY_THRESHOLD` 8 (the source tests `binCount >= TREEIFY_THRESHOLD` after the insert's traversal: the exact off-by-one, whether the ninth node or the eighth triggers it, is **read and replayed in `examples.py`** before it is stated) and the table has at least `MIN_TREEIFY_CAPACITY` (64) bins, the bin becomes a balanced tree of `TreeNode`s ("a specialized form of red-black trees") bounding search "to O(log N)", read from the source; if the table is smaller than 64, `treeifyBin` resizes instead (read); a tree bin is turned back into a list at `UNTREEIFY_THRESHOLD` 6, which the source applies when a resize splits a tree bin (`lc <= UNTREEIFY_THRESHOLD`), not on removal alone (to verify for the removal path); why: the source says non-uniform hash distributions include "dumb or hostile usages in which multiple keys are designed to have identical hash codes", so this is **Chapter 3's HashDoS defence inside a data structure** (the topic ties it to `hashdos`), with the source's own caveat that it bounds work "so long as keys are Comparable"; the tree bin carries its own read-write lock "parasitic on the main bin-synchronization strategy", with the stated consequence that "readers need never block" (they fall back to the slow `next`-pointer traversal while the root lock is held).
  - the resize every thread helps with (the part of "CAS on bins" that makes growth non-blocking for readers): a **ForwardingNode** placed at the head of each migrated bin; a thread that finds one calls `helpTransfer` and joins the migration of the next range of bins; a reader that finds a forwarding node follows it to the new table (the source's comments and the call sites at the update methods, read at planning time: the exact protocol is read in full at research time before it is drawn); this is Chapter 3's **incremental rehashing** made concurrent (Redis's two-table migration was one thread amortizing the move; here every thread pays a share).
  - "split-ordered lists (Shalev & Shavit, JACM 2006) for lock-free resizing": the lock-free alternative: Shalev and Shavit, "Split-ordered lists: lock-free extensible hash tables" (J. ACM 53(3), 2006, pp. 379–405, read at planning time): one lock-free linked list of **all** items, sorted by the **bit-reversal** of the hash key ("recursive split-ordering ... achieved by simple binary reversal: reversing the bits of the hash key so that the new key's most significant bits are those that were originally its least significant"), with **dummy nodes** marking bucket starts, so a bucket is a pointer into the list and **doubling the table only adds dummy nodes and never moves an item** (a "split" is directing a new bucket pointer into an existing sublist); the bucket array starts at size 2, doubles when the item count exceeds the array size times a load factor, and an uninitialized bucket's parent is initialized recursively; the list underneath builds on Michael's lock-free list (the paper: "Michael [2002a], builds on the work of Harris [2001]"); what it gives (resizing with no stop and no migration of items) and what it costs (a list traversal inside each bucket, dummy nodes, memory reclamation, which the skipped "Safe memory reclamation" topic owns); the topic says plainly that the paper reports a lock-free table that performed as well as the best lock-based ones in its experiments (the paper's claim, quoted with its machines) and does **not** claim anything about how widely it is used in production, which is **not checked** and left out unless a primary source is found.
