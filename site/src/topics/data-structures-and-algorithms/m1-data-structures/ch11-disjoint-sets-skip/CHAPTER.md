## The chapter

### The problem it solves

Chapters 1–10 each answered "how do I store and find things". This chapter holds three structures whose job is narrower and whose cost is hidden inside bigger systems. A pipeline that merges 10⁷ "record i matches record j" pairs must answer "are these two already one entity?" after every pair, and a labelled array or a graph search per pair is quadratic; union–find does it at an amortized cost that grows like the inverse Ackermann function, which is at most 4 for any n that fits in the universe (to verify; topic 38). A storage engine's in-memory write buffer must be ordered, must allow readers to run while a writer inserts, and a balanced tree's rotations make that hard; a skip list balances by coin flips and links a new node in with one pointer store per level (topic 39). A cache that is full must decide which entry to give up: least recently used is O(1) with the right pair of structures and is the textbook answer, until one table scan larger than the cache throws out everything that mattered (topics 40–41). The thread is **an invariant kept cheap on every operation**: the forest's rank bound, the tower-height distribution, the recency order, and the question the last topic asks: what recency forgets. Each topic also answers "what does this cost under contention or under adversarial input", the question Chapters 12–14 pick up (a filter in front of a cache, a lock-free ring, a concurrent map).

### Order of ideas, and why

1. **§11.1 Union–find (38).** First, because Chapter 10's last handoff asks it: after storing a graph's edges, how do you track which vertices are connected as edges arrive one at a time? Union–find is the structure for exactly that question, it consumes the chapter-10 edge list, and its analysis is the payoff of Chapter 1's potential method.
2. **§11.1 Skip lists (39).** Second, because it returns from "components" to an ordered dictionary, the kind of structure Chapters 4–5 built, with the opposite balancing idea: randomness instead of an invariant. It is also the memtable structure Chapter 5 named, and it is the bridge to the concurrency chapter (14), where its easy-to-make-concurrent property is the point.
3. **§11.2 LRU caches (40).** Third, a new problem (a bounded memory deciding what to evict) built from structures already taught (hash table plus doubly linked list). It opens §11.2, and the Data Engineering domain teaches the same policies from the database side (§5.1 buffer pool, §5.5 caching), which this topic points to rather than repeats.
4. **§11.2 Scan-resistant policies (41).** Last, because it only makes sense as the answer to LRU's failure: why one scan flushes the cache, and the four designs (LFU with decay, 2Q, ARC, LIRS) that each remember something recency does not.
5. **Handoff to Chapter 12.** Topic 41 ends on ARC's and 2Q's *ghost lists*: lists of keys already evicted, kept only so a second request can be recognised. That is a set-membership question answered with a full key per entry. Chapter 12 opens with Bloom filters: the same question in a few bits per key, with an error in one direction only.

**Skipped in this chapter** (stay in the curriculum, get no reel, per `syllabus/review-notes/dsa-cuts.md`, "Chapter 11 — Disjoint Sets, Skip Lists and Cache Structures (1 of 5)"): **Admission and FIFO-based eviction** (§11.2: W-TinyLFU's sketch-based admission in Caffeine, S3-FIFO at SOSP 2023, SIEVE at NSDI 2024). They are named once, in topic 41's post-notes "Where this goes next", with their venues; none is built. The syllabus's own *Lab* names SIEVE; see "Notes for the release run".

### Shared notation and terms

- **Union–find:** elements 0…n−1 (or the letters A–F in the picture); `parent[x]`; a root has `parent[x] = x`; `find(x)` returns the root; `union(x, y)` joins two sets; **rank** and **size** as the two union rules. **α(n)** is always the inverse Ackermann function, written with its argument and said "inverse Ackermann of n", never read as a load factor (the Chapter 1 convention, which wrote it α(n) beside the load factor α = n / cap). **log\*** is written `log*` and said "iterated logarithm".
- **Skip list:** level 0 is the full sorted list; `p` is the promotion probability and the tower height h of a node is the number of levels it appears on; `L(n) = log_{1/p} n`. Written exactly as Pugh writes them so a reader of the paper recognises them.
- **Caches:** **C** the capacity in entries; **hit**, **miss**, **miss ratio** (the chapter reports miss ratio, as the syllabus lab does); **recency** (how long ago), **frequency** (how many times), **reuse distance** (distinct entries touched between two uses of one entry). A software "cache miss" is named as such; the CPU event is `cache-miss` from Chapter 1.
- **Spoken numbers:** narration has no digits, symbols or code names (automatic check). Say "inverse Ackermann", "iterated logarithm", "union by rank", "path compression", "path halving", "probability one in four", "least recently used", "clock hand", "ghost list", "reuse distance"; speak every number in words (QUALITY.md #29). Redis config names (`maxmemory-samples`) and Java class names are not spoken.

### 38. Union–find (`dsa.union-find`): full, §11.1

- **Folder:** `union-find`. About 14 min.
- **Scope (syllabus clause → what it delivers):**
  - "union by rank/size": the forest representation (`parent` array, roots point to themselves); the naive union that links one root under the other and builds a chain of height n−1 under an adversarial order; union by size (smaller tree under the larger) and union by rank (shorter under taller, rank rises only on a tie), and the invariant that bounds the height of either at log₂ n, with the proof in one frame (a node's depth rises only when its tree at least doubles).
  - "path compression (or halving/splitting)": compression makes every node on the find path point to the root (two-pass, or recursive); path halving makes every other node on the path point to its grandparent in one pass; splitting makes every node point to its grandparent; why the one-pass variants exist (no second pass, no recursion stack) and that they carry the same bound (to verify in Tarjan and van Leeuwen 1984).
  - "the O(α(n)) amortized bound (Tarjan 1975)": the statement — m operations on n elements cost O(m·α(m, n)) with union by rank or size plus compression, α the inverse of the Ackermann function, at most 4 for any n that fits in the universe (to verify against the sources named below); the shape of the proof (rank, levels of the Ackermann hierarchy, `log*` as the first rung of the ladder) and **not** the proof; what the bound does not say (per-operation cost can still be Θ(log n); the bound is amortized and there is no matching worst-case); that the potential form of the argument is cited from the sources and not re-derived (Chapter 1 topic 6 already states that Tarjan's 1975 proof is not a potential argument and cites the 2023 potential proof; this topic repeats neither claim); the lower-bound side named, with the claims to be verified at research time (Tarjan 1979, pointer machines; Fredman and Saks 1989, cell probes).

### 39. Skip lists (`dsa.skip-lists`): full, §11.1

- **Folder:** `skip-lists`. About 14 min.
- **Scope (syllabus clause → what it delivers):**
  - "geometric tower heights": every node gets a height by repeated coin flips with promotion probability p (Pugh's original p = ½, his recommendation p = ¼; LevelDB's `kBranching = 4` with `kMaxHeight = 12`; Redis's `ZSKIPLIST_P` 0.25 with `ZSKIPLIST_MAXLEVEL` 32, both read from source at planning time); the height of a node is geometric, so the fraction of nodes at level i or above is pⁱ; the expected number of pointers per node is 1/(1−p) (4/3 at p = ¼, 2 at p = ½, derived and asserted in `examples.py`); the cap and why it is safe (Pugh: MaxLevel = L(N), with the expected maximum level at most L(n) + 1/(1−p)).
  - "expected O(log n) search": the search path (start at the top-left, step right while the next key is smaller, else drop a level) and its expected length, analysed backwards as Pugh does (a climb up levels, each step a coin flip), stated with its constants from the paper and checked against a measured seeded run; **expected** in the Chapter 1 sense (over the coin flips, not over inputs), why no input sequence is consistently bad, and Pugh's quoted tail statement (for more than 250 elements, the chance a search takes more than 3 times the expected time is less than one in a million, to be quoted from the paper).
  - "simple ordered iteration": level 0 is a sorted linked list, so iteration is a pointer walk and a range scan is one search followed by that walk; against a tree's in-order traversal; the one asymmetry (LevelDB's iterator has no `prev` pointer, so `Prev` is a fresh search for the last node below the key, read from `skiplist.h`).
  - "why they are easy to make concurrent": inserting a node is splicing it into each level, bottom-up, and a splice is a single pointer store at each level, so a reader on any level always sees a consistent list; a tree rotation rewrites several pointers that must change together. LevelDB's `skiplist.h` states the contract: writes need external synchronization, reads need none beyond the list not being destroyed, nodes are never deleted until the whole list is, a node's contents are immutable after it is linked, and release-stores publish nodes (`SetNext`) that readers acquire-load (`Next`). The topic explains that argument with one picture of the release/acquire pairing and nothing more: the memory-model detail is Rust Systems Engineering Chapter 7, **declared** here, and the lock-free multi-writer algorithms are Chapter 14 (the *(skipped)* "Concurrent skip lists" and the progress-guarantee topics).
  - "the memtable in LevelDB/RocksDB": the skip list as Chapter 5's memtable: sorted, ordered iteration for the flush to an SSTable, point lookup and insert in expected O(log n); RocksDB's default memtable is skiplist-based, `write_buffer_size` defaults to 64 MB, and only the skiplist memtable supports concurrent insert (RocksDB wiki, read at planning time); the other memtable types named only.
  - "Redis sorted sets (skip list + hash table)": a sorted set is a dict (member → score, for O(1) score lookup) and a skip list (score order, for O(log n) insert, range and rank), kept together; each skip-list link carries a `span`, the number of elements it skips, which makes `ZRANK` O(log n): the same rank augmentation as Chapter 4's order-statistic tree in a different structure. The Redis documentation's own statement ("a dual-ported data structure containing both a skip list and a hash table") and `server.h`'s `zset` struct are the sources; small sorted sets use a compact encoding controlled by `zset-max-listpack-entries` (128) and `zset-max-listpack-value` (64) in `redis.conf`: to verify the exact semantics before saying it.
  - "→ Ch.14": named, as the pointer to the concurrent-structures chapter; nothing of Chapter 14 is built here.
- **Outcomes:**
  - Build a skip list with seeded coin flips and show its height histogram and expected pointer count at p = ¼ and p = ½.
  - Trace a search and an insert, state the expected search cost with its constants and say what "expected" ranges over.
  - Explain why a reader can run with no lock while a writer inserts (the one-store-per-level splice), and name where a Redis sorted set and a LevelDB memtable use this.

### 40. LRU caches (`dsa.lru-caches`): full, §11.2

- **Folder:** `lru-caches`. About 14 min.
- **Scope (syllabus clause → what it delivers):**
  - "hash map + doubly linked list for O(1) get/put": the two structures and why each is needed (the map finds an entry in O(1), the doubly linked list orders entries by recency and lets a node be unlinked and moved to the front in O(1) because the node knows its own neighbours: the exact "where lists still win: O(1) splice" payoff of topic 11, "Linked and intrusive lists"); `get` = lookup, unlink, push front; `put` = insert at front and evict the tail on overflow; the O(1) bound and what makes it hold; a get is a write (it reorders the list), the fact that makes the next clause necessary. ### 41. Scan-resistant policies: LFU, 2Q, ARC, LIRS (`dsa.scan-resistant-policies-lfu`): full, §11.2

- **Folder:** `scan-resistant-policies-lfu`. About 15 min.
- **Scope (syllabus clause → what it delivers):**
  - "why plain LRU is flushed by one large scan": the scan trace measured: a hot set that fits in the cache, one scan longer than the cache, and LRU's miss ratio before, during and after (every hot page evicted, then re-fetched); the cause in one sentence (recency alone cannot tell a page touched once from a page reused); real defences named for context: PostgreSQL's 256 KB ring for sequential scans (read from its buffer README) and that PostgreSQL once shipped ARC (8.0) and replaced it with 2Q in 8.0.2 "to avoid a pending US patent on ARC", then moved to clock sweep in 8.1 (release notes read at planning time). The full buffer-pool design is Data Engineering's and is pointed to, not retold.
  - "frequency counting and decay": LFU (evict the least frequently used) keeps hot pages through a scan but never forgets: a once-hot page stays forever; decay (periodically halving or ageing counts) as the fix; Redis's LFU as the real instance: since Redis 4.0, a probabilistic (Morris) counter in a few bits per object, saturating near a million hits at the default `lfu-log-factor` of 10 and decaying every `lfu-decay-time` of one minute (Redis eviction documentation and `redis.conf`, read at planning time). The probabilistic counter is explained as a device and its approximate-counting theory is not developed; sketch-based admission (W-TinyLFU) is the skipped topic.
  - "ghost lists" (2Q and ARC): 2Q (Johnson and Shasha, VLDB 1994): a short FIFO `A1in` for first-time pages, a ghost list `A1out` of identifiers of pages that left `A1in`, and an LRU `Am` for pages seen again while in `A1out`; the suggested sizes (Kin 25% of the page slots, Kout 50%, read from the paper); a ghost entry holds the key and no data, which is what "I have seen this before" costs.
  - "adaptive partitioning in ARC (Megiddo & Modha, FAST 2003)": the cache split into a recency list T1 and a frequency list T2 with ghost lists B1 and B2, a directory of up to 2c entries for a cache of c, and one adaptation parameter p (the target size of T1) that rises on a hit in B1 and falls on a hit in B2, so the cache tunes itself to the workload; the paper's statement that ARC maintains no frequency counts and needs no tuning parameters (to quote exactly); ARC's one operational caveat named only as the PostgreSQL 8.0.2 release notes state it (replaced "to avoid a pending US patent on ARC"), with no claim about who holds a patent unless the research stage finds it in a primary source.
  - "reuse distance in LIRS": LIRS (Jiang and Zhang, SIGMETRICS 2002): rank pages by reuse distance (distinct pages touched between two consecutive uses) instead of recency, keep a small low-reuse-distance set (LIR) resident and let high-reuse-distance pages (HIR) cycle through a few slots; why this survives a scan and loops slightly larger than the cache where LRU gets zero hits. The paper's PDF could not be fetched at planning time (host refused it), so the definitions above are from a secondary description and **every LIRS claim is to be verified against the paper itself** at research time; if it cannot be opened, LIRS is reduced to the reuse-distance idea with the claim cut.
  - Names, without building, the skipped "Admission and FIFO-based eviction" topic (W-TinyLFU in Caffeine, S3-FIFO at SOSP 2023, SIEVE at NSDI 2024) in the post-notes: the SIEVE paper's abstract (read at planning time) says SIEVE needs fewer than 20 lines of code change on average in five production cache libraries and reports up to 63.2% lower miss ratio than ARC on 1559 traces; quote exactly or leave out.
  - The syllabus *Lab*'s cache half is completed here: ARC, 2Q and an LFU-with-decay on the same replay harness as topic 40, reporting miss ratio per policy on the public trace and on the scan trace.
- **Outcomes:**
  - Show, on a trace, why one scan flushes an LRU cache and which information (frequency, ghost history or reuse distance) each of LFU, 2Q, ARC and LIRS uses to protect the hot set.
  - Explain ARC's adaptation rule (what a hit in each ghost list says about which list is too small) and run it by hand on a short trace.
  - Choose a policy for a workload and say what each costs in memory per entry and per access.
- **Introduces:** `scan-pollution`, `lfu-frequency-decay`, `two-queue-2q`, `ghost-list`, `arc-adaptive-partition`, `reuse-distance-lirs`. **Uses:** `lru-cache`, `hash-map-doubly-linked-list`, `clock-reference-bit`, `sampled-lru`, `miss-ratio-trace-replay` (topic 40), `doubly-linked-list`, `fifo`, `queue` (Chapter 2: 2Q's `A1in` is a FIFO queue). **Declared:** none.
- **Bridge:** word for word, topic 40's handoff above ("Every variant in this topic answers the same question the same way… Scan-resistant policies, next.").
- **Handoff:** "Scan resistance came from remembering something LRU forgets, and the cheapest thing to remember turned out to be the identity of pages that were just evicted: a ghost list holds only keys, and its one job is to answer 'have I seen this before?' Exactly that question, at billions of keys, in a few bits each, and with a wrong answer allowed in one direction only, is its own data structure. Bloom filters, next."
- **Prerequisites panel:** topic 40 (Before this); topic 12 "Stacks, queues and deques" (Before this, for the FIFO in 2Q). Data Engineering "Buffer pool and page replacement" (another track, live) as the production view. On-site: none new. Chapter 34 "Online paging" as "Goes deeper later".
- **Pre-notes terms:** working set, sequential scan, access frequency, counter decay, ghost entry (an identifier kept after its data left), reuse distance (one line, since the topic defines it fully), FIFO queue (one line).
- **Hook:** a cache holds the 1,000 hottest rows and serves 90% of requests; one nightly report scans 5,000 rows once; the next morning's miss ratio is near 100% until the hot set warms back up. Under LRU, how many of the 1,000 hot rows survive the scan? None: every one was used before every scanned row, and recency alone cannot tell a page touched once from a page reused.
