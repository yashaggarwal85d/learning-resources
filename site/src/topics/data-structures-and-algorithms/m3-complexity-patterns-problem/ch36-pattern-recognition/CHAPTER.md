## The chapter

### The problem it solves

Thirty-five chapters taught the toolkit. A senior engineer rarely meets a problem labelled with the chapter it belongs to. They meet a sentence: "given a log of ten million events and a query for the busiest minute", "schedule these jobs on those machines", "find the cheapest way to change this word into that one with a dictionary". The skill this chapter teaches is the step *before* the algorithm: reading the sentence for what it permits. It is four skills, taught in the order a good engineer applies them. **First, read the size and the limit as a budget** (topic 113): the input size n and the time limit say, before the problem is understood, which growth rates are allowed. **Second, read the operations as a structure choice** (topic 114): the mix of lookups, range queries, insertions and top-k asks says which of the structures from Milestone 1 pays for itself. **Third, read the situation as a graph when it is one** (topic 115): states and moves are vertices and edges, and the graph often need never be built. **Fourth, read the problem as a known one in disguise** (topic 116): flow, matching, 2-SAT, shortest path, an interval schedule, a DP on a DAG, and a short catalogue of patterns, each recognised by what it *asks for*, not by its story. The thread through all four: **recognition is a check against a list of necessary conditions, and a mismatch is as informative as a match** (a budget that rules out O(n²) has done real work before any algorithm is chosen; a problem that *looks* like a matching but has odd cycles in it is not a bipartite matching).

### Order of ideas, and why

1. **§36.1 Complexity budgeting from constraints (113).** First, because it is the cheapest filter: it uses nothing but numbers already on the page. The one table every competitive programmer carries (n ≤ 10 allows n!, n ≤ 20 allows 2ⁿ, n ≤ 500 allows n³, n ≤ 5000 allows n², n ≤ 10⁶ allows n log n or n, and "n is large" allows O(1) or O(log n)), *derived* from "a modern machine does some hundreds of millions of simple operations per second" and then *corrected* by what Chapter 1 taught: constants, memory traffic and cache misses (the budget at n ≤ 10⁸ is "linear and cache-friendly", the syllabus's own words). Plus the **signal words** that say which technique the budget points at ("sorted", "k-th", "all pairs", "minimum maximum").
2. **§36.1 Choosing the structure for the operation mix (114).** Second: having decided *how much* work, decide *how to organise the data*. The syllabus gives the dispatch table (lookup → hash; ordered or range → balanced tree or B-tree; top-k → heap or quickselect; membership at scale → filter; grouping → union–find; prefixes → trie; range aggregates → Fenwick or segment tree), and the topic's job is the part the table hides: *the mix is what chooses* (a structure that wins on one operation loses on another, so the decision is an inner product of operation frequencies and per-operation costs), and each row has a *breaking condition* (a hash table fails when order matters; a Bloom filter fails when you need the key back).
3. **§36.1 Modelling problems as graphs (115).** Third, because many problems that do not mention a graph are one, and recognising it unlocks Milestone 2's graph chapters at once. States as vertices and moves as edges (word ladders, puzzles, lock combinations), the **implicit graph** (the graph is a *function* from a state to its neighbours and is never stored: the 8-puzzle's 181,440 reachable states are generated, not listed), and the **layered graph** that turns a constraint such as "at most k discounts" into plain shortest-path by making the count part of the state.
4. **§36.1 Recognizing reductions to known problems (116).** Last, because it needs everything before it: a *catalogue* of the shapes that recur (flow, matching, 2-SAT, shortest path, interval scheduling, DP on a DAG) and of the patterns the course met as techniques (fast and slow pointers, top-K via a heap, k-way merge, intervals, matrix traversal, binary search on the answer, monotonic stack). The recognition rule the topic teaches is a *test of the necessary condition*: for each shape, the one structural fact the input must have, and the one *near-miss* that looks like it and is not (a matching problem with odd cycles; a shortest path with negative edges; a "scheduling" problem that is bin packing). It is also the place Chapter 33's direction of reduction is turned around (see "Inherits").
5. **Handoff to Chapter 37.** The chapter's last word is that a choice of structure is made from a *requirements* sheet, and the next chapter takes it to the place where it is made at the highest stakes: inside a database or a pipeline, where the structure is a hash table with a build phase and a probe phase and a spill to disk, not a textbook object. Chapter 37's first topic is "Hash tables inside hash joins".

**The chapter's *Lab*** ("take 30 unseen problems, and for each write only the recognized pattern, the target complexity and the key invariant within five minutes; then solve and score your recognition accuracy") is a practice protocol, not a program. It belongs to topic 116's post-notes, with the builder choosing the 30 problems from public sources whose licence it checks (see "Notes for the release run").

### Shared notation and terms

- **Budget, n, limit:** *n* is the input size as the statement gives it (possibly several parameters: n, m, q, W); the *limit* is the time limit; the *budget* is the number of simple operations the limit allows on the machine in question. The chapter writes the budget as a number of operations and the cost of an algorithm as a count of the *same* operations, so the comparison is a comparison of numbers.
- **Signal, pattern, shape:** a *signal* is a word or number in the statement that narrows the algorithm ("sorted", "k-th"); a *pattern* is a recurring technique the course taught (two pointers, monotonic stack); a *shape* is a recurring problem structure with a known algorithm (flow, matching). The chapter keeps the three words apart.
- **Near-miss:** a problem that satisfies the *surface* of a shape and fails the condition that makes the algorithm work. Each catalogue entry names one. This is the chapter's recognition test.
- **Reduction, in this chapter:** *to* a known polynomial-time problem, to show a new problem is easy. Chapter 33's `karp-reduction` goes the other way for hardness; the chapter never writes the bare word "reduction" without saying which way.
- **State, move, implicit graph, layer:** a *state* is everything needed to say where you are; a *move* takes one state to another; an *implicit graph* is the graph whose neighbour function is code; a *layer* is a copy of the state space indexed by a counter.
- **Spoken numbers:** narration has no digits, symbols or code names (automatic check). Say "n log n", "big O of n squared", "two to the n", "hundred million operations a second"; speak every number in words (QUALITY.md #29). Names: Laaksonen, Skiena, Carroll, Aspvall, Plass, Tarjan, Kleinberg: the builder checks them against `site/narration/voice.json` aliases and adds missing ones.

### One visual language for the chapter's reel

The chapter builds from `site/src/reels/kit.tsx` and `DESIGN.md`'s briefing theme: black and white carry everything, colour is rare and means something. On top of that this chapter shares one grammar:

- **Colour:** `crema` the problem statement's own text and a structure or graph as it is; `latte` secondary labels (n, a count, a cost); `taupe` a candidate ruled out; `caramel` **the thing to look at**: the word or number in the statement that the recognition rests on, the structure chosen, the condition being tested; `cinnamon` (rare) **the alternative being compared**, always the same side of each pair: the budget against the algorithm's cost; the winning structure against the runner-up; `cherry` with `cherryText` **the bad outcome**: a growth rate over budget, a structure at its breaking condition, a near-miss that looks like the shape and is not.
- **The statement is drawn as text with its signals lit:** a one-sentence problem on screen, the words that matter locking on one at a time (`Reticle`, at most one per step) and a small label under each saying what it rules in or out. Never a bulleted list of tips.
- **A budget is drawn as a ruler:** a horizontal log-scale bar of operations from 10³ to 10¹⁸ with the limit as a vertical line at 10⁸ to 10⁹, each growth rate a tick placed at its count for the given n and coloured `cherry` where it crosses the line. A table of the form "n against allowed rate" appears only as the *result* of that picture.
- **A choice is drawn as a scored grid:** operations as rows, candidate structures as columns, each cell a measured cost, a row weighted by the mix's share (drawn as bar height); the winner locks on and the mix slider moves it. Not a decision tree.
- **A graph is drawn as what the problem is:** states as nodes with their real content (a word, a board, four digits), moves as edges drawn on demand (`Draw`) because the graph is implicit; a layered graph as stacked copies of the same graph with the cross-layer edges `caramel`.
- **A reduction is drawn as a function box from the new problem's input to the known problem's input,** the same visual as Chapter 33 with the arrow's meaning written on it ("solves it with"), so the reversal of direction is *seen*.

### 113. Complexity budgeting from constraints (`dsa.complexity-budgeting-from-constraints`): full, §36.1

- **Folder:** `complexity-budgeting-from-constraints`. About 15 min.
- **Scope (syllabus clause → what it delivers):**
  - "reading n, value ranges and time limits as a budget": the derivation, in the order a reader can check: a machine does on the order of 10⁸ simple operations per second (Laaksonen, read at planning time: "a modern computer can perform some hundreds of millions of operations in a second"), so a time limit of one second is a budget of about 10⁸ operations (a rule of thumb the topic labels as one, and measures on the builder's machine); an algorithm's cost is a count of the same operations; the comparison is a division. The *worked arithmetic that makes the table fall out* (running example): n² at n = 10⁵ is 10¹⁰ operations, about 100 seconds, so too slow; n log₂ n at n = 10⁵ is 1,660,964, 0.017 seconds; so the table is not memorised but *computed*. Value ranges as the second parameter: when the statement bounds values by V, a table of size n·V, or an array indexed by value, is in play (Chapter 33 topic 108's pseudo-polynomial warning is the reason the topic checks *both* n and the values).
  - "(n ≤ 20 → 2ⁿ; n ≤ 10⁵ → n log n; n ≤ 10⁸ → linear, cache-friendly)": the syllabus's three anchors, and the fuller table from the source (Laaksonen, read: n ≤ 10 → O(n!), n ≤ 20 → O(2ⁿ), n ≤ 500 → O(n³), n ≤ 5000 → O(n²), n ≤ 10⁶ → O(n log n) or O(n), "n is large" → O(1) or O(log n); the book's *own* hedge that "a time complexity is only an estimate of efficiency, because it hides the constant factors", read), with each row *derived* (not recited) and each given its **meeting-in-the-middle exception** (the 2ⁿ at n = 40 is 1.1 × 10¹², and two halves of 2²⁰ each is 2,097,152: the exception the *(skipped)* Chapter 23 "Meet in the middle" topic builds, named once here with only that arithmetic). The **cache-friendly** clause at n ≤ 10⁸, taught: at 10⁸ elements the work *must* be a sequential pass (one scan, a prefix sum, a counting pass), because a random access per element is a cache miss (Chapter 1 `cache-miss`, `word-ram`: the rule of thumb's "operation" assumes a hit), shown by the builder's measurement of the same count of operations as a sequential loop and as a random-access loop (the running example's second row); the word-RAM caveat that numbers beyond a word cost more, with a one-sentence pointer to Chapter 1.
  - "signals like 'sorted', 'k-th', 'all pairs', 'minimum maximum'": a *signal* is a word that narrows the technique, taught as a pair (the word, the question it should provoke), each demonstrated once on a small instance against a brute force: **"sorted"**: is there a binary search (Chapter 16's topic 55, by title) or a two-pointer scan (Chapter 24's two pointers, by title); **"k-th"**: quickselect or a size-k heap (Chapter 6 `binary-heap`; Chapter 16's quickselect, by title) at O(n) or O(n log k); **"all pairs"**: *is n² allowed by the budget?* If yes the answer is the double loop; if no, the pairs must be *counted or aggregated without being listed* (sorting then two pointers, a hash of complements, a sweep: Chapter 28 `sweep-line`); **"minimum maximum"** (or "maximise the minimum"): a monotone predicate over the answer, so *binary search on the answer* (Chapter 16 topic 56, by title; the predicate "is there a solution with maximum ≤ x?" is checked in O(n) and the search adds a factor log of the range: 30 iterations for a range of 10⁹, 60 for 10¹⁸, so 3,000,000 operations at n = 10⁵ and 10⁹ range, *computed*). The topic is explicit that a signal is a *hint with a failure rate*: "sorted" can also mean "so a merge works" and "all pairs" can mean "so it is a graph". 
  - What the budget *cannot* say, and the exit: an over-budget exact algorithm for a problem that is NP-hard (Chapter 33) is a reason to reach for approximation or a heuristic (Chapter 34 `approximation-ratio`, `heuristic-without-guarantee`): "n ≤ 20 → 2ⁿ" is *also* a hint that the problem is hard and small on purpose. The budget gives a necessary condition (the algorithm's cost must fit) and never a sufficient one (fitting does not make the algorithm correct). The final frame is the three-question routine the topic ends on: *what is n and what are the values? what does the limit allow? what do the signal words point at?*

It builds no algorithm; every algorithm named is a pointer to the topic that built it (by id if published, else by syllabus title and number).

  - Say why n ≤ 10⁸ forces a sequential pass, and measure that claim.

### 114. Choosing the structure for the operation mix (`dsa.choosing-structure-operation-mix`): full, §36.1

- **Folder:** `choosing-structure-operation-mix`. About 14 min.
- **Scope (syllabus clause → what it delivers):**
  - "lookup → hash": the first row, with its **cost and its breaking condition**. A hash table (Chapter 3 `separate-chaining`, `open-addressing`, `swiss-table`) answers *equality lookup* in expected O(1) and answers nothing about order. The mix that favours it, the mix that breaks it (a "next larger key" or a range scan: the table has no order to consult; the builder runs the failing call), and the engineering note that a *worst-case* bound needs more than the average-case one (Chapter 3 topic 16's `hashdos`, used by id).
  - "ordered/range → balanced tree or B-tree": a **balanced tree** (Chapter 4 `binary-search-tree`, `red-black-invariant`) for in-memory ordered access and a **B-tree or B+-tree** (Chapter 5 `b-tree`, `b-plus-tree`, `sibling-link-range-scan`) when data is paged or on disk, giving predecessor, successor and range in O(log n) plus the output, and what each costs (more per insert than a hash, pointer or page structure). The measured crossover in the running example: at which share of range queries a tree starts to beat a hash plus a sort-on-demand.

  - "membership at scale → filter": a **Bloom filter** (Chapter 12 `bloom-filter`, `bloom-false-positive-rate`, `bloom-space-lower-bound`) when the set is too large to hold, a wrong "yes" is cheap and a wrong "no" is impossible; its breaking conditions (it cannot return the key, cannot list members, cannot delete: `bloom-no-delete`), and the decision rule *what does a false positive cost, and what does the exact set cost?* The builder prices both for an LSM-read-shaped workload using Chapter 12's bits-per-key arithmetic (used, not re-derived).
  - "grouping → union–find": **disjoint sets** (Chapter 11 `disjoint-set-union`, `path-compression`, `cycle-test-by-union`) for *incremental* equivalence (merge groups, ask whether two items are in the same group) in near-constant amortised time; its breaking condition (it cannot split a group, and cannot enumerate a group's members without extra work) and the contrast with the other thing "grouping" can mean: *group-by aggregation* over a dataset is a hash table, not union–find (Chapter 3; named, with Chapter 37's "Union–find inside entity resolution" as the data-systems case).
  - "prefixes → trie": a **trie** (Chapter 7 `trie`, `node-representation`, `trie-lookup-bound`) for prefix queries and ordered iteration over strings, lookup bounded by the key length and not the number of keys; its breaking condition (a *substring* query, not a prefix one, is a different problem: the *(skipped)* suffix structures and Aho–Corasick of Chapter 27) and its memory cost against a hash.
  - "range aggregates → Fenwick/segment tree": a **Fenwick tree** (Chapter 8 `fenwick-tree`, `prefix-sum-query`) for prefix sums with point updates and a **segment tree** (Chapter 8 `segment-tree`, `lazy-propagation`, `associative-combine-function`) for general range queries and range updates, at O(log n) each; the breaking conditions (a Fenwick tree needs an *invertible* operation for range sums from prefix sums, a segment tree needs an *associative* one: so a range *maximum* needs the segment tree, and a *static* array with no updates is better served by prefix sums or a sparse table, Chapter 8's static range-query material if built, otherwise named only).
  - **The part the table hides, which is the topic's thesis:** the structure is chosen by the *mix*, not by the biggest single operation. A cost model the topic makes explicit: total cost ≈ Σ over operations of (frequency × per-operation cost), so a structure with a cheap common operation and an expensive rare one beats the reverse, and the ranking *changes* with the mix. The builder runs the running example's three mixes and prints a table in which the winner differs (a hash for the first mix, a tree for the second, a heap-assisted structure for the third); it also states what the model leaves out: constant factors, memory footprint and cache behaviour (topic 113's lesson again), concurrency (Chapter 14), persistence (Chapter 13), and the cost of building once against querying many times (a static sorted array wins when the data never changes). ### 115. Modelling problems as graphs (`dsa.modelling-problems-as-graphs`): full, §36.1

- **Folder:** `modelling-problems-as-graphs`. About 15 min.
- **Scope (syllabus clause → what it delivers):**
  - "states as vertices and moves as edges (word ladders, puzzles, lock combinations)": the modelling move, taught by three problems that share one shape. A **word ladder** (change a start word to a target one letter at a time, every intermediate word in a dictionary; invented by Lewis Carroll, who said he invented it on Christmas 1877 and first noted it in his diary on 12 March 1878 as "Word-links", per the Wikipedia page read at planning time, **to be confirmed from a primary or scholarly source before the dates are stated**; the minimum number of steps is at least the Hamming distance between the words, Wikipedia read): vertices are dictionary words, an edge joins two words that differ in exactly one letter, and the shortest ladder is the shortest path in an unweighted graph, i.e. breadth first search (Chapter 17 topic 59, by title). A **sliding-tile puzzle** (the 8-puzzle): a vertex is a board, a move slides a tile into the blank. A **combination lock** with four wheels and ten digits: a vertex is four digits, a move turns one wheel one notch, and forbidden codes are removed vertices. The recognition step each time: *name the state (everything needed to know where you are and nothing more), the move, and the question (reachability, fewest moves, cheapest)*, and the observation that *the question is a graph question regardless of the story*. The distinction between the *state* chosen too small (the answer is wrong, because two situations that behave differently are merged) and chosen too large (the graph explodes): shown by the lock with and without a "visited a forbidden code" flag when the rule is about *order*.
  - "implicit graphs": the graph is a *function* from a state to its neighbours and is **never stored**. The 8-puzzle has 9!/2 = 181,440 reachable states and a maximum shortest distance of 31 moves from the goal (computed at planning time by breadth first search); the 15-puzzle has 16!/2 = 10,461,394,944,000 states (computed), so *only* an implicit representation is possible there, and the search must be one that does not need to enumerate the space (the topic names heuristic search such as A\* as the next tool, Chapter 18's *(skipped)* topic, with no claim). The *cost* of an implicit graph (the neighbour function runs on every expansion; the visited set is the memory cost and is a hash set, Chapter 3: the dominant term, and the topic shows its size on the lock and the 8-puzzle) and the *trick* that makes the word ladder cheap (generate neighbours through wildcard buckets: `h_llo`, `he_lo`, … five buckets per five-letter word instead of comparing a word against all others, so the *edges are found without being compared*; the builder counts edges by the naive pair scan and by the buckets and asserts they agree, then times both). Where the topic touches Chapter 10: an implicit graph is the extreme case of choosing a representation (topic 36's adjacency lists and matrices store the graph; this one *computes* it), and *when the graph is explicit* the layouts of Chapter 10 apply.
  - "layered graphs for constraints such as 'at most k discounts'": the idea that a constraint on a *count* is handled by making the count part of the state. A shortest path where up to k edges may be taken at half price: the state is (vertex, discounts used), the layered graph has (k + 1) copies of the graph, an ordinary edge stays inside a layer and a discounted edge goes from layer j to layer j + 1 at half cost, and the answer is the cheapest path to the target in *any* layer. Size: (k + 1)·V vertices and about (2k + 1)·E edges (running example: V = 10⁵, E = 3·10⁵, k = 3 gives 400,000 vertices and 2,100,000 edges, computed), so the cost grows *linearly in k*, which is why the technique works for small k and not for k of the order of V. The same device for "at most k stops", "exactly k edges", "must pass a checkpoint" (a two-layer graph: before and after) and "alternating colours" (a layer per colour). The *algorithmic* point: Dijkstra (Chapter 18 topic 63, by title) runs unchanged on the layered graph, because the *modelling* removed the constraint. The builder checks the layered shortest path against a brute force on small instances for the discount and the stops variants.
  - What the graph model *does not* give, and where it goes: a **near-miss** the topic states honestly, since this is a recognition skill: "find the longest simple path" and "visit every vertex once" *look* like graph problems and are NP-hard (Hamiltonian cycle is NP-hard, Erickson read at planning time: "The Hamiltonian cycle problem in directed graphs is NP-hard" and "Euler circuits are easy to find and construct in linear time"; the contrast between an Euler and a Hamiltonian circuit is the textbook example of two problems that differ in one word), so *modelling as a graph tells you which question is being asked and the question may still be hard*: Chapter 33's recognition applies at once, and the topic ends the thread with it. Also named, with no claim: the graph algorithms themselves (Chapters 17–20, by title), and 0-1 BFS and Dijkstra variants on a layered graph.
  - What this topic **does not** do, and where it goes: building the search algorithms (Chapters 17–18); explicit graph layouts (Chapter 10, used); heuristic search (A\*, *(skipped)*); Data Engineering's lineage and DAG graphs (§17.3 there; this topic is about *problems* modelled as graphs, not graph data).
- **Outcomes:**
  - Given a puzzle or a constrained-path problem, write down the state, the move and the question, and say which graph algorithm answers it.
  - Explain why an implicit graph can be searched when it cannot be stored, and what the visited set costs.
  - Build a layered graph for a count constraint, give its size in terms of V, E and k, and say when it stops being practical.

### 116. Recognizing reductions to known problems (`dsa.recognizing-reductions-known-problems`): full, §36.1

- **Folder:** `recognizing-reductions-known-problems`. About 16 min.
- **Scope (syllabus clause → what it delivers):**
  - "spotting flow, matching, 2-SAT, shortest path, interval scheduling or DP on a DAG inside a word problem": the **direction first, because Chapter 33 taught the opposite one.** Chapter 33's reductions go *from a known-hard problem to a new one*, to prove the new one hard. The reductions in this topic go *from a new problem to a known-easy one*, to prove it solvable and to get an algorithm for free: if you can map every instance of your problem to an instance of flow, solve it there and map the answer back, then your problem is no harder than flow (the same many-one idea, Chapter 33's `karp-reduction`, pointed the other way, **and the topic draws the two arrows in the same picture so the reversal is seen**). Six shapes, each taught by *the structural fact the input must have*, *what the statement's wording looks like*, *what to build*, and *the near-miss*:
    - **Shortest path** (Chapter 18, by title): costs on moves, a start and a goal, non-negative or the algorithm changes (Dijkstra's non-negativity is a condition; Bellman–Ford handles negative edges and detects negative cycles); *near-miss*: a "shortest path" that must visit every vertex or avoid repeating a vertex is the travelling salesman or longest path problem, NP-hard (topic 115's near-miss). The layered graph of topic 115 is how a *constrained* shortest path is reduced to a plain one.
    - **Flow and cut** (Chapter 20 `flow-network`, `max-flow-min-cut`, `residual-graph`, `ford-fulkerson`; published plan): *something moves from sources to sinks through capacity-limited links*, or the question is the *cheapest set of things to remove to disconnect*; build a network with capacities, a super-source and super-sink if there are several; the answer is the flow's value and the cut is the certificate (the max-flow min-cut theorem); *near-miss*: flow where each unit must be routed *whole* along one path with an indivisible demand (integral multicommodity flow) is NP-hard, which the topic states only if the builder reads a source for it.
    - **Matching** (Chapter 20 `bipartite-matching`, `matching-as-unit-flow`, `hopcroft-karp`, `konig-theorem`, `hall-obstruction`): *pair items from two groups, each used at most once, with allowed pairs*; the structural fact is that **the graph is bipartite**; build the bipartite graph and run the flow-based or Hopcroft–Karp algorithm; *near-miss*: pairing within *one* group (roommates, a general graph with odd cycles) is **not** bipartite matching and needs the *(skipped)* blossom algorithm of Chapter 20's skipped topic, so the recognition test is "can the items be split into two sides so that every allowed pair crosses?". König's theorem as the shortcut for "minimum vertex cover in a bipartite graph" (a use Chapter 34's vertex cover topic relies on).
    - **2-SAT** (Chapter 17 topic 62, by title, strongly connected components): *a set of yes/no choices with constraints that each involve at most two choices* ("if A then B", "not both A and C"); build the implication graph (a vertex per literal, two edges per clause); satisfiable iff no variable and its negation lie in the same strongly connected component (Wikipedia's 2-satisfiability page, read at planning time, which names Aspvall, Plass and Tarjan 1979 for the linear-time algorithm *via strongly connected components*; **the primary paper to read before attribution**); the *near-miss* is the sharpest in the chapter: **three** choices per constraint is 3-SAT, NP-complete (Chapter 33 topic 107's `satisfiability`; the topic shows the same instance shape with clauses of size two solved in linear time and size three the entry point to NP-completeness), so the recognition test is *the arity of the constraints*.
