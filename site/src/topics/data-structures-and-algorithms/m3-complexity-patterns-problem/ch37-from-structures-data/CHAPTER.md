## The chapter

### The problem it solves

Thirty-six chapters taught each structure under its textbook contract: a hash table that fits in memory, a heap that holds its elements, a sort that has all its input, a graph that one thread can walk. A data system keeps the structure and breaks the contract. The hash table's build side no longer fits. The sort has to survive a memory budget it shares with other operators. The heap merges streams that arrive from files. The graph is a job graph with durations and a fixed number of workers. The set is clusters of records, built across machines. This chapter is eight bridge reels, one per structure, and each answers the same three questions in the same order: **what is the textbook structure, what constraint does the production system add, and what exactly changed in the structure because of it.** The answers are read from real source code and documentation (PostgreSQL's executor, Spark, RocksDB, Pebble, Velox, Airflow, Redis, Cassandra, HAProxy, Kafka), never from retellings. The learner leaves able to open an engine's source, recognize a Chapter 3, 6, 11 or 15 structure inside it, and predict which constraint bent it.

### Order of ideas, and why

The syllabus order is kept. It also reads as three movements.

1. **Memory is the constraint (117–119).** Hash joins (117) first: the build side that outgrows memory and the partition-and-spill answer, plus the two ways a join avoids work (Bloom-filter pushdown, skew handling). Sorting (118) takes the other spill path: external merge sort inside sorts, sort-merge joins and aggregations, and the hash-aggregation spill that falls back to sort. Heaps (119) then show the one kernel both share, the k-way merge, in LSM compaction and shuffle reads, and the bounded heap that makes `ORDER BY … LIMIT` cheap. 117 before 118 because 118 contrasts the sort path with the hash path; 118 before 119 because 119 zooms into the merge inside 118.
2. **The graph is the constraint (120–121).** Topological sort (120): a scheduler is Kahn's algorithm with a priority queue and a worker count. Union–find (121): entity resolution is connected components over a match graph that arrives in pieces.
3. **Placement and summary are the constraint (122–124).** Search trees (122): the index layer of a storage engine, where the textbook B+-tree and LSM tree are modified by versioned keys, by paging the index itself and by filters. Consistent hashing (123): partition assignment as a table that moves ownership of fixed units. Sketches (124): a summary is useful in a distributed aggregate only if it merges.
4. **Handoff to Chapter 38.** The chapter ends having read eight structures inside real systems. Chapter 38 turns from reading to building and proving: implement each structure once, argue it correct, test it, and explain it under time pressure.

**Skipped in this chapter:** none. All eight §37.1 topics get a reel. The syllabus's cross-references to Data Engineering and Rust Systems Engineering are respected: this chapter owns the *structure inside the system*, those own the system. Each topic below says where the line is.

### 117. Hash tables inside hash joins (`dsa.hash-tables-inside-hash`): full, §37.1

- **Folder:** `hash-tables-inside-hash`. About 15 min.
- **Scope (syllabus clause → what it delivers):**
  - "build/probe phases": the Chapter 3 hash table used as the middle of a join. The build side (the smaller relation, `customers`) is inserted into the table keyed on the join key; the probe side (`orders`) streams past it, one lookup per row, never stored. Two real tables are read, one per Chapter 3 family: PostgreSQL's executor (`nodeHash.c`, read at planning time on `master` and `REL_18_STABLE`) keeps a power-of-two bucket array with chained tuples, sizes it for `NTUP_PER_BUCKET` = 1 (REL_18), and stores each tuple's full 32-bit hash value in the tuple header (`hashjoin.h`: `uint32 hashvalue`) so later steps never rehash; Spark's `LongToUnsafeRowMap` (`HashedRelation.scala`, read at planning time) is an append-only open-addressing map for long keys whose own comment says quadratic probing with triangular numbers addresses the slots. The topic says in one sentence why each family fits its engine (chaining tolerates variable-size tuples and load above 1; open addressing on a single `long` key is compact and cache-friendly) and leaves the chapter-3 mechanics to Chapter 3.
  - "partitioning for cache and memory (Ch.31)": the same hash value is used twice. PostgreSQL's `ExecHashGetBucketAndBatch` (identical on `master` and `REL_18_STABLE`) takes the low bits for the bucket (`hashvalue & (nbuckets - 1)`) and the next bits, by rotating right by `log2_nbuckets`, for the batch (`& (nbatch - 1)`), so a row's batch and bucket are independent and the number of batches is a power of two. **Memory:** the batch count is chosen so that one batch's table fits the budget M; the planner estimates it, and the executor measures the real size and doubles the batch count when the table outgrows the budget (header comment of `nodeHashjoin.c`: "The number of batches is always a power of two, so an increase in the number of batches doubles it"). **Cache:** a table whose bucket array is larger than the cache (and the TLB's reach, Chapter 1) pays a miss per probe; partitioning until each piece fits is the same idea one level up. Multi-pass radix partitioning sized to the cache and TLB is Chapter 31's skipped "Radix-partitioned in-memory joins": named once, not built. The partitioned and hybrid hash join *algorithm* (recursive partitioning, a resident partition, skew handling in general) is Chapter 31's topic "Partitioned hash joins: Grace and hybrid" (topic 104, planned); this topic shows only what a production executor changed in it.
  - "Bloom-filter pushdown": a Bloom filter built from the build side's join keys is sent to the probe side's scan, which drops rows that cannot match before they are shuffled or joined. Spark (`InjectRuntimeFilter.scala`, read at planning time): the rule inserts a filter on the "application side" when one can be extracted from the "creation side"; the docstring says "The runtime filter is logically an IN subquery with the join keys. Currently it's always bloom filter"; the documented defaults (Spark 4.2.0 configuration page, read at planning time): `spark.sql.optimizer.runtime.bloomFilter.enabled` true (since 3.3.0, "if one side of a shuffle join has a selective predicate"), `expectedNumItems` 1,000,000, `numBits` 8,388,608, `maxNumItems` 4,000,000, `applicationSideScanSizeThreshold` 10GB. **The surprise:** those two defaults are about 8.4 bits per expected item, so Chapter 12's formula gives the filter's false-positive rate before a row is read; the builder computes it at the k Spark's `BloomFilterImpl` uses (to read at research time) and checks it against a measured filter. Trino's dynamic filters (read at planning time, Trino 484 documentation) show the other design: the build side's *distinct values* are collected, and "When the build side exceeds these thresholds, Trino switches to collecting min and max values per column", a much coarser filter. The engine-level story (when the planner injects it, dynamic partition pruning, AQE) is Data Engineering's live topic "Adaptive execution and runtime filters"; this topic owns the Bloom filter as a data structure inside the join.
  - "and spilling when the build side outgrows memory → Data Engineering §2.3, Ch.7": batch 0 stays resident while the build side is read; once the budget is exceeded, tuples of the other batches (and, later, the probe side's rows for them) go to per-batch temporary files, and each later batch is loaded and joined on its own. PostgreSQL's growth has a guard (same header comment): "If after a batch increase, there is a batch which retained all or none of its tuples, the executor disables growth in the number of batches globally", the case of one key too frequent to split by any hash. And a skew table: `ExecHashBuildSkewHash` gives the most common join-key values of the outer relation their own buckets "up to the number of slots allowed based on available memory", limited by `SKEW_HASH_MEM_PERCENT` = 2 (`hashjoin.h`), so hot keys keep joining without being written to disk. How to read `work_mem`, `Batches:` and the spill in a plan, and Spark's choice between join strategies, belong to Data Engineering's live "Memory budgets, spilling and grace hash join" and its Chapter 7 topics; this topic stays on the table and its bits.
- **Outcomes:**
  - Trace a hash join's build, probe and spill on a small dataset with a fixed budget M, and count the rows written to and read back from temporary files.
  - Explain why one hash value is split into bucket bits and batch bits, why the batch count doubles, and why PostgreSQL stops doubling when a batch keeps all or none of its tuples.
  - Compute a runtime Bloom filter's false-positive rate from Spark's default bits-per-item and say what it costs a probe side that is not selective.

The rest of this milestone does the same one level down: when the problem is a production system, which textbook structure sits inside it, and what did the system have to change? The first answer is in every join: a hash table, with a memory budget it was never designed for."
- **Handoff:** "A hash join whose build side does not fit in memory is cut by hash into partitions, written to temporary files, and joined one partition at a time. That is the hash path out of memory. The other path is a sort: sorted runs written to disk and merged back, inside sorts, sort-merge joins and aggregations alike. - **Prerequisites panel:** Chapter 3 topics 18 and 20 (Before this, for open addressing and resizing); Chapter 12 topic 42 (Before this, the Bloom-filter rate); Chapter 31 topic 104 (Before this, once live); Chapter 1 topic 9 "Measuring the memory hierarchy" (TLB reach). On-site: none new.

- **Hook:** the shop joins a large `orders` table to a smaller `customers` table with a memory budget that holds one twentieth of the build side (the builder scales the sizes down; the ratio is what matters). A textbook hash join cannot start: its table does not fit. Yet PostgreSQL finishes, and the builder counts how often each order row is written to disk. ### 118. Sorting inside spilling operators (`dsa.sorting-inside-spilling-operators`): full, §37.1

- **Folder:** `sorting-inside-spilling-operators`. About 14 min.
- **Scope (syllabus clause → what it delivers):**
  - "external merge sort (Ch.15) as the spill path of sorts": PostgreSQL's `tuplesort.c` (read at planning time, both `master` and `REL_18_STABLE`). Tuples are absorbed into an unsorted array until the memory budget is hit; if input ends first the array is sorted in memory; otherwise runs are written to logical tapes and merged. Four changes from the textbook are quoted from the file's own header, each as a modification with its reason: (1) **balanced k-way merge instead of polyphase** since PostgreSQL 15 ("with modern hardware, a straightforward balanced merge is better. Knuth is assuming that tape drives are expensive beasts"); (2) **run generation by quicksort, not replacement selection** ("Historically, we divided the input into sorted runs using replacement selection... but now we always use quicksort", and `master` adds "or radix sort"; REL_18 says only quicksort, so the topic states the version), which is the textbook's 2M-long-runs trick given up for speed and simplicity; Data Engineering's live "External merge sort and k-way merge" already built replacement selection, so this topic only says what production chose; (3) **prereading**: the merge needs only one tuple per run, but the file reads about `workMem/M` bytes at a time from each tape so the access pattern is sequential rather than "very erratic", the I/O model's block transfer applied to M runs at once; (4) **the final merge is done on the fly** ("saves one cycle of writing all the data out to disk and reading it in") when the caller does not need random access. `EXPLAIN` names the methods ("quicksort", "top-N heapsort", "external merge"; strings read in `tuplesort.c`). The pass-count bound and replacement selection stay with Chapter 15 topic 54 and Data Engineering §1.3.
  - "sort-merge joins": both inputs are sorted on the join key and merged; the production difference is in the buffer for runs of equal keys. Spark's `SortMergeJoinExec.scala` (read at planning time) takes two thresholds, `sortMergeJoinExecBufferSpillThreshold` and `sortMergeJoinExecBufferSpillSizeThreshold`, beyond which the buffered matches for one key spill, and reports a "spill size" metric: a key that appears many times on both sides is where a sort-merge join's memory goes. On the reduce side of a shuffle, when the dependency has a key ordering, `BlockStoreShuffleReader` creates an `ExternalSorter` (read at planning time), so a shuffle read is itself an external sort of fetched blocks. Which join the planner picks is Data Engineering's live join topics and Chapter 7's "Shuffle joins: sort-merge vs shuffled hash".
  - "and aggregations": two different spill designs for the same operator, both read at planning time. PostgreSQL's hash aggregation enters "spill mode" when the table is over budget: tuples for groups already in the table keep updating their transition states; tuples that would create a new group are written, partitioned by hash, to logical tapes and processed later, recursively if a partition is still too large (`nodeAgg.c`: partitions = estimate × `HASHAGG_PARTITION_FACTOR` 1.50, between `HASHAGG_MIN_PARTITIONS` 4 and `HASHAGG_MAX_PARTITIONS` 1024). Spark's `TungstenAggregationIterator` takes the other road: when the hash map cannot get memory it sorts the map's entries by grouping key and spills them, merges the spills with an external sorter, and continues as a **sort-based aggregation** ("Then, this iterator works in the way of sort-based aggregation"). A hash structure that becomes a sort when memory ends is this topic's surprise; the contrast with PostgreSQL's hash-partitioning of the same problem is the point, and the crossover between hash and sort aggregation (Data Engineering's live "Hash vs sort aggregation") is only referenced.
  - "→ Data Engineering §1.3, Ch.7": Data Engineering owns the algorithm's cost in the I/O model, the pipeline view and Spark's executor memory and spill metrics (Chapter 7 "Spill and shuffle memory pressure"); this topic owns the structural question: which sorted-run machinery sits inside which operator.
- **Outcomes:**
  - Trace a spilling sort through run generation, tape layout and the final on-the-fly merge, and say what each of PostgreSQL's four departures from Knuth buys.
  - Explain why a hash aggregation can spill by hash partitioning (PostgreSQL) or by turning into a sort (Spark), and what each costs in extra passes over the data.
  - Name the structure behind a sort-merge join's spill and behind a shuffle read, and where each reads its runs from.
- **Introduces:** `external-sort-spill-path`, `spilling-hash-aggregation`, `sort-merge-join-spill`, `sorted-run-merge-operator`. **Uses:** `io-model`, `io-sort-bound` (Chapter 1), `binary-heap`, `k-way-merge-bound` (Chapter 6), `hash-join-batch-spill` (topic 117: the hash partitioning the aggregation spill reuses). **Declared** (Chapter 15, planned, ids provisional): `external-merge-sort`, `run-generation`, `replacement-selection`, `quicksort-partitioning`, `radix-sort`.
- **Bridge:** word for word, topic 117's handoff above.
- **Handoff:** "A sort's spill path and a hash aggregation's fallback end in the same step: merge several sorted runs, one element at a time, with the next-smallest picked by a heap or a tree of losers. That merge is not confined to operators. It runs inside LSM compaction and shuffle reads, and a bounded copy of the same heap answers ORDER BY with a LIMIT. Heaps inside compaction, shuffle and top-N, next."
- **Prerequisites panel:** topic 117 (Before this); Chapter 15 topic 54 "External merge sort" (Before this); Chapter 6 topic 31 (Before this); Data Engineering "External merge sort and k-way merge" and "Hash vs sort aggregation" (another track). On-site: none new.
- **Pre-notes terms:** sorted run, memory budget, temporary file, tape (a logical sequential file), fan-in, group (in a GROUP BY), aggregate state, shuffle.
- **Hook:** `ORDER BY amount` over 20 million rows with room for 200,000. The textbook says: sort runs, merge them, log base M/B passes. But PostgreSQL abandoned the textbook's best run-generation trick (replacement selection, runs twice the memory) years ago. Predict: given memory for 200,000 rows and 20 million rows, how many runs does quicksort generation make, and how many merge passes if the engine can hold all runs' read buffers at once?
- **Visual idea:** the shared merge picture (k run streams into one output through a heap), preceded by the run-generation strip (a memory box filling, sorting, writing a run); the four departures as four small labelled swaps on the textbook picture, each `cinnamon`; the hash aggregation spill drawn twice side by side (hash-partitioned tapes against a sorted-map spill), counting rows written for each on the same group distribution.
- **Sources to start from:** PostgreSQL `tuplesort.c` and `nodeAgg.c` header comments (read at planning time, versions `master` and `REL_18_STABLE`); Spark `TungstenAggregationIterator.scala`, `SortMergeJoinExec.scala`, `BlockStoreShuffleReader.scala`, `ExternalSorter.scala` (read at planning time); the DuckDB engineering write-ups on external sorting and external aggregation (fetched at planning time, partly read: "K-way merge... is traditionally used for external sorting... because it minimizes I/O. Cascade merge... is used for in-memory sorting"; the 2024 post's "over-partition" argument for external aggregation; the newer sorting post is fetched but **not read**); Knuth vol. 3 and Chapter 15's sources for the algorithm.

### 119. Heaps inside compaction, shuffle and top-N (`dsa.heaps-inside-compaction-shuffle`): full, §37.1

- **Folder:** `heaps-inside-compaction-shuffle`. About 14 min.
- **Scope (syllabus clause → what it delivers):**
  - "k-way merges with heaps or loser trees in LSM compaction and shuffle reads": one kernel, found in five real files, all read at planning time. **A heap over streams, in LSM engines:** Pebble's `merging_iter.go` says "The core of a mergingIter is a heap of internalIterators... The heap can operate as either a min-heap, used during forward iteration... or a max-heap, used during reverse iteration", and "fixes" the heap after advancing the winner; RocksDB's `MergingIterator` (`table/merging_iterator.cc`) "uses a min/max heap to combine data from point iterators", with range tombstones put into the heap as two keys each (start and end), and a compaction builds its input iterator in `VersionSet::MakeInputIterator` (`version_set.cc`; the builder reads what it constructs from the input files before stating that it is a merging iterator over all of them). RocksDB orders its internal keys by user key and breaks ties by decreasing sequence number (`dbformat.h`: "breaks ties by decreasing sequence number"), so the newest version of a key comes first: the Chapter 5 tombstone and compaction ideas, seen as a heap comparator. That the compaction iterator then drops the shadowed versions is read in `compaction_iterator.h` and `compaction_job.cc` at research time (fetched at planning time, not read for this) before it is stated. **A heap over spills, in Spark:** `UnsafeSorterSpillMerger` holds a `PriorityQueue` of spill readers (it adds a reader only if non-empty, and its comment explains the empty-record trap it avoids), and `ExternalSorter.mergeSort` builds a Scala `PriorityQueue` of buffered iterators reversed because "PriorityQueue dequeues the max", dequeues one, takes its head, re-enqueues if more remain: the exact pop-then-replace of Chapter 6, and PostgreSQL's tuplesort merge ("a heap containing just the frontmost tuple from each source run") is the same. **A tree of losers, in Velox:** `TreeOfLosers.h` ("Implements a tree of losers algorithm for merging ordered streams... At each call of next(), it returns the Stream that has the lowest value") is used by `Merge.cpp`; its constructor lays the leaves out to fill the last two levels of a complete tree (the 12-stream example in its comment), so the Chapter 6 bound of one root-to-leaf replay per output is code, not a proof. The topic measures both on the same k and n (`examples.py`) and reports comparisons per output; it does **not** claim that engines choosing a heap are wrong. It reports what each chose and what the comparison count is (the Chapter 6 bound is ⌈log₂ k⌉ for a loser tree against about 2·log₂ k for a binary-heap replace, verified by the builder).
  - "bounded heaps for `ORDER BY … LIMIT`": the top-N operator keeps only N elements in a heap whose root is the *worst* kept one, so each new row is compared with the root and either discarded (O(1)) or replaces it (O(log N)). Three real instances: PostgreSQL's `tuplesort.c` (`make_bounded_heap`: "we want to keep the largest entry at the root... This allows us to discard the largest entry cheaply. Therefore, we temporarily reverse the sort direction"; the switch rule in the source: it switches to a bounded heapsort "if the input tuple count exceeds twice the desired tuple count (this is a heuristic for where heapsort becomes cheaper than a quicksort), or if we've just filled workMem and have enough tuples to meet the bound"; the `EXPLAIN` label "top-N heapsort"); Spark's `BoundedPriorityQueue` ("only the top K elements are retained", replacing the lowest only if the new element is greater) used by `Utils.takeOrdered` and `RDD.takeOrdered`, whose plan is a bounded heap per partition then a `mergeOrdered` of the per-partition arrays, and `TakeOrderedAndProjectExec` in `limit.scala` ("This could have been named TopK, but Spark's top operator does the opposite in ordering"). The bound O(n log N) against sorting's O(n log n), and why the heap holds N and not n, are the topic's arithmetic. ### 120. Topological sort inside schedulers (`dsa.topological-sort-inside-schedulers`): full, §37.1

- **Folder:** `topological-sort-inside-schedulers`. About 14 min.
- **Scope (syllabus clause → what it delivers):**
  - "DAG orchestration": a scheduler decides what may run from a dependency graph. The textbook is Kahn's algorithm (Chapter 17 topic 61, planned): a task is ready when its in-degree, the count of unfinished upstream tasks, reaches zero. The production difference is that the graph is *live*: tasks finish at times the scheduler does not control, workers are limited, and the ready set is consumed in an order that matters. The chapter's DAG (12–16 tasks with durations, two or three workers) is run both ways: unlimited workers (the span is the critical path) and limited workers (a list-scheduling result). The Apache Airflow task graph is the real instance: tasks hold direct upstream and downstream relatives and the scheduler reads the task instances that are ready (`scheduler_job_runner.py`, read at planning time, orders the candidate task instances `.order_by(-TI.priority_weight, DR.logical_date, TI.region_index)`).
  - "ready queues": the ready set is a priority queue (Chapter 6), keyed here by a *weight*, not by a distance. Airflow's documentation (read at planning time): "`priority_weight` defines priorities in the executor queue. The default `priority_weight` is `1`, and can be bumped to any integer; larger numbers mean higher priority", with a `weight_rule` that is `downstream` by default; and the scheduler selects by `-priority_weight` first. The queue is also bounded by *slots* (pools, a slot count): a ready task with no slot waits. The topic shows the queue as a heap whose key was computed once when the DAG was parsed, not recomputed per step.
  - "critical-path prioritization": Airflow's default `downstream` rule is the sum of the task's own weight and the weights of **all downstream descendants** (`priority_strategy.py`, `_DownstreamPriorityWeightStrategy.get_weight`: `ti.task.priority_weight + sum(dag.task_dict[task_id].priority_weight for task_id in ti.task.get_flat_relative_ids(upstream=False))`; the docs: "upstream tasks will have higher weight and will be scheduled more aggressively"). **The topic's point: with the default weight of 1 per task, that number is one plus the count of descendants, not the longest chain below the task and not remaining duration.** The rule measures *how much depends on a task*, which is a different thing from *how long the dependent chain is*; a user who wants the critical path must set each task's `priority_weight` to its duration, and even then the sum is a total of work, not a maximum over chains. The critical path (Chapter 18 topic 66's longest path in a DAG, planned) is the max over chains of summed durations, and the sum over descendants adds each descendant once, *not once per path* (the builder reads `get_flat_relative_ids` to confirm that it yields each descendant once, so that a descendant reachable by two routes is counted once; a wide fan-out of short tasks can outweigh one long chain). The builder constructs a DAG where the two rules order two ready tasks differently, schedules it with each rule (default weights, and weights set to durations), and reports the finish time (the makespan): sometimes the sum rule is as good as the critical-path rule, sometimes worse, and the topic reports the measured numbers, not a general claim. Graham's list-scheduling bound for a greedy scheduler (makespan at most (2 − 1/m)·optimal) is the guarantee any ready-queue order has, derived by the builder in the Deep dive and cited to a source at research time (Chapter 34's skipped "Bin packing and makespan scheduling" is the full treatment, topic 110, planned).
  - "and cycle rejection": a DAG with a cycle can never run, so the scheduler rejects it when the DAG is loaded, before anything runs. Airflow's `DAG.check_cycle` (read at planning time) raises `AirflowDagCycleException(f"Cycle detected in Dag: ... Faulty task: ...")`, and the detector (`airflow_shared/dagnode/cycle.py`) is **an iterative three-colour DFS** (`_NEW`, `_IN_PROGRESS`, `_DONE`; its own comment: "Iterative rather than recursive: Python's stack depth limit is easily reached by a graph with long chains"; it returns the node whose edge closes a cycle). That is Chapter 17's DFS with back-edge detection (Chapter 17 topic 60, planned), chosen over Kahn here for the one thing the user needs, the *name of the faulty task*. The two methods are compared: Kahn's leftover nodes show *which* tasks are stuck, DFS names one edge; the builder shows both on the chapter's DAG with a planted cycle. The older module `dag_cycle_tester.py` is deprecated since Airflow 3.1.0 (file says so): the topic cites the current method.
  - "→ Data Engineering Ch.11": Data Engineering owns orchestrators as systems (scheduler loop, executors, pools, backfills, idempotency); this topic owns the graph algorithm and the queue inside. Airflow's `SKIP LOCKED` HA coordination and the metadata database are explicitly out.
- **Outcomes:**

### 124. Sketches inside approximate aggregation (`dsa.sketches-inside-approximate-aggregation`): full, §37.1

- **Folder:** `sketches-inside-approximate-aggregation`. About 15 min.
- **Scope (syllabus clause → what it delivers):**
  - "mergeable partial aggregates in warehouses and stream processors": an exact aggregate is mergeable when its *state* is small and associative: PostgreSQL's partial aggregation page (read at planning time) defines it: "run the aggregate's state transition function over different subsets of the input data independently, and then to combine the state values resulting from those subsets to produce the same state value that would have resulted from scanning all the input in a single operation"; MAX and MIN combine with the same comparison, SUM with addition; "it's usually impossible to define a useful combine function for aggregates that are sensitive to input row order". A sketch is the same contract for a question whose exact state is not small. The topic states the **merge law** (the merged sketch equals the sketch of the union of inputs, exactly for HyperLogLog's register maximum, within the error guarantee for quantile and top-k sketches) and tests it on the chapter's partitioned `orders` stream with 8 partitions: sketch each partition, merge, compare with a single-pass sketch and with the exact answer.
  - "HLL": Spark's `approx_count_distinct` is "the estimated cardinality by HyperLogLog++", with `relativeSD` default 0.05 (Spark source `HyperLogLogPlusPlus.scala` and the 4.2.0 function page, read at planning time; the source cites Google's HLL++ paper); BigQuery's `HLL_COUNT.INIT`, `HLL_COUNT.MERGE`, `HLL_COUNT.MERGE_PARTIAL` and `HLL_COUNT.EXTRACT` (function page read at planning time: "HLL++ functions are approximate aggregate functions. Approximate aggregation typically uses fewer resources than exact aggregation functions, like `COUNT(DISTINCT)`") expose the *sketch* as a value so rollups can be merged in SQL; Spark 4.2.0 also lists `hll_sketch_agg` and `hll_union_agg` (whose docs speak of an "HllSketch" and its `lgConfigK`; the library behind them is read at research time) and `theta_sketch_agg`/`theta_union_agg`/`theta_intersection_agg`. The structure itself is Chapter 30 topic 101; this topic owns *where the register array travels* (a byte string between operators) and the merge by element-wise maximum, which the builder verifies on the chapter's partitions.
  - "KLL/t-digest": Spark has `kll_sketch_agg_*` and `kll_merge_agg_*` (default `k` 200, range 8–65535, 4.2.0 page read at planning time) and `percentile_approx` whose `accuracy` default is 10000 with relative error 1/accuracy (page text), implemented in Spark by `QuantileSummaries.scala`, which cites Greenwald and Khanna and has a `merge` method (read at planning time); Druid's DataSketches extension offers Theta, Tuple, Quantiles and KLL sketches ("Sketches are data structures implementing approximate streaming mergeable algorithms... can be stored in Druid segments as additive metrics", read at planning time). Which engine uses which sketch is read at research time per engine; **no claim about t-digest or DDSketch usage in any named product is made from this plan** (not opened). The DE topic on quantile sketches (planned) owns the guarantees; this topic owns merging.
  - "and reservoir samples": Spark's `RangePartitioner.sketch` takes a per-partition **reservoir sample** (`SamplingUtils.reservoirSampleAndCount`, seeded from the partition index) and uses the samples to choose range boundaries so that output partitions are roughly balanced (`samplePointsPerPartitionHint` default 20, sample size capped at 1e6, oversampling by 3, re-sampling partitions much larger than average; source read at planning time). A sample is mergeable only if the merge is weighted by the number of items each came from; Spark's `sketch` returns `(numItems, sketched)` for exactly that reason. This is the one place in the chapter where a data system's *own planning* uses a sketch-like structure; the topic uses it as its closing example because it connects to topic 123 (range partition boundaries) and topic 117 (balanced partitions). Chapter 29 "Reservoir sampling" (planned) owns the algorithm.
  - "→ Data Engineering §5.6": Data Engineering owns the sketches' error guarantees, sizing, persistence as stored aggregates ("Sketches as stored, mergeable aggregates", skipped there) and production usage. This topic owns the structural idea: **a sketch is useful inside a distributed aggregate exactly when it has a merge**, and it names which parts of an aggregate pipeline (map-side combine, shuffle, final merge) the sketch travels through (Chapter 32 topic 106's combiner, planned).
  - **The negative result, measured.** Averaging per-partition percentiles is wrong and the topic shows it on the chapter's skewed partitions: the average of eight partition medians against the true median and against a merged KLL or GK sketch. Averaging two HyperLogLog estimates is wrong for the same reason (distinct users overlap across partitions). Both are computed in `examples.py`; the sketches are implemented from the cited descriptions or taken from a library whose version is recorded.
- **Outcomes:**
  - State the merge law for HyperLogLog, a quantile sketch and a top-k summary, and verify it on a partitioned stream.
  - Say why an exact `COUNT(DISTINCT)` is not mergeable by addition and an approximate one is mergeable by maximum, and show the error of the wrong merges.
  - Name where, in a map-combine-shuffle-merge aggregate, a sketch travels, and what it costs in bytes per partition.
- **Introduces:** `mergeable-partial-aggregate`, `sketch-merge-law`, `sketch-as-value`, `range-boundary-sampling`. **Uses:** `bounded-top-n-heap`, `distributed-top-n-merge` (topic 119: top-N per partition then one merge is the same shape), `fixed-slot-table`, `token-ring-partitioning` (topic 123: the same stream partitioned), `bloom-filter`, `bloom-filter-pushdown` (topics 117 and Chapter 12: a Bloom filter is also mergeable by OR if built with equal parameters, said once). **Declared** (Chapters 29 and 30, Chapter 32 topic 106, all planned, ids provisional): `hyperloglog`, `quantile-sketch`, `count-min-sketch`, `heavy-hitters-summary`, `reservoir-sampling`, `map-reduce-combiner`; the builder moves each to `uses` if the registry has it.
- **Bridge:** word for word, topic 123's handoff above.
- **Handoff:** "That closes the chapter's eight crossings: a hash table that spills, a sort that spills, a heap that merges, a queue that schedules, a union–find that clusters, a tree that indexes, a ring that places, a sketch that merges.
