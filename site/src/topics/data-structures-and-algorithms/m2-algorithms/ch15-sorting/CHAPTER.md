## The chapter

### The problem it solves

Every system sorts, and every serious system sorts with a hybrid: a standard library's `sort` is three or four algorithms stitched together, each covering a case another one handles badly. The learner arrives knowing the textbook trio (insertion sort, merge sort, quicksort) and the Ω(n log n) bound from Chapter 1, and leaves able to answer the three questions that decide which sort a real engine runs. **What does the input look like?** Random, already sorted, reversed, a few distinct values, nearly sorted with a burst of noise: five shapes, and an algorithm that is optimal on the first is catastrophic or merely wasteful on another. **What must the sort guarantee?** Stability (equal keys keep their order), a worst case (an adversary cannot make it quadratic), memory (in place, or n/2 spare). **What is the machine charging for?** Comparisons, branch mispredictions, cache lines, or block transfers: Chapter 1 named these costs, and this chapter is where they choose between algorithms with the same asymptotics. The thread through the seven topics is that **a lower bound is a statement about a model, and every real sort is a way of leaving the model**: by exploiting runs (topics 49, 52), by partitioning around duplicates (50), by bounding the worst case (51), by reading the key as digits (53), or by changing the unit of cost to a block (54). The chapter ends where Milestone 2's next chapter begins: a sorted array is the precondition for binary search.

### Order of ideas, and why

1. **§15.1 Elementary sorts and sorting networks (48, refresher).** First, because it names the vocabulary every later topic uses (stable, in place, inversion, comparison count) and answers the question the chapter starts from: why does the *slowest* algorithm get the last word in every hybrid? Insertion sort's cost is n + (number of inversions), so it is optimal on tiny and nearly sorted input, and a small sorting network is the branch-free form of the same idea. It uses Chapter 1's lower bound without re-proving it.
2. **§15.1 Merge sort (49).** Second, because it is the algorithm with the guarantee (n lg n comparisons, stable) and the one whose cost shows how close to the information-theoretic bound a real algorithm gets (17 against 16 at n = 8). Its natural variant (merge the runs the input already has) is the idea topic 52 industrialises.
3. **§15.1 Quicksort and partitioning schemes (50).** Third, the in-place counterpart: divide first, work after. The topic is the partition step and its variants, because that step is where duplicates, branch mispredictions and adversarial inputs each bite. It ends on the one thing quicksort cannot give, a worst case.
4. **§15.1 Heapsort (51, refresher).** Fourth, because it is the answer to that gap: in place, worst-case O(n log n), and the fallback inside every production quicksort. It is a refresher because Chapter 6 already built both of its halves; what the topic adds is why it is nobody's first choice (locality) and its role in introsort.
5. **§15.1 Timsort, Powersort and driftsort (52).** Fifth, the synthesis: run detection (49's idea), insertion sort on short runs (48), galloping (a binary search inside the merge), and a *merge policy* that decides which adjacent runs to merge. The policy is where a 2015 bug and a 2022 replacement live, and it is the topic that ties the chapter's themes together on two real libraries (CPython and Rust).
6. **§15.2 Counting, radix and bucket sort (53).** Sixth, leaving the comparison model for the word-RAM, as Chapter 1 topic 2 promised. It comes after the comparison sorts so that the escape is felt as an escape, and it hosts the chapter's in-memory benchmark lab (quicksort variants, a radix sort, a library sort, on the five shapes).
7. **§15.2 External merge sort (54).** Last, because it changes the unit of cost once more (a block, not a comparison) and uses topic 49's merge, Chapter 6's loser tree and Chapter 1's I/O sort bound together. It hosts the chapter's external-memory lab.
8. **Handoff to Chapter 16.** Topic 54 ends with a file sorted at the cost of a few passes over the disk. A sorted sequence is worth that price because of one operation it makes cheap. Chapter 16 opens with binary search, whose invariants and boundaries are famously easy to get wrong.

**Skipped in this chapter** (stay in the curriculum, get no reel, per `syllabus/review-notes/dsa-cuts.md`, "Chapter 15 — Sorting (2 of 9)"): **Introsort and pdqsort** and **SIMD and parallel sorting** (§15.1, §15.2). ### Shared notation and terms

- **Keys, records and order.** n records, each with a key; `a[lo, hi)` is a **half-open** range (the convention Chapter 16 uses for binary search; written the same way here). "Less than" is a strict weak order; equal keys are distinguished on screen by a letter tag (3a, 3b) so stability is visible.
- **Costs counted.** A sort is charged in **comparisons C(n)** and **moves** (writes of a record) separately; the reel names which it counts on its first step that counts. **Stable** means equal keys keep their input order; **in place** means O(1) extra memory beyond the input, with the exact exception stated (quicksort's recursion stack is O(log n) when the smaller side is recursed on first: say so, do not claim it uses none). **Adaptive** means the cost falls with the input's order; an **inversion** is a pair out of order, and **runs** are maximal ascending stretches.
- **Bounds.** ⌈lg n!⌉ is the information-theoretic minimum number of comparisons (Chapter 1 topic 4); lg is log₂ on screen where the base changes a number, plain log inside O(·) (Chapter 1's convention). External-memory costs are written exactly as Chapter 1 writes them: N, M, B in items, **sort(N) = Θ((N/B)·log_{M/B}(N/B))**, and the pass count log_{M/B}(N/M) of topic 54.
- **Spoken numbers:** narration has no digits, symbols or code names (automatic check). Say "insertion sort", "sorting network", "compare and exchange", "natural run", "galloping", "merge policy", "three way partition", "dual pivot", "least significant digit", "most significant digit", "replacement selection", "fan in"; speak every number in words (QUALITY.md #29). Library function names (`sort_unstable`, `list.sort`) and algorithm nicknames that are not words (pdqsort, ipnsort, driftsort) are not spoken: say "the unstable sort in the Rust standard library".

### One visual language for the chapter's reels

The chapter builds from `site/src/reels/kit.tsx` and `DESIGN.md`'s briefing theme: black and white carry everything, colour is rare and means something. On top of that this chapter shares one grammar:

### 48. Elementary sorts and sorting networks (`dsa.elementary-sorts-sorting-networks`): refresher, §15.1

- **Scope (syllabus clause → what it delivers):**

### 49. Merge sort (`dsa.merge-sort`): full, §15.1

- **Folder:** `merge-sort`. About 14 min.
- **Scope (syllabus clause → what it delivers):**
  - "top-down vs bottom-up": the **merge** procedure first (two sorted ranges into one in one linear pass: the two-pointer loop, between min(m, n) and m + n − 1 comparisons, so a merge of [1..8] with [9..16] costs 8 and a perfect interleaving 15, the topic's first predict question); then **top-down** (split at the midpoint, sort both halves, merge: the recursion tree of Chapter 1 topic 3 with a merge at every node) and **bottom-up** (merge adjacent runs of width 1, then 2, then 4, with no recursion and no stack); the identical comparison counts when n is a power of two and the exact way they differ otherwise (the builder computes both on n = 5, 6, 7 and every n up to a bound, and states what differs: the split points, hence the comparison count); the recurrence 2T(n/2) + n is **cited** as Chapter 1 topic 3's worked case 2, giving Θ(n log n), not re-derived. The brute-force worst case over all permutations (the planning table: 5, 8, 11, 14, 17 for n = 4 … 8) equal to n⌈lg n⌉ − 2^⌈lg n⌉ + 1 (the formula is **to verify** against Knuth vol. 3 §5.2.4 before it is stated), and the gap to the information-theoretic bound (17 against 16 at n = 8), the topic's surprising number: merge sort is within one comparison of optimal at n = 8 and about 5% above it at n = 1,024 (9,217 against 8,770: planning values); its worst case is n lg n minus a linear term, so the gap to ⌈lg n!⌉ grows only linearly (the builder computes the gap for n up to a bound and states the largest ratio it finds; at planning time it stayed below 0.53 n for every n up to 200,000).
  - "stability": a merge takes the left key on a tie, which is the whole proof of stability (shown on the tagged deck: 3a stays left of 3b); the one-character change (`<` against `<=`) that breaks it, demonstrated; why stability decides library choices (a stable sort lets the caller sort by a second key first and then the primary key; object sorts in several standard libraries are stable and primitive sorts are not, **to verify per library at research time**: Java's `Arrays.sort` for objects is documented as stable and adapted from Tim Peters's list sort, read at planning time; the Rust slice docs distinguish `sort` from `sort_unstable`, read).
  - "O(n) buffer": the merge needs somewhere to put its output; the simple version copies the whole input (n spare slots), the usual refinement copies only the left half (n/2), and Timsort's refinement copies only the shorter of the two runs, min(A, B) (the CPython `listsort.txt` text: "if we have temp memory equal to min(A, B), it's easy", read at planning time, which also says in-place linear-time merging is known as a theoretical construction "too difficult and slow for practical use": quoted as that file's statement). Merge sort on arrays against merge sort on linked lists (Chapter 2's lists: the merge needs no buffer and the splice is O(1), a one-frame contrast, nothing built). Why stable and in place and O(n log n) together is not what the standard libraries ship (each real sort gives up one of the three; the four-cell table from topic 48 filled in).

### 51. Heapsort (`dsa.heapsort`): refresher, §15.1

### 52. Timsort, Powersort and driftsort (`dsa.timsort-powersort-driftsort`): full, §15.1

- **Folder:** `timsort-powersort-driftsort`. About 15 min.
- **Scope (syllabus clause → what it delivers):**
  - "run detection": the first stage of every algorithm in this topic, built on topic 49's natural runs: scan from the left for the next **run** (non-decreasing, or strictly decreasing and then reversed in place, because reversing a strictly descending run keeps the sort stable; CPython's `listsort.txt`, read at planning time, describes exactly this and the trick of extending a reversed run by an adjacent ascending one: "given [3, 2, 1, 3, 4, 5, 0], the 3-element descending prefix is reversed in-place, and then extended by [3, 4, 5]"); a run shorter than **minrun** is extended by a stable **binary insertion sort** (Chapter 1's `binary-search` idea plus topic 48's insertion sort; the file's reasoning about CPython's comparison cost is quoted as that file's statement, not generalised), and minrun is chosen so the number of runs is a power of two (CPython's `listsort.txt` now describes a scheme by Stefan Pochmann that lets minrun vary by one: "The number of runs is a power of 2. At most two different run lengths appear", with a 315-element example, 39 and 40: read at planning time, **the version of CPython whose source adopted it to be read in the changelog, not asserted**). The five shapes: sorted and reversed each one run (n − 1 comparisons: CPython's file shows 32,767 comparisons for 32,768 elements on ascending, descending and equal data), random data all runs of minrun length, the deck with its ascending stretch.
  - "galloping merges": merging two adjacent runs with an **exponential search** (galloping): when one side has won MIN_GALLOP times in a row (CPython: 7, adaptive), search ahead 1, 3, 7, 15, … positions then binary-search the final stretch, so a long winning stretch costs O(log) comparisons instead of one per element; the table in `listsort.txt` (if A[0] belongs at B[i], linear search needs i + 1 comparisons and galloping 2⌊lg i⌋ + 2, and galloping first wins at i = 6: read, and **recomputed in `examples.py`**); why it is adaptive (the threshold rises when galloping does not pay), and the cost when it does not (the file's "Galloping with a Broken Leg"). Credit: McIlroy (SODA 1993, "Optimistic Sorting and Information Theoretic Complexity": cited by the file and by the Java `Arrays.sort` Javadoc, both read) and Demaine, López-Ortiz and Munro (named in the file). The merge buffer is min(A, B) (topic 49's refinement, now used) and a pre-merge binary search trims the elements already in place.
  - "merge-policy invariants": the part that is easy to get wrong. A sort that merges runs as it finds them must decide **which adjacent runs to merge** (stability forbids merging non-adjacent runs: the file's A:10000, B:20000, C:10000 example) so as to keep the stack of pending runs short and the merges balanced; the original Timsort maintained invariants on the run-length stack (each run longer than the sum of the next two, and longer than the next) re-established after every push. **The 2015 bug:** de Gouw, Rot, de Boer, Bubel and Hähnle, "OpenJDK's java.util.Collection.sort() is broken: the good, the bad and the worst case" (CAV 2015, LNCS 9206, pp. 273–289; the Springer page and its open-access text were read at planning time): while trying to prove the implementation correct with the KeY tool the authors found that `mergeCollapse` checked the invariant only on the top three entries, so merging could break it deeper in the stack; their example is the run lengths 120, 80, 25, 20, 30, which after one merge leave 120, 80, 45, 30 with the invariant 120 > 80 + 45 false (**reproduced at planning time by transcribing the JDK 7 loop**: the topic reproduces it in `examples.py`), and the stack-size array, sized from the invariant, can then overflow: the paper builds an input (smallest example 67 million elements, "of non-primitive type") on which the unfixed code throws `ArrayIndexOutOfBoundsException`, the same bug "is present in Python as well, ever since the method was introduced" per the paper, and the fix checks the top four. ### 54. External merge sort (`dsa.external-merge-sort`): full, §15.2
