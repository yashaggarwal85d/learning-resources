## The chapter

### The problem it solves

Chapter 16 answered questions about a single value in an ordered or orderable collection: one key, one boundary, one order statistic. This chapter leaves arrays behind. The data is now a **graph** — vertices and edges, with no inherent order — and the question is not "what value is here" but "what can be reached, in what order, and what does the shape of reachability itself prove." The thread through all four topics is **systematic exploration that never revisits a vertex**: breadth-first search and depth-first search are the two orders in which that exploration can proceed (frontier-by-frontier, or as deep as possible before backtracking), and everything else in the chapter — topological order, strongly connected components — is a *structural fact about the graph* that one of those two traversals reveals as a side effect, not a new kind of search. The chapter ends where Chapter 18 begins: once a graph's vertices can be visited and ranked, the next question adds weights to the edges and asks for the *cheapest* way to reach them, not merely *a* way.

### Order of ideas, and why

1. **Breadth-first search (59, full).** First, because it is the simplest traversal to state correctly (a queue, a visited set, one frontier at a time) and because its own guarantee — the first time a vertex is dequeued, the path to it is shortest in edge count — is the chapter's first proof that a traversal order can *be* an answer, not just a way of visiting. 0-1 BFS and bipartiteness are both built as direct extensions of the same frontier idea, not new algorithms.
2. **Depth-first search and edge classification (60, full).** Second, because DFS is the traversal every later topic in this chapter (and Chapter 19's cycle tests) is secretly built from, and because the four-way edge classification (tree/back/forward/cross) is the single idea that both cycle detection and topological order are built on — introduced here once, reused by name in topics 61 and 62 rather than rederived.
3. **Topological sort (61, full).** Third, because it is the first topic whose entire output is "a DFS, run a certain way" (reverse finish order) or "a BFS on in-degrees" (Kahn's algorithm) — proof that a traversal order is itself a structural answer, extending topic 59's shortest-path guarantee to a different kind of guarantee (a valid dependency order) from the same two primitives.
4. **Strongly connected components (62, full).** Last, because it is the chapter's hardest structural fact — not every DAG-like property, but the graph's own partition into maximal mutually-reachable pieces — and because both algorithms that find it (Tarjan's single-pass low-link, Kosaraju's two-pass) are DFS again, with nothing new borrowed from outside the chapter.
5. **Handoff to Chapter 18.** Topic 62 ends on a graph whose vertices are grouped by what reaches what, with no notion of distance anywhere in the chapter — every edge has counted for exactly one step. The next question puts a cost on each edge and asks for the cheapest path, not merely a reachable one. Dijkstra's algorithm, next.

### Shared notation and terms

- **Graph.** `G = (V, E)`, `n = |V|`, `m = |E|`; directed unless stated undirected. Every topic states up front which it means, since edge classification (topic 60) and SCCs (topic 62) are directed-graph concepts that have no undirected analogue (an undirected graph's DFS tree has only tree and back edges, never forward or cross — stated once in topic 60, not rediscovered in topic 62).
- **Visited set and frontier.** A traversal marks each vertex visited exactly once; BFS's frontier is the set of vertices at the current distance, held in a FIFO queue; DFS's frontier is the current recursion stack (explicit or call-stack), held LIFO. Both are O(n + m) — every vertex and every edge is examined a bounded number of times — stated and reused as the chapter's one running complexity fact.
- **Discovery and finish time (DFS only).** Each vertex gets a discovery time (when first visited) and a finish time (when its subtree is fully explored); the four edge types are defined purely from these two numbers and the tree structure, the definition topic 60 gives in full and topics 61–62 reuse by name.
- **Spoken numbers:** narration has no digits, symbols or code names (automatic check); say "breadth-first search", "depth-first search", "topological sort", "strongly connected components", "low-link value", "condensation graph"; speak every number in words (QUALITY.md #29). Authors' names that are not words (BFPRT-style) are spoken as names: "Robert Tarjan", "Kahn's algorithm" (a name, said as a name, not spelled out).

### 59. Breadth-first search (`dsa.breadth-first-search`): full

- **Folder:** `breadth-first-search`. About 14 min.
- **Scope (syllabus clause → what it delivers):**
  - "level-by-level frontier": a FIFO queue holding the current frontier, each vertex dequeued once, each neighbour enqueued the first time it is seen; the topic proves (not just states) that this visits vertices in strictly non-decreasing distance order, by induction on the queue's own ordering.
  - "unweighted shortest paths": the proof above, restated as the guarantee that the first time a vertex is dequeued, its distance (edge count from the source) is final; `examples.py` builds a graph where a vertex has several paths of different lengths and shows BFS finds the shortest, with parent pointers reconstructing the path.
  - "multi-source BFS": seed the queue with several sources at distance 0 simultaneously rather than one; the result is, for every vertex, the distance to the *nearest* of the sources — the topic's worked example (a grid with several fire sources, "time for the fire to reach every cell") and why running single-source BFS once per source and taking the minimum gives the identical answer but costs O(k(n+m)) against multi-source's O(n+m).
  - "0-1 BFS with a deque": edges weighted either 0 or 1 (not the general weighted case, left to Chapter 18) are handled by pushing a 0-weight edge's endpoint to the *front* of a deque and a 1-weight edge's endpoint to the *back*, keeping the deque's own order non-decreasing in distance without a priority queue; the topic's measured comparison against running plain Dijkstra on the same 0/1-weighted graph (same answer, no heap needed).
  - "bipartiteness and odd-cycle detection by 2-colouring": BFS (or DFS) 2-colours a graph by alternating colour at each frontier step; a graph is bipartite iff this never assigns the same colour to both endpoints of an edge, and the first edge where it does is the topic's witness of an odd cycle (the two colour-equal endpoints plus their common BFS-tree ancestor path form an odd cycle, shown constructively, not merely asserted).
  - "direction-optimizing BFS (Beamer et al., SC 2012) for low-diameter graphs": named and cited (Beamer, Asanović, Patterson, "Direction-Optimizing Breadth-First Search", SC12; fetched and quoted) as the production fix for BFS's own worst case on low-diameter, high-degree graphs (a social network, not a road network): once the frontier is large, it is cheaper to scan *unvisited* vertices and ask "is any neighbour of mine in the frontier" (bottom-up) than to scan the frontier's own (many) outgoing edges (top-down); the topic states the paper's own switching heuristic and its reported speedup at the level the primary source supports, without reimplementing the full hybrid (a from-scratch top-down/bottom-up toggle on a small synthetic graph in `examples.py`, honestly labelled as a demonstration of the shape of the saving, not the paper's tuned heuristic).
  - Leaves the general traversal order (depth-first) and its edge classification to topic 60; leaves weighted shortest paths entirely to Chapter 18.
- **Outcomes:**
  - Implement BFS with a FIFO queue and parent pointers, and prove it finds unweighted shortest paths.
  - Run multi-source BFS and 0-1 BFS with a deque, and say when each is the right tool over plain BFS or Dijkstra.
  - 2-colour a graph by BFS to test bipartiteness, and produce a witnessing odd cycle when it fails.
- **Introduces:** `breadth-first-search`, `frontier`, `unweighted-shortest-path`, `multi-source-bfs`, `zero-one-bfs-deque`, `bipartiteness-two-coloring`, `direction-optimizing-bfs`. **Uses:** `adjacency-list`, `edge-list` (Chapter 10), `queue`, `deque` (Chapter 2), `big-o-theta-omega` (Chapter 1).
- **Bridge:** word for word, topic 58's handoff above ("Finding one key, one boundary, one order statistic… Breadth-first search, next.").
- **Handoff:** "A breadth-first frontier answers one question well: the fewest edges to reach a vertex. It says nothing about which vertex to visit next when the graph has structure a single widening ring can't see — a dependency that must come before another, a group of vertices that can all reach each other and nothing outside the group. Those answers come from visiting as deep as possible before backtracking, not level by level. Depth-first search and edge classification, next."
- **Prerequisites panel:** Chapter 10 "Adjacency lists, matrices and edge lists" (Before this). On-site: topics 60–62 as "Goes deeper later".
- **Pre-notes terms:** graph, vertex and edge, directed vs undirected (one line), queue (recap: FIFO), neighbour.
- **Hook:** a social network with a billion edges can still answer "how many people separate you from this stranger" in a handful of steps, because the people worth checking next are never more than one step past the people already checked — a widening ring, never a wrong turn. Predict: starting breadth-first search from one vertex, is the first time a vertex is reached always its shortest distance from the source, or can a vertex be reached again later by a shorter path? (Always shortest the first time: every vertex one step further is enqueued only after every vertex the current step away has been.)
- **Visual idea:** a graph with a source vertex lit `caramel`, a widening ring of `caramel` vertices each step with a distance label appearing under each; a split frame contrasting single-source BFS run `k` times against multi-source BFS run once on the same multi-source grid; a deque drawn with 0-weight pushes to the front and 1-weight pushes to the back; a 2-colouring sweep that hits an odd cycle, the offending edge and its ancestor path highlighted `cherry`.
- **Sources to start from:** CLRS 4th ed., chapter on elementary graph algorithms (BFS section; chapter/section to verify) for the shortest-path proof and the standard framing; Beamer, Asanović and Patterson, "Direction-Optimizing Breadth-First Search" (SC12, 2012) — fetch and quote the top-down/bottom-up switching idea and its stated speedup exactly; a bipartiteness-by-2-colouring reference (CLRS exercises or a competitive-programming reference, to verify) for the odd-cycle witness construction.

### 60. Depth-first search and edge classification (`dsa.depth-first-search-edge`): full

- **Folder:** `depth-first-search-edge`. About 14 min.
- **Scope (syllabus clause → what it delivers):**
  - "discovery/finish times": every vertex gets a discovery time (a counter incremented on first visit) and a finish time (incremented when its recursion fully returns); the topic's worked example prints both for a small graph and shows the **parenthesis property** (one DFS tree's discovery/finish intervals are either nested or disjoint, never partially overlapping) as the structural fact edge classification is built from.
  - "tree/back/forward/cross edges": the four-way classification purely from discovery/finish times and tree membership (tree: part of the DFS tree; back: to an ancestor, discovery time later, finish time not yet set when seen; forward: to a descendant already finished whose discovery is later; cross: to neither ancestor nor descendant, in a different DFS subtree entirely) — the topic states, and `examples.py` confirms by direct computation on a constructed directed graph with at least one of each type, that **undirected graphs have only tree and back edges** (forward and cross are impossible once the graph has no direction, proved from the parenthesis property, not merely asserted).
  - "three-colour cycle detection in directed graphs and parent-check in undirected graphs": white/grey/black vertex colouring (unvisited/on the current recursion stack/finished) detects a cycle in a directed graph exactly when a back edge (an edge to a grey vertex) is found, which is the single case the edge classification above already names; the undirected case needs no colouring at all — a visited neighbour that is not the immediate parent is already a cycle, because an undirected graph's DFS has no cross edges to confuse with a real cycle (the reason the two cases need different tests, stated as the topic's own contrast, not two unrelated rules).
  - "iterative DFS with an explicit stack to avoid recursion-depth limits": a real recursive DFS on a graph with a long path (a near-linear chain of a few hundred thousand vertices) overflows a language's call stack; the topic reproduces this failure directly in `examples.py` (a real `RecursionError` or a measured crash threshold, not claimed from memory) and converts the same traversal to an explicit stack holding (vertex, iterator-position) pairs so it can pause and resume a vertex's neighbour scan without the language's own call stack, and shows the converted version completing on the same input that crashed the recursive one.
  - Leaves the use of discovery/finish order to produce a global ordering to topic 61; leaves the use of the same traversal to find SCCs to topic 62.
- **Outcomes:**
  - Compute discovery/finish times for a DFS and classify every edge as tree, back, forward or cross from them alone.
  - Detect a cycle in a directed graph by three-colouring and in an undirected graph by a parent check, and explain why the two tests differ.
  - Convert a recursive DFS to an explicit-stack iterative one, and reproduce the recursion-depth failure the conversion fixes.
- **Introduces:** `depth-first-search`, `discovery-finish-time`, `edge-classification`, `parenthesis-property`, `three-colour-cycle-detection`, `iterative-dfs-explicit-stack`. **Uses:** `adjacency-list` (Chapter 10), `stack` (Chapter 2), `breadth-first-search` (topic 59, contrast only), `big-o-theta-omega` (Chapter 1).
- **Bridge:** word for word, topic 59's handoff above ("A breadth-first frontier answers one question well… Depth-first search and edge classification, next.").
- **Handoff:** "A directed graph with no back edges — no cycle anywhere — has a DFS finish order that is itself a valid answer to a question BFS was never asked: in what order can every vertex be processed so that nothing is processed before the things it depends on. That order falls out of the traversal just built, almost for free. Topological sort, next."
- **Prerequisites panel:** topic 59 (Before this); Chapter 2 "Stacks, queues and deques" (Before this, for the explicit-stack conversion). On-site: topics 61–62 as "Goes deeper later".
- **Pre-notes terms:** recursion and the call stack (one line), cycle (a path that returns to its own start), ancestor and descendant in a rooted tree.
- **Hook:** a depth-first search written the natural recursive way works perfectly on every graph in a textbook and crashes on a real one — a dependency chain a few hundred thousand deep blows the call stack before the algorithm's logic ever gets a chance to be wrong. Predict: an edge from a vertex to one of its own ancestors in the DFS tree — is that a tree edge, a back edge, a forward edge, or a cross edge? (A back edge: that is the definition, and it is also exactly the edge a directed cycle needs.)
- **Visual idea:** a graph with a single `caramel` path diving deep, a stack panel beside it growing and shrinking as the path advances and backtracks; discovery/finish time labels appearing and then locking in under each vertex; four small callout edges each labelled tree, back, forward or cross with its own two-colour nesting diagram; a split frame showing the recursive version's stack overflowing (`cherry`) against the iterative version completing on the identical input.
- **Sources to start from:** CLRS 4th ed., chapter on elementary graph algorithms, DFS and edge-classification sections (chapter/section to verify) for discovery/finish times, the parenthesis property and the four edge types; a reference on directed-cycle detection by three-colouring (CLRS or a competitive-programming reference, to verify) for the white/grey/black framing; a language-specific note on default recursion/call-stack limits (to verify at build time against the actual runtime `examples.py` runs under) for the iterative-DFS failure reproduction.

### 61. Topological sort (`dsa.topological-sort`): full

- **Folder:** `topological-sort`. About 13 min.
- **Scope (syllabus clause → what it delivers):**
  - "Kahn's in-degree queue vs reverse DFS finish order": two independent algorithms for the same output, built side by side: **Kahn's algorithm** (Kahn, "Topological sorting of large networks", CACM 5(11), 1962; fetched and quoted) repeatedly removes a vertex with in-degree zero and decrements its neighbours' in-degrees, using a plain queue — the topic's direct reuse of topic 59's queue mechanics on in-degrees instead of distances; **reverse DFS finish order** runs topic 60's DFS to completion and reads off vertices in decreasing finish time — the topic proves these give equally valid (though not always identical) topological orders, and `examples.py` runs both on the same DAG and confirms each is internally valid (every edge points from an earlier position to a later one) without requiring the two orders to match vertex-for-vertex.
  - "cycle detection as a by-product": Kahn's algorithm cannot be run to completion (vertices remain with positive in-degree, none ever reaching zero) exactly when the graph has a cycle, and DFS's finish-order approach already has topic 60's own back-edge test built in; the topic states that *neither* algorithm needs a separate cycle check bolted on, since a cycle shows up as the natural failure mode of each.
  - "lexicographically smallest order with a heap": among all valid topological orders, the lexicographically smallest one picks, at every step, the smallest-labelled vertex currently available (in-degree zero); replacing Kahn's plain queue with a min-heap keyed on vertex label gives exactly this, at the cost of O(log n) per removal instead of O(1) — the topic's measured contrast (heap-based Kahn's against queue-based Kahn's on the same DAG, confirming the heap version's order is lexicographically smaller whenever more than one valid order exists).
  - "critical-path scheduling on DAGs → Data Engineering Ch.11": named as the production use of a topological order (process every task after everything it depends on, tracking the longest weighted path to each vertex as the project's critical path) with the pointer to Data Engineering's own treatment of DAG-based pipeline scheduling, stated once in post-notes as where the full scheduling machinery is built, not rebuilt here.
  - Leaves the strongly-connected-components case (what happens when the graph is *not* a DAG and has no valid topological order at all) to topic 62.
- **Outcomes:**
  - Run Kahn's algorithm and reverse-DFS-finish-order topological sort on the same DAG and confirm both orders are valid.
  - Explain why each algorithm detects a cycle as a natural failure rather than a separate check.
  - Produce the lexicographically smallest topological order with a heap-based Kahn's algorithm, and say what it costs over the plain queue version.
- **Introduces:** `topological-sort`, `kahns-algorithm`, `reverse-dfs-finish-order`, `lexicographically-smallest-topo-order`. **Uses:** `breadth-first-search` (topic 59, the queue mechanics reused on in-degrees), `depth-first-search`, `discovery-finish-time`, `three-colour-cycle-detection` (topic 60), `binary-heap` (Chapter 6), `directed-acyclic-graph` (Chapter 10).
- **Bridge:** word for word, topic 60's handoff above ("A directed graph with no back edges… Topological sort, next.").
- **Handoff:** "A topological order says which vertices can come before which. It says nothing about which vertices can reach each other at all, in a graph that is not a DAG and has no topological order to give — a graph with cycles, where whole groups of vertices can each reach every other member of the group and nothing outside it. Finding those groups is the chapter's last structural question. Strongly connected components, next."
- **Prerequisites panel:** topics 59–60 (Before this); Chapter 6 "Binary heaps and heapify" (Before this, for the heap-based variant). On-site: topic 62 as "Goes deeper later".
- **Pre-notes terms:** in-degree (recap: number of incoming edges), dependency order, DAG (recap from Chapter 10: a directed graph with no cycle).
- **Hook:** a build system with ten thousand targets, each depending on a handful of others, must run every target after everything it needs — and it finds that order not by trial and error but by the same two traversals already built this chapter, pointed at in-degrees instead of distances. Predict: can a directed graph with a cycle have any valid topological order at all? (No: any order would require some vertex in the cycle to come both before and after another vertex in the same cycle.)
- **Visual idea:** a small DAG with in-degree labels on every vertex, a queue draining vertices as their in-degree hits zero (`caramel`), each removal decrementing its neighbours' labels live; a side-by-side DFS finish-order sweep on the identical graph, reversed into the same order shown as valid but not identical; a heap-based version visibly picking the smallest available label each round; a cyclic graph shown stalling with vertices stuck at positive in-degree (`cherry`).
- **Sources to start from:** Kahn, "Topological sorting of large networks" (*Communications of the ACM* 5(11), 558–562, 1962) — fetch and quote the in-degree algorithm exactly if available, else cite via a secondary source stated as such; CLRS 4th ed., topological-sort section (chapter/section to verify) for the reverse-DFS-finish-order algorithm and its correctness proof; Data Engineering's own DAG/critical-path scheduling topic (Chapter 11, read its registry entry and post-notes only, not rebuilt) for the cross-domain pointer.

### 62. Strongly connected components (`dsa.strongly-connected-components`): full

- **Folder:** `strongly-connected-components`. About 15 min.
- **Scope (syllabus clause → what it delivers):**
  - "Tarjan's low-link single pass vs Kosaraju's two passes": **Tarjan's algorithm** (Tarjan, "Depth-first search and linear graph algorithms", *SIAM Journal on Computing* 1(2), 146–160, 1972; fetched and quoted) runs a single DFS, maintaining for each vertex a **low-link value** (the smallest discovery time reachable from it via tree and back edges, through a maintained explicit stack of "still on the stack" vertices) and pops a complete SCC exactly when a vertex's low-link equals its own discovery time; **Kosaraju's algorithm** runs DFS once to get a finish order, reverses every edge, and runs DFS again in decreasing finish order, each new DFS tree in the second pass being exactly one SCC — the topic builds both from scratch, proves each correct at the level its own primary source supports, and measures the one practical difference (Tarjan needs one DFS and one explicit stack; Kosaraju needs two full DFS passes and an explicit graph-transpose step) on the same input in `examples.py`.
  - "the condensation DAG": contracting every SCC to a single vertex turns any directed graph into a DAG (proved: a cycle among condensed vertices would mean their original SCCs were mutually reachable, contradicting maximality) — the topic's worked example builds the condensation graph from a constructed input with several SCCs and confirms directly (not merely asserts) that it has no cycle, reusing topic 60's own cycle test on the condensation graph as the proof.
  - "2-SAT solved via SCCs": the implication graph construction (each boolean variable gets two vertices, true and false; a clause `(a ∨ b)` becomes two implications, `¬a → b` and `¬b → a`) and the fact that a 2-SAT instance is satisfiable iff no variable's true and false vertices land in the same SCC (if they did, the formula would force a variable to be both true and false); the topic builds a small 2-SAT instance, constructs its implication graph, runs the chapter's own SCC algorithm on it, and reads off satisfiability directly — the chapter's closing demonstration that a hard-looking logic problem reduces entirely to a traversal already built.
  - Nothing is left to another topic in this chapter; the three skipped syllabus entries (articulation points/bridges/biconnectivity, Eulerian paths, lowest common ancestor) are named once each as frontier pointers, not built.
- **Outcomes:**
  - Implement Tarjan's single-pass low-link SCC algorithm and Kosaraju's two-pass algorithm, and state what each costs over the other.
  - Build the condensation DAG of a graph's SCCs and confirm directly that it has no cycle.
  - Reduce a small 2-SAT instance to an implication graph and decide satisfiability by its SCCs.
- **Introduces:** `strongly-connected-components`, `low-link-value`, `tarjan-scc`, `kosaraju-scc`, `condensation-graph`, `two-sat-via-scc`. **Uses:** `depth-first-search`, `discovery-finish-time`, `edge-classification`, `iterative-dfs-explicit-stack` (topic 60), `topological-sort` (topic 61, the condensation graph's own ordering), `stack` (Chapter 2), `directed-acyclic-graph` (Chapter 10).
- **Bridge:** word for word, topic 61's handoff above ("A topological order says which vertices can come before which… Strongly connected components, next.").
- **Handoff:** "Finding one key, one boundary, one order statistic was Chapter 16's business. This chapter answered a different kind of question about a graph with no weights at all: which vertices are reachable, in what order, and which groups of vertices can all reach each other. Every answer cost exactly one traversal, because every edge counted for one step and no more. The next chapter puts a cost on each edge and asks a question neither breadth-first nor depth-first search can answer on its own: not merely a path, but the cheapest one. Dijkstra's algorithm, next."
- **Prerequisites panel:** topics 59–61 (Before this). On-site: none later in this chapter.
- **Pre-notes terms:** strongly connected (recap in one line: every vertex can reach every other), satisfiability (one line: an assignment of true/false to variables that makes every clause true), implication.
- **Hook:** a graph where every vertex can reach every other looks, from a distance, indistinguishable from one where only small pockets can reach each other — and telling the two apart, for a graph with a billion edges, takes exactly one more depth-first search, carrying one extra number per vertex.
