## The chapter

### The problem it solves

A sorted array answers "is x here, and if so where" in about twenty steps for a million keys, against a million steps unsorted — Chapter 15 ended on exactly that trade. This chapter is the twenty steps, done right, and then generalised twice: first to a question that is not "is x in the array" but "what is the smallest answer that works" (binary search on a monotone predicate, not a value), and second to the question "what is the k-th smallest", which does not need the array sorted at all. The thread through all four topics is **monotonicity**: binary search works whenever a predicate is false, false, …, false, true, true, …, true across a range, whether that range is array indices, a real-valued rate, or (less obviously) the two halves of a rotated sorted array. Selection breaks from that thread on purpose, in topic 58: quickselect answers "the k-th smallest" in linear expected time by borrowing Chapter 15's partition and throwing away the side it doesn't need, and median-of-medians shows the same idea can be made to run in linear time even in the worst case, at the cost of a constant nobody uses in practice. The chapter ends where Chapter 17 begins: once you can find one key fast in a sorted structure, the next question is how to find a path through a structure with no order at all.

### Order of ideas, and why

1. **Binary search invariants and boundaries (55, full).** First, because every later topic in the chapter is binary search on something else, and the thing that goes wrong — an off-by-one, an infinite loop, an integer overflow that shipped in the JDK for nine years — goes wrong at the boundary, not in the big-picture idea. The topic's job is to make the loop invariant and the half-open convention automatic before any variant is attempted.
2. **Binary search on the answer (56, full).** Second, the generalisation that the syllabus singles out: the predicate doesn't have to be "a[mid] < x", it can be "is rate r enough", and the search space doesn't have to be integers. This is where binary search stops being an array technique and becomes a technique for monotone predicates in general, and where parametric search (Megiddo, 1983) is introduced as the idea that a decision procedure plus binary search gives an optimisation algorithm.
3. **Search in rotated and sorted matrices (57, full).** Third, because it is the chapter's proof that recognising which half of a range is sorted is itself an invariant argument, not a special case to memorise, and because the 2-D staircase search (strictly increasing rows and columns) is a second shape of monotonicity, no binary search needed, that a reader will otherwise confuse with the 1-D case.
4. **Quickselect and median-of-medians (58, full).** Last, because it answers a question binary search cannot: find the k-th smallest without a sorted order to search, using the one tool from Chapter 15 this chapter borrows, the partition step, and because its worst-case fix (BFPRT, 1973) is the chapter's running example of trading a worse constant for a guaranteed bound — the same trade Chapter 15 topic 51 made with heapsort.
5. **Handoff to Chapter 17.** Topic 58 ends on an array that can be queried and ranked in linear time with no comparisons wasted on a full sort. The next question a working engineer asks is not about an array at all: given a graph of relationships, what can be reached, and in what order. Chapter 17 opens with breadth-first search.

Their facts that other topics need are carried where they already live: galloping (exponential search bounding an unbounded range) is Chapter 15 topic 52's "galloping merges" clause, taught there in full; nothing from either skipped topic is a prerequisite for topics 55–58, so neither is named again except once in topic 55's post-notes "Where this goes next" pointer. ### Shared notation and terms

- **Ranges.** Every search is written over a **half-open** range `[lo, hi)`, the same convention Chapter 15 topic 15.1's notation used for a sorted prefix: `lo` is always a candidate, `hi` is always one past the last candidate, and the loop invariant is stated as "the answer, if it exists, is in `[lo, hi)`" at the top of every iteration, never only in prose.
- **The overflow-safe midpoint.** `mid = lo + (hi - lo) / 2` (not `(lo + hi) / 2`), because `lo + hi` can overflow a fixed-width integer before the division runs; this is the chapter's first fact and the subject of topic 55's hook.
- **Monotone predicate.** A boolean function p over an ordered range such that once p is true it stays true (or symmetrically, once false stays false); binary search finds the boundary between the false run and the true run. "Is `a[i] >= x`" is one instance; "can a courier deliver by time t" is another.
- **Selection.** The k-th **order statistic** of a multiset is its k-th smallest element under a total order; "median" means the order statistic at index ⌈n/2⌉ (one convention, stated once and used consistently); selection is a weaker guarantee than sorting (it does not fix every element's rank, only one).
- **Spoken numbers:** narration has no digits, symbols or code names (automatic check); say "binary search", "half open range", "overflow safe midpoint", "monotone predicate", "quickselect", "median of medians", "order statistic"; speak every number in words (QUALITY.md #29). Library and paper names that are not words (BFPRT) are not spoken: say "the Blum, Floyd, Pratt, Rivest and Tarjan selection algorithm" once, then "median of medians".

### 55. Binary search invariants and boundaries (`dsa.binary-search-invariants-boundaries`): full

- **Folder:** `binary-search-invariants-boundaries`. About 14 min.
- **Scope (syllabus clause → what it delivers):**
  - "half-open intervals": the `[lo, hi)` convention above, contrasted once with a closed `[lo, hi]` version to show why the half-open form makes "empty range" and "loop invariant" both trivial to state (`lo == hi`, nothing else to check); the invariant stated and kept on screen every iteration: "the answer, if present, lies in `[lo, hi)`".
  - "lower/upper bound, first/last occurrence": **lower_bound** (first index where `a[i] >= x`) and **upper_bound** (first index where `a[i] > x`) as the two predicates everything else is built from (C++'s `std::lower_bound`/`std::upper_bound` naming, read at research time from cppreference and cited as such); first occurrence of x is `lower_bound(x)` if that slot holds x, last occurrence is `upper_bound(x) - 1`; the count of x in a sorted array is `upper_bound(x) - lower_bound(x)`, the topic's worked example.
  - "the overflow-safe midpoint (the bug found in many libraries in 2006)": Joshua Bloch, "Extra, Extra — Read All About It: Nearly All Binary Searches and Mergesorts are Broken" (Google Research blog, 2 June 2006; fetched and quoted exactly): the JDK's own `Arrays.binarySearch`, unnoticed for about nine years, computed `mid = (low + high) / 2`, which overflows a 32-bit `int` and goes negative for arrays of roughly 2^30 elements or more, causing an out-of-bounds access; the fix, `mid = low + ((high - low) / 2)` (the C/C++-safe form; Bloch's first proposed fix, an unsigned shift, is Java-specific and is named as the JDK's actual fix, `(low + high) >>> 1`, with the two kept distinct). The topic reproduces the overflow on a small integer width in `examples.py` (not a real 2-billion-element array; a toy fixed-width integer type that overflows at a small bound, so the failure is actually observed, not merely asserted) rather than claiming it from memory.
  - "proving termination by invariant": every iteration either returns or strictly shrinks `hi - lo` (for lower_bound-style search, `lo = mid + 1` or `hi = mid`, both strictly inside the previous range since `lo <= mid < hi` for half-open ranges with `lo < hi`), so the loop terminates in at most ⌈lg n⌉ iterations; the topic proves this by the invariant, not by running it and counting, though `examples.py` also counts it on several n to confirm ⌈lg(n+1)⌉ for a present-or-absent search and states the exact figure for n = 1,000,000 (20 iterations).
  - Leaves monotone-predicate search over a non-index domain to topic 56, the rotated/2-D case to topic 57, and selection without a sorted order to topic 58.

  - Implement lower_bound and upper_bound and use them to count occurrences and find first/last occurrence.
  - Explain the 2006 midpoint overflow bug from the primary source, write the safe midpoint, and reproduce an overflow failure on a small bound.

### 57. Search in rotated and sorted matrices (`dsa.search-rotated-sorted-matrices`): full

- **Folder:** `search-rotated-sorted-matrices`. About 14 min.
- **Scope (syllabus clause → what it delivers):**
  - **Rotated sorted array:** an array sorted ascending and then rotated at an unknown pivot (e.g. `[4,5,6,7,0,1,2]`) still lets binary search run in O(log n), because at every `mid`, **at least one of the two halves `[lo, mid]` and `[mid, hi)` is itself sorted** (the invariant the topic proves, by case analysis on `a[lo] <= a[mid]`), and once the sorted half is identified, the predicate "is the target in this half's range" is checked in O(1) and the search recurses into whichever half can contain it; the topic also covers finding the rotation point itself (the index of the minimum) as the special case "search for the boundary where `a[i] > a[i+1]` fails", and the duplicate-keys case, where the invariant can degrade to O(n) in the worst case (`a[lo] == a[mid] == a[hi]` tells you nothing about which half is sorted; the topic states this honestly, with the adversarial all-equal-but-one array as the worst case, rather than hiding it) — citing Chapter 1's adversary-argument framing for why duplicates defeat the O(log n) bound here specifically.
  - **2-D sorted (staircase) matrix search:** a matrix whose rows and columns are each sorted ascending (the common formulation: "Search a 2D Matrix II"-style, where only rows and columns are individually sorted, not the whole matrix in one order) is searched in O(m + n), not O(log(mn)), by starting at one corner (top-right or bottom-left) where one direction decreases and the other increases, and moving in the one direction indicated by comparing the target to the current cell — a linear "staircase" walk, not binary search, and the topic says plainly why binary search does not apply here (no single monotone predicate over a 1-D range exists for the whole matrix; the structure is two independent sorted orders, not one) so the two halves of this topic are not secretly the same algorithm, on purpose, since conflating them is the error this topic exists to prevent. A stronger variant, where the whole matrix is sorted in row-major order (`matrix[i][j] < matrix[i][j+1]` and `matrix[i][0] > matrix[i-1][last]`), *does* reduce to ordinary 1-D binary search by treating the matrix as a flattened array via `(mid / cols, mid % cols)` — shown as the contrast case, so the reader sees exactly which structural assumption buys back O(log(mn)).
  - "the interview variants and their invariants": the topic frames both halves above (rotated-array pivot location, staircase search) explicitly as the two invariants a reader must tell apart under exam or interview pressure — "which half is sorted" versus "which direction shrinks the search" — closing on a one-frame checklist contrasting the three structures built in this topic (rotated 1-D, staircase 2-D, row-major-flattened 2-D) by which invariant each relies on, so the clause is answered by the topic's own structure, not a separate section.
  - Leaves the general predicate-over-the-answer-space idea to topic 56 (used, not reproduced) and selection without any order to topic 58.
- **Outcomes:**
  - Prove and use the invariant that one half of a rotated sorted array is always sorted, and search it in O(log n); state why duplicate keys can force O(n).
  - Search a row/column-sorted (staircase) matrix in O(m + n) and explain why this is not binary search.
  - Search a fully row-major-sorted matrix in O(log(mn)) by flattening the index, and say which structural assumption makes that reduction valid.
- **Introduces:** `rotated-array-search`, `staircase-matrix-search`, `row-major-matrix-search`. **Uses:** `binary-search`, `half-open-range`, `loop-invariant` (topic 55), `monotone-predicate` (topic 56), `adversary-argument` (Chapter 1 topic 4), `big-o-theta-omega` (Chapter 1).
- **Bridge:** word for word, topic 56's handoff above ("The predicate in every example so far has had one shape… Search in rotated and sorted matrices, next.").
- **Handoff:** "Every search in this chapter so far has assumed the data is already ordered, in one shape or another, and the whole cost was in exploiting that order. The next question has no order to exploit: given an unsorted collection, find the k-th smallest element, as fast as possible, without paying to sort the rest. - **Prerequisites panel:** topics 55 and 56 (Before this); Chapter 1 topic 4 "Lower bounds and adversary arguments" (Before this, for the duplicate-keys worst case). On-site: topic 58 as "Goes deeper later".

### 58. Quickselect and median-of-medians (`dsa.quickselect-median-medians`): full

- **Folder:** `quickselect-median-medians`. About 15 min.
- **Scope (syllabus clause → what it delivers):**
  - **Quickselect (Hoare, "Algorithm 65: FIND", CACM 4(7), 1961; fetched and quoted where possible, cited alongside the modern restatement):** partition the array around a pivot (Chapter 15 topic 50's Lomuto or Hoare partition, reused exactly, not rebuilt) and recurse into **only the side that contains the k-th rank**, discarding the other side entirely rather than sorting it; the expected cost is Θ(n) (the recurrence T(n) = T(n/2) + O(n) in the expected case, by the same random-pivot analysis Chapter 15 topic 50 used for quicksort, cited not rederived), and the topic's measured numbers (comparisons to find the median of n = 1,000 and n = 1,000,000 random keys by quickselect against a full sort) show the gap: quickselect does a small constant times n comparisons where sorting costs n log n.
  - **The worst case, and why it matters:** with an adversarial or always-unlucky pivot (first or last element, sorted/reversed input), quickselect degrades to Θ(n²), exactly as Chapter 15 topic 50's unguarded quicksort did; the topic states this as the same fact seen before, not a new one, and the fix available (randomised pivot) suffers the same "expected, not worst-case" caveat.
  - **Median-of-medians (Blum, Floyd, Pratt, Rivest and Tarjan, "Time Bounds for Selection", *Journal of Computer and System Sciences* 7, 448–461, 1973; fetched and quoted):** the algorithm, PICK — divide into groups of 5 (the paper's own requirement that the group size be at least 5 and odd for the stated bound to hold, stated as the paper's finding, not derived from scratch), sort each tiny group (a handful of comparisons, insertion sort), take each group's median, recursively find the median of those group-medians, and use *that* as the pivot; the counting argument for why this discards a guaranteed fraction of the array every round (at least 3/10 of the elements are provably smaller and at least 3/10 provably larger than the chosen pivot, so at most 7/10 survive to the next round — the paper's own fraction, quoted and then verified in `examples.py` by direct counting on constructed inputs, not asserted); the recurrence T(n) = T(n/5) + T(7n/10) + O(n), solved by the Chapter 1 recursion-tree method (cited, not rederived) to Θ(n) — worst case, not expected.
  - **Why nobody uses it:** the constant hidden in that Θ(n) is large enough (the group-of-5 sorting and the recursive calls both cost real work) that median-of-medians is almost always slower in practice than randomised quickselect, despite the better worst-case guarantee; the topic states this as the chapter's closing trade (the same shape as Chapter 15 topic 51's heapsort-versus-quicksort trade: a worse constant bought for a guaranteed bound) and measures it directly in `examples.py` (wall-clock or comparison-count comparison on the same inputs, with the machine recorded if wall-clock is used, per the project's `OUTLINE.md` convention for timing claims) rather than asserting the gap from memory.
  - **Introselect:** the same depth-limit fix Chapter 15 topic 51 gave quicksort (Musser, "Introspective Sorting and Selection Algorithms", *Software: Practice and Experience* 27(8), 1997 — the paper's title names selection alongside sorting, and its selection algorithm is what the topic cites, not rederived): run quickselect, count recursion depth, and when it exceeds a bound proportional to log n, switch the current range to median-of-medians, so the worst case becomes Θ(n) with quickselect's good average case intact; named as the production answer to the Θ(n²) worst case shown above, and cited against a real standard library's `nth_element` (libstdc++'s `std::nth_element`, read at research time, falls back to median-of-medians past a recursion-depth bound in exactly this way, **version and source location to verify at build time**).
  - **Floyd–Rivest sampling:** Floyd and Rivest, "Expected Time Bounds for Selection" and the companion "Algorithm 489: SELECT" (*Communications of the ACM* 18(3), 165–172 and 173, March 1975; fetched and quoted where the text is available, else cited via the abstract and a secondary restatement, named as such): instead of partitioning the whole range around a plain pivot, first **take a small random sample**, find (by recursion) an element of the sample just below and just above the expected rank, and partition the *full* range using those two bounds to narrow the working range before ever touching most of the array; the paper's own expected-comparison bound, n + min(k, n−k) + O(√n), quoted exactly, and the topic's measured number: Floyd–Rivest makes noticeably fewer comparisons than plain randomised quickselect on the same random input in `examples.py`'s side-by-side count, without changing the worst case.
  - **`nth_element`-style top-k:** the topic names the common library shape (C++'s `std::nth_element(first, nth, last)`, which this topic's quickselect is a from-scratch version of, cited for the contract: after the call, the element at `nth` holds the value that would be there after a full sort, with everything before it no larger and everything after it no smaller, but neither side itself sorted) and shows the one-line extension to "the k smallest elements, unordered": call it once and take the prefix, the way a real caller gets a top-k list without paying to sort it.
  - **The lab's adversarial-input half** (the syllabus's "implement quickselect and median-of-medians and compare them on adversarial inputs"): `examples.py` runs both algorithms, each with a fixed and with a randomised pivot rule, against a constructed worst-case input (sorted, reversed, and a crafted sequence that defeats a fixed first-element pivot, reusing Chapter 15 topic 50's adversary-construction technique) and reports the comparison counts side by side — the topic's closing table.
