# Sources: Producer batching, compression and acks (`de.producer-batching-compression-acks`)

## Apache Kafka: producer configuration reference (`batch.size`, `linger.ms`, `compression.type`, `acks`, `enable.idempotence`)

URL: https://kafka.apache.org/44/generated/producer_config.html (the generated, fully-rendered
config-reference page; the unversioned `/44/documentation.html#producerconfigs` assembles
client-side and returns only a redirect shell to a plain fetch — see Notes below).
Version: Apache Kafka 4.4 documentation.

> This configuration controls the default batch size in bytes. No attempt will be made to batch records larger than this size.

> Note: This setting gives the upper bound of the batch size to be sent. If we have fewer than this many bytes accumulated for this partition, we will 'linger' for the linger.ms time waiting for more records to show up. This linger.ms setting defaults to 5, which means the producer will wait for 5ms or until the record batch is of batch.size (whichever happens first) before sending the record batch.

> The default changed from 0 to 5 in Apache Kafka 4.0 as the efficiency gains from larger batches typically result in similar or lower producer latency despite the increased linger.

> This setting gives the upper bound on the delay for batching: once we get batch.size worth of records for a partition it will be sent immediately regardless of this setting, however if we have fewer than this many bytes accumulated for this partition we will 'linger' for the specified time waiting for more records to show up.

> The compression type for all data generated by the producer. The default is none (i.e. no compression). Valid values are none, gzip, snappy, lz4, or zstd. Compression is of full batches of data, so the efficacy of batching will also impact the compression ratio (more batching means better compression).

> The number of acknowledgments the producer requires the leader to have received before considering a request complete.

> acks=0 If set to zero then the producer will not wait for any acknowledgment from the server at all.

> acks=1 This will mean the leader will write the record to its local log but will respond without awaiting full acknowledgement from all followers.

> acks=all This means the leader will wait for the full set of in-sync replicas to acknowledge the record. This guarantees that the record will not be lost as long as at least one in-sync replica remains alive. This is the strongest available guarantee.

> When set to 'true', the producer will ensure that exactly one copy of each message is written in the stream.

> Idempotence is enabled by default if no conflicting configurations are set.

Contents:
- `batch.size`: default (16384 bytes) and the whichever-first relationship with `linger.ms` (used
  for the hook and the "Setup" step's two dashed-line race).
- `linger.ms`: default 5, changed from 0 in Kafka 4.0 (used verbatim for the hook's claim that the
  modern default is no longer "lowest latency means zero linger").
- `compression.type`: default `none`; valid values include `lz4`/`zstd`; compression is of whole
  batches, not individual records (used verbatim for the batch-level-compression reveal).
- `acks`: the three levels and what each guarantees, default `all` (used verbatim for the acks
  reveal and its three-position figure).
- `enable.idempotence`: default `true`, and requires `acks=all` (used to support the "idempotence
  implies acks=all" framing, read alongside KIP-679 below for why that pairing became the default).

## Apache Kafka: KIP-679, "Producer will enable the strongest delivery guarantee by default"

URL: https://cwiki.apache.org/confluence/display/KAFKA/KIP-679%3A+Producer+will+enable+the+strongest+delivery+guarantee+by+default
Version: accepted KIP (the change shipped in Kafka 3.0).

> The producer should enable the strongest message delivery guarantee by default.

> Producer config defaults will change in release version 3.0

> false
> true

> acks
> 1

Contents:
- The motivation (at-least-once plus possible leader-only data loss was the old default) and the

## Apache Kafka: KIP-480, "Sticky Partitioner"

URL: https://cwiki.apache.org/confluence/display/KAFKA/KIP-480%3A+Sticky+Partitioner
Version: accepted KIP (the sticky default-partitioner behaviour this topic's toy comparison
reimplements the shape of, not a line-by-line port).

> Currently, in the case where no partition and no key is specified, the default partitioner partitions records in a round-robin fashion. That means that each record in a series of consecutive records will be sent to a different partition until we run out of partitions and start over again. While this spreads records out evenly among the partitions, it also results in more batches that are smaller in size.

> The sticky partitioner attempts to create this behavior in the partitioner. By "sticking" to a partition until the batch is full (or is sent when linger.ms is up), we can create larger batches and reduce latency in the system compared to the default partitioner.

> After sending a batch, the partition that is sticky changes. Over time, the records should be spread out evenly among all the partitions.

Contents:
- Why round-robin (no key, no explicit partition) produces smaller batches than sticking to one
  partition until it fills or sends (used verbatim for the sticky-partitioning reveal and its toy
  round-robin-vs-sticky comparison).
- The partition changes only when a new batch starts, not per record (used to support the toy
  simulation's own switching rule).

Notes on this topic's research:

`kafka.apache.org/44/documentation.html#producerconfigs` and the unversioned
`kafka.apache.org/documentation/#producerconfigs` both return a client-side-assembled redirect
shell page ("Documentation Redirect..." titles) to a plain fetch with no JS execution, the same
failure mode topic 1 hit with the design page. The fix here is the same: Kafka's own docs build
publishes each config table as a separate, fully-rendered static page under `/44/generated/`
(`producer_config.html`), which the version-pinned `documentation.html` page includes via an
iframe/include at render time. Fetching that generated page directly works cleanly and quote-
matches.

Real measurements this topic also uses, not drawn from any of the sources above: a toy batch-fill
simulation (a clock and a size counter racing to `batch.size`/`linger.ms`, whichever first) and a
real compression-ratio measurement on a synthetic batch of order-event JSON, run with Python's
`zstandard` and `lz4.frame` bindings (both installed in this sandbox) against the same bytes —
see `examples.py`. These are the toy's own numbers, not Kafka's, and are disclosed as such in
`references.md`.
