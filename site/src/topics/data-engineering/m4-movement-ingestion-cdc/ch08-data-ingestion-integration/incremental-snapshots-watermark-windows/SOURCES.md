## DBLog: A Watermark Based Change-Data-Capture Framework (Andreakis & Papapanagiotou, Netflix, arXiv:2010.12597)

URL: https://arxiv.org/pdf/2010.12597
Fetched: 2026-11-01.

Quotes:
> Our solution allows log events to continue progress without stalling while processing selects. Selects can be triggered at any time on all tables, a specific table, or for specific primary keys of a table. DBLog executes selects in chunks and tracks progress, allowing them to pause and resume. The watermark approach does not use locks and has minimum impact on the source.

> Log event processing is briefly paused (step 1). Watermarks are generated by updating the watermark table (steps 2 and 4). The chunk selection occurs between the two watermarks and the chunk is stored in-memory (step 3). After the high watermark is written, we resume log event processing, send received log events to the output, and watch for the low watermark event in the log. Once the low watermark event is received, we start removing rows from the chunk in-memory for all primary keys that changed between the watermarks (step 6). Once the high watermark event is received, we finally append all remaining chunk entries to the output-buffer before processing log events again in a sequential manner (step 7).

> The window is opened by writing a low watermark, then the selection runs, and the window is closed by writing a high watermark. As the exact position of the select is unknown, all selected chunk rows are removed, which collide with log events within that window. This ensures that the chunk selection can not override the history of log changes.

Items: the watermark-window algorithm this topic's own `examples.py` implements by hand against
this sandbox's real PostgreSQL, run under concurrent updates and deletes.

## Debezium docs: PostgreSQL connector (incremental snapshots, read-only variant)

URL: https://debezium.io/documentation/reference/stable/connectors/postgresql.html
Fetched: 2026-11-01.

Quotes:
> The chunk size determines the number of rows that the snapshot collects during each fetch operation on the database. The default chunk size for incremental snapshots is 1024 rows.

> If the progress of an incremental snapshot is interrupted, you can resume it without losing any data. After the process resumes, the snapshot begins at the point where it stopped, rather than recapturing the table from the beginning.

> During the snapshot windows, the primary keys of the READ events in the buffer are compared to the primary keys of the incoming streamed events. If no match is found, the streamed event record is sent directly to Kafka. If Debezium detects a match, it discards the buffered READ event, and writes the streamed record to the destination topic, because the streamed event logically supersede the static snapshot event.

> The Debezium connector for PostgreSQL does not support schema changes while an incremental snapshot is running.

> data-collections N/A An array that contains regular expressions matching the fully-qualified names of the tables to include in the snapshot.

> additional-conditions N/A An optional array that specifies a set of additional conditions that the connector evaluates to determine the subset of records to include in a snapshot.

> You submit a stop snapshot signal to the signaling table by sending it in a SQL INSERT query. The stop-snapshot signal specifies the type of the snapshot operation as incremental, and optionally specifies the tables that you want to omit from the currently running snapshot.

> To run an incremental snapshot with read-only access, the connector uses the current in-progress transaction as high and low watermarks. The state of a chunk's window is updated by comparing the transaction ID of write-ahead-log events or heartbeat events against low and high watermarks.

Items: the default chunk size, the pause/resume-without-loss guarantee, Debezium's own buffered
collision-resolution mechanism (the documented analogue this topic's hand-written algorithm
reproduces by hand on real data), the PostgreSQL schema-change limitation, the signal fields
(`data-collections`, `additional-conditions`, `stop-snapshot`), and the PostgreSQL read-only
variant's own watermark source.

## Debezium docs: MySQL connector (read-only incremental snapshots)

URL: https://debezium.io/documentation/reference/stable/connectors/mysql.html
Fetched: 2026-11-01.

Quotes:
> To run an incremental snapshot with read-only access, the connector uses the executed global transaction IDs (GTID) set as high and low watermarks. The state of a chunk's window is updated by comparing the GTIDs of binary log (binlog) events or the server's heartbeats against low and high watermarks.

Items: the MySQL read-only variant's own watermark source, named for contrast with PostgreSQL's
transaction-id-based one; this sandbox has no MySQL server (confirmed absent in topic 11), so

## Flink CDC docs: PostgreSQL CDC connector (parallel incremental snapshot)

URL: https://nightlies.apache.org/flink/flink-cdc-docs-stable/docs/connectors/flink-sources/postgres-cdc/
Fetched: 2026-11-01.

Quotes:
> Incremental snapshot is a new mechanism to read snapshot of a table. Compared to the old snapshot mechanism, the incremental snapshot has many advantages, including: (1) source can be parallel during snapshot reading, (2) source can perform checkpoints in the chunk granularity during snapshot reading, (3) source doesn't need to acquire global read lock (FLUSH TABLES WITH READ LOCK) before snapshot reading.
