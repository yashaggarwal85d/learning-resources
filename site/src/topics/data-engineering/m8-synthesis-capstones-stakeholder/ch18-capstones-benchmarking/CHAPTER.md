## The chapter

### The problem it solves

Every topic in Chapters 1–17 ended with a number on screen: an AUC, a latency, a throughput, a recall. This chapter asks the question none of them stopped to answer: **is the number true?** The claim the chapter exists to prove, stated once in topic 1's hook and tested by every topic after it: **a benchmark's first job is to not lie to the person reading it, and the easiest way it lies is measuring the system before it has warmed up, averaging away its tails, feeding it unrealistic data, or borrowing a vendor's number without checking what question that number actually answered.** The chapter teaches the method that makes a reported number defensible — discard the warm-up, report percentiles instead of means, generate load that doesn't lie about its own worst case, use data skewed the way real data is skewed — then names the analytical benchmark suites (TPC-H, TPC-DS, ClickBench, the Join Order Benchmark, TPC-DI) as worked examples of the method applied at industry scale, and the trap (vendor "benchmarketing," DeWitt-clause licence terms) that the method exists to resist. This closes Milestone 8's first half; §18.2's pass bar and §18.3–§18.5's capstones (not reel topics) are what the method is then applied to.

### Order of ideas, and why

1. **Warm-up and steady-state measurement (topic 1).** Opens, as Chapter 17's handoff promised, with the first and most basic way a benchmark lies: measuring a system before it has reached the state it will actually run in. Every later topic in this chapter assumes its own numbers were taken after this topic's discard rule was applied.
2. **Latency percentiles and histogram aggregation (topic 2).** Once the numbers are taken from a warmed-up system, the next lie is how they are summarized: a mean hides exactly the tail that matters, and merging per-host or per-window data wrongly (averaging percentiles instead of merging histograms) manufactures a second, subtler lie on top of the first. This topic also hosts the chapter's one lab's center: a closed-loop and a constant-rate generator, run at the same offered load with a 2-second stall injected, showing the gap between the two load models' reported p99 — the sharpest possible demonstration that *how load is generated* is itself a measurement choice, not a neutral detail.
3. **Representative data and workload skew (topic 3).** A correctly measured, correctly summarized number is still a lie if the data behind it isn't shaped like real data: uniform toy rows hide the hot keys, skewed joins and cardinality surprises production data actually has. This topic turns the lab's load generator into a full, seeded, reproducible harness by giving it a realistic (Zipfian) dataset instead of a uniform one, and states the harness and dataset as a committed artifact, the half of the chapter lab's final clause ("publish the harness, seeded dataset and baseline") that belongs here.
4. **Analytical benchmark suites (topic 4).** Closes the chapter by naming the five industry-standard suites built from exactly this method (steady state, percentiles, representative skew) at a scale this course's own harness cannot reach, and the trap the method gets built to resist: a vendor choosing which of these suites to publish, under what licence terms, is still "benchmarketing" even when every individual number it reports is true. Closes with the final clause of the chapter lab (publishing the baseline alongside the harness and dataset) and hands off to §18.2's pass bar, which asks for exactly this chapter's method applied to a real capstone's own benchmarks.

### One running example: benchmarking the shop's own Postgres

Same fictional online shop as Chapters 1–17 (no real company, no real person; `orders`, `orders-rollup`, `order-events`), now treated as the system under test instead of the system under build. Every topic benchmarks the same question against the same table — "how fast does the shop's order-lookup query run, honestly measured?" — and each topic changes one thing about how that question is answered:

- **Topic 1** runs the query in a tight loop from cold start and shows the first several seconds of latency numbers are not the steady-state number anyone should report, then applies a steady-state detector to find where they stop lying.
- **Topic 2** replaces the tight loop with two load generators — closed-loop and constant-rate — at the same offered rate, injects a 2-second artificial stall mid-run (standing in for a GC pause or a lock wait), and shows the closed-loop generator's own slowdown hides exactly the samples a constant-rate generator would have reported as the worst ones.
- **Topic 3** replaces the query's uniform `customer_id` parameter with a Zipfian one, matching real traffic's hot-key shape, and shows the same query's p99 move once a few customers dominate the traffic the way real top customers do.
- **Topic 4** steps back from the shop's one query to name what TPC-H, TPC-DS, ClickBench, the Join Order Benchmark and TPC-DI each stress that this one-table harness cannot, and publishes the harness, the seeded dataset generator and the measured baseline as the chapter's one committed, reproducible artifact.

Every number on screen comes from the topic's own `examples.py`, run against this sandbox's Postgres; where the syllabus's own scale (TPC-H's full schema, a 10M-row representative dataset, a multi-node cluster) cannot be reproduced on the build machine, the topic says so and states the disclosed, smaller scale it actually measured.

### 1. Warm-up and steady-state measurement (`de.warmup-steady-state-measurement`): full, §18.1

- **Folder:** `warmup-steady-state-measurement`. About 15 min. Hosts the chapter's steady-state measurement groundwork ahead of topic 2's lab.
- **Scope:** "why the first minutes lie: JIT/code-gen warm-up, cold page cache and buffer pool, empty result caches, LSM compaction debt and table-format small files not yet accumulated; detecting steady state, run length, repeated trials with confidence intervals, and reporting cold-cache and hot-cache numbers as two separate results" — the full syllabus line, clause by clause:
  - *why the first minutes lie:* a benchmark that starts measuring the instant a system starts running reports the system's worst, most transient state as if it were representative, because several independent things are all still "spinning up" at once.
  - *JIT/code-gen warm-up, cold page cache and buffer pool, empty result caches, LSM compaction debt and table-format small files not yet accumulated:* five distinct causes, each with its own clock: a JIT or query-plan code-gen layer (named, not built on Postgres, since Postgres has no JIT-by-default query path in this sandbox's configuration — stated honestly rather than invented) needs repeated executions before it compiles its fastest path; the OS page cache and Postgres's own shared-buffer pool are empty on a cold start and every early read pays a disk round trip a later, cached read won't; a result cache (named forward to Chapter 17's BI topics, reused by name) starts with nothing cached; an LSM-based store accumulates unmerged levels that a long-enough run would compact away (named for comparison, not reproduced on Postgres's own B-tree storage); a table-format lakehouse's "small files" problem (Chapter 6's material, named forward) is the same shape of debt in a different storage model. The topic reproduces the two causes this sandbox's own Postgres actually exhibits — cold shared-buffer/page cache and an empty result cache — directly, and names the other three from their own documentation as the same failure in systems the build machine doesn't run.
  - *detecting steady state, run length:* a simple, explicit detector (a sliding window of recent latency samples whose mean stops moving by more than a stated threshold between windows) marks the point after which the run is in steady state; the *run length* is how long the measurement window after that point must last to be trustworthy, stated as a number of requests or a duration, not "long enough."
  - *repeated trials with confidence intervals:* a single steady-state run still has sampling noise; repeating the trial several times and reporting a confidence interval around the reported number (not just the number itself) is what lets a reader judge whether two systems' reported numbers actually differ or only appear to.
  - *reporting cold-cache and hot-cache numbers as two separate results:* a system's cold-start number and its steady-state number answer two different real questions (a system that restarts often cares about the first; one that runs for days cares about the second) and reporting only one, or averaging them together, answers neither question honestly.
- **Leaves out:** how the resulting steady-state samples should be summarized once collected — means versus percentiles, and how to merge them across trials or hosts (topic 2); whether the data driving these requests is realistic (topic 3); the named industry suites that apply this same discipline at scale (topic 4).
- **Outcomes:** Run the shop's order-lookup query from a cold Postgres start and show the first requests are measurably slower than the rest; build and apply a steady-state detector that marks where the run stops improving; run repeated trials and report a confidence interval, not a single number; report a cold-cache and a hot-cache result for the same query as two separate, honestly labeled numbers instead of one blended average.
- **Introduces:** `warmup-causes-taxonomy`, `steady-state-detection`, `repeated-trials-confidence-interval`, `cold-vs-hot-cache-reporting`. **Uses:** none from an already-live chapter (Chapter 17's own concepts, including `de.distributed-sql-architecture`'s single-node-commit baseline, are named in prose only, since Chapter 17 is not live). **Declared:** basic familiarity with a database connection pool and a page/buffer cache. Builds on Chapter 6's table-format small-files material (not yet live) and Chapter 17's own benchmarking-adjacent numbers (not yet live) in prose only.
- **Bridge:** "That closes this chapter's look at where the data stack is heading. Everything in it, from a point-in-time join to a managed zero-ETL feed, is a claim someone has to be able to test, not just trust. The next chapter is the method for testing claims like that honestly: how to benchmark a system so the number you report is the number that's actually true, starting with the first way a benchmark lies — the warm-up period you forgot to discard." (Chapter 17's own handoff, quoted exactly; see the assumption at the top.)
- **Handoff:** "A warmed-up, steady-state run still has to be summarized into one number someone reads, and the easiest way to summarize it is also the most dishonest: a mean. The next topic is why that single number hides exactly the tail that matters, and what to report instead."
- **Prerequisites panel:** none from an already-live chapter; basic familiarity with a database query and a cache (Before this). **Pre-notes terms:** JIT, page cache, buffer pool, result cache, steady state, confidence interval.

### 2. Latency percentiles and histogram aggregation (`de.latency-percentiles-histogram-aggregation`): full, §18.1

- **Folder:** `latency-percentiles-histogram-aggregation`. About 18 min. Hosts the chapter lab's closed-loop/constant-rate/stall core.
- **Scope:** "why means hide tails; p50/p95/p99/p99.9/max; percentiles cannot be averaged across hosts or time windows, so merge histograms (HdrHistogram) or mergeable sketches (t-digest/DDSketch, §5.6) instead; tail amplification under fan-out (a request touching 100 shards hits at least one shard's p99 about 63% of the time)" — the full syllabus line, clause by clause:
  - *why means hide tails:* a mean latency can look fine while one request in a hundred takes ten times as long, because the mean is dragged only slightly by a rare large value — the topic reproduces this directly on the shop's query by injecting a rare, large stall and showing the mean barely moves while the tail percentiles move sharply.
  - *p50/p95/p99/p99.9/max:* five points on the same latency distribution, each answering a different real question (the typical request, the request a typical unlucky user sees, the request a very unlucky user sees, the request so rare it shows up only at real production volume, and the worst case ever observed in the run) — reported together, never as a single "the latency," because each omits what the others show.
  - *percentiles cannot be averaged across hosts or time windows, so merge histograms (HdrHistogram) or mergeable sketches (t-digest/DDSketch, §5.6) instead:* averaging two hosts' p99s is not the fleet's p99 (a worked counterexample on two simulated hosts shows the naive average both overstating and understating the true combined p99 depending on how the two hosts' distributions differ); **HdrHistogram**'s own documentation describes exactly the fix: fixed-bucket histograms that can be merged bucket-by-bucket, so a true combined percentile can be read off the merged histogram instead of approximated by averaging; **t-digest** and **DDSketch** (Chapter 5 §5.6's quantile-sketch material, named by id since it is already live) are the mergeable-sketch alternative for when memory, not exactness, is the constraint, reused here rather than re-taught.
  - *tail amplification under fan-out (a request touching 100 shards hits at least one shard's p99 about 63% of the time):* a fan-out request's overall latency is set by its *slowest* shard, and the probability that at least one of 100 independent shards, each with its own 1 percent chance of being a p99-or-worse outlier, lands in that tail is `1 − 0.99^100 ≈ 0.63` — the topic derives this number from first principles on the shop's own simulated fan-out (a query artificially split across shards) rather than quoting it, and shows it directly: a single shard's own p99 at the query's full concurrency hits the end-to-end request at a far higher rate than 1 percent once fan-out is added.
- **Leaves out:** whether the latency distribution being summarized came from realistic data in the first place (topic 3); the named industry suites whose own published numbers depend on exactly this percentile discipline (topic 4). The stall injected by this topic's lab is an artificial, deterministic one (a `pg_sleep`-based delay on a fraction of requests), not a reproduction of a real GC pause or lock wait's actual cause.
- **Outcomes:** Show a mean latency staying nearly flat while p99 and p99.9 move sharply under an injected rare stall; report p50 through max together and say what real question each answers; merge two hosts' histograms correctly and show the naive average of their percentiles disagreeing with the true merged value; derive the fan-out tail-amplification probability for a stated shard count and reproduce it on a simulated fan-out query. Run the chapter lab's core: a closed-loop generator and a constant-rate generator at the same offered load against the shop's query, with a 2-second stall injected, and show the closed-loop generator's own self-slowdown hides exactly the worst samples the constant-rate generator reports, then report the corrected (constant-rate) p99 as the number that should actually be published.
- **Introduces:** `mean-hides-tail-latency`, `percentile-ladder-p50-to-max`, `histogram-merge-vs-percentile-average`, `fanout-tail-amplification`, `closed-loop-vs-constant-rate-generator`, `coordinated-omission-effect`. **Uses:** `steady-state-detection`, `cold-vs-hot-cache-reporting` (topic 1); `quantile-sketches-t-digest` (Chapter 5, §5.6, live). **Declared:** basic probability (independent events, a product of probabilities). Builds on HdrHistogram's own documented bucket structure in prose only (no course chapter teaches HdrHistogram's internals).
- **Bridge:** "A warmed-up, steady-state run still has to be summarized into one number someone reads, and the easiest way to summarize it is also the most dishonest: a mean. This topic is why that single number hides exactly the tail that matters, and what to report instead: the full percentile ladder, histograms merged instead of averaged, and the fan-out math that makes a tail far more common than it looks." (Answers topic 1's handoff.)
- **Handoff:** "Every number in this topic came from requests generated against the shop's real schema with a uniform customer id — data far tidier than any real traffic actually is. The next topic asks what changes once the data looks the way real data looks: a few customers dominating the traffic, not an even spread."
- **Prerequisites panel:** topic 1; Chapter 5's quantile-sketch topic (Before this). **Pre-notes terms:** percentile, histogram, mergeable sketch, fan-out, closed-loop generator, constant-rate generator, coordinated omission.
- **Hook:** a load test reports a mean latency of forty milliseconds and a shopper still waits four full seconds on a bad request, during the same run. Which five numbers would have shown that gap where the mean hid it, and which of two ways to generate the test's own load would have caught the four-second request at all? (A prediction: the full percentile ladder shows it immediately at p99.9, but only if the load generator itself paces requests at a constant rate — a closed-loop generator that waits for each response before sending the next would have quietly skipped measuring exactly the slow request that caused the wait.)
- **Visual idea:** the chapter's two-generators figure: a closed-loop lane (thick, visibly pausing after the stall before its next request) and a constant-rate lane (thin, ticking at a fixed metronome regardless of the stall) both feeding the same query box with a red stall block dropped in mid-run; each lane's own histogram **Plotted** beside it, the closed-loop lane's histogram visibly missing mass in the tail the constant-rate lane caught; a separate panel derives the fan-out probability as a shrinking bar (`0.99` to the hundredth power) landing at `0.37`, labeled as "the chance every shard is fine," its complement called out as the real answer.

### 3. Representative data and workload skew (`de.representative-data-workload-skew`): full, §18.1

- **Folder:** `representative-data-workload-skew`. About 15 min. Builds the chapter lab's seeded, reproducible dataset generator.
- **Scope:** "uniform toy data hides hot keys, skewed joins and spills; Zipfian key distributions (the YCSB default), realistic cardinalities and cross-column correlations (what breaks cardinality estimators), scale factors, and the seeded data generator as a committed artifact of the benchmark" — the full syllabus line, clause by clause:
  - *uniform toy data hides hot keys, skewed joins and spills:* a benchmark that generates its `customer_id` or join key uniformly at random never produces the one thing real traffic reliably produces, a small number of keys carrying a disproportionate share of the load — the topic reruns topic 2's exact query and load shape with a uniform key first, confirming no hot-key effect appears, as the baseline the rest of the topic contrasts against.
  - *Zipfian key distributions (the YCSB default):* a Zipfian distribution (a small number of keys each with disproportionately high frequency, following a power law) is YCSB's own documented default key-popularity model for exactly this reason — it is named and cited from YCSB's own paper/documentation, then reproduced on the shop's query by replacing the uniform key generator with a Zipfian one and re-running topic 2's same measurement, showing the previously-flat latency distribution grow a visible hot-key tail as a few customers now dominate.
  - *realistic cardinalities and cross-column correlations (what breaks cardinality estimators):* a toy dataset's columns are usually generated independently, so a query planner's cardinality estimator (which typically assumes column independence) estimates correctly almost by construction; real data's columns correlate (a `country` column correlates with a `currency` column, a `product_category` correlates with a `price_band`), and an estimator that assumes independence under-, or over-, estimates a join's output size badly once correlation is introduced — the topic reproduces one correlated-column pair on the shop's schema and shows Postgres's own query plan mis-estimate a join's row count against it, compared against the same join on independently generated columns.
  - *scale factors:* a benchmark dataset is generated at a stated multiple of a base size (TPC-style "scale factor," named here and defined fully by topic 4), so a result can be compared against another run at the same declared scale rather than an unstated one; this topic states its own scale factor (the row count actually generated) explicitly, at the small, disclosed size the build machine can hold and query interactively.
  - *the seeded data generator as a committed artifact of the benchmark:* the Zipfian-and-correlated generator, given the same seed, produces byte-identical data every run — the topic commits this generator (not just a one-off dataset) as `examples.py`'s own reusable function, the dataset half of the chapter lab's "publish the harness, seeded dataset and baseline" clause.
