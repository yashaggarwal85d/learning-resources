## Lab claims (executed, not just sourced)

- **All four processing approaches run on the identical synthetic feed, honestly scaled down from the chapter's own 20 GB target** (disclosed as a fraction of a percent of it, not silently presented as the full size), with the native engine (Polars/DuckDB) measured fastest by roughly two orders of magnitude over the plain loop, multiprocessing modestly ahead of the plain loop, and async measured clearly slower than the plain loop — a real, lived demonstration that applying the wrong chapter tool (async, built for network waits) to a CPU-bound local-parsing workload doesn't just fail to help, it actively costs more.
- **A real tracemalloc bug was found and fixed during this build**: an initial version compared the number of live memory blocks immediately AFTER each approach returned, rather than the peak traced during the run, and got a backwards result — the plain loop's own short-lived per-row objects are already freed by snapshot time, while a library's persistent wrapper objects are still live and get counted instead. Fixed by reading `tracemalloc.get_traced_memory()`'s own peak before stopping, which measures the real high-water mark instead of a post-hoc live count.
- **py-spy genuinely attaches to an already-running process and reads its real call stack**, confirmed by checking that the dump output names the exact function (`process_plain_loop`) the live subprocess was actually executing, not a canned or simulated trace.
- **Scalene genuinely separates Python time from native time** on the Polars/DuckDB leg, confirmed by reading native time as the clear majority of the reported split from Scalene's own JSON output.
- **The Arrow-vs-CSV handoff timing was re-designed after the first, more "obvious" test (buffer-address identity) gave a real, honest negative result**, documented above rather than discarded, with the actual measurable benefit relocated to where it genuinely shows up.

## Red-team analysis of the two predicts

- **Predict 1 (step 3):** the tempting wrong answer ("async beats the plain loop here too, the way topic 3 showed it winning at I/O") is directly refuted by the measured result — async is the slowest of the four approaches on this CPU-bound local-parsing workload, exactly because it's the wrong tool for it.
- **Predict 2 (step 7):** the tempting wrong answer ("an external attach can only see generic addresses, not real function names, without code changes") is directly refuted by py-spy's own dump output naming the exact function and file the live process was running.
