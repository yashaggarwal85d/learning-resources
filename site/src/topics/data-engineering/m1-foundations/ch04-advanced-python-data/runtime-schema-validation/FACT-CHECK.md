## Red team

- **Is the "Rust core speed difference" claim actually demonstrated, or just asserted from the source?** Initially attempted as an in-process comparison against a hand-rolled pure-Python validator function, but that measurement came back the wrong way (the hand-rolled function was faster, since Pydantic's own object-construction and validator-dispatch overhead dominates at this scale and isn't a fair stand-in for "no Rust core") — caught and not published. Fixed by running the real, sourced comparison instead: Pydantic v1 (pure-Python core) against Pydantic v2 (Rust core) on the identical model definition and identical generated records, in two separate Python environments. That comparison lands consistently in the expected direction across repeated runs and is disclosed as a one-time cross-venv measurement rather than something `examples.py` claims to reproduce on every run, since v1 and v2 cannot coexist in one process and a scratch venv isn't guaranteed to exist in every environment this file might run in.
- **Does the pandas-vs-Polars pandera reveal actually test "the same schema," or two schemas that happen to look alike?** The two schema classes declare the identical fields and the identical `Field(in_range=...)` check, differing only in which base class (`pandera.pandas.DataFrameModel` vs. `pandera.polars.DataFrameModel`) they inherit from — the minimum difference pandera's own API requires to target a different backend, not two independently written validation rules that happen to agree.
- **Does the row-level vs. batch-level comparison fairly represent the claim, or stack the deck?** Both paths check the exact same condition (every value falls within `[0, n]`) against the exact same data; the row-level path is a plain Python `for` loop doing the identical bounds check per element, and the batch-level path is pandas' own vectorized `Series.between()` — not a contrived slow version of the row-level path.
- **Predict question (step 4) wrong-answer trap.** The tempting wrong answer ("a pandas DataFrame and a Polars DataFrame need two separately written schemas") plays on the correct intuition that pandas and Polars are genuinely different libraries with different APIs underneath, while missing that pandera's own class-based schema syntax is designed to abstract over exactly that difference. The reveal demonstrates the same declared checks working against both, not merely asserting it.

## Problem Solving

The pydantic Rust-core speed comparison was attempted twice. The first attempt compared Pydantic v2 against a hand-written pure-Python validator function doing equivalent type coercion; this measurement came back showing Pydantic *slower*, which would have been a dishonest basis for the sourced "Rust core" speed claim, since the hand-rolled function skips all of Pydantic's object-construction and validator-dispatch machinery and isn't a fair "no Rust core" baseline. Rather than publish a reveal built on that misleading number, the comparison was rebuilt as a real Pydantic v1 vs. v2 benchmark in two separate Python environments (the sandbox's installed v2, and a freshly `pip install`ed v1 in a scratch venv, cleaned up afterward) — the comparison the sourced claim is actually about, and the one that measures in the expected direction. `examples.py` itself was then rewritten to demonstrate something reproducible in any single environment instead (validation cost scaling linearly with record count), with the real v1-vs-v2 numbers disclosed here as a one-time measurement rather than claimed as part of every run.
