## Red team

- **Is the "jitter spreads out synchronized retries" demonstration a real measurement, or just asserting the source's own claim back at it?** It's an explicitly disclosed simulation, not a network measurement — and that's deliberate, matching the source article's own method: the AWS Architecture Blog post's own graphs come from "a simple simulation of OCC behavior" it names directly, not a live multi-client test against a real backend. This topic's simulation computes, for a hundred clients that all fail at the same instant, the retry time each one schedules under capped backoff with no jitter (all landing on the same fixed delay) versus with full jitter (spread randomly across that same cap), and measures how many land in the same ten-millisecond bucket — a direct, honest computation of the mechanism the source describes, labeled as a simulation throughout (reel, narration, post-notes), never presented as a live network measurement.
- **Does the circuit breaker step fairly represent "fails fast," or does the comparison stack the deck?** The Closed-state calls and the Open-state call are the identical call (the same always-failing endpoint, the same client timeout) wrapped by the same breaker instance — the only thing that changes is the breaker's own state, confirmed by checking `breaker.state` directly rather than assuming it tripped. The Open-state call's sub-millisecond elapsed time is compared against the Closed-state calls' own measured elapsed times from the same run, not against a hypothetical number.
- **Does the idempotency demonstration actually prove deduplication, or just that the client got the same text back?** The assertion checks the server's own internal effect counter (`FlakyHandler.state["effect_count"]`), not only the three response bodies looking identical — ruling out the uninteresting alternative that the server happened to compute the same response three times rather than truly skipping the second and third write. The no-key control (two calls, no `Idempotency-Key` header, two distinct effects) is kept in the same run as a contrast, so the dedup behavior is shown to come from the key, not from some other property of the endpoint.
- **Predict question (step 4) wrong-answer trap.** The tempting wrong answer ("capped exponential backoff on its own already prevents clients bunching up") plays on the correct intuition that backoff does slow every client down, while missing that it slows every client down by the *same* schedule, so they remain correlated. This is precisely the distinction the source's own time-series graphs make (backoff alone still shows "clusters of calls"), so the trap is real, not manufactured.

## Problem Solving

No abandoned approaches this topic. The deadline-propagation demonstration was simplified once during drafting: an earlier version tried to measure it across three real local HTTP hops (A calls B calls C over real sockets), which worked but added real network variance that didn't change what the step teaches (a shared deadline running out partway through a chain) while making the "why did hop C skip its work" trail harder to read at a glance. Replaced with a direct, in-process three-hop simulation using `time.monotonic()` for the shared deadline and real `time.sleep()` calls for each hop's own work — still a real, measured elapsed-time trail, just without the added real-socket round trips that weren't the point of the step.
