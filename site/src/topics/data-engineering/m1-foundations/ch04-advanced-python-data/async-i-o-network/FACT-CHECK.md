# Fact-check — de.async-i-o-network

| # | Claim | Status | Basis |
|---|---|---|---|
| 1 | The event loop is the core of every asyncio application; it runs tasks/callbacks and performs network I/O on one thread | Confirmed | SOURCES.md, asyncio event loop docs |
| 2 | `asyncio.TaskGroup` is a more modern alternative to `create_task()` | Confirmed | SOURCES.md, same doc |
| 3 | The first sibling task in a TaskGroup that fails with a real exception cancels the rest of the group | Confirmed, and independently reproduced | SOURCES.md, same doc. `examples.py`'s `taskgroup_structured_concurrency()` measures a long-running sibling genuinely cancelled when another sibling fails. |
| 4 | A semaphore's internal counter blocks `acquire()` once it reaches zero, until a `release()` call | Confirmed, and independently reproduced | SOURCES.md, asyncio synchronization docs. `examples.py`'s `semaphore_backpressure()` measures the real peak concurrent in-flight requests never exceeding the semaphore's own limit. |
| 5 | `asyncio.timeout()` cancels the wrapped task and transforms the resulting `CancelledError` into a catchable `TimeoutError` | Confirmed, and independently reproduced | SOURCES.md, asyncio tasks docs. `examples.py`'s `cancellation_timeout()` measures the real elapsed time close to the timeout, not the slow task's own duration, with `TimeoutError` genuinely raised. |
| 6 | There is no asynchronous file I/O in asyncio; `loop.run_in_executor()` is the documented way to avoid blocking the loop on regular file I/O | Confirmed | SOURCES.md, same doc. Generalizes directly to any blocking call, not just file I/O — `examples.py`'s own lab extends this to a blocking `time.sleep()`. |
| 7 | A blocking call made directly inside a coroutine (not offloaded) delays every other task on the same event loop, not just the one that made the call | Confirmed, and independently reproduced | `examples.py`'s `blocking_call_stalls_loop()` measures sibling coroutines' own finish times pushed back to the blocking call's full duration, and measures the delay disappear once the same call runs via `run_in_executor()`. |
| 8 | psycopg's `AsyncConnection`/`AsyncCursor` support an asyncio interface with the same design as the sync API | Confirmed | SOURCES.md, psycopg docs |
| 9 | An `AsyncConnection` can be used by several `asyncio.Task`s at once, but access to the connection is serialized, the same as with threads | Confirmed, and independently reproduced | SOURCES.md, same doc. `examples.py`'s `async_postgres_driver()` fans twenty queries out concurrently on one connection against this sandbox's own running Postgres 16 cluster and confirms every row returned is correct. |
| 10 | Async and threads for I/O fan-out, compared honestly rather than assumed | Measured directly, result nuanced | `examples.py`'s `async_vs_threads_fanout()` measures latency for the identical fan-out against this sandbox's own stub server and finds the two close at this scale (occasionally favoring threads) — the lab's own server adds comparable per-connection overhead on both sides, so this topic does not claim async is unconditionally faster. |
| 11 | The real, measured asymmetry between async and threads is resource cost per unit of held concurrency, not latency at modest scale | Measured directly | `examples.py`'s `memory_cost_of_concurrency()` holds two thousand units of concurrency open at once as real OS threads versus as asyncio tasks and measures real OS threads costing roughly two orders of magnitude more resident memory for the identical amount of simultaneous waiting. |

## Lab claims (executed, not just sourced)

- **A single event loop genuinely interleaves many waiting coroutines rather than serializing them**, measured directly: twenty real network waits of fifty milliseconds each against a real local stub server finish in close to fifty milliseconds total, not one second.
- **A real deadlock was found and fixed during this build**: an earlier version of the async-vs-threads comparison joined the worker threads directly on the main thread, which is the same thread running the event loop under `asyncio.run()` — blocking that thread on `Thread.join()` stopped the loop from ever servicing the connections those threads were making, hanging indefinitely. Fixed by running the thread-start-and-join logic through `run_in_executor()` so the loop keeps running while the main thread waits. This is itself a direct, lived demonstration of this topic's own "a blocking call stalls the loop" claim.
- **A real asyncio PostgreSQL round trip against this sandbox's own running Postgres 16 cluster** (started for this build, not assumed running) returns correct, verified rows for twenty concurrently fanned-out queries on one connection.

## Red-team analysis of the two predicts

- **Predict 1 (step 3):** the tempting wrong answer ("twenty waits cost twenty times as long") is directly refuted by the measured near-single-wait total time — the event loop's whole point, stated in its own docs before the lab measures it, is interleaving exactly these waits for free.
- **Predict 2 (step 7):** the tempting wrong answer ("a blocking call only costs the coroutine that made it") is directly refuted by the measured sibling-delay result — every other coroutine on the same loop is genuinely delayed too, which is exactly the lived bug this build's own research ran into and had to fix in its own benchmark code.
