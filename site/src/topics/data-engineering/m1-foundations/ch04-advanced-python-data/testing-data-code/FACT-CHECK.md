## Red team

- **Does the integration-test layer actually prove anything, given Testcontainers itself can't run here?** The claim being demonstrated isn't "Testcontainers runs in this sandbox" — it's "an integration test proves something a mock never can, because the dependency can really disagree." That claim is proven directly: the test runs a real `INSERT` then `SELECT` against this sandbox's own live PostgreSQL cluster (confirmed reachable via `pg_lsclusters` and a direct `psql` connection before writing the demo), not against an in-memory stub. What's honestly disclosed as unavailable is only the mechanism Testcontainers specifically adds on top — spinning up and tearing down a disposable container per test — confirmed absent via a real failing `docker info` call, not assumed.
- **Is the Pact demo a real contract test, or just hitting a plain mock HTTP server?** The distinguishing claim in the source is that the interaction is defined once (`upon_receiving`/`given`/`with_request`/`will_respond_with`) and the mock server is built *from* that definition, so the consumer's real client code is exercised against it — not a hand-rolled stub the test also controls the shape of. `examples.py`'s `pact_consumer_contract_test()` does exactly this: `fetch_user()` is a standalone client function with no knowledge of the Pact test, called against `mock_provider.url` the same way it would call a real provider, and the response it gets back is generated by the Pact framework's own mock server from the registered interaction, not hand-written inline.
- **Does the property test actually test more than a unit test would have, or is that just assumed?** Verified directly rather than assumed: the property test runs the same dedup rule (`len(effects) == len(distinct keys))` across 100 generated sequences of varying length (1–50) and varying key reuse patterns, including sequences a hand-written unit test is unlikely to pick (e.g. the same key repeated at both the start and the end of a 50-item sequence, interleaved with several other keys). A single hand-picked 3-attempt example, by contrast, cannot by construction explore more than the one case it was written for.
- **Predict question (step 4) wrong-answer trap.** The tempting wrong answer ("three hand-picked retries already cover the dedup logic") plays on the correct intuition that a hand-written test with multiple retries does exercise *some* dedup behavior, while missing that it only ever exercises the specific sequence someone thought to type — not the space of sequences a generator searches. This is the same class of trap as the backoff-vs-jitter predict question in the previous topic: the wrong answer isn't false on its face, it's incomplete in a way the reveal makes concrete.

Rather than retry further or fabricate quoted text, this source was dropped entirely; the topic proceeds with four sources, each already covering one of the syllabus's four named mechanisms (Hypothesis, Testcontainers, Pact/contract testing) directly, with the golden-output mechanism covered conceptually by the Codurance article without needing a snapshot-library-specific citation.
