## Red team

- **Is the prepared-statement failure reproduction a fair test of the documented caveat, or an artificial one?** The documented mechanism is: a SQL-level `PREPARE`/`EXECUTE` is forwarded straight to the physical backend (not tracked/rewritten by PgBouncer, per `pgbouncer-config.txt`'s own note elsewhere on the page), and transaction pooling can hand that backend to a different transaction before the original client's next one. Rather than relying on a timing-sensitive race between concurrent clients (tried first, and abandoned — see Problem Solving below), the reproduction here uses a second, explicit client running `DISCARD ALL` on the one shared backend between the first client's `PREPARE` and the third client's `EXECUTE`, which is exactly the kind of "someone else used this physical connection in between" event the documentation warns about, made deterministic rather than left to chance. The test records and asserts that all three steps land on the *same* physical backend PID throughout (`same_physical_backend_reused_throughout`), which rules out the alternative, uninteresting explanation that the failure happened because of an actual *different* backend rather than the shared-backend handoff itself.
- **Could the bulk-load timing comparison be dominated by connection setup rather than the load itself?** Initially yes — the first version of `bulk_load_comparison` timed ADBC's own `connect()` call inside the measured region, making it look over 4x slower than `COPY` (a misleading result, since the `executemany`/`COPY` timings already excluded `psycopg.connect()`, which ran once before the timed block). Fixed by moving `adbc_dbapi.connect()` outside the timed region to match how the psycopg timings are structured, after which ADBC's bulk-ingest time tracked `COPY` closely across repeated runs. The assertion kept in `examples.py` (`adbc_much_faster_than_executemany`, not `adbc_within_2x_of_copy`) is deliberately looser than the single best run suggested, since the absolute times here are tens of milliseconds and genuinely vary run to run — the qualitative claim (close to `COPY`, far ahead of `executemany`) is what's asserted, not a specific ratio.
- **Does the Little's Law demonstration honestly represent the source's worked example?** The source's own numbers (0.1s hold, pool of 5) are illustrative, not measured on real hardware. A first attempt measured this sandbox's own trivial round-trip time (`select 1`) as Ws, which is near-instant on a local loopback connection and produced an honestly-reported but pedagogically thin result (a required pool size under one connection). Fixed by measuring Ws against a connection held for a disclosed, simulated amount of request-handling work (`pg_sleep`), explicitly labeled as simulated work rather than passed off as a real workload's own processing time, and kept the trivial round-trip measurement alongside it as an explicit contrast (`simulated_work_ws_much_larger_than_trivial_round_trip`) so the reel can state plainly that network round-trip alone understates a real connection's hold time.
- **Predict question (step 4) wrong-answer trap.** The tempting wrong answer ("yes — it's the same client's own connection the whole time") plays on the correct intuition that the *client's TCP connection* to PgBouncer never changes, while missing that the *backend* PgBouncer forwards to can change between transactions under transaction pooling. This is precisely the distinction the documentation draws ("each transaction ends up in a different connection"), so the trap is real, not manufactured.

## Problem Solving (abandoned approach, recorded for anyone resuming this topic)

An earlier attempt reproduced the prepared-statement caveat using two Python threads racing to control which backend PgBouncer handed back next (forcing two distinct backends open concurrently via a `threading.Barrier`, then releasing them in a controlled order). This genuinely hung for the length of a 30-minute background-task limit on one run, for a reason not fully diagnosed (suspected an interaction between `psycopg`'s connection I/O and Python thread scheduling in this sandbox, not a PgBouncer or PostgreSQL issue). Abandoned in favor of the current, fully sequential, zero-concurrency reproduction (client A prepares, client B explicitly runs `DISCARD ALL` on the same backend, client C's `EXECUTE` fails) — deterministic, fast, and faithful to the real mechanism without needing any race at all.
