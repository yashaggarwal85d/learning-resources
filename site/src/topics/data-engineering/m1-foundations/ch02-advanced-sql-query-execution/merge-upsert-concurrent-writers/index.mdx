## Into the internals

Every topic in this section has been about reading. `MERGE` and `ON CONFLICT` are where §2.1 closes on writing — specifically, writing when you don't know in advance whether a row already exists.

### `MERGE`: one join, several conditional actions

`MERGE` runs a join between a target and a source, classifies each resulting row as `MATCHED`, `NOT MATCHED BY SOURCE`, or `NOT MATCHED [BY TARGET]`, and performs the first `WHEN` clause of the matching kind that succeeds:

```sql
MERGE INTO wines w
USING wine_stock_changes s ON s.winename = w.winename
WHEN NOT MATCHED AND s.stock_delta > 0 THEN
  INSERT VALUES (s.winename, s.stock_delta)
WHEN MATCHED AND w.stock + s.stock_delta > 0 THEN
  UPDATE SET stock = w.stock + s.stock_delta
WHEN MATCHED THEN
  DELETE
RETURNING merge_action(), w.winename, old.stock AS old_stock, new.stock AS new_stock;
```
(PostgreSQL 18 docs, `MERGE`, "Examples" — the `wines` example quoted directly.) `MERGE` can `INSERT`, `UPDATE` and `DELETE` in the same statement, branching per row — something neither `INSERT ... ON CONFLICT` nor a plain `UPDATE`/`DELETE` can do alone.

### The duplicate-source-row error

`MERGE`'s documentation states a requirement you must enforce yourself: "you should ensure that the join produces at most one candidate change row for each target row... If it does [join to more than one], then only one of the candidate change rows will be used to modify the target row; later attempts to modify the row will cause an error. If the repeated action is an `INSERT`, this will cause a uniqueness violation, while a repeated `UPDATE` or `DELETE` will cause a cardinality violation; the latter behavior is required by the SQL standard" (PostgreSQL 18 docs, `MERGE`, "Notes"). A source table with two rows for the same key — a duplicate in a staging load, say — doesn't silently apply both; it errors, loudly, on the second attempt. This is a feature, not friction: the alternative (quietly applying one of the two and discarding the other) is exactly the kind of silent data loss this chapter has spent several topics warning against.

### Why `MERGE` can still race, and `ON CONFLICT` cannot

`INSERT ... ON CONFLICT DO UPDATE` makes an unusually strong promise: it "guarantees an atomic `INSERT` or `UPDATE` outcome; provided there is no independent error, one of those two outcomes is guaranteed, even under high concurrency. This is also known as **UPSERT**" (PostgreSQL 18 docs, `INSERT`). `MERGE` does not make that promise, and PostgreSQL's own transaction-isolation documentation is explicit about why: "a `MERGE` command with both `INSERT` and `UPDATE` subcommands looks similar to `INSERT` with an `ON CONFLICT DO UPDATE` clause but **does not guarantee that either `INSERT` or `UPDATE` will occur**... If `MERGE` attempts an `INSERT` and a unique index is present and a duplicate row is concurrently inserted, then a uniqueness violation error is raised; `MERGE` does not attempt to avoid such errors by restarting evaluation of `MATCHED` conditions" (PostgreSQL 18 docs, §13.2, "Transaction Isolation"). The mechanical reason: `ON CONFLICT` is implemented as a genuinely atomic attempt-insert-then-pivot-on-conflict operation at the index level, while `MERGE` decides `MATCHED` vs `NOT MATCHED` from an ordinary snapshot read of the join and then performs the chosen action — if another transaction's conflicting insert commits in the gap between that read and `MERGE`'s own `INSERT`, `MERGE` just hits the unique-index error like any other `INSERT` would, instead of silently re-routing to the `UPDATE` branch the way `ON CONFLICT` does. The two statements "are not interchangeable" (`MERGE` docs, "Notes") precisely because of this gap: `ON CONFLICT` is the one to reach for when the actual requirement is "insert, or update if it's already there, with no possible race," and `MERGE` is the one to reach for when the real requirement is richer than that single pattern — multiple source tables' worth of logic, `DELETE` as one of the branches, or several differently-conditioned `INSERT`/`UPDATE` branches — accepting that a genuine concurrent conflict can still raise an error you must be ready to retry.

(`MERGE` does handle the more ordinary concurrency case gracefully: "if `MERGE` attempts an `UPDATE` or `DELETE` and the row is concurrently updated but the join condition still passes... then `MERGE` will... perform its action on the updated version of the row," re-evaluating conditions from the top against that newer version — same source. It is specifically the *insert* path, racing against a *concurrent insert* of the same key, that can still error.)

### `RETURNING`, `merge_action()`, and `OLD`/`NEW`

`MERGE` could not report what it did at all until PostgreSQL 17 added `RETURNING` support, "the new `RETURNING` function `merge_action()` reports on the DML that generated the row" (PostgreSQL 17 release notes) — so a single statement that might `INSERT`, `UPDATE` or `DELETE` different rows can tell you, per row, which one actually happened. PostgreSQL 18 went further with general "`OLD` and `NEW` support for `RETURNING` clauses in `INSERT`, `UPDATE`, `DELETE`, and `MERGE` commands" (PostgreSQL 18 release notes) — the `wines` example above uses exactly this, returning `old.stock` and `new.stock` side by side so a caller can see the before-and-after of a row that may have been inserted, updated or deleted by that one statement.

### Lakehouse `MERGE INTO`: a file-rewrite, not a row-level update

A row-store `MERGE` updates a row in place (subject to its own MVCC rules). A lakehouse table — Parquet files under a table format such as Delta Lake or Iceberg (Chapter 6 in full) — has no in-place row update at all: a `MERGE INTO` there has to rewrite whole data files that contain any touched row. Delta Lake's own documentation warns about exactly this cost on the common `WHEN NOT MATCHED BY SOURCE DELETE` pattern: "we recommend adding an optional conditional clause to avoid fully rewriting the target table" (Delta Lake documentation, "Table deletes, updates, and merges") — an unconditional delete-the-rest clause can force every file in the table to be rewritten, not just the files containing matched rows. The same documentation notes the operation "shuffles data multiple times to compute and write the updated data," with the shuffle partition count directly controlling how many new files come out the other side. The syllabus's §6.3 covers lakehouse MERGE's full cost model (copy-on-write vs merge-on-read, write amplification); the takeaway here is simply that "MERGE" means something structurally different once the target isn't a page-based row store — the same four letters, a very different engineering cost.

## Build, break, measure

### Lab · The two-session MERGE race

This hosts the §2.1 chapter lab's concurrent-writer part — the suite's final trap.

1. **Reproduce the race.** Open two sessions against a scratch copy of `customers` (unique on `customer_id`). In session A, begin a `MERGE INTO customers USING (...) ON customer_id = ... WHEN NOT MATCHED THEN INSERT ...` for a brand-new `customer_id`, but pause after the join/before commit (a `pg_sleep` inside a wrapping transaction, or a breakpoint, works for a lab). In session B, insert a row with the *same* `customer_id` and commit. Let session A's `MERGE` proceed and commit; confirm it raises a uniqueness-violation error — the exact failure mode the transaction-isolation docs describe, reproduced on purpose.
2. **Confirm `ON CONFLICT` doesn't race the same way.** Replace session A's `MERGE` with the equivalent `INSERT ... ON CONFLICT (customer_id) DO UPDATE ...` and repeat the exact same two-session timing. Confirm it never errors: it either inserts (if it wins the race) or updates (if session B won), but one of those two outcomes is guaranteed either way.
3. **Report `merge_action()` and `OLD`/`NEW`.** Run a `MERGE` against `orders`/a staging table that has a genuine mix of inserts, updates and deletes in one statement, with `RETURNING merge_action(), old.*, new.*`, and confirm each returned row correctly labels which action produced it and shows the right before/after values (`old`/`new` are NULL on the sides that don't apply — an insert has no `old`, a delete has no `new`).

<section data-section="production">

## In production — a review checklist

- **Default to `INSERT ... ON CONFLICT DO UPDATE` for the simple upsert case**, specifically because it is race-free by construction; reach for `MERGE` when the logic genuinely needs more than one branch, more than one action kind, or a second source table.
- **Guarantee at most one source row per target key before a `MERGE`**, or be ready to handle the uniqueness/cardinality-violation error it raises on a duplicate; don't assume a `MERGE` with a duplicated source silently picks one row and moves on.
- **Treat a `MERGE`'s `INSERT` branch as still capable of raising a unique-violation error under concurrency**, and have an application-level retry for that specific case if the workload has concurrent writers racing on the same key.
- **Use `merge_action()` and `OLD`/`NEW` in `RETURNING`** whenever a caller needs to know exactly what a mixed `INSERT`/`UPDATE`/`DELETE` statement actually did to each row, rather than re-querying afterward.
- **On a lakehouse table, write `MERGE INTO` conditions to touch as few files as possible** — an unconditional catch-all branch can force a full-table rewrite that a plain row-store `MERGE` would never need.
