## Into the internals

Every topic so far treated a row's columns as flat scalars. Real rows aren't always that simple: this chapter's `orders` table now carries `tags` and `discount_amounts` (arrays), and `metadata` (a JSON document) — a promo-tag list, its matching discounts, and free-form checkout context that doesn't fit a fixed schema.

### Three nested shapes, one relational engine

- **Arrays** (`tags text[]`, `discount_amounts numeric[]`) hold an ordered list of same-typed values in one column.
- **Composite types** are SQL's "struct" — `CREATE TYPE address AS (city text, zip text)` gives a column that is itself a labeled bundle of fields, and `ROW(...)` constructs one inline.
- **JSON/JSONB** is the de facto "map"/document type: PostgreSQL has no native `MAP` type, so arbitrary, dynamically-shaped key-value data (this chapter's `orders.metadata`) is stored as `jsonb`, queried with the operators and path language below.

### Unnesting one array is safe; unnesting two, carelessly, is not

`unnest(anyarray) → setof anyelement` "expands an array into a set of rows... read out in storage order" (PostgreSQL 18 docs, §9.19, "Array Functions and Operators"). One array, one row per element — nothing surprising yet. The trap appears the moment a row has *two* arrays meant to line up element-by-element, like this chapter's `tags` and `discount_amounts`.

There are two ways to write "unnest both," and they do different things:

```sql
-- WRONG: two separate unnest() calls as two separate FROM items.
-- An order with 3 tags and 3 discounts returns 3 x 3 = 9 rows,
-- pairing every tag with every discount, including the wrong ones.
SELECT o.order_id, tag, discount
FROM orders o, unnest(o.tags) AS tag, unnest(o.discount_amounts) AS discount
WHERE o.order_id = 42;

-- RIGHT: one unnest() call, given both arrays as arguments.
-- Zips them positionally: exactly 3 rows, each tag with its own discount.
SELECT o.order_id, tag, discount
FROM orders o, unnest(o.tags, o.discount_amounts) AS t(tag, discount)
WHERE o.order_id = 42;
```

The first query is topic 1's product operator (`×`) in disguise: two independent `FROM` items with no correlation between them combine as every row of one with every row of the other — exactly the Cartesian product, just produced by two unrelated calls to the same function instead of two different tables. The second query uses `unnest`'s documented multi-argument form: "Expands multiple arrays (possibly of different data types) into a set of rows. If the arrays are not all the same length then the shorter ones are padded with `NULL`s. This form is only allowed in a query's `FROM` clause" (same source) — it is, by specification, "as if `unnest` had been called on each parameter separately and combined using the `ROWS FROM` construct" (§7.2.1.4, "Table Functions"), which pairs by position, not by cross product. If `tags` ever legitimately has one more element than `discount_amounts` (a tag with no discount), the multi-argument form NULL-pads the shorter array rather than silently miscounting rows.

**`WITH ORDINALITY`** adds the element's position as an extra column — "an additional column of type `bigint`... numbers the rows of the function result set, starting from 1" (§7.2.1.4) — useful whenever the array's order carries meaning (the first tag applied, say), rather than relying on the engine's unspecified row order to recover it.

### Querying JSON: operators, then a relational view

`orders.metadata` holds free-form checkout context such as `{"device": "ios", "utm": {"source": "email", "campaign": "winter25"}}`. The arrow operators drill in directly: `metadata -> 'utm'` returns the nested JSON object, `metadata -> 'utm' ->> 'source'` returns `'email'` as text (`->>` always returns `text`; `->` keeps the result as `json`/`jsonb` for further chaining) (PostgreSQL 18 docs, §9.16.1).

For anything beyond one or two levels, or for turning a JSON array into several output rows and columns at once, **`JSON_TABLE`** (PostgreSQL 17+) is the cleaner tool: it "queries JSON data and presents the results as a relational view, which can be accessed as a regular SQL table... [using] a JSON path expression to extract a part of the provided data to use as a row pattern," with a `COLUMNS` clause defining the output schema and a `NESTED PATH` clause for data at a deeper nesting level (PostgreSQL 18 docs, §9.16.4). Tellingly, "the rows produced by `JSON_TABLE` are laterally joined to the row that generated them, so you do not have to explicitly join the constructed view with the original table holding JSON data" (same source) — `JSON_TABLE` is built *on* `LATERAL` (topic 6): it is, mechanically, a per-row computation that turns one JSON document into however many output rows its path produces, exactly the shape topic 6 introduced for top-N-per-group. `JSON_TABLE()` was added in PostgreSQL 17 (released 2024-09-26, "New SQL/JSON capabilities, including constructors, identity functions, and the `JSON_TABLE()` function, which converts JSON data into a table representation," PostgreSQL 17 release notes).

### Binary semi-structured types: not just "JSON, but faster"

Storing semi-structured data as JSON *text* means every read has to re-parse the whole document, byte by byte, even to pull out one field — and a column of raw text gets none of a columnar engine's per-column statistics or pruning, because to the storage layer it's all just one opaque string. Several systems instead define a genuine **binary** semi-structured type:

- **Snowflake's `VARIANT`** "can store a value of any other type, including `OBJECT` and `ARRAY` values," up to 128 MB of uncompressed data per value (Snowflake SQL reference, "Semi-structured data types"). Snowflake's own guidance is explicit about when flattening still wins: "for better pruning and less storage consumption, we recommend flattening your `OBJECT` and key data into separate relational columns if your semi-structured data includes" dates/timestamps stored as strings, numbers inside strings, or arrays (Snowflake docs, "Considerations for semi-structured data stored in `VARIANT`") — a `VARIANT` column is efficient, not free.
- **Databricks' `VARIANT`** type (Databricks Runtime 15.3+) likewise "represents semi-structured data," and is directly tied to the table format underneath it: "Iceberg v2 tables do not support `VARIANT` columns. Apache Iceberg v3 supports `VARIANT` columns" (Databricks SQL reference, "VARIANT type") — the binary type is a feature of the *storage format version*, not just the query engine.
- **The Parquet/Iceberg v3 Variant type, with shredding**, is the open, on-disk specification underneath both: "query engines encode each Variant value in a self-describing format, and store it as a group containing `value` and `metadata` binary fields in Parquet. Since data is often partially homogeneous, it can be beneficial to extract certain fields into separate Parquet columns to further improve performance. This process is called **shredding**... [it] enables the use of Parquet's columnar representation for more compact data encoding, column statistics for data skipping, and partial projections" (Apache Parquet format specification, "Variant Shredding"). Concretely: `SELECT variant_get(event, '$.event_ts', 'timestamp') FROM tbl` only has to load the shredded `event_ts` column — the specification's own example — instead of deserializing every row's entire variant payload just to reach one field.

The gap between this and plain JSON text is architectural, not incidental: a shredded field is a real Parquet column with its own statistics and encoding, prunable like any other; a field buried in a JSON text blob is invisible to the storage layer until a row is fully parsed. The exact speedup for any one workload depends on how homogeneous the data is and which fields are actually queried — *measure in build* rather than assume a fixed multiplier.

## Build, break, measure

### Try it · The cardinality trap, caught by an assertion

1. **Reproduce the explosion.** Load a handful of orders with `tags` and `discount_amounts` of equal length (three each is enough) and run both the "WRONG" and "RIGHT" queries above. Assert, don't eyeball: the row count from the two-`unnest()`-items version must equal `array_length(tags,1) * array_length(discount_amounts,1)` for that order, and the single-call version's row count must equal `array_length(tags,1)` exactly (or the longer array's length, once you test an intentionally mismatched pair, with the shorter side's values coming back `NULL`).
2. **Add ordinality and recover intended order.** Rewrite the correct query with `unnest(o.tags, o.discount_amounts) WITH ORDINALITY AS t(tag, discount, pos)` and confirm `pos` recovers each tag's original array position, independent of whatever row order the engine happens to produce.
3. **Query `metadata` three ways.** Pull `metadata ->> 'device'` and `metadata -> 'utm' ->> 'campaign'` with the arrow operators, then rewrite the same extraction as a `JSON_TABLE` with a `COLUMNS` clause, and confirm both approaches return identical values — the second is clearer once more than one or two fields need extracting at once, not a different answer.

<section data-section="production">

## In production — a review checklist

- **Never comma-separate two `unnest()` calls over arrays that are supposed to line up.** Use the multi-argument `unnest(arr1, arr2, ...)` form, or join explicitly on `WITH ORDINALITY` position, and verify row counts with an assertion, not a glance at a sample.
- **Add `WITH ORDINALITY` whenever an array's position carries meaning** (first tag applied, primary vs secondary) rather than depending on engine-specific, unspecified row order.
- **Reach for `JSON_TABLE` once a JSON extraction needs more than a field or two,** rather than stacking `->`/`->>` chains that get harder to read with every added level.
- **Flatten the handful of fields you query constantly into real typed columns, even inside a semi-structured-friendly system.** Snowflake's own guidance — pull dates, numbers, and arrays out of `VARIANT` for pruning — generalizes to every engine in this comparison.
- **Prefer a binary variant type with shredding (Iceberg v3, Snowflake/Databricks `VARIANT`) over plain JSON text for anything queried repeatedly at scale,** and confirm the table format version actually supports it (Iceberg v2 does not) before assuming the feature is available.
