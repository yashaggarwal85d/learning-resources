## Into the internals

Chapter 1 priced the machine. This topic prices nothing; it fixes what a query *means*, because every later topic in this chapter — rewrites, cost estimates, join algorithms, physical design — only makes sense once "what the query computes" is pinned down exactly. The running example is the shop's analytics warehouse: `orders` (100,000,000 rows), `order_items` (300,000,000 rows, about 3 per order), `products` (50,000 rows) and `page_views` (100,000,000 rows, the clickstream).

### The operators, as a tree

Relational algebra is a small set of operators, each taking one or two relations and returning a relation, that compose into a tree — the same tree shape a query optimizer builds and rewrites (CMU 15-445/645, Fall 2024, Lecture 1, "Relational Model & Algebra," §6):

| Operator | Symbol | SQL | Reads |
|---|---|---|---|
| Selection | σ_predicate(R) | `WHERE` | "the rows of R where predicate holds" |
| Projection | π_A1,…,An(R) | `SELECT` list | "R, keeping only columns A1…An" |
| Join | R ⋈ S | `JOIN … ON/USING` | "combine R and S's rows that agree on their shared columns" |
| Product | R × S | `CROSS JOIN` | "every pairing of an R row with an S row" |
| Union / Intersect / Except | R ∪ S, R ∩ S, R − S | `UNION`, `INTERSECT`, `EXCEPT` | "rows in R or S / in both / in R but not S" |
| Aggregation | γ_cols;aggs(R) | `GROUP BY` | "R, collapsed to one row per group, with aggregates" |

`σ_status='refunded'(orders) ⋈ products` reads directly as `SELECT * FROM orders JOIN order_items … JOIN products WHERE orders.status = 'refunded'`, and the tree shape — leaves are tables, each node is one operator, the root is the final result — is exactly what the planner draws internally and what topic 16 names as a plan tree. Every later §2.1–§2.4 topic adds a new operator or a new way to execute one of these; none of them replace this vocabulary.

### Why SQL is a bag language, not a set language

A mathematical *set* cannot contain the same element twice. A *bag* (multiset) can, and counts how many times. Codd's 1969–70 relational model defined a relation as a set of tuples, but SQL, standardized afterward, chose bags: "a relation is an unordered set that contains the relationship of attributes that represent entities… it is possible to have repeated / duplicated elements in a relation" (CMU 15-445/645 Lecture 1, §4, "Relational Model"). This is not a bug tolerated for convenience — it is necessary for SQL to mean what it obviously should mean. Run

```sql
SELECT customer_id FROM orders;
```

against 100,000,000 orders and you get 100,000,000 rows, with a frequent customer's id repeated as many times as they ordered. Each row is a fact — "this order happened" — and collapsing repeated customer ids would silently delete facts: an aggregate like `SELECT customer_id, SUM(amount) FROM orders GROUP BY customer_id` depends on every order row surviving long enough to be counted once each. A set-based `SELECT DISTINCT customer_id FROM orders` throws that multiplicity away on purpose, and only on purpose: `DISTINCT`, and the `ALL`-less set operators below, are the few places SQL deliberately steps down from bag to set semantics.

### The set-operator pairs, union-compatible, bag by default

SQL's set operators come in `ALL` and non-`ALL` forms, and the non-`ALL` form is the one that is *not* the mathematical default:

- `R UNION ALL S` — the bag union: every row of R, every row of S, concatenated, nothing removed. This is the direct SQL spelling of algebraic ∪ over bags.
- `R UNION S` — bag union *followed by duplicate elimination*, "in the same way as `DISTINCT`" (PostgreSQL 18 docs, §7.4, "Combining Queries").
- `R INTERSECT ALL S` / `R INTERSECT S` — a row appears `min(count in R, count in S)` times with `ALL`, or once (if it appears at all) without.
- `R EXCEPT ALL S` / `R EXCEPT S` — a row appears `max(0, count in R − count in S)` times with `ALL`, or once (if the result is positive) without.

Both operands must be **union-compatible**: same number of columns, pairwise-compatible types (PostgreSQL 18 docs, §7.4). `INTERSECT` binds tighter than `UNION` and `EXCEPT`, which associate left to right without parentheses — `query1 UNION query2 INTERSECT query3` means `query1 UNION (query2 INTERSECT query3)`, the same source states.

**Worked example.** The shop flags orders two ways: an automated fraud score (`flagged_auto`, built from `orders`) and a manual review queue (`flagged_manual`, built from `page_views` support-ticket joins). Suppose order 42 is on both lists.

```sql
SELECT order_id FROM flagged_auto
UNION ALL
SELECT order_id FROM flagged_manual;   -- order 42 appears twice: bag union
```
```sql
SELECT order_id FROM flagged_auto
UNION
SELECT order_id FROM flagged_manual;   -- order 42 appears once: set union
```

If the goal is "how many flag *events* fired" (a count that should include order 42 twice, once per detector), `UNION ALL` is correct and `UNION` silently under-counts. If the goal is "which distinct orders are flagged by either detector," `UNION` is correct and `UNION ALL` double-counts order 42 in any later `COUNT(*)`. Picking the wrong one doesn't error — it gives a plausible, wrong number.

### The equivalences an optimizer relies on

A query is one tree of these operators; several different trees compute the *same* bag. The optimizer (topic 17 covers this at the plan-rewrite level) is only free to pick the fastest tree among trees proven equivalent to the one you wrote. Three equivalences recur everywhere:

- **Selection pushdown.** `σ_p(R ⋈ S) ≡ R ⋈ σ_p(S)` when `p` only mentions columns of `S`. Filtering `products` by `category = 'electronics'` before joining to `order_items` touches far fewer rows than joining everything and filtering after — same CMU lecture's own example: filtering a billion-row relation down to one matching row *before* a join beats joining first and filtering after, even though both trees return the same answer (§6, "Observation"). This is why `WHERE` clauses that only touch one table are safe to write anywhere in the query; the engine moves them regardless.
- **Projection pushdown.** `π_cols(R ⋈ S) ≡ π_cols(π_(cols ∩ R)(R) ⋈ π_(cols ∩ S)(S))` — drop columns you don't need as early as possible, ideally right at the scan. This shrinks every row moving through the rest of the tree and, named only here and taught in full in Chapter 1 topic 7, is what lets a columnar engine skip whole column chunks it was never going to read.
- **Join commutativity and associativity.** `R ⋈ S ≡ S ⋈ R` and `(R ⋈ S) ⋈ T ≡ R ⋈ (S ⋈ T)`. Both hold for bags exactly as for sets — a join's result bag doesn't depend on operand order or grouping. This is the entire reason a cost-based optimizer can search *join orders* at all (topic 20): it is choosing among algebraically equal trees, not changing the answer.

### Where bag intuition breaks: idempotence

Sets obey `A ∪ A = A` — union with yourself changes nothing, because a set cannot hold an element twice anyway. Bags do not: `A UNION ALL A` doubles the count of every row A has. This single broken law has real consequences:

- A rewrite that is valid for sets — "a relation unioned with itself is redundant, drop one copy" — is **not** valid for bags whenever a plan must preserve multiplicities (a later `COUNT`, `SUM`, or an `ALL`-flavoured set operator downstream). The optimizer tracks which parts of a query need bag-exact answers and which have already been reduced to sets (by `DISTINCT`, `GROUP BY`, or a non-`ALL` set operator) before it is allowed to apply set-only simplifications.
- Selection and projection *do* distribute over bag union exactly as over set union — `σ_p(R ∪ S) ≡ σ_p(R) ∪ σ_p(S)` holds either way, because filtering and projecting a bag preserve each surviving row's multiplicity. It is specifically idempotence-style laws (dropping a duplicate operand, `A ∩ A = A`, `A − A = ∅` under careless duplicate handling) that need the min/max-of-counts bag definitions above, not the naive set ones.

### Why `UNION` pays for a dedup, and `UNION ALL` doesn't

This is a planner fact, not folklore. PostgreSQL's planner treats `UNION ALL` and `UNION` through genuinely different code paths (`src/backend/optimizer/prep/prepunion.c`, function header: *"UNIONs are much different from INTERSECT/EXCEPT"*; and *"If a subquery consists entirely of simple UNION ALL operations, it is converted into an 'append relation'"*):

- **`UNION ALL`** becomes an **Append** node (or, when every branch is itself a plain `UNION ALL`, the whole chain flattens into one Append) over the branches' own plans — concatenation, no comparison between rows, no extra pass over the data. `generate_union_paths()`'s own comment: the row-count estimate "is correct for UNION ALL" straight from the summed input sizes.
- **`UNION`** builds that same Append, then is *required* to deduplicate it, and tries two different ways to do that and keeps whichever the cost model says is cheaper: a **HashAggregate** (`AGG_HASHED`) over the appended rows, or a **Sort** followed by a **Unique** node (`create_sort_path` then `create_unique_path`) when hashing the grouping columns isn't viable. Either way, the planner's own row estimate switches from "sum of child sizes" (`UNION ALL`'s number) to an estimated distinct-group count, because — as the same function's comment states — "distinct(A union B) ≤ distinct(A) + distinct(B)."

So a `UNION` costs an Append *plus* a full extra pass that either hashes or sorts every row to find duplicates — paid even when the two inputs happen to share no rows at all, because the planner cannot know that without doing the work. `INTERSECT` and `EXCEPT` (with or without `ALL`) go through a third, dedicated path, `nodeSetOp.c`'s `SetOp` node: sorted inputs are merge-joined on the grouping columns while counting matches per group (`SETOP_SORTED`), or an in-memory hash table counts occurrences per group across both inputs (`SETOP_HASHED`) — the file's own header is explicit that "this node type is not used for UNION or UNION ALL, since those can be implemented more cheaply (there's no need to count the number of matching tuples)." `ALL` only changes which counts the node emits (`min`, or `max(0, …)`), never whether the counting happens.

The practical rule: reach for `UNION ALL` whenever you don't actually need deduplication (branches you already know are disjoint, or a case where duplicates are meaningful facts), and reserve `UNION`/`INTERSECT`/`EXCEPT` for when the dedup or the set logic is the point — then let the planner's cost-based choice between hashing and sorting do its job.

## Build, break, measure

### Try it · See the bag, see the plan

1. **The bag is real.** `SELECT customer_id FROM orders ORDER BY customer_id LIMIT 20;` against the 100,000,000-row `orders` table: a customer who ordered five times appears five times, in a plain, unaggregated result. This is the mechanism, not a bug — confirm it by also running `SELECT customer_id, COUNT(*) FROM orders GROUP BY customer_id ORDER BY COUNT(*) DESC LIMIT 5;` and checking the counts match how many raw rows that customer_id had.
2. **Watch the dedup appear.** Run `EXPLAIN` on both of:
   ```sql
   SELECT order_id FROM orders WHERE status = 'refunded'
   UNION ALL
   SELECT order_id FROM orders WHERE amount > 500;

   SELECT order_id FROM orders WHERE status = 'refunded'
   UNION
   SELECT order_id FROM orders WHERE amount > 500;
   ```
   Expect the first plan to be an `Append` over the two filtered scans and nothing else. Expect the second to add a `HashAggregate` or a `Sort` + `Unique` node on top of the same `Append` — the exact choice depends on the planner's cost estimate for the row counts involved (*measure in build*; report which one PostgreSQL 18 actually picks for this data distribution, and why, from the `EXPLAIN` cost numbers).
3. **Break the idempotence intuition.** Compare `COUNT(*)` from `(SELECT order_id FROM orders WHERE status = 'refunded') UNION ALL (SELECT order_id FROM orders WHERE status = 'refunded')` (doubles the refunded count) against the same query with `UNION` (returns exactly the refunded count, unchanged) — the visible proof that `A ∪ A ≠ A` for bags but `A ∪ A = A` once `UNION`'s implicit `DISTINCT` is in play.
4. **`INTERSECT ALL` vs `INTERSECT`.** Build two small bags by hand — `VALUES (1),(1),(2)` and `VALUES (1),(2),(2)` — and run both `INTERSECT ALL` (expect `1, 2`, since `min(count)` is `1` for both values) and `INTERSECT` (expect `1, 2` deduplicated to one each regardless) to see the multiplicity arithmetic directly, independent of any one engine's query planner internals.

## In production — a review checklist

- **Default to `UNION ALL` unless you specifically need deduplication.** Every unnecessary `UNION` costs a hash or sort pass over the combined rows that `UNION ALL` never pays. Reach for `UNION` only when duplicate rows across the branches would be a wrong answer, not a wasted comparison.
- **Know which `ALL` you forgot.** `INTERSECT`/`EXCEPT` without `ALL` silently collapse multiplicities the same way `UNION` does — if a downstream `COUNT` or `SUM` depends on exact row counts, use the `ALL` form and verify against a hand-built small bag first.
- **Don't assume `A ∪ A = A` holds in SQL.** A query that is logically "the same relation combined with itself" (common after a refactor merges two branches that turn out identical) needs the `ALL`-aware version of that reasoning, or it will quietly double every row it touches.
- **State union-compatibility explicitly.** Mismatched column counts or incompatible types across set-operator branches are a compile error, not a silent bug, but mismatched *semantics* across branches (one side pre-deduplicated, the other not) is not caught by the engine and must be reviewed by eye.
- **Read `EXPLAIN` for the extra node, not just the extra time.** An unexpected `HashAggregate` or `Sort`/`Unique` sitting on top of an `Append` is the fingerprint of a `UNION` that could have been a `UNION ALL`; it is the first thing to check when a query that "just appends two queries" runs slower than expected.
