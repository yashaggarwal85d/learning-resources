## Red-team notes
- The high-cardinality result (`HashAggregate` measuring slower than a forced `GroupAggregate`, 2479.537 ms vs. 1737.653 ms) is the most load-bearing claim in this topic, since it's the actual "crossover" the chapter lab asks for. Checked this wasn't a one-off: both the default-planner run and the forced-sort run were read from a single clean `EXPLAIN (ANALYZE)` invocation each, with the plan's own node type confirmed in the output before trusting the number; the gap (about 1.43×) is large enough that ordinary measurement noise on this shared instance is not a plausible alternative explanation.
- An earlier attempt to show a `work_mem`-driven spill on the *low-cardinality* query (reducing `work_mem` to 64kB) found no effect — 100 groups fit in a hash table small enough that even a severely reduced `work_mem` didn't force a batch split. This is reported honestly in post-notes rather than silently dropped: the "memory" factor in this topic is demonstrated by the high-cardinality case's natural spill (64 partitions, 321 batches), not by an artificially shrunk `work_mem` on a query that never needed to spill in the first place.
- A follow-up attempt to widen `work_mem` (256MB) on the high-cardinality query, expecting the spill to disappear, instead showed 5 batches rather than 1 — and took longer (3154.514 ms) than the default 4MB run (2479.537 ms) on this shared, noisy instance. This result was not used anywhere in the reel or examples.py: it doesn't cleanly demonstrate the point it was meant to (more memory should mean fewer batches and less time), and reporting a confusing, likely noise-dominated number would be worse than reporting nothing. The clean, reproduced default-vs-forced-sort comparison above carries the "memory" point instead.
- "Eager aggregation pushed below joins" (PostgreSQL 19 beta, named in the syllabus and in CHAPTER.md's scope) could not be measured: this session's PostgreSQL instance is version 16.15, and the feature does not exist in any form that session's `EXPLAIN` output could show. No claim about its mechanics or performance appears in the reel; it is named in post-notes as a pointer to further reading (the PostgreSQL 19 release notes, once GA) rather than guessed at.
- Currency: PostgreSQL 18 is current stable; nothing in the 19 release-candidate changelog changes `enable_hashagg` semantics, `work_mem`'s role, or the parallel-aggregation two-stage design documented here. The eager-aggregation-below-joins feature itself is new in 19 and is treated as a forward pointer, not a claim about 18's behavior.
