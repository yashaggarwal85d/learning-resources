# Fact-check, self-review, 2026-10-22

Each claim re-derived by hand against the fetched source text (`SOURCES.md`), or re-run against the real PostgreSQL instance.

|---|---|---|
| `work_mem` is the base budget per sort/hash operation, not per query or per session; several operations (or sessions) multiply it | Verbatim from `runtime-config-resource.txt`: "a complex query might perform several sort and hash operations at the same time… several running sessions could be doing such operations concurrently… the total memory used could be many times the value of work_mem." | Confirmed |
| Hash-based operations get `work_mem × hash_mem_multiplier`, more room than sort gets the same `work_mem` | Verbatim from the same source. Reproduced directly: same `work_mem = 4MB`, `hash_mem_multiplier` 1.0 → 4.0 took the same hash join from 8 batches to 2. | Confirmed, and reproduced |
| A sort too big for `work_mem` spills to an external merge sort rather than erroring | `EXPLAIN (ANALYZE)` on `ORDER BY sort_key` at every tested `work_mem` below 256MB reported `Sort Method: external merge  Disk: …kB`; at 256MB it reported `Sort Method: quicksort` instead — read directly off the plan's own line, not assumed. | Confirmed |
| At the default `work_mem` (4MB), the spilling sort is not meaningfully slower than the fully in-memory one | Re-ran both twice each with `max_parallel_workers_per_gather = 0` to rule out a parallel-plan confound: 4MB (external merge) 757–785 ms vs. 256MB (quicksort) 829–849 ms — the spilling run was consistently *faster*, not slower, across both repeats. | Confirmed, and the direction (spill faster, not just "comparable") is reported as measured |
| A severely undersized `work_mem` (64–128kB) *is* measurably slower, even though the same ~35MB still spills | Same method, same query, `work_mem` 64kB and 128kB: 1017–1090 ms, consistently slower than both the 4MB and 256MB runs across two repeats each. Disk spilled (`35288`–`35296kB`) is within noise of the 4MB run's `35248kB` — so the slowdown isn't "more data written," since the write volume barely changed; it's how many merge passes that data takes to combine, which the docs and `nodeHash.c` describe only abstractly for the hash side, not for sort. This topic reports the *effect* (measured) without overclaiming the exact pass count, which `EXPLAIN` doesn't report for sorts. | Confirmed, with the pass-count mechanism left unmeasured rather than guessed |
| A hash join too big for its budget partitions into batches instead of erroring, and the batch count doubles each time `work_mem` halves | Forced `enable_mergejoin = off`, `enable_nestloop = off`, `max_parallel_workers_per_gather = 0` on the same join across `work_mem` settings: 256MB→1 batch, 4MB→4, 1MB→16, 512kB→32, 256kB→64, 64kB→256. At the two adjacent halvings actually tested (1MB→512kB and 512kB→256kB), the batch count doubles exactly (16→32→64); the three widely-spaced settings used in the reel (256MB, 4MB, 1MB, 256kB, 64kB) only show the net effect of several halvings at once, not a per-step rate. | Confirmed at the granularity actually tested; the reel states "doubles each halving," checked at fine granularity rather than inferred from coarse jumps |
| `ExecHashIncreaseNumBatches` is the mechanism that doubles the batch count, with a cutoff (`growEnabled`) | Read directly in `nodeHash.c` (REL_18_0): the function's own name and its "do nothing if we've decided to shut off growth" guard, both present in the fetched source text. Quoted only the single-line fragment that `sources.mjs check` can verify word for word (the function's multi-line `/* … */` doc-comment quotes broke the checker because every continuation line carries a literal `" * "` prefix in the raw text; rather than fight the checker, the claim is supported by the parts that quote cleanly). | Confirmed |
| PostgreSQL protects a skewed (frequent) key's rows from repeated spilling with a dedicated in-memory bucket | Read directly in `nodeHash.c`: the skew-tuple branch and "we never decrease the number of buckets" comment both present. Attempted to measure this independently (a join on `mem_demo.skew_key`, where one value carries 1% of all rows, at `work_mem = 64kB`) — `EXPLAIN`'s own output showed only the ordinary `Buckets`/`Batches` line, no separate skew indicator. There is no GUC to turn the optimization off for an A/B comparison either. | Confirmed as documented mechanism; **not independently measurable** on this version — reported as a gap, not faked as measured |

## Red-team notes
- The most load-bearing — and most counter-intuitive — claim in this topic is that spilling itself, at the *default* `work_mem`, is not slower here than staying fully in memory. Checked this wasn't a fluke of JIT warm-up or a single lucky run: both the 4MB and 256MB sorts were run twice each, with consistent orderings (4MB always faster than 256MB across both repeats) and with `max_parallel_workers_per_gather = 0` fixed so a parallel-plan choice at one `work_mem` setting but not another couldn't be the real explanation. The honest framing kept in the reel is narrower than "spilling is free": it's "a spill small enough to need only a modest number of merge passes measured no slower here," not a general claim that disk I/O never costs anything.
- Considered whether the 4MB-faster-than-256MB result was really about quicksort's larger in-memory array having worse cache behavior than several smaller sorted runs merged from disk (a real, documented phenomenon in external-sort literature) rather than something specific to this machine's storage. Did not claim this explanation in the reel or post-notes, since it wasn't independently measured (e.g. with `perf` cache-miss counters) — named only as a plausible "why" in post-notes' internals section, clearly marked as not measured here.
- The hash join's batch counts (1, 4, 16, 64, 256) are suspiciously clean powers of 4, which could look cherry-picked. They are not: the five `work_mem` values tested (256MB, 4MB, 1MB, 256kB, 64kB) were chosen before running anything, as a simple log-scale sweep, and the batch counts are exactly what `EXPLAIN` reported — no intermediate run was discarded. The one run not used anywhere (see below) was dropped for noise, not for an inconvenient batch count.
- An early run also tried `work_mem = 512kB` (between 1MB and 256kB) to check whether the doubling is really per-halving or jumps in bigger steps: `EXPLAIN` reported `Buckets: 32768  Batches: 32`, exactly between 1MB's 16 and 256kB's 64 — confirming the doubling is a clean per-halving rule at this finer granularity, not just a coincidence of the five widely-spaced settings used in the reel. Execution Time measured 1140.622 ms, consistent with the batched-join range. Not used in examples.py or the reel (the five-point sweep already demonstrates the mechanism and adding a sixth point would clutter the step without changing the conclusion), but recorded here since it directly checks the claim rather than just restating it.
- Currency: PostgreSQL 18 is current stable; the `work_mem`/`hash_mem_multiplier` semantics and the batch-doubling mechanism in `nodeHash.c` are unchanged between 16 (this instance) and 18/REL_18_0 (the fetched source and docs) for everything claimed here — nothing in this topic depends on a behavior that changed between those versions.
