## Into the internals

Topic 2 showed that `NOT IN` can vanish an entire result when its subquery contains a NULL. This topic explains why, from the other direction: what a semi-join and an anti-join actually are, and exactly which SQL spellings the planner can and cannot turn into one.

### A semi-join never multiplies rows; an anti-join only keeps the unmatched

A plain join `R ⋈ S` can return a row of `R` more than once, if several rows of `S` match it — this is ordinary bag semantics (topic 1): join `products` to `order_items` and a popular product reappears once per order line. A **semi-join**, written `R ⋉ S`, answers a different question: "does this row of `R` have *at least one* match in `S`?" — and keeps each qualifying row of `R` exactly once, no matter how many matches it has. An **anti-join**, written `R ▷ S`, is the complement: every row of `R` with *no* match in `S` at all.

- "Which products have ever been ordered?" is a semi-join: `products ⋉ order_items`.
- "Which customers have never placed an order?" is an anti-join: `customers ▷ orders`.

Both questions are naturally about existence, not about the matched row's columns — which is exactly why SQL gives them their own spellings instead of making you write a join and then clean up the duplicates yourself.

### Four SQL spellings, two different safety classes

| Spelling | Reads as | Always safe under NULLs? |
|---|---|---|
| `EXISTS (correlated subquery)` | "does at least one matching row exist" | Yes |
| `col IN (subquery)` | "does `col` equal some row of the subquery" | Yes |
| `NOT EXISTS (correlated subquery)` | "does no matching row exist" | Yes |
| `col NOT IN (subquery)` | "does `col` equal none of the subquery's rows" | **No** — only when the subquery's output and `col` are provably non-null |
| `LEFT JOIN S ON … WHERE S.key IS NULL` | "keep rows of R with no match in S" | Yes, as long as `S.key` is a column that is non-null on every genuinely matched row (its primary key, say) |

`EXISTS` and `NOT EXISTS` test whether a row exists at all — a yes/no fact that doesn't depend on whether any column inside the matching row happens to be NULL. `IN` and `NOT IN` instead build a chain of value comparisons against the subquery's rows, and value comparisons are exactly where three-valued logic (topic 2) enters: a `NULL` among the compared values can turn the whole chain `UNKNOWN`. `LEFT JOIN … IS NULL` sidesteps the issue by testing a specific column for being literally NULL (a real, two-valued test, as long as that column couldn't be NULL on a genuine match) rather than testing an equality chain.

### What the planner is actually allowed to do

PostgreSQL's planner rewrites subqueries into joins in `src/backend/optimizer/plan/subselect.c`, and the two conversion functions make the asymmetry above load-bearing, not stylistic.

`convert_EXISTS_sublink_to_join()` turns `EXISTS`/`NOT EXISTS` into a semi-join or anti-join **unconditionally** — the function has no nullability check at all, because testing "a row exists" is already a plain two-valued fact; there is no three-valued case to protect against.

`convert_ANY_sublink_to_join()` handles `IN`/`NOT IN` (`ANY` is `IN`'s internal name), and its own comment states the asymmetry outright:

> "Per SQL spec, NOT IN is not ordinarily equivalent to an anti-join, so that by default we have to fail when under_not. However, if we can prove that neither the outer query's expressions nor the sub-select's output columns can be NULL, and further that the operator itself cannot return NULL for non-null inputs, then the logic is identical and it's safe to convert NOT IN to an anti-join."

Read literally: a plain `IN` is converted to a semi-join without any such proof (an `UNKNOWN` test is dropped by `WHERE` exactly the same way whether it came from a real semi-join or from the raw three-valued `IN`, so there is nothing to protect). `NOT IN`, though, is only converted to a true anti-join when the planner can *prove* — from an actual `NOT NULL` constraint it already knows about, via `sublink_testexpr_is_not_nullable()` and `query_outputs_are_not_nullable()`, not by sampling the data at runtime — that neither side of the comparison can ever be NULL. This is a **null-aware anti-join rewrite**: the planner is aware that an ordinary anti-join is the *wrong* answer whenever NULLs are possible, so it only takes the fast path once nullability is ruled out by the schema itself.

When that proof fails — the subquery's column has no `NOT NULL` constraint the planner can see, even if the data happens to contain no NULLs today — PostgreSQL does not give up on correctness. It falls back to evaluating the subquery as a `SubPlan` (or a hashed subplan for simple, uncorrelated cases), executed with the real three-valued `NOT IN` semantics from topic 2, including the vanishing-rows behaviour when a NULL is actually present. The query still returns the right answer; it just can't take the cheap anti-join plan shape, and on a large subquery that difference is often the entire performance gap people attribute, incorrectly, to "`NOT IN` being slow" — it isn't slow because it's `NOT IN`; it's slow because the planner correctly refused an unsafe shortcut.

### Reading it in `EXPLAIN`

PostgreSQL's `EXPLAIN` names the join type directly on `Nested Loop`, `Merge Join` and `Hash Join` nodes (`src/backend/commands/explain.c`): `Join Type: Semi` for a semi-join, `Join Type: Anti` for an anti-join (printed as "Hash Semi Join", "Nested Loop Anti Join," and so on in text format). PostgreSQL 18 added a further refinement, **Right Semi Join**, letting the optimizer build the hash table from the probing side of a semi-join rather than always the historically-fixed side ("Allow the optimizer to use Right Semi Join plans… semi-joins are used when needing to find if there is at least one match," PostgreSQL 18 release notes). Seeing `Semi` or `Anti` in a plan is the direct confirmation that the planner found the fast path; seeing a `SubPlan` or `Hashed Subplan` node under a `NOT IN` instead is the signature of the fallback above.

### Worked examples, with the running tables

**Semi-join, done two ways.** "Which products have ever been ordered?"

```sql
-- (a) EXISTS: a semi-join. Each product appears at most once, by construction.
SELECT p.* FROM products p
WHERE EXISTS (SELECT 1 FROM order_items oi WHERE oi.product_id = p.product_id);

-- (b) JOIN + DISTINCT: the same answer, the hard way.
SELECT DISTINCT p.* FROM products p
JOIN order_items oi ON oi.product_id = p.product_id;
```
(b) must join all 300,000,000 `order_items` rows against `products` and then deduplicate (topic 1's "`UNION` pays for a dedup," here paid by a join instead) — (a) never produces the duplicates in the first place.

**Anti-join, safe and unsafe versions of "the same" question.**

```sql
-- Safe: orders.customer_id is NOT NULL, so the planner can prove the rewrite is sound.
SELECT c.* FROM customers c
WHERE c.customer_id NOT IN (SELECT customer_id FROM orders);

-- Also safe, and portable to engines without the planner proof above:
SELECT c.* FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id);

-- Also safe: the classic manual anti-join, testing orders' own primary key for NULL.
SELECT c.* FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
WHERE o.order_id IS NULL;
```

```sql
-- UNSAFE: referred_by_customer_id is nullable, so the planner CANNOT prove
-- the rewrite is sound, and falls back to the real NOT IN semantics —
-- which, per topic 2, returns next to nothing the moment one order has no referrer.
SELECT c.* FROM customers c
WHERE c.customer_id NOT IN (SELECT referred_by_customer_id FROM orders);
```

The first query and the last query have the identical shape — `col NOT IN (SELECT other_col FROM orders)` — and only one of them is safe, because only one of them is backed by a `NOT NULL` constraint the planner can see. That is the entire lesson: the safety of `NOT IN` is a property of the schema, checkable in `EXPLAIN`, not a property of how the query happens to read.

## Build, break, measure

### Try it · Watch the planner choose, and refuse to choose

1. **Confirm the semi-join.** Run `EXPLAIN` on the `EXISTS` and `JOIN + DISTINCT` queries above and confirm the first shows a `Semi` join type with no separate dedup step, while the second shows a plain inner join followed by a `HashAggregate` or `Sort`/`Unique` doing the deduplication topic 1 already named. Compare total cost estimates (*measure in build* for the actual numbers on your data).
2. **Confirm the safe anti-join.** Run `EXPLAIN` on the safe `NOT IN` version above (over `orders.customer_id`, which is `NOT NULL`) and confirm it shows `Join Type: Anti`. Then drop the `NOT NULL` constraint on a scratch copy of `orders.customer_id` and re-run `EXPLAIN` on the exact same query — expect the plan to change to a `SubPlan`/`Hashed Subplan` shape, because the planner can no longer prove the rewrite is safe even though the data is unchanged. This is the single clearest demonstration that the planner's decision is schema-driven, not data-driven.
3. **Confirm the unsafe case, and its correct, slow answer.** Run the `referred_by_customer_id` query and confirm `EXPLAIN` shows no `Anti` join type (a `SubPlan`-shaped plan instead), and that the result is empty or near-empty exactly because `referred_by_customer_id` has NULLs for every organically-acquired customer (topic 2's bug, now caused on purpose). Rewrite it with `NOT EXISTS` and confirm the result becomes the expected, non-empty anti-join.

## In production — a review checklist

- **Default to `EXISTS`/`NOT EXISTS` for existence questions.** They need no `NOT NULL` proof, never produce duplicates, and the planner always has a safe fast path for them.
- **Never trust `NOT IN` on a column without a real `NOT NULL` constraint.** "The data happens not to have NULLs today" is not something the planner can see or rely on; only a declared constraint lets it take the anti-join path, and only a declared constraint protects you when the data changes.
- **`LEFT JOIN … IS NULL` is a legitimate anti-join**, and often the clearest to a reader coming from another SQL dialect — just test a column that is guaranteed non-null on a real match (the joined table's own primary key is the safe default), not an arbitrary column that could itself be NULL.
- **When a query with `NOT IN` is unexpectedly slow, check `EXPLAIN` for the join type before tuning anything else.** A missing `Anti` and a `SubPlan` node in its place means the planner refused the fast path — the fix is usually a schema change (add `NOT NULL`) or a rewrite (`NOT EXISTS`), not an index.
- **Don't `DISTINCT` your way out of a join when a semi-join says what you mean.** If the question is "has at least one match," write `EXISTS`; a join followed by `DISTINCT` does the same job by generating the duplicates first and discarding them after, which is strictly more work.
