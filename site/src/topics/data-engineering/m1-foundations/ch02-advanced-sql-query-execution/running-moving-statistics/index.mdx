## Into the internals

Topic 13 turned a point-in-time stream into episodes. This topic is about the statistics computed *over* a run of numbers once you have them — running totals, moving averages, and the specific aggregates (percentiles, deciles) that need the whole ordered set at once, not just a sum.

### Cumulative vs moving: the same frame-shape choice from topic 11

A **cumulative** aggregate only ever grows: `SUM(amount) OVER (ORDER BY event_time ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)` is "the running total to date," and topic 11 already named exactly why it's cheap — PostgreSQL's cumulative algorithm keeps the previous result and just adds whatever's new. A **moving** (sliding) aggregate has a fixed-width frame that both grows on one end and shrinks on the other as it advances — `ROWS BETWEEN 6 PRECEDING AND CURRENT ROW` ("the last seven rows") — and needs the *removable* cumulative algorithm (or a segment tree, if the bounds move unevenly) to stay cheap, because old rows have to be subtracted out, not just new ones added in. The frame shape you choose here is exactly the input topic 11's execution engine decides its strategy from.

### Calendar time, not row count: `RANGE` with `INTERVAL`

"Last seven rows" and "last seven days" sound similar and are not the same thing the moment order volume isn't perfectly even. `ROWS BETWEEN 6 PRECEDING AND CURRENT ROW` always covers exactly seven *rows* — on a day with triple the normal order volume, that's a much shorter *span of time*; on a quiet day, a much longer one. A genuine calendar window needs `RANGE`, with an interval offset: "the data type of the offset expression varies depending on the data type of the ordering column... but for datetime ordering columns it is an interval. For example, if the ordering column is of type date or timestamp, one could write `RANGE BETWEEN '1 day' PRECEDING AND '10 days' FOLLOWING`" (PostgreSQL 18 docs, §4.2.8, "Window Function Calls"). `RANGE` in this mode "require[s] that the `ORDER BY` clause specify exactly one column," and the offset "specifies the maximum difference between the value of that column in the current row and its value in preceding or following rows of the frame" — measuring by elapsed value, not position:

```sql
SELECT event_time, amount,
  SUM(amount) OVER (
    ORDER BY event_time
    RANGE BETWEEN INTERVAL '7 days' PRECEDING AND CURRENT ROW
  ) AS trailing_7d_revenue
FROM orders;
```

This genuinely covers the trailing seven calendar days of revenue for every row, regardless of how many orders happened to land in that window — a weekend with fewer orders gets a correctly shorter row-count but the exact same seven-day span; `ROWS BETWEEN n PRECEDING AND CURRENT ROW` cannot do this at all, because it has no concept of elapsed time, only position.

### Exact percentiles: `PERCENTILE_CONT` vs `PERCENTILE_DISC`

Both are **ordered-set aggregates** — called with `WITHIN GROUP (ORDER BY ...)` instead of a plain argument, because the whole ordered set, not a running total, is what the computation needs:

- **`percentile_cont(fraction) WITHIN GROUP (ORDER BY ...)`** "computes the continuous percentile, a value corresponding to the specified fraction within the ordered set of aggregated argument values. **This will interpolate between adjacent input items if needed**" (PostgreSQL 18 docs, §9.21). The median of an even-sized dataset, for instance, is the average of the two middle values — a number that may not actually appear in the data at all.
- **`percentile_disc(fraction) WITHIN GROUP (ORDER BY ...)`** "computes the discrete percentile, **the first value within the ordered set** of aggregated argument values whose position in the ordering equals or exceeds the specified fraction" — always a value that genuinely occurred in the data, never an interpolation.

Both also accept an *array* of fractions in one call — `percentile_cont(ARRAY[0.5, 0.9, 0.99]) WITHIN GROUP (ORDER BY amount)` returns the median, p90 and p99 order amounts together, from one pass over the sorted data, instead of three separate aggregate calls each re-sorting independently.

Pick `PERCENTILE_DISC` whenever the answer must be a real, traceable row (a representative order you might want to look up afterward); pick `PERCENTILE_CONT` whenever a smooth statistical estimate is what's actually wanted and an interpolated number is fine.

### `NTILE` and `CUME_DIST`

`ntile(num_buckets)` "returns an integer ranging from 1 to the argument value, dividing the partition as equally as possible" (PostgreSQL 18 docs, §9.22, Table 9.67) — `NTILE(10) OVER (ORDER BY lifetime_spend)` splits customers into ten roughly-equal-sized spend deciles directly, with no manual bucket-boundary math. `cume_dist()` "returns the cumulative distribution, that is (number of partition rows preceding or peers with current row) / (total partition rows)" — "what fraction of all rows rank at or below this one," the window-function cousin of a percentile rank computed the other direction.

### Why exact percentiles motivate an approximate one

Both `PERCENTILE_CONT` and `PERCENTILE_DISC` need the *entire* ordered set in hand before they can answer anything — there is no cumulative shortcut the way there is for `SUM`, because "the p99 of everything so far" genuinely changes depending on every value seen, not just the running tally. At the scale of a 100,000,000-row partition (or a dashboard that recomputes this on every page load), a full sort every time is a real, recurring cost. This is exactly the gap approximate percentile algorithms (t-digest and related sketch structures, covered in full in §5.6) exist to close: trading an exact answer for a single-pass, bounded-memory estimate that's close enough for most monitoring and analytics purposes. The decision to accept that trade is a real engineering choice, not a free upgrade — it belongs in §5.6's full treatment, not assumed here.

## Build, break, measure

### Try it · Watch ROWS lie about elapsed time

1. **Build both trailing-window versions.** Compute a seven-row trailing sum (`ROWS BETWEEN 6 PRECEDING AND CURRENT ROW`) and a seven-day trailing sum (`RANGE BETWEEN INTERVAL '7 days' PRECEDING AND CURRENT ROW`) over `orders`, ordered by `event_time`. On a day with an unusually high or low order count, confirm the two give visibly different answers for "the last week's revenue," and confirm only the `RANGE`/`INTERVAL` version's window actually spans seven real calendar days (check the earliest row inside each window's frame against the current row's timestamp).
2. **Compare continuous and discrete percentiles.** Run `PERCENTILE_CONT(0.5)` and `PERCENTILE_DISC(0.5)` `WITHIN GROUP (ORDER BY amount)` over an even-sized sample of `orders.amount` and confirm `PERCENTILE_CONT`'s result does not necessarily equal any actual row's amount, while `PERCENTILE_DISC`'s result always does (*measure in build* for the actual values).
3. **Build spend deciles.** Compute `NTILE(10) OVER (ORDER BY lifetime_spend)` over a per-customer lifetime-spend aggregate and confirm each decile bucket has (as close to) one-tenth of all customers, with the "as close to" explained by any remainder from a customer count not divisible by ten.

## In production — a review checklist

- **Never use `ROWS BETWEEN n PRECEDING...` as a stand-in for "the last n days/hours."** Use `RANGE BETWEEN INTERVAL '...' PRECEDING...` whenever the requirement is genuinely calendar-based, and reserve `ROWS` for genuinely position-based windows (the last n *records*, regardless of when they happened).
- **State explicitly whether a percentile should be continuous or discrete**, and justify it by whether the downstream consumer needs a traceable real row.
- **Compute multiple percentiles with the array form of `PERCENTILE_CONT`/`PERCENTILE_DISC` in one call**, not with repeated single-fraction aggregate calls that each re-sort independently.
- **Before shipping an exact percentile that recomputes on every dashboard load at real scale, measure its cost against your actual data size and refresh frequency**, and reach for an approximate algorithm (§5.6) once that cost is unacceptable, rather than assuming exactness is always affordable.
