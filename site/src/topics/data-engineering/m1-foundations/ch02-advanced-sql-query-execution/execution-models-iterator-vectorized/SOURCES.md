## DuckDB documentation, "Execution Format" (internals)

URL: https://duckdb.org/docs/2.0/internals/vector.html

> DuckDB uses a vectorized query execution model.

> The default STANDARD_VECTOR_SIZE is 2048 tuples.

## Boncz, Zukowski, Nes, "MonetDB/X100: Hyper-Pipelining Query Execution" (CIDR 2005)

URL: https://cs.brown.edu/courses/cs227/archives/2008/Papers/ColumnStores/MonetDB.pdf

> the common way to implement the popular Volcano [10] iterator model for pipelined processing, leads to tuple-at-a-time execution, which causes both high interpretation overhead, and hides opportunities for CPU parallelism from the compiler.

> X100 uses a default vector size of 1024, but users can override it.

> the optimal vector size seems to be 1000, but all values between 128 and 8K actually work well.

## Neumann, "Efficiently Compiling Efficient Query Plans for Modern Hardware" (VLDB 2011, HyPer)

URL: https://www.vldb.org/pvldb/vol4/p539-neumann.pdf

> The classical iterator style query processing technique is very simple and flexible, but shows poor performance on modern CPUs due to lack of locality and frequent instruction mispredictions.

> Processing is data centric and not operator centric.

> Data is not pulled by operators but pushed towards the operators.

## Leis, Boncz, Kemper, Neumann, "Morsel-Driven Parallelism: A NUMA-Aware Query Evaluation Framework for the Many-Core Age" (SIGMOD 2014)

URL: https://db.in.tum.de/~leis/papers/morsels.pdf

> Morsel-driven query processing takes small fragments of input data (“morsels”) and schedules these to worker threads that run entire operator pipelines until the next pipeline breaker.

> The degree of parallelism is not baked into the plan but can elastically change during query execution, so the dispatcher can react to execution speed of different morsels

## Measured directly

URL: n/a — executed locally, not a web source.

Identical logical data in both engines, generated by the same deterministic, id-based formula (`a = (id % 97) / 10.0`, `b = (id % 13) + 1`, `c = id % 1000`) for 20,000,000 rows, so both engines compute over the same numbers without transferring a file between them. Query: `SELECT c, SUM(a*b), AVG(a), COUNT(*) FROM exec_demo WHERE a > 0.1 GROUP BY c ORDER BY c`.

Correctness check first: both engines agree on the filtered row count (19,587,629) and the filtered sum (671854810.5000007 in PostgreSQL 16.15, 671854810.5000004 in DuckDB 2.0.0 — the last-digit difference is floating-point summation-order rounding, not a logic difference).

- PostgreSQL 16.15, single execution thread (`max_parallel_workers_per_gather = 0`), JIT off (`jit = off`, so no PostgreSQL-side per-query compilation blurs the "plain iterator" baseline): three repeated runs, 4210.137 ms / 3956.844 ms / 3985.218 ms.
- PostgreSQL 16.15, its own default settings on this 4-core machine (parallel workers + JIT both on): three repeated runs, 1438.229 ms / 1730.269 ms / 1519.423 ms.
- DuckDB 2.0.0 (Python client), `PRAGMA threads=1`: three repeated runs, 246.217 ms / 240.726 ms / 264.865 ms.
- DuckDB 2.0.0, `PRAGMA threads=4` (all cores on this machine): three repeated runs, 85.807 ms / 72.693 ms / 73.080 ms.
- DuckDB's own `EXPLAIN` on this query shows a "Perfect Hash Group By" node and reports its intermediate row counts in the thousands at a time (its plan prints counts like "~4,000,000 rows" for a whole pipeline stage, not one row), confirming its operators move arrays of rows, not one row at a time.
- PostgreSQL's own `EXPLAIN (ANALYZE, BUFFERS)` on the same query (single-threaded, JIT off) shows `HashAggregate` with `Batches: 1` fed by a plain `Seq Scan`, each `actual time` line reporting a single cumulative total across all 19,587,629 rows pulled one at a time through the plan — the standard way PostgreSQL's executor reports a Volcano-style pull plan.
