- **Iterator (Volcano) model**: the classic way a query plan runs — every operator exposes a "give me the next row" call, and the top of the plan pulls rows up through it one at a time. *Where you meet it:* PostgreSQL's own executor, measured at 3956.844 ms single-threaded.
- **Vector (batch)**: an array of rows an operator processes together in one call, instead of one row at a time. *Where you meet it:* DuckDB's default vector of 2048 rows, measured at 240.726 ms single-threaded on the same query.
- **Interpretation overhead**: the cost of repeatedly calling a general-purpose operator's code for every single row, instead of running a tight loop or dedicated machine code. *Where you meet it:* the step that explains why 19,587,629 one-row function calls cost more than the same rows looped over in batches.
- **Pipeline breaker**: a point in a plan (like a sort or a hash build) where every input row has to be consumed before any output row can be produced — the place vectors and compiled code fragments both have to materialize their result. *Where you meet it:* the morsel-driven step, where a worker thread runs a whole pipeline up to its next pipeline breaker.
- **Morsel**: a small chunk of input data handed to one worker thread at run time, rather than splitting the work into fixed pieces before the query starts. *Where you meet it:* this topic's own scaling measurement, from 1 thread to 4.
