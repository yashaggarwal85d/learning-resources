# Fact-check, de.execution-models-iterator-vectorized, 2026-10-22

## Claims table

| # | Claim | Source | Verified how |
|---|---|---|---|
| 1 | The Volcano iterator model pulls tuples one at a time through the plan; this causes high interpretation overhead and hides CPU parallelism from the compiler. | MonetDB/X100 paper (Boncz, Zukowski, Nes) | Quoted verbatim in SOURCES.md. | 3 | A batch/vector size has a real sweet spot — too small reintroduces per-tuple overhead, too large no longer fits the CPU cache. | MonetDB/X100 paper's own vector-size experiment | Quoted verbatim (optimal around 1000, 128–8K all work well, degrades once vectors overflow cache). ## Red-team notes
- **Is 16× a fair comparison, or is it "PostgreSQL badly configured vs. DuckDB well configured"?** Checked both directions: with PostgreSQL's *own default* settings (parallel workers on, JIT on — i.e. its best real-world configuration on this 4-core box, not artificially crippled), the query still took 1438.229–1730.269 ms, against DuckDB's default (4 threads) at 72.693–85.807 ms — still roughly 17–24× apart. The iterator-vs-vectorized gap survives both engines' own best single-box configuration; the single-threaded, JIT-off numbers isolate the execution-model difference specifically from the parallelism/JIT differences, which is why both pairs are reported in SOURCES.md rather than only the most dramatic one.
- **Is the workload rigged to favor vectorization?** The query (`a*b` arithmetic, a filter, a `GROUP BY`, three aggregates) is a plain CPU-bound aggregation, not a pathological case — it's structurally similar to the TPC-H-style decision-support queries both the X100 and HyPer papers used to make their own case, not hand-picked to maximize the gap here.
- **Are the two engines actually computing the same thing?** Checked, not assumed: both engines filter to the same row count (19,587,629) and the same sum to the last meaningfully precise digit (671854810.5000007 vs. 671854810.5000004 — floating-point summation-order rounding, not a logic difference). If these hadn't matched, the comparison would be meaningless.
- **Could the "compiled is fastest" claim (step 10–11) be unsupported since nothing compiled was run here?** Flagged honestly: it is the HyPer paper's own reported result, explicitly attributed to the paper in the reel's wording, never phrased as something this topic measured. The paper's own Figure 1 (hand-written C++ roughly matching the compiled engine, both well ahead of a classical iterator on TPC-H Query 1) is the basis, cited as such.
- **Is "PostgreSQL is a pure iterator" an oversimplification, given PostgreSQL has its own JIT?** Yes, partially — PostgreSQL 16 can JIT-compile expressions (not whole operator pipelines) above a cost threshold, which is a form of compilation layered onto an otherwise unchanged Volcano plan. This is named explicitly in post-notes as a real nuance, and the topic's own "iterator baseline" measurement runs with `jit = off` specifically so the number being called "the iterator model's cost" isn't quietly including a different optimization.
