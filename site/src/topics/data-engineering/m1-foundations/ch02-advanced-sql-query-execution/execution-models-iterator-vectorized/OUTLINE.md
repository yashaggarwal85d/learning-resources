# Outline, de.execution-models-iterator-vectorized

Syllabus line: "Volcano tuple-at-a-time pull, vectorized batches (MonetDB/X100, DuckDB, Velox, ClickHouse), data-centric code generation (HyPer/Umbra), push-based pipelines and morsel-driven parallelism; trade-offs in interpretation overhead, compile latency and debuggability."

## Running example
The same SQL query (`SELECT c, SUM(a*b), AVG(a), COUNT(*) FROM exec_demo WHERE a > 0.1 GROUP BY c`) run over the exact same 20,000,000-row logical dataset — generated by an identical deterministic formula in both engines, so they compute over the same numbers without ever copying a file between them — on PostgreSQL (a Volcano-style, tuple-at-a-time executor) and DuckDB (a vectorized engine). Both agree on the answer (same row count, same sum to floating-point rounding). The whole topic is about why the time to get there differs so much.

## Steps

1. **Hook — "The same query, the same answer, two very different costs"**: state the result up front (PostgreSQL single-threaded ≈ 3,957 ms; DuckDB single-threaded ≈ 241 ms — about 16× apart, same table, same SQL, same answer).
2. **Predict: why would the exact same SQL, computing the exact same answer, take 16× longer on one engine than another?** (options: different hardware / a smarter query plan / the same plan, run very differently). Correct: the same plan can be *executed* in fundamentally different ways.
3. **Reveal: the Volcano iterator** — PostgreSQL's executor pulls one row at a time up through the whole operator tree; every operator calls the next one's `next()`-equivalent for every single row.
4. **How the iterator model actually runs** — a function call per operator per row; the X100 paper's own diagnosis (tuple-at-a-time execution causes high interpretation overhead and hides CPU parallelism from the compiler).
5. **Reveal: vectorization** — DuckDB's operators work over a whole array of rows (a "vector") at once; DuckDB's own default is 2048 tuples, X100's is 1024.
6. **How a vectorized operator actually works** — a tight loop over an array instead of a function call per row; the array is sized to fit the CPU cache, which is why it's not "as big as possible."
7. **Predict: is a bigger batch always faster?** (options: yes, always / no, there's a sweet spot / size doesn't matter). Correct: there's a sweet spot.
8. **Reveal: the sweet spot** — X100's own vector-size experiment: tuple-at-a-time (vector size 1) is as slow as a pure interpreter; the optimal size was about 1000 for their workload, with 128–8K all working well, but performance degrades once the vectors no longer fit in cache.
9. **How compiling goes further than vectorizing** — HyPer's data-centric, push-based model: operator boundaries are blurred into one code fragment per pipeline, values stay in CPU registers instead of being materialized into arrays at every step.
10. **Predict: with three models on the table — iterator, vectorized, compiled — which wins on a single core?** (options: the iterator, because it's simplest / vectorized, because it's the modern default / compiled, because it eliminates the most overhead). Correct: compiled, in principle — but it isn't free.
11. **Reveal: the real trade-off is compile latency and debuggability, not raw speed** — HyPer's own figure (hand-written C++ rivaling the compiled engine; both far ahead of the classical iterator) plus the cost side: compiling a query to machine code takes real time before the first row comes out, and a stack trace through generated code is harder to read than one through an interpreter loop.
12. **Morsel-driven parallelism** — instead of fixing how many threads run a query at plan time, split the input into small morsels and hand them to idle worker threads at run time; this topic's own DuckDB measurement scaling from one thread (≈ 241 ms) to four (≈ 73 ms), about 3.3× on 4 cores, is the same kind of scaling the morsel-driven paper reports (over 30× on 32 cores for TPC-H/SSB).
13. **Recap** — five ideas: pull vs. push; one row vs. a cache-sized batch; vectorizing vs. compiling; the batch-size sweet spot; morsels instead of a fixed plan-time thread count.
14. **Prove it · 1 of 2** — given a plan shape (or a reported row count per call), decide whether an engine is pulling tuple-at-a-time or working in batches.
15. **Prove it · 2 of 2** — given a scaling result (e.g. 1 thread → N threads), decide whether it looks morsel-driven (elastic, close to linear) or a fixed static split.

## Claims and sources
1. The Volcano iterator model pulls tuples one at a time and this causes measurable interpretation overhead — MonetDB/X100 paper, quoted in SOURCES.md; measured directly (PostgreSQL single-threaded, JIT off, ≈ 3,957–4,210 ms).
2. Vectorized execution processes a whole array ("vector") of rows per operator call, with DuckDB defaulting to 2048 and X100 to 1024 — DuckDB docs + X100 paper, quoted; measured directly (DuckDB single-threaded, ≈ 241–265 ms — ≈ 16× faster than the iterator baseline on an identical answer).
3. Vector/batch size has a real sweet spot: too small reintroduces interpretation overhead, too large overflows the CPU cache — X100 paper's own vector-size experiment, quoted.
4. Compiling a query to native code (HyPer) goes further than vectorizing by making processing data-centric and push-based, blurring operator boundaries so values stay in registers — HyPer paper, quoted.
5. Morsel-driven parallelism dispatches small chunks of work to idle threads at run time rather than fixing the degree of parallelism in the plan — morsel-driven paper, quoted; measured directly (DuckDB 1 → 4 threads, ≈ 241 ms → ≈ 73 ms, ≈ 3.3× on 4 cores).
6. PostgreSQL's executor is a real-world Volcano-style plan (confirmed on this topic's own `EXPLAIN (ANALYZE, BUFFERS)` output) and DuckDB's is a real-world vectorized one (confirmed on this topic's own `EXPLAIN` output and its "Perfect Hash Group By" plan node and chunk-level row-count reporting) — measured directly, both named explicitly as real production systems rather than illustrations.

## Honest gaps
- No compiled engine (HyPer/Umbra) is installed on this sandbox, so step 11's "compiled is fastest, but costs compile time" claim is sourced from the HyPer paper's own reported figure, not independently measured here. Flagged in FACT-CHECK.md and in the reel's own wording ("HyPer's own measurement," not "we measured").
- DuckDB's own scheduler is not verified against the morsel-driven paper's source code or DuckDB's own source; the measured 1→4 thread scaling is real and DuckDB's documentation and third-party write-ups describe it as the same lineage, but this topic doesn't claim DuckDB's internals are a byte-for-byte implementation of the 2014 paper's dispatcher.
- Velox and ClickHouse are named in the syllabus line as other vectorized engines; neither is installed or measured here — named once as further examples of the same vectorized family, not claimed to behave identically to DuckDB.
