## Red team: predict questions
- **Step 2** ("why would the same command show more in a newer version?"): tried the counter "maybe this sandbox's PostgreSQL 18 install is just non-standard" — ruled out by checking the claim against PostgreSQL 18's own official documentation first, independent of this sandbox's install, before ever running the comparison.
- **Step 6** ("what's worth checking first, regardless of vocabulary?"): the tempting wrong answer is "whatever field has the biggest number," which isn't reliable (a huge but expected row count isn't a problem; a small but 1000x-looped node can dominate wall time). The reveal and recap are explicit that it's the *comparison* (estimate vs. actual, or a node's own cost relative to the whole plan) that matters, not any single raw number.
- **Step 9** ("which field actually tells you it spilled?"): tried the trap "a large shuffle-write number means it spilled" — ruled out directly by this topic's own clean-run measurement, where `shuffleWriteBytes=73464` is nonzero and entirely normal, while `memoryBytesSpilled`/`diskBytesSpilled` are the fields that are actually zero in a healthy run and nonzero only when memory ran out.
