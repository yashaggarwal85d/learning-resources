## Red-team notes
- Considered claiming GEQO "sacrifices plan quality for speed" as a general rule and illustrating it with a worse-cost example. Rejected: this topic's own measurements show GEQO matching the optimum on its query shape, and manufacturing a worse result to fit a tidier narrative would be exactly the kind of guess the project rules forbid. The honest finding (same cost, far less time, with the documented caveat that this isn't guaranteed) is used instead.
- Considered testing geqo_seed variability (different seeds → different plans) to show GEQO's non-determinism directly. Not pursued after the n=16 crash made further heavy exhaustive-adjacent runs on this schema a real risk to the shared instance; the planning-time curve and the documented "won't necessarily find the best" warning already carry the point without needing a second heavy run.
- Volcano/Cascades (the syllabus's "top-down transformation search" lineage) is named in CHAPTER.md's scope but could not be backed by a fetched primary-source quote in this session (the accessible pages found either lacked the text or were inaccessible). No claim about Volcano/Cascades internals appears in the reel; it is left out rather than guessed. Noted in post-notes as further reading with a plain citation, not a factual claim.
- Checked that the `cost_demo` tables' uniform 1:1 id-to-id joins don't make the "bad order" demo misleading: the cost gap comes from *when* the one real filter (`j1.flag`, 50 of 100,000 rows) gets applied relative to the unfiltered joins, which is a genuine, common real-world pattern (a selective filter on one table in a join chain), not an artifact of the toy schema.
- Currency: PostgreSQL 18 is current stable; 19 RC1 was seen (per the docs site's own banner) but not GA, and nothing in the RC changes the cost-constant defaults, collapse-limit semantics, or GEQO threshold documented here.
