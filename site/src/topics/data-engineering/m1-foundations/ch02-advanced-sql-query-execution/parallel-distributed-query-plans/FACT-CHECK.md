# Fact-check, de.parallel-distributed-query-plans, 2026-10-22

## Claims table

| # | Claim | Source | Verified how |
|---|---|---|---|
| 1 | PostgreSQL's partition-wise join lets a join between partitioned tables be performed by joining matching partitions, instead of combining everything into one plan first. | PostgreSQL 18 documentation §19.7 | Quoted verbatim. Measured directly: `EXPLAIN` on the same query under `enable_partitionwise_join = off` shows one `Hash Join` over an `Append` of all 4 order and all 4 customer partitions; under `= on`, it shows an `Append` of 4 independent `Hash Join`s, each over one matching partition pair. Both plans return the identical answer (8,000,000 matched rows). |
| 2 | That plan-shape change has a real, measurable memory consequence: the number of nodes whose memory is bounded by `work_mem` increases with the number of partitions, which can avoid a spill that the combined plan would otherwise need. | PostgreSQL 18 documentation §19.7 (quoted: "the number of nodes whose memory usage is restricted by work_mem ... can increase linearly") | Measured directly: at `work_mem = 16MB`, the combined hash table (2,000,000 rows) spills (`Batches: 4`, temp files written); each of the 4 per-partition hash tables (500,000 rows) doesn't (`Batches: 1`). Three repeated runs each: off (spilling) 4619.117/4621.824/4363.915 ms; on (not spilling) 3684.680/3497.753/3699.608 ms — a consistent, repeated ~20% difference. |
| 3 | With PostgreSQL's own default settings (ample `work_mem`, parallel workers on), the two plans' wall-clock times converge rather than one dominating. | — | Measured directly: off 1387.614/1421.772 ms; on 1556.110/1407.918 ms — no consistent winner. Reported honestly rather than omitted, since it's the more common real-world case (most installations don't run with `work_mem` constrained this tightly) and it changes what the topic can honestly claim: the structural plan-shape difference is always real; the wall-clock win specifically shows up under the memory pressure this topic deliberately created. |

## Red-team notes
- **Why wasn't a local Spark cluster actually run, when Java and `pip install pyspark` were both attempted?** `pip install pyspark` failed to build on this sandbox's Python 3.13 (a `setuptools`/`distutils` incompatibility in the package's own build backend, unrelated to this topic's content). A manual download of the official Spark binary distribution (to run it directly via `bin/pyspark` without needing the pip wheel) was started but was slow enough over this sandbox's network that continuing it stopped being worth the wait — and, more importantly, a single-machine Spark run (even a successful one) could not have honestly demonstrated the actual claim at stake: the cost of moving data *between physical machines*, which is the entire reason the broadcast-vs-shuffle choice exists. A local run would show both strategies finishing in comparable time, for the uninteresting reason that there's no network to cross — which would be worse than not measuring it at all, since it would look like a measurement while actually testing nothing related to the claim. This is reported honestly rather than silently worked around, matching topic 24's treatment of HyPer's compiled-execution claim.
- **Is the "partition-wise join = co-located join one level up" synthesis (step 12) actually the same mechanism, or just a loose analogy?** Checked against PostgreSQL's own stated requirements for partition-wise join (join condition includes every partition key; partition keys share a data type; matching child-partition sets) and against what a shuffle exchange specifically exists to produce (data redistributed so that matching rows land on the same node) — the two are structurally the same condition (rows that must match are already co-located, whether "co-located" means "same partition" or "same node"), so the synthesis is presented as a real structural parallel, not merely a metaphor. The reel's own wording keeps this distinction explicit: it says the two ideas share a structure, not that PostgreSQL's planner and Trino's/Spark's are implemented identically.
- **Did the measured 20% speedup depend on an artificially tight `work_mem`, chosen to manufacture a result?** Yes, deliberately and disclosed: `work_mem = 16MB` was chosen specifically because it's large enough that the per-partition hash tables (27.5 MB each via `hash_mem_multiplier`) fit without spilling, while the single combined hash table (which needs roughly 4× that) doesn't. This is reported as exactly what it is — a demonstration of the mechanism under memory pressure, not a claim that partition-wise join is always ~20% faster — and the topic also reports the converged, no-clear-winner result under default settings for honesty (see claim 3).
- **Does the join actually test the partition-wise mechanism, or could the planner have found this plan shape anyway without the setting?** Checked: `enable_partitionwise_join` defaults to `off` in PostgreSQL, and the `EXPLAIN` plan under that default genuinely shows the single combined `Hash Join` over both `Append`s — the four-way split plan only appears once the setting is explicitly turned on, confirming the setting is what's actually responsible for the plan-shape change being measured.
