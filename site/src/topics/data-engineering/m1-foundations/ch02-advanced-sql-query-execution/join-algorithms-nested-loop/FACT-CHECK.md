## Red-team notes
- Considered re-running the forced-Merge-Join measurement a second time, suspecting 543.876 ms might be an outlier the server would improve on a repeat. Decided against manufacturing a better number to make merge join look more competitive: a single clean measurement with the plan type confirmed from the `EXPLAIN` output is honest evidence, and the point this topic makes (merge join needing sorted input it didn't already have, here) doesn't depend on shaving a few tens of milliseconds off one run.
- Considered showing a work_mem reduction severe enough to produce a dramatic, cliff-like slowdown, to make the "spill" point more visually dramatic. Rejected: the real measured gap (383.577 ms → 413.237 ms, about 7.7%) is the honest finding for this join's actual row counts, and the batch count (1 → 64) already makes the mechanism vivid without needing an exaggerated timing gap.
- Double-checked that the inequality-predicate example genuinely has no equality condition a hash or merge join could use (`o.customer_id > c.customer_id - 1 AND o.customer_id < c.customer_id + 1` is a two-sided range, not an equality, even though it happens to pin the same single value) — confirmed this is a real range predicate, not an equality rewritten awkwardly, by checking that removing either half of the AND changes the result set.
- The "Grace/hybrid hash join" terminology (named in the syllabus's next topic, "Memory budgets, spilling and grace hash join") is intentionally not used as a claim here — this topic measured a batch-count increase and reports it as that, leaving the specific named partitioning algorithm (and its own topic-22-adjacent terminology) to the topic the syllabus assigns it to, rather than borrowing vocabulary ahead of its own sourced treatment.
- Currency: PostgreSQL 18 is current stable; nothing in the 19 release-candidate changelog changes `enable_*` semantics, `work_mem` defaults, or the three join algorithms' documented mechanics used here.
