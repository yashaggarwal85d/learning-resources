## Into the internals

Topic 17's rewrites all applied inside one query level. A CTE (`WITH name AS (...)`) raises a question those rewrites don't answer by themselves: should the CTE's own definition be visible to the optimizer *inside* the rest of the query (so pushdown and index use can reach into it), or should it be computed once, in isolation, and handed up as an opaque, already-finished result?

### The optimization fence, before PostgreSQL 12

"Previously, CTEs were never inlined and were always evaluated before the rest of the query" (PostgreSQL 12 release notes). This made every `WITH` clause an **optimization fence**: no matter how simple the CTE's own `SELECT` was, the planner treated its result as a sealed black box, unable to push a later `WHERE` clause down into it or use an index that the CTE's own definition could otherwise have benefited from. Writing `WITH w AS (SELECT * FROM big_table) SELECT * FROM w WHERE key = 123` on an old PostgreSQL version meant scanning the whole of `big_table` first, materializing it, and only then filtering — even though an index on `key` was sitting right there, unreachable through the fence.

### PostgreSQL 12+: inlined by default, with one exception

"CTEs are automatically inlined if they have no side-effects, are not recursive, and are referenced only once in the query. Inlining can be prevented by specifying `MATERIALIZED`, or forced for multiply-referenced CTEs by specifying `NOT MATERIALIZED`" (same release notes). PostgreSQL's own documentation states the general rule and both override keywords precisely: "if a `WITH` query is non-recursive and side-effect-free (that is, it is a `SELECT` containing no volatile functions) then it can be folded into the parent query, allowing joint optimization of the two query levels. By default, this happens if the parent query references the `WITH` query just once, but not if it references the `WITH` query more than once" (PostgreSQL 18 docs, §7.8.3, "Common Table Expression Materialization").

The documentation's own two worked examples make the trade-off concrete:

```sql
-- Referenced once: inlined by default. Folds to the same plan as
-- SELECT * FROM big_table WHERE key = 123 — an index on key gets used.
WITH w AS (SELECT * FROM big_table)
SELECT * FROM w WHERE key = 123;

-- Referenced twice: materialized by default. The CTE becomes a
-- temporary copy of big_table joined to itself, with NO index use at all.
WITH w AS (SELECT * FROM big_table)
SELECT * FROM w AS w1 JOIN w AS w2 ON w1.key = w2.ref WHERE w2.key = 123;
```

In the second query, forcing inlining recovers the lost pushdown: "`WITH w AS NOT MATERIALIZED (SELECT * FROM big_table) SELECT * FROM w AS w1 JOIN w AS w2 ON w1.key = w2.ref WHERE w2.key = 123` ... so that the parent query's restrictions can be applied directly to scans of `big_table`" — at the cost of scanning `big_table` twice (once per reference) instead of once. The documentation is explicit this is a genuine trade-off, not a strict improvement: "the latter choice risks duplicate computation of the WITH query, but it can still give a net savings if each usage of the WITH query needs only a small part of the WITH query's full output."

The opposite override matters just as much. "`WITH w AS (SELECT key, very_expensive_function(val) AS f FROM some_table) SELECT * FROM w AS w1 JOIN w AS w2 ON w1.f = w2.f` ... materialization of the WITH query ensures that `very_expensive_function` is evaluated only once per table row, not twice." Here `w` is referenced twice, so it already materializes by default — but if a future edit added a reason to prefer `NOT MATERIALIZED` elsewhere in the same query, writing `MATERIALIZED` explicitly protects this specific guarantee from quietly disappearing.

### Engines that always re-execute, no fence at all

PostgreSQL's `MATERIALIZED`/`NOT MATERIALIZED` choice assumes a database that *can* materialize a CTE's result. Not every engine offers that option in either direction. SQL Server's documentation states its own behavior flatly: "query results from common table expressions aren't materialized. Each outer reference to the named result set requires the defined query to be re-executed. For queries that require multiple references to the named result set, consider using a temporary object instead" (Microsoft Learn, "WITH common_table_expression"). A SQL Server CTE referencing `very_expensive_function` twice will call it twice, full stop — there is no `MATERIALIZED` keyword to reach for, and the documented workaround is exactly what PostgreSQL's materialization does automatically: compute the result once into a real temporary object, and reference *that* instead of the CTE.

### When a fence is what you want

A fence (materialization) is worth asking for on purpose when: the CTE is referenced more than once and recomputing it would duplicate real, expensive work (the `very_expensive_function` case); the CTE wraps a function with side effects, where "evaluated only once" is a correctness requirement, not just a performance preference (topic 8's volatility framing applies directly — a volatile function inside a CTE is exactly the kind of thing a fence protects); or the query's structure is clearer with a deliberately isolated, named intermediate step, even at some performance cost. Removing the fence (inlining, the default for single-reference CTEs, or forced with `NOT MATERIALIZED`) is worth it whenever the optimizer reaching into the CTE's own definition — to push a filter down, to use an index, to fold it into a larger join order search (topic 20) — saves more than any duplicated work costs.

## Build, break, measure

### Try it · Reproduce both documented examples exactly

1. **Confirm single-reference inlining.** Build the `big_table`/single-reference example over a scratch table with an index on `key`, run `EXPLAIN`, and confirm the plan is identical to querying `big_table` directly with the filter — specifically, confirm the index on `key` is actually used.
2. **Confirm multi-reference materialization, and the `NOT MATERIALIZED` fix.** Build the self-join example, run `EXPLAIN` by default and confirm no index use (a full materialized copy feeding both sides of the join); add `NOT MATERIALIZED` and confirm the index on `key`/`ref` is now used, at the cost of two separate scans of the base table instead of one shared materialization (*measure in build* for which one actually wins on your data size — the documentation is explicit this is a genuine trade-off, not a universal win).
3. **Confirm `MATERIALIZED` guarantees single evaluation.** Wrap a function with an observable side effect (e.g., one that appends to a log table, or simply counts its own calls into a sequence) in a CTE referenced twice; confirm the default (materialized, since it's multiply-referenced) calls it once per base row, and that adding `NOT MATERIALIZED` makes it call twice per base row instead — a visible, countable difference, not just a plan-shape one.

<section data-section="production">

## In production — a review checklist

- **Don't assume a CTE behaves like a view or an opaque subquery by habit — check which regime applies on your engine and your PostgreSQL version.** The default changed in PostgreSQL 12; code written for, or copied from, an older version may be relying on fencing behavior that no longer holds.
- **State `MATERIALIZED`/`NOT MATERIALIZED` explicitly wherever the choice actually matters**, rather than relying on PostgreSQL's reference-count-based default — a later edit that changes the reference count can silently flip the default's behavior.
- **Treat a volatile or expensive function inside a multiply-referenced CTE as a correctness question, not just a performance one, and verify single-evaluation with a real test**, not just an inspection of the plan.
- **On engines with no materialization option (SQL Server and similar), use an explicit temporary table or indexed temp object whenever a CTE needs to be computed once and referenced many times.**
