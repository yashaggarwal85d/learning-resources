## After this topic you can

- Choose correctly among `ROW_NUMBER`, `RANK` and `DENSE_RANK` for a given tie-handling requirement, and predict each one's output on tied input.
- Add a tie-breaker to `ORDER BY` so a ranking's output is reproducible run to run, not just "probably the same."
- Write `QUALIFY` where it's available, and know what to use instead where it isn't.
- Compare the `QUALIFY`/ranking-function top-N-per-group pattern against topic 6's `LATERAL`+`LIMIT` pattern, and pick between them.

## Into the internals

Topic 11 explained how a window function computes efficiently. This topic is about the specific family built directly on top of that machinery: assigning a position to each row within its partition, and using that position to pick exactly the rows you want.

### `ROW_NUMBER`, `RANK`, `DENSE_RANK`: three different answers to ties

All three number rows within a partition in `ORDER BY` order, and they only disagree about what happens when rows tie:

- **`row_number()`** "returns the number of the current row within its partition, counting from 1" — every row gets a distinct number, tie or no tie (PostgreSQL 18 docs, §9.22, Table 9.67).
- **`rank()`** "returns the rank of the current row, **with gaps**; that is, the `row_number` of the first row in its peer group" — tied rows share the same rank, and the next distinct value jumps ahead by however many rows tied (three rows tied for rank 1 means the next rank is 4).
- **`dense_rank()`** "returns the rank of the current row, **without gaps**; this function effectively counts peer groups" — tied rows share a rank too, but the next distinct value is always exactly one more, regardless of how many rows tied.

Three customers tied for the most orders this month: `row_number()` arbitrarily picks one of them to be "1" and the others "2" and "3"; `rank()` calls all three "1" and the next customer "4"; `dense_rank()` calls all three "1" and the next customer "2". None of the three is "the correct one" in the abstract — the question "which one did you actually mean" is answered by what the number is used for afterward (a single top-N cutoff wants `row_number` or a deliberate tie policy; a leaderboard display usually wants `rank`; "how many distinct performance tiers are there" wants `dense_rank`).

### Reproducible output needs a reproducible order

`row_number()`'s choice among tied rows is not specified by the standard or guaranteed by any engine — "without `ORDER BY`, rows are processed in an unspecified order" generalizes directly: an `ORDER BY` that doesn't fully distinguish every row leaves the tied portion's `row_number()` assignment up to whatever order the rows happened to arrive from the scan beneath it, which can differ between runs, after a reindex, or after a minor planner change. The fix costs nothing: add a column that is guaranteed unique (a primary key) as the final `ORDER BY` key, purely to break ties deterministically — `ORDER BY event_time, order_id`, as topic 10's running-total fix already modeled. Two runs of the exact same query, same data, now produce the exact same row-to-number assignment every time, which matters the moment that assignment feeds a `LIMIT`, a dedup, or anything a test suite asserts against.

### `QUALIFY`: filtering on a window function without a subquery

Filtering on a window function's result the obvious way doesn't work — `WHERE row_number() OVER (...) <= 3` is rejected, because `WHERE` runs before window functions are computed, the same reason `HAVING`, not `WHERE`, filters on an aggregate. The textbook fix is to compute the ranking in a subquery or CTE and filter in the level above (exactly topic 10's "nested windows" staging pattern). Several analytical engines offer a shorter spelling instead: **`QUALIFY`**, which "does with window functions what `HAVING` does with aggregate functions and `GROUP BY` clauses" (Snowflake SQL reference, "QUALIFY"), evaluated in a fixed position after window functions and before `DISTINCT`/`ORDER BY`/`LIMIT`:

```
FROM → WHERE → GROUP BY/aggregation → HAVING → WINDOW → QUALIFY → DISTINCT → ORDER BY → LIMIT
```

(Both Snowflake's and BigQuery's own documentation state this exact evaluation order.) The idiomatic top-N-per-group query becomes one line shorter:

```sql
SELECT customer_id, order_id, amount
FROM orders
QUALIFY ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY event_time DESC, order_id) <= 3;
```

`QUALIFY` is supported by Snowflake, Google BigQuery, DuckDB and Databricks SQL — all four confirmed directly in their own current syntax references — but it is **not part of the ISO/ANSI SQL standard**; PostgreSQL does not have it, and the two-level CTE/subquery form from topic 10 remains the portable way to write the same filter anywhere `QUALIFY` isn't available.

### Deterministic dedup: keep one row per key

Deduplicating is the same pattern with a cutoff of one. "Keep the latest record per customer" is `ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY updated_at DESC, record_id DESC) = 1`, filtered with `QUALIFY` or a CTE. Two details make it safe to rerun: the tie-breaker (`record_id`) so that two records with the same `updated_at` always resolve the same way, and using `ROW_NUMBER` rather than `RANK`, because `RANK` would return several rows for a tied first place and the "dedup" would keep duplicates. A job that dedups with an incomplete `ORDER BY` can pass its tests and still flip which record survives between runs.

### Two physical shapes for the same top-N-per-group question

Topic 6 already showed one way to get "this group's top N": `LATERAL` with its own `ORDER BY`/`LIMIT`, re-run once per outer row. The ranking-function-plus-filter pattern here is a second, different way to express the identical question, and the two aren't just two spellings of one plan:

- The **`LATERAL`** version re-sorts (or re-seeks, with the right index) each group's own rows independently, once per group.
- The **ranking-function** version sorts the *entire* input once (partitioned, per topic 11's partition-and-sort cost), assigns a number to every row, and only then throws away the rows that didn't make the cutoff.

Neither is universally faster: `LATERAL` wins when an index on `(partition_key, order_key)` turns each group's per-row `ORDER BY ... LIMIT` into a cheap, bounded index scan (topic 6's point exactly); the ranking-function version wins when no such index exists, or when the same single sorted pass is already needed for other window functions in the same query (topic 11's sort-reuse argument) — in which case the ranking column is nearly free to add, while a `LATERAL` subquery would be an entirely separate per-group pass.

## Build, break, measure

### Try it · Three rankings, one tie, and two top-N plans

1. **See the three functions diverge on a real tie.** Build a small set of orders for one customer with two orders tied on `amount` (or construct a parallel ranking by `amount DESC`), and compute `row_number()`, `rank()` and `dense_rank()` side by side over the same `PARTITION BY customer_id ORDER BY amount DESC`. Confirm the three produce different numbers for the tied rows and for the row right after them, matching the "with gaps"/"without gaps" definitions exactly.
2. **Prove non-determinism, then fix it.** Run the same `row_number()` query twice with an `ORDER BY` that doesn't fully break ties (just `amount DESC`), and show the tied rows' assigned numbers aren't guaranteed to stay in the same order (this may require forcing a different scan order, such as via a fresh `VACUUM`/reindex, since a single run on unchanged data often happens to repeat — *measure in build* for whether your setup reproduces it directly). Add `order_id` as a tie-breaker and confirm the assignment is now stable under re-ordering of the underlying scan (e.g., via a `pg_hint`-free re-run after inserting and deleting unrelated rows).
3. **Compare the two top-N plans.** If targeting an engine with `QUALIFY` (DuckDB is the easiest local option), write the top-three-orders-per-customer query both with `QUALIFY` and with topic 6's `LATERAL`+`LIMIT`, and compare `EXPLAIN` plans and timing with and without an index on `(customer_id, event_time)` (*measure in build* for the actual numbers, but expect the index to matter far more to the `LATERAL` plan than to the ranking-function plan).

<section data-section="production">

## In production — a review checklist

- **State explicitly which of `ROW_NUMBER`/`RANK`/`DENSE_RANK` you mean, and why,** rather than defaulting to whichever one happens to compile — the three disagree exactly on ties, which is precisely the case most likely to show up unexpectedly in production data.
- **Always add a unique tie-breaking column to a ranking's `ORDER BY`** when the ranking feeds a `LIMIT`, a dedup, or anything compared across runs; an incomplete `ORDER BY` makes the output non-deterministic by specification, not by bad luck.
- **Use `QUALIFY` where it's available for a visibly shorter top-N query, but don't forget it isn't portable** — keep the CTE/subquery form in mind for PostgreSQL or any engine without it.
- **Pick between a ranking-function top-N and a `LATERAL`+`LIMIT` top-N based on whether a usable index exists and whether the sort is already shared with other window functions**, not by habit.
