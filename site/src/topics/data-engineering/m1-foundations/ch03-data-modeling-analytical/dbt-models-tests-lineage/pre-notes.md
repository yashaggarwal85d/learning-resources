- **Model**: a dbt model file, which is just one select statement — dbt wraps it in the DDL or DML a configured warehouse needs. *Where you meet it:* the lab's own `stg_orders`, `stg_customers`, `stg_products`, `fct_orders`, and `mart_revenue_by_region` models, each one file, each one select statement.
- **`ref()`**: the function that declares a dependency between two models, in place of writing a literal table name. *Where you meet it:* the lab's own `fct_orders.sql`, which joins three staging models entirely through `ref()` calls.
- **DAG**: the dependency graph dbt builds from every `ref()` call, used to compute build order. *Where you meet it:* read directly from the real project's own `target/manifest.json` after a real build, not drawn by hand.
- **Macro**: reusable Jinja code, defined once and called from inside a model's own SQL. *Where you meet it:* the lab's own `cents_to_dollars()` macro, called once from `stg_orders.sql`.
- **Data test**: a select query that returns failing rows, checked by `dbt test` or `dbt build`. *Where you meet it:* a deliberately introduced dangling `customer_id`, caught by a built-in `relationships` test, actually blocking every model downstream of it.
- **Unit test**: a dbt-native test that validates modeling logic against small, fixed, fabricated inputs, without touching any real data. *Where you meet it:* the lab's own unit test on `stg_orders`, run in isolation with `dbt test --select test_type:unit`.
