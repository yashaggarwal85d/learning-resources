# Expert list: asymptotic notation and logarithms (5-minute refresher)

Syllabus line: "O/Θ/Ω and how costs grow with input size; logarithms in any base and the change of base; why a large base makes the logarithm tiny (B-tree height, external-sort passes); full treatment -> Data Structures & Algorithms Ch.1".

Every source below was fetched with `scripts/sources.mjs fetch` and read (text in /tmp/expert-<n>.txt) before being cited. Quotes are verbatim from the fetched text. | 9 | Base irrelevant in O, relevant in counts. | 10 | B-tree height is about log of the fan-out: with at most m children per node, a full tree of height h holds m^(h+1) - 1 entries, so minimum height is ceil(log_m(n+1)) - 1; real indexes with millions of rows are 4-5 levels deep, "hardly ever" 6. Height is also a worst/best-case range, not one number (nodes are partially filled). | [P] Use The Index, Luke: "Real world indexes with millions of records have a tree depth of four or five. | 11 | External merge sort pass count is a ceiling of a logarithm: after the run-forming pass, you need ceil(log_k(runs)) merge passes for k-way merge. Each pass reads and writes the whole file, so total I/O is about 2N/B x (1 + passes). | [S] Wikipedia, External sorting: "This is because each merge pass reads and writes every value from and to disk, so reducing the number of passes more than compensates for the additional cost of a k-way merge." and the worked case of 50 GB with 100 MB RAM using "two merge passes". https://en.wikipedia.org/wiki/External_sorting (expert-6). | 12 | Fan-out is bounded by memory: a k-way merge needs k input buffers plus an output buffer, so a larger k means smaller reads and eventually seek-dominated I/O. The optimal base is capped by RAM and the block size, not free. | [S] Wikipedia, External sorting: "as the number of chunks increases, memory will be divided into more buffers, so each buffer is smaller. Eventually, the reads become so small that more time is spent on disk seeks than data transfer." Same URL (expert-6) | later: external merge sort; memory hierarchy |
| 13 | Comparison sorting needs Ω(n log n) comparisons because there are n! orderings and each comparison yields one bit: log2(n!) <= number of comparisons, and log2(n!) ~ n log2 n - n / ln 2. | 14 | Best, worst, average and amortized are separate axes from O/Θ/Ω. Each case has its own function that can be bounded above or below. [S] Wikipedia, Amortized analysis: "looking at the worst-case run time can be too pessimistic. | 15 | The cost model decides what you count.
