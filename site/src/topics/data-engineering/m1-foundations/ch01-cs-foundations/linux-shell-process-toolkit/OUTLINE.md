## Learning outcomes ("After this refresher you can")

1. Predict what a pipeline with redirections writes where (`>`, `>>`, `2>&1` and its order trap, `|`), and make a script fail loudly with `set -euo pipefail` instead of exiting 0 after a failed middle step.

### Step 5 · "Exit codes: 0 to 255, and 128 plus the signal"

- **The idea:** Git's step 6 drew the bands bisect reads; this step shows where they come from. One number line 0–255: the program's own codes; the shell's 126 and 127 (and *why* 126: the x bit); and above 128, not a code the program chose but 128 + the number of the signal that killed it. ### Step 6 · "TERM asks; KILL doesn't"

- **The idea:** the same job, two bolts. SIGTERM lands on a box that *catches* it: the box writes its last lines ("flushed and closed") and returns a crema `0`. SIGKILL can't be caught: the box vanishes mid-write and the parent gets a cherry `137`. Then the two things left behind when parents and children die out of order: a zombie (finished, not yet waited for: a dashed box with `Z`) and an orphan (its parent gone, adopted by init).
- **Portrait (`Svg h≈340`):**
  - Two columns. Left (x 30–280): `bash` box at the top (y≈50), child `load_orders.py` at y≈160; a caramel bolt labelled `TERM 15` (13) strikes the child; a small speech line under the child "flushed and closed" (latte 13); token `0` rides up.
  - Right (x 320–570): the same tree; bolt `KILL 9`; the child box's outline breaks (the box fades to 30 % with a cherry crack line); cherry token `137` rides up.
  - Bottom row (y≈300): two small boxes side by side, 60 units apart: a dashed box `Z` with the label "zombie: ended, not yet waited for" (taupe 13, below), and a box whose parent line is cut and re-attached to a tiny `init` box above it, label "orphan: adopted by init". (Labels on separate lines; if the bottom row crowds on a phone, drop the orphan drawing and keep the word in the caption.)
  - Landscape: same.
- **Beats:** 0.2 both trees; 0.8 TERM bolt; 1.2 "flushed and closed"; 1.6 token 0 rides; 2.2 KILL bolt; 2.5 crack; 2.8 token 137 rides; 3.4 zombie box; 3.8 orphan re-attach.
- **Values:** 15, 9, 0, 137; `Z`. Executed: a Python job with a SIGTERM handler prints "flushed and closed" and exits 0 when sent TERM; the same job sent KILL gives 137 (as Bash reports it; Python's `subprocess` reports the same death as `-9`); a finished-but-unwaited child shows `State: Z (zombie)` in `/proc/<pid>/status` and `<defunct>` in `ps -o args` (the `comm` column shows only the name); an orphan's `PPid` changes from its parent's PID once the parent exits (asserted as "changed", printed, not shown as a number: in a container the adopter may be a subreaper, not PID 1).
- **Final frame:** both trees with their tokens and the two bottom boxes.
- **Caption:** "A signal is a one-number message. SIGTERM (15) is the polite stop: a program can catch it, flush and close. SIGKILL (9) can't be caught, blocked or ignored: the kernel ends the process where it stands, so whatever it still held in its own buffers is lost. SIGINT (2) is Ctrl-C; SIGHUP (1) is 'your terminal went away', which is how an ssh job dies with the session. A child that has ended but not been waited for is a zombie; a child whose parent died is adopted by init (or a subreaper). So: TERM first, wait, then KILL."
- **Duration:** 4.2.

- **Question frame, portrait (`Svg h≈320`):**

  - Landscape: identical.
- **Predict:** "The nightly load has sat for an hour, not finished, not failed. `ps` says `S`, `strace -p` shows `read(4,` and nothing more. What is it doing?"
  - Options: "Spinning in a loop" · **"Waiting in read() on fd 4, a socket nobody writes to"** (correct) · "Waiting for the disk" · "It's a zombie".
  - Explain: "Waiting in `read()` on fd 4, a socket. `S` is an interruptible sleep: it will wake the moment data arrives, or a signal. ## Deep dive (`index.mdx`)

Sections in the Python essentials pattern (`data-section` names), plus a frontier section:

- **outcomes — "After this refresher you can"**: the five outcomes above.
- **internals — "A little deeper"**
  - **### Files, inodes and permissions**: a path is resolved component by component; a file is an inode, and a name is a link to it: `ln a b` gives two names with the same inode number and a link count of 2, `ln -s` makes a separate small file that holds a path (executed: same inode, count 2; the symlink's own inode differs and `stat -L` follows it). The nine bits `rwx` for user, group and other; on a directory the third bit is *search*: without it a lookup fails with EACCES (`Permission denied`) even when the file itself is readable, while the read bit alone still lists the names (executed under a non-root user: `setpriv --reuid=65534` when the runner is root, native otherwise; printed as `skipped` if neither is possible: with the directory at `744`, `ls d` prints `file` and exits 0 but `cat d/file` gets `Permission denied`; at `711` it is the other way round). `chmod 644 clean.py` leaves `rw-r--r--`, and running it gives 126 (step 5), **even as root**: root's override "grants execute permission only when at least one of the file's three execute permission bits is set" (`path_resolution(7)`; executed as root → 126). `umask` turns bits *off* from the mode a program asks for: `0666 & ~022 = 0644`; `umask 077` gives a new file `600` (executed); a child inherits it across fork and exec; a default ACL on the parent directory overrides it (`umask(2)`). setuid, by name only: the first octal digit's 4 bit; on exec the effective user ID becomes the file's owner's (no example program is named: no fetched source says which programs are setuid); `chmod` clears the set-group-ID bit of a file whose group isn't one of yours unless you are privileged; a data job never needs it. `/proc/<pid>/status` shows a process's `Umask`.
  - **### Pipes, redirection and the pipeline's status**: fd 0, 1, 2 and `/proc/<pid>/fd` as the live table (one symlink per open file; pipes and sockets show as `type:[inode]`, executed). `>` truncates, `>>` appends, `2>` redirects errors, `2>&1` copies 1's current target into 2, **left to right** (the Bash manual's own `ls 2>&1 > dirlist` example; executed both orders: 0 vs 1 lines in the file). `|` connects 1 to 0 through a kernel pipe. The pipeline's status is the last command's unless `pipefail`, which makes it the rightmost non-zero; `PIPESTATUS` holds all of them (executed `2 0 0`). `set -e` exits on a failing pipeline, but not for "any command in a pipeline but the last (subject to the state of the pipefail shell option)", nor inside an `if` test, a `while`/`until` condition, all but the last command of an `&&`/`||` list, or after `!` (Bash manual; so `-e` without `pipefail` still misses the `jq` failure in step 4: executed). `-u` makes an unset variable an error and a non-interactive shell exits (the manual gives no number; executed on 5.2.21: exit **1** from a script file, but **127** under `bash -c '…'`, so `examples.sh` tests it from a file). **The `pipefail` trap the other way:** `yes | head -1` or `seq 1 100000 | head -1` exits **141** under `pipefail` (the writer dies of SIGPIPE, 128 + 13, after `head` stops reading; executed), so a script with `set -o pipefail` can fail on a pipeline that did exactly what it should. POSIX.1-2024 standardised `pipefail`, so `sh` scripts may use it on a current shell; older `dash` may not (executed: dash 0.5.12, the sandbox's, says `Illegal option -o pipefail`): say which shell the shebang names. Patterns: `cmd 2>&1 | tee log`, `cmd > /dev/null 2>&1` (order again), `exec > >(logger)` as a pointer only.
  - **### The process model: fork, exec, wait and the exit status**: `fork()` duplicates the caller: the child is a copy in its own memory, inherits copies of the open file descriptors (same open file descriptions, so a redirected fd set before `exec` survives it), gets `0` back while the parent gets the child's PID (executed with `os.fork`); `execve()` replaces the program in the same process, new stack, heap and data, same PID ("there is no new process", `execve(2)`; executed: `exec` keeps `$$`), same fds except those marked close-on-exec (`execve(2)`; Python opens its own files close-on-exec, so it is 0, 1, 2 and explicit redirections that carry over), which is why a shell's `exec cmd` replaces the shell; the parent's `wait()` collects the status: `WEXITSTATUS` is the low 8 bits of what the child passed to `exit` (executed: `exit 300` reads as 44; `exit(-1)` as 255), `WIFSIGNALED` / `WTERMSIG` say it was killed and by which signal (executed: 9 for a killed child), and the shell turns that into 128 + n (137). 126 and 127 are the shell's: found but not executable (no x bit, or a directory), and not found (a missing interpreter in the `#!` line also gives 127 in Bash 5.2: "cannot execute: required file not found", executed). POSIX requires only that a signal death be reported as "greater than 128" and allows values above 255; 128 + n is Bash's rule. Why bisect reserved 125 and re-checks a first-run 126/127: it reads these bands (Git refresher, step 6 and its Deep dive "Bisect"). `PPid` in `/proc/<pid>/status` names the parent that forked you; `$$` and `$!`; `exec` in scripts; `nohup` runs a command "ignoring hangup signals" (`nohup(1)`); `setsid` runs it "in a new session" (`setsid(1)` itself does not mention SIGHUP, so the page says only that).
  - **### Signals, zombies, orphans and threads**: a signal's default action (Term, Ign, Core, Stop, Cont); the four to know: SIGHUP 1 (terminal or session leader gone), SIGINT 2 (Ctrl-C), SIGTERM 15 (the polite stop, catchable), SIGKILL 9 (cannot be caught, blocked or ignored; the kernel ends the process, buffers unflushed); numbers from `kill -l` (executed; the x86/ARM numbers quoted from `signal(7)`'s table). A handler in Python (`signal.signal(SIGTERM, …)`: flush, close, exit 0, executed) and in a shell script (`trap`). `kill -TERM` then `kill -KILL`, and why a D-state process ("uninterruptible sleep") usually can't act on either until the I/O returns: the signal stays pending (reasoning from the state's name; not reproduced). SIGSTOP/SIGCONT and `T`. Zombies: a child that terminated but was not waited for keeps its PID and status (`Z`, `<defunct>` in `ps -o args`, executed; it has no open files left: `/proc/<pid>/fd` is empty, executed); the fix is in the parent (wait, or `SIGCHLD` set to `SIG_IGN`, after which children "do not become zombies", `wait(2)`), and `kill -9` on a zombie does nothing (it is already dead; note as reasoning from `wait(2)`, not a quoted claim). Orphans: when a parent exits, "any children of the process are inherited by init(1) (or by the nearest "subreaper" process…)" (`_exit(2)`), which waits for them (executed: `PPid` changes; in the sandbox to 1). **Threads, one paragraph:** a process can run several threads that share its memory and open files; `Threads:` in `/proc/<pid>/status` counts them, `Tgid` is the process ID they share, `ps -L` shows LWP and NLWP (executed: a Python job with a worker thread shows `Threads: 2`). What they cost and how they share safely is topic 8 (`threads-context-switches-synchronization`); topic 7 needs only this.
  - **### Looking at processes: ps, top, htop and load average**: the states: `R` running or runnable, `S` interruptible sleep (waiting for an event), `D` uninterruptible sleep (usually I/O), `Z` zombie, `T` stopped, `I` idle kernel thread (`ps(1)`), plus the extra characters `l` multi-threaded, `s` session leader, `+` foreground (why the hung job shows `Sl`); which columns matter for a data job: `pid,ppid,stat,wchan,etime,rss,pcpu,comm` (executed: a `ps -eo` line for the hung job; the field descriptions are quoted from `ps(1)`), `ps -L` for threads, `ps --forest` for the tree. `top -bn1` for a snapshot (executed: header printed, numbers not asserted); the load average is three numbers over 1, 5 and 15 minutes from `/proc/loadavg`, counting jobs in the run queue (`R`) *or* waiting for disk I/O (`D`) (`proc_loadavg(5)`, now quoted), so a high load with idle CPUs points to D-state waits. `htop` is the interactive version (not installed in the sandbox: named, not executed; no claim about its display beyond "shows threads"). Container caveat: `/proc` shows the container's PID namespace.
  - **### One-liners over order_events**: JSON lines means one object per line (`jq -c` prints that shape; `-r` prints strings raw; `-s` slurps the whole input into one array, which is the one thing *not* to do on 1 TiB: the Python refresher's generators-vs-lists rule in shell form). `jq -r .status`, `jq 'select(.status == "refunded")'`, `jq -s 'group_by(.status) | map({status: .[0].status, n: length})'` (executed: 7 groups on the raw file, 4 after cleaning); `jq`'s exit codes: 2 for a usage problem or system error such as a missing file, 3 for a compile error (the manual), and 5 for an input parse error or an uncaught runtime error (executed on 1.7; not in the manual, whose 5 is only `halt_error`'s default, but set in jq 1.8.2's `src/main.c`). awk: records and fields, `$1`, `$NF`, `NF`, `-F`, patterns and actions, associative arrays (`n[$1]++` then `END { for (k in n) … }`), `tolower`, `$1 = $1` to rebuild the record from its fields and `OFS` (gawk manual), which trims *and* squeezes inner runs of blanks to one space, so it equals Python's `strip()` only when a value has no inner double spaces (true here; `tolower` is also ASCII-only in mawk where `str.lower()` is Unicode) (executed: the awk-only counter gives the same four lines as `uniq -c`). sed: `-n` and `p`, `s/regexp/replacement/flags`, `-i` with care; `sed` on a log line, not on JSON. grep: `-E`, `-c`, `-o`, `-F` for literal strings, `-r`; the trap that regular expressions count strings, not values: `grep -Ec '"status": *"(refunded|cancelled)"'` gives 1,495, not 1,500, because 5 events say `" refunded"` (executed). `sort | uniq -c`, `sort -k2`, `LC_ALL=C sort` for byte order (what `clean.py` sorts by, so `diff` can be empty), `cut`, `tr`, `wc -l`, `head`/`tail`, `xargs -P` (pointer), `tee`. All awk constructs are POSIX, so the runner's mawk and the manual's gawk agree.
  - **### cron**: the five fields with their ranges (minute 0–59, hour 0–23, day of month 1–31, month 1–12, day of week 0–7 with 0 and 7 Sunday), lists, ranges and steps, `@daily` and friends; cron checks entries once a minute and runs the command when minute, hour and month match and *either* day field matches (both restricted: either one, executed by the parser against `crontab(5)`'s rule); the minimal environment (SHELL `/usr/bin/sh` on Debian's cron, LOGNAME, HOME from passwd; set `PATH` in the crontab or use absolute paths, but a crontab value "is not parsed for environmental substitutions", so `PATH=$HOME/bin:$PATH` does not work; `%` in the command is a newline unless escaped); redirect both streams or mail; one timezone for the daemon, no per-user timezone (a `TZ=` line in a crontab changes only the commands' environment, not when they run), so a job meant for a market's local time needs the conversion done in the job (or a scheduler that has timezones: Chapter 11). Overlap: neither `crontab(5)` nor `cron(8)` describes any check for a run still in progress (stated as the documentation's silence, not as a quote), so a job scheduled hourly that takes 70 minutes on a bad night overlaps the next one; guard with `flock -n`, which will "fail rather than wait if the lock cannot be immediately acquired" (`flock(1)`; executed: the second `flock -n` exits 1). **DST (now sourced: Debian `cron(8)`):** for clock changes under 3 hours, "those jobs which would have run in the time that was skipped will be run soon after the change", and jobs in a repeated hour "will not be re-run"; this applies only to fixed-time jobs, not ones with `*` in the hour or minute or `@hourly`. The reel's `15 2 * * *` sits exactly in that window: in Europe/Berlin 02:15 does not exist on 29 March 2026 and occurs twice on 25 October 2026; in America/New_York it does not exist on 8 March 2026 (executed with Python `zoneinfo`, tzdata 2026c). Debian's cron then runs it once each night, late in spring; other crons (cronie) are not quoted here. Simplest: run cron in UTC. Real orchestration (retries, dependencies, backfills) is Chapter 11.
  - **### ssh and tunnels**: keys (`-i`, `~/.ssh/authorized_keys` on the server; agent forwarding as a pointer), `-L [bind:]port:host:hostport` (local port to a host *as seen from the server*), `-R` (the reverse: a server port to your side), `-J` (jump through a bastion; several hops comma-separated), `-N` (no command), `-f`, `ServerAliveInterval`, `~/.ssh/config` `Host` blocks with `ProxyJump`. Reaching the shop's PostgreSQL behind a bastion: `ssh -N -L 5433:db.internal:5432 user@bastion` (the bastion connects to `db.internal`), then `psql -h localhost -p 5433`; with `-J bastion user@app-host` instead, the bastion only relays and the database connection is made "from the remote machine", `app-host`, so `db.internal` must be reachable and resolvable from there. `ssh` ignores a private key file "if it is accessible by others" (`ssh(1)`). Not executed: the commands are shown and parsed, never run (no `sshd` in the sandbox or CI), and the Deep dive says so.
  - **### A hung job: /proc and strace**: `/proc/<pid>/status` (`State`, `Threads`, `Tgid`, `PPid`, `Umask`, `SigCgt`), `wchan` (the kernel symbol the process sleeps in; the name depends on the kernel version: `wait_woken` for the socket read on 6.18, `anon_pipe_read` for a pipe read), `fd` (which file, pipe or socket each descriptor is), `stack` (the kernel call chain; only with `CONFIG_STACKTRACE`; needs ptrace permission), `/proc/<pid>/syscall` (the number of the system call it is inside, architecture-specific: 0 is `read` on x86-64). `strace -p <pid>` attaches and prints the call in progress (only the thread whose ID is given: `-f -p` "attaches to all of its threads"); Ctrl-C detaches and leaves the process running, and a detach while the call is blocked prints `<detached ...>` after `read(4, ` (executed); `-f` for threads and children, `-e trace=network`, `-T` for call durations, `-y` to print paths next to fds, `-o file` to write the trace to a file (all quoted). What to conclude: `read(4,` on a socket with no sender → the other side is gone or silent (check the connection, then TERM); state `D` with `wchan` in a filesystem or block function → the storage, not the job (and signals wait); `R` at 100 % CPU → profile, not strace. Ptrace permission: with Yama's `ptrace_scope` at 1 a process may attach only to its own descendants (unless the target declares a tracer with `prctl(PR_SET_PTRACER, …)`), at 2 only with `CAP_SYS_PTRACE` (kernel Yama docs), and container seccomp profiles can refuse `ptrace` too, so `strace -p` fails with `EPERM` for a job started by a sibling process. `/proc/<pid>/syscall` and `stack` are behind the same ATTACH-mode check (their man pages) and fail with it; `status`, `wchan` and `fd` need only a READ-mode check, so those three are the fallback.

### The process model (step 2)
1. `fork()` creates a new process by duplicating the caller; the two run in separate memory spaces. — SOURCES.md § fork(2): "fork() creates a new process by duplicating the calling process."; "The child process and the parent process run in separate memory spaces."
2. The child inherits copies of the parent's open file descriptors, each referring to the same open file description. — § fork(2): "The child inherits copies of the parent's set of open file descriptors." Executed: a redirected fd set in the shell is what the child writes to.
3. `fork()` returns the child's PID in the parent and 0 in the child. — § fork(2): "On success, the PID of the child process is returned in the parent, and 0 is returned in the child." Executed (`fork_demo.py`).
4. `execve()` replaces the running program in the same process, with new stack, heap and data. — § execve(2): "execve() executes the program referred to by path. This causes the program that is currently being run by the calling process to be replaced with a new program, with newly initialized stack, heap, and (initialized and uninitialized) data segments." Executed: the child's label becomes `sh -c 'exit 42'` and its status comes back.
5. A process's PPid names the process that forked it (until that parent exits: see claim 23). — § credentials(7): "A process's parent process ID identifies the process that created this process using fork(2)." Executed: `PPid` in `/proc/<pid>/status`.
6. `wait()` reports a child's termination, stop or resume; the exit status is the low 8 bits of what the child passed to `exit`. — § wait(2): "A state change is considered to be: the child terminated; the child was stopped by a signal; or the child was resumed by a signal."; "WEXITSTATUS(wstatus) returns the exit status of the child. This consists of the least significant 8 bits of the status argument that the child specified in a call to exit(3) or _exit(3) or as the argument for a return statement in main()." Executed: `exit 300` → 44; `sys.exit(-1)` → 255; `WEXITSTATUS` → 42. (Bash's own wording: "Exit statuses fall between 0 and 255".)
7. A child killed by a signal is reported as such, with the signal number. — § wait(2): "WIFSIGNALED(wstatus) returns true if the child process was terminated by a signal."; "WTERMSIG(wstatus) returns the number of the signal that caused the child process to terminate." Executed: `WTERMSIG` 9.
8. fds 0, 1, 2 are standard input, output and error; `/proc/<pid>/fd` lists one symlink per open file, pipes and sockets as `type:[inode]`. — § proc_pid_fd(5): "This is a subdirectory containing one entry for each file which the process has open, named by its file descriptor, and which is a symbolic link to the actual file. Thus, 0 is standard input, 1 standard output, 2 standard error, and so on."; "For file descriptors for pipes and sockets, the entries will be symbolic links whose content is the file type with the inode." Executed: `0 -> pipe:[…]`, `4 -> socket:[…]`.

### Redirection and pipelines (steps 3–4)
9. Redirections apply in order; `2>&1 > file` sends only stdout to the file because stderr was copied from stdout before stdout was redirected. — § GNU Bash Reference Manual: "The order of redirections is significant."; "ls > dirlist 2>&1"; "ls 2>&1 > dirlist"; "directs only the standard output to file dirlist, because the standard error was made a copy of the standard output before the standard output was redirected to dirlist." Executed: 0 vs 1 lines in the file.
10. A pipeline's status is its last command's unless `pipefail`; with `pipefail` it is the rightmost non-zero status, or 0. — § GNU Bash Reference Manual: "The exit status of a pipeline is the exit status of the last command in the pipeline, unless the pipefail option is enabled"; "If pipefail is enabled, the pipeline’s return status is the value of the last (rightmost) command to exit with a non-zero status, or zero if all commands exit successfully." Executed: 0, then 2; `(exit 3) | (exit 4)` → 4.
11. `pipefail` is in POSIX.1-2024. — § POSIX.1-2024 Shell Command Language: "The exit status of a pipeline shall depend on whether or not the pipefail option (see set) is enabled".
12. `set -e` exits on a failing pipeline; `set -u` treats unset variables as an error. — § GNU Bash Reference Manual: "Exit immediately if a pipeline (see Pipelines), which may consist of a single simple command"; "Treat unset variables and parameters other than the special parameters ‘@’ or ‘*’, or array variables subscripted with ‘@’ or ‘*’, as an error when performing parameter expansion."; the exception: "any command in a pipeline but the last (subject to the state of the pipefail shell option)" does not trigger `-e`; for `-u`, "a non-interactive shell will exit". Executed: `unbound variable`, exit 1 from a script file (127 under `bash -c`: the manual gives no number, so the page says "exits with an error"); `-e` alone continues past the failing `jq`. Also executed (Deep dive): `pipefail` turns `seq … | head -1` into 141.
13. `jq` exits 2 when it cannot open the input file. — § jq 1.8 Manual: "Normally jq exits with 2 if there was any usage problem or system error, 3 if there was a jq program compile error, or 0 if the jq program ran." Executed (jq 1.7: "Could not open file", exit 2). ### Exit codes (step 5)
14. A command killed by signal N exits with 128 + N in Bash. — § GNU Bash Reference Manual: "When a command terminates on a fatal signal whose number is N, Bash uses the value 128+N as the exit status." Executed: 129, 130, 137, 143. POSIX only says "greater than 128" and that shells "are permitted to assign an exit status greater than 255" (§ POSIX.1-2024), so the page attributes 128 + N to Bash.
15. Command not found → 127; found but not executable → 126, in Bash and in POSIX. — § GNU Bash Reference Manual: "If a command is not found, the child process created to execute it returns a status of 127."; "If a command is found but is not executable, the return status is 126."; § POSIX.1-2024: "If the command is not found, the exit status shall be 127."; "Otherwise, if the command name is found, but it is not an executable utility, the exit status shall be 126." Executed: `./clean.py` without an x bit → 126 (`Permission denied`), as root too (§ path_resolution(7): "grants execute permission only when at least one of the file's three execute permission bits is set"); a misspelt command name (`pyhton3`) → 127. Not 127: `python3 clean.pyy` (exit 2, `python3` was found). A missing `#!` interpreter → 127 on Bash 5.2, a directory → 126 (executed).
16. The exit status is one byte (0–255). — claim 6's "least significant 8 bits"; § GNU Bash Reference Manual: "Exit statuses fall between 0 and 255"; executed: `exit 300` → 44.
17. Signal numbers: SIGHUP 1, SIGINT 2, SIGKILL 9, SIGTERM 15. — § signal(7): "The first numeric value in each table row shows the signal number on x86, ARM, and most other architectures" and the rows SIGHUP 1, SIGINT 2, SIGKILL 9, SIGTERM 15 (checked in the fetched table). Executed (`kill -l HUP INT KILL TERM` → `1 2 9 15`).
18. bisect reserved 125 because 126 and 127 are the shells' codes, and re-checks a first-run 126/127 on the good commit. — § git-bisect (2.56.0): "125 was chosen as the highest sensible value to use for this purpose, because 126 and 127 are used by POSIX shells to signal specific error status"; § git builtin/bisect.c (v2.56.0): "Exit code 126 and 127 can either come from the shell" … "Check with a known-good" [revision] …, under `if (is_first_run && (res == 126 || res == 127))`. Note the docs alone say 126/127 are "normal errors in the script" (bad); the first-run re-check is in the source only, so the page cites the source for it.

### Signals, zombies, orphans, threads (step 6)
19. A signal's default action Term terminates the process. — § signal(7): "Term Default action is to terminate the process."
20. SIGKILL and SIGSTOP cannot be caught, blocked or ignored. — § signal(7): "The signals SIGKILL and SIGSTOP cannot be caught, blocked, or ignored." Executed: the handler job dies with 137 on KILL and exits 0 on TERM.
21. What the four signals mean. — § signal(7) table comments: "Hangup detected on controlling terminal or death of controlling process" (SIGHUP); "Interrupt from keyboard" (SIGINT); "Kill signal" (SIGKILL); "Termination signal" (SIGTERM).
22. A child that terminates but is not waited for is a zombie. — § wait(2): "A child that terminates, but has not been waited for becomes a \"zombie\"." Executed: `State: Z (zombie)`, `<defunct>`.
23. When a parent exits, its children are adopted by init (or the nearest subreaper), which waits for zombies. — § _exit(2): "Any children of the process are inherited by init(1) (or by the nearest "subreaper" process as defined through the use of the prctl(2) PR_SET_CHILD_SUBREAPER operation)." (this covers living children, the orphans); § wait(2): "If a parent process terminates, then its \"zombie\" children (if any) are adopted by init(1), (or by the nearest \"subreaper\" process as defined through the use of the prctl(2) PR_SET_CHILD_SUBREAPER operation); init(1) automatically performs a wait to remove the zombies." (The page never says "orphan"; the Deep dive uses the word for this behaviour and says so.) Executed: `PPid` changes.
