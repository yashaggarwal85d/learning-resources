## Learning outcomes ("After this refresher you can")

1. Predict what a pipeline with redirections writes where (`>`, `>>`, `2>&1` and its order trap, `|`), and make a script fail loudly with `set -euo pipefail` instead of exiting 0 after a failed middle step.
2. Read an exit status: 0 to 255, the program's own codes, 126 (found but not executable: the missing x bit) and 127 (not found), and 128 + n for a process killed by signal n (130, 137, 143); and so say why bisect reserved 125 and treats a first-run 126 or 127 as a broken test.
3. Diagnose a hung job with `ps` (R, S, D, Z and the thread view), `/proc/<pid>/status`, `wchan`, `fd` and `stack`, and `strace -p`, then stop it gracefully (SIGTERM, which a program can catch and use to flush) before forcefully (SIGKILL, which it can't).
4. Reproduce a Python script's aggregation with `jq | awk | sort | uniq -c` and `diff` the two outputs (the §1.1 chapter lab's pipeline half).
5. Schedule a job with cron (five fields, the minimal environment, one timezone, no overlap guard) and reach a private database through an ssh tunnel (`-L`, `-R`, `-J`, keys).

### Step 3 · "Where did the error go?" (predict)

- **The idea:** the three fd sockets are a table, and a redirection re-points one entry *at the moment it is read, left to right*. `2>&1 > out.log` copies fd 1's current target (the terminal) into fd 2 and only then points fd 1 at the file, so the error never reaches the log. ### Step 6 · "TERM asks; KILL doesn't"

- **The idea:** the same job, two bolts. SIGTERM lands on a box that *catches* it: the box writes its last lines ("flushed and closed") and returns a crema `0`. SIGKILL can't be caught: the box vanishes mid-write and the parent gets a cherry `137`. Then the two things left behind when parents and children die out of order: a zombie (finished, not yet waited for: a dashed box with `Z`) and an orphan (its parent gone, adopted by init).
- **Portrait (`Svg h≈340`):**
  - Two columns. Left (x 30–280): `bash` box at the top (y≈50), child `load_orders.py` at y≈160; a caramel bolt labelled `TERM 15` (13) strikes the child; a small speech line under the child "flushed and closed" (latte 13); token `0` rides up.
  - Right (x 320–570): the same tree; bolt `KILL 9`; the child box's outline breaks (the box fades to 30 % with a cherry crack line); cherry token `137` rides up.
  - Bottom row (y≈300): two small boxes side by side, 60 units apart: a dashed box `Z` with the label "zombie: ended, not yet waited for" (taupe 13, below), and a box whose parent line is cut and re-attached to a tiny `init` box above it, label "orphan: adopted by init". (Labels on separate lines; if the bottom row crowds on a phone, drop the orphan drawing and keep the word in the caption.)
  - Landscape: same.
- **Beats:** 0.2 both trees; 0.8 TERM bolt; 1.2 "flushed and closed"; 1.6 token 0 rides; 2.2 KILL bolt; 2.5 crack; 2.8 token 137 rides; 3.4 zombie box; 3.8 orphan re-attach.
- **Values:** 15, 9, 0, 137; `Z`. Executed: a Python job with a SIGTERM handler prints "flushed and closed" and exits 0 when sent TERM; the same job sent KILL gives 137; a finished-but-unwaited child shows `State: Z (zombie)` in `/proc/<pid>/status` and `<defunct>` in `ps`; an orphan's `PPid` changes from its parent's PID once the parent exits (asserted as "changed", printed, not shown as a number: in a container the adopter may be a subreaper, not PID 1).
- **Final frame:** both trees with their tokens and the two bottom boxes.
- **Caption:** "A signal is a one-number message. SIGTERM (15) is the polite stop: a program can catch it, flush and close. SIGKILL (9) can't be caught, blocked or ignored: the kernel ends the process where it stands, so buffers are lost. SIGINT (2) is Ctrl-C; SIGHUP (1) is 'your terminal went away', which is how an ssh job dies with the session. A child that has ended but not been waited for is a zombie; a child whose parent died is adopted by init. So: TERM first, wait, then KILL."
- **Duration:** 4.2.

## Deep dive (`index.mdx`)

Sections in the Python essentials pattern (`data-section` names), plus a frontier section:

- **outcomes — "After this refresher you can"**: the five outcomes above.
- **internals — "A little deeper"**
  - **### Files, inodes and permissions**: a path is resolved component by component; a file is an inode, and a name is a link to it: `ln a b` gives two names with the same inode number and a link count of 2, `ln -s` makes a separate small file that holds a path (executed: same inode, count 2; the symlink's own inode differs and `stat -L` follows it). The nine bits `rwx` for user, group and other; on a directory the third bit is *search*: without it a lookup fails with EACCES (`Permission denied`) even when the file itself is readable (executed under a non-root user: `setpriv --reuid=65534` when the runner is root, native otherwise; printed as `skipped` if neither is possible). `chmod 644 clean.py` leaves `rw-r--r--`, and running it gives 126 (step 5). `umask` turns bits *off* from the mode a program asks for: `0666 & ~022 = 0644`; `umask 077` gives a new file `600` (executed); a child inherits it across fork and exec. setuid, by name only: the first octal digit's 4 bit; on exec the effective user ID becomes the file's owner's, which is how `passwd` works, and why `chmod` quietly clears set-group-ID bits it shouldn't set; a data job never needs it. `/proc/<pid>/status` shows a process's `Umask`.
  - **### Pipes, redirection and the pipeline's status**: fd 0, 1, 2 and `/proc/<pid>/fd` as the live table (one symlink per open file; pipes and sockets show as `type:[inode]`, executed). `>` truncates, `>>` appends, `2>` redirects errors, `2>&1` copies 1's current target into 2, **left to right** (the Bash manual's own `ls 2>&1 > dirlist` example; executed both orders: 0 vs 1 lines in the file). `|` connects 1 to 0 through a kernel pipe. The pipeline's status is the last command's unless `pipefail`, which makes it the rightmost non-zero; `PIPESTATUS` holds all of them (executed `2 0 0`). `set -e` exits on a failing pipeline (so `-e` without `pipefail` still misses the `jq` failure in step 4), `-u` makes an unset variable an error (executed: `unbound variable`, exit 1). POSIX.1-2024 standardised `pipefail`, so `sh` scripts may use it on a current shell; `dash` in CI images may not: say which shell the shebang names. Patterns: `cmd 2>&1 | tee log`, `cmd > /dev/null 2>&1` (order again), `exec > >(logger)` as a pointer only.
  - **### The process model: fork, exec, wait and the exit status**: `fork()` duplicates the caller: the child is a copy in its own memory, inherits copies of the open file descriptors (same open file descriptions, so a redirected fd set before `exec` survives it), gets `0` back while the parent gets the child's PID (executed with `os.fork`); `execve()` replaces the program in the same process, new stack, heap and data, same PID, same fds (that is why `exec` keeps the PID and why a shell's `exec cmd` replaces the shell); the parent's `wait()` collects the status: `WEXITSTATUS` is the low 8 bits of what the child passed to `exit` (executed: `exit 300` reads as 44; `exit(-1)` as 255), `WIFSIGNALED` / `WTERMSIG` say it was killed and by which signal (executed: 9 for a killed child), and the shell turns that into 128 + n (137). 126 and 127 are the shell's: found but not executable (also an interpreter line that can't run), and not found. Why bisect reserved 125 and re-checks a first-run 126/127: it reads these bands (Git refresher, step 6 and its Deep dive "Bisect"). `PPid` in `/proc/<pid>/status` names the parent that forked you; `$$` and `$!`; `exec` in scripts; `nohup` / `setsid` to survive SIGHUP (pointer; needs its quote, see Needed quotes).
  - **### Signals, zombies, orphans and threads**: a signal's default action (Term, Ign, Core, Stop, Cont); the four to know: SIGHUP 1 (terminal or session leader gone), SIGINT 2 (Ctrl-C), SIGTERM 15 (the polite stop, catchable), SIGKILL 9 (cannot be caught, blocked or ignored; the kernel ends the process, buffers unflushed); numbers from `kill -l` (executed; the x86 numbers from `signal(7)`'s table, see Needed quotes). A handler in Python (`signal.signal(SIGTERM, …)`: flush, close, exit 0, executed) and in a shell script (`trap`). `kill -TERM` then `kill -KILL`, and why a D-state process ignores both until the I/O returns. SIGSTOP/SIGCONT and `T`. Zombies: a child that terminated but was not waited for keeps its PID and status (`Z`, `<defunct>`, executed); the fix is in the parent (wait, or `SIGCHLD` set to ignore), and `kill -9` on a zombie does nothing (it is already dead; note as reasoning from `wait(2)`, not a quoted claim). Orphans: when a parent exits, its children are adopted by init (or the nearest subreaper), which waits for them (executed: `PPid` changes). **Threads, one paragraph:** a process can run several threads that share its memory and open files; `Threads:` in `/proc/<pid>/status` counts them, `Tgid` is the process ID they share, `ps -L` shows LWP and NLWP (executed: a Python job with a worker thread shows `Threads: 2`). What they cost and how they share safely is topic 8 (`threads-context-switches-synchronization`); topic 7 needs only this.
  - **### Looking at processes: ps, top, htop and load average**: the states: `R` running or runnable, `S` interruptible sleep (waiting for an event), `D` uninterruptible sleep (usually I/O), `Z` zombie, `T` stopped (`ps(1)`); which columns matter for a data job: `pid,ppid,stat,wchan,etime,rss,pcpu,comm` (executed: a `ps -eo` line for the hung job; the field descriptions need quotes, see Needed quotes), `ps -L` for threads, `ps --forest` for the tree. `top -bn1` for a snapshot (executed: header printed, numbers not asserted); the load average is three numbers over 1, 5 and 15 minutes from `/proc/loadavg`, counting runnable *and* D-state tasks, so a high load with idle CPUs means I/O waits (needs `proc_loadavg(5)`'s quote; until then say only "three numbers, 1, 5, 15 minutes", which the `top` header shows). `htop` is the interactive version (not installed in the sandbox: named, not executed; no claim about its display beyond "shows threads"). Container caveat: `/proc` shows the container's PID namespace.
  - **### One-liners over order_events**: JSON lines means one object per line (`jq -c` prints that shape; `-r` prints strings raw; `-s` slurps the whole input into one array, which is the one thing *not* to do on 1 TiB: the Python refresher's generators-vs-lists rule in shell form). `jq -r .status`, `jq 'select(.status == "refunded")'`, `jq -s 'group_by(.status) | map({status: .[0].status, n: length})'` (executed: 7 groups on the raw file, 4 after cleaning); `jq`'s exit codes (2 for a system error such as a missing file, 5 for a parse or runtime error, executed on 1.7; needs the manual's quote). awk: records and fields, `$1`, `$NF`, `NF`, `-F`, patterns and actions, associative arrays (`n[$1]++` then `END { for (k in n) … }`), `tolower`, `$1 = $1` to rebuild the record (trim) (executed: the awk-only counter gives the same four lines as `uniq -c`). sed: `-n` and `p`, `s/regexp/replacement/flags`, `-i` with care; `sed` on a log line, not on JSON. grep: `-E`, `-c`, `-o`, `-F` for literal strings, `-r`; the trap that regular expressions count strings, not values: `grep -Ec '"status": *"(refunded|cancelled)"'` gives 1,495, not 1,500, because 5 events say `" refunded"` (executed). `sort | uniq -c`, `sort -k2`, `LC_ALL=C sort` for byte order (what `clean.py` sorts by, so `diff` can be empty), `cut`, `tr`, `wc -l`, `head`/`tail`, `xargs -P` (pointer), `tee`. All awk constructs are POSIX, so the runner's mawk and the manual's gawk agree.
  - **### cron**: the five fields with their ranges (minute 0–59, hour 0–23, day of month 1–31, month 1–12, day of week 0–7 with 0 and 7 Sunday), lists, ranges and steps, `@daily` and friends; cron checks entries once a minute and runs the command when minute, hour and month match and *either* day field matches (both restricted: either one, executed by the parser against `crontab(5)`'s rule); the minimal environment (SHELL `/usr/bin/sh`, LOGNAME, HOME from passwd; set `PATH` in the crontab or use absolute paths; `%` in the command is a newline unless escaped); redirect both streams or mail; one timezone for the daemon, no per-user timezone, so a job meant for a market's local time needs the conversion done in the job (or a scheduler that has timezones: Chapter 11). Overlap: nothing in cron waits for the previous run, so a 02:15 job that takes 70 minutes on a bad night overlaps the next one if scheduled hourly; guard with `flock -n` (needs its quote; otherwise phrase as "use a lock file"). **DST:** this `crontab(5)` says nothing about daylight-saving changes; the Deep dive makes no DST claim unless a primary source is fetched (candidate: cronie's `cron(8)`, "Daylight Saving Time and other time changes"); until then it says exactly that: test what your cron does at 02:30 on the switch nights before scheduling there. Real orchestration (retries, dependencies, backfills) is Chapter 11.
  - **### ssh and tunnels**: keys (`-i`, `~/.ssh/authorized_keys` on the server; agent forwarding as a pointer), `-L [bind:]port:host:hostport` (local port to a host *as seen from the server*), `-R` (the reverse: a server port to your side), `-J` (jump through a bastion; several hops comma-separated), `-N` (no command), `-f`, `ServerAliveInterval`, `~/.ssh/config` `Host` blocks with `ProxyJump`. Reaching the shop's PostgreSQL behind a bastion: `ssh -N -L 5433:db.internal:5432 -J bastion user@app-host`, then `psql -h localhost -p 5433`. Not executed: the commands are shown and parsed, never run (no `sshd` in the sandbox or CI), and the Deep dive says so.
  - **### A hung job: /proc and strace**: `/proc/<pid>/status` (`State`, `Threads`, `Tgid`, `PPid`, `Umask`, `SigCgt`), `wchan` (the kernel symbol the process sleeps in; the name depends on the kernel version: `wait_woken` for the socket read on 6.18, `anon_pipe_read` for a pipe read), `fd` (which file, pipe or socket each descriptor is), `stack` (the kernel call chain; only with `CONFIG_STACKTRACE`; needs ptrace permission), `/proc/<pid>/syscall` (the number of the system call it is inside, architecture-specific: 0 is `read` on x86-64). `strace -p <pid>` attaches and prints the call in progress; Ctrl-C detaches and leaves the process running; `-f` for threads and children, `-e trace=network`, `-T` for call durations, `-y` to print paths next to fds (each needs its quote). What to conclude: `read(4,` on a socket with no sender → the other side is gone or silent (check the connection, then TERM); state `D` with `wchan` in a filesystem or block function → the storage, not the job (and signals wait); `R` at 100 % CPU → profile, not strace. Ptrace permission: Yama `ptrace_scope` and container seccomp can refuse `strace -p` (`EPERM`); then `wchan`, `fd` and `syscall` still tell most of the story (the fallback `examples.sh` uses).

### The process model (step 2)

4. `execve()` replaces the running program in the same process, with new stack, heap and data. — § execve(2): "execve() executes the program referred to by path.
