<section data-section="outcomes">

## After this refresher you can

- Predict what a pipeline with redirections writes where (`>`, `>>`, `2>&1` and its order trap, `|`), and make a script fail loudly with `set -euo pipefail` instead of exiting 0 after a failed middle step.
- Read a mode string such as `rw-------` and predict who can read, enter or delete: `rwx` for user, group and other, `x` on a directory as "enter", and `umask` as the bits a new file does not get (a job that writes under `umask 077` leaves a group member's loader with `Permission denied`).
- Read an exit status: 0 to 255, the program's own codes, 126 (found but not executable: the missing x bit) and 127 (not found), and 128 + n for a process killed by signal n (130, 137, 143); and so say why `git bisect run` reserves 125 and re-checks a first-run 126 or 127 on a known-good revision.
- Diagnose a hung job with `ps` (R, S, D, Z and the thread view), `/proc/<pid>/status`, `wchan`, `fd` and `stack`, and `strace -p`, then stop it gracefully (SIGTERM, which a program can catch to flush and then re-raise, so the status still reads 143, not 0) before forcefully (SIGKILL, which it cannot).
- Reproduce a Python script's aggregation with `jq | awk | sort | uniq -c` and `diff` the two outputs (the pipeline half of the chapter lab).
- Schedule a job with cron (five fields, the minimal environment, one timezone, no overlap guard) and reach a private database through an ssh tunnel (`-L`, `-R`, `-J`, keys).

## A little deeper

Everything in the reel was run: `examples.sh` uses the real `bash`, `jq`, `awk`, `sed`, `grep`, `sort`, `uniq`, `diff`, `ps` and `strace` in a temporary directory and `examples.py` re-asserts every number the reel shows. The running example is `order_events.jsonl`, raw order events as JSON lines (one object per line with `order_id`, `customer_id`, `status`, `amount`, `event_time`); the examples use 10,000 lines built so that the counts are exact (6,000 paid, 2,500 shipped, 1,300 cancelled, 200 refunded), the real file being a terabyte, which is why every pipeline here streams. `clean.py` is the Git refresher's `clean()` (`strip().lower()`) with a `main` that counts events per cleaned `status`. They ran on **Bash 5.2.21**, **jq 1.7**, **mawk 1.3.4** (the runner's `awk`; only POSIX awk is used, so gawk behaves the same), **GNU sed 4.9**, **grep 3.11**, **coreutils 9.4**, **strace 6.8**, **procps-ng 4.0.4** and **Linux 6.18**; `examples.sh` prints every version it ran on. The manuals quoted are newer (see Sources); nothing the examples use changed between them. Three things were not run, and the text says so where it matters: cron (no daemon, so the crontab line is parsed against `crontab(5)`), ssh (no `sshd`, so the `-L` argument is parsed), and `htop` (named, never relied on).

### Files, inodes and permissions

- **A path is resolved one component at a time**, and a file is an inode: a name is a link to it. `ln a b` gives two names with the same inode number and a link count of 2; `ln -s a c` makes a separate small file that holds a path, with its own inode (`stat -L` follows it). Executed: same inode, count 2; the symlink's own inode differs.
- **Nine bits: `rwx` for user, group and other.** On a *directory* the third bit means *search*: without it a lookup fails with `Permission denied` even when the file itself is readable, while the read bit alone still lists the names. Executed as a user who is not the owner: with the directory at read-only, `ls d` prints `file` (exit 0) but `cat d/file` gets `Permission denied`; with search-only it is the other way round. Write on the *directory*, not on the file, is what deletes or renames a name in it (executed: a world-writable file could not be removed from a directory without the w bit, and an unreadable file could be removed from a directory with it).
- **`chmod 644 clean.py` leaves `rw-r--r--`, and running it gives 126, even as root.** Root's override "grants execute permission only when at least one of the file's three execute permission bits is set" (`path_resolution(7)`); executed as root. That is the whole story of 126 in the reel.
- **`umask` turns bits off from the mode a program asks for**: `0666 & ~022 = 0644`; `umask 077` gives a new file mode 600 (executed). A child inherits it across fork and exec, and a default ACL on the parent directory overrides it (`umask(2)`). So a job that writes files nobody else can read is usually an inherited umask problem, not a `chmod` problem. Executed as root: a file written under `umask 077` has mode 600 and a loader in the file's group got `Permission denied`; under `umask 027` the mode is 640 and the same loader read it. The fix is a deliberate umask in the job (`027`), or a set-group-ID landing directory below. `/proc/<pid>/status` shows a process's `Umask`.
- **setuid, setgid, sticky.** The first octal digit holds them: 4 set-user-ID (on exec the effective user ID becomes the file's owner's), 2 set-group-ID, 1 the restricted deletion flag (`chmod(1)`). On a directory, the sticky bit "prevents unprivileged users from removing or renaming a file in the directory unless they own the file or the directory", commonly on world-writable directories like `/tmp` (executed: with the bit, another user could not delete a file they did not own; without it they could). A set-group-ID directory makes new files take the *directory's* group, the usual fix for a shared landing zone (executed: a file made in a `2775` directory had the directory's group). `chmod` clears the set-group-ID bit of a regular file whose group isn't one of yours unless you are privileged. A data job never needs setuid.

### Pipes, redirection and the pipeline's status

- **Every process starts with three open files**: 0 standard input, 1 standard output, 2 standard error. `/proc/<pid>/fd` is the live table, one symlink per open file; pipes and sockets show as `type:[inode]`.
- **`>` truncates, `>>` appends, `2>` redirects errors, `2>&1` copies where 1 points now, left to right.** The Bash manual's own example is `ls 2>&1 > dirlist`: the error still goes to the terminal. Executed both orders: `2>&1 > out.log` left the file empty (0 lines) and the error on the terminal; `> out.log 2>&1` put the 1 line in the file. `|` connects 1 to the next command's 0 through a kernel pipe. Patterns: `cmd 2>&1 | tee log`, `cmd > /dev/null 2>&1` (order again). Bash's shorthands: `&>file` sends both streams to the file and `|&` pipes both (executed: 1 line each), and `set -o noclobber` makes `>` refuse to overwrite an existing file (executed: status 1; `>|` overrides it).
- **A pipeline's status is the last command's unless `pipefail`**, which makes it the rightmost non-zero; `PIPESTATUS` holds them all (executed `2 0 0`; `(exit 3) | (exit 4) | true` under pipefail gives 4).
- **`set -e` has deliberate holes.** It does not fire for "any command in a pipeline but the last (subject to the state of the pipefail shell option)", nor inside an `if` test, a `while`/`until` condition, all but the last command of an `&&`/`||` list, or after `!`. Executed: `set -e` alone continued past the failing `jq`; `set -eo pipefail` stopped with status 2. `set -u` makes an unset variable an error and a non-interactive shell exits: executed on Bash 5.2.21 with exit 1 from a script file but 127 under `bash -c '…'`, so test it from a file. `set -euo pipefail` plus explicit checks is the defensible baseline, not a guarantee.
- **The `pipefail` trap the other way:** `seq 1 100000 | head -1` exits 141 under `pipefail` (the writer is killed by SIGPIPE, 128 + 13, after `head` stops reading; `PIPESTATUS` is `141 0`), so a script can fail on a pipeline that did exactly what it should. Likewise a `grep` that finds nothing exits 1, and under `set -e` or `pipefail` that aborts the script unless you handle it (`|| true`, or an explicit test).
- **Stages are separate processes.** `producer | while read x; do n=…; done` runs the loop in a subshell, so the variable is lost afterwards (executed: 0), unless `shopt -s lastpipe` is set (executed: 2).
- **A pipe is a bounded kernel buffer**, 65,536 bytes by default on Linux (executed with `F_GETPIPE_SZ`; a non-blocking writer filled exactly that many bytes). A writer blocks when the reader is slow, which is free backpressure; and writing to a pipe whose readers are all gone is what raises SIGPIPE.
- **POSIX.1-2024 standardised `pipefail`**, so `sh` scripts may use it on a current shell. Whether `/bin/sh` has it depends on the distribution's `dash` build: Debian's changelog for `dash (0.5.12-7)` (17 May 2024) lists "Implement pipefail option", and Debian's `dash(1)` documents it ("If the pipefail option was enabled when the shell began execution of the pipeline, …"). The sandbox's `dash` is Ubuntu's `0.5.12-6ubuntu5`, the version before that entry, and it says `Illegal option -o pipefail` (executed), so `#!/bin/sh` plus `set -o pipefail` fails at line 1 here. Name `bash` in the shebang when you need it.

### The process model: fork, exec, wait and the exit status

- **Every external command is `fork()` then `exec`** (builtins such as `cd`, `export` and `set` run inside the shell itself; `$$` is the shell's own PID (Bash manual: "Expands to the process ID of the shell"), which is why `bash -c 'kill -KILL $$'` kills that shell). **`fork()` duplicates the caller.** The child is a copy in its own memory, inherits copies of the open file descriptors (the same open file descriptions, so they share offsets and flags), and gets 0 back while the parent gets the child's PID (executed with `os.fork`). Memory is copy-on-write, and only the calling thread is duplicated: "the child process is created with a single thread—the one that called fork()".
- **`execve()` replaces the program in the same process**: new stack, heap and data, same PID ("there is no new process", `execve(2)`; executed: `exec` keeps `$$`). Descriptors stay open unless marked close-on-exec; Python opens its own files close-on-exec, so what carries over is 0, 1, 2 and explicit redirections. That is why a shell's `exec cmd` replaces the shell.
- **The parent's `wait()` collects the status.** `WEXITSTATUS` is the low 8 bits of what the child passed to `exit` (executed: `exit 300` reads as 44, `exit(-1)` as 255, `sh -c 'exit 42'` as 42); `WIFSIGNALED` and `WTERMSIG` say it was killed and by which signal (executed: 9), and the shell turns that into 128 + 9 = 137. Python's `subprocess` reports the same death as `-9`, not 137: 137 is the shell's encoding.
- **Conventions:** 0 success, 1 to 125 whatever the command defines (a Bash builtin used wrongly exits 2: executed), 126 and 127 the shell's own, 128 + n a signal death.
- **126 and 127 are the shell's**: found but not executable (no x bit, or a directory, executed) and not found. A misspelt command gives 127; `python3 clean.pyy` gives 2, because `python3` *was* found and it is the file that is missing (executed). A missing interpreter in the `#!` line also gives 127 in Bash 5.2 ("required file not found", executed), not 126.
- **POSIX requires only** that a signal death be reported as "greater than 128" and allows values above 255; 128 + n is Bash's (and dash's) rule.
- **Why bisect reserved 125.** `git bisect run` reads these bands (0 good, 1 to 127 bad except 125, 125 skip; anything else aborts), and on the first run a 126 or 127 is re-checked on a good revision, because it means the test could not even start (Git refresher, step 6 and its "Bisect" section; Git v2.56.0 `builtin/bisect.c`). 125 sits just under the shell's own 126 and 127 so a test can say "skip" without being mistaken for one.
- `PPid` in `/proc/<pid>/status` names the parent that forked you. `nohup` runs a command "ignoring hangup signals", `setsid` runs it "in a new session" (the `setsid(1)` page itself says nothing about SIGHUP). `timeout` sends SIGTERM and exits 124 when it fires (executed: 124); add `--kill-after` to escalate for a child that ignores TERM, and then the status is 137, "if COMMAND (or timeout itself) is sent the KILL (9) signal" (`timeout(1)`; executed: 137). Its own 125 means `timeout` itself failed, the same number bisect reserves for skip.

### Signals, zombies, orphans and threads

- **A signal's default action** is Term, Ign, Core, Stop or Cont. The four to know: SIGHUP 1 (the terminal or session leader went away: how a job dies with its ssh session), SIGINT 2 (Ctrl-C), SIGTERM 15 (the polite stop, catchable), SIGKILL 9 (cannot be caught, blocked or ignored; the kernel ends the process and its unflushed buffers are lost). The numbers come from `kill -l` (executed `1 2 9 15`; the x86 and ARM numbering is the one `signal(7)` tables).
- **Handlers.** A Python `signal.signal(SIGTERM, …)` handler can flush and close, and then should end the job as stopped, not as done. The C library manual's advice: "The cleanest way for a handler to terminate the process is to raise the same signal that ran the handler in the first place", because "reraising the signal sets the return status from the process correctly" (glibc, "Termination in Handler"). In Python that is restoring the default action (`signal.signal(SIGTERM, SIG_DFL)`) and `os.kill(os.getpid(), SIGTERM)`, or `sys.exit(128 + signum)`. Executed: the handler printed `flushed and closed` and the status was 143 either way; the same job sent KILL gave 137; with no handler TERM gave 143. The two ways differ in a threaded job: `sys.exit` raises `SystemExit` in the main thread only, and "the entire Python program exits when no alive non-daemon threads are left" (Python `threading` docs), so a non-daemon worker still busy or stuck keeps the process alive; re-raising TERM ends it at once (executed: with a 2-second worker, `sys.exit(143)` ended the process only after the worker finished, the re-raise before it; both read 143). A handler that calls `sys.exit(0)` is the trap (executed: status 0): cron, a CI gate, `git bisect run` or an orchestrator then reads an interrupted, half-finished load as a success, the false success the pipeline example warns about. In Python the handler runs in the main thread at the next bytecode ("Python signal handlers are always executed in the main Python thread of the main interpreter"; the low-level handler only "sets a flag"), so a job inside a long call implemented purely in C "may run uninterrupted for an arbitrary amount of time, regardless of any signals received" (Python `signal` docs; the docs' example is a regular-expression match, and a database driver's call is the same kind of thing, which is reasoning, not run). That is how a scheduler's grace period can run out and the 137 arrive. In a shell script the same is `trap`. If Bash is waiting for a command to complete and a trapped signal arrives, "it will not execute the trap until the command completes"; a wrapper that must forward SIGTERM runs the child in the background and `wait`s on it ("the wait builtin will return immediately with an exit status greater than 128, immediately after which the shell executes the trap"; executed: the trap ran once and `wait` returned above 128). Dispositions matter across `fork` and `exec`: a child created by `fork` "inherits a copy of its parent's signal dispositions" (executed: a handler set before `os.fork` ran in the child), so a handler is live in a forked copy but gone once that copy `exec`s another program; during an `execve` the dispositions of handled signals are reset to the default, while ignored ones stay ignored (`signal(7)`, `execve(2)`), which is how `nohup` works. When an interactive shell itself receives SIGHUP (the ssh connection dropped), it "resends the SIGHUP to all jobs, running or stopped" before exiting (unless a job was removed with `disown`), so a job started from that session dies with it unless it ignores SIGHUP; on a plain `exit` it does that only if `shopt -s huponexit` is set, and then only for an interactive login shell.
- **Stopping a job**: `kill -TERM`, wait, then `kill -KILL`. A process in `D` state (uninterruptible sleep) usually can't act on either until the I/O returns, because the signal stays pending (reasoned from the state's name; not reproduced). `kill -0 <pid>` sends nothing but tests whether the process exists and you may signal it (executed: 0 and 1). `kill -TERM -- -<pgid>` signals a whole process group (executed under `set -m`: a leader and its two `sleep` children all ended, leader status 143), which is how you stop a job's whole tree.
- **Zombies.** A child that terminated but was not waited for keeps its PID and status: state `Z`, `<defunct>` in `ps -o args` (executed; `comm` shows only the name), and it holds no open files (executed as root: its `fd` directory was empty). The fix is in the parent (wait, or set `SIGCHLD` to `SIG_IGN`, after which children "do not become zombies", `wait(2)`). `kill -9` on a zombie does nothing: it is already dead.
- **Orphans.** When a parent exits, "any children of the process are inherited by init(1) (or by the nearest "subreaper" process…)" (`_exit(2)`), which waits for them (executed: the grandchild's `PPid` changed once its parent exited; in a container the adopter may be a subreaper rather than PID 1, so the new number is printed, not asserted). A program running as PID 1 in a container takes on init's job, which is why images use a minimal init; that is the images topic's business.
- **Threads, one paragraph.** A process can run several threads that share its memory and open files. `Threads:` in `/proc/<pid>/status` counts them, `Tgid` is the process ID they share, `ps -L` shows `LWP` and `NLWP` (executed: the reel's job shows `Threads: 2`). What they cost and how to share safely is the "Threads, context switches and synchronization cost" topic in §1.2; this topic needs only this.

### Looking at processes: ps, top, htop and load average

- **The states** (`ps(1)`): `R` running or runnable, `S` interruptible sleep (waiting for an event), `D` uninterruptible sleep (usually I/O), `Z` zombie, `T` stopped, `I` idle kernel thread; extra characters follow: `l` multi-threaded, `s` session leader, `+` foreground. That is why the hung job reads `Sl`: `S`, plus the multi-threaded flag.
- **The columns that matter for a data job**: `ps -eo pid,ppid,stat,wchan,etime,rss,pcpu,comm` (executed). `ps` and `/proc/<pid>` show only the processes visible in the PID namespace of the mount, so inside a container they list the container's processes (`pid_namespaces(7)`). `ps -L` lists threads (the reel's job: two rows, both sleeping, one in the socket read and one in a timer), `ps --forest` the tree, and `ps -eo pid,stat,wchan:20,cmd` shows the kernel function each process sleeps in.
- **`top -bn1`** is a snapshot (executed: it printed its header; numbers not asserted). In `top`, a multi-threaded process may show more than 100 % CPU ("amounts greater than 100% may be reported"), because the figure is per CPU; with Irix mode off, top "will operate in Solaris mode where a task's cpu usage will be divided by the total number of CPUs" (toggle with `I`). `wa` is "time waiting for I/O completion", and `VIRT` is everything in use or merely reserved, including "pages that have been mapped but not used", so a big `VIRT` alone is not a leak: watch `RES`. **`htop`** is the interactive version, not installed in the sandbox: named, not run.
- **Load average** is three numbers over 1, 5 and 15 minutes, in the first fields of `/proc/loadavg`, counting jobs in the run queue (`R`) *or* waiting for disk I/O (`D`) (`proc_loadavg(5)`). So a high load with idle CPUs points to D-state waits (stuck NFS, a failing disk), not CPU saturation. Read it against the CPU count (`nproc`): a 1-minute load near the number of CPUs means every CPU has work; well above it, tasks are queueing (reasoning from the definition above, not a quote).

### One-liners over order_events

- **JSON lines** means one object per line (`jq -c` prints that shape; executed: 10,000 lines). `-r` prints strings raw. `-s` slurps the whole input into one array, the one thing *not* to do on a terabyte: the Python refresher's generators-versus-lists rule in shell form. `--arg` passes a shell value as a string (never splice shell variables into the filter text); `-e` sets the exit status from the last output (executed: a `null` result exits 1 under `-e`, no output at all exits 4, and neither without `-e`).
- **More jq**: `//` supplies a default for `null` or `false` (executed), `@tsv` and `@csv` hand rows to awk or `sort` (executed: a tab-separated line), `--argjson` passes a value as JSON rather than a string (executed: `5 + 1` is 6), and `--stream` emits `[path, leaf]` events for an input too large to load whole (executed: `{"a":[1,2]}` gives 4 events).
- **`jq` exit codes**: 2 for a usage problem or system error such as a missing file, 3 for a compile error (the manual); an input parse error or an uncaught runtime error gave 5 (executed on 1.7; not in the manual, whose only 5 is `halt_error`'s default, but set in jq 1.8.2's `src/main.c`).
- **The lab's pipeline**: `jq -r .status order_events.jsonl | awk '{ $1 = $1; print tolower($0) }' | LC_ALL=C sort | uniq -c`. `clean.py` prints `%7d %s` (`print(f'{counts[status]:7d} {status}')`), the width `uniq -c` pads to (executed: `   1300 cancelled`), which is the only reason `diff` prints nothing; with your own script, normalise both sides first (for example `awk '{print $2, $1}'`) or `diff` fails on whitespace alone. Group counts: `jq -s 'group_by(.status) | map({status: .[0].status, n: length})'` gave 7 groups on the raw file and 4 after cleaning (executed).
- **awk**: records and fields, `$1`, `$NF`, `NF`, `-F`, patterns and actions, associative arrays (`n[$1]++`, then `END { for (k in n) … }`), `tolower`. It splits on runs of blanks by default (and is not a CSV parser). Assigning to any field rebuilds the record from its fields and `OFS`, so `$1 = $1` trims *and* squeezes inner runs of blanks to one space (executed: `'  a   b  '` becomes `a b`). That equals Python's `strip()` only when a value has no inner double spaces (true here), and the runner's mawk leaves `É` alone in `tolower` (executed: `Éa`) where Python's `str.lower()` gives `éa`, so the pipeline and the script can disagree on non-ASCII values; the lab's data is ASCII. The awk-only counter (`n[tolower($0)]++`) gave the same four lines as `uniq -c`.
- **sed**: `-n` and `p`, `s/regexp/replacement/flags`. `-i` edits in place with no undo (`-i.bak` keeps a backup: executed); test the expression without it first. `-E` switches to extended regular expressions, `-s` treats files separately instead of as one stream (executed: the last line of each of two files, against only the last of the second), and `-z` splits on NUL bytes, for `find -print0` style input (executed). It can pull a field out of JSON (executed: 10,000 lines) but it is the wrong tool for JSON: use it on a log line.
- **grep**: `-E`, `-c`, `-o`, `-r`, and `-F` for literal strings (executed: `10.0.0.1` as a regex matched 2 lines, as a fixed string 1, because a dot matches anything). "Binary file matches" means GNU grep decided a file is binary (often a stray NUL byte or an encoding problem): it suppresses output from the first NUL byte on, and lines with bad encoding, then prints that notice to stderr (executed on grep 3.11 with the NUL on the first line: stdout got no lines); `-a` forces text (executed: both lines). Its exit status is a three-way signal: 0 a line matched, 1 none, 2 an error (executed). Regular expressions count *strings*, not values: `grep -Ec '"status": *"(refunded|cancelled)"'` gave 1,495, not 1,500, because 5 events say `" refunded"` (executed).
- **The rest of the toolbox**: `sort | uniq -c`, `sort -k2`, `LC_ALL=C sort` for byte order (what `clean.py` sorts by, so `diff` can be empty), `cut`, `tr`, `wc -l`, `head`/`tail`, `tee`, `xargs -P` (a pointer). `diff` exits 0 when the files are the same and 1 when they differ (executed). All the awk constructs are POSIX, so the runner's mawk and the manual's gawk agree.

### cron

- **Five fields** with their ranges: minute 0 to 59, hour 0 to 23, day of month 1 to 31, month 1 to 12, day of week 0 to 7 (0 and 7 are Sunday); lists, ranges and steps; `@daily` and friends. cron checks entries once a minute and runs the command when minute, hour and month match and the day fields do: with *both* day fields restricted, **either** one matching is enough (executed with a parser written from `crontab(5)`: `0 0 13 * 5` is due on a Friday that is not the 13th, and on the 13th that is not a Friday).
- **The minimal environment.** On Debian's cron: `SHELL` is `/usr/bin/sh`, `LOGNAME` and `HOME` come from the password file (`crontab(5)`); the page lists no others, and cron does not read your shell's startup files (reasoning from that list, not a quote). Set `PATH` in the crontab or use absolute paths, but a crontab value "is not parsed for environmental substitutions", so `PATH=$HOME/bin:$PATH` does not work. A `%` in the command is a newline unless escaped. Redirect both streams or the output is mailed (or lost).
- **One timezone.** The daemon has one; a `TZ=` line in a crontab changes only the commands' environment, not when they run. A job meant for a market's local time needs the conversion done in the job, or a scheduler that has timezones (Chapter 11). Simplest: run cron in UTC.
- **DST.** For clock changes under 3 hours, "those jobs which would have run in the time that was skipped will be run soon after the change", and jobs in a repeated hour "will not be re-run" (Debian `cron(8)`); this applies only to fixed-time jobs, not ones with `*` in the hour or minute or `@hourly`. The reel's `15 2 * * *` sits exactly in that window: in Europe/Berlin 02:15 does not exist on 29 March 2026 and occurs twice on 25 October 2026; in America/New_York it does not exist on 8 March 2026 (executed with Python `zoneinfo`, tzdata 2026c). Debian's cron then runs it once each night, late in spring; other crons are not quoted here.
- **No overlap guard.** Neither `crontab(5)` nor `cron(8)` describes any check for a run still in progress (stated as the documentation's silence, not as a quote), so an hourly job that takes 70 minutes on a bad night overlaps the next one. Guard with `flock -n`, which will "fail rather than wait if the lock cannot be immediately acquired" (`flock(1)`; executed: the second `flock -n` exits 1). cron also has no retries, backfill, dependencies or catch-up for runs missed while the host was down: those are why pipelines move to an orchestrator (Chapter 11).

### ssh and tunnels

- **Keys.** Your private key stays with you (`-i` selects it); the server lists the public keys allowed to log in in `~/.ssh/authorized_keys`. `ssh` "will simply ignore a private key file if it is accessible by others", so a bastion key with the wrong permissions is not used. It is not silent: OpenSSH's `sshkey_perm_ok` prints `@ WARNING: UNPROTECTED PRIVATE KEY FILE! @`, then `Permissions 0%3.3o for '%s' are too open.`, then `This private key will be ignored.` (`authfile.c`, openssh-portable master). The check applies to a key file you own. ssh then tries the next key or method: a password prompt by hand, but under cron or `BatchMode=yes` there is no prompt, so the job fails with ssh's 255 and the warning goes to stderr, which is lost unless it was redirected (the redirection lesson again; the permission check was read in the source, not run: no `sshd` here).
- **`-L [bind:]port:host:hostport`** forwards a local port to a host *as seen from the server*; **`-R`** is the reverse: a server port to your side; **`-D`** makes ssh act as a SOCKS server; **`-N`** runs no remote command; **`-J`** jumps through a bastion (several hops, comma-separated); **`-f`** goes to the background. In `~/.ssh/config` a `Host` block can carry `ProxyJump`, and `ServerAliveInterval` sends keep-alives after that many seconds of silence (default 0: none), which is the fix for a tunnel that drops without a word.
- **Reaching the shop's PostgreSQL behind a bastion**: `ssh -N -L 5433:db.internal:5432 user@bastion`, then `psql -h localhost -p 5433`. The bastion is the ssh destination and it connects to `db.internal`. With `-J bastion user@app-host` instead, the bastion only relays TCP to `app-host`, and the database connection is made "from the remote machine", `app-host`, so `db.internal` must be reachable and resolvable from there.
- **Agent forwarding (`-A`)** "should be enabled with caution": anyone able to bypass file permissions on the remote host can use your loaded identities while you are connected, and the manual's "safer alternative may be to use a jump host". `ssh` exits with the remote command's status, or 255 if an error occurred, which matters when it wraps remote steps in a script.
- **Not executed.** The commands are shown and parsed (`-L 5433:db.internal:5432` into port, host and host port; `-J` into hops), never run: no `sshd` in the sandbox or CI.

### A hung job: /proc and strace

- **`/proc/<pid>/status`** has `State`, `Threads`, `Tgid`, `PPid`, `Umask` and the signal masks. **`wchan`** is the kernel symbol the process sleeps in; the name depends on the kernel (here `wait_woken` for the socket read on Linux 6.18, `anon_pipe_read` for a pipe read). **`fd`** says which file, pipe or socket each descriptor is (the reel's job: `4 -> socket:[…]`). **`stack`** is the kernel call chain (only with `CONFIG_STACKTRACE`; executed as root: `sk_wait_data`, `tcp_recvmsg_locked`). `/proc/<pid>/syscall` is the number of the system call it is inside, architecture-specific (0 is `read` on x86-64).
- **More of `/proc` for triage**: `fdinfo/<n>` has `pos`, "the file offset", which tells you progress through an input (executed: after reading 600 bytes it said `pos: 600`); `io` has `read_bytes` and `write_bytes`, the bytes "really fetched from" and "sent to the storage layer", so you can see whether they move (executed: both fields present); and `environ` is "the initial environment that was set when the currently executing program was started" (executed), so it does not show later changes.
- **`strace -p <pid>`** attaches and prints the call in progress; Ctrl-C detaches and leaves the process running, and a detach while the call is blocked prints `<detached ...>` after `read(4, ` (executed: the trace's only line was `read(4, <detached ...>`, with no closing bracket because the call never returned). It attaches only to the thread whose ID it is given (the main thread here, the one in `read`); `-f -p` "attaches to all of its threads", needed when a read is blocked in a worker thread. Useful options (all in `strace(1)`): `-e trace=network`, `-T` for call durations (`-tt` adds microsecond timestamps), `-y` to print paths next to fds, `-o file` to write the trace to a file, `-c` for a per-syscall summary. Tracing slows syscall-heavy processes: use it briefly on production jobs.
- **What to conclude.** `read(4,` on a socket with no sender: the other side is gone or silent. Find out which peer it is before you TERM: `ss -tnp` ("-p, --processes Show processes using sockets", `ss(8)`; not installed in the sandbox, so not run), `lsof -nP -p <pid>`, or match the socket's inode (`socket:[…]` in `/proc/<pid>/fd`) against the 10th field of a row in `/proc/net/tcp` (`tcp6` for IPv6; state `01` is ESTABLISHED) (executed: the reel's job's socket was an ESTABLISHED connection whose remote port was the port its own listening socket held). For a Python job, a Python-level stack dumper such as `py-spy dump --pid` is the usual next tool (named, not run or sourced). State `D` with `wchan` in a filesystem or block function: the storage, not the job (and signals wait). `R` at 100 % CPU: profile it, don't strace it.
- **Permission to look.** With Yama's `ptrace_scope` at 1 a process may attach only to its own descendants (unless the target declares a tracer with `prctl(PR_SET_PTRACER, …)`), at 2 only with `CAP_SYS_PTRACE`; container seccomp profiles can refuse `ptrace` too, so `strace -p` fails with `EPERM` for a job started by a sibling process. `/proc/<pid>/syscall` and `stack` need the same access as attaching; `status`, `wchan` and `fd` need only a read-mode check, so those three are the fallback. `examples.sh` has the job declare any tracer (`PR_SET_PTRACER_ANY`) so `strace -p` works under scope 1, and falls back to those three where ptrace is refused.

### Small things that bite

- **`rm` only removes a name.** A file is a reference-counted inode: if a process still holds it open, the data and its disk space persist until the last descriptor closes. Executed: after `unlink`, `/proc/self/fd/N` pointed at `… (deleted)` and the 1,000 bytes were still readable. That is why `df` shows a full disk that `du` cannot find: look for `(deleted)` targets under `/proc/<pid>/fd`.
- **Write a temp file, rename it over the final name.** `rename()` atomically replaces an existing target, so readers see the old file or the new one, never a partial one (executed with `os.replace`). That is atomic for readers, not durable after a crash: that needs `fsync` on the file before the rename and on the directory after it ("Storage devices and fsync durability", §1.2). It fails with `EXDEV` when the two paths are not on the same mounted filesystem (`rename(2)`; executed across `/dev/shm`), and then `mv` falls back on copying, "then ... removes the original" (coreutils manual; executed), which loses the atomicity, so put the temp file in the same directory.
- **Pipe writes smaller than `PIPE_BUF` are atomic** ("On Linux, PIPE_BUF is 4096 bytes", `pipe(7)`; executed: `getconf PIPE_BUF /` is 4096), while writes of more than that "may be nonatomic: the kernel may interleave the data with data written by other processes", so larger writes from parallel workers can tear lines.
- **`timeout 30 cmd`** is the standard guard on a step that can hang: it exits 124 on timeout (executed), or 137 if it had to send KILL (see above).

## In production

- **A nightly script that "succeeded" with an empty table.** A failed middle step and no `pipefail`: the status was the last command's, 0.
- **An error that never reached the log.** `2>&1` on the wrong side of the file redirection.
- **A job killed by the OOM killer.** The scheduler's log says 137: that is a SIGKILL from outside, not an exit code the job chose (the OOM killer itself is a later topic's).
- **143 from a scheduler's graceful stop**, and what the job did in its handler: it had until the grace period ended to flush, and it should then exit 143 (or re-raise TERM) so the scheduler records a stop, not a success.
- **A load job hung on a database socket for hours.** Keep-alives and statement timeouts are the fix (later chapters); the diagnosis is this topic's.
- **A `D`-state job on a dying disk.** Even KILL usually waits until the I/O returns; it is a storage problem.
- **Zombies filling a PID table** because a supervisor never waited.
- **A cron job that works from the shell and fails under cron.** `PATH`, `HOME`, a `%` in the command, a relative path.
- **A cron job starting on top of its previous run**, and a 02:15 job on the DST nights.
- **A tunnel that drops silently** (`ServerAliveInterval`), and a bastion key with the wrong permissions (ssh warns, ignores the key, and under cron then fails with 255).
- **A nightly job that "fails" with 141 under `pipefail`** because a `| head` closed the pipe early.
- **`grep -c` counting strings instead of values** (1,495 against 1,500).

## What's changing

- **`pipefail` is standard.** POSIX.1-2024 (Issue 8) added `set -o pipefail`, so portable scripts may use it; Debian's `dash` has it from 0.5.12-7 (2024), while this run's Ubuntu `dash` 0.5.12-6ubuntu5 lacks it, so check the runner's shell, not the upstream version.
- **systemd timers** are systemd's own scheduler, the alternative to cron on a host that runs systemd, and `Persistent=` closes one gap named under cron (one catch-up run, not a backfill of every missed one): "If true, the time when the service unit was last triggered is stored on disk. When the timer is activated, the service unit is triggered immediately if it would have been triggered at least once during the time when the timer was inactive" (`systemd.timer(5)`, Debian unstable; it "only has an effect on timers configured with OnCalendar="). Nothing more of systemd is claimed here; orchestrators (Chapter 11) are the next step up.
- **Bash 5.3** is the current manual (the examples ran on 5.2.21); **jq 1.8** is the current manual and 1.8.2 the current release (the examples ran on 1.7; nothing used is 1.8-only, and `trim`, new in 1.8.0, is avoided: the examples trim in awk); **procps-ng 4.0.7** documents `ps` (the runner has 4.0.4); **strace 7.2** (the runner has 6.8); **coreutils 9.12** upstream (Debian's 9.10 pages are quoted).
- **`wchan` names change between kernel versions**, which is why the reel's value is a label for the idea, not a constant to match on.
- Nothing here changes the mechanisms; the versions are stated so the fact-check can re-run them.
