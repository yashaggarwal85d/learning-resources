## Learning outcomes ("After this refresher you can")

1. Review a change against explicit norms: take the broad view, then the design of the main part first, then tests, naming and the rest; keep PRs small (about 100 lines is reasonable, 1,000 usually too large); reply within one business day; approve once the change definitely improves code health, marking polish as "Nit:".
2. Write a unit test that pins a data bug: plain `assert`, one parametrized case per bad spelling, a fixture for a fresh input file, and check that the test fails on the broken code (here 4 failed, 2 passed on commit 731's `clean()`).
3. Read a CI pipeline as a chain of exit statuses: each step is a new shell whose exit status is its verdict, the first non-zero one fails the job and skips the steps after it, a required status check blocks the merge, and `shell: bash` (not the default shell) adds `pipefail`.
4. Spot a flaky test (same code, different verdicts) and fix its cause (uncontrolled state) instead of re-running it.
5. Decide a version bump from what changed (fix → PATCH, compatible addition → MINOR, renamed output column → MAJOR; 0.y.z promises nothing), and know that a published version's contents never change.
6. Pin dependencies so a build is reproducible: a range in a library (`>=1.4,<2` or `~=1.4`), exact pins with hashes in an application, and say what a lock file guarantees (the same versions and the same bytes on every install) and what it doesn't (that those versions are correct, or the same file on every platform).

### Step 9 · "A lock file freezes the tree"

- **The idea:** freeze the cinnamon branch. The application's lock line names one version and the sha256 of one file; the tree turns crema and rigid.   - **### Semantic versioning**: MAJOR.MINOR.PATCH and the three rules (incompatible API change, backward compatible functionality, backward compatible bug fix; lower numbers reset); declare a public API first (for a data library that includes the documented output columns, so `shopclean`'s rename is MAJOR; executed: the consumer's `KeyError: 'status'`); released contents never change; 0.y.z is initial development ("Anything MAY change at any time"), 1.0.0 defines the API ("If your software is being used in production, it should probably already be 1.0.0"); deprecate in a minor release before removing in a major; an accidental breaking minor release is fixed by a new minor release that restores compatibility, never by changing the released one; precedence is numeric per part (1.9.0 < 1.10.0; executed: text sort puts 1.10.0 first) and pre-releases sort before the release (1.0.0-alpha < 1.0.0); "v1.2.3" is not a semantic version; too-tight specifications cause version lock, too-loose ones version promiscuity. Python's versions follow PEP 440, which is compatible with semver's MAJOR.MINOR.PATCH but spells pre-releases differently: the normal form is `1.0.0rc1`; PEP 440 tools accept `1.0.0-rc.1` and normalise it to `1.0.0rc1` (executed with `packaging` 26.3), but a semver pre-release such as `1.0.0-x.7.z.92` is invalid, and a `+build` suffix becomes a PEP 440 local version label, which "SHOULD NOT be used when publishing upstream projects to a public index server".
  - **### Ranges, pins and lock files**: PEP 440 specifiers (comma = and; `~=` compatible release: `~=1.4` = `>=1.4, ==1.*`, `~=1.4.5` = `>=1.4.5, ==1.4.*`; `==` strict, `.*` prefix; pre-releases excluded unless already installed, asked for, or the only match; pip followed the "only match" clause only from 26.0 (changelog: "package>1.0 with versions 1.0, 2.0rc1 now installs 2.0rc1 instead of failing"; executed: `shopclean>=1.4` with only 2.1.0rc1 on the index installs nothing on pip 24.0 and 2.1.0rc1 on pip 26.2.1). Executed table: which of 1.4.0, 1.4.9, 1.5.0, 2.0.0 (and 0.4.2, 0.5.0) each of `>=1.4`, `>=1.4,<2`, `~=1.4`, `~=1.4.0`, `~=0.4`, `~=0.4.0`, `==1.5.0` admits; the 0.y.z trap: `~=0.4` admits 0.5.0, although under 0.y.z anything may change. Who uses which: a published library declares a range (PEP 440: `==` in published dependencies is "strongly discouraged" because it blocks security fixes); an application deployed repeatedly pins with `==` (PEP 440: what `==` is "intended primarily for"; pip: pinning "protects you from bugs or incompatibilities in newly released versions"). pip's three levels of repeatability: pins (`pip freeze` pins transitive dependencies too; `--no-deps` as insurance), hash-checking (defends against a compromised index or certificate chain and a re-published file), a wheelhouse (offline, but OS- and architecture-specific). Hash-checking mode: any `--hash` turns it on for every requirement; every requirement must be hashed, transitive ones included (executed on pip 24.0 and 26.2.1: an unhashed requirement is refused, and a lock with `pluggy` deleted is refused with "must have their versions pinned with =="). The docs also say every requirement must be pinned with `==`, "to prevent a surprising hash mismatch upon the release of a new version", but only older pip enforces that for a hashed line: executed, `shopclean>=1.4 --hash=<1.5.0's>` is refused by pip 24.0 for the missing pin, while pip 26.2.1 accepts the range, resolves the newest version and refuses 2.0.0 for the hash mismatch (and installs 1.5.0 from last week's index). Write `==` yourself; don't rely on pip to demand it; sha256 recommended, md5/sha1/sha224 refused; several hashes per package for several platform wheels; the index's own `#sha256=` guards only against corruption, not tampering; `--only-binary :all:` so no build code runs; a lock with hashes is generated with pip alone by `pip install --dry-run --ignore-installed --report` (the report carries each file's sha256) or `pip hash` on downloaded files (executed: both give `c939baf79b61…`, equal to `sha256sum`). pip's own caveat: the report "is not meant to be a lock file format as such", and it records the environment it was resolved for, which is why a lock made from it fits only that kind of environment. What a lock guarantees: the same versions and the same bytes on every machine that can install them. What it doesn't: that those versions are bug-free or safe (it freezes yesterday's bugs too: update it on purpose, in a reviewed PR, with the tests as the gate), that the same file exists for every platform (one hash per wheel), that the same set of packages applies on every Python (executed: this lock is refused on Python 3.10, where pytest 9.1.1 also needs `exceptiongroup` and `tomli`), or the interpreter and system tools (the runner image). "Works on my machine": the laptop resolved last week, CI resolves today (executed).
