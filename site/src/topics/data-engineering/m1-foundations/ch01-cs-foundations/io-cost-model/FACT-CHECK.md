### The model
1. The external-memory model (also "I/O model", "disk access machine / DAM") was introduced by Alok Aggarwal and Jeffrey Scott Vitter, "The Input/Output Complexity of Sorting and Related Problems", Communications of the ACM 31(9), September 1988, pp. 1116–1127.
2. In that model: N = number of records in the problem, M = number of records that fit in internal memory, B = number of records per block; an I/O moves one block (the paper also has P blocks transferred concurrently; P = 1 is the single-disk case). Computation in internal memory is free; cost = number of I/Os.
3. Scanning N records costs Θ(N/B) I/Os.
4. Sorting N records costs Θ((N/B) · log_{M/B}(N/B)) I/Os (the paper states it as Θ((N/B) · log(1+N/B) / log(1+M/B)) with P=1), and this is a lower bound for comparison-based sorting in the model, matched by external merge sort.
5. Permuting N records costs Θ(min(N, (N/B) log_{M/B}(N/B))) I/Os — i.e. for typical parameters, permuting is as hard as sorting.
6. A B-tree search costs Θ(log_B N) I/Os (B-tree: Bayer & McCreight, 1972, Acta Informatica 1).
7. Parallel disk model: Vitter & Shriver, "Algorithms for parallel memory I: Two-level memories", Algorithmica 12 (1994).
8. Cache-oblivious algorithms: Frigo, Leiserson, Prokop, Ramachandran, "Cache-Oblivious Algorithms", FOCS 1999 — algorithms that are optimal in the I/O model without knowing M or B.
9. Bender et al., "Small Refinements to the DAM Can Have Big Consequences for Data-Structure Design", SPAA 2019, introduces the affine model and the PDAM (parallel DAM) to capture that SSDs serve many I/Os in parallel and that an I/O's cost grows with its size (setup cost + per-byte cost). Check exact author list and venue/year.

### Worked numbers (arithmetic — check)
10. 100 million rows, 100 rows per page → 1,000,000 pages. A full scan = 1,000,000 page reads.
11. If 2% of rows (2,000,000 rows) match, and matches are spread uniformly at random, the expected fraction of pages holding at least one match is 1 − 0.98^100 ≈ 86.7%.
12. Unclustered index: ~1 random page read per matching row (ignoring caching) → 2,000,000 reads vs 1,000,000 for the scan. Crossover (all page reads equal cost) at a selectivity of about 1/B = 1/100 = 1%.
13. If a random page read costs r times a sequential one, the crossover moves to about 1/(r·B); with r = 4 and B = 100, about 0.25%.
14. Clustered (table physically ordered by the key): matching rows are contiguous, cost ≈ k/B pages, so an index range scan beats a full scan at any selectivity below 100% (plus a few index pages).
15. External sort, 1 TiB data, 16 GiB memory, 1 MiB blocks: run formation produces 1 TiB / 16 GiB = 64 sorted runs; merge fan-in up to M/B − 1 = 16,383 ≥ 64, so one merge pass; total 2 passes over the data (read+write each pass). With 2-way merging instead: log2(64) = 6 merge passes, 7 passes total.
16. Replacement selection produces runs of expected length 2M on randomly ordered input (Knuth, TAOCP Vol. 3, §5.4.1).
17. Halving memory to 8 GiB: 128 runs, fan-in 8,191 → still 2 passes.
18. Quiz: 50M rows, 50 rows/page → 1M pages; unclustered index query returning 400,000 rows → 400,000 random reads (< 1M, index wins if all reads cost the same); with r = 4 → equivalent of 1.6M sequential reads (> 1M, scan wins).
19. Quiz: 4 TiB, 8 GiB memory, 8 MiB blocks → 512 runs, fan-in 1,023 → one merge pass → 2 passes.

### PostgreSQL
20. PostgreSQL's planner cost settings: seq_page_cost default 1.0, random_page_cost default 4.0 (check the current docs, PostgreSQL 18, "Planner Cost Constants").
21. The docs explain that random access to mechanical disk is normally much more expensive than 4× sequential, and 4.0 can be thought of as modeling random access as 40× slower than sequential while expecting 90% of random reads to be cached; and that SSD-like storage may be better modeled with a lower value such as 1.1. Quote the exact current wording.
22. PostgreSQL's default block (page) size is 8 kB (BLCKSZ).
23. In PostgreSQL's cost_index() (src/backend/optimizer/path/costsize.c) the I/O cost of an index scan interpolates between a best case (perfectly correlated, min_IO_cost) and worst case (uncorrelated, max_IO_cost) using the square of the index correlation (pg_stats.correlation): csquared = indexCorrelation^2; run_cost += max_IO_cost + csquared * (min_IO_cost - max_IO_cost). It uses the Mackert–Lohman approximation (index_pages_fetched) to estimate pages fetched accounting for cache (effective_cache_size).
24. PostgreSQL's bitmap heap scan collects matching TIDs from the index into a bitmap and then visits heap pages in physical order, each page at most once — a middle ground between an index scan and a sequential scan. (Docs: "Using EXPLAIN", or the planner docs.)
25. pg_stats.correlation: "Statistical correlation between physical row ordering and logical ordering of the column values. This ranges from -1 to +1."
26. PostgreSQL 18 added asynchronous I/O (io_method setting: worker, io_uring, sync), which affects sequential scans, bitmap heap scans and vacuum.

### Hardware numbers (order of magnitude; give a primary or authoritative source)
27. CPU cache line: 64 bytes on current x86-64 (and most ARM server) CPUs.
28. DRAM access latency ≈ 100 ns order of magnitude.
29. NVMe SSD random 4 KiB read latency: tens of microseconds (≈10–100 µs).
30. HDD (7,200 rpm): average rotational latency 4.17 ms (half of 8.33 ms per revolution); random 4 KiB reads total ≈ 5–10 ms with seek, i.e. on the order of 100–200 random IOPS, while sequential throughput is on the order of 100–250 MB/s.

32. Linux default page size on x86-64: 4 KiB.
