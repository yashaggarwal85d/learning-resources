## Learning outcomes ("After this refresher you can")

1. Say what merge and rebase each do to the commit graph (a merge commit with both parents vs. replayed commits with new IDs and a straight line), show that both can end with the same files, and pick one: rebase your own unpushed work, merge or rebase-and-merge what is shared.
2. Clean up a branch before you push it (`rebase -i`, `--fixup` + `--autosquash`, `drop`, `reword`), and undo a rewrite from the reflog.
3. Resolve a conflict knowing what the three versions are (base, ours, theirs), with the base on screen (`zdiff3`), and know that ours and theirs swap during a rebase.
4. Find a regression in about log₂ N test runs with `git bisect run` and a failing test as the oracle, and write that oracle with the right exit codes (0 good, 1–127 bad except 125, 125 skip, anything else stops the run).
5. Choose how a PR lands (merge commit, squash, rebase-and-merge) and what each does to history, and explain why trunk-based development with short-lived branches avoids the repeated conflicts of long-lived ones.

### Step 3 · "Clean up before you push"

- **The idea:** the todo list *is* the interface; show the real one Git proposed, and watch it edit itself into a clean history: the fixup line jumps up under its target and changes its verb, the debug commit is dropped, and four dots collapse into two. Then the ghost of the old branch, one reflog entry back, which is what makes rewriting safe.
- **Portrait:** `Stack`: a `Code` panel titled `git rebase -i --autosquash main` with 4 lines (the real todo after autosquash, with the drop applied on beat 2), then `Svg fill` below (h≈200) with the commit dots.
  - Code lines (real, from `examples.sh`):
    ```
    pick  5f14405 add email check
    fixup 84e21ce fixup! add email check
    drop  3d6cce4 wip debug print
    pick  dad1c0d test email check
    ```
    Beat 0 shows the four commits as they were made (`pick` ×4, fixup line third, `wip` second); beat 1 the fixup line slides up and its verb becomes `fixup` (highlight); beat 2 `pick` → `drop` on `wip debug print` (struck through, `C.cherryText`). Honesty note (FACT-CHECK F9): beat 0 is the commit order (`git log`), not a screen Git shows; with `--autosquash` the todo Git opens already has beat 1's order and verb, so label beat 0 "as committed" and beat 1 "what Git proposes". The line format (`fixup <id> fixup! …`) is the same in Git 2.43 and 2.56 (sequencer source).
  - Svg: four crema dots in a row (x = 90, 210, 330, 450) → collapse into two caramel dots `bf1d3f6 add email check`, `81f8447 test email check` (IDs 15 units, messages 13 units on a second line). Big label "4 → 2" (Fraunces 24, caramel) at the right. Then one taupe dashed row below: `emails@{1}` → "the 4 old commits" (13 units).
  - Landscape: code panel and drawing side by side is *not* needed; keep the stack (fits).
- **Beats:** 0.2 code lines arrive (0.15 s apart); 1.0–1.6 fixup line moves up + verb flips; 1.9–2.3 drop; 2.5–3.2 dots collapse 4 → 2 (the fixup dot merges into the first, the wip dot fades out); 3.5 reflog ghost row fades in.
- **Values:** IDs above; counts `4` and `2`; `emails@{1}`.
- **Final frame:** the edited todo list, two caramel dots, "4 → 2", the reflog ghost row.
- **Caption:** "Before you push, rewrite freely. `git rebase -i` lets you reorder, `reword`, `squash`, `fixup` and `drop` commits. ### Step 4 · "Conflicts: base, ours, theirs"

- **The idea:** a conflict is three versions of the same lines. Show them as three cards, numbered by the index stage that holds them (1 base, 2 ours, 3 theirs), flying into the file in the order the `zdiff3` markers lay them out. The learner sees why the base matters: without it you can't tell which side changed what.
- **Portrait (`Svg h≈440`):**
  - Top: three small cards stacked (x 30–570, each 46 units tall, 10 apart), each with a stage badge on the left (Fraunces 18: `1`, `2`, `3`) and one line of real code (15 units, mono):
    - `1 base` → `return email.strip()` (latte)
    - `2 ours · HEAD (lower)` → `return email.strip().lower()` (crema)
    - `3 theirs · casefold` → `return email.strip().casefold()` (caramel)
  - Bottom (y 200–430): the file box `clean.py` with the real conflicted text (13–14 units, no indentation shown beyond 2 spaces):
    ```
    <<<<<<< HEAD
      return email.strip().lower()
    ||||||| 0fd676d
      return email.strip()
    =======
      return email.strip().casefold()
    >>>>>>> casefold
    ```
    Marker lines in taupe; each code line in its card's colour.
  - Landscape: same layout (cards on top, file below); the canvas fits.
- **Beats:** 0.2 / 0.6 / 1.0 the three cards arrive; 1.5–2.4 each card's line flies down into its place (ours first, then base under `|||||||`, then theirs under `=======`), markers fade in around them; 2.8 the block collapses to one line, `return email.strip().casefold()` (caramel), with a footer line "edit → git add → git merge --continue" (taupe 13).
- **Values:** stages `1 2 3`; merge base `0fd676d`; the real lines; merge result has `2` parents (Deep dive).
- **Final frame:** the three cards and the resolved file with the footer. (Keep the marker version visible as a faded ghost behind the resolved line, so a paused learner still sees what the markers looked like.)
- **Caption:** "When both sides change the same lines, Git stops and keeps three versions: the common ancestor, yours, and theirs. Set `merge.conflictStyle` to `zdiff3` and the file shows the ancestor too, so you can see what each side changed. Edit, `git add`, then `--continue`, or `--abort` to back out. ### Step 5 · "bisect halves the suspects" (predict)

- **The idea:** a thousand commits as one long strip, and a window of suspects that halves with each test. The count falls 499, 249, 124 … 0 and the number of tests stops at 10. The surprise is how few tests that takes: the binary search is the point of the step.
- **Question frame, portrait (`Svg h≈360`):**
  - A horizontal strip (x 30–570, y≈170, 26 tall) made of 1,000 thin ticks (or a `Bar` with a fine tick texture), left end crema, right end cherry.
  - Left label: "commit 1 · test passes" (latte 13, below the strip, start-anchored at x 30); right label "commit 1,000 · test fails" (`C.cherryText` 13, end-anchored at x 570). These two labels sit on separate lines (y 210 and y 236) so they can't meet on a phone.
  - Above the strip: "?" (Fraunces 28, caramel), centred.
  - Landscape: same.
- **Predict:** "Somewhere in 1,000 commits, a change broke the cleaner's test. How many test runs does `git bisect` need to find it?"
  - Options: **"About 10"** (correct) · "About 32" · "About 500" · "About 1,000".
  - Explain: "10. Each test halves the suspects: 1,000 commits need about log₂ 1,000 ≈ 10 tests (9 or 10, depending on where the bug sits). Checking the 999 suspects one by one could take 998."
  - Why 998, not 999 (FACT-CHECK F11): commit 1 is known good and commit 1,000 known bad, so the first bad commit is one of 999 (commits 2–1,000); walking them in order you never need to test the last one, so the linear worst case is 998 tests. The draft's option "999" became "About 1,000" (the one-by-one intuition), so the explanation's exact 998 doesn't read as a nitpick against an option. Could a wrong option be right? "About 32" (√1,000) and "About 500" (the linear average) never match bisect; on a linear history every culprit position took 9 or 10 (F12); only many skipped commits or merge-heavy history add steps, not to 32.
- **Answer frame:** a caramel window over the strip starts full-width and shrinks on each beat to the real path bisect took: tested commits 500 good, 750 bad, 625 good, 687 good, 718 good, 734 bad, 726 good, 730 good, 732 bad, 731 bad. Each tested commit leaves a small tick above the strip (crema = good, cherry = bad). A counter top-left (17 units, crema) steps "test 1 · 499 left" → … → "test 10 · 0 left" (the real "revisions left to test" values: 499 249 124 62 31 15 7 3 1 0). Final: the window is one commit at 73.1 % of the strip with a caramel pin and its label on two lines: `784d178` (17 units) and "clean: simplify normalisation" (13 units); and the one big number "10 tests" (Fraunces 26, caramel), with "one by one: up to 998" (taupe 13) under it.
- **Beats (from the answer):** ten beats, 0.35 s apart (3.5 s), then the pin and the big number at 3.8 s. Optional interactivity (Rule #1): tapping the drawing advances one test at a time; if built, it must still finish on its own.
- **Values:** 1,000; 10; 499 … 0; 731; `784d178`; tested positions above; 999 suspects (`suspects` in `examples.sh`); 998 (linear worst case, `suspects - 1`).
- **Final frame:** strip with ten verdict ticks, the pinned commit, "10 tests".
- **Caption:** "`git bisect` is a binary search through history. Mark one commit good and one bad; it checks out the middle, you test it, and every answer halves the suspects. A thousand commits: how many tests until the first bad commit?"
- **Duration:** 1.2.

### Step 6 · "bisect run: the test is the oracle"

- **The idea:** `git bisect run` hands each checkout to your test and reads only one thing back: the exit code. Draw the code as a number line 0–255 cut into bands, and drop a marker on it for each kind of answer. Learners remember the bands (and the one odd value, 125) far better than a table.
- **Portrait:** `Stack`: `Code` (2 lines) above `Svg fill`:
  ```
  $ git bisect run python3 ~/test_clean.py
  784d178… is the first bad commit
  ```
  (Real: `examples.sh` runs exactly this command, with the test file outside the repo as the docs advise, and the run found `784d178`. Git prints the full 40-character ID; the panel shortens it to 7 and shows "…" so it doesn't pass for verbatim output. Wording is Git 2.43's; Git 2.55+ prints "is the first 'bad' commit", the term in quotes (FACT-CHECK F13; `bisect.c` at v2.43.0 vs v2.56.0).)
  - Svg (h≈220): a bar from x 30 to 570 representing 0–255 (scale 540/256 ≈ 2.1 units per code), with bands: `0` a narrow crema band at the left, label "0 good" above; `1–127` cherry fill, label "1–127 bad" above (cherryText); a notch at `125` in taupe with a pin label below "125 skip: can't test this one"; `128–255` dark (`C.void` with mocha outline), label "128–255 stops the run" below. Labels alternate above and below the bar so no two share a line.
  - Landscape: same stack.
- **Beats:** 0.2 code lines; 0.8 bar and bands draw left to right; 1.6 a crema marker drops on 0 ("an old commit: the test passes"); 2.2 a cherry marker drops on 1 ("a failing assert exits with 1"); 2.8 a taupe marker on 125; 3.4 a marker on 255 with a small "✕ abort".
- **Values:** 0, 1, 125, 127, 128, 255; `784d178`. (All asserted: exit 0 / 1 / 125 / 128 / 255 behaviours are executed in `examples.sh` on a 16-commit repo.)
- **Final frame:** the banded bar with the four markers and the code above.
- **Caption:** "Give `git bisect run` a command and it tests every step for you. Exit 0 means good, 1 to 127 means bad, except 125, which means 'can't test this one, skip it'. Anything else stops the bisect. A test that fails only because of the bug makes the ideal oracle; keep it outside the repo, so checking out old commits can't change it."
- **Red team (FACT-CHECK F15):** a Python oracle exits 1 for *any* uncaught exception (an `ImportError` on an old commit is read as "bad"), and `python3 -O` / `PYTHONOPTIMIZE` strip `assert`, so a broken commit "passes" (exit 0). Both executed. The Deep dive says: exit 125 when the test can't run, and never run an assert-based oracle with `-O`.
- **Duration:** 3.8.

### Step 7 · "Three ways to land a PR" (predict)

- **The idea:** the same three-commit PR landing on `main` three ways, in three lanes, so the difference is visible in one glance: a merge node, one squashed dot, or three new dots. Then the trap: reuse a squash-merged branch and the next PR drags the old commits back.
- **Question frame, portrait (`Svg h≈430`):** three lanes, each 120 tall:
  - Lane 1 "Merge commit" (title crema 15): `main` line; three crema dots on an arc joining a merge dot (caramel ring); right label "2 parents · commits kept" (latte 13).
  - Lane 2 "Squash and merge": `main` line with one caramel dot `Dedupe rows (#12)`; the three crema dots fade to taupe dashed above it; right label "1 commit · 1 parent".
  - Lane 3 "Rebase and merge": `main` line extended by three caramel dots; right label "3 new commits, new IDs".
  - Right labels sit on their own line under each lane title (not beside the dots) to avoid collisions at phone scale.
  - Landscape: same lanes.
- **Predict:** "You squash-merged the PR. Then you add one commit to the same branch and open a new PR. How many commits does it show?"
  - Options: "1" · **"4"** (correct) · "0" · "2: the squash and the new one".
  - Explain: "4: the squash commit isn't made of your three commits, so Git still sees them as unmerged, and the new PR shows them again with the new one. Here it also conflicts: merging or rebasing that branch onto `main` stops in `dedupe.py`. After a squash merge, start a fresh branch from `main`."
  - Why the fourth option changed (FACT-CHECK F17): the plan's "A conflict, nothing to show" was half right. In this exact scenario merging the reused branch into `main` *does* conflict (add/add in `dedupe.py`, executed), so GitHub would flag the PR as conflicted while still listing its 4 commits. A wrong option must be wrong in every reading.
- **Answer frame:** portrait swaps lanes for one enlarged lane 2 (python-essentials' panel-swap pattern): `main` with the squash dot `#12`; the branch with its three old dots (cherry outline, label "already in main as #12", cherryText 13) and one new caramel dot; a bracket over all four: "next PR: 4 commits, 1 new" (crema 17); below it "merge or rebase onto main → conflict: dedupe.py" (taupe 13).
- **Beats:** lanes arrive 0.4 s apart (question frame); on answer: 0.0–0.6 lane 2 grows to full height, others fade; 0.8 new dot pops; 1.2 bracket draws; 1.6 old dots turn cherry-outlined; 2.0 conflict line.
- **Values:** 2 parents; 1 commit / 1 parent; 3 new commits; 4 commits, 1 new; `dedupe.py`; `#12` (the commit message).
- **Final frame:** the enlarged lane with the bracket and the conflict line (portrait); landscape may keep the three lanes small on the left and the enlarged lane on the right if it fits without crowding; otherwise use the portrait layout.
- **Caption:** "A pull request asks for review and CI before a branch lands. GitHub can land it three ways: a merge commit keeps every commit; squash makes one commit; rebase-and-merge replays them as new commits in a straight line. Squash suits short-lived branches. What happens if you keep using the branch after a squash?"
- **Duration:** 1.6.

### Step 8 · "Short-lived branches, one trunk"

- **The idea:** branch *length* is the risk. Above, a trunk with many tiny branches that leave and rejoin within moments; below, one long-lived branch running beside the trunk while the gap between them (shaded) widens, until its merge back throws a cluster of conflict sparks. No numbers: the shape is the lesson.
- **Portrait (`Svg h≈400`):**
  - Top half (y 40–170): title "trunk-based" (crema 15); a crema trunk line x 30–570 at y≈120; six small latte arcs, each leaving and rejoining within about 60 units, each rejoin a small dot; label under the line "short-lived PR branches: review + CI, then merge" (latte 13).
  - Bottom half (y 220–390): title "long-lived branch" (crema 15); a trunk line at y≈260 and a branch leaving at x≈60 and running at y≈330 to x≈520, the area between them filled cherry at low opacity, widening to the right (the trunk keeps moving: small dots on it); at x≈520 the branch curves back up into the trunk with five cherry sparks; label "merge hell" (`C.cherryText` 15) under the sparks.
  - Landscape: same.
- **Beats:** 0.2 both trunk lines draw; 0.5–2.3 the short arcs appear one by one, 0.3 s apart; 0.8–2.6 in parallel the long branch extends and the wedge widens; 2.9 merge back + sparks.
- **Values:** none on screen (the caption says "at least daily", sourced; no digits).
- **Final frame:** both halves complete, sparks visible.
- **Caption:** "Trunk-based development: everyone merges into one branch, the trunk, at least daily, through short-lived PR branches that exist for review and CI. Bigger changes still land in small steps, with feature flags and branch by abstraction; releases are cut from the trunk just in time, or shipped from it with fixes forward. A long-lived branch drifts: the longer it lives, the bigger the merge, and the same conflicts come back again and again."

## Deep dive (`index.mdx`)

Sections in the Python essentials pattern (`data-section` names), plus a frontier section:

- **outcomes — "After this refresher you can"**: the five outcomes above.
- **internals — "A little deeper"**
  - **### Commits, IDs and the graph**: a commit names its tree and its parents (plus author, committer, message), and its ID is a hash of all that, so changing the parent changes the ID (executed with `git commit-tree`: same tree, message and dates, different parent, different ID; in step 2 the tree changed too, since the replayed commits also contain `main`'s files). A real rebase also stamps the current time as committer date while keeping the author date (git-rebase, `--committer-date-is-author-date`); `examples.sh` pins the dates, which is why its IDs are reproducible. History is a graph of parent links; a merge commit is the node with two parents. `git log --first-parent` follows main's own line (4 commits in the merged example, 7 in all).
  - **### Merge and rebase, precisely**: fast-forward vs true merge (`--ff` fast-forwards when it can and merges otherwise, `--no-ff` always makes a merge commit, and only `--ff-only` refuses, exiting non-zero, when a fast-forward isn't possible); the merge commit's parents; rebase's algorithm (list the commits not already upstream, detach at upstream, replay one by one like cherry-pick, move the branch); "equivalent commit" = same patch-id, which is why rebasing after upstream already took your patch skips it, with a "skipped previously applied commit" warning (executed; `--reapply-cherry-picks` turns this off), and why it does *not* help when upstream changed the patch, for example squashed it with others (Pro Git: "This only works if C4 and C4' that your partner made are almost exactly the same patch."); a rebase onto where the branch already sits replays nothing (IDs unchanged), while `--force-rebase`/`--no-ff` replays every commit with a new committer date, hence new IDs (executed; with this script's pinned dates `-f` rebuilds identical commits, so don't demo it without a new date); `--onto` to transplant part of a branch; `--rebase-merges` vs the default of dropping merges; `git pull --rebase` (and `pull.rebase`). Same files, different history: the two results in step 2 have the same tree, when conflicts (if any) are resolved the same way. History as a record vs history as a story (Pro Git).
  - **### Rewriting history safely**: the interactive verbs (`pick`, `reword`, `edit`, `squash`, `fixup`, `fixup -C`, `drop`, `break`, `exec`); `--fixup`/`--squash` commits and `--autosquash` (and `rebase.autoSquash` for interactive rebases); `[version]` `--autosquash` without `-i` works from Git 2.44 (release notes) and is silently ignored on 2.43 (executed: the fixup commit stays), so the reel always shows `-i --autosquash`; `-x/--exec` to run the tests after every rewritten commit, so every commit is bisectable (executed: ran once per commit; with `--autosquash`, only after each fixup series); `--update-refs` for stacked branches; author of a squashed commit; the golden rule (never rewrite commits others may have based work on: they must repair their history, and rewriting pushed commits needs a force push); recovery: `ORIG_HEAD`, `branch@{1}`, `HEAD@{2}`; the reflog is local only, entries expire after 90 days by default, entries no longer reachable from the branch after 30 (`gc.reflogExpire`, `gc.reflogExpireUnreachable`; executed: a lost commit 31 days old is gone after `git reflog expire`, 29 days old it is still there). "Expire" means *eligible for pruning*: entries are removed when `git reflog expire` runs, normally via `git gc` (git-reflog: "This is typically not used directly by end users — instead, see git-gc[1]."), so say "kept for at least 30 days", not "deleted on day 30"; recovering from an upstream rebase (`git rebase --onto subsystem subsystem@{1}`, the hard case).
  - **### Conflicts**: the three index stages (`git ls-files -u`, `git show :1:path` etc.), conflict markers and the `diff3`/`zdiff3` styles (the default doesn't show the base); `git merge --continue` / `--abort` (and that `--abort` may not restore uncommitted changes present before the merge); rebase stops at the first conflicting commit, `--continue`/`--skip`/`--abort`; ours/theirs swapped during rebase (executed: stage 2 is the upstream, stage 3 your commit; and at your second commit "ours" already contains your first, replayed: it is "the so-far rebased series, starting with <upstream>"; the same reversal applies to `-X ours`/`-X theirs` in a rebase); `git rerere` (enable `rerere.enabled`; records and replays resolutions; leaves the index alone, so you still check and `git add`; executed).
  - **### Bisect**: the algorithm (binary search over the good..bad range; "roughly N steps"; 1,000 linear commits took 10 tests in `examples.sh`, and 9 or 10 for every culprit position tried in the fact-check; merges and skips can add steps); `refs/bisect/bad`; `git bisect reset`; `skip`, and that skipping a commit adjacent to the culprit leaves several candidates (executed: 3); several good commits and a pathspec to shrink the range; `--first-parent` to blame the merge rather than a broken commit inside a merged branch (executed); `--no-checkout`; alternate terms (`old`/`new`) for finding a fix instead of a regression; `bisect log`/`replay`. **bisect run exit codes in full:** 0 good, 1–127 bad except 125, 125 skip, anything else (128–255, and `exit(-1)` which shows as 255) aborts (executed: the message "is < 0 or >= 128"; a crash by signal, such as a segfault's 139, aborts too). Exit statuses are taken modulo 256 ("chopped with & 0377"), so a script's `exit 256` reads as 0, good. 125 was chosen because 126 and 127 are the shells' "not executable" and "command not found"; if the very first test exits 126 or 127, Git re-runs it on the good commit and stops when that fails the same way (executed on 2.43 for both codes; not in the docs, but in Git's source at both v2.43.0 and v2.56.0, `builtin/bisect.c`: "Exit code 126 and 127 can either come from the shell … Check with a known-good revision to avoid trashing the bisect run due to a missing or non-executable script"). The message is "bogus exit code 127 for good revision" on 2.43 and "bogus exit code 127 for 'good' revision" from 2.55 on. **The oracle, red-teamed:** in Python *any* uncaught exception exits 1, so an `ImportError` on an old commit counts as bad (exit 125 when the test can't run); `python3 -O` or `PYTHONOPTIMIZE` strips `assert`, so a broken commit passes (both executed). Keep the test script outside the repository. `[version]` `--reset-when-found` is new in Git 2.56.0 (release notes; absent from 2.43's `git bisect -h` and source).
  - **### Landing a pull request**: GitHub's three strategies: merge commit (uses `--no-ff`, keeps every commit, explicit merge point), squash and merge (one commit, landed as a fast-forward, intermediate commits not kept), rebase and merge (each commit added individually, linear, always new IDs and new committer information, unlike `git rebase` onto an ancestor; drops originally-empty commits). Squash works best for short-lived branches; reusing the branch brings the old commits back and repeated conflicts (executed: 4 commits, 1 new; both merging and rebasing it onto `main` conflict in `dedupe.py`, so GitHub would also flag the PR as conflicted; `git branch -d` refuses: "not fully merged"); for long-running branches use a merge commit or rebase before the next PR. Nuance (executed): when the squashed PR had a single commit, the squash has that commit's patch-id, so rebasing the reused branch drops the old commit cleanly; with several commits the combined patch matches none of them and the rebase conflicts. Whether a *merge* conflicts depends on what the new commit touches (a new commit in an unrelated file merged cleanly in the fact-check, though the PR still listed the old commits). Indirect merges (a PR marked merged when its commits reach the base another way, even if its branch protection wasn't satisfied).
  - **### Branching models**: trunk-based development (one trunk, no long-lived development branches; PR branches short-lived, for review and CI; commit to trunk at least once every 24 hours (the site gives this as "the core requirement of Continuous Integration"); feature flags and branch by abstraction for longer changes (and flags for "hedging on the order of releases"); release branches cut just in time or release from trunk and fix forward) vs GitFlow and other models with long-running branches; why long-lived branches hurt (repeated conflicts: rerere's own description; squash merges don't suit them).

### Commits and IDs

### Merge vs rebase (step 2)
