## Into the internals

The page cache (last topic) hid the device so well that a `write()` returning success tells you almost nothing about durability. This topic goes under the cache: what makes a real device fast or slow, and the exact sequence of calls it takes for a write to survive a power cut. We keep the chapter's cost shape **T(n) = α + n/β**: α is the fixed latency of one I/O, β its streaming bandwidth. The crossover size **α·β** (latency × bandwidth) is where waiting equals transferring: below it you are latency-bound and must batch or add concurrency; above it you are bandwidth-bound. The running example is the loader writing the `orders` table (1,000,000 pages of 8 KB, about 7.6 GiB) into PostgreSQL and compacting `order_events` to Parquet; its write-ahead log is where fsync earns its keep.

### Sequential vs random, and why the gap outlives the disk head

On a **hard disk** a read costs three things in series: a *seek* (moving the head to the right track, several ms), *rotational latency* (waiting for the sector to come under the head — half a rotation on average, which at 7,200 rpm is 4.16 ms), then the *transfer*. A random 4 KiB read therefore costs on the order of several ms and the drive manages only a couple of hundred of them per second, even when it reorders a queue of requests; a 7,200 rpm enterprise drive is quoted at about 168 random 4K read IOPS at queue depth 16, against roughly 285 MB/s streaming sequentially (Seagate Exos datasheet). That is a random-to-sequential throughput gap near three orders of magnitude, and it is pure mechanics: the chapter's held prerequisites use a round 7 ms seek for it.

A **solid-state drive** has no head and no platter, so there is no seek and no rotational latency: a random 4 KiB read is tens of microseconds. Yet random still costs more than sequential on flash, for two different reasons on the two paths:

- **Reads** are latency-bound at low concurrency. One outstanding read sees the full flash + controller + queueing latency; at queue depth 1 the IOPS ceiling is just 1/α, so a tens-of-µs latency caps a single thread at a few tens of thousands of reads per second however fast the drive is rated. An SSD only reaches its headline bandwidth when *many* I/Os are in flight at once, spread across its internal parallelism (multiple channels, dies and planes). Sequential reads get this for free — the controller reads ahead and stripes across chips — while a lone random read touches one page on one die. This is α + n/β read off the device: raise concurrency (queue depth) and you amortize α across many transfers.
- **Writes** are worse than reads when random, because of how flash is rewritten (next section): small scattered writes drive up write amplification and provoke garbage collection, which steals bandwidth from your foreground writes.

So the slogan "sequential beats random" survives the move to SSDs, but the mechanism changes: on an HDD it is the head; on an SSD it is queue depth for reads and the flash-rewrite machinery for writes. The I/O cost model's ratio **r** (how many sequential reads one random read costs) is topic 14's; here it is a property of the device, and it is a function of queue depth, not a constant.

### Block size and alignment

A block device reports two sizes, both readable under `/sys/block/<dev>/queue`:

| sysfs attribute | Meaning |
|---|---|
| `logical_block_size` | Smallest unit the device will address, historically 512 bytes (kept at 512 even on 4K media for compatibility, "512e"). |
| `physical_block_size` | The real media unit — 4096 bytes on Advanced-Format HDDs and essentially all SSDs. |
| `minimum_io_size` | The smallest I/O the device prefers (the physical block). |
| `optimal_io_size` | The preferred streaming unit, e.g. a RAID stripe width; 0 if unset. |
| `rotational` | 1 for a spinning disk, 0 for flash. |

The number that bites is the physical block. If you write less than one physical block, or a write that straddles a block boundary when the media unit is 4 KiB, the device (or the filesystem/RAID layer) must do a **read-modify-write**: read the surrounding block, splice in your bytes, and write the whole block back. One small write becomes a read *plus* a write, and on flash it also inflates write amplification. Aligning writes and their sizes to the 4 KiB physical block avoids it; a 512e drive that lets you address 512-byte sectors will still pay the penalty under the covers.

**`O_DIRECT` alignment.** `O_DIRECT` (topic 9) bypasses the page cache and DMAs straight between the device and your user-space buffer, so the buffer address, the file offset and the length must all be aligned — otherwise the I/O either fails with `EINVAL` or silently falls back to buffered I/O. The exact requirement varies by filesystem and kernel version: Linux 2.4 required the filesystem block size (typically 4096), Linux 2.6.0 relaxed this to the device's *logical* block size (typically 512), and since Linux 6.1 the precise alignment can be queried with `statx()` and the `STATX_DIOALIGN` flag rather than guessed (open(2) NOTES). Treat 4 KiB alignment as the portable, safe choice.

### Inside an SSD: FTL, erase blocks, garbage collection, write amplification

NAND flash has an awkward asymmetry. It is organized into **pages** (the read and program unit, a few to sixteen KiB) grouped into **erase blocks** (the erase unit, hundreds of pages — hundreds of KiB to several MiB). You can read a page and you can program a page once, but **you cannot overwrite a page in place**: to put new data where old data sits, the entire erase block must first be erased, and erases are slow and physically wear the cells (each block tolerates a limited number of program/erase cycles).

So an SSD never updates in place. The **Flash Translation Layer (FTL)** maps the logical block addresses the host sees onto physical flash pages and writes **out-of-place**: a write to a logical address already in use is placed on a fresh page elsewhere and the mapping is repointed; the old page is marked *stale*. Agrawal et al. ("Design Tradeoffs for SSD Performance", USENIX ATC 2008) frame this as allocating each logical page (they use 4 KiB) from a pool of flash, and show how much of SSD performance and lifetime turns on these allocation and cleaning choices.

Out-of-place writing fills the drive with a mix of live and stale pages, so free pages eventually run low and the FTL must reclaim space — **garbage collection**. GC picks a victim erase block, copies its still-*live* pages into a fresh block, then erases the victim. Those copy writes are extra writes the host never asked for.

**Write amplification** measures the damage:

> write amplification = flash (physical) bytes written ÷ host (logical) bytes written  ≥ 1

GC copies, FTL metadata and read-modify-write all push it above 1. The pattern decides how far: **large sequential writes** that fill whole erase blocks leave few stale-but-live mixes to clean, so amplification stays near 1; **small random writes** scatter live and stale pages together, so every GC pass copies more live data, and amplification climbs. That is the deeper reason random writes cost more on flash — they do not just run slower, they wear the device faster.

Two levers fight back:

- **Over-provisioning** — the drive keeps spare flash the host can never address (e.g. selling 480 GB on 512 GiB of media). More spare means GC finds emptier victim blocks, copies fewer live pages, and sustains higher random-write throughput; enterprise SSDs over-provision heavily for exactly this.
- **TRIM / discard** — when a filesystem frees space (a file is deleted), it tells the device which logical blocks are now garbage (`discard_granularity` in queue-sysfs). Without TRIM the FTL still believes that data is live and keeps copying it through every GC pass forever, inflating amplification; with TRIM those pages are marked stale and skipped.

The failure mode to recognize: a nearly full, lightly over-provisioned SSD under a random-write workload can fall off a *write cliff* once its free pages are exhausted and GC runs in the foreground, dropping to a fraction of the fresh-device rate. The fixes are structural — keep writes large and aligned, leave free space, enable TRIM — and they are why log-structured and LSM designs (topic 13, at the data-structure level) try to turn random updates into sequential appends.

### Durability: what fsync actually promises

Follow a write down the stack. `write()` copies your bytes into the kernel **page cache** and returns; the pages are now *dirty* in RAM, not on the device. Writeback flushes them lazily under the `vm.dirty_*` thresholds (topic 9). A crash in that window loses the data even though `write()` reported success — the cache lied by design, to make writes fast.

**`fsync(fd)`** forces all of a file's dirty pages, *plus* its metadata, out to the storage device, and — crucially — flushes the device's own write cache "if present", blocking until the device reports the transfer complete (fsync(2)). **`fdatasync(fd)`** does the same but skips metadata not needed to read the data back, such as the last-modified time; a change to the file size still forces a metadata flush. For an append-only log, `fdatasync` saves one metadata write per sync, which is why `wal_sync_method` defaults to `fdatasync` on Linux (PostgreSQL 18).

**Device write caches and FUA.** Drives hold a small volatile write cache. A write "completes" when it lands there, not on the media, so durability requires either a cache-flush command (what fsync issues) or writes tagged Force Unit Access. If the cache is on and the flush is skipped or not honored — a drive that lies, or `fsync=off` — a power cut loses whatever sat in the cache. The fsync(2) HISTORY note records that older kernels and filesystems could not flush disk caches at all, so caches had to be disabled with `hdparm`/`sdparm` to be safe. Enterprise SSDs sidestep this with power-loss protection (on-board capacitors that flush the cache on power failure); consumer drives generally do not have it.

**The directory gotcha.** Creating a file is two independent facts: the file's inode and data, and the *directory entry* that names it. fsync on the file does not promise the directory entry is durable — "an explicit fsync() on a file descriptor for the directory is also needed" (fsync(2)). The same applies to the atomic rename-into-place pattern. So the durable-create recipe is:

> 1. `write()` the data.
> 2. `fsync()` (or `fdatasync()`) the **file** — forces data and needed metadata to the device and flushes its cache.
> 3. `fsync()` the **parent directory** — forces the directory entry, needed after a create or a rename.
> 4. Only now will a crash leave the data intact.

Skip step 3 and a crash can leave a durable file that nothing points to, or a rename that half-happened.

### fsyncgate 2018: a failed fsync must not be retried

In early 2018 PostgreSQL discovered its entire checkpoint durability protocol rested on a false reading of fsync (reported by Craig Ringer on pgsql-hackers; narrated in Jonathan Corbet's LWN piece "PostgreSQL's fsync() surprise"). PostgreSQL wrote buffered and handed fsync to a separate checkpointer process that opened files on demand, called fsync, and on an `EIO` error logged it and retried later. Two things broke that:

- When buffered writeback hits a hardware error, Linux filesystems **mark the failed dirty pages clean and discard their contents** — ext4, XFS and Btrfs all do this (Rebello et al., USENIX ATC 2020: "pages are always marked clean"). The error is reported to an fsync caller *once* and then forgotten. So a **second fsync after a failed one can return 0 (success)** with the data never on disk: there is nothing dirty left to flush, so the call "succeeds" and the in-memory copy is already gone.
- Before Linux 4.13 the error could be lost entirely if the file descriptor that saw the writeback failure was not the one that later called fsync — exactly what the checkpointer's open-on-demand, LRU descriptor scheme did. Linux 4.13 rebuilt writeback error reporting (the `errseq_t` mechanism) and 4.16 improved it further, so an error now reaches an fsync caller even across a close/open — but it is still delivered **only once**, and the data pages are already clean, so a retry still cannot recover anything.

The lesson is that fsync's contract is weaker than a durability protocol wants. A failed fsync does not mean "transient, try again"; it means data has been lost and its only copy in memory has already been thrown away. The safe response is to stop trusting any later success and recover from a known-durable point. PostgreSQL's fix (committed for version 12, back-patched to 11, 10, 9.6, 9.5 and 9.4) is to **PANIC on fsync failure**, crashing the server so recovery replays the write-ahead log from the last checkpoint known to be durable rather than continuing over silently lost pages (PostgreSQL wiki, "Fsync Errors"). InnoDB/MySQL and WiredTiger/MongoDB made parallel changes. Rebello et al. went on to test PostgreSQL, LMDB, LevelDB, SQLite and Redis and found that *no* failure-handling strategy was sufficient — fsync failures could still cause data loss or corruption — which is why "crash and recover from the log" has become the accepted answer, not "retry". WAL design and recovery themselves are Chapter 5; here the takeaway is the primitive's real guarantee.

### Keeping a fast device busy: io_uring and PostgreSQL 18

Durability aside, a modern SSD only delivers its rated throughput with many I/Os outstanding, and the classic one-syscall-per-I/O, one-blocked-thread-per-I/O model cannot cheaply supply that (threads are expensive — topic 8). **`io_uring`** (Linux 5.1+) replaces that model with two ring buffers shared between the application and the kernel: a *submission queue* where the app posts submission queue entries (SQEs) describing operations, and a *completion queue* where the kernel posts one completion event (CQE) per SQE. A single `io_uring_enter()` can submit many operations and reap many completions, so one thread keeps dozens of reads or writes in flight without a syscall per operation (io_uring(7)). This is precisely the "P parallel transfers" the refined parallel I/O models assume (topic 14's frontier) and what flash needs to reach its IOPS ceiling.

PostgreSQL 18 added an asynchronous I/O subsystem exposed as the **`io_method`** setting (Resource Consumption):

| `io_method` | What it does |
|---|---|
| `worker` | **Default.** A pool of I/O worker processes (`io_workers`, default 3) performs the I/O; portable to every platform. |
| `io_uring` | Uses io_uring directly; requires a build with `--with-liburing` (the docs give no further detail) and a Linux kernel that supports it. |
| `sync` | The old synchronous behavior for I/O that is otherwise eligible to be asynchronous. |

Two companion knobs: `io_combine_limit` (default 128 KiB) caps how large neighbouring reads are coalesced into one I/O, and `io_max_concurrency` (default −1, which picks a value from `shared_buffers` and the maximum number of processes, never more than 64) caps outstanding I/Os per process. In 18 this accelerates the read-heavy, prefetchable paths — sequential scans, bitmap heap scans and vacuum — and it does **not** touch fsync's durability contract. It helps exactly when the device can serve more than one I/O at once *and* the workload can name its next reads in advance; it does nothing for a chain of dependent reads, one pointer at a time, which is the same lesson the parallel disk model taught in topic 14. Deeper async-I/O engineering is Rust Systems Engineering M3.

## Build, break, measure

### Lab · Sequential vs random, buffered vs direct, on NVMe

This is the §1.2 chapter-lab part for storage. Point `fio` at a scratch file on an NVMe drive and sweep two axes: access pattern (sequential vs random) and the page cache (buffered vs `O_DIRECT`). Report throughput (MB/s) for sequential and IOPS for random, cold and warm.

```bash
# A — sequential read, buffered (hits the page cache once warm)
fio --name=seq-buf  --filename=/mnt/nvme/t --size=8G \
    --rw=read      --bs=1M  --direct=0 --ioengine=psync

# B — sequential read, direct (goes to the device every time)
fio --name=seq-dir  --filename=/mnt/nvme/t --size=8G \
    --rw=read      --bs=1M  --direct=1 --ioengine=io_uring --iodepth=8

# C — random 4 KiB read, direct, queue depth 1 (latency-bound)
fio --name=rr-qd1   --filename=/mnt/nvme/t --size=8G \
    --rw=randread  --bs=4k  --direct=1 --ioengine=io_uring --iodepth=1

# D — random 4 KiB read, direct, queue depth 32 (parallelism-bound)
fio --name=rr-qd32  --filename=/mnt/nvme/t --size=8G \
    --rw=randread  --bs=4k  --direct=1 --ioengine=io_uring --iodepth=32

# Cold cache before any buffered run:
echo 3 | sudo tee /proc/sys/vm/drop_caches
```

**Expected shapes** (ranges, not promises — your drive sets the exact numbers; *measure in build*):

- **A warm** reads at RAM bandwidth, not the device: the file is in the page cache, so you are benchmarking memory. This is the trap — it can read many GB/s and tell you nothing about the disk.
- **B** reads at the drive's sequential bandwidth (a few GB/s on a mainstream NVMe drive; cite your drive's datasheet).
- **C** is latency-bound: IOPS ≈ 1/latency, so a tens-of-µs latency gives only tens of thousands of IOPS no matter the drive's rating.
- **D** is far higher — hundreds of thousands of IOPS — because thirty-two outstanding reads fan out across the drive's internal parallelism. C→D is the queue-depth story made visible.

On a spinning disk the same sweep would show random staying three orders of magnitude below sequential at any queue depth: no amount of concurrency grows a second head.

**Break it.**

- Run A *without* dropping caches and watch "disk" throughput exceed the drive's rated bandwidth — the page cache answering, not the device. Buffered benchmarks lie; `--direct=1` and a cache drop are how you stop them.
- Switch C/D to `--rw=randwrite` on a nearly full drive and watch throughput fall over time as garbage collection starts running in the foreground — the write cliff and write amplification in the flesh.

### Micro-lab · The durable-write recipe

A few lines that write one record three ways — no fsync, `fsync` the file only, and `fsync` file **then** directory — and time each. The timing gap between them *is* the cost of durability. Verifying that only the third survives a real crash needs a power-cut or a crash-injection harness (`dm-flakey`, CrashMonkey); describe the expected result and *measure in build*. The point to feel: the fast version and the correct version differ by a directory fsync you would never guess was needed.

## In production — a review checklist

- **Does durability survive a power cut, end to end?** A `write()` that returned is not durable. On consumer SSDs the write cache is volatile unless the drive has power-loss protection; confirm fsync is reaching and flushing the device, and never run with `fsync=off` except for data you can rebuild from scratch.
- **Never retry a failed fsync — treat it as data loss.** Prefer engines that crash and recover from a log on fsync failure (PostgreSQL 12+, modern MySQL) rather than logging and retrying. Check the kernel: writeback error reporting is only reliable from 4.13, better from 4.16, and even then the error arrives once.
- **fsync the directory after create or rename.** Use the write → fsync(file) → fsync(dir) recipe, or a library that already does (SQLite's rename-and-fsync, for instance). A durable file nothing points to is still lost.
- **Align to 4 KiB.** Match writes to `physical_block_size`; watch for 512e/4Kn mismatches and set I/O to `optimal_io_size` on RAID. `O_DIRECT` buffers, offsets and lengths must be block-aligned, or the I/O fails or quietly falls back to buffered.
- **Keep SSDs healthy.** Leave free space / over-provision, enable TRIM (`fstrim` or a `discard` mount), and monitor write amplification and endurance (SMART, drive-written bytes). Random-write-heavy workloads — OLTP, LSM compaction — wear flash faster; account for it at the data-structure level (topic 13).
- **Benchmark the way production reads.** Cold cache, production access pattern and queue depth, `--direct=1`. A warm buffered benchmark measures the page cache, not the drive.
- **Pick `io_method` deliberately.** PostgreSQL 18 defaults to `worker` (portable); `io_uring` needs a `liburing` build and a recent kernel and only pays off on read-heavy, prefetchable work. Measure before switching, and remember it changes nothing about fsync.
- **`fdatasync` for append-only logs.** It saves a metadata flush per sync; it is the Linux default for `wal_sync_method`.
