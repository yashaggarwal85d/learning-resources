# What an expert must know: memory hierarchy and latency numbers

Syllabus line: registers, L1/L2/L3, DRAM (local vs remote NUMA), NVMe SSD, HDD, same-AZ network, object storage; order-of-magnitude latency and bandwidth per tier; estimating a job's lower bound before running it.

Every source below was fetched raw with `node scripts/sources.mjs fetch` into /tmp/claude-0/expert-src/ and read. Exact absolute figures that a source does not state are not claimed here; the item says so and tells the learner to measure.

| 1 | Latency is a ladder of orders of magnitude, not a table to memorise: register at most 1 cycle, L1d about 3, L2 about 14, main memory about 240 cycles (Pentium M example). The ratio between rungs matters, not the exact value, and the numbers date quickly. | https://akkadia.org/drepper/cpumemory.pdf (sec. 3.1, cost of hits and misses) | here |
| 2 | Cycles must be converted to time using the clock of the machine at hand; a miss of 200+ cycles is tens of nanoseconds, a same-AZ network hop is hundreds of microseconds or more, an S3 first byte is tens to hundreds of milliseconds. Expert habit: write every tier in the same unit (ns) before comparing. | https://akkadia.org/drepper/cpumemory.pdf (cycle costs) and https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance.html (about 100-200 ms small-object / first-byte latency) | here |
| 3 | Why the hierarchy exists: fast SRAM is costly, DRAM needs a refresh and is slower; caches work only because of locality, so a working set that fits a level runs at that level's speed and one that does not falls to the next. | https://akkadia.org/drepper/cpumemory.pdf (sec. 2 and 3) | here |
| 4 | Latency and bandwidth are separate axes. Sequential access with prefetching hides DRAM latency; dependent random access (pointer chasing) exposes it. The same tier can look 100x different. | https://akkadia.org/drepper/cpumemory.pdf (hardware and software prefetching, sec. 3.3 and 6.3; pointer-chase measurements) | here (intro); detail in "CPU caches/SIMD" and "bandwidth latency locality" |
| 5 | Sustained bandwidth is not pin bandwidth: use the measured steady-state memory bandwidth (STREAM-style), not the datasheet peak, when estimating. | https://www2.eecs.berkeley.edu/Pubs/TechRpts/2008/EECS-2008-134.pdf (Roofline: "steady state bandwidth potential ... not the pin bandwidth") | here |
| 6 | Lower bound by the roofline form: attainable rate = min(peak compute, peak memory bandwidth x operational intensity). For a scan-heavy data job the bytes-moved term usually wins, so time >= bytes / slowest-link bandwidth. | https://www2.eecs.berkeley.edu/Pubs/TechRpts/2008/EECS-2008-134.pdf | here |
| 7 | The back-of-envelope recipe: bytes read x tier bandwidth, plus (number of dependent/serial requests x per-request latency), take the max across resources (disk, network, memory, CPU), because the pipeline runs at its slowest stage. Compare the estimate with the measured run; a large gap is the finding. | https://www2.eecs.berkeley.edu/Pubs/TechRpts/2008/EECS-2008-134.pdf (bound-and-bottleneck reasoning); https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance-guidelines.html ("look at network throughput, CPU, and DRAM requirements") | here |
| 8 | NUMA: memory attached to another socket costs more. Drepper's AMD example: 2-hop reads and writes are 30% and 49% slower than 0-hop reads. The "NUMA factor" is machine-specific, so use the relative ratio and measure on the target host. | https://akkadia.org/drepper/cpumemory.pdf (sec. 5.4, remote access costs) | here |
| 9 | NUMA is observable and controllable on Linux: numa_hit / numa_miss / numa_foreign counters show whether allocations land on the preferred node, and memory policy (bind, preferred, interleave, first-touch default) decides placement. | https://docs.kernel.org/admin-guide/numastat.html ; https://docs.kernel.org/admin-guide/mm/numa_memory_policy.html | here (concept); tuning in "CPU caches/SIMD" |
| 10 | Page cache and write-back sit between DRAM and disk: dirty pages are flushed by thresholds (dirty_background_ratio, dirty_ratio, writeback interval) and drop_caches exists, so a "disk" benchmark can really be a DRAM benchmark and a write can return before it is durable. | https://www.kernel.org/doc/html/latest/admin-guide/sysctl/vm.html | here (warning); fsync detail in "storage devices and fsync" |
| 11 | Cloud block storage is specified in IOPS and MiB/s caps and a latency class, not by the medium: e.g. EBS gp3 vs io2 Block Express, "consistent sub-millisecond latency", "more than 16,000 IOPS" classes. Local NVMe and network-attached volumes are different tiers. | https://docs.aws.amazon.com/ebs/latest/userguide/ebs-volume-types.html | here (that cloud caps exist); device details in "storage devices and fsync" |
| 12 | HDD volumes are for large streaming workloads where throughput, not IOPS, is the dominant attribute; SSD volumes for small-I/O, IOPS-dominated work. Random vs sequential is the deciding access pattern on spinning media. | https://docs.aws.amazon.com/ebs/latest/userguide/ebs-volume-types.html (HDD vs SSD sections) | here |
| 13 | Flash is not ideal media: error rates, wear and drive failures are field-measured in millions of drive-days, so SSD capacity and speed come with failure and aging behaviour, not just a latency number. | https://www.usenix.org/system/files/conference/fast16/fast16-papers-schroeder.pdf | a later syllabus topic: storage devices and fsync |
| 14 | The NVMe protocol is a family of specifications (base, command sets, transports); "NVMe SSD" names the interface, and the number of queues and depth is why it scales parallelism. | https://nvmexpress.org/specifications/ | a later syllabus topic: storage devices and fsync |
| 15 | Instance network bandwidth is a per-instance limit that applies to inbound and outbound separately, with baseline plus credit-based burst; a stated "up to" figure is not guaranteed. | https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-instance-network-bandwidth.html | here (cap exists); depth in "TCP/network topics" |
| 16 | Single-flow limits: one 5-tuple flow is limited to 5 Gbps outside a cluster placement group, up to 10 Gbps inside one, and ENA Express in the same AZ up to 25 Gbps. One connection never fills a large instance's NIC. | https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-instance-network-bandwidth.html | a later syllabus topic: TCP/network topics |
| 17 | Placement matters for latency: cluster placement groups pack instances within an AZ for low-latency node-to-node traffic. Same-AZ is the cheap/fast tier; cross-AZ and cross-Region are further rungs. AWS publishes no latency figure on this page, so measure. | https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/placement-groups.html | here (tier definition); TCP detail in "TCP/network topics" |
| 18 | Bandwidth-delay product: to fill a long path the TCP window must reach bandwidth x RTT; the classic 16-bit window caps at 64 KiB, hence window scaling. Latency therefore limits throughput per connection. | https://www.rfc-editor.org/rfc/rfc7323.txt (sec. 1.1 "Large Fat Networks") | a later syllabus topic: TCP/network topics |
| 19 | Object storage is high-latency, high-parallelism: first-byte latency about 100-200 ms for small objects, so throughput comes from many concurrent connections and byte-range GETs, not from one stream. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance.html ; https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance-guidelines.html | here (as a tier in the ladder); mechanics in "object storage as a storage tier" |
| 20 | Object storage has request-rate limits as well as bandwidth: at least 3,500 write and 5,500 read requests per second per prefix, scaling gradually with 503 Slow Down in the meantime. A job with millions of small objects is request-bound, not byte-bound. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance.html | a later syllabus topic: object storage as a storage tier |
| 21 | Single-instance S3 transfer can reach up to 100 Gb/s (the instance NIC), and aggregate scales across instances; the lower bound for reading a dataset is min(NIC, per-prefix request rate x object size, S3 throughput). | https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance.html | here (formula use); limits in "object storage as a storage tier" |
| 22 | Co-locate compute and data: S3 and EC2 in the same Region reduces latency and transfer cost, so "same-AZ/Region" is part of the estimate, and egress price is a second cost axis. | https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance-guidelines.html | here |
| 23 | Tail latency changes the estimate: at scale, rare slow requests dominate the whole job; the expected completion time of a fan-out is set by the slowest part. S3 advises retrying the slowest 5% of large requests, or a small request after about 2 s. | https://research.google/pubs/the-tail-at-scale/ ; https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance-design-patterns.html | a later syllabus topic: tail latency |
| 24 | Lower bound is a floor, not a forecast: it ignores serialization, compression, skew, retries and cold caches. An expert reports the bound, the bottleneck tier, and the ratio measured/bound. | https://www2.eecs.berkeley.edu/Pubs/TechRpts/2008/EECS-2008-134.pdf (hardware limits vs attained performance) | here |
