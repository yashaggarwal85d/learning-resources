<section data-section="internals">

## A little deeper

Two families carry almost every indexed read and write in a data system. A **B+-tree** keeps the data sorted in place and updates it where it lives; an **LSM-tree** (Log-Structured Merge-tree) never updates in place, it writes new sorted runs and merges them later. The same hundred million keys live under both, but they pay their costs in opposite places. This is a glance: the mechanics of splits, write-ahead logs and node layout are §5.1, and the exact crossover arithmetic is the next topic, the I/O cost model. Here we only need the shapes.

Throughout, a **page** is the fixed-size block the database reads and caches as a unit: 8 KB (8,192 bytes) in PostgreSQL. The memory hierarchy already told you what one page read costs at each tier (a few microseconds from the page cache, tens of microseconds from NVMe, tens of milliseconds from object storage). An index's whole job is to decide **how many** of those page reads a query pays.

### A B+-tree is short because it is wide

A B+-tree node is exactly one page. All the keys live in the leaves; the internal nodes hold only **separator keys and downlinks** that route a search. The number of children a node can hold is its **fan-out**, and the fan-out is just the page size divided by the size of one entry:

**fan-out ≈ usable bytes per page / bytes per (key + pointer)**

For an 8 KB page and an 8-byte key, each internal entry is roughly a 20-byte triple of key, tuple header and line pointer, so a node routes to **a few hundred** children (the exact figure depends on the key width and the fill factor, and is worth measuring on your own index — *measure in build*). A tree of height *h* with fan-out *f* addresses up to *f*<sup>*h*</sup> keys, so the height is

**h = ⌈log<sub>f</sub> N⌉,**

a logarithm in a **large base** — exactly the reason the asymptotic-notation refresher cared about change of base. The large base is what makes the tree flat:

| Keys *N* | fan-out *f* | $\log_f N$ | Levels (root → leaf) |
|---|---|---|---|
| 100,000,000 | 256 | 3.32 | **4** |
| 100,000,000 | 512 | 2.95 | **3** |
| 100,000,000 | 1,000 | 2.67 | **3** |
| 1,000,000,000 | 1,000 | 3.00 | **3** |

So the `orders` index on 100 million keys is **three or four levels deep** for any realistic fan-out — the same arithmetic as the refresher's $\log_{1000}(10^9) = 3$. A **point lookup** walks one path, root → leaf: three or four page reads, then one more to fetch the row from the table (unless the index is covering). But the top of the tree is tiny and hot. The root is one page; the second level is a few hundred pages, a few megabytes in all. After the first few queries those upper levels sit in the page cache permanently, so a lookup pays **about one real page read**, at the leaf, plus the heap fetch. That is the "few page reads" the next topic's bridge says you have just revised.

A **range scan** (`WHERE id BETWEEN …`) descends once to the first matching leaf, then walks sideways. PostgreSQL's B-tree is a Lehman–Yao *B-link* tree: every leaf carries a **right-link** to its next sibling and a **high key** bounding its contents, so a range scan follows the leaf chain in key order without ever climbing back up. Reporting *k* matches from a clustered index costs about $k/B$ sequential reads, not $k$ random ones — a distinction the I/O cost model makes precise.

### An LSM-tree is fast to write because it never seeks

An LSM-tree turns every write into an append. A new key-value pair goes into a **memtable** — a small sorted in-memory structure, often a skip list — after being appended to a write-ahead log for durability. When the memtable fills, it is frozen and flushed to storage as an immutable **sorted run** (an SSTable). Flushing is one large sequential write, which is why ingest is cheap: no page to find, no seek, no read-modify-write. The original O'Neil formulation had two components, an in-memory C0 and an on-disk C1 merged by a rolling merge; modern engines generalise this to many runs organised into **levels**.

Because runs are never modified, they accumulate, and a background process must bound their number by **compaction**: a *k*-way merge of several sorted runs into fewer, larger ones (the external-merge-sort mechanism of topic 16). In RocksDB's default **leveled** compaction each level past L0 is a single sorted run, and each level is about ten times larger than the one above (`max_bytes_for_level_multiplier` = 10). A read finds a key by binary search within a level, after consulting a per-file Bloom filter.

### Read, write and space amplification — the RUM trade-off

Athanassoulis et al.'s **RUM conjecture** names the tension cleanly: for **R**ead overhead, **U**pdate overhead and **M**emory (space) overhead, a design can minimise at most two at the expense of the third. The B+-tree and the LSM-tree sit on opposite corners.

| | B+-tree (in-place) | LSM-tree (out-of-place) |
|---|---|---|
| **Point read** | one root → leaf path; ~1 real page read once the top is cached | check memtable, then newest run down; L0 files + one file per level, but a Bloom filter means usually **one** file read |
| **Range scan** | walk the linked leaf level in order | merge across every overlapping run (Bloom filters don't help): read ≈ L0 files + non-empty levels |
| **Write (ingest)** | update in place: rewrite the whole leaf **page** for a small change; splits propagate up; random, scattered writes | append to memtable, flush sequential runs; **high throughput**, no in-place seek |
| **Write amplification** | low per logical change in count, but a 16-byte update dirties an 8 KB page; WAL doubles it (§5.1) | compaction rewrites each byte several times: RocksDB's own worked example gives ≈ 1 + 2 + 10 + 10 + 10 ≈ **33×** for leveled |
| **Space amplification** | fill-factor slack and page splits leave pages partly empty | leveled stays tight (RocksDB example ≈ 1.14×); size-tiered / universal lowers write amplification but can **double** space during compaction |

Read **amplification** is page reads per query; **write amplification** is bytes written to storage per byte written by the application; **space amplification** is bytes stored per byte of live data (RocksDB's tuning guide defines all three this way). The B+-tree optimises reads and pays with random, page-granular writes. The LSM-tree optimises writes and pays with reads that may touch many runs and with background compaction work — which it hides with Bloom filters (RocksDB's default is 10 bits per key, about a 1% false-positive rate, so most point reads touch a single file).

**Two amplifications multiply.** The structural write amplification here stacks on top of the *device* write amplification from the storage-devices topic: an SSD's flash-translation layer rewrites flash to garbage-collect erase blocks. RocksDB's own worked example puts leveled compaction's structural amplification at a sourced **33×**; a device amplification of **2×** is only an illustrative, unsourced round number for a moderately random-write workload, not a measured figure, and the resulting **~66×** flash writes per logical byte is likewise an illustrative product of the two, not itself a cited number. That product is why write-heavy LSM workloads watch both numbers, and why compaction tuning is a flash-lifetime decision, not just a throughput one.

### Why one favours point reads and the other ingest

- **`orders` lookups → B+-tree.** Finding one order by `order_id`, or a small customer's orders by range, is a short cached descent and a sorted leaf walk. Reads dominate, updates are modest, and the tree keeps both read and space overhead low. This is why operational databases (PostgreSQL, and the clustered indexes of MySQL/InnoDB) default to B+-trees.
- **`order_events` ingest → LSM-tree.** A terabyte of events arriving as a high-rate append stream wants sequential writes and no read-before-write. An LSM absorbs it at memory speed and defers the sorting into background compaction (the nightly merge). Reads pay a little more and compaction burns I/O, but the write path never seeks. This is why RocksDB, Cassandra, ScyllaDB and most time-series and event stores are LSM-based.

The honest one-liner: **a B+-tree trades write cost for read cost; an LSM-tree trades read and space cost for write cost.** Pick the structure whose cheap side matches your workload's hot path. The next topic counts those costs exactly, in block transfers.

## Try it

This refresher has no chapter lab of its own — the §1.3 lab (external merge sort and a spilling hash aggregation) is hosted by *External merge sort and k-way merge* and *Hash tables inside query engines*, and LSM compaction reappears there as a *k*-way merge. But two five-minute checks make the shapes concrete.

**See a real B+-tree's height.** In PostgreSQL, the `pageinspect` extension reports the metapage, whose `level` field is the height of the tree above the leaves:

```sql
CREATE EXTENSION IF NOT EXISTS pageinspect;

-- Build an index on a few million distinct keys, then read its height.
SELECT level, root, fastlevel
FROM bt_metap('orders_pkey');   -- level: 0 = leaf-only, grows by 1 each split up
```

Load ten times the keys and watch `level` tick up by one only when the fan-out is exhausted — a large base climbing slowly. Divide the index's size in pages by its live tuple count to estimate the fan-out, and check it against ⌈log<sub>f</sub> N⌉ (*measure in build*; exact numbers depend on your key width and fill factor).

**See LSM amplification.** Against any RocksDB-backed store (or `db_bench`), write a known volume of keys and read back the amplifications RocksDB already tracks:

```
rocksdb.stats          -> compare "Cumulative writes" against disk bytes written (write amplification)
rocksdb.estimate-live-data-size vs file sizes on disk     (space amplification)
```

Then raise `max_bytes_for_level_multiplier` or switch to universal compaction and watch write amplification fall while space amplification rises — the RUM trade-off, moving under your hands.

**What to look for.** The B+-tree height barely moves as data grows ten-fold; the LSM write-amplification number is large and tunable, and no setting makes read, write and space all cheap at once.

## In production

A short checklist for choosing and reasoning about these two:

- **Match the structure to the hot path.** Read-heavy, point-and-range access on mutable rows → B+-tree. High-rate append/upsert ingest where reads tolerate some amplification → LSM-tree. State the workload's dominant operation before arguing the index.
- **Estimate height from fan-out, not from memory.** ⌈log<sub>f</sub> N⌉ with a fan-out in the hundreds is three or four levels for a hundred million keys. If someone fears a "deep" index, the large base is the answer.
- **The upper levels are free; the leaf and the heap fetch are not.** Count a point lookup as roughly one real read plus the row fetch, because the top of the tree is cached. A covering index removes the heap fetch.
- **An in-place update is page-granular.** A one-column update rewrites an 8 KB page and every index entry on it, and the WAL writes it again. "Small update" is not small in bytes — this is where B+-tree write amplification hides.
- **Watch two write-amplification numbers for an LSM.** The structural one (compaction, tens-fold for leveled) multiplies with the device one (the SSD FTL). Both bound sustainable write throughput and flash lifetime.
- **Bloom filters make LSM point reads cheap but do nothing for ranges.** A range or prefix scan merges across runs; size compaction and run count for the scan pattern you actually run.
- **You cannot win all three corners.** If a vendor claims low read, low write and low space at once, find which number was measured on which workload. The RUM conjecture says one of them gave.
- **Go deeper where it matters.** The in-place and out-of-place internals (page splits, B-link concurrency, WAL, memtables, SSTables, compaction policies and the RUM trade-off in full) are §5.1; the build-from-scratch versions are *Data Structures & Algorithms* Ch.5 (B-trees and write-optimised trees).
