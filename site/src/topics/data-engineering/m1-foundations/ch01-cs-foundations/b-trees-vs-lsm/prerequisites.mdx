<section class="prereq basics" data-section="basics">

### <span class="n">00</span> Basics: words the reel takes for granted

- **Index**: a separate structure that maps column values to the rows holding them, so a query can find rows without scanning the table. *Where you meet it:* `CREATE INDEX` on a column you filter by often.
- **Key and separator**: a key is the value an index orders by; a separator is a key stored in an inner node to tell a search which way to go. *Where you meet it:* a phone book's header "Ma–Mo" at the top of a page.
- **Sorted run**: a sequence of key-value pairs stored in key order, which is what makes it searchable by binary search and mergeable with other runs. *Where you meet it:* the output of `sort` on a text file.
- **Point lookup vs range scan**: a point lookup fetches one key; a range scan fetches every key between two bounds. *Where you meet it:* `WHERE id = 7` versus `WHERE created_at BETWEEN a AND b`.
- **Write-ahead log (WAL)**: an append-only record of changes written before the changes themselves, so a crash can be replayed. *Where you meet it:* PostgreSQL's `pg_wal` directory.

<p class="check"><b>Check yourself:</b> a tree with fan-out one thousand over a billion keys is how many levels deep? (Answer: three, since log<sub>1000</sub>(10<sup>9</sup>) = 3.)</p>

### <span class="n">01</span> Logarithms in a large base, and change of base

A tree's height is a logarithm in the base of its fan-out, and a large base makes the logarithm tiny. You should be able to say why log<sub>1000</sub>(10<sup>9</sup>) = 3 in your head, and convert between bases with log<sub>b</sub> x = ln x / ln b.

### <span class="n">02</span> Devices, pages and write amplification

Why an in-place update is expensive and a sequential append is cheap comes from the devices: random versus sequential I/O, how a write reaches stable storage, and the SSD's own write amplification, which multiplies with an LSM-tree's. The page cache is why a B+-tree's upper levels cost almost nothing after the first query.
