## The chapter

### The problem it solves

Chapters 1–16 built one organization's warehouse, lake, streams and plant floor. This chapter asks what changes when the consumer of all that data is a model instead of a dashboard. The claim the chapter exists to prove, stated once in §17.1's hook and tested by every topic after it: **most ML and RAG failures are ordinary data-engineering failures wearing a new name.** A leaked label is a join done in the wrong temporal order (§2.2's as-of join, misused). Train/serve skew is two code paths computing "the same" feature differently (exactly the inconsistency Chapters 3 and 8 spent a domain-wide vocabulary on). A stale RAG answer is a freshness SLA nobody wrote down (Chapter 11's contract-enforcement idea, unenforced). The chapter teaches the new vocabulary this domain actually needs — point-in-time correctness for training sets, feature stores, embeddings and vector indexes, the serving-layer boundary between data engineering and BI, and the "zero-ETL" pattern that is still CDC under another name — and keeps naming which old idea each new one really is.

### Order of ideas, and why

1. **§17.1 ML data foundations (topics 1–5).** Opens, as Chapter 16's handoff promised, with the as-of join applied to a label instead of a sensor reading (1): point-in-time correctness is the one idea every later topic in this section assumes. Then the platform that makes that join reusable instead of reimplemented per model, the feature store, and the inconsistency it exists to prevent (2). Then the two concrete techniques that make "point-in-time" and "consistency" actually checkable in production: logging the served vector itself (3) and giving a training set a verifiable identity over time (4). The section closes with what happens after shipping, drift (5), because every earlier topic in the section assumed the join and the store were built once; this one admits they decay.
2. **§17.1.1 Embeddings and vector search (topics 6–7), heavily skipped.** The syllabus cuts the entire mechanism layer (models, chunking, similarity metrics, HNSW, IVF, quantization, disk indexes, filtering, hybrid search, freshness) and keeps only the production-economics bookends: the pipeline that keeps embeddings fresh at scale without the mechanism underneath it (6), and the decision of which store to run once you have vectors, which depends on everything the skipped topics would have taught but is taught here from its *inputs and outputs* rather than its internals (7). Topic 6 bridges from drift (5) on purpose: an embedding is a feature too, and it drifts the same way, at a different cost.
3. **A gap of three full subsections (§17.1.5 production RAG, §17.2 reverse ETL, §17.3–§17.4 graph data).** All skipped in full. Topic 7's handoff is written to be honest about this: it hands off to the BI serving boundary, not to RAG or graphs, because the syllabus does not ask for them here.
4. **§17.7 The analytics-engineering last mile (topics 8–10).** The chapter's center of gravity shifts from ML back to BI, on purpose: the same warehouse now has two kinds of consumer (models and dashboards) and this section is where data engineering hands off to each. The ownership handoff itself, in prose and contract terms (8); then what the tools on the other side of that handoff actually are, as a refresher since senior engineers already know Looker and Power BI by name (9); then the performance mechanics of serving many of those tools from one warehouse without melting it (10).
5. **A second gap (§17.6 agents/MCP, §17.8 foundation-model training data), skipped in full**, then **§17.9 convergence (topic 11)**, which closes the chapter and the domain's "frontier" milestone on the pattern that ties the whole chapter together: a system that claims to remove the pipeline (zero-ETL) and, examined honestly, has only renamed CDC. It hands off to Chapter 18's benchmarking method, which is what every capstone (including one built from this chapter's own ideas, §18.4's RAG capstone) is judged by.

### One running example: the shop's data platform grows an ML and a BI side

Same fictional online shop as Chapters 1–16 (no real company, no real person; `orders`, `orders-rollup`, `order-events`). This chapter gives the shop two new consumers of the same warehouse:

- **A churn model**, trained on the shop's own order and support-ticket history (topics 1–5): its label is "churned within 30 days," its features come from the same tables Chapter 3 modeled, and its first bug is leakage from a feature computed *after* the churn date.
- **A support-ticket search assistant**, embedding ticket text for retrieval (topics 6–7): never built into a full RAG pipeline (that subsection is skipped), but far enough to show what re-embedding a changed ticket costs and why the shop picks `pgvector` over a dedicated vector database at its size.
- **The shop's own BI layer** (topics 8–10): the same conformed marts Chapter 3 built, now served to a Looker-style tool and accelerated so ad hoc dashboards don't requeue the warehouse's expensive queries.
- **A zero-ETL mirror** (topic 11): the shop's operational Postgres mirrored into the warehouse without a visible pipeline, and the chapter's last reveal of what "zero" actually hides.

Every number on screen comes from the topic's own `examples.py`, run on this sandbox's Postgres and a small local embedding model; where the syllabus's own scale (10M vectors, a managed warehouse) cannot be reproduced on the build machine, the topic says so and states the disclosed, smaller scale it actually measured.

### 1. Point-in-time correct training data (`de.point-time-correct-training`): full, §17.1

- **Folder:** `point-time-correct-training`. About 15 min. Hosts the first half of the §17.1 chapter lab.
- **Scope:** "label/feature timelines, as-of joins of features to label timestamps, leakage from future data or post-outcome fields, feature TTLs; backfilling a new feature historically with the same logic used online; batch vs streaming feature computation" — the full syllabus line, clause by clause:
  - *label/feature timelines, as-of joins of features to label timestamps:* a label has a timestamp (when the outcome became true) and every feature has its own timestamp (when it was known); the training-set builder's job is an **as-of join**, Chapter 2's `as-of-join` applied to a label instead of a neighbour row: for each label, take the latest feature value at or before the label's timestamp, never after.
  - *leakage from future data or post-outcome fields:* two distinct leaks, both reproduced in `examples.py` on the shop's churn dataset: **temporal leakage** (a naïve join takes the feature's *current* value instead of its as-of value, so a feature updated after the churn event leaks the future into training — exactly Chapter 2's `temporal-leakage`, now at the model's whole-dataset scale instead of one row) and **post-outcome fields** (a feature that is only populated *because* the label happened, such as a "cancellation reason" column that exists only for churned customers, which no as-of join can fix because the field's very existence encodes the label).
  - *feature TTLs:* a feature computed from a window of history (Chapter 2's window functions) goes stale past some age; a TTL marks when a feature is too old to use and the join must either fall back or drop the row, stated as an explicit, versioned setting rather than left implicit in a query.
  - *backfilling a new feature historically with the same logic used online; batch vs streaming feature computation:* a feature added after a model is already live must be computed for every *historical* label too, with the identical transformation logic that will run online, or training and serving quietly diverge from day one; a feature computed from a batch window (yesterday's orders) versus from a stream (today's order, Chapter 9's material named and not retaught) changes how fresh it can be and how it is backfilled, which the topic states as a design choice, not a detail.
- **Leaves out:** the platform that materializes a feature once to two stores so this logic is written exactly once (topic 2); logging the exact served vector to catch skew after the fact (topic 3); giving a training set a reproducible identity (topic 4); what happens to this join's correctness after the data distribution moves (topic 5). The streaming side of batch-vs-streaming is named, not built: Chapter 9's material is not retaught here.
- **Outcomes:** Build a training set with a naïve join and with a correct as-of join over the same synthetic churn data and measure the leakage-inflated offline AUC the naïve join produces; name a leak as temporal (fixable by the join) or post-outcome (not fixable by any join); set and justify a feature TTL; design a backfill for a new feature that reuses its online transformation logic exactly.
- **Introduces:** `label-feature-timeline-join`, `post-outcome-field-leakage`, `feature-ttl-staleness`, `backfill-same-online-logic`. **Uses:** `as-of-join`, `temporal-leakage`, `window-vs-self-join-cost` (Chapter 2, §2.2; all live). **Declared:** basic supervised-learning vocabulary (label, feature, training set, AUC). Builds on Chapter 9's stream-vs-batch material (§9.3) in prose only; not a resolved id.
- **Bridge:** "That closes the chapter, from a plant's hierarchy through the time series its machines produce to the shell that describes them. One idea from it travels straight into the next: the as-of join that attaches the right temperature to a pressure spike is the same join that attaches the right feature to a label, and getting it wrong leaks the future into a model. The next chapter is the data layer of machine learning and of language models, and it opens there: point-in-time correct training data." (Chapter 16's own handoff, quoted exactly; see the assumption at the top.)
- **Handoff:** "Getting the join right once, in one script, proves the idea. It does not stop the next engineer on the next model from writing the same join wrong, or from computing the 'same' feature a second way for the live service. The next topic is the platform built to make that impossible: the feature store, and the online/offline consistency it exists to guarantee."
- **Prerequisites panel:** Chapter 2's as-of join and window-function topics (Before this); basic classifier evaluation (AUC). **Pre-notes terms:** label, feature, timestamp, leakage, TTL, backfill, AUC.
- **Hook:** a churn model scores 0.94 AUC offline and barely beats a coin flip in production. The training set joined each customer's "support tickets opened" feature at its *current* value, not its value on the label date — and customers who churn open more tickets *after* cancelling, while explaining why. What would the as-of join have shown instead, and why didn't the naïve join catch it? (A prediction: the as-of AUC drops sharply, because most of the first model's signal was the future leaking in.)
- **Visual idea:** the chapter's two-clock timeline: a label mark fixed on the axis, a feature's value changing at several points before and after it; the naïve join's **Reticle** locks onto the rightmost (current) point, crossing past the label mark in red; the as-of join's **Reticle** locks onto the latest point at or before the label, in black; a second panel bars the two resulting AUCs side by side.
- **Lab:** hosts the first half of the §17.1 chapter lab: build the naïve and point-in-time training sets over the synthetic churn dataset and show the leakage-inflated offline AUC. The online-skew half is topic 2's.
- **Sources:** Chapter 2's own `point-in-time-as-of-joins` topic (reused, not re-derived) as the join mechanism's primary citation within the course; Google's "Rules of Machine Learning" page on training/serving skew and leakage (for the production framing of a leak, fetched and quoted at research time); one real feature-store vendor's documentation (Feast or Tecton, whichever is reachable at research time) for its own worked definition of a point-in-time join, read for comparison and not assumed — fetched and quoted at research time.

### 2. Feature stores and online/offline consistency (`de.feature-stores-online-offline`): full, §17.1

- **Folder:** `feature-stores-online-offline`. About 16 min. Hosts the second half of the §17.1 chapter lab.
- **Scope:** "one feature definition materialized to an offline store (lakehouse tables) and an online store (low-latency KV); freshness SLAs, train/serve skew sources (different code paths, different joins, stale online values); Feast (OSS), Tecton (acquired by Databricks, 2025), Hopsworks, cloud-native feature stores" — the full syllabus line, clause by clause:
  - *one feature definition materialized to an offline store and an online store:* a feature store compiles **one** transformation, runs it over history into an offline (lakehouse-table) store for training and over the latest window into an online (low-latency key-value) store for serving, so the two never drift because they were never two implementations — Feast's own documentation describes exactly this split (an offline store for historical, time-series retrieval used to build training data and to materialize into the online store, and an online store that serves only the latest values for low-latency lookup), and notes the stores are configurable and can even be the same engine playing both roles.
  - *freshness SLAs:* how stale the online store's value may be before it is treated as missing, stated as a number (minutes, not "fresh enough"), because materialization itself takes time and a feature's source table has its own update cadence.
  - *train/serve skew sources — different code paths, different joins, stale online values:* three distinct causes, each reproduced: a serving path that recomputes a feature in different code than the training pipeline used (the single most commonly cited cause of this skew in the industry's own writing); a serving path that joins differently (e.g., the current value instead of topic 1's as-of value — the same leak, now at inference time instead of training time); and a materialization lag that leaves the online store serving a value older than its SLA without anyone noticing, because nothing alerted on staleness.
  - *Feast (OSS), Tecton (acquired by Databricks, 2025), Hopsworks, cloud-native feature stores:* named and compared at the level of what each is **for**, not a tutorial: Feast as the open-source reference architecture (the split above, pluggable stores); Tecton as a commercial real-time feature platform, **acquired by Databricks in 2025** to unify online serving with Databricks' own agent tooling (the acquisition's date and purpose are re-verified against Databricks' own announcement at research time, not repeated from a news aggregator); Hopsworks as another open feature-store platform with its own offline/online split; and cloud-native options (a warehouse's own low-latency serving layer) as the "no separate system" alternative, with its own consistency trade-offs named.
- **Leaves out:** logging the exact vector actually served, to catch a skew the store itself didn't prevent (topic 3); dataset identity and reproducibility (topic 4); drift in a feature's distribution over time, as opposed to a staleness/skew bug (topic 5). The internals of any named vendor's materialization engine are out of scope; only the architecture and the consistency guarantee are taught.
- **Outcomes:** Draw a feature store as one definition feeding two stores and say what guarantee that buys; set and check a freshness SLA against a materialization lag; reproduce all three named causes of train/serve skew on the shop's churn feature and show which the architecture prevents and which it does not (a different join is still possible even inside a feature store, if the serving code asks for "current" instead of "as of"); place Feast, Tecton and Hopsworks by what each is for, not by name alone.
- **Introduces:** `feature-store-single-definition`, `online-offline-materialization`, `train-serve-skew-causes`, `feature-freshness-sla`. **Uses:** `label-feature-timeline-join`, `post-outcome-field-leakage`, `feature-ttl-staleness` (topic 1). **Declared:** basic familiarity with a key-value store's read latency. Builds on Chapter 5's Redis/Valkey topic (§5.6, not yet live) and Chapter 9's streaming-ingestion material (§9.3) in prose only; not resolved ids.
- **Bridge:** "Getting the join right once, in one script, proves the idea. It does not stop the next engineer on the next model from writing the same join wrong, or from computing the 'same' feature a second way for the live service. This topic is the platform built to make that impossible: the feature store, and the online/offline consistency it exists to guarantee." (Answers topic 1's handoff.)
- **Handoff:** "A feature store guarantees the definition is the same. It cannot tell you, after the fact, whether the value a real request actually saw matched what training assumed — that has to be measured, not assumed, and the way to measure it is to log the exact vector the model scored."
- **Prerequisites panel:** topic 1. **Pre-notes terms:** offline store, online store, materialization, SLA, key-value store, code path.
- **Hook:** the shop's churn model performs well in every offline test and visibly worse the week it goes live, with no code change anyone can find. The online feature pipeline computes "days since last order" with a slightly different timezone boundary than the offline pipeline did. Which of the three named skew sources is this, and what would a single shared definition have prevented? (A prediction: it is a different-code-path skew, and a feature store with one definition removes exactly this cause, though not every cause.)
- **Visual idea:** the chapter's two-parallel-pipes figure: one feature definition box at the top, an offline pipe and an online pipe below it, both **Decode**-ing from the same box; a skew bug is drawn as a second, smaller box appearing beside the online pipe (a different definition sneaking in), with the two pipes' outputs failing to match at a checkpoint, lit red.
- **Lab:** hosts the second half of the §17.1 chapter lab: serve topic 1's features online (a small local key-value store standing in for a production online store) and measure skew against the offline values, under each of the three named causes in turn.

### 3. Inference logging and log-and-wait features (`de.inference-logging-log-wait`): full, §17.1

- **Folder:** `inference-logging-log-wait`. About 15 min.
- **Scope:** "logging the exact feature vector and model version at serving time, joining to delayed labels to build training sets that are skew-free by construction; shadow/canary capture; storage cost and PII in logged payloads" — the full syllabus line, clause by clause:
  - *logging the exact feature vector and model version at serving time:* the fix to topic 2's "did the request see what training assumed" question is to stop inferring it and start **recording** it: every served prediction logs the exact post-transformation feature vector the model actually scored, together with the model version that scored it, a request id, and the serving timestamp — a raw-request log cannot answer this, because the skew lives in the transformation, not the input.
  - *joining to delayed labels to build training sets that are skew-free by construction:* when the true label arrives later (topic 5's "label delay," named forward and not yet taught), it is joined back to the **logged** vector by request id, not recomputed from source tables — this is "skew-free by construction" because training now literally uses the values serving used, closing the loop topic 1–2 could only narrow.
  - *shadow/canary capture:* a shadow deployment computes and logs features and a prediction **without acting on it**, so a new model or a new feature pipeline can be evaluated against real traffic before it owns any decision; a canary is the same idea at partial, acted-on traffic. Both reuse exactly this topic's logging mechanism; the difference is only whether the output is used.
  - *storage cost and PII in logged payloads:* logging every served vector at production volume is a real storage bill (sized in the lab, from request rate and vector width), and a feature vector built from customer data can itself be sensitive even with the customer id redacted (Chapter 13's sensitivity-tier material named forward, not yet live) — the topic states the retention and redaction policy a logging pipeline needs rather than treating the log as exempt from the rules the rest of the platform follows.

### 5. Drift and label-delay monitoring (`de.drift-label-delay-monitoring`): full, §17.1

- **Folder:** `drift-label-delay-monitoring`. About 16 min. Closes §17.1.
- **Scope:** "data drift vs concept drift; PSI, KS and Jensen–Shannon tests per feature; schema and null-rate drift that silently corrupt features; proxy metrics while labels arrive days or weeks later" — the full syllabus line, clause by clause:
  - *data drift vs concept drift:* **data drift** is the input distribution moving (customers' order sizes shift with a new product line); **concept drift** is the relationship between inputs and the label moving even if inputs look the same (a feature that predicted churn well last year stops meaning the same thing); the topic reproduces one of each on the shop's data and shows that a feature-distribution monitor catches the first and misses the second entirely.
  - *PSI, KS and Jensen–Shannon tests per feature:* three complementary per-feature tests, each with its own shape: the **Population Stability Index** bins a feature and compares bucket proportions between a reference and a current window (a widely used rule of thumb reads below 0.1 as no significant drift, 0.1–0.2 as worth investigating, and above 0.2 as significant — stated as a convention to calibrate, not a law); the **Kolmogorov–Smirnov** test compares the two windows' empirical cumulative distributions without binning and comes with a p-value, so it answers whether an observed gap is larger than sampling noise would explain, for continuous features; **Jensen–Shannon divergence** is a bounded, symmetric measure (0 to 1) that handles zero-probability bins gracefully, useful for sparse or categorical distributions and for comparing full output distributions. The topic runs all three against the same synthetic shift so their disagreement on one case is visible, not asserted.
  - *schema and null-rate drift that silently corrupt features:* a feature that quietly starts receiving a different type, a new categorical value never seen in training, or a rising null rate is not a distribution shift a PSI/KS/JS test over the non-null values will necessarily flag — the topic reproduces a null-rate creep that a naive mean-imputation pipeline absorbs silently, changing the feature's effective meaning with no distributional alarm at all, and the schema/null check that does catch it.
  - *proxy metrics while labels arrive days or weeks later:* when the true label (topic 3's "delayed label") takes days or weeks, the team cannot wait for ground truth to notice a problem, so it watches **proxies** — the input and output distributions themselves, confidence-score distributions, downstream business signals — explicitly named as proxies, with the gap between "the proxy moved" and "the model got worse" stated honestly rather than treated as equivalent.
- **Leaves out:** retraining policy and when a drift alert should trigger one (a judgment call named, not resolved, since it depends on cost — out of this topic's scope); the versioning of the dataset used as the "reference window" (topic 4, reused); embedding-specific drift, which gets its own cost profile in the next topic.
- **Outcomes:** Classify a reproduced shift as data drift, concept drift, or both; run PSI, KS and Jensen–Shannon on the same feature pair and explain a case where they disagree; detect a null-rate creep that a per-feature distributional test misses and say what check does catch it; name which signals are available as proxies while a label is delayed, and state precisely what a proxy's movement does and does not prove about real model performance.
- **Introduces:** `data-drift-vs-concept-drift`, `psi-ks-js-per-feature-tests`, `schema-and-null-rate-drift`, `proxy-metrics-during-label-delay`. **Uses:** `dataset-snapshot-reproducibility`, `label-version-drift` (topic 4); `feature-ttl-staleness`, `label-feature-timeline-join` (topic 1); `log-and-wait-label-join` (topic 3, the delayed-label mechanism this topic's proxies stand in for). **Declared:** basic descriptive statistics (a histogram, a cumulative distribution).
