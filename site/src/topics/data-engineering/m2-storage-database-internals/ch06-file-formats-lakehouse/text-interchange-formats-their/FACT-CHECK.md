## Currency check

- RFC 4180 (October 2005) and RFC 8259 (December 2017) are both final, unchanged standards-track RFCs; no later RFC obsoletes or updates either for the clauses this topic relies on. No currency risk.
- The Unicode BOM FAQ is a living page with no version number; re-fetched 2026-10-30 and quoted directly from that fetch. No currency risk for the stated mechanism (U+FEFF's role), which has been stable since Unicode's own BOM convention was introduced.
- jsonlines.org is a community convention page, not a standards document; it is cited only for the specific, narrow claim that JSONL requires no BOM and uses `\n`, both of which the page states as its own normative "requirements," not as a claim about any external standard.

## Red team

1. **"Is the backslash-escape example a strawman — does any real CSV producer actually write a backslash escape?"** Not a strawman: several non-conformant CSV writers (notably some MySQL `SELECT ... INTO OUTFILE` configurations and some shell-generated exports) do emit a backslash-escaped quote by convention, which is exactly why RFC 4180's doubled-quote rule and the backslash convention collide in practice. The reel doesn't claim backslash-escaping is a format anyone should write; it demonstrates what a strict RFC 4180 reader does when it meets one.
2. **"Is 9,007,199,254,740,993 a realistic order id, or a contrived edge case that never occurs in practice?"** It's 2^53 + 1 specifically because that's the smallest positive integer a double can't represent exactly — chosen to be the precise boundary RFC 8259 §6 names, not an arbitrary large number. Real-world analogs exist (Twitter/X snowflake ids, some database auto-increment bigints) that do exceed 2^53 and have caused this exact class of bug in JavaScript-based pipelines; the claim on screen is scoped to "a number this large can lose precision," not to any specific vendor's id scheme.
3. **"Does showing the backslash-escape result as the same colour (not red/bad) as the correct result undersell that it's wrong?"** `OUTLINE.md`'s step 3 storyboard explicitly notes "no red; just focus/quiet contrast" because the backslash case is a *misparse*, not a *crash* — DESIGN.md reserves `C.bad`/red for a failure/danger/wrong-answer state. A misparsed-but-successfully-returned string is distinguished by being visibly the wrong text next to the right one, which the caption and takeaway state explicitly; this is a correctness issue, not a crash, so red is reserved for step 6's BOM parse failure instead, which is a true thrown exception.
4. **"Is claim 5 (JSON encoding/BOM) now correctly scoped after the nuance was added?"** Re-checked against the exact RFC text: §8.1 requires UTF-8 outside a closed ecosystem, forbids a writer from adding a BOM, and explicitly leaves readers free to either reject or tolerate one. The reel now attributes the rejection to "a parser that doesn't tolerate it" (true of Python's own `json` module, demonstrated directly in `examples.py`) rather than claiming the RFC itself mandates rejection, which the fetched text does not support.
5. **"Could the JSON-precision example be an artifact of Python's own `parse_int=float` hook rather than a real double-precision JSON parser's behaviour?"** `parse_int=float` is used deliberately to *simulate*, inside this sandbox, exactly what a double-precision-only JSON implementation does when it decodes every number as a double — the same representation RFC 8259 §6 itself names (IEEE 754 binary64). This is disclosed in the function's own docstring and in `OUTLINE.md`'s claims list (claim 4), not presented as "we ran a second real JSON library," since the point (binary64 can't hold 2^53+1 exactly) is a property of the number representation, not of any one parser's code.
