## The chapter

### The problem it solves

Chapter 5 went all the way down to the single page a database engine reads and writes, and all the way out to replication, partitioning and the probabilistic sketches a distributed system needs at scale — but every one of those topics assumed a *database*: one engine that owns its own files and decides their format. This chapter opens the much more common shape data actually takes today: files sitting in object storage, written by one tool and read by five others, with no single engine's internals to rely on. It starts at the bottom, with the physical bytes themselves — the row-oriented text formats everyone still has to accept at the edge (CSV, JSON) and the row-vs-columnar decision every later format makes once (§6.1) — then spends real time on the one columnar format that won the lakehouse (Parquet): its file anatomy, the encodings that make it small, the record-shredding trick that lets it hold nested data at all, and the statistics that let a query skip most of the file without reading it (§6.2). It then asks the question a plain file can't answer on its own: what does "a table," with atomic commits, concurrent writers, time travel and schema evolution, mean when the storage underneath is an object store with no atomic rename and no file you can edit in place? Chapter 6's middle third is the answer every modern table format converges on — snapshots, optimistic commits, copy-on-write vs merge-on-read, deletion vectors, compaction — taught once as shared foundations (§6.3) before two real implementations (Iceberg, Delta) show the same ideas as actual running systems (§6.3.1–§6.3.2), and a shared catalog layer shows how more than one of those tables gets discovered and governed at all (§6.3.4, §6.3.6). It closes by turning to the engines that actually read all of this: general-purpose lakehouse query engines (Trino, ClickHouse, DuckDB, §6.4) and the three cloud data warehouses most of the learner's future career will actually involve tuning (Snowflake, BigQuery, Redshift, §6.5), ending on the one question every one of those engines eventually forces: when does a managed warehouse beat an open lakehouse engine, and when does it not. The learner leaves able to explain, with a real Parquet footer and a real Iceberg or Delta table they built themselves in this sandbox, why the "mutable table on an immutable object store" problem exists at all and exactly how each format solves it — not as marketing claims, but as mechanisms they can point to in a file.

### Order of ideas, and why

1. **§6.1 Serialization and file formats (topics 1–3).** Two refreshers set the floor before any new mechanism: the row-oriented text formats everyone still has to accept at the edge, and why they have no types, no schema and no columnar pushdown (1) → the row-vs-columnar-vs-PAX decision every later format in this chapter makes once, so "columnar" has a precise meaning before Parquet is ever named (2) → schema evolution across formats, the one genuinely new topic of the section, which needs topic 1's formats and topic 2's columnar vocabulary as the vocabulary it compares against, and sets up the column-ID machinery §6.3 reuses (3).
2. **§6.2 Parquet and columnar storage (topics 4–9).** Parquet's own file anatomy first, since every later topic in this section is a mechanism *inside* that anatomy (4) → the columnar encodings that live inside the pages topic 4 just named (5) → nested data (repetition/definition levels), the one part of topic 4's anatomy complicated enough to need its own topic, and only teachable once pages and column chunks already exist (6) → data skipping (statistics, page indexes, bloom filters), which depends on topic 4's footer metadata and topic 5's encodings to explain what gets skipped and why (7) → the Variant type and shredding, a genuinely new logical type that depends on topic 6's shredding vocabulary by direct analogy (8) → ORC vs Parquet, closing the section by comparing everything topics 4–8 just built against Parquet's one real rival (9).
3. **§6.3 Transactional table formats: shared foundations (topics 10–20).** Object storage's own guarantees first, since every later topic in this section is a mechanism built *because* of what object storage does and doesn't guarantee (10) → why Hive-style tables broke, the direct consequence of topic 10's guarantees (no atomic rename, listing cost) meeting a real workload (11) → snapshot-based table metadata, the first half of the fix every modern format converges on (12) → optimistic commits, the second half: how a snapshot actually gets written without two writers corrupting each other (13) → copy-on-write vs merge-on-read, the fundamental choice every later operation (deletes, updates) makes against the commit model topics 12–13 just built (14) → deletion vectors, the one deletion mechanism precise enough to need its own topic, and only explainable once topic 14's MOR concept exists (15) → schema evolution with column IDs, returning to topic 3's cross-format problem now solved the table-format way (16) → snapshot lifecycle (time travel to garbage collection), the natural next question once topic 12 established that a snapshot is a real, addressable thing (17) → small files and compaction, the maintenance bill topic 14's MOR path and ordinary ingestion both create (18) → data layout (sorting, Z-order, Hilbert), which decides whether topic 7's and topic 12's statistics actually prune anything (19) → incremental reads and change feeds, closing the section by showing that a sequence of topic 12's snapshots is itself a new kind of readable object (20).
4. **§6.3.1–§6.3.2 Iceberg and Delta (topics 21–30).** Section 6.3 is taught once in the abstract; these ten topics show the same ideas as two real, concretely different systems. Iceberg first: its metadata tree and scan planning, the direct concretization of topics 12–13 (21) → hidden partitioning, Iceberg's own answer to a problem §6.3 never raised (partition columns the query never has to name) (22) → position and equality deletes, Iceberg's concrete version of topic 15's deletion vectors, including the delete mechanism (equality deletes) deletion vectors are replacing (23) → Iceberg v3 spec features, which only make sense once topics 21–23 establish the v2 baseline they extend (24) → Iceberg statistics and Puffin files, extending topic 7's data-skipping vocabulary with table-level, not just file-level, statistics (25) → branches, tags and write-audit-publish, closing the Iceberg arc with a workflow that depends on topic 21's snapshot tree existing as addressable refs (26). Delta next, structured as a direct comparison: the Delta transaction log, Delta's own concretization of topics 12–13 built from a visibly different mechanism (an ordered JSON log, not a metadata tree) (27) → Delta's commit protocol and catalog-managed tables, the put-if-absent mechanics topic 27's log depends on, and where Delta's own catalog story is heading (28) → Delta DML (MERGE/UPDATE/DELETE), the concrete operations that produce the log entries topics 27–28 described (29) → Delta Lake 4.x and Delta Kernel, closing the Delta arc with the current release line and the library that lets every non-Spark engine read it correctly (30).
5. **§6.3.4, §6.3.6 Catalogs and choosing a format (topics 31–33).** Catalogs as commit coordinators, the abstraction both topic 21's and topic 27's "atomic pointer move" actually needs a place to live (31) → the Iceberg REST catalog protocol, the one concrete, vendor-neutral implementation of topic 31's abstraction worth teaching in depth, since it is what topics 21–26's Iceberg tables actually commit through in production (32) → choosing a table format and catalog, closing the whole §6.3 arc (topics 10–32) with the decision framework a real engineer applies, now that both real formats and the catalog layer are on the table (33).
6. **§6.4–§6.5 Query engines over the lakehouse and cloud warehouses (topics 34–40).** Trino first, the general-purpose federated engine that reads everything topics 21–33 just built, with no storage of its own (34) → ClickHouse, a deliberately different architecture (its own MergeTree storage, not a reader of someone else's tables) that answers "what if the engine does own its storage after all" (35) → DuckDB, closing the open-engine trio with the single-node, in-process case, directly extending topics 10–33 since this chapter's own labs already lean on it as the engine of record (36) → Snowflake storage internals, opening the cloud-warehouse trio by showing a fourth, proprietary micro-partition design next to topics 4–9's Parquet (37) → BigQuery's Dremel execution and storage, a second proprietary design built on genuinely different infrastructure (Colossus, Borg, Jupiter) (38) → Redshift distribution and sort keys, a third proprietary design descended from classic shared-nothing MPP rather than Snowflake's or BigQuery's disaggregated model (39) → warehouse versus lakehouse engine choice, closing the chapter (and handing off to Chapter 7's Spark material) with the decision topics 34–39 all set up: when a managed warehouse's engine beats an open lakehouse engine reading topics 21–33's own tables, and when it does not (40).

### 1. Text interchange formats and their traps (`de.text-interchange-formats-their`): refresher, §6.1

### 5. Columnar encodings: dictionary, RLE, delta, byte-stream-split (`de.columnar-encodings-dictionary-rle`): full, §6.2
