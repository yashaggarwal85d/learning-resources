## Currency note

Both sources fetched 2026-10-31. Iceberg spec is the v3/v4-current page at iceberg.apache.org/spec/ (same source as topic 12, fetched fresh for this topic). Delta's concurrency-control page is the open-source docs.delta.io page, not a Databricks-proprietary page — it was chosen over Databricks' docs because this chapter cites only open, vendor-neutral specs/docs per topics 1-12's established sourcing discipline.

## Red-team

1. **"WriteSerializable vs Serializable isolation levels" (CHAPTER.md's originally planned framing) does not appear in the open-source Delta docs.** That specific two-named-levels framing (`delta.isolationLevel` = `Serializable` / `WriteSerializable`) is a Databricks-platform feature, documented only on docs.databricks.com, not in the open-source Delta Lake project's own docs.delta.io or PROTOCOL.md. Rather than cite a vendor-specific page as if it were the open Delta Lake spec, this topic uses what docs.delta.io actually documents: the three-stage optimistic-concurrency protocol and its five named conflict exceptions, which is the real open-source equivalent of "writers can choose what to validate." Topic 13's reel text was adjusted to match (no claim of a named "WriteSerializable" level); Iceberg's own "writers can select what to validate" quote (claim #11) carries the "isolation is a choice" idea instead, sourced correctly.
2. **The local-disk demo's "delete" is really a file removal from the snapshot's file list, not a real row-level delete file.** This is disclosed in examples.py's docstring and above: the specific mechanism that transfers is the validate-before-retry shape (is the named file still present?), not a claim that this reproduces Iceberg's actual position/equality delete-file machinery, which is a separate, more complex on-disk format covered nowhere in this topic.
3. **The two "writers" in examples.py are sequential Python calls in one process, not real concurrent processes.** Same disclosed limitation as topic 12's compare-and-swap race — the CAS primitive (`os.open(O_CREAT | O_EXCL)`) is genuinely atomic and OS-enforced regardless of whether the two calls happen to be sequential in one script; what's being demonstrated is the correctness of the retry logic given a real atomic primitive, not a stress test of concurrency itself.
4. **Partitioning-based conflict avoidance (claim #12) is named but not built.** Demo 1 and 2 model file-level conflict (same base, overlapping vs disjoint files); they do not build a partitioned table or demonstrate that two writers hitting different partitions never generate a CAS race at all. This is explicitly scoped out — the reel names it as the documented mitigation without claiming to have reproduced it, consistent with this topic's 20-minute budget and its handoff to topic 14 (copy-on-write vs merge-on-read), which is the next topic that actually builds row-level delete files.
5. **Iceberg's "Replace operations" quote names format changes and compactions as examples, not row-level deletes specifically.** The reel's step 7 uses "delete vs delete" language for demo 2, which maps most directly to Iceberg's "Delete operations must verify that specific files to delete are still in the table" clause (claim #6), not the "Replace operations" clause (claim #5) — both are quoted and both describe the same validate-the-named-files-are-still-present shape, so the reel's choice of wording (framing demo 2 as a delete/compaction conflict) is consistent with either clause; FACT-CHECK's claims table attributes demo 2 to claim #6 and #9 specifically to avoid conflating the two.

## Problem-solving notes

- CHAPTER.md's planned source line ("Delta Lake's protocol documentation on optimistic concurrency control and its WriteSerializable vs Serializable isolation levels") turned out not to match what PROTOCOL.md or even docs.delta.io actually say — PROTOCOL.md has no isolation-level section and docs.delta.io's concurrency-control page documents the three-stage protocol and conflict-exception taxonomy instead, with no "WriteSerializable" naming (that is Databricks-proprietary). Resolved by sourcing from what docs.delta.io actually contains and adjusting the reel's claims to match (see red-team #1), rather than fabricating a quote or reaching for a non-open-source page.
- `examples.py` demo 1 initially failed because `try_atomic_swap` wrote both writers' staged snapshot content to the *same* filename (`snapshot-{version}.json`) before checking the CAS marker, so the losing writer's write clobbered the winning writer's snapshot content even though the CAS correctly rejected it. Fixed by giving every staged snapshot a globally unique filename (version + random suffix) so only the CAS marker — not the snapshot filename — decides which writer's content becomes canonical.
