# Outline — de.schema-evolution-column-ids

DE §6.3 · 10 steps

1. **Hook** — bridge from topic 15: "A deletion vector works because a row's identity survives fine inside one data file. This topic is what happens when a whole column needs to survive a rename or reorder at the table level — exactly the problem topic 3 raised for Parquet alone, now solved by Iceberg's field IDs and Delta's column mapping."
2. **Predict** — a table renames a column and inserts a new one before it. If a reader still matches columns by their position in the file, what happens to the data? (A) Nothing — the data just reads back correctly. (B) Every column after the insert silently reads the wrong file column's data. Correct: B — this is topic 3's own corruption, now reproduced on a real on-disk table.
3. **Reveal: reproduced for real — position-based matching corrupts the table** (takeaway) — real measured result: the inserted column silently takes the next column's real value, and every later column shifts one slot wrong, just as topic 3 showed for plain Parquet.
4. **Reveal: Iceberg's real fix — columns are selected by field ID, never by name or position** — Iceberg's own spec: "Columns in Iceberg data files are selected by field id... Renaming an existing field must change the name, but not the field ID."
5. **Reveal: reproduced for real — field-ID projection survives the identical rename and insert** (takeaway) — real measured result: the renamed column still resolves to its real data, and the genuinely new column correctly reads back missing — read from the same real file as step 3, this time by field ID.
6. **Predict: how does Delta, which uses real Parquet files with real column names, survive a rename without a rewrite?** — (A) It always rewrites the Parquet file to the new name. (B) A stable physical name is kept in metadata, separate from the logical name. Correct: B — Delta's column mapping.
7. **Reveal: without column mapping, a rename really does rewrite the file** — real measured result: with the physical column name equal to the logical name, renaming a column is a real file rewrite, measured directly on disk.
8. **Reveal: reproduced for real — column mapping renames without touching the data file** (takeaway) — Delta's own docs: column mapping "enables Delta schema evolution operations such as RENAME COLUMN and DROP COLUMNS on a Delta table without the need to rewrite the underlying Parquet files." Real measured result: the data file's bytes are byte-for-byte identical before and after the rename.
9. **Reveal: the same stable-ID idea also makes three more moves safe** — Iceberg's own default-value rules ("The initial-default must be set when a field is added and cannot change... The write-default... may change") show why adding a column, widening a type, or evolving a nested struct are all safe once identity no longer depends on name or position.
10. **Recap** — a stable ID (Iceberg's field ID, Delta's physical column name) is what makes rename, reorder, add, widen and nested-struct evolution all safe; name- or position-based matching is the real failure mode underneath every one of them.
