## Delta Kernel, Introduction

URL: https://docs.delta.io/kernel/rust/introduction
Version: fetched 2026-11-02

> Delta Kernel is a Rust library for building Delta Lake connectors. It handles the
> Delta protocol so you don’t have to. Connectors read and write Delta tables through
> Kernel’s API without needing to understand the protocol internals.

> Kernel is query-engine agnostic.

### Red team

- No deltalake/delta-rs library has been avoided in this topic — it is the point: this is the
  first topic in the chapter to deliberately install and use `deltalake` (the delta-rs Python
  binding) directly, rather than hand-building the mechanism, because this topic is specifically
  about delta-rs and Delta Kernel as real, independent implementations of the protocol the rest of
  the chapter has been hand-building.
- CHAPTER.md's own syllabus line groups "Flink, Trino, DuckDB, delta-rs" together as engines that
  use Delta Kernel. That grouping is wrong for delta-rs: DuckDB's own blog post explains it chose
  Kernel specifically *instead of* delta-rs, because delta-rs is a separate, independent Rust
  implementation of the Delta protocol (the same one `deltalake` is built on), not a Kernel
  connector. This topic corrects that and states delta-rs as a standalone implementation, Kernel
  as the separate shared-protocol library other engines (DuckDB, confirmed) build on instead.
- CHAPTER.md's syllabus line also says Variant shredding is "out of preview in 4.3." Delta Lake
  4.3.0's own release notes show the feature is still named `variantShredding-preview` in 4.3, with
  a separate, still-optional `Production-Ready` flag whose enforcement had not yet shipped as of
  that release. This topic states the actual 4.3 status rather than repeating CHAPTER.md's claim,
  the same kind of correction topic 28 made for a different wrong date in this chapter.
- Delta Kernel itself is a Java/Rust library with no Python bindings usable in this sandbox, so it
  is named and sourced, not built. The script's own `deltalake`/delta-rs demos are a different,
  independently-implemented engine exercising the same protocol, not Kernel itself.
- Collations and the Geospatial table feature are both documented as Delta Kernel features
  specifically (not Delta Spark) in the 4.2.0 release notes -- this topic states that precisely
  rather than attributing them to "Delta Lake 4.x" generically.
- Type widening's own docs page states it reached full support in Delta Lake 4.0, not newly in the
  4.x line generally -- stated with that precision rather than CHAPTER.md's looser "4.x" framing.
- The real protocol-feature-enabling demo (deletion vectors, row tracking, Variant type) in
  examples.py uses delta-rs's own `TableFeatures` enum and `alter.add_feature` API against a local
  table -- a real protocol action written by a real, independent implementation, not a simulation.
