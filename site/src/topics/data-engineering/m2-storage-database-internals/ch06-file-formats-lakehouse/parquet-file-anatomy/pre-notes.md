- **A page as a fixed unit of I/O**: background from Chapter 5's own page material (§5.1) and this chapter's own PAX topic, where a page is a database engine's own fixed-size I/O unit. *Where you meet it:* Parquet's own "page" borrows the name and the "fixed region of a file" idea, but is a compression/encoding unit inside a column chunk, not a database engine's storage page.
- **Columnar layout**: storing one column's values together rather than one row's values together, from this chapter's row-vs-columnar topic. *Where you meet it:* the reason a Parquet file groups values into column chunks in the first place, and why a dictionary can see a whole column before choosing how to encode it.
- **Schema resolution across a rename**: how a reader matches a writer's fields to its own, from this chapter's schema-evolution topic (by name, by number, or by a stable ID). *Where you meet it:* Parquet's own schema lives in exactly the footer this topic reads, and its column-matching options come back when table formats add their own IDs on top, later in this chapter.
- **Thrift as a serialization format**: a binary, schema-defined encoding used to describe structured data compactly, general background. *Where you meet it:* Parquet's footer is itself one Thrift-encoded structure (`FileMetaData`), compact-protocol encoded, which this topic's own code decodes by hand.
- **Unix epoch time**: a timestamp as a count of time units since 1970-01-01 UTC, general computing background. *Where you meet it:* both of this topic's timestamp columns — the legacy and the modern one — are built on exactly this count, which is where the two readers' disagreement starts.
