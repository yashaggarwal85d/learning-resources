## Currency check

- The Wikipedia LSM-tree article and the three RocksDB wiki pages were all fetched on 2026-10-24. The RocksDB pages describe the current, maintained engine (the Bloom Filter page's own "since version 6.15.0" and "format_version=5 (version 6.6) and later" notes show it is kept up to date); nothing taught here (memtable, flush, pipelining, point/range read order, tombstones, Bloom filters, the block index) depends on a version-specific knob that has since changed.
- The original O'Neil et al. 1996 Acta Informatica paper could not be fetched (see "Changes from the chapter plan" in `OUTLINE.md`): the UMass Boston mirror serves a broken TLS certificate chain (confirmed with a direct `curl -v`, not a proxy artifact — the handshake fails with "self-signed certificate in certificate chain" before any proxy-side policy applies) and the UC Berkeley course mirror now 404s. The Wikipedia article is used instead; it states the same mechanism in the same terms (C0/C1/C2 components, tombstones, Bloom filters, the merge-via-priority-queue) and nothing in it conflicts with what the paper is known to have introduced.
- RocksDB's concrete numbers (bits-per-key effectiveness table, Ribbon filter savings, the 500000000-style freeze-age tuning seen in the previous topic) are not claimed here at all; this topic only claims the mechanisms and this sandbox's own measured counters, so there is no version-skew risk from RocksDB release-to-release tuning changes.

## Red team

1. **"Is '0 L0 hits' in claim 14 really proof the file was never opened, or could RocksDB open the file and just not count it as a 'hit'?"** `rocksdb.l0.hit` is RocksDB's own statistic for "key found at L0," incremented only when a get is actually answered from an L0 file; a file RocksDB decided not to consult (because the memtable already answered the query) produces no hit of any kind, counted or not. The claim is phrased as "0 L0 hits," which is exactly what the counter measures, not a stronger claim about file-open syscalls the experiment can't directly observe. Held, with the OUTLINE.md wording kept to what the counter actually shows.
2. **"Step 6's '494 rejected, 6 false positives, 0 wrong answers' — could any of the 6 false positives have actually been for keys that DO exist, making it not a false positive?"** No: the 500 probed keys (`k000000a` through `k000499a`) are constructed to differ from every real key (`k000000`–`k000499`) by an appended character, and the experiment's own assert (`true_positives == 0`) confirms none of them were ever actually found. Held.
3. **"Doesn't claim 8's 'merged via a priority queue' overstate what `examples.py`'s `range_read_merges_sorted_runs` actually tests, since `rocksdict`'s own iterator might not literally use a priority queue internally?"** The claim about the priority-queue *mechanism* is attributed to the Wikipedia source describing LSM trees generally, not to `examples.py`; `examples.py`'s own claim (claim 15) is scoped correctly, to the observable *result* of the merge (each key once, newest value, sorted order) rather than to RocksDB's internal implementation detail. The storyboard (step 5) keeps the same separation: the visual names the behavior, not the exact data structure RocksDB uses internally. Held.
4. **"Is 'a point read stops at the first match' (step 4's takeaway) too strong — could RocksDB sometimes check more than one structure even after finding a match, e.g. for MVCC/snapshot reasons?"** For the simple get() this topic measures (no open snapshot), yes, it stops at the first match, which is exactly what the measured 1-memtable-hit/0-L0-hit counters in claim 14 demonstrate. Snapshot-based reads (an `Iterator` or a held `Snapshot`) can need to look further to find the version visible to that snapshot, but that mechanism belongs to RocksDB's own `Snapshot` API (named in `rocksdb-overview.txt` but out of this topic's scope) and is not claimed or shown here. Held, with the scope kept to the plain get() this topic actually measures.
5. **"Step 7's block index claim — is a binary search over a whole SST file's data blocks still cheap once `optimize_filters_for_hits` or partitioned indexes are in play?"** Those are documented optimizations/variants of the same mechanism (named in `bloom-filter.txt` and `block-based-table-format.txt`'s own cross-references) and don't contradict the base claim this topic makes: a per-file index block, built once at write time, turns "search this whole file" into "find one data block." The variants are left to `post-notes.md` → Frontier rather than taught as if they changed the base mechanism. Held.

## Problem Solving

- **The original primary source (O'Neil et al.'s 1996 LSM-tree paper) could not be fetched.** The UMass Boston author mirror's certificate chain fails TLS verification (confirmed independent of the session's own HTTPS proxy, via a direct `curl -v` showing the handshake failing before reaching the proxy's own CA); the UC Berkeley course mirror that used to host a copy now returns 404. **Fixed** per the skill's own rule — substituted the Wikipedia article on the structure, which states the same mechanism in the same vocabulary (memtable/C0, immutable components, tombstones, Bloom filters, the merge) and is independently fetchable and verifiable, rather than citing the original paper from memory.
- **GitHub wiki pages 403 when fetched directly** (`https://github.com/facebook/rocksdb/wiki/<Page>`), the same class of failure as the previous session's `dev.mysql.com` and MariaDB KB issues. **Root-caused** as GitHub's own bot detection on rendered wiki pages specifically (plain `github.com` repository pages also 403'd the same way; `raw.githubusercontent.com` file URLs did not). **Fixed** by using GitHub's wiki raw-content URL form, `https://raw.githubusercontent.com/wiki/<owner>/<repo>/<Page>.md`, which returns the same Markdown source as the rendered wiki page and fetches cleanly.
- **The syllabus clause "guided by per-file Bloom filters and block indexes" had no source for the "block indexes" half** after the first two RocksDB wiki pages were fetched (Overview and Bloom Filter). **Fixed** by fetching a third RocksDB wiki page, `Rocksdb-BlockBasedTable-Format`, which documents the index block directly ("Index blocks are used to look up a data block containing the range including a lookup key. It is a binary search data structure.") — added as `SOURCES.md`'s fourth source before any syllabus clause was left uncovered.
