## Red team

- **Could the old tuple simply be deleted immediately instead of kept?** No — if it were, a concurrent reader with an older snapshot would have nothing to read, directly contradicting `pg-mvcc-model`'s own claim that reading never blocks writing. The old tuple's survival until nothing needs it is the mechanism, not an implementation accident.
- **Does "no private copies" (InnoDB) mean the undo log is a copy, contradicting itself?** No — "no private copies" describes the table's own data structures (indexes and the clustered row itself stay single-copy); the undo log is explicitly a separate structure, which the same source sentence says in the next clause.
- **Is "snapshot too old" actually about table size, not time?** No — re-read `oracle-snapshot-too-old`: the trigger is other writers' undo overwriting the specific records a reader still needs, which is a function of write *volume* and read *duration*, not the table's own row count. A small, rarely-written table with one very long read is just as exposed as a huge, heavily-written one.
- **Counter-example attempted against the predict-4 question:** could a real system "wait" for the old value instead of reconstructing it from a log, making option (a) partly correct? Lock-based databases without MVCC do block readers behind a writer's lock — but neither InnoDB nor Oracle (the two systems this topic names) do that for ordinary reads; both are confirmed MVCC systems by their own docs (`innodb-read-view`, `oracle-undo-read-consistency`). Option (a) stays wrong for the systems actually named.
- **Counter-example attempted against the predict-10 question:** could raising `undo_retention` be a complete fix if the workload is static and known in advance? In principle a sufficiently generous, permanently fixed retention could outlast any read that will ever run — but the documented mechanism (lines 846–852) is retention as a *target*, not a hard cap, and real production workloads grow; the question's own framing ("a nightly report job," an ongoing job, not a one-off) makes the delay-not-cure framing the honest answer for the scenario asked.
- **Checked index-maintenance claim scope:** `OUTLINE.md`'s claim about index maintenance is deliberately narrow (ctid changes on a Postgres update vs. InnoDB's fixed clustered-key location) rather than a specific claim about whether InnoDB skips secondary-index work on a non-key update — that more specific claim could not be verified against a current, fetchable MariaDB page (see "Problem Solving"), so it was left out rather than asserted unsourced.

## Problem Solving

- **`dev.mysql.com` returns HTTP 403 on every fetch attempt** (confirmed again this topic, same failure as the previous topic's research) — worked around entirely with MariaDB's own current documentation (`mariadb.com/docs/server/...`), which covers the same InnoDB mechanisms as a real, fetchable, current primary source.
- **A specific claim about InnoDB skipping secondary-index maintenance on a non-indexed-column update could not be sourced.** Searched for a current MariaDB docs page addressing it directly; the two most likely URLs (`mariadb.com/docs/server/sql/features/indexes/enterprise-server/secondary` and the `/docs/all/...` variant) both returned HTTP 404 at fetch time, and a MariaDB Enterprise Server page surfaced only in search summary (not independently fetched and verified) suggested secondary indexes actually use their own copy-on-write/delete-marking behaviour for MVCC — which would have made the originally planned claim wrong, not just unsourced. Caught before writing `OUTLINE.md`'s claims list: the index-maintenance claim was narrowed to only what `innodb-clustered-pk` and `pg-heap-tuple-header` actually support (fixed physical location vs. a changing `ctid`), and the more specific, unverifiable claim was dropped entirely rather than asserted.
- **Designing `examples.py`'s heap-tuple proof (claim 12) required controlling page placement.** A `pageinspect` read of `heap_page_items` on a specific page only shows both the old and new tuple together if the update's new tuple actually lands on that same page. Caught during design, before running anything: used a fresh, single-row table (so the first update's new tuple has trivially enough room on page 0) rather than a larger table where a real engine could legitimately place the new tuple elsewhere.
