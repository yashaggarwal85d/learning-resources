# Fact-check — de.vacuum-bloat-transaction-id

Role: adversarial fact-checker, not the author. Every claim re-derived from the fetched source text in `sources/`, not from memory of writing `OUTLINE.md`.

## Claims

| # | Claim | Status | Evidence |
|---|---|---|---|
| 1 | An UPDATE/DELETE's old row version is not immediately removed; VACUUM reclaims its space for reuse but does not return it to the OS except at the end of the file. | Confirmed | `pg-routine-vacuuming.txt` §24.1.2: "does not immediately remove the old version of the row... ## Currency check

- All four Postgres documentation sources were fetched against the "current" (18) manual on 2026-10-24; the banner on each page notes PostgreSQL 19 RC 1 was released October 15, 2026, but no 19-specific change to vacuum, HOT, the visibility map, replication slots or XID wraparound is documented on these pages, and this sandbox's own cluster is 16.15 — the mechanisms taught here (dead tuples, HOT's two preconditions, the visibility map, the threshold formula, 32-bit circular XID comparison, the warning/error thresholds, the three-step recovery) are all present, word for word, in the PostgreSQL 16 release notes' predecessors and have been stable since long before 16; nothing here is version-skewed.
- One live detail the PG18 doc has that 16 does not: "eager scanning" (`vacuum_max_eager_freeze_failure_rate`, mentioned in §24.1.5). This sandbox's 16.15 cluster doesn't have that knob. It is **not** used as a claim or shown on screen; it is named once in `post-notes.md` → Frontier as "PostgreSQL 18's own addition," explicitly scoped there rather than taught as if universal.
- Sentry's postmortem is from 2015 and describes Postgres of that era (pre-9.4's freezing mechanism, named in a `pg-routine-vacuuming.txt` note, replaced an XID in place rather than setting a flag bit — a detail Sentry's own post doesn't mention and this topic doesn't need). The *outage mechanism* itself (XID wraparound, autovacuum, the fix direction) is unchanged in every version since; it's cited as a real historical incident illustrating a still-current failure mode, not as current configuration advice to follow verbatim (hence claim 11's correction above).

## Red team

1. **"Doesn't a HOT update still need vacuum eventually, so is step 3's takeaway ('skips the index entirely') overstated?"** No — the claim is specifically about the *index*, not all cleanup. HOT updates still leave dead tuples that ordinary VACUUM (or opportunistic pruning) must reclaim; the reel's own step 2 teaches that half, and step 3's takeaway is scoped to "the index" only, matching the source's own two-part claim (no new index entry; *and separately*, intermediate versions may be pruned outside VACUUM). Held.
2. **"Could index-only scans make HOT's index-size numbers actually vary with query pattern, not update pattern?"** No — `pg_relation_size` measures the index's own on-disk bytes regardless of how any later query reads it; the experiment never runs an index-only scan, so this doesn't contaminate the measurement. Held.
3. **"Is it true that VACUUM 'can't tell apart' a load-bearing open transaction from a forgotten one, or does Postgres actually log which backend/slot is the oldest?"** Postgres *can* surface which backend or slot has the oldest xmin (`pg_stat_activity`, `pg_replication_slots`) — that's exactly how the documented recovery steps find them. The reel's step 5 claim is narrower and still true: VACUUM's own decision of what it may reclaim depends only on the horizon value, not on *why* that horizon is where it is; a human, not VACUUM, has to go look up which backend or slot is responsible. Clarified in step 5's narration rather than left ambiguous.
4. **"Would a reader push back that the sandbox's 600-row-table bloat is too small to generalize to real production tables?"** The experiment's purpose is to make the *mechanism* visible, not to model production scale; the Sentry citation supplies the production-scale consequence (a multi-hour, real outage) the small experiment can't itself demonstrate. The storyboard pairs them for exactly this reason (step 6 for mechanism, step 8/10 for real-world stakes).
5. **"Is 'disable autovacuum' really common advice, or is that Sentry's own framing for dramatic effect?"** Sentry's post states it plainly as something "the internet is full of" — not something this topic invented; still, it's attributed as Sentry's own characterization (narration says "Sentry's own postmortem calls this out," not "it is widely known that"), so the claim's strength matches its sourcing.

## Problem Solving

- **`pg_stat_user_tables` reads were stale for up to ~1.5 seconds after the DML that should have changed them**, even from a fresh `autocommit=True` connection, because Postgres's stats collector flushes asynchronously rather than synchronously with the triggering statement. The first version of `examples.py` read `n_dead_tup` and `n_tup_hot_upd` immediately after a batch of updates and got zeros across the board, including for inserts that had clearly completed. **Root-caused** by testing with growing `time.sleep()` delays interactively until the real counts appeared, then confirming the delay was a stats-flush interval rather than a `stats_fetch_consistency = cache` transaction-caching issue (ruled out by testing with both a single long-lived connection and fresh connections per read). **Fixed** by writing a `wait_for()` poll helper that re-queries every 0.3s up to a 6s timeout until the value satisfies the expected predicate, used for every `pg_stat_user_tables` read; `pg_relation_size`/`pg_total_relation_size` and `pg_class.age(relfrozenxid)` needed no such polling, since they reflect the catalog directly rather than the asynchronous stats collector.
- **The first design for the HOT-vs-non-HOT comparison (updating the same single row many times, like the previous topic's growth experiment) produced a non-deterministic dead-tuple count** (43 unpruned dead tuples after 400 HOT updates to one row, with no clear trigger for when opportunistic pruning actually runs on a single hot page). Rather than chase that timing, the comparison was **redesigned** around a page-pruning-independent, fully deterministic measurement instead: the *index's own byte size* after one update per row across many distinct rows, which is unaffected by opportunistic heap pruning and gave identical results across three separate runs (16384 → 16384 bytes for HOT-eligible updates, 16384 → 32768 bytes for non-HOT updates).
- **Sentry's postmortem never states the specific old value of `autovacuum_freeze_max_age`**, only the new one (500000000) and that the old one was "too high." Caught during fact-check (claim 11); corrected `OUTLINE.md` to not assert a specific old number that isn't in the source.
