## Currency check

- The ACID acronym and its four properties are foundational, unchanged vocabulary since 1983; nothing in this topic depends on a version-specific detail. No currency risk.
- The Consistency (database systems) Wikipedia article's own framing of the engine/application split is itself long-standing (cites C. J. Date's 2012 edition and the original 1983 paper); not a recent or contested claim. No currency risk.
- PostgreSQL's own docs were fetched on 2026-10-24 against the current (18) documentation; this sandbox's own Postgres is 16.15, and nothing taught here (Serializable's definition, MVCC's own snapshot mechanism, Read Committed vs. Repeatable Read) depends on a version-specific feature. No currency risk.

## Red team

1. **"Is the 'engine vs. application owns consistency' framing actually contested, or is this topic picking one side of a real debate and presenting it as settled?"** The Wikipedia source itself (not a single opinionated blog) states the split plainly, and a web search for alternative framings (e.g. Kleppmann's *Designing Data-Intensive Applications*) turned up the same conclusion from an independent, widely-cited source: the database only enforces declared constraints, and application-level correctness is a separate, application-owned concern. Not a one-sided framing; the two sources agree. The `OUTLINE.md` predict step's own wrong option ("the engine, because it's the one that actually checks the rules") is deliberately tempting precisely because the engine *does* check some rules — that's the nuance the reveal step corrects.
2. **"Does the consistency example (`reserved` exceeding `on_hand`) actually demonstrate an undeclared invariant, or could it be reframed as a declared one that was just never enforced?"** It is genuinely undeclared: the schema in `examples.py` has no CHECK, trigger or constraint mentioning `reserved` at all, only on `on_hand`. The engine has no mechanism by which it could know this rule exists, which is the entire point — it isn't a missing CHECK that should have been written, it's the illustration that *some* correctness lives outside any schema the engine could enforce. Held.
3. **"Is the durability experiment actually testing durability, or just testing that a WAL position number changes?"** Labeled honestly as a proxy, both in `FACT-CHECK.md` (claim 13) and in the reel's own caption and narration — it measures two real, documented facts (the WAL advances on commit; a separate connection reads the committed value), not a crash recovery. The real crash-survival mechanism (WAL replay) was already taught with a full measured recovery in §5.1's own write-ahead-logging topic; this topic does not re-claim to prove that again.
4. **"Could the isolation example's result be explained by something other than the isolation level — e.g. PostgreSQL's connection pooling or caching?"** No: each `interleaved_reread` call opens two fresh `psycopg2` connections per run (reader and writer), with `set_session(isolation_level=...)` set explicitly on the reader before its first query, and the table is reset to a known value between the two isolation-level runs. The only variable that changes between the two assertions is the isolation level itself. Held.
5. **"Is it fair to call the 1973-to-1983 gap 'surprising', or is this an overstatement for engagement?"** The ten-year gap between IBM IMS's own ACID-equivalent behavior (1973) and the acronym's own coinage (1983) is stated plainly by the source itself, not inferred or rounded. It is presented on screen as a dated fact ("1973... 1983"), not as a subjective claim of surprise beyond what the two dates themselves show.

## Problem Solving

- **The canonical ACID source (Härder & Reuter, 1983) could not be fetched.** Every candidate free-mirror URL tried (Cornell, Harvard, SFU, Berkeley course sites) either hit a genuine TLS failure or redirected to an unrelated page (one resolved to a Harvard faculty bio page instead of a PDF). **Fixed** by substituting two Wikipedia articles ("ACID" and "Consistency (database systems)") that quote and cite the original paper directly and state the same four properties and the consistency split independently, per the skill's own source-substitution rule — the same pattern used for the previous two topics' own unreachable sources.
- **The first `SOURCES.md` draft put two PostgreSQL doc URLs on one `URL:` line** ("...transaction-iso.html and ...mvcc-intro.html"), which `scripts/sources.mjs`'s own URL-line parser only reads as a single whitespace-delimited token, silently dropping the second URL. **Fixed** by splitting into two separate `##` source sections, one URL each, matching the format every other topic's `SOURCES.md` uses. `node scripts/sources.mjs check` passed afterward (10 quotes, 0 problems).
- **Two quotes failed the exact-match check on the first pass**: the "In 1983..." quote had its inline citation markers (`[1]`, `[2]`) dropped when first copied, and the bank-transfer example quote used `...` to elide a sentence, neither of which the checker's exact-text matching allows. **Fixed** by copying both quotes exactly as they appear in the fetched source text, citation markers and full sentences included.
