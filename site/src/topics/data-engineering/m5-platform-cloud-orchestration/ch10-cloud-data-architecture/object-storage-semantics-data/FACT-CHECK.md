# FACT-CHECK: Object storage semantics for data engineers

Self-review, fact-check and red team, 2026-10-30. Each row re-derives the claim from the fetched source text in `sources/`, checks the quote actually supports it, and tries to break it with an edge case.

| # | Claim | Status | Evidence |
|---|---|---|---|
| 1 | S3 delivers strong read-after-write consistency for any storage request, and strong list consistency after a write, since Dec 2020, at no additional cost. | Confirmed | `sources/aws-s3-consistency-announce.txt`, quoted verbatim in `SOURCES.md`. Red-team check: the announcement says "automatically for all applications" — no opt-in, no account-level setting — so the reel's wording ("since December 2020, any read or list request... immediately reflects") is a flat fact, not a typical-case claim, matching the source's own framing. |
| 2 | Updates to a single S3 key are atomic (never partial/corrupt data on a concurrent GET); there is no cross-key atomicity. | Confirmed | `sources/aws-s3-welcome.txt`, both sentences quoted verbatim. Red-team check: the source's own note says S3 does **not** support object locking for concurrent writers — "last timestamp wins" on a simultaneous PUT with no precondition. The reel's hook (step 1) relies on exactly this: two unconditional PUTs, no error either way, last one wins. Matches. |
| 3 | A rename on a flat object store is implemented as copy + delete, two separate requests with a real gap between them. | Confirmed | Not a single AWS sentence but a direct consequence of claim 2 (no cross-key atomicity) plus the AWS/boto3 API surface itself, which has no `rename` or `move` call — only `copy_object` and `delete_object`. Verified directly: `examples.py`'s `rename_is_copy_then_delete` reproduces the exact two-call sequence against the local S3-compatible server and asserts both keys exist simultaneously mid-sequence. |
| 4 | ADLS Gen2's hierarchical namespace makes directory rename atomic (one entry updated) instead of per-blob; Hive/Spark write-then-rename jobs are the motivating case. | Confirmed | `sources/azure-adls-hns.txt`, both sentences quoted verbatim. Red-team check: the source itself hedges ("this rename operation can **often** take longer than the analytics process itself" — not "always"); the reel's wording preserves that hedge rather than overstating it as a universal. |
| 5 | Conditional writes (`If-None-Match`, `If-Match`) support `PutObject`/`CompleteMultipartUpload`/`CopyObject`, with no additional charge, including on a failed precondition. | Confirmed | `sources/aws-s3-conditional.txt`, quoted verbatim. |

Conditional `CopyObject` launched Oct 29, 2025. | Confirmed | Each date and mechanism quoted verbatim from its own dedicated AWS "What's New" post (`sources/aws-s3-conditional-writes-2024.txt`, `aws-s3-if-match-2024.txt`, `aws-s3-copyobject-conditional-2025.txt`). ## Changes-from-chapter-plan review (engine of record)

MinIO's release channel (`dl.min.io`) was checked directly at research time and returns HTTP 410 Gone with an explicit "archived and no longer maintained" notice — not assumed from memory, not a transient failure (retried once, same response). No Docker daemon is available in this sandbox to fall back to MinIO's container image. The substitute, `moto`'s `ThreadedMotoServer`, was verified directly (not assumed) to implement real `412 Precondition Failed` responses for both `If-None-Match` and `If-Match` before any example was written — see the ad hoc verification run in the session transcript. The one place this substitute's behavior is *not* claimed as a measurement of real S3 — the per-prefix throttle — is implemented as an explicitly local, disclosed simulation (`TokenBucketPrefixLimiter`), never asserted against the moto server itself.

## Red team on the predict question (step 2)

Edge case tried: could a learner object that S3's own strong consistency (Dec 2020) already prevents the race in the hook, since a careful client would re-GET right before writing? Checked against claim 1's exact wording: strong consistency guarantees what a *subsequent read* sees after a write — it says nothing about whether a *write* is allowed to proceed once issued. A client that re-checks immediately before writing still has a window between its own check and its own PUT in which another client's PUT can land; consistency makes that check accurate, not atomic with the write that follows it. The step's answer explain text was worded to make this distinction explicit ("a precondition evaluated by the server at write time — not a read performed by the client beforehand") rather than leaving "stronger consistency" as a plausible-sounding near-miss with no stated reason it fails.
