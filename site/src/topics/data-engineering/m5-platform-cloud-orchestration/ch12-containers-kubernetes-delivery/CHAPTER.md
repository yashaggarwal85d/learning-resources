## The chapter

### The problem it solves

Chapters 7 and 9 taught how Spark and Kafka/Flink behave, and Chapter 11 how their work is scheduled and gated. All of that assumed the processes simply exist and have the memory they asked for. In production they do not: a Spark executor is a Linux process inside a control group on a shared node, scheduled there by a number written in a YAML file, and killed by the kernel the moment it exceeds another number. The classic incident of this chapter is the executor whose JVM heap looks healthy and whose pod is `OOMKilled` anyway, and the engineer who "fixes" it by raising executor memory and makes the job fail more often. This chapter teaches the whole chain from the artefact to the running process to the change that put it there: the **image** a job is packaged in and what its layers cost (§12.1), the **cgroup limits** the kernel enforces and the three different ways a container dies of memory (§12.1), the **Kubernetes objects** that declare how it runs and the **requests, limits, QoS classes and eviction rules** that decide where it lands and who is killed first under pressure (§12.2), the **Jobs and CronJobs** that run a batch pipeline to completion and their failure semantics, **Spark's** own driver-creates-executor-pods design and what happens to its shuffle data when a node disappears, the **stateful streaming** systems (Kafka, Flink) that cannot be treated as disposable pods, and finally **GitOps**, the pull-based reconciliation that delivers all of it and corrects the manual edit someone made at 3 a.m. (§12.3). The learner leaves able to read a pod's resource block and predict what the kernel and the kubelet will do with it, diagnose an OOM from the right signature in the right log, explain why a streaming upgrade must go through a savepoint, and state what Git, not a person with `kubectl`, is allowed to change.

### Order of ideas, and why

1. **§12.1 Containers for data workloads (topics 1–2).** Everything above the kernel is built from what a container really is, so this opens with the *artefact*: an image is stacked, read-only layers plus a thin writable one, and the order of your build instructions decides what the cache can reuse (1, a refresher, because senior engineers already know it and need only the data-workload cases: a fat PySpark image, a Compose stack with Kafka, Postgres and an object store). It then opens the *runtime*: a container is a process in a control group, the limit is a kernel file, and a memory limit is where three different failures (kernel OOM kill, JVM `OutOfMemoryError`, Python resident-set growth) get confused (2). Topic 2 is placed before Kubernetes on purpose: requests and limits in §12.2 are only intelligible once `memory.max` and `cpu.max` are.
2. **§12.2 Kubernetes for data workloads (topics 3–7).** A refresher of the objects every later topic names (3), because the chapter assumes Pods, Deployments, StatefulSets, volumes, taints and the reconciliation idea without pausing. Then the one resource mechanism the whole section turns on, requests versus limits and the QoS and eviction rules built from them (4), which is topic 2's kernel mechanism seen from the scheduler's side. Then the first workload shape, the batch pod that is supposed to finish (5), then the engine whose executors are pods it creates itself (6), then the shape that cannot be disposable, stateful brokers and stateful stream jobs (7), in increasing order of how much the platform has to know about the application.
3. **§12.3 Delivery (topic 8).** Last, because it delivers everything before it: the same reconciliation idea topic 3 introduced, now applied to the cluster's own configuration, so that Git is the only writer. It closes the chapter and the container story, and hands off to Chapter 13, whose first question is how you *know* the delivered platform is healthy.

### One running example: the shop's orders pipeline, as two workloads

Same fictional online shop as Chapters 1–5 (no real company, no real person). Where earlier chapters built the shop's data and engines, this chapter runs the shop's **orders pipeline as two deployable workloads** and follows both from image to delivery:

- **`orders-rollup`**, the nightly PySpark batch job (Chapter 7's workload): packaged as a container image (1), given a memory limit and killed by it (2), declared as a Job on a schedule (5), run by Spark's own driver and executor pods (6).
- **`order-events`**, the streaming side: a Kafka topic of order events and a keyed Flink job that aggregates them with state (Chapter 9's workload): run as brokers with stable identities and a job upgraded through a savepoint (7), delivered by Git (8).

The same two names recur in every topic's visuals, so a number seen in topic 2 (an executor's heap versus its container limit) is the number topic 4 reads off a pod's `resources` block and topic 6 reads off a Spark configuration. Every number on screen comes from the topic's own `examples.py`; sizes are measured on the builder's machine and disclosed, not quoted from memory.

### Shared notation and terms

- **`req` and `lim`:** a container's resource *request* (what the scheduler reserves) and *limit* (what the kernel enforces), written exactly so on screen from topic 2 onward; **`WSS`** is a process group's working set (what `memory.max` is compared against, with reclaimable page cache excluded where the kernel allows it; each topic that quotes a number says which counter it read).
- **Memory vocabulary** (topic 2 introduces, reused in 4, 6, 7): *heap*, *non-heap/native*, *RSS*, *page cache*, `memory.max`, `memory.high`, an *OOM kill*, exit code 137 (Chapter 1's shell refresher teaches signals and exit codes; the 128-plus-signal-number reading of 137 is stated and checked in topic 2 itself).
- **Desired vs actual state** (topic 3 introduces the *reconciliation loop*; reused in 5, 7, 8): a *spec* (what you declared), a *status* (what is true), a *controller* (the loop that closes the gap), *drift* (an actual state that no longer matches the declared one).
- **Failure vocabulary** (topics 2, 4, 5 introduce): `OOMKilled`, *evicted*, *preempted*, *disrupted* (voluntary disruption), *backoff*, *missed schedule*; each is a different cause with a different log line, and each topic's job is to keep them apart.
- **Spoken numbers:** narration has no digits, symbols or code names (same automatic check as Chapters 1–5): "memory max", "C P U quota" are said as plain words, any number is spoken aloud. YAML field names stay on screen and in the description, never in the narration.
- **Versions to state, not assume:** every feature that this plan dates (Kubernetes GA/beta versions, Spark 4.2 behaviour, Strimzi 0.46 KRaft-only, Argo CD options) is re-verified at build against the then-current documentation and quoted with its version.

### One visual language for the chapter's reels

Built from `site/src/reels/kit.tsx` and `DESIGN.md`'s briefing theme (black and white carry everything; colour only for failure, pale blue only for a second series), with the kit's moves (`Draw`, `Plot`, count, `Decode`, `Reticle`) doing the motion. The chapter shares five conventions:

- **A layer stack** (topic 1; reused in 2 and 6): an image drawn as horizontal slabs, one per layer, sized by bytes, with one thin writable slab on top; a rebuild redraws only the slabs below the first changed instruction, so cache reuse is *seen*, not stated.
- **The limit line** (topic 2, reused in 4, 6, 7): one horizontal line across the drawing is the kernel limit (`lim`); a bar grows toward it; crossing it is the only red in the step. Nested boxes (container > JVM heap + native + page cache) show *which* part crossed it, so "OOMKilled with a healthy heap" is a picture: the heap box is half full while the outer box is full.
- **The node as a bin** (topics 3, 4, 6, 7): a node is a rectangle of fixed memory; pods are blocks sized by `req` (what is reserved) with a lighter fill for actual usage; eviction is a block lifted out in QoS order, so "who dies first" is an animation of the order.
- **The control loop** (topics 3, 5, 7, 8): two stacked strips, *spec* above and *status* below, a thin arrow that repeatedly pulls the lower strip toward the upper; drift is the lower strip changing by itself, correction is the arrow acting. Topic 8's whole story is this one figure with Git as the upper strip.
- **Worker lanes** (carried from Chapters 4–5; topics 5, 6, 7): one lane per pod or executor, time left to right, a filled segment where work happens and a gap where the pod is gone; retries, executor loss and decommissioning are gaps and refills in these lanes.
- Every topic keeps the full-topic reel shape of Chapters 1–5 (hook, a prediction within the first four steps, mechanism in steps, at least three takeaways, recap, "Prove it"); this chapter's refreshers are topics 1 and 3 (about 5 minutes, at least one prediction).

### 1. Images, layers and local environments (`de.images-layers-local-environments`): refresher, §12.1

- **Folder:** `images-layers-local-environments`. About 5 min.
- **Scope:** "layers and copy-on-write filesystems, build-cache ordering, multi-stage builds, volumes and networks, Compose for local multi-service stacks (Kafka + Postgres + object store), configuration via environment and mounted files" — the full syllabus line, clause by clause:
  - *layers and copy-on-write filesystems:* an image is an ordered stack of read-only layers (each a changeset; a deletion is recorded as a "whiteout" entry, so deleting a file in a later layer hides it but never shrinks the image), a container adds one writable layer on top, and the union filesystem copies a file up into that layer on first write (OverlayFS copies the whole file, however small the write).
  - *build-cache ordering:* each instruction is a layer reused from cache only while it and everything above it are unchanged, so one early change invalidates every layer below; the practical rule (dependency manifests before source) shown on a PySpark image.
  - *multi-stage builds:* a build stage with compilers and caches, a runtime stage that copies only the artefacts; what this removes from a JVM-plus-Python data image.
  - *volumes and networks:* named volumes vs bind mounts vs tmpfs and what survives the container; a user-defined bridge network where services find each other by name.
  - *Compose for local multi-service stacks:* one file describing Kafka, Postgres and an S3-compatible object store, start order by health (`depends_on` with a healthy condition) instead of by luck.
  - *configuration via environment and mounted files:* environment variables for simple settings, mounted files for structured config and secrets, and where each leaks (an environment is visible to anyone who can inspect the container).
- **Leaves out:** pinned digests, lockfile-driven determinism, SBOMs and provenance (SLSA), signing (Sigstore) and scanning in CI belong to the *(skipped)* syllabus topic "Reproducible, minimal, signed images"; this entry names them in its Deep dive "Where this goes next" and does not teach them. What Kubernetes does with an image and its config (ConfigMaps, Secrets) is topic 3; what a container may use is topic 2.

### 2. Container resource limits: cgroups and OOM (`de.container-resource-limits-cgroups`): full, §12.1

- **Folder:** `container-resource-limits-cgroups`. About 15 min. Hosts part of the §12.1 chapter lab.
- **Scope:** "cgroups v2 memory and CPU limits, CFS quota throttling, `OOMKilled` (kernel) vs JVM `OutOfMemoryError` vs Python RSS growth, container-aware JVM sizing, Spark `memoryOverhead`, liveness vs readiness vs startup probes and the restart loops a wrong probe causes" — the full syllabus line, clause by clause:
  - *cgroups v2 memory and CPU limits:* the limit as a file (`memory.max`, `memory.high`, `cpu.max`, `memory.events`, `cpu.stat`), what the defaults are, and that a container runtime only writes those files.
  - *CFS quota throttling:* `cpu.max` as quota per period, how a multi-threaded process burns its quota early in the period and is stopped for the rest (`nr_throttled`, `throttled_usec`); the **mechanism** only. Whether to set a CPU limit at all is topic 4's debate.
  - *`OOMKilled` (kernel) vs JVM `OutOfMemoryError` vs Python RSS growth:* three different failures with three different signatures (a `memory.events` `oom_kill` count and exit code 137; a Java exception with a stack trace while the process lives on; a resident set that climbs until the first one fires), and which log or counter distinguishes them; which process in the control group the kernel kills, and whether the whole group goes (`memory.oom.group`, default 0 in the kernel documentation), is verified on the build machine and quoted, not assumed, because a container's main process can survive the death of a child.
  - *container-aware JVM sizing:* the JVM reads the container's limit, but its default maximum heap is a fraction (the Oracle documentation states a 25 percent default for `MaxRAMPercentage`), and heap is only part of the process (metaspace, thread stacks, direct buffers, native libraries).
  - *Spark `memoryOverhead`:* the arithmetic that turns an executor's heap into a container limit (heap plus overhead, with the factor Spark's own Kubernetes documentation gives for JVM and non-JVM jobs); the executor's internal memory regions are Chapter 7 §7.3's job and are not retaught here.
  - *liveness vs readiness vs startup probes and the restart loops a wrong probe causes:* what each probe decides (restart the container; remove it from service; hold the others back until it has started), and a slow-starting JVM killed by a liveness probe that began too early, forever.
- **Leaves out:** the scheduler's use of the same numbers (requests, QoS, eviction) is topic 4; Spark executor memory regions and spill are Chapter 7 §7.3; the CPU-limit debate is topic 4; the OOM event as it appears on a Spark pod is topic 6.
- **Outcomes:** Read `memory.events` and `cpu.stat` for a running container and say what each counter means; given an `OOMKilled` pod with a healthy heap, name what the kernel counted that the heap did not and set heap, overhead and limit consistently; tell the three memory deaths apart from their log lines; explain why a liveness probe on a slow JVM start produces a restart loop and which probe fixes it.
- **Introduces:** `cgroup-memory-cpu-limits`, `oom-kill-vs-runtime-oom`, `health-probes-restart-loops`. **Uses:** `image-layers-build-cache`, `process-model`, `signals`, `exit-status` (exit 137 is 128 plus signal 9, from the Linux and Git refreshers), `process-inspection`, `cpu-memory-profiling` (Chapter 4: how to see Python RSS growth). **Declared:** the JVM heap and a Python process's memory as a user sees them. Builds on Chapter 7 §7.3 (executor memory model, JVM OOM vs container OOM-kill): look up its `introduces` id in `registry.ts` for `uses`.
- **Bridge:** "An image is a frozen filesystem. Running it is something else: a Linux process in a control group, with a limit written in a kernel file. This topic opens that file and what the kernel does when the process asks for more." (Answers topic 1's handoff.)
- **Handoff:** "A limit is a number in a kernel file. Someone has to write that number and decide which machine the process lands on. In a data platform that someone is Kubernetes, starting with the objects it is made of."
- **Prerequisites panel:** topic 1; the Linux shell refresher (`/proc`, signals, exit codes). **Pre-notes terms:** control group, resident set size (RSS), page cache, exit code 137, JVM heap vs non-heap, thread stack, native memory, liveness vs readiness.
- **Hook:** an executor pod is `OOMKilled` while its JVM heap sits at about half of what it was given; the engineer raises executor memory and the pod is killed *more often*. Why does more memory make it worse? (The Appendix A question for Containers and Kubernetes, scoped to the container: what did the kernel count that the heap did not.)
- **Visual idea:** the chapter's limit line, with nested boxes (heap, non-heap, page cache inside the container) so the outer box reaches the line while the heap box is half full; three fatal ends drawn as three different final frames (kernel kill, a Java exception that the process survives, a slow RSS slope that never shows a heap problem); a CPU lane drawn as quota per period with the throttled gap visible.
- **Lab:** hosts the §12.1 lab's second half: run topic 1's image under a memory limit 10 percent below measured need, and capture the kernel signature against the Java signature in the logs and counters, plus a Python RSS-growth case. ### 4. Requests, limits, QoS and eviction (`de.requests-limits-qos-eviction`): full, §12.2

- **Folder:** `requests-limits-qos-eviction`. About 15 min.
- **Scope:** "the scheduler places by requests, the kubelet enforces limits; QoS classes (Guaranteed/Burstable/BestEffort) and eviction order under node pressure, the CPU-limit throttling debate, priority classes and preemption, PodDisruptionBudgets, in-place pod resize (GA in 1.35)" — the full syllabus line, clause by clause:
  - *the scheduler places by requests, the kubelet enforces limits:* a pod fits a node if the sum of requests fits; limits are topic 2's kernel files; the gap between the two is overcommit.
  - *QoS classes and eviction order under node pressure:* the criteria that make a pod Guaranteed, Burstable or BestEffort, and the two **different** things QoS and eviction decide. QoS sets the kubelet's `oom_score_adj` per container (the Kubernetes documentation gives -997 for Guaranteed and 1000 for BestEffort), which steers the **kernel** OOM killer. The kubelet's own **node-pressure eviction** does not use QoS class to order pods (the eviction page says so in as many words): it ranks pods by whether usage exceeds requests, then Priority, then by how far over requests the usage is, so BestEffort and over-request Burstable pods go first and Guaranteed pods and under-request Burstable pods last, and QoS is only a rough estimate of that order. Eviction thresholds (the documented default hard threshold for memory is 100Mi, soft thresholds with a grace period); and that the kubelet may not observe memory pressure fast enough, so the kernel OOM killer can act first (the documentation names the memcg-notification flag as the mitigation).
  - *the CPU-limit throttling debate:* with a CPU limit a pod is throttled even on an idle node (topic 2's mechanism); without one it competes by weight derived from its request. Both positions are presented with their primary evidence; the builder labels any practitioner opinion as opinion.
  - *priority classes and preemption:* priority is the second key of the kubelet's eviction ranking (after "usage exceeds requests") and lets a pending high-priority pod preempt lower-priority ones.
  - *PodDisruptionBudgets:* they govern voluntary disruption through the Eviction API (a drain, a node upgrade) and do **not** bind node-pressure eviction (the kubelet ignores them and may use a zero grace period under a hard threshold).
  - *in-place pod resize (GA in 1.35):* requests and limits become mutable on a running pod, often without a restart; memory-limit decreases are permitted but the kubelet's check is best-effort, and a resize that would change the pod's QoS class is rejected.
