## The chapter

### The problem it solves

Chapters 1-10 built pipelines that are, in isolation, each correct: a query that returns the right rows, a batch job that computes the right aggregate, a stream that delivers events in order. This chapter asks what happens when thousands of those correct pieces must run on a schedule, survive a crashed worker, be re-run over five years of history without melting the source, and be trusted enough that nobody has to open a terminal at 2 a.m. to find out why today's numbers are wrong. The classic incident is two sentences long. A DAG with ten thousand mapped tasks saturates the metadata database's connection pool and the scheduler itself stops scheduling, with no single task ever "failing"; and a backfill kicked off on a whim re-reads five years of a slowly-changing dimension through a JDBC source built for one day's load, and the source falls over an hour later. This chapter is the discipline that prevents both: how an orchestrator is actually built and where it breaks, when a DAG orchestrator is the wrong model entirely, and the operational practices — SLOs, incident response, disaster recovery, testing and safe deploys — that keep a pipeline inside its promises once it is live.

It teaches, in order, **orchestration beyond DAG syntax** first (11.1), because every later section assumes a mental model of what schedules a task, what retries it, and what a backfill actually re-executes: the scheduler/executor/metadata-DB architecture, idempotent tasks and failure semantics, data intervals and backfills, dynamic fan-out, concurrency controls, the deferrable-task model, data-aware scheduling, the asset-centric alternative (Dagster), and finally the landscape of choices. It then asks the harder question those tools answer badly (11.2): when the "task" is a multi-day, human-paced process rather than a short batch job, durable execution (Temporal) is a different model, and the chapter teaches only how to choose between DAG, asset and durable models, since the durable-execution internals themselves are out of scope here (marked *(skipped)*, carried as a sourced pointer in the one topic that survives). It then turns from scheduling correctness to **operating** the result (11.3): SLIs/SLOs and error budgets, incident response and blast radius, disaster recovery, and the schema-change rollout discipline that keeps producers and consumers from breaking each other. It closes with **DataOps** (11.4): the testing pyramid for transformations, data-diff regression testing, slim CI, write-audit-publish safe deploys, and contract enforcement in CI — the practices that make a pipeline change as safe to ship as application code.

The learner leaves able to look at an orchestration design and say what actually re-runs when a backfill is kicked off, what a stalled triggerer or a saturated pool does to the whole system, what SLO a given freshness alert really protects, and how a schema change reaches production without an outage.

### Order of ideas, and why

1. **11.1 Orchestration beyond DAG syntax (topics 1-9).** First the architecture every later idea sits on top of: scheduler, executor, metadata DB (1), because "idempotent task," "pool," "deferred task" and "asset" are all properties of specific pieces of this architecture. Then the correctness property every orchestrated task must have, idempotency and failure semantics (2), placed second because retries — the thing (1)'s executor does on failure — are only safe if the task is idempotent. Then what a schedule actually re-executes, data intervals, catchup and backfills (3), the direct, expensive consequence of (2): a backfill is many retries of the same idempotent task over historical intervals. Then the two knobs that turn one DAG into many running tasks and bound how many run at once: dynamic task mapping and fan-out (4), then concurrency controls — pools, queues, priorities (5), placed right after fan-out because fan-out is exactly what a pool exists to bound. Then the mechanism that lets a task wait for hours without occupying a worker, deferrable tasks and the triggerer (6), a scaling answer to the same resource pressure (5) just taught. Then the two ways a DAG can be told to run by something other than a clock: data-aware and event-driven scheduling (7), then the alternative mental model built entirely around that idea, asset-centric orchestration (8), placed last among the concepts because it needs (1)-(7) as the vocabulary it either keeps or replaces. Then the landscape and selection topic (9), last, because it can only be judged by someone who knows what a good orchestrator must do (1)-(8).
2. **11.2 Durable execution and Temporal (topic 10 only; four syllabus entries skipped).** The chapter's narrowest section: not how Temporal works internally (skipped — event history, replay, versioning, signals and sagas are each a syllabus entry marked *(skipped)*, and the durable-execution landscape survey is skipped too), but the one decision a working data engineer actually needs, choosing DAG, asset or durable models (10) for a given workload, with Temporal's shape (code-first, event-sourced, long-lived) carried only as far as that decision needs it, sourced from Temporal's own documentation and disclosed as such wherever the builder's machine cannot run a multi-day workflow to prove a claim.
3. **11.3 Data reliability engineering (topics 11-14).** From scheduling correctness to operating the result. Data SLIs, SLOs and error budgets (11) first, because the rest of the section is built on them: incident response (12) is what happens when an SLO is breached, disaster recovery (13) is the SLO extremes (RPO/RTO) applied to whole-platform loss, and schema-change rollout (14) is a planned risk whose blast radius and error-budget gate come straight from (11) and (12).
4. **11.4 DataOps: testing, CI/CD and deployment (topics 15-19; one syllabus entry skipped).** Testing pyramid for transformations (15) first, the foundation every CI practice tests against. Data-diff regression testing (16) next, because it is the test *type* slim CI (17) runs selectively — placed before (17) so the learner has the technique before the system that schedules it efficiently. Zero-copy environments (clones and branches) is *(skipped)* and carried only as a named, sourced pointer inside (17) and (18), which both lean on it conceptually. Write-audit-publish and safe deploys (18) next, the deployment-time analogue of (16)'s diff, now gating a real promotion rather than a CI check. ### Shared notation and terms

- **The three orchestrator components** (topic 1 introduces, reused through 11.1): the **scheduler** (decides what should run now), the **executor** (runs it, somewhere), the **metadata DB** (the durable record of every run, task instance and state — the thing that makes the scheduler itself restartable). - **Interval vocabulary** (topic 3 introduces, reused through 11.1 and 11.3): a **logical date** / **data interval** (the half-open time range a run owns, distinct from wall-clock run time), **catchup** (scheduling every missed interval since the DAG's start date), a **backfill** (an explicit re-run of past intervals), **blast radius** (topic 12 formalises it, topic 3 uses it informally for "what a backfill touches downstream").

### 2. Idempotent tasks and failure semantics (`de.idempotent-tasks-failure-semantics`): full, 11.1

- **Folder:** `idempotent-tasks-failure-semantics`. About 15 min. Hosts the kill-a-worker-mid-task leg of the 11.1 lab.
- **Scope:** "tasks run at-least-once (retries, zombie/orphaned tasks, heartbeats), idempotency through deterministic, interval-keyed outputs (partition overwrite, not append), retryable vs non-retryable errors and backoff, task-level vs run-level failure, trigger rules and `upstream_failed` propagation, timeouts" — the full syllabus line, clause by clause:
  - *at-least-once, zombies, heartbeats:* a worker that dies without reporting back leaves a task instance that still looks "running"; the scheduler detects it by a missed heartbeat and marks it a zombie, then retries it — meaning the task's first attempt may in fact have completed and written output before the worker died, so "retried" can mean "ran twice."
  - *idempotency via deterministic, interval-keyed outputs:* the fix from Chapter 8 topic 6's general recipe, applied at orchestrator scale: a task's output partition is named by its data interval (`orders/2026-10-2N`) and the task **overwrites** that partition rather than appending, so a second run of the same interval leaves the same state.
  - *retryable vs non-retryable, backoff:* a transient error (a timeout, a 503) is retried with backoff; a data error (a malformed row) is not, and retrying it only wastes the retry budget while hiding the real problem.
  - *task-level vs run-level failure, trigger rules, `upstream_failed`:* one task failing doesn't always fail the whole DAG run; trigger rules (`all_success`, `one_failed`, `all_done`) decide whether a downstream task runs anyway, and a task whose upstream never got to run is marked `upstream_failed`, distinct from `failed`.
  - *timeouts:* an `execution_timeout` bounds a hung task so it becomes a normal retryable failure instead of an invisible stall.
- **Leaves out:** what a backfill does with idempotent tasks at scale is topic 3; dynamic fan-out multiplies this topic's task-state grid, taught in topic 4; pools bound how many retry at once, topic 5.
- **Outcomes:** Reproduce a zombie task (kill its worker mid-run) and show the scheduler's retry can duplicate work unless the task is idempotent; design a task whose output is safe to re-run by keying it to its data interval; classify an error as retryable or not and configure backoff and a timeout accordingly; trace `upstream_failed` through a trigger-rule DAG.
- **Introduces:** `idempotent-tasks-failure-semantics`, `zombie-task-detection`, `trigger-rule-propagation`. **Uses:** `orchestrator-architecture-scheduler`, `exactly-once-effect-recipe` (Chapter 8 topic 6), `deterministic-batch-id` (Chapter 8 topic 6). **Declared:** none beyond topic 1.
- **Bridge:** "The executor's job is to retry a failed task, but that retry is only safe if running the task twice does no harm. This topic is that property, the two ways a task can fail without ever reporting failure, and the interval-keyed output design that makes a retry harmless." (Answers topic 1's handoff.)
- **Handoff:** "An idempotent task can safely be re-run for one interval. A backfill re-runs it for every interval across years of history, which is the same safety property at a much larger and more dangerous scale."
- **Prerequisites panel:** Chapter 8 topic 6 (Before this). **Pre-notes terms:** at-least-once, zombie task, heartbeat, idempotent, retryable error, backoff, trigger rule, `upstream_failed`, timeout.
- **Hook:** a worker is OOM-killed four minutes into a fifteen-minute load task; the scheduler sees no heartbeat, marks it a zombie, retries it, and the task that "ran once" in the logs actually ran twice, doubling every row count in the output; the figure is the task-state grid with one cell silently lit twice.
- **Visual idea:** the task-state grid (topic 1's figure, reused) with a column showing a task's state over time: running → (worker dies, no event) → zombie-detected → retried, with a second lane showing the output partition count doubling only when the task appends instead of overwrites.
- **Lab:** hosts the kill-a-worker-mid-task leg of the 11.1 chapter lab, including the idempotency-diff proof (two full re-runs of the same interval, outputs diffed byte-identical).

### 3. Data intervals, catchup and backfills (`de.data-intervals-catchup-backfills`): full, 11.1

- **Folder:** `data-intervals-catchup-backfills`. About 15 min. Hosts the kill-the-scheduler-during-a-backfill leg of the 11.1 lab.
- **Scope:** "logical date and data-interval semantics, catchup (off by default in Airflow 3), scheduler-managed backfills (Airflow 3: API/UI-driven, bounded concurrency, reprocess policy), Dagster partition backfills (per-partition vs single-run), resumable backfill design, and the blast radius of a 5-year backfill on shared sources and warehouses" — the full syllabus line, clause by clause:
  - *logical date / data interval:* a run's logical date is the **start** of the half-open interval it owns, not the time it actually executes — a daily DAG's run "for" 2026-10-27 covers `[2026-10-27, 2026-10-28)` and typically executes after that interval closes.
  - *catchup, off by default in Airflow 3:* scheduling every missed interval since a DAG's `start_date` happens automatically in catchup mode; Airflow 3 defaults `catchup` to off, a behaviour change from Airflow 2's default, stated from Airflow's own migration documentation.

### 13. Disaster recovery for lakehouse platforms (`de.disaster-recovery-lakehouse-platforms`): full, 11.3

- **Folder:** `disaster-recovery-lakehouse-platforms`. About 15 min. Hosts the region-loss leg of the 11.3 lab.

### 18. Write-audit-publish and safe deploys (`de.write-audit-publish-safe`): full, 11.4

- **Folder:** `write-audit-publish-safe`. About 15 min. Hosts the WAP-publish leg of the 11.4 lab.
- **Scope:** "WAP via an Iceberg audit branch fast-forwarded on success or a staging table with atomic swap/view repoint; blue-green tables, shadow runs diffed before cutover, canary by partition or tenant, feature-flagged transforms, rollback via time travel" — the full syllabus line, clause by clause:
  - *WAP via an Iceberg audit branch or a staging-table swap:* write to an Iceberg branch (or a staging table) first, audit it (run topic 16's diff, topic 15's tests, topic 11's SLO checks against it) while production is untouched, then either fast-forward the branch into main or atomically swap/repoint a view to the staging table only if the audit passes — demonstrated end to end on the shop's `fct_orders`, including a deliberately failed audit that never reaches production.
  - *blue-green tables:* two full copies of a table, one live and one being rebuilt, swapped atomically, as the table-level analogue of a blue-green application deploy.
  - *shadow runs diffed before cutover:* a new pipeline version runs in parallel with the old one, its output diffed (topic 16's technique) against the old version's real output before anyone cuts traffic over, catching a regression with zero production risk.
  - *canary by partition or tenant:* a change rolled out to one partition or one tenant first, measured, then expanded, rather than to everyone at once.
  - *feature-flagged transforms:* a transformation's new logic gated behind a flag so it can be toggled without a redeploy, including instantly off if something goes wrong.
  - *rollback via time travel:* using a table format's own snapshot history (Chapter 6) to roll back to the exact prior state in one operation, rather than attempting to manually undo a bad write.

- **Outcomes:** Implement a WAP publish with an audit step that can block promotion, and show a deliberately bad write never reaches production; design a canary rollout by partition or tenant with a measured rollback trigger; use a table format's time travel to roll back a bad publish in one step.
