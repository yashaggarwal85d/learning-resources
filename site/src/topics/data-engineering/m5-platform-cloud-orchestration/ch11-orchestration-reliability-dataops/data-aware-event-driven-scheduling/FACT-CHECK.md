# Fact-check

1. **Airflow's data-aware scheduling unit was called `Dataset` through the 2.x line and renamed `Asset` in 3.0.** Sourced directly, Airflow docs: "Changed in version 3.0: The concept was previously called 'Dataset'."

2. **A DAG scheduled on multiple assets only runs once all of them have updated since its last run.** Sourced, Airflow docs: "Airflow schedules a Dag after all assets the Dag consumes have been updated at least once since the last time the Dag ran... If one asset is updated multiple times before all consumed assets update, the downstream Dag still only runs once."

3. **One asset update can fire many downstream DAG runs at once — a real, measured "thundering herd."** Reproduced directly: one producer DAG task updated a single asset; six separate consumer DAGs, each scheduled on that asset, all created a Dag run within 17 microseconds of each other (examples.py, real `airflow dags list-runs` output, 2026-10-31).

4. **`AssetWatcher` is the pull-based mechanism for turning an external message-queue event into an asset update.** Sourced, Airflow docs: "An AssetWatcher monitors an external source such as a queue or storage system. When a relevant event occurs, it updates the corresponding asset and triggers Dag execution." Not independently run against a real message queue in this topic — disclosed as sourced-not-operated (the mechanism this chapter uses Kafka/queue semantics for is Chapter 9's own topic, used not re-taught, per CHAPTER.md's own "leaves out" note).

5. **Only a subset of triggers can back event-driven scheduling, specifically to prevent runaway rescheduling.** Sourced, Airflow docs: "Only triggers that inherit from BaseEventTrigger are compatible, to avoid infinite rescheduling scenarios."

6. **Partition-driven asset scheduling and partition mappers translate between differently-partitioned assets.** Sourced, Airflow docs: "Pre-determined partitioning — the partition key is worked out before the task runs, using the timetable's schedule cadence and partition mappers to match upstream keys to downstream keys." Reproduced directly: `StartOfHourMapper.to_downstream()`, called live on four real timestamps, correctly collapsed three same-hour keys to one downstream key and mapped the fourth (one second into the next hour) to a different one (examples.py).

7. **A missed or duplicated asset event is a real, documented failure mode of Airflow's event-driven scheduling, with a partial mitigation.** Sourced, Airflow docs: "After a triggerer restart, the broker redelivers messages that were never advanced... Triggers that re-subscribe later join as late subscribers... so they may miss events committed in the window between the first subscription and their own." The same docs state the mitigation (`shared_stream_cohort_grace_period`) is "a best-effort window — it reduces but does not eliminate the risk." Not independently reproduced (would require killing and restarting a live triggerer mid-event) — disclosed as sourced-not-operated. The companion claim — "a failure can therefore cause duplicate delivery but never a lost event" — is the stated design intent for the ordinary (non-late-subscriber) case.

8. **Dagster's declarative automation conditions state *when* an asset should run, rather than imperatively scheduling it.** Sourced, Dagster docs: "The AutomationCondition.eager condition allows you to automatically update an asset whenever any of its dependencies are updated," and "The AutomationCondition.on_missing condition will execute a missing asset partition when all upstream partitions of the asset are available." Not run against a live Dagster install in this topic (Chapter 11's Dagster asset model, including any live Dagster `orders` assets, is the next topic's own scope per CHAPTER.md) — disclosed as sourced-not-operated here.

9. **Dagster's freshness policies communicate and enforce a data-staleness contract, distinct from automation conditions.** Sourced, Dagster docs: "Freshness policies help you understand which of your assets have materialized recently and which ones are running behind... Freshness policies also communicate expectations for data freshness." Time-window and cron freshness policy types both sourced directly from the same docs.

10. **Time-based and data-driven triggering carry opposite trade-offs.** This topic's own synthesis, directly supported by the sourced mechanics above: data-driven (asset-triggered) scheduling reacts the moment an upstream asset updates (the measured six-DAG fan-out), at the cost of depending on that upstream event actually arriving, once, on time (the sourced missed/duplicate-event failure mode); time-based scheduling has none of that dependency, at the cost of being blind to whether the data it runs against is actually fresh.
