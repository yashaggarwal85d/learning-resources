# Fact-check

1. **A standard sensor in poke mode occupies a worker slot for its entire wait, even while idle.** Sourced, Airflow docs (deferring.html): "Standard Operators and Sensors take up a full worker slot for the entire time they are running, even if they are idle." Reproduced: measured 61.87 real worker-seconds across twelve 15-second `TimeDeltaSensor(deferrable=False)` waits — matches elapsed time exactly (examples.py).

2. **Deferring frees the worker; the triggerer does the waiting instead.** Sourced, Airflow docs: "the task no longer occupies a worker slot." Reproduced: the same twelve waits with `deferrable=True` cost only 3.03 real worker-seconds — a 95.1% reduction, read from the actual task logs' "Pausing task as DEFERRED" / resume timestamps (examples.py).

3. **Deferral is not free in wall-clock time.** Reproduced: the deferred run's twelve tasks took 196.74s of elapsed wall time vs 61.87s for poke, on this run. The worker-time savings is real; the latency cost (trigger pickup, re-queueing on the scheduler) is also real and not hidden in this topic.

4. **The triggerer is a separate, independently-scaled Airflow component.** Sourced, Airflow docs: "Triggers are designed to work in a high availability (HA) architecture. If you want to run a high availability setup, run multiple copies of triggerer on multiple hosts." Not independently reproduced (would require multiple triggerer hosts); disclosed as sourced-not-operated.

5. **Trigger serialization can silently corrupt an unserializable argument rather than failing loudly at defer time.** Reproduced directly: a live `threading.Lock` round-tripped through Airflow's own `airflow.serialization.serialized_objects.BaseSerialization` came back as a `str`; `serialize()` raised no exception; the failure only appeared later, calling `.acquire()` on the reconstructed string (`AttributeError: 'str' object has no attribute 'acquire'`) (examples.py). This is a stronger and more specific claim than "trigger serialisation fails" — it fails *late*, not at the point an author might expect.

6. **Triggerer saturation and its mitigation are the documented numbers, not independently reproduced.** Sourced, Airflow docs: default `capacity` is 1000 triggers per triggerer process; `max_trigger_to_select_per_loop` defaults to 50 and is recommended "significantly lower than capacity" to keep HA deployments balanced; "two Triggerers can still claim 1,000 triggers within one second" per Airflow's own benchmarks. Not reproduced here (would require thousands of concurrent triggers to observe delay) — disclosed.

7. **Airflow 3.1 introduced Human-in-the-Loop (HITL) operators that pause in a deferred state, running off the triggerer.** Sourced, Airflow 3.3.2 release notes (the 3.1.0 section): "Airflow 3.1 introduces Human-in-the-Loop (HITL) functionality... HITL tasks pause execution in a deferred state while waiting for human input." A later (3.3.0) changelog entry confirms explicitly: "Add awaiting_input task state for Human-in-the-Loop, running off the triggerer (#68028)."

8. **Airflow 3.1 also introduced Deadline Alerts, in the same release.** Sourced, same release notes, 3.1.0 section: "Deadline Alerts provide proactive monitoring for DAG execution by automatically triggering notifications when time thresholds are exceeded... Deadline Alerts are experimental in 3.1." The syllabus line groups HITL and Deadline Alerts together as both "reusing" the deferral mechanism; this topic states what's directly sourced (both ship in 3.1, HITL explicitly runs off the triggerer) without asserting Deadline Alerts' own internal implementation detail, which the fetched docs don't state explicitly.

9. **`mode='reschedule'` and `deferrable=True` solve the same idle-wait problem differently.** Sourced, Airflow docs (deferring.html's own comparison table): reschedule "continuously reschedules itself until condition is met" (higher resource use, built-in, good for conditions expected to change over time); deferrable "pauses execution when idle, resumes when condition changes" (lower resource use, requires custom logic, good for waiting on external events).
