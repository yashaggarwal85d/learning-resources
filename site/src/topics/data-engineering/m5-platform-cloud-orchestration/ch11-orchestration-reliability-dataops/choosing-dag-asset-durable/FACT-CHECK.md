# Fact-check

1. **A Temporal Workflow can run for years, surviving infrastructure failure.** Sourced and reproduced directly: `examples.py` asserts Temporal's own documentation states "Temporal Workflows are resilient. They can run—and keep running—for years, even if the underlying infrastructure fails," verified word for word against the fetched page text.

2. **A crashed Worker recovers a Workflow's state from the Event History, not from process memory.** Sourced and reproduced directly: `examples.py` asserts "if the Worker crashes, the Worker uses the Event History to replay the code and recreate the state of the Workflow Execution to what it was immediately before the crash," verified against the fetched page text.

3. **Resuming a Workflow replays its Event History rather than restoring a memory snapshot.** Sourced, Temporal's own docs: "When it's time to continue the Workflow, Temporal doesn't restore memory from a snapshot. It starts the Workflow code from the beginning, replays the Event History step by step."

4. **A Worker Process polls a Task Queue and executes code in response to a dequeued Task.** Sourced, Temporal's own docs: "A Worker Process is responsible for polling a Task Queue, dequeueing a Task, executing your code in response to a Task, and responding to the Temporal Service with the results."

5. **Worker Versioning reached General Availability across all Temporal SDKs.** Sourced and reproduced directly: `examples.py` asserts Temporal's own blog states "Today, we're announcing the General Availability of Worker Versioning and a Public Preview of Upgrade on Continue-as-New," verified against the fetched page text.

6. **A saga coordinates a sequence of local transactions, each with a compensating action run in reverse order on failure.** Sourced and reproduced directly: `examples.py` asserts Temporal's own documentation states "The Saga pattern manages distributed transactions across multiple services by coordinating a sequence of local transactions, each with a compensating action that can undo its effects if subsequent steps fail," verified against the fetched page text.

7. **Prefect's flows are Python-native and their structure can depend on runtime values, unlike a statically-defined DAG.** Sourced, Prefect's own docs (reused from topic 9's own fetch): "Prefect is an open-source orchestration engine that turns your Python functions into production-grade data pipelines with minimal friction... in pure Python—no DSLs or complex config files."

8. **A sensor polling an in-process counter in reschedule mode never accumulates state across pokes.** Run and reproduced directly, this session's own real Apache Airflow 3.3.2 sandbox: `examples.py` asserts the real `sensor_state_loss_dag` run's attempt log recorded twelve pokes, every one reporting the counter at exactly one, never climbing toward the three pokes the sensor needed, ending in a timeout failure. This is the project's own experiment, not a third-party claim.

9. **A sensor polling a fact held in the metadata database survives a real scheduler process restart mid-wait.** Run and reproduced directly, this session's own real Apache Airflow 3.3.2 sandbox: `examples.py` asserts the real `vendor_approval_gate_dag` run's attempt log recorded nine pokes and eight reschedule cycles; the scheduler process was killed and relaunched by hand after the fourth poke, and the task's state (held in the metadata DB, not the scheduler's own memory) was unaffected — the ninth poke, after the approval file was created, succeeded.

10. **The decision rule (duration, human-in-the-loop, data-product framing, saga need) is this topic's own synthesis, built from CHAPTER.md's stated scope.** Not independently sourced as a named rule from any one vendor's documentation; it is this topic's explicit turning of CHAPTER.md's own scope clause ("task duration... whether a human is in the loop, whether the unit of work is better thought of as a data product than an action, and whether multi-system compensation... is needed") into the four-question test applied on screen, consistent with the chapter's framing of this topic as the decision across models already taught or sourced, not a new mechanism of its own.

11. **Temporal's internal mechanics (event-sourced replay in full, workflow determinism and versioning, signals/timers/sagas, the durable-execution landscape survey) are *(skipped)* syllabus entries, carried here only as a named, sourced pointer.** Per CHAPTER.md's own scope for this chapter: these four entries get no reel of their own, and this topic never demonstrates them step by step — only cites Temporal's own documentation for the single claim (Event History and replay) the hybrid-handoff reveal needs.

12. **The full 11.2 chapter lab (migrate the approval gate to Temporal, kill workers mid-approval, deploy a code change mid-flight, compare recovery time/code size/infrastructure cost) could not be run to completion in this sandbox.** Disclosed directly: the Temporal CLI dev server binary downloads and extracts cleanly, but every attempt to make it executable or run it (directly, or indirectly through the `temporalio` Python SDK's local test environment) is blocked by this session's own sandbox execution policy. The two Airflow sensor runs (facts 8 and 9) are the real evidence this topic could gather locally; the Temporal-side claims are sourced only, per CHAPTER.md's own "disclosed sourced-only for any leg it cannot complete" rule.
