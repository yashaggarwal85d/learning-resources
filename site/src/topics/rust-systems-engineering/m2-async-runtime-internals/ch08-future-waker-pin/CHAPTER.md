## A.1 The problem it solves

Every chapter through Milestone 1 assumed a thread, once started, is simply running: it executes until it finishes, blocks on a lock or a syscall, or is preempted — but it is always either doing work or waiting for a resource to free it to continue. Async Rust breaks that assumption on purpose. An `async fn` compiles to a value — a `Future` — that does nothing at all until something external asks it to make progress, and asking "is this done yet" is a method call (`poll`), not a thread resuming. This chapter is about the actual machinery that makes that work: what a `Future` really is (a state machine, not a thread, not a promise with a callback registered against it by the runtime), what a pending future owes the system that's driving it (the `Waker` contract: arrange to be polled again, or the program silently stops), why the compiler-generated state machine needs `Pin` at all (it can end up holding a reference into itself, something nothing in the ordinary ownership model anticipates), and the specific places the 2026 language surface still has rough edges around all of this (the `Send` bound problem on `async fn` in traits, chief among them). None of this is runtime-specific — it's what `async`/`.await` compile to and what the `Future` trait promises, before any particular executor (Tokio, in the next chapter) enters the picture at all.

By the end of the chapter the learner can: explain why constructing a future does no work, and why that laziness is itself a form of backpressure; state the `Poll::Pending` contract precisely (a pending future must arrange for its `Waker` to be called, or it may never be polled again) and describe the actual architecture — future → waker → scheduler → poll — with no hidden thread anywhere in it; describe what `async fn` lowers to (an enum of suspension states holding each `.await` point's live locals) and why that can make a future large, and why a single `!Send` value held across an `.await` point makes the entire future `!Send`; explain concretely why `Pin` exists (a self-referential state machine whose internal reference breaks if the value moves after its first poll) and read `Pin<&mut Self>`, `Unpin`, and the difference between structural and non-structural pin projection; and name the `Send` bound problem on `async fn` in traits as a real, currently-unfixed gap in the stable language, together with its practical workarounds.

## A.2 The order of ideas, and why

1. **Futures, Poll, and the Waker contract** (topic 24) — the foundation: a `Future` is a lazy computation (constructing one runs no code; only `poll`ing does), and that laziness is itself the backpressure mechanism async Rust relies on instead of a thread blocking. Builds a `Future` by hand (no `async` sugar yet) that returns `Poll::Pending` once and `Poll::Ready` the next time it is polled, together with a minimal hand-rolled executor (a runnable queue plus a `Waker` built from `Arc<Task>` via `std::task::Wake`) to make "future → waker → scheduler → poll" a real, running loop with no hidden thread anywhere in it. States the `Poll::Pending` contract precisely: a future that returns `Pending` without arranging for its `Waker` to be called may simply never be polled again — demonstrated by a future that breaks this contract and genuinely hangs.
2. **async/await lowering and future size** (topic 25) — needs (1): takes the hand-built future from topic 24 and shows what the compiler actually produces for the equivalent `async fn` — an enum with one variant per suspension point, holding exactly the locals still live across that `.await`. Measures a real future's size with `std::mem::size_of` to make "large futures cost a real `memcpy` every time they're moved" concrete, not asserted, and reproduces the `!Send` propagation rule directly: a `!Send` value (e.g. an `Rc`) held across an `.await` point makes the surrounding future `!Send`, shown by a real compile failure with its exact error code.
3. **Pin and self-referential state** (topic 26) — needs (1) and (2): now that a real suspension-state enum exists from topic 25, shows the one way a generated state machine can end up holding a reference into itself (a local referencing another local, both captured across the same `.await`), why that reference is unsound the moment the whole value moves, and why `Pin<&mut Self>` is the fix — a promise the compiler can check, not merely a well-intentioned convention. Covers `Unpin` (most types, including every type in Chapters 1–7, implement it automatically and are entirely unaffected by any of this), the `pin!` macro for stack-pinning, and pin projection (`pin-project-lite`), distinguishing structural projection (sound: the pinned field moves only if the whole struct does) from non-structural projection (the one case pin projection must not allow).
4. **Async fn in traits and Send bounds** (topic 27) — needs (1)–(3): `async fn` in traits and return-position `impl Trait` in traits have been stable since Rust 1.75, but they expose a real, currently-unsolved gap: a trait's `async fn` returns some anonymous future type, and nothing in today's stable language lets a caller require that returned future be `Send` — demonstrated by a real multi-threaded executor rejecting a trait object built from such a trait. Names Return-Type Notation (RFC 3654) as the eventual fix, still unstable as of 2026, and surveys the stable workarounds in actual use today: `trait-variant` (generates a `Send`-bounded sibling trait), the boxing `async-trait` (erases the future into a `Pin<Box<dyn Future>>`, at a real allocation cost shown directly), and `dynosaur` for `dyn`-safe async traits. Hands off to Chapter 9 (Tokio Runtime Architecture): everything built here (the future/waker/poll loop, pinning, the `Send` bound problem) was runtime-agnostic by design — the next question is what a real, production multi-threaded scheduler actually does with all of it.

## A.3 The running example: a hand-rolled future and a minimal executor

All four topics share one self-contained running example (no cross-topic imports, per Chapters 1–7's convention): a `Delay`-shaped future (returns `Pending` the first time it is polled, registers interest, and `Ready` the next time something wakes it) driven by a tiny single-threaded executor built from a runnable-task queue and `Waker`s constructed via `std::task::Wake` over `Arc<Task>` — small enough to read in full, and real enough that the identical shape (poll once, arrange a wake-up, poll again) is exactly what every `async fn` compiles down to and exactly what Tokio's own scheduler does at a larger scale.

- **Topic 24** builds the executor and the hand-written `Future` impl from scratch, with no `async` sugar anywhere, and demonstrates the broken-contract case (a future that returns `Pending` without ever arranging a wake) hanging for real, with a timeout proving it, rather than merely describing the risk.
- **Topic 25** rewrites the identical `Delay` behavior as an `async fn` using `.await` on topic 24's future, and measures the compiler-generated state machine's real size via `std::mem::size_of`, plus a second future that holds an `Rc` across an `.await` point to produce a real, cited `!Send` compile error.
- **Topic 26** extends topic 25's async function with a second local that borrows from a sibling local captured across the same `.await`, to construct the one shape that is genuinely self-referential after the first poll, and shows both the unsound un-pinned version (behind a deliberately contained, commented `unsafe` demonstration of what breaks) and the `Pin`-protected fix.
- **Topic 27** wraps the chapter's executor in a multi-threaded variant to make the `Send` bound problem concrete: a trait with an `async fn` whose returned future is used from an object-safe trait object fails to compile across threads, then each workaround (`trait-variant`, `async-trait`, `dynosaur`) is applied in turn and shown to actually fix it, with `async-trait`'s extra allocation made visible.

## A.4 Terms and notation (continuing Chapters 1–7's vocabulary)

Everything in Chapters 1–7 §A.4 still applies. This chapter adds:

- **Future**: a lazy computation represented as a value; constructing one does no work at all, and nothing happens until it is polled.
- **Poll**: the `Future::poll` method's return type — `Poll::Ready(value)` once the future has a result, `Poll::Pending` while it does not.
- **The Waker contract**: a future that returns `Pending` must arrange, before returning, for its `Waker` to be called once it can usefully be polled again — the one obligation the whole model depends on.
- **Backpressure (via laziness)**: because constructing a future does no work, a system can hold far more pending futures than it has resources to run concurrently, without anything running until it's actually polled.
- **Suspension state**: the compiler's name, informally, for each distinct point an `async fn`'s state machine can be paused at — one per `.await` point, each holding exactly the locals still live there.
- **Self-referential state**: a value that holds a reference into its own fields; sound only as long as the value never moves after that reference is formed.
- **Pin**: a wrapper that promises a value will never move again (or, for `!Unpin` types, enforces it); `Pin<&mut Self>` is how `poll` receives a future that might be self-referential.
- **Unpin**: a type that is always safe to move even behind a `Pin`; almost every ordinary type, including everything built in Chapters 1–7, implements it automatically.
- **Structural vs non-structural pin projection**: structural projection pins a field exactly when the whole struct is pinned (sound); non-structural projection would let a field be moved independently of its pinned container (unsound, and pin projection must forbid it).
- **The Send bound problem**: a trait's `async fn` returns an anonymous future type a caller cannot currently constrain to be `Send`, blocking that trait's use from a multi-threaded executor through a trait object.

Narration words (continuing the convention: no digits, no code-style names spoken): "a value that does nothing until asked" for a future; "ready, or not yet" for poll's two outcomes; "promising to be checked on again" for the waker contract; "holding resources without doing work" for backpressure via laziness; "one pause point, with everything still alive there" for a suspension state; "a value pointing into its own insides" for self-reference; "a promise this value will never move again" for pin; "safe to move regardless" for unpin; "the field moves only if the whole thing does" for structural projection; "no way yet to ask for a particular kind of future back" for the send bound problem.
