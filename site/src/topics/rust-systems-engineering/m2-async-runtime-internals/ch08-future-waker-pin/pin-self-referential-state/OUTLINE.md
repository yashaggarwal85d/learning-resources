# Outline: Pin and self-referential state (`rust.pin-self-referential-state`)

Chapter 8, topic 26 (third of four). Single `/make-topic` session, 2026-10-23.

## Changes from the chapter plan

`CHAPTER.md` §A.3 proposed extending topic 25's `async fn` with a second local borrowing from a sibling captured across the same `.await`, to construct the self-referential shape directly inside an `async fn` body. In practice there is no simple, stable way to form that borrow inside an ordinary `async fn` without unsafe scaffolding that would obscure the point rather than illustrate it. Instead this topic uses a hand-written struct standing in for "the one thing the generated enum could hold" — which is exactly how the primary source itself frames the claim: the `std::pin` module docs name "the state machines generated by the compiler to implement `Future` for async fns" as *the* key example of a self-referential type, without needing to write one out by hand. The hand-written stand-in keeps every example real, compiled, and executed, with no unsafe code hidden from the reel.

## Learning outcomes

1. State precisely why `Pin` exists: a value that holds a reference into its own fields is sound only as long as it never moves after that reference is formed, and the compiler-generated async state machine is the standard-library-named example of exactly such a value.
2. Read `Pin<&mut Self>` and `Unpin` correctly: `Pin<Ptr>` is a promise that a pointer's pointee will not move, enforced by the type, not a container; `Unpin` is auto-implemented for almost every type and opts a type back out of needing that promise at all.
3. Distinguish structural from non-structural pin projection: a field projects to `Pin<&mut Field>` only when pinning that field is declared structural (the field moves exactly when its container does); every other field projects to an ordinary reference.

## Reel steps (storyboard)

1. **"Can a local inside a function end up holding a pointer into another local of that same function?"** (predict, hook) — `fig`: two locals, `value` and `pointer`, sitting side by side. Options: no, locals are always independent of each other / yes — one local can hold a pointer straight into another's address (correct) / only across separate function calls.
2. **"Yes — and the standard library names the exact place this happens by default"** — `fig`: the `std::pin` docs' own words, quoted directly: the compiler's generated async state machines are *the* key example of a self-referential type. NO takeaway (first non-predict step after a predict step).
3. **"A self-referential value's own pointer breaks the instant it moves"** — `fig`: `self_ref_breaks_on_move.rs`'s two measurements, valid before the move and stale after. Takeaway: "A value holding a pointer into itself is sound only until it moves — moving it leaves that pointer pointing at the old address."
4. **"Does wrapping it in a Box<T> fix this?"** (predict) — `fig`: the same struct, now behind `Box::new`. Options: yes, `Box` pins its contents in place / no — the `T` can still be moved out of the `Box` (correct) / only if the struct derives `Clone`.
5. **"Pin<Ptr> is a promise about the pointee, enforced by the type"** — `fig`: the `std::pin` docs' own definition, quoted: `Pin<Ptr>` wraps a pointer and promises its pointee will not be moved or invalidated. Takeaway: "Pin<Ptr> is a promise a pointer's pointee will never move again — a guarantee the type carries, not a convention the caller has to remember."
6. **"Pinned — on the heap or the stack — the identical self-reference stays valid"** — `fig`: `pin_prevents_the_break.rs` (`Box::pin`) and `pin_macro_stack_pin.rs` (`pin!`), both measured, both staying valid. Takeaway: "PhantomPinned plus Box::pin or the pin! macro keeps a self-reference valid — two ways to make the identical promise."
7. **"With a Pin<Box<T>> where T is not Unpin, can T still be moved out?"** (predict) — `fig`: `takes_by_value(*a)` next to a `Pin<Box<SelfRef>>`. Options: yes, Box always allows moving its contents out / no — the compiler refuses outright (correct) / only with an explicit unsafe block.
8. **"rustc's own diagnostic: this move is rejected outright"** — `fig`: `move_out_of_pin_fails.rs`'s real `error[E0507]`, naming `Pin<Box<SelfRef>>` directly. Takeaway: "Moving a value out of a Pin<Box<T>> when T is not Unpin fails to compile with error E0507 — Pin's guarantee enforced at compile time, not merely documented."
9. **"A pinned field projects by the type's own choice, not automatically"** — `fig`: `structural-projection`'s real `pin_project!`-generated struct: one field marked `#[pin]`, one left ordinary. Takeaway: "Structural pin projection follows the type's own declared structure: a #[pin] field stays pinned exactly when its container does; every other field is reached through a plain reference."
10. **Recap** — a self-referential value is sound only until it moves, proven directly; Pin<Ptr> is a type-level promise the pointee will not move, not a convention; the compiler enforces that promise at compile time, rejecting a move with a real error; and pin projection is a per-field, declared choice, never automatic. Handoff: every future and every guarantee this chapter built has been about one future, running alone — the next question is what happens the moment a trait is asked to hand one back across a thread boundary.
