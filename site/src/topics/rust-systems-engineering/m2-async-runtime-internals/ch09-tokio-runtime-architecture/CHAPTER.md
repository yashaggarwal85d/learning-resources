## A.1 The problem it solves

Chapter 8 built the future/waker/poll contract and proved it with a hand-rolled, single-threaded executor — deliberately agnostic about what any real scheduler does with it. This chapter answers that exact question for Tokio, the runtime every later chapter's I/O and concurrency content assumes. A task is not a thread: it is a `Future` plus the bookkeeping Tokio needs to poll it again, and the whole point of an async runtime is to multiplex a very large number of these onto a very small number of real OS threads. That multiplexing has real, learnable mechanics — a per-worker local queue, a cross-thread work-stealing deque, a single-slot LIFO fast path for message-passing locality, a global injection queue for work with nowhere else to go — and real, learnable failure modes when its one hard rule is broken: a task that blocks its worker thread without yielding stalls every other task scheduled to that worker, because nothing preempts it. Chapter 9 covers exactly this architecture and the operating rules it implies: how tasks get scheduled and stolen, how cooperative budgeting keeps one greedy task from starving its neighbours, what to do with a genuinely blocking or CPU-bound operation that cannot cooperate at all, how the I/O and timer drivers turn a readiness event into a woken task, and the tooling and rules of thumb (tokio-console, bounded channels, explicit cancellation) that keep a real async service observable and well-behaved in production.

By the end of the chapter the learner can: explain precisely why tasks are multiplexed onto worker threads rather than mapped 1:1 onto OS threads, and choose between the current-thread and multi-thread runtimes as a workload-shape decision rather than a default; describe Tokio's actual scheduling path — local queue, LIFO slot, work-stealing from a sibling worker's queue, the global injection queue — and state the cooperative-budgeting rule that forces a task to yield after a bounded number of resource operations; name `spawn_blocking` and `block_in_place` as the correct homes for genuinely blocking or CPU-bound work, and the thread-per-core alternative (glommio, monoio, compio) as a different design point entirely; describe the I/O driver's register → park → readiness event → wake → poll cycle and the hierarchical timer wheel it uses for deadlines; and state the chapter's operating rules (keep tasks small enough to yield, bound every channel and every pool, define cancellation semantics explicitly) as consequences of the architecture just learned, not merely as advice.

## A.2 The order of ideas, and why

1. **Tasks multiplexed on worker threads** (topic 28) — the foundation: a task is a lightweight state machine, not an OS thread, and Tokio multiplexes many of the former onto a small, fixed-size pool of the latter. Builds a real multi-thread runtime and a real current-thread runtime side by side, spawns far more tasks than there are worker threads on the multi-thread one, and demonstrates the chapter's one hard failure mode directly: a task that blocks its worker thread without yielding stalls every other task scheduled there, measured as real latency on an unrelated task rather than merely asserted. Introduces `LocalSet` as the way to run `!Send` tasks on the current-thread runtime, where Chapter 8's `!Send`-propagation rule becomes a real scheduling constraint rather than only a compile-time one.
2. **Work stealing and cooperative budgeting** (topic 29) — needs (1): takes the multi-thread runtime from topic 28 and shows its actual scheduling path, straight from Tokio's own documentation of its current behavior: each worker's local queue, the single LIFO slot used for message-passing locality (and disabled after three consecutive uses), the global injection queue, and work stealing by moving half of a busy worker's local queue to an idle one. Reproduces cooperative budgeting directly: a hot loop over a resource operation is forced to yield after a bounded per-poll budget, measured by counting how many iterations run before a forced yield, and contrasts it with `task::unconstrained`, which opts a future out of that budget entirely and can starve its neighbours as a result.
3. **Blocking and CPU-bound work** (topic 30) — needs (1)–(2): a task that must call a genuinely blocking API, or burn real CPU time with no natural yield point, cannot cooperate no matter how it's written — the fix is to move it off the worker pool entirely. Demonstrates `spawn_blocking`'s dedicated, dynamically-sized blocking pool directly (measuring that a blocking call there does not stall the main worker pool's unrelated tasks, unlike the exact same call made directly on a worker), and names `block_in_place`, a `rayon` or dedicated-runtime split for CPU-heavy work, and thread-per-core shared-nothing runtimes (`glommio`, `monoio`, `compio`) as the alternative design point this architecture deliberately is not.
4. **I/O and time drivers** (topic 31) — needs (1)–(3): completes the picture of what actually wakes a parked worker. Builds a minimal, direct `mio`-based readiness loop (register interest, park, receive a readiness event, wake the registered task, poll again) to make the I/O driver's real cycle concrete rather than asserted, and demonstrates a timer firing through the same wake-and-poll path, naming the hierarchical timer wheel Tokio actually uses for deadlines at scale. Names `io_uring` support as a real, currently unstable, opt-in feature (`tokio_unstable`) rather than the default path.
5. **Runtime observability and operating rules** (topic 32) — needs (1)–(4): closes the chapter by turning everything built so far into a short, defensible list of operating rules — keep tasks small enough to yield, bound concurrency with a `Semaphore`, bound every channel, define cancellation semantics explicitly — each one justified directly by a mechanism from topics 28–31, not merely asserted as good practice. Names `tokio-console` and Tokio's runtime metrics as the real tools that make a violation of these rules observable in production, with a tracked LTS line and rolling MSRV as the chapter's closing, practical note. Hands off to Chapter 10 (Channels, Backpressure, Cancellation, and Graceful Shutdown), where "bound every channel" becomes its own full chapter.

*(The chapter's lab — a bounded-semaphore TCP accept loop, overloaded past its bound, then one worker deliberately blocked with a synchronous sleep while `tokio-console` watches unrelated connections' p99 — is not a reel; it stays in the syllabus as a lab exercise per `CLAUDE.md`'s convention, exercising topics 28–32 together rather than introducing new tested claims of its own.)*

## A.4 Terms and notation (continuing Chapters 1–8's vocabulary)

Everything in Chapters 1–8 §A.4 still applies. This chapter adds:

- **Task**: a unit of work the runtime schedules — a `Future` plus the bookkeeping needed to poll it again — multiplexed onto a worker thread, never mapped 1:1 onto one.
- **Worker thread**: one of a fixed, small pool of real OS threads a multi-thread runtime creates at startup to run tasks.
- **Local queue / global injection queue**: each worker's own FIFO of ready tasks, preferred over the one shared, cross-worker queue every task not locally scheduled falls back to.
- **LIFO slot**: a single, per-worker fast-path slot for a task that was just woken by another task on that same worker, favouring message-passing locality; disabled temporarily after three consecutive uses.
- **Work stealing**: an idle worker moving half of a busy sibling worker's local queue to its own, to redistribute load without a single shared lock.
- **Cooperative budgeting**: a bounded per-poll allowance of resource operations a task is allowed before the runtime forces it to yield, so one hot loop cannot starve its neighbours.
- **`spawn_blocking`**: moves a genuinely blocking operation onto a separate, dynamically-sized blocking thread pool, off the cooperative worker pool entirely.
- **Thread-per-core runtime**: an alternative scheduler design (`glommio`, `monoio`, `compio`) pinning one worker per core with no cross-core work stealing at all — a different tradeoff, not a defect in Tokio's design.
- **I/O driver**: the component (built on `mio`) that turns "register interest in a socket" into "park the worker" into "a readiness event wakes the registered task."
- **Hierarchical timer wheel**: the data structure Tokio's time driver uses to fire a large number of deadlines without scanning every one of them on every tick.

Narration words (continuing the convention: no digits, no code-style names spoken): "a lightweight unit of work, not a real thread" for a task; "a small, fixed crew of real threads" for the worker pool; "a fast lane for a task that just woke a neighbour" for the LIFO slot; "borrowing half of a busy neighbour's queue" for work stealing; "a spending limit before being asked to step aside" for cooperative budgeting; "a separate pool for work that can't step aside at all" for the blocking pool; "one worker glued to one processor, no borrowing at all" for thread-per-core; "register interest, then wait to be tapped on the shoulder" for the I/O driver's cycle; "a clock built from nested rings, not a single long line" for the timer wheel.

## A.8 Bridges and handoffs

- **28** bridges from topic 27's real handoff ("Every piece of this chapter — the poll loop, the state machine, pinning, even where the language still falls short — was deliberately runtime-agnostic. The next question is what a real, production, multi-threaded scheduler actually does with all of it: how tasks get multiplexed onto worker threads, and what happens when one of them blocks.") and opens by answering it directly: a small, fixed pool of worker threads, and a task that blocks one of them stalls everything else scheduled there. Hands off to 29: "A blocked worker stalls its own queue completely — but even an unblocked one has to decide, task by task, what runs next and where a newly-woken task actually goes. That decision has real, documented mechanics, not just a queue."
- **29** bridges from 28's handoff and shows the real scheduling path: local queue, LIFO slot, stealing, injection queue, and the budget that keeps any one task from monopolizing it. Hands off to 30: "Cooperative budgeting only works for a task that is willing to cooperate at all — written so that it has a point to yield at. Some real work, a blocking system call or a long CPU-bound computation, has no such point. What happens to the worker running one of those?"
- **30** bridges from 29's handoff and answers it: move it off the worker pool entirely, onto a pool built for exactly that. Hands off to 31: "Every task this chapter has scheduled so far was already ready to run, or was told directly to stop being ready. The other half of the picture is how a task that is waiting on something external — a socket, a timer — ever gets told it's ready again at all."
- **31** bridges from 30's handoff and closes the loop Chapter 8 opened: the I/O and time drivers are the thing that actually calls `wake()`. Hands off to 32: "Every mechanism in this chapter is real, and every one of them can also be violated — a task that never yields, a channel with no bound, a cancellation path nobody defined. The question left is how any of that becomes visible before it becomes an incident."
- **32** bridges from 31's handoff and closes the chapter on a short, defensible list of operating rules, each one a direct consequence of a mechanism already built. Hands off to Chapter 10 (Channels, Backpressure, Cancellation, and Graceful Shutdown): "Bound every channel was this chapter's shortest rule and its least explained one.
