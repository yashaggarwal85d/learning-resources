## Storyboard (8 steps, 3 predict/reveal pairs)

1. **BurstPredict** — Six real requests arrive in a real, rapid burst against a service whose own queue and worker together can only admit so many before the burst finishes. Once the dust settles, does every real request end up accounted for as either admitted or shed? Options: no, some requests just vanish under real load; yes, genuinely, every single one is either admitted or shed, with nothing left over (correct); only if the burst is slow enough.
2. **BurstReveal** — Measured: of six real requests, exactly three are genuinely admitted and exactly three are genuinely shed, and every one of the six is accounted for as one or the other, with no real request left unaccounted for. No separate takeaway here (this is the reel's own "from" step for the phone swipe test; its takeaway moves to step 7, the connecting step, below).
3. **SuffixPredict** — Among the three real requests that get shed, could any of them have arrived earlier in the real submission order than one of the three that got admitted? Options: yes, shedding could land on an arbitrary one of the six; no, genuinely, every shed request comes strictly after every admitted one (correct); only if two requests happen to tie exactly.
4. **SuffixReveal** — Measured: every one of the three real shed requests' own position in the submission order genuinely falls after every one of the three admitted requests' own position; the real shedding is a real suffix of the order they arrived in, never an arbitrary subset. Takeaway: a real, saturated queue sheds whatever arrives once it is already full, not an arbitrary pick from everything that arrived.
5. **ReproduciblePredict** — The identical real burst is run again, from a fresh instance of the identical service. Does it genuinely reproduce the identical three-admitted, three-shed split, or does real timing noise change the outcome? Options: it changes, since real timing always varies at least a little; it reproduces exactly, genuinely, because the real margins here are wide (correct); only if the second run happens to be run more slowly.
6. **ReproducibleReveal** — Measured: the identical real burst, run again from a fresh instance, genuinely reproduces the identical split, exactly three admitted and exactly three shed, confirming this is real, deterministic saturation behaviour rather than a flaky, one-off accident of the first run. Takeaway: a real failure budget is only meaningful against behaviour that genuinely reproduces; a rate that cannot be reproduced cannot be budgeted for at all.
7. **DocsReveal** — The `tower::load_shed` documentation and the Google SRE book's own chapter on error budgets each state this directly, in their own words: `load_shed` is middleware for shedding load when an inner service isn't ready; an error budget is a clear, objective metric for how unreliable a service is allowed to be. Does this topic's own two measured bursts model exactly the real distinction both sources draw, between shedding itself and the explicit budget that judges it? Takeaway (moved here from step 2): an explicit, stated failure budget is what turns a measured rejection rate from an unexplained rise in errors into a real, judged, expected cost of real overload.
8. **Recap** — A real burst of requests past a real queue's own capacity is shed, genuinely and reproducibly, as a real suffix of arrival order, never arbitrarily; an explicit, stated failure budget is what lets that exact, reproducible rate be read as a real, saturated resource behaving correctly, rather than an unexplained rise in errors.
