## A.1 The problem it solves

Every earlier chapter in this domain measured one real mechanism in isolation: a bounded channel's own backpressure (Ch.10), a `Tower`/`Axum` service's own `poll_ready` contract (Ch.18), a span, a structured field, a metric, and a typed error (Ch.33). A real production service needs all of them at once, composed so that a failure in one real layer (a slow downstream, a full queue, a client that disconnects) cannot silently corrupt or overload a different layer. This chapter integrates Ch.9–10, Ch.18, and Ch.33 into one real, running async service, and measures two real, specific costs of getting that composition wrong: a service whose own HTTP edge can reach storage directly, bypassing its own bounded queue, genuinely loses the backpressure that queue was built to provide, continuing to accept and touch storage for work it should have shed; and a service with no explicit, measured failure budget cannot tell a caller, or itself, whether an increase in rejected requests under real load is the real, intended behaviour of a saturated resource or a real bug.

By the end of this chapter's two topics, the learner can: build a real async service where each layer (HTTP edge, bounded queue, worker pool, storage, shutdown coordinator) owns a narrow, real state boundary, and measure that a request rejected at one boundary genuinely never touches the layers behind it; and drive that same real service under increasing real concurrent load, measuring the real point at which its own bounded queue saturates, the real shape of the resulting rejections, and that a real shutdown signal drains in-flight work correctly instead of dropping it.

## A.2 The order of ideas, and why

1. **Service topology and state boundaries** (topic 90, this chapter's first topic) — builds the real service itself: a real Axum HTTP edge that only ever validates a request and tries to enqueue it on a real, bounded `tokio::sync::mpsc` channel; a real worker pool pulling from that channel and calling a real, minimal storage layer; and a real shutdown coordinator. Measures that a request rejected at the queue boundary (because the queue is full) genuinely never reaches the worker pool or the storage layer, and that a real shutdown signal lets in-flight queued work finish and reach storage rather than being dropped.
2. **Failure budget and overload behaviour** (topic 91) — drives the identical real service from topic 90 under real, increasing concurrent load until its own bounded queue genuinely saturates, measuring the real, exact count of requests it sheds once saturated (against an explicit, stated failure budget) and that every shed request is genuinely one that arrived once the queue was already full, never an arbitrary one.

Each topic's own `examples/` folder holds its own independent copy of the service at the point that topic needs it, continuing this domain's own self-contained-topic rule.

- **Topic 90** builds the real service with five real layers, each owning a narrow real boundary: an Axum handler (validates, then `try_send`s onto a bounded channel, returning a real 503 immediately if the channel is full, without ever calling the worker pool or the storage layer); the bounded channel itself; a small real worker pool (`tokio::spawn`ed tasks) that receives from the channel and calls the storage layer; a real, minimal storage layer (a `Vec` behind a `Mutex`, with a small real delay standing in for real I/O); and a real shutdown coordinator (a `tokio_util::sync::CancellationToken`) that stops the edge from accepting new work and waits for the worker pool to drain the queue before exiting. ## A.4 Terms and notation (continuing Chapters 1–33's vocabulary)

Everything in Chapters 1–33 §A.4 still applies. This chapter adds:

- **State boundary**: a real, specific point in a service's own layering where one real component owns a piece of state (a queue, a connection, a storage handle) and the components on either side of it only ever reach it through one real, narrow interface.
- **Load shedding**: a real, deliberate rejection of a request once a real resource (here, the bounded queue) is at capacity, returned immediately rather than queued or retried, continuing Ch.10's own `try_send` vocabulary.
- **Failure budget**: a real, explicit, stated threshold for how much of a specific real failure (a queue-full rejection, a downstream timeout) a service is allowed to produce before that rate itself is treated as a real incident rather than expected, saturated behaviour.
- **Graceful shutdown**: a real, coordinated stop in which a service stops accepting new real work the instant a shutdown signal arrives, but lets real work already admitted finish before the process actually exits, continuing Ch.10's own structured-shutdown vocabulary.

Narration words (continuing the convention: no digits, symbols, or code-style names spoken): "a narrow door between two parts" for a state boundary; "turned away on purpose because there's no room" for load shedding; "how much of that is actually allowed" for a failure budget; "finishing what's already in before closing the door" for graceful shutdown.
