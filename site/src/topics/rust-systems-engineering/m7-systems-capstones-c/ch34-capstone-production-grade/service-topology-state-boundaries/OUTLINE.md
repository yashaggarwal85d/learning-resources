## Storyboard (8 steps, 3 predict/reveal pairs)

1. **BoundaryPredict** — A real, bounded queue (capacity one) sits behind a real Axum edge. Three real requests arrive quickly, faster than the single worker can finish its first real storage write. Does the third one get queued like the first two? Options: yes, the queue just grows to fit whatever arrives; no, genuinely, the third is rejected once the queue is already full (correct); only if the requests arrive in a different order.
2. **BoundaryReveal** — Measured: the first two real requests are genuinely queued, and the third is genuinely rejected the instant it finds the bounded queue already full, before the worker pool or storage layer is ever involved. No separate takeaway here (this is the reel's own "from" step for the phone swipe test; its takeaway moves to step 7, the connecting step, below).
3. **StoragePredict** — Does that rejected third request show up in the real storage layer once the worker has finished processing everything it actually received? Options: yes, it was submitted, so it eventually gets written; no, genuinely, a request rejected at the queue never reaches storage at all (correct); only if storage is checked too soon.
4. **StorageReveal** — Measured: once the worker finishes, the real storage layer holds exactly the first two requests and nothing else; the rejected third request never reached it, because the boundary that rejected it sits entirely in front of the worker pool and the storage layer. Takeaway: a request rejected at one real boundary genuinely never touches any real layer behind it.
5. **ShutdownPredict** — A real shutdown coordinator stops a second, independent instance of this service from accepting new work. Two real requests were already queued first. Does the work already queued get finished, or dropped along with the shutdown? Options: dropped, since the service is shutting down; finished, genuinely, since the queue is drained before the service actually stops (correct); only if the requests happen to be queued slowly enough.
6. **ShutdownReveal** — Measured: once shutdown begins, a real new request is genuinely rejected immediately, while the two real requests already queued are genuinely drained all the way to storage before the worker pool itself stops. Takeaway: a real shutdown coordinator closes the door to new work immediately, but finishes draining whatever had already gotten in.
7. **DocsReveal** — The `tokio::sync::mpsc` and `tokio-util::sync::CancellationToken` documentation each state this directly, in their own words: a bounded channel at capacity rejects a send and provides backpressure; a cancellation token signals a real request to one or more tasks. Does this topic's own two measured scenarios model exactly the real mechanisms both sources describe? Takeaway (moved here from step 2): a service's own real topology is only as strong as its narrowest boundary, the one place a rejection is actually allowed to happen.
8. **Recap** — A request rejected at a real, bounded boundary never reaches the layers behind it; the same boundary, closed deliberately during a real shutdown, still lets whatever had already gotten through finish, rather than dropping it; together, that is what makes a layered service's own topology real rather than only drawn on a diagram.
