# Outline — Feature flags and their combinatorics

Concept ledger: introduces `a-feature-must-stay-additive-under-unification`; uses `a-crate-is-the-real-unit-of-a-rebuild` (topic 82) only in prose, per Chapter 32's own CHAPTER.md §A.7 — this topic takes the workspace topic 82 already built and asks what happens when two sibling crates in it want slightly different behavior from the one dependency they share.

Bridge/handoff (verbatim from CHAPTER.md §A.8): "A workspace decides which crates exist and what each one depends on; it says nothing yet about what happens when two of those crates want slightly different behavior from the one dependency they share." Hands off to topic 84 (verbatim): "A feature that stays additive under real unification is a real, local correctness property; it says nothing yet about whether anyone but its own author ever actually checks that property before it ships."

Chapter 32's own disclosed convention (§A.3/§A.6) applies, in a variant form: this topic's own workspace (`feature_demo/`) has three crates, `core_crate` (owning two feature-gated behaviors) and two siblings depending on it, `consumer_a` (the one that requests features) and `consumer_b` (the one being measured, which never asks for either feature itself). A second, legacy-resolver workspace (`feature_demo_legacy/`, same shape, two crates only) isolates the dev-dependency claim from a real historical resolver default. All three claims are measured via a real built binary's own stdout, never a timed benchmark or a parsed build log.

## Storyboard (8 steps, 3 predict/reveal pairs)

1. **NonAdditivePredict** — `consumer_b` never asks for `core_crate`'s own `fast_mode` feature. It is built alone, then built again in the same cargo invocation as `consumer_a`, which does request `fast_mode` on the shared `core_crate`. Does `consumer_b`'s own real output change, even though `consumer_b` itself asked for nothing new? Options: no, a crate only sees the features it itself requests; yes, genuinely, because `fast_mode` changes `core_crate`'s own existing behavior and cargo unifies it across the build (correct); only if `consumer_b` is rebuilt by hand afterward.
2. **NonAdditiveReveal** — Measured: `consumer_b` built alone genuinely prints `"plain"`; the identical `consumer_b`, built in one invocation alongside `consumer_a --features consumer_a/fast_mode`, genuinely prints `"fast"` instead, with `consumer_b`'s own source and `Cargo.toml` never touched. No separate takeaway here (this is the reel's own "from" step for the phone swipe test; its takeaway moves to step 7, the connecting step, below).
3. **AdditivePredict** — The identical comparison, but now `consumer_a` requests `core_crate`'s other feature, `fancy`, which only adds a new function and touches nothing `consumer_b` already calls. Does `consumer_b`'s own output change this time? Options: yes, any sibling's requested feature changes a shared dependency's build; no, genuinely, because `fancy` is additive and never touches `plain_output` (correct); only if `fancy` happens to be enabled by default.
4. **AdditiveReveal** — Measured: `consumer_b` built alone and `consumer_b` built alongside `consumer_a --features consumer_a/fancy` genuinely print the identical `"plain"` both times. Takeaway: a feature that only adds, and never changes, a dependency's own existing behavior leaves every sibling that never asked for it genuinely untouched.
5. **DevDepPredict** — `consumer_b` itself declares `core_crate` twice: once as a plain dependency, and once as a dev-dependency with `fast_mode` turned on, for its own tests. Under the resolver edition 2024 makes the default, does that dev-only feature request leak into a plain, non-test build of `consumer_b`? Options: yes, a dev-dependency's own features always apply everywhere; no, genuinely, the modern resolver keeps dev-dependency features out of a non-test build (correct); only if `cargo test` is run first.
6. **DevDepReveal** — Measured: the identical `Cargo.toml` declaration, built under the old, pre-2021 resolver default, genuinely leaks `fast_mode` into the plain build (`consumer_b` prints `"fast"` with no test in sight); built under resolver 3, the edition-2024 default, the identical declaration genuinely does not leak (`consumer_b` prints `"plain"`). Takeaway: the resolver a workspace declares decides whether a dev-only feature request can genuinely reach a build nobody meant it to touch.
7. **DocsReveal** — The Cargo Book states these rules directly, in its own words: cargo unifies the union of every feature requested on a shared dependency across the whole build, and a feature should stay additive so that enabling any combination of features stays safe. Does this topic's own three measured comparisons model exactly the rule and the risk both quotes describe? Takeaway (moved here from step 2): a feature's own real safety is never a property of the crate that defines it alone; it is a property of every combination the build graph can actually unify it into.
8. **Recap** — A feature a sibling crate requests is unified into a shared dependency's own single build, for better or worse; staying additive is what keeps that unification safe, and the resolver a workspace declares decides whether even a dev-only request can leak somewhere nobody meant it to go.
