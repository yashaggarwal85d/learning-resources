## A.1 The problem it solves

A synchronous program's own call stack already tells a debugger most of the story: who called whom, in what order, still waiting for what. An async Rust program genuinely breaks that story, since one task's own execution hops between other tasks on a shared pool of worker threads, and a single logical operation's own real work can be interleaved with a dozen others on the identical thread at the identical moment. Every one of this chapter's own four topics measures a real, specific cost of trying to diagnose that system with the wrong tool: a `Span::enter()` guard held across a real `.await` point genuinely fails to compile the instant it crosses a thread boundary, since the guard itself is deliberately not `Send`; a formatted log line loses a real field's own structure the moment another string is embedded in it, where a structured field survives being queried, filtered, and joined; a counter and a histogram answer two genuinely different real questions about the identical overload, and asking a counter the histogram's own question gives a real, wrong answer; and a timeout, a cancellation, and a genuine remote error are three genuinely different real failures that an identical, untyped `Result<T, String>` makes indistinguishable, driving the identical, wrong retry policy for all three.

By the end of this chapter's four topics, the learner can: instrument a real async function with a span that genuinely survives every `.await` inside it, and measure the real, specific way the classic "guard across await" mistake breaks; emit a real structured field a plain formatted log line cannot preserve, and measure what survives a real query against it that a string cannot; choose between a real counter, gauge, and histogram for a real overload question and measure a case where the wrong one answers it incorrectly; and design a real, typed error distinguishing a timeout from a remote error from a local resource exhaustion, and measure that each genuinely drives a different, correct retry decision a single untyped error cannot.

## A.4 Terms and notation (continuing Chapters 1–32's vocabulary)

Everything in Chapters 1–32 §A.4 still applies. This chapter adds:

- **Span**: a real, named period of time `tracing` tracks, with a real start and a real end, that a function's own execution can enter and exit any number of times (for example, once before and once after an `.await` suspends it).
- **Event**: a real, single, point-in-time record `tracing` emits inside a span's own currently-entered context, carrying real, structured fields rather than only a formatted string.
- **Guard (`Span::enter()`)**: a real, deliberately non-`Send` value whose own lifetime marks exactly when a span is entered; holding it across a real `.await` point is this chapter's own first, classic measured mistake.
- **Subscriber / Layer**: the real, pluggable component `tracing-subscriber` uses to decide what happens to a span or event once it is recorded — filtering, formatting, exporting, or (as every topic in this chapter measures directly) simply collecting it for inspection.
- **Counter / gauge / histogram**: three real, genuinely different metric shapes; a counter only ever goes up, a gauge can be read as a real current value that goes up or down, and a histogram buckets a real distribution of measured values, each answering a genuinely different real question about the identical system.

Narration words (continuing the convention: no digits, symbols, or code-style names spoken): "a period the code is really inside of" for a span; "a real moment with facts attached" for an event; "something that can't survive being handed to another thread" for a non-`Send` guard; "what's happening right now" for a gauge, versus "how many has it been" for a counter; "a shape mistake tells apart" for a typed error.
