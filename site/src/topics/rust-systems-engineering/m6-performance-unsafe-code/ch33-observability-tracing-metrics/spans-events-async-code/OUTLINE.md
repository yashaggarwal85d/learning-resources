# Outline — Spans and events in async code

Concept ledger: introduces `a-spans-lifetime-ties-to-being-polled`; uses no earlier chapter's own introduced id directly in its own measured code, per Chapter 33's own CHAPTER.md §A.7 — this topic opens the chapter by building the one real async operation every later topic in this chapter extends.

**Changes from the chapter plan:** CHAPTER.md's own first draft of this topic's introduced id (`a-span-that-crosses-await-must-stay-send`) assumed holding `Span::enter()`'s own guard across a real `.await` fails to compile once the future must be `Send`. Direct, empirical verification (building and checking the real guard's own `Send`-ness) found this is false in the current `tracing` release: `Entered<'_>` (returned by `.enter()`) is genuinely `Send`, since it holds only a reference to the `Span`; only the separate, owned `EnteredSpan` guard (returned by `.entered()`, not used by this topic) carries a deliberate `PhantomNotSend` field. The real mistake compiles cleanly and is a real, measured logic bug instead (a leaked thread-local span context), which is what this topic actually measures. CHAPTER.md's own A.7 table and this topic's own introduced id were corrected to `a-spans-lifetime-ties-to-being-polled` to match the real, verified finding before any later topic could reference the inaccurate one.

Bridge/handoff (verbatim from CHAPTER.md §A.8): "A workspace, a feature, a lint policy, and a release profile are all real, project-shaping decisions made once and paid for on every later build; this chapter turns to a system that is actually running, where the cost of a wrong decision shows up only once real traffic is already flowing through it." Hands off to topic 87 (verbatim): "A span that survives every real await inside it tells you when something happened and for how long; it says nothing yet about what, specifically, was true while it was happening."

Chapter 33's own disclosed convention (§A.3/§A.6) applies: this topic's own crate (`examples/span_demo/`) is one small library plus three binaries, all sharing one real custom `tracing_subscriber::Layer` (`span_demo::Capture`) that records, for every event, the name of whichever span `tracing` considers "current" the instant that event fires. Each binary runs two real async tasks together on a real, single-threaded tokio runtime, so both genuinely interleave on the identical OS thread, which is exactly the condition the classic mistake needs to show up at all.

## Storyboard (8 steps, 3 predict/reveal pairs)

1. **BadPredict** — `task_a` holds a real `Span::enter()` guard across a real `.await`; while it is suspended, a genuinely different task, `task_b`, runs on the identical thread and records one real event. Does that event get recorded as happening inside `task_a`'s own span? Options: no, a span only ever covers the task that entered it; yes, genuinely, the span is never exited across the await, so it leaks onto whatever runs next (correct); only if both tasks share the identical span.
2. **BadReveal** — Measured: the real, captured event fires with its own current span genuinely recorded as `task_a`, even though it happened entirely inside `task_b`'s own code, on a different task that never touched `task_a`'s span at all. No separate takeaway here (this is the reel's own "from" step for the phone swipe test; its takeaway moves to step 7, the connecting step, below).
3. **InstrumentPredict** — The identical two tasks are run again, but `task_a` now wraps its own future with `.instrument(span)` instead of holding a guard. Does `task_b`'s own event still get misattributed to `task_a`'s span? Options: yes, the span still has to be entered somehow; no, genuinely, the span is correctly exited and re-entered around each real await (correct); only on a multi-threaded runtime.
4. **InstrumentReveal** — Measured: the identical captured event now genuinely has no current span at all, since `.instrument(span)` exits `task_a`'s span the instant it yields and only re-enters it once `task_a` itself resumes. Takeaway: a span attached to a future, not held by hand, is exited and re-entered around every real await inside it.
5. **MacroPredict** — The identical comparison once more, this time with `task_a` written as a plain async function carrying `#[instrument]` instead. Does it behave the same, correct way `.instrument(span)` did? Options: no, the macro only adds fields, it does not fix the leak; yes, genuinely, the macro generates the identical, correct `.instrument` wrapping under the hood (correct); only if the function takes no arguments.
6. **MacroReveal** — Measured: the identical captured event again has no current span at all, exactly matching `.instrument(span)`'s own real result, confirming `#[instrument]` genuinely generates the same correct code by hand would otherwise have to write. Takeaway: the attribute macro is not a shortcut with different behavior, it is the identical, correct mechanism, generated for you.
7. **DocsReveal** — The `tracing` crate's own documentation states this directly, in its own words: holding the guard across an await results in incorrect traces, since another task will begin executing while remaining in the entered span; the attached span is instead entered every time the instrumented future is polled. Does this topic's own three measured runs model exactly the mistake and the fix the docs describe? Takeaway (moved here from step 2): a span's own lifetime has to be tied to a future being polled, never to a guard a human remembers to hold for exactly the right duration.
8. **Recap** — Holding a span's own guard across an await lets it leak onto whatever runs next on the same thread; `.instrument(span)` and `#[instrument]` both fix it the identical, correct way, by exiting and re-entering the span around every real await instead.
