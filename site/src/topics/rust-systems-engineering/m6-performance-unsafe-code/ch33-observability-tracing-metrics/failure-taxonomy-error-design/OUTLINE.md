## Storyboard (8 steps, 3 predict/reveal pairs)

1. **TypedPredict** — A real, typed error distinguishes a real timeout from a real remote error. Matched directly on its own variant, does a real retry decision correctly retry the timeout and skip the remote error? Options: no, a typed error still has to be read as text first; yes, genuinely, matching the variant directly gives the correct decision for both (correct); only if the variant names happen to be spelled a specific way.
2. **TypedReveal** — Measured: matched directly on the real, typed variant, the retry decision correctly retries the real timeout and correctly skips the real remote error, exactly as the taxonomy says it should. No separate takeaway here (this is the reel's own "from" step for the phone swipe test; its takeaway moves to step 7, the connecting step, below).
3. **UntypedPredict** — The identical two real errors, rendered only as plain strings, are checked by the identical crate's own retry logic, now reading each message's own text instead of a variant. Does it still correctly tell the timeout and the remote error apart? Options: yes, the words in the message still say which kind it is; no, genuinely, both real messages share a substring any plausible check would key on (correct); only if the messages are read in the wrong order.
4. **UntypedReveal** — Measured: checked by text alone, the real retry decision now retries both the real timeout and the real remote error, since both of this crate's own real error messages share the identical "operation failed" substring the untyped check keys on; it genuinely cannot tell the two failure kinds apart at all. Takeaway: a string rendering of an error can share the identical words for two genuinely different failures, where a typed variant cannot.
5. **DisagreePredict** — On the identical real remote error, does the typed decision and the untyped decision actually disagree about whether to retry it? Options: no, both decisions always agree once an error has already happened; yes, genuinely, the typed version correctly skips it while the untyped version incorrectly retries it (correct); only if the remote error's own message is unusually long.
6. **DisagreeReveal** — Measured: on the real remote error, the typed decision correctly says no, and the untyped decision incorrectly says yes, a real, direct disagreement produced by the identical two real errors, read two different ways. Takeaway: an untyped error's own wrong retry decision is not a hypothetical risk; it is a real, measured outcome of reading the identical failure as text instead of as a type.
7. **DocsReveal** — The `thiserror` and `anyhow` crates' own documentation each state this directly, in their own words: `thiserror` provides a derive macro for the standard library's own `Error` trait, fitting a library's own typed errors; `anyhow` provides a single, dynamic error type for an application's own contextual errors. Does this topic's own typed-versus-untyped comparison model exactly the real distinction both crates are built around? Takeaway (moved here from step 2): a typed error is chosen at a library's own boundary specifically so a caller can match on what happened, not merely read about it.
8. **Recap** — A real, typed error, matched on its own variant, correctly drives two different real retry decisions for two genuinely different real failures; the identical pair, read only as text, cannot tell them apart at all, and a real retry loop built on it gets one of the two decisions genuinely wrong.
