Bridge/handoff (verbatim from CHAPTER.md §A.8): "This chapter measured what a safety contract has to guarantee, what makes a value valid in the first place, and how a real checker catches a violation only on the path it actually runs; the next chapter turns to a boundary where Rust's own rules stop applying at all, because the code on the other side of it was never written in Rust." Chapter 31's own disclosed limitation (§A.6) applies: this sandboxed container cannot add and link a genuinely separate compiled C library, so the FFI boundary is built as real `extern "C"` and `extern "C-unwind"` functions inside the same crate, called only through their own declared extern signature, exactly as a genuinely separate C caller would; this is a real ABI boundary even though both sides happen to be compiled by `rustc` here.

## Storyboard (8 steps, 3 predict/reveal pairs)

1. **OwnershipPredict** — A real buffer handle crosses the boundary through `allocate_buffer_handle`/`free_buffer_handle`. After a handle is correctly freed once, what happens when the identical handle is freed a second time? Options: it frees successfully again, silently; the free is genuinely rejected, since the handle is no longer live (correct); the program crashes immediately.
2. **OwnershipReveal** — Measured: every correct allocate/free pair is accepted exactly once, a second free on the same handle is genuinely rejected rather than performed, and no handle is ever left outstanding afterward. No separate takeaway here (this is the reel's own "from" step for the phone swipe test; its takeaway moves to step 7, the connecting step, below).
3. **ErrorCodePredict** — `checked_divide` writes its real result through an out pointer and returns a status code, since there is no `Result` on the wire. When the real call fails (dividing by zero), what happens to the out pointer? Options: it is set to zero; it is left genuinely untouched, carrying whatever the caller put there before the call (correct); it is set to the error code itself.
4. **ErrorCodeReveal** — Measured: a genuine success writes the real value through the out pointer and returns the OK status; a genuine failure returns its own status code and leaves the out pointer genuinely untouched. Takeaway: a status code is only half the error protocol; where the real answer is written matters just as much.
5. **UnwindPredict** — `run_step` is declared `extern "C-unwind"` and panics when told to. When a real caller on the other side of the boundary catches that panic, does the caller genuinely keep running afterward? Options: no, the whole process has already aborted; yes, genuinely, since `"C-unwind"` defines exactly this crossing (correct); only if the panic message is empty.
6. **UnwindReveal** — Measured: the real panic crossing the `"C-unwind"` boundary is genuinely caught, and the caller genuinely keeps running afterward, exactly as the ABI's own unwind contract defines. Takeaway: `"C-unwind"` is not a suggestion; it is the one calling convention that genuinely defines what crossing with an unwind means.
7. **DocsReveal** — The Rustonomicon states the identical ownership and unwinding rules directly, in its own words: a foreign library handing off ownership of a resource to the calling code requires Rust's own destructors to guarantee its release, and a boundary expecting a panic or a foreign exception to cross it must use the appropriate `-unwind` ABI string; the Rust Reference's own definition of a calling convention names who is responsible for cleaning up the stack as part of that same real protocol. Does this topic's own three measured boundaries model exactly the protocol both sources describe? Takeaway (moved here from step 2): a calling convention's string names only the visible fraction of a protocol both sides keep by hand.
8. **Recap** — Matching a C struct's own layout is necessary, but a real FFI boundary is a protocol: who frees a handle, where a failure's real answer is written, and what a panic crossing the line is actually defined to do.
