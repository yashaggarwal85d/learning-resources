## A.1 The problem it solves

Chapter 10's own handoff named the gap directly: "every shutdown sequence in this chapter has been a Rust-level story — tasks, channels, tokens. Underneath every one of those tasks sits a real kernel handle — a file descriptor, a process, a signal — whose ownership rules this chapter has been quietly assuming the whole time." Milestone 2 built an entire runtime's worth of async machinery on top of readiness and task ownership without ever asking what a file descriptor actually is, or what happens to it across a `fork`, a `clone`, or a dropped `Command`. This chapter answers that directly. An fd is not a value a program owns outright the way it owns a `Vec`; it is a process-local handle into a kernel-side *open file description*, and two fds — one duplicated, one inherited across a `fork` — can share that same open file description and its read/write offset, which is exactly the kind of aliasing Rust's ownership model is built to make explicit rather than implicit. I/O safety (RFC 3128, stabilized in Rust 1.63) gives this aliasing the same ownership/borrow distinction Chapters 1–2 already taught for memory — `OwnedFd` closes the real kernel resource on `Drop`, `BorrowedFd<'a>`/`AsFd` borrow it without taking ownership, and `into_raw_fd`/`from_raw_fd` are the explicit, auditable points where that ownership crosses an API boundary — specifically so that a use-after-close bug (one fd closing a resource a different, unrelated owner still believes it holds) becomes a type error instead of a runtime failure mode. None of this is confined to file I/O: `std::process::Command` spawns a real child process by forking and execing, and a `fork` inside a multithreaded process leaves the child with exactly one thread and a heap that may be in the middle of being locked by a mutex some other, now-nonexistent thread held — which is precisely why only async-signal-safe operations are permitted between `fork` and `exec`, and why Rust made `std::env::set_var` `unsafe` in the 2024 edition over its own real race with C's `getenv`.

By the end of the chapter the learner can: explain why an fd is a handle rather than a value, predict exactly when two fds share an offset (duplication, `fork`) and when they do not; use `OwnedFd`, `BorrowedFd<'a>`/`AsFd`, and `into_raw_fd`/`from_raw_fd` to make an ownership transfer explicit at an API boundary, and name why `O_CLOEXEC` being std's default closes the specific leak-across-`exec` hole that an unset `CLOEXEC` flag opens; and explain why only async-signal-safe operations are permitted in a forked multithreaded child before `exec`, what a pidfd buys over a raw PID for race-free process management, and why `std::env::set_var` needed to become `unsafe` in Rust 2024.

## A.2 The order of ideas, and why

Measures `O_CLOEXEC` being std's actual default, and what a cleared `CLOEXEC` flag actually leaks into a child process across a real `exec`.
2. **Processes, signals, and environment safety** (topic 37) — needs (1): once a real fd's ownership and closing behaviour is established, spawning a real child process raises the exact next question — what is and is not safe to do between `fork` and `exec` in a process that was multithreaded a moment before. ## A.3 The running example: a real fd, duplicated, forked, and crossed into a child

Both topics share one running example family (no cross-topic imports, per Chapters 1–10's convention, except where a topic explicitly measures a previous topic's own construction as its baseline): a real file opened by the process itself, whose raw fd is then put through the exact operations this chapter is about.

- **Topic 36** opens a real temp file, duplicates its fd with `dup`, and measures directly that writing through one fd moves the shared offset the other one then reads from — the same-offset claim, measured, not assumed. It wraps the duplicated fd in `OwnedFd`, drops it, and measures that the underlying descriptor is genuinely closed (a subsequent raw syscall on that fd number fails) while a `BorrowedFd` taken from the *other*, still-owned fd remains valid — the use-after-close boundary I/O safety exists to draw. It opens a file once with std's default flags and once with `O_CLOEXEC` explicitly cleared via `OpenOptionsExt`, `fork`s a child via `Command`, and measures directly which fd is still open inside the child's own `/proc/self/fd` and which is not.
- **Topic 37** reuses topic 36's real open file and spawns a real child process with `std::process::Command` around it, measuring the child's actual exit status and what it can see of the parent's fd table. It demonstrates, directly and safely (never calling a genuinely unsafe operation inside a real fork-to-exec window, only describing and citing it), why a `Mutex` held by one thread at `fork` time cannot be unlocked by any thread in the child — the thread that held it does not exist there — and measures a pidfd obtained via `Command`'s own pidfd support staying valid and unambiguous across a real process exit, where a raw PID could in principle be reused. It measures the real, hand-built data race between a thread calling something that reads the environment internally and a thread calling `std::env::set_var` concurrently, demonstrating why Rust 2024 made `set_var` `unsafe`.

## A.4 Terms and notation (continuing Chapters 1–10's vocabulary)

Everything in Chapters 1–10 §A.4 still applies. This chapter adds:

- **File descriptor (fd)**: a small integer, local to one process, that indexes into that process's own fd table; it is a handle, not the resource itself.
- **Open file description**: the kernel-side object an fd points to — holding the real read/write offset, flags, and file state — which two different fds (via `dup`, or via `fork`) can point to at once, sharing that same offset.
- **I/O safety**: the ownership/borrow distinction RFC 3128 gives to raw fds — `OwnedFd` (closes on `Drop`), `BorrowedFd<'a>`/`AsFd` (borrows without owning), `into_raw_fd`/`from_raw_fd` (the explicit, auditable ownership handoff), built to make use-after-close a type error rather than a runtime failure.
- **`O_CLOEXEC`**: the flag that closes an fd automatically across `exec`, which std sets by default specifically to stop fds leaking into a child process that never asked for them.
- **Async-signal-safe**: the narrow set of operations safe to call in a forked, not-yet-exec'd multithreaded child (or inside a signal handler) — because any lock another thread held at that moment belongs to a thread that, in the child, no longer exists to release it.
- **pidfd**: a real, open file descriptor that refers unambiguously to one specific process, immune to the PID-reuse race a raw numeric PID carries once that process has exited.
- **`std::env::set_var` as `unsafe` (Rust 2024)**: the environment is process-global, shared mutable state that C's own `getenv` reads without synchronization, which is the real race `set_var` from another thread can hit.

Narration words (continuing the convention: no digits, no code-style names spoken): "a handle, not the thing itself" for a file descriptor; "two handles, one real file underneath, sharing where they've read to" for a shared open file description; "who owns it, and who's only allowed to look" for the I/O-safety ownership/borrow split; "closed automatically the moment a new program takes over" for `CLOEXEC`; "only the few operations proven safe with a lock nobody's left to release" for async-signal-safety; "a handle to one exact process, never confused with a later one reusing its number" for a pidfd; "a global and a thread, reading and writing it at once" for the environment race.

- **36** bridges from Chapter 10's own real handoff ("underneath every one of those tasks sits a real kernel handle — a file descriptor, a process, a signal — whose ownership rules this chapter has been quietly assuming the whole time") and opens by answering it directly: a file descriptor's real ownership rules, made explicit the same way Chapters 1–2 made memory ownership explicit. - **37** bridges from 36's handoff and shows that sharper rule directly: why a forked, not-yet-exec'd multithreaded process can safely do almost nothing, and what a pidfd and a `set_var` race both reveal about process-level state being shared more widely than it looks. Hands off to Chapter 12 (Virtual Memory, mmap, Page Faults, and Memory Mappings): "A process's file descriptors and its signals are both kernel handles this chapter made explicit. Its memory is a kernel handle too — just one so heavily abstracted by the virtual memory system that most code never has to think of it as one at all, until it's mapped directly."
