## A.1 The problem it solves

Chapter 15's own handoff left the question open at exactly the right place: that chapter was about a process getting its own data durably onto its own disk, and this one is about getting bytes reliably to another process entirely, over a connection that offers none of a filesystem's guarantees. TCP is the first surprise most people miss: it is a byte stream, not a message queue, so a single `read` or `write` call can return fewer bytes than asked for, with no error, for entirely ordinary reasons (the kernel's own socket buffers, Nagle's algorithm batching small writes, delayed ACK batching small reads) — and a protocol that assumes a `write` call equals a message is just wrong. Getting whole messages back out of that byte stream needs an explicit framing strategy, chosen deliberately: length-prefixing (fast, but an unbounded length field is a denial-of-service vector unless capped), delimiter-based (simple, but needs escaping and a scan for the delimiter costs something), or fixed-size (simplest, but wastes bandwidth on anything that doesn't fit the size exactly). None of this says anything about overload: a connection that produces data faster than it's consumed needs explicit backpressure — pausing the producer by not reading (so the TCP window itself closes and the remote sender blocks), dropping by policy, or closing the connection once a bound is hit — or it becomes an unbounded buffer, and then an outage.

By the end of the chapter the learner can: explain why TCP's own byte-stream contract means partial reads and writes are not bugs, and name the specific mechanisms (Nagle, delayed ACK, socket buffer sizing against the bandwidth-delay product, half-close versus RST, `SO_LINGER`, TIME_WAIT) that shape when and how much of a message actually arrives in one call; choose and implement a framing strategy with its own documented failure mode addressed (a capped length prefix, not an unbounded one) and extract frames without copying, using `tokio_util::codec` and `BytesMut::split_to`; and implement connection-level backpressure as an explicit state machine — stop reading to signal pause, bound the per-connection output buffer, set timeouts, and defend against a slow-loris-style resource exhaustion attack.

## A.3 The running example: one real TCP connection, measured both ways

Self-contained per topic (no cross-chapter imports except where a topic explicitly measures a prior chapter's own construction as its baseline), continuing Chapters 1–15's conventions.

- **Topic 42** opens a real TCP connection over `127.0.0.1` (a real `TcpListener`/`TcpStream` pair, not a mock), writes a payload in one call, and measures how many `read` calls it actually takes to receive it on the other end — across a small payload (likely one read), a payload that straddles the socket buffer's own size, and a `TCP_NODELAY` toggle's measured effect on latency for small writes. Half-close is measured by calling `shutdown(Write)` on one side and confirming the peer's `read` returns `0` (EOF) while the connection can still be written to in the other direction; `SO_LINGER` and TIME_WAIT are measured or quoted depending on what this container's own loopback networking can actually demonstrate.
- **Topic 43** builds a real length-prefixed framing layer over that same kind of connection, measuring that a frame under the cap round-trips correctly and a frame claiming a length over the cap is rejected before the implementation ever allocates a buffer that large — the actual DoS the cap exists to prevent. `BytesMut::split_to`'s zero-copy claim is measured by confirming the extracted frame's buffer is not a fresh allocation (via a pointer/capacity check), not merely asserted from the API's documentation.
- **Topic 44** builds a real connection that deliberately stops calling `read` once a policy threshold is reached, and measures that the remote peer's own `write` calls genuinely block (or report `WouldBlock` on a non-blocking socket) once the TCP window closes — a real, observable backpressure signal, not a simulated one. A bounded output buffer and a per-connection timeout are measured the same way: pushing past the bound and confirming the implementation's own policy fires, and starving a connection past its deadline and confirming the timeout actually closes it.

## A.4 Terms and notation (continuing Chapters 1–15's vocabulary)

Everything in Chapters 1–15 §A.4 still applies. This chapter adds:

- **Byte stream, not a message queue**: TCP delivers an ordered, undifferentiated sequence of bytes; a single `read` or `write` call can return fewer bytes than requested, for entirely ordinary reasons, with no error.
- **Nagle's algorithm / delayed ACK**: Nagle batches small outgoing writes to avoid flooding the network with tiny packets; delayed ACK batches small acknowledgments on the receiving side; together they can compound into measurable added latency for small, latency-sensitive messages. `TCP_NODELAY` disables Nagle's batching on a given socket.
- **Bandwidth-delay product**: the amount of data that can be in flight on a connection at once (bandwidth × round-trip time), which bounds how large a socket's own send/receive buffers need to be to keep a fast, high-latency link fully utilized.
- **Half-close vs RST**: `shutdown(Write)` closes only the local side's ability to send, letting the peer finish reading and still reply — a graceful half-close; an RST is an abrupt, abnormal termination that discards unread data and tells the peer the connection is simply gone.
- **`SO_LINGER` / TIME_WAIT**: `SO_LINGER` controls whether a `close()` call blocks to flush pending data or discards it immediately; TIME_WAIT is the kernel-held state a closed connection's local endpoint occupies afterward, specifically to catch stray late packets from the old connection.
- **Framing strategy**: the explicit, application-level scheme (length-prefix, delimiter, fixed-size) that turns TCP's byte stream back into discrete messages; each has its own documented failure mode an uncapped or careless implementation can hit.
- **Zero-copy frame extraction**: extracting a complete frame from a buffer without copying its bytes into a new allocation, as `BytesMut::split_to` does by splitting the underlying buffer in place.
- **Connection-level backpressure**: an explicit state-machine response to a connection producing faster than it's consumed — pausing the producer (by stopping reads, so the TCP window closes), dropping by policy, or closing once a bound is hit — rather than letting an unbounded buffer absorb the difference.

Narration words (continuing the convention: no digits, symbols, or code-style names spoken): "an undifferentiated stream of bytes, not a queue of messages" for the byte-stream contract; "batching small writes, and batching small acknowledgments" for Nagle/delayed ACK; "a cap on how much can be in flight at once" for the bandwidth-delay product; "closing your own side gracefully, versus the connection just being gone" for half-close vs RST; "deliberately capping how large a single message can claim to be" for length-prefix framing's own cap; "splitting the buffer in place, not copying it" for zero-copy frame extraction; "stop reading, and the sender itself slows down" for connection-level backpressure.
