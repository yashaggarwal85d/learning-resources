# Outline — Checkpoints, offsets, and watermarks

Concept ledger: introduces `a-checkpoint-taken-before-the-real-commit-loses-data`; reuses `an-owned-buffer-moved-forward-keeps-memory-bounded` (topic 97, this chapter), per Chapter 43's own CHAPTER.md §A.7.

Bridge (verbatim from CHAPTER.md §A.8): "A pipeline whose own real memory stays bounded under a slow sink has solved one real problem, keeping up; the next real problem is what happens when it stops running entirely, mid-stream, and has to start again without losing or repeating a single real record." Hands off within the chapter to topic 99 (verbatim): "Surviving a real crash without losing or repeating a single real record is a real, structural property of a pipeline's own restart logic; it says nothing yet about whether that same pipeline is actually efficient while it runs, which is a real, separate question a single throughput number can hide."

Chapter 43's own disclosed convention (§A.3/§A.6) applies: this topic's own crate (`examples/checkpoint_demo/`) reuses topic 97's own real, channel-connected source-and-sink shape and adds a real checkpoint, recorded either after the sink's own real commit genuinely returns (correct) or at the moment a batch is merely handed to the sink, before that real commit has run at all (wrong). Both real pipelines are driven through the identical real crash point, the instant the fourteenth real commit has finished but the fifteenth has only just begun; a restart is then modeled directly from each pipeline's own real checkpoint value against what was genuinely, durably committed before the crash.

## Storyboard (8 steps, 3 predict/reveal pairs)

1. **CorrectPredict** — A real pipeline checkpoints only once a batch's own real commit has genuinely returned, never before. It crashes mid-stream, right as its fifteenth real batch begins committing. Does a restart from that real checkpoint reprocess anything already committed, or lose anything that was not? Options: it reprocesses whatever was already committed, just to be safe; it reprocesses nothing already committed and loses nothing that was not (correct); it depends on how long the crash takes to notice.
2. **CorrectReveal** — Measured: the real, correct pipeline's own checkpoint lands on exactly the fourteenth batch, the identical real batch its own commit genuinely finished last, so a restart from that checkpoint reprocesses zero batches and loses zero records. No separate takeaway here (this is the reel's own "from" step for the phone swipe test; its takeaway moves to step 7, the connecting step, below).
3. **WrongPredict** — The identical real crash, at the identical real point, this time against a second pipeline that checkpoints the moment a batch is merely handed to the sink, before its own real commit has run at all. Does its own real checkpoint still match what was genuinely committed, or does it run ahead? Options: it still matches, since the handoff happens right before the commit anyway; it runs one real batch ahead of what was genuinely committed (correct); it depends on how slow the commit itself is.
4. **WrongReveal** — Measured: the real, wrong pipeline's own checkpoint lands on the fifteenth batch, one real batch ahead of the fourteen its own commits genuinely finished, because the crash landed exactly while that fifteenth commit was still in flight. Takeaway: a checkpoint taken before the real commit records a promise the pipeline never actually kept.
5. **RestartPredict** — The real, wrong pipeline's own restart resumes from the batch after its own real checkpoint, the sixteenth, skipping the fifteenth entirely. Does that fifteenth batch's own real records get reprocessed later, or are they gone? Options: reprocessed later, once the pipeline catches up; gone, permanently, since the restart never looks at that batch again (correct); it depends on whether the source still has them.
6. **RestartReveal** — Measured: the real, wrong pipeline's own restart genuinely loses the fifteenth batch's own full set of records, permanently, since its checkpoint told it that batch was already done. Takeaway: an advanced checkpoint does not reprocess too much; it loses whatever was never actually, durably committed.
7. **DocsReveal** — The Rust standard library's own documentation on a real, durable file sync states this directly, in its own words: a real commit's own job is to make sure in-memory data genuinely reaches the filesystem before it returns; a checkpoint taken before that return has happened is a checkpoint for a commit that has not, in fact, happened yet. Does this topic's own two measured restarts match exactly what that sentence implies? Takeaway (moved here from step 2): a real checkpoint is only as true as the real commit it is supposed to follow, never the one it merely anticipates.
8. **Recap** — A real checkpoint taken after a real commit genuinely returns lets a restart pick up exactly where it left off, reprocessing nothing and losing nothing; a real checkpoint taken before that same commit returns can look identical right up until a real crash lands in between, at which point it silently erases whatever was never actually, durably committed.
