Hands off within the chapter to topic 98 (verbatim): "A pipeline whose own real memory stays bounded under a slow sink has solved one real problem, keeping up; the next real problem is what happens when it stops running entirely, mid-stream, and has to start again without losing or repeating a single real record."

Chapter 43's own disclosed convention (§A.3/§A.6) applies: this topic's own crate (`examples/pipeline_demo/`) builds two independent, real, three-stage async pipelines (source, batch builder, sink), sharing the identical shape and driven by the identical fast producer (50 batches of 1000 bytes each) against the identical, deliberately slow sink (20ms per batch). The bounded, owning pipeline connects its stages with real, bounded `tokio::sync::mpsc` channels (capacity 4 batches) and moves each batch forward rather than cloning it. The unbounded, cloning pipeline connects its stages with real, unbounded channels and clones each batch before handing it downstream. Both track real, total bytes held across all in-flight batches via an `Arc<AtomicUsize>`, with a second atomic recording the real measured peak via `fetch_max`.

## Storyboard (8 steps, 3 predict/reveal pairs)

1. **BoundedPredict** — A real, bounded pipeline connects its stages with channels that hold only 4 batches at a time, moving each batch forward rather than copying it, against a sink that is deliberately twenty times slower than the producer that feeds it. Does the pipeline's own real, measured memory keep growing while the producer runs ahead, or does it stay capped? Options: it keeps growing for as long as the producer outruns the sink; it stays capped near the channel's own real capacity, however far ahead the producer gets (correct); it grows only until the producer finishes, then shrinks back.
2. **BoundedReveal** — Measured: the real, bounded pipeline's own peak bytes held across every in-flight batch lands at 6,000 bytes, just a few batches' worth, for the entire real run of fifty batches. No separate takeaway here (this is the reel's own "from" step for the phone swipe test; its takeaway moves to step 7, the connecting step, below).
3. **UnboundedPredict** — The identical real producer and the identical real, slow sink, this time connected by channels with no real limit on how many batches they can hold, each stage cloning its own batch before handing it downstream. Does the pipeline's own real, measured peak memory land anywhere near the bounded pipeline's own real peak, or far past it? Options: close to the bounded pipeline's own real peak, since the sink is identically slow either way; far past it, growing toward the full real run's own total bytes (correct); it depends only on how many stages clone, not on the channel's own real capacity.
4. **UnboundedReveal** — Measured: the real, unbounded, cloning pipeline's own peak bytes held reaches 51,000 bytes, essentially the entire real run's own total batch bytes, because its fast producer never once has to wait on the real, slow sink for a single batch. Takeaway: a channel with no real limit removes the one real signal that would have told a fast producer to slow down.
5. **ComparePredict** — The real, bounded pipeline's own measured peak (6,000 bytes) against the real, unbounded pipeline's own measured peak (51,000 bytes), for the identical real workload. Is that real gap a small, incidental difference, or a large, structural one? Options: a small, incidental difference, since both pipelines process the identical real batches; a large, structural difference, over eight times larger, that holds for as long as the real producer outruns the real sink (correct); a difference that only shows up because this run happened to pick a slow sink.
6. **CompareReveal** — Measured: the real, unbounded pipeline's own peak is more than eight times the real, bounded pipeline's own peak, for the identical fifty real batches and the identical real sink delay, a real, structural gap rather than an incidental one. Takeaway: a bounded channel's own real limit is what turns a fast producer's own real head start into backpressure, not goodwill from either stage.
7. **DocsReveal** — The tokio `mpsc` module's own documentation states this directly, in its own words: a bounded channel at capacity rejects a send until capacity frees up, which is exactly how it provides backpressure; an unbounded channel's own send always completes immediately, with no real limit to push back against. Does this topic's own two measured runs match exactly what those two sentences describe? Takeaway (moved here from step 2): an owned buffer moved forward, through a channel that can actually say no, keeps a real pipeline's own memory bounded; cloning into a channel that never says no does not.
8. **Recap** — A real, bounded pipeline that moves each batch forward through channels with a real, enforced limit keeps its own real memory capped under a slow sink; a real, unbounded pipeline that clones each batch into channels with no real limit lets a fast producer's own real head start turn into unbounded real memory, however identically slow the sink stays underneath it.
