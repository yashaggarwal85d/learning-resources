Concept ledger: introduces `records-per-second-alone-hides-a-real-allocation-cost`; reuses `a-checkpoint-taken-before-the-real-commit-loses-data` (topic 98, this chapter), per Chapter 43's own CHAPTER.md §A.7. This is the final topic of Chapter 43 and of the entire Rust Systems Engineering domain.

Bridge (verbatim from CHAPTER.md §A.8): "Surviving a real crash without losing or repeating a single real record is a real, structural property of a pipeline's own restart logic; it says nothing yet about whether that same pipeline is actually efficient while it runs, which is a real, separate question a single throughput number can hide." Hands off to whatever comes after this domain's own final chapter (verbatim, closing this domain): "A bounded pipeline that keeps its own memory capped, restarts without losing or repeating a single real record, and is measured by more than one real number, is what every earlier chapter in this domain was building toward: a real system, judged end to end, by how it actually behaves rather than by any one mechanism in isolation."

Chapter 43's own disclosed convention (§A.3/§A.6) applies: this topic's own crate (`examples/alloc_demo/`) builds two real transform implementations over the identical twenty thousand real records: one that borrows each record's own backing buffer directly (`transform_move`), and one that clones it needlessly before doing the identical real work (`transform_clone`). A real, custom `#[global_allocator]` wraps the system allocator in an `AtomicUsize` counter, measuring the real, total bytes each implementation actually allocates. Both are timed with `std::time::Instant` to measure real records per second.

## Storyboard (8 steps, 3 predict/reveal pairs)

1. **ThroughputPredict** — Two real transform implementations process the identical twenty thousand real records, computing the identical real checksum. One borrows each record directly; the other clones it first, needlessly, before doing the identical work. Does that real difference show up in how many real records per second each one processes? Options: the cloning version is dramatically slower, records per second included; both land within a real, modest band of each other (correct); only the borrowing version produces a real, measurable number at all.
2. **ThroughputReveal** — Measured: the real, borrowing implementation and the real, cloning implementation both process several million real records per second, landing within a real, modest band of each other, statistically indistinguishable throughput for the identical real workload. No separate takeaway here (this is the reel's own "from" step for the phone swipe test; its takeaway moves to step 7, the connecting step, below).
3. **AllocationPredict** — The identical real workload, this time measured by a real, custom global allocator counting every real byte each implementation actually allocates. Does that real number look as close between the two as records per second did? Options: yes, since they process the identical records at the identical speed; no, the cloning version allocates a real, dramatically larger number of bytes per record (correct); only if the records themselves are unusually large.
4. **AllocationReveal** — Measured: the real, borrowing implementation allocates only a handful of real bytes per record, essentially none of each record's own data, while the real, cloning implementation allocates right around each record's own full real size, every single time. Takeaway: records per second measured the identical real speed; bytes allocated measured a real, completely different story underneath it.
5. **GapPredict** — The real, measured gap between eight real bytes per record and two hundred eight real bytes per record, for implementations whose own real throughput looked statistically indistinguishable. Is that a modest, incidental difference, or a real, structural one? Options: modest, since the two implementations run at essentially the identical real speed; a real, structural difference, over twenty times larger, that records per second alone never once revealed (correct); a difference that only shows up at this exact record size.
6. **GapReveal** — Measured: the real, cloning implementation's own bytes per record is more than twenty times the real, borrowing implementation's own, for the identical real throughput and the identical real checksum result, a real, structural gap a single speed number hid completely. Takeaway: two real implementations can run at the identical real speed while paying a dramatically different real cost underneath.
7. **DocsReveal** — The Rust standard library's own documentation on a real global allocator states this directly, in its own words: a real, registered allocator stands behind every real allocation a running program makes, invoked through functions the program never calls directly. Does this topic's own real counting allocator match exactly what that sentence describes? Takeaway (moved here from step 2): records per second alone hides a real allocation cost; a second real number, bytes allocated per record, is what actually exposes it.
8. **Recap** — Two real transform implementations, run over the identical real workload, can report statistically indistinguishable real throughput while one of them allocates more than twenty times the real bytes per record the other does, a real, structural cost that records per second, measured alone, never once reveals.
