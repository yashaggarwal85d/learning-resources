Chapter 41's own disclosed convention (§A.3/§A.6) applies: this topic's own crate (`examples/parser_demo/`) builds a tiny, real binary record format (a one-byte tag, a four-byte little-endian length, then that many bytes of payload) and two real parsers for it: a naive one that reads the length and slices with it directly, and a checked one that validates it against both the real remaining buffer and a real, stated maximum, using `checked_add`, before ever touching it. A second, independent pair of functions measures the identical naive-versus-checked contrast for a real 32-bit addition of two attacker-influenced lengths.

## Storyboard (8 steps, 3 predict/reveal pairs)

1. **BoundsPredict** — A naive parser reads a declared length straight off the wire and slices the buffer with it, no check against how much buffer is actually left. A real, deliberately malformed input claims far more bytes than the real buffer holds. What happens? Options: it returns whatever bytes happen to be there; it genuinely panics, since the slice's own end index runs past the buffer (correct); it silently returns an empty result.
2. **BoundsReveal** — Measured: the naive parser's own unchecked slice genuinely panics on the oversized claim, while a checked parser, validating the same length against the real remaining buffer first, rejects it cleanly with no panic at all. No separate takeaway here (this is the reel's own "from" step for the phone swipe test; its takeaway moves to step 7, the connecting step, below).
3. **PolicyPredict** — Now a declared length that genuinely fits inside the real buffer, but is still larger than this format's own stated maximum payload size. Does the naive parser, which only ever checks the buffer's own bounds, actually catch this one too? Options: yes, any oversized length gets caught the same way; no, genuinely, it fits the buffer so the naive parser lets it straight through (correct); only if the maximum is checked somewhere else first.
4. **PolicyReveal** — Measured: the naive parser genuinely accepts the over-policy payload, since nothing in it ever checks a maximum size at all, while the checked parser, which validates against that real, stated maximum directly, rejects it. Takeaway: a length that merely fits the buffer still isn't safe without a real, separate maximum-size policy checked on purpose.
5. **OverflowPredict** — Two attacker-influenced lengths get added together with plain, unchecked arithmetic, in a real release build, where overflow checks are off by default. Does a real sum that genuinely overflows actually show up as a big, obviously wrong number? Options: yes, overflow always produces something that looks huge and wrong; no, genuinely, it silently wraps around to a small number instead (correct); only in a debug build.
6. **OverflowReveal** — Measured: the naive, unchecked sum of two lengths that genuinely overflow a 32-bit addition wraps silently to a small number, while the identical real addition done with `checked_add` correctly reports that it overflowed, rather than handing back a small number that looks perfectly safe. Takeaway: silent wraparound is the dangerous case, since it looks like a small, safe number instead of an obvious failure.
7. **DocsReveal** — The Rust standard library's own `checked_add` documentation and Cargo's own reference on `overflow-checks` each state this directly, in their own words: `checked_add` reports `None` on overflow instead of wrapping, and a release build's own overflow checks are off by default, so an unchecked `+` genuinely wraps there instead of panicking. Does this topic's own two measured comparisons match exactly what both sources describe? Takeaway (moved here from step 2): a length read from untrusted input is a real security boundary whether or not anyone decided to treat it as one.
8. **Recap** — A length that merely fits the buffer, and a sum that merely looks small, are both real traps a parser can fall into without ever doing anything that looks obviously wrong; checking a real maximum and using real, checked arithmetic are what actually turn an assumed boundary into a real one.
