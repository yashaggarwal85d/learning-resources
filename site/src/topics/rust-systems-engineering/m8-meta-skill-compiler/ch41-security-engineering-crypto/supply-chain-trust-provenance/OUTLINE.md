## Storyboard (8 steps, 3 predict/reveal pairs)

1. **LookupPredict** — A real project pins a dependency at a specific, real version, one a real, published security advisory names as vulnerable. Nobody on this project wrote that advisory, or decided to check for it by hand. Does a real lookup against the real, published database actually catch it anyway? Options: no, only a project that knows to look for one specific crate catches it; yes, genuinely, the real lookup catches any crate the database actually names (correct); only if the version is extremely recent.
2. **LookupReveal** — Measured: a real `cargo audit` run against the real, pinned vulnerable version reports the real advisory by its own real id, with no project-specific configuration telling it what to look for. No separate takeaway here (this is the reel's own "from" step for the phone swipe test; its takeaway moves to step 7, the connecting step, below).
3. **PatchPredict** — The very next real release of the identical crate, one version later, is the one the advisory itself names as fixed. Does the identical real lookup still flag anything for that one? Options: yes, since the crate itself was involved in a real vulnerability once; no, genuinely, the real lookup reports a clean result for the patched version (correct); only after a real delay for the database to catch up.
4. **PatchReveal** — Measured: the identical real lookup against the real, patched version reports a clean result, finding nothing, from the exact same real, live database that flagged the version one release earlier. Takeaway: a real advisory lookup tracks a real, specific version, not a crate's own reputation in general.
5. **ComparePredict** — Side by side, both real lookups ran against the identical real crate, one version apart. Did the real database actually tell the two versions apart correctly, or did it just flag the crate as a whole? Options: it flagged the crate as a whole, catching both; it told them apart correctly, genuinely, catching only the real vulnerable one (correct); it depends on which version was checked first.
6. **CompareReveal** — Measured: the real advisory is reported for exactly the one real, pinned version it actually names, and only that one, confirming the lookup is checking the real, specific version pinned in each real `Cargo.lock`, not merely the crate's own name. Takeaway: whether a real dependency is actually vulnerable is a published fact to look up, not something to guess from how recently it shipped.
7. **DocsReveal** — The RustSec Advisory Database's own front page states this directly, in its own words: it is a real vulnerability database for the Rust ecosystem, and its own `cargo-audit` tool audits a real `Cargo.lock` file for crates with known, real vulnerabilities. Does this topic's own two measured lookups match exactly what both of those sentences describe? Takeaway (moved here from step 2): a real, continuously updated advisory lookup finds what a guess, or a check done only once, genuinely cannot.
8. **Recap** — The identical real crate, one version apart, gets a genuinely different real answer from the identical real lookup; that is what makes supply-chain trust something to actually check, on a real, published record, rather than something to assume because nothing has broken yet.
