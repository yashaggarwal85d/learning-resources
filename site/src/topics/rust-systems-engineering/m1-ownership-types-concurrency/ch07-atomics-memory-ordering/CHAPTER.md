## A.1 The problem it solves

Chapter 6 answered "is this safe to share, and is this safe to touch concurrently" — `Send`/`Sync` for the first, `Arc`/`Mutex` for the second — but never once asked what, exactly, is guaranteed about *when* one thread's write becomes visible to another thread's read, once sharing is already sound. That question splits into two genuinely separate concerns the syllabus itself insists on keeping apart: **atomicity** (a single operation on a location either completes as a whole or hasn't happened at all — no torn, half-written value visible to anyone) and **ordering** (which operations other threads are guaranteed to see as having happened before which others). A `Mutex` buys both at once, at the cost of blocking; an atomic type lets a program ask for exactly the ordering guarantee it needs — `Relaxed`, `Acquire`/`Release`, or `SeqCst` — and nothing more, for operations far too fine-grained to justify a lock. Rust's atomics are not a bespoke invention: they follow the C++20 memory model directly (minus the never-quite-finished `consume` ordering), which means the chapter's vocabulary — happens-before, per-location modification order, data races as undefined behavior — is the same vocabulary used industry-wide, not a Rust-specific dialect.

By the end of the chapter the learner can: state the difference between atomicity and ordering in one sentence each, and explain why a program can have one without the other; name Rust's four (really three it needs day-to-day) memory orderings — `Relaxed`, `Acquire`, `Release`, `SeqCst` — and say which job each one actually does; build the acquire/release publication pattern correctly (release-store a flag or pointer, acquire-load it before touching what it published) and say why `Relaxed` is enough for a statistics counter but wrong for publication; and recognize the one shape of problem (`SeqCst`-only store-load litmus tests like Dekker's algorithm or the store-buffer pattern) where weaker orderings genuinely aren't enough, while knowing that on x86-TSO hardware a missing ordering can silently "work" where the identical program breaks on ARM.

## A.2 The order of ideas, and why

1. **Atomicity versus ordering** (topic 22) — the foundation: separates the two concerns precisely, with a torn-read demonstration (a plain, non-atomic `u64` genuinely torn between threads on a target where that's observable, or the honest fallback of explaining why it's UB regardless of whether it's caught) and an ordering-violation demonstration (two relaxed loads/stores that compile and "work" on this one run, named as a data race regardless), establishes Rust's atomics as following the C++20 model (minus `consume`) with happens-before and per-location modification order as the two load-bearing terms, and states data races as UB precisely (not merely "undefined output" but a real soundness hole the compiler is allowed to assume never happens). Names the Linux kernel's own memory model (LKMM) as a distinct, stricter model that matters only for kernel Rust (forward-referenced to Chapter 39, not built here).
2. **Acquire/Release publication and SeqCst** (topic 23) — needs (1): takes atomicity and ordering as already-separated concepts and builds the one pattern that matters most in practice — release-store a flag or a pointer, then acquire-load it before reading whatever it published — and proves, not just asserts, that `Relaxed` is sufficient for an independent statistics counter (no publication involved) but wrong for publication itself (a real, reproducible failure to read the published data reliably without the acquire/release pair, where the target lets that be observed). Narrows `SeqCst` to its real, narrow job: store-load patterns like Dekker's algorithm or the store-buffer litmus test, where even acquire/release isn't enough because the guarantee needed is a single global total order across *all* threads' operations, not just a pairwise happens-before edge. Introduces `fence`/`compiler_fence` as the tool for when no single atomic operation carries the ordering a situation needs, and closes the milestone by showing how orderings map to real hardware: x86-TSO is strong enough to hide a missing acquire/release on some patterns that ARM's weaker model will expose — the reason "it worked when I tested it" is not evidence of correctness here. Hands off to Chapter 8 (Milestone 2, async runtimes): the Future/Waker/Pin machinery topic 23 hands off to depends on exactly this chapter's ordering vocabulary to explain how a waker's wake-up is actually guaranteed to be seen.

## A.3 The running example: a one-shot "ready" flag publishing a computed value

Both topics share one self-contained running example (no cross-topic imports, per Chapters 1–6's convention): a worker thread computes a value, stores it behind an atomic flag, and a reader thread spins on that flag before reading the value — the canonical minimal shape of the acquire/release publication pattern, small enough to make every ordering's effect on it observable and real enough that the identical shape appears constantly in real lock-free code (one-time initialization, a ready/not-ready handshake, a lock-free single-producer/single-consumer handoff).

- **Topic 22** builds the flag-and-value pair three ways to separate atomicity from ordering concretely: a plain (non-atomic) flag and value, to demonstrate why this needs an atomic type at all (a data race, named as real UB, not merely "risky"); an `AtomicBool`/`AtomicU64` pair using `Relaxed` everywhere, to show that atomicity alone (no more torn reads) does not imply the reader ever reliably sees the value the flag claims is ready; and the identical pair with the correct acquire/release ordering, to show the first version that is actually sound. Every claim about what a weaker ordering does or doesn't guarantee is demonstrated by a real, executed Rust program under `loom` or a stress-looped runtime measurement — never asserted from the spec alone without an attempt to observe it.
- **Topic 23** reuses the identical flag-and-value shape, now making the acquire/release version from topic 22 the explicit, named pattern (not a coincidence this topic reconstructs from scratch), contrasts it against a `Relaxed`-only statistics counter (many threads incrementing an independent counter with no data being published through it, where `Relaxed` is not just adequate but the entire story) to show the pattern-dependent nature of the choice, then builds one genuine `SeqCst`-dependent litmus test (Dekker's algorithm or the store-buffer pattern) where acquire/release demonstrably isn't enough and `SeqCst` is, and closes with `compiler_fence`/`fence` and a concrete, named contrast between what x86-TSO permits by default and what ARM does not.

## A.4 Terms and notation (continuing Chapters 1–6's vocabulary)

Everything in Chapters 1–6 §A.4 still applies. This chapter adds:

- **Atomicity**: a single operation on a location completes as one indivisible step — no other thread ever observes a partially-written value.
- **Ordering**: which of one thread's operations are guaranteed to be visible, and in what order, to another thread's operations.
- **Happens-before**: the relation the C++20 (and Rust) memory model uses to say "this operation is guaranteed visible to that one," built from program order on one thread plus the synchronizes-with edges an acquire/release pair creates.
- **Per-location modification order**: every thread agrees on a single total order of all writes to one specific atomic location, even under `Relaxed` — the one guarantee `Relaxed` never gives up.
- **Data race**: two unsynchronized, conflicting accesses (at least one a write) to the same location from different threads with no ordering between them — undefined behavior in Rust, exactly as in C++20, not merely an incorrect result.
- **`Relaxed`**: the weakest ordering; atomic (no torn values, a per-location total order exists) but carries no happens-before guarantee about anything else.
- **`Acquire`/`Release`**: a load/store pair where a `Release` store and a later `Acquire` load of the same value create a happens-before edge — everything written before the `Release` is guaranteed visible after the matching `Acquire`.
- **`SeqCst`**: the strongest ordering; all `SeqCst` operations across every thread agree on one single global total order, needed only for store-load patterns no pairwise acquire/release edge can express.
- **The publication pattern**: release-store a flag or a pointer, then acquire-load it before reading whatever it published — the chapter's running shape.
- **`fence`/`compiler_fence`**: a standalone ordering constraint not attached to any one atomic operation, for the rare case no single operation carries the ordering a situation needs.
- **LKMM**: the Linux kernel's own, distinct memory model; relevant only to kernel Rust, named here and deferred to Chapter 39.

Narration words (continuing the convention: no digits, no code-style names spoken): "no half-written value, ever" for atomicity; "what's guaranteed to be seen, and in what order" for ordering; "guaranteed to have already happened, from another thread's point of view" for happens-before; "two threads touching the same memory with no agreement about order" for a data race; "the weakest guarantee, just enough to never see a torn value" for relaxed; "a release and a matching acquire, handing off everything written before it" for acquire/release; "every thread agreeing on one single order of events" for sequential consistency; "write the data, then raise the flag; check the flag, then read the data" for the publication pattern.
