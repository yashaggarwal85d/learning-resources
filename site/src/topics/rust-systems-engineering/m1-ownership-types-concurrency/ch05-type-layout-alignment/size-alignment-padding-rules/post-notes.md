## Outcomes

- Compute a struct's size and a field's offset from its fields' sizes, alignments, and order alone, and state the two rules that always hold: size is a whole multiple of alignment, and a field's offset is a multiple of its own alignment.
- Explain why `repr(Rust)` (the default) can reorder fields and is not a layout contract, and recognize `-Z randomize-layout` as deliberate proof of that instability, not a bug.
- Use `offset_of!` and a compile-time assertion to make a layout claim something the build itself checks, and recognize `error[E0080]` as that check failing.

## Internals

`repr(Rust)`'s layout algorithm is, today, roughly "place fields in whatever order minimizes padding, generally larger-alignment fields first" — but the Reference is explicit that this is only what the current compiler happens to do, not a guarantee: "Type layout can be changed with each compilation. Instead of trying to document exactly what is done, we only document what is guaranteed today." The only guarantees `repr(Rust)` actually makes are the two soundness-minimum rules: a field's offset is divisible by that field's own alignment, and the type's alignment is at least the maximum alignment of its fields. Everything else — which field goes where, how much padding appears, even the total size — is free to change between a patch release, a build flag, or (demonstrably) a `-Z layout-seed`.

`-Z randomize-layout`'s own unstable-book page is candid that it's a blunt instrument: "Randomization only approximates the intended freedom of repr(Rust). Sometimes two distinct types may still consistently result in the same layout due to limitations of the current implementation." That's exactly what this topic's own research run into: the four-field packet header used everywhere else in this topic showed no visible movement across two different `-Z layout-seed` values, because a struct with only two one-byte fields and two multi-byte fields has very few valid orderings for alignment to allow at all — the randomizer had almost no room to work with. The reel's randomize-layout step therefore uses a second, eight-field struct instead, purpose-built to have enough degrees of freedom that two different seeds visibly produce two different arrangements (and, in the sandbox this topic was built in, two different total sizes: 20 bytes under one seed, 16 under another, for the identical eight fields). The flag also needs `-Z layout-seed=<u64>` supplied explicitly to guarantee a difference between runs at all — the page says plainly that "randomization is not guaranteed to use a different permutation for each compilation session" on its own.

## Lab

The chapter's own syllabus line asks for one more thing this reel leaves to the Deep dive rather than a step: *repr attributes and niche optimization* is marked `*(skipped)*` in the syllabus, so it gets no reel content, but the one-sentence version is worth having here, since the next topic's byte-level views assume it. A niche is a bit pattern a type never otherwise uses — `&T` is never the null pointer, so `Option<&T>` can represent `None` as that otherwise-impossible all-zero pattern instead of needing an extra byte (or more, with padding) to store the `Some`/`None` tag separately. The practical result: `size_of::<Option<&T>>() == size_of::<&T>()`, and the same holds for `Option<Box<T>>` and `Option<NonZeroU32>`. This is a real, checkable fact (`assert_eq!(size_of::<Option<&u8>>(), size_of::<&u8>())` holds on every target this topic's toolchain was tested on), but it is only ever guaranteed for the specific, documented cases the standard library actually promises — a hand-written type does not get a niche just by looking like it has unused bit patterns, unless the compiler's layout algorithm is actually told to find one (and, per `repr(Rust)`'s own non-guarantee above, whether it finds one is not something to assume either).

The chapter's lab also asks to "define a C-compatible packet header and verify `size_of`/`align_of`/field offsets against a C compiler" — this reel's `repr(C)` header (`examples/repr_c_field_order_matters.rs`) is exactly that packet header, verified here against Rust's own `offset_of!` rather than a separate C toolchain, since `repr(C)`'s contract with the platform's C ABI is precisely what `offsets_checked.rs`'s assertions pin down and the build itself checks on every run.

## In production

The next topic in this chapter exists because of exactly the bug class this topic's padding rules make possible: a program that receives a raw byte buffer from a socket or a file and reinterprets it as a struct — through `transmute` or a raw pointer cast — is, if that struct has any padding at all, reading bytes the sender may never have initialized, and the buffer's own layout may not match the receiving struct's chosen layout unless both sides are pinned to `repr(C)` (or an explicitly matching wire format). Rust's own documentation is blunt that this is undefined behaviour, not merely "probably fine in practice" — the next topic exists to show the derive-checked alternative that makes the compiler refuse to compile the unsound version instead of trusting the programmer to get it right by convention.

## The frontier

`-Z randomize-layout` has sat behind nightly since its tracking issue (rust-lang/rust#106764) opened, years before this topic was written, and its own documentation is candid that it approximates rather than fully exercises `repr(Rust)`'s freedom. That the Rust project has not judged it safe or complete enough for stable, even though its entire purpose is catching code that already shouldn't be relying on any one layout, is itself a sign of how much latent code in the wild silently assumes a stable `repr(Rust)` layout today — code this flag is built to find, not yet broadly turned loose on it. `repr(packed)` and `repr(align(N))`, the chapter's other `*(skipped)*` syllabus items, sit in the same space: real, documented representations with real safety hazards of their own (a `repr(packed)` field's reference can be genuinely unaligned, which is why taking one now requires `&raw const` rather than an ordinary `&`), left out of this chapter's reel because the syllabus marks them refresher-depth only here.

## Where this goes next

Everything this topic measured was about one value's own layout, standing still, inside one process.
