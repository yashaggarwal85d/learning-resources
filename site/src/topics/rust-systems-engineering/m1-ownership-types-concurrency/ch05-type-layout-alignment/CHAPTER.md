## A.1 The problem it solves

Every chapter so far has asked "who owns this value, and who may mutate it" — the compiler's promises about *ownership*. This chapter asks a different, more basic question the earlier chapters quietly assumed an answer to: what does the compiler actually promise about a type's *bytes* — how large it is, where each field starts, what lies in the gaps? The syllabus's own framing is blunt: "size is a multiple of alignment, and padding depends on field order," and `repr(Rust)` — the layout every struct gets unless told otherwise — is explicitly *not* a promise: the compiler is free to reorder fields, and `-Z randomize-layout` exists specifically to break code that assumed otherwise. The chapter's second half asks what happens when a program needs the opposite of that freedom: reading a struct that came from a wire or a file, where the bytes' layout is fixed by the protocol, not the compiler, and the padding the compiler quietly leaves behind is itself undefined — reading it as a value is undefined behaviour. The chapter's own lab line states the shape of both halves at once: build a C-compatible packet header, verify its layout against a C compiler with `size_of`/`align_of`/`offset_of!` and compile-time assertions, then show how `repr(Rust)` breaks that assumption and how a niche changes `Option<T>`'s size.

By the end of the chapter the learner can: compute a struct's size and a field's offset from its type's sizes, alignments, and field order alone, and explain why reordering fields can shrink a struct with no other change; state precisely why `repr(Rust)` layout can never be relied on across a compiler invocation (and demonstrate it moving under `-Z randomize-layout`) while `repr(C)` and `offset_of!`/compile-time assertions give a real, checkable guarantee; and read a wire or on-disk struct's bytes safely with a derive-checked crate (`zerocopy` or `bytemuck`) instead of a hand-rolled `transmute`, naming exactly why reading uninitialized padding bytes as a value is undefined behaviour and how the derive-checked path avoids it.

## A.2 The order of ideas, and why

1. **Size, alignment, and padding rules** (topic 16) — the ground truth every later idea in the chapter stands on: a type's size is always a multiple of its alignment, padding is inserted between fields (and at the end) to keep every field's start aligned, and padding's exact amount and placement depends on field *order*, which `repr(Rust)` lets the compiler choose for itself and is free to change between compilations — demonstrated directly with `-Z randomize-layout` on nightly, not just asserted from the reference. `size_of`, `align_of`, and `offset_of!` (plus a `const` assertion) are the tools that make a layout claim checkable instead of assumed.
2. **Safe byte-level views of structs** (topic 17) — needs (1): once a program actually needs to read bytes whose layout is fixed by something other than the Rust compiler (a wire protocol, an on-disk record), it needs `repr(C)` to pin the layout down, and it needs a safe way to view those bytes as a value — because the padding bytes this chapter's first topic just showed are real and can be uninitialized, and reading uninitialized bytes through an ordinary reference, even as part of a bigger struct, is undefined behaviour. `zerocopy`/`bytemuck`'s derive-checked `FromBytes`/`IntoBytes` traits verify at compile time (size, alignment, no padding in the fields that matter) what a hand-rolled `transmute` only ever asserted by convention.

## A.4 Terms and notation (continuing Chapters 1–4's vocabulary)

Everything in Chapters 1–4 §A.4 still applies. This chapter adds:

- **Size**: the total number of bytes a value occupies, always a whole multiple of the type's alignment.
- **Alignment**: the byte boundary a value's address must fall on; every type has one, and it is always a power of two.
- **Padding**: bytes a type's layout inserts between fields (or after the last one) purely to keep every field's start aligned and the whole type's size a multiple of its alignment; padding bytes carry no meaningful value and may be uninitialized.
- **Field order**: the order fields are written in the struct's source; under `repr(Rust)` the compiler may store them in a different order than written, choosing whichever ordering minimizes padding (or for any other reason it likes).
- **`repr(Rust)`**: the default representation; size, alignment, field order, and padding are chosen by the compiler and are an implementation detail, not a contract — they may differ between compiler versions, build flags, or (demonstrably, via `-Z randomize-layout`) between runs of the very same compiler.
- **`-Z randomize-layout`**: a nightly flag that deliberately randomizes a `repr(Rust)` type's field order on each compilation, built specifically to break code that silently assumed a stable layout.
- **`repr(C)`**: a representation that fixes field order to source order and layout rules to the platform's C ABI, making size, alignment, and offsets a real, checkable, cross-language contract.
- **`size_of::<T>()`** / **`align_of::<T>()`**: `std::mem` functions returning a type's size and alignment, computable at compile time.
- **`offset_of!`**: a macro returning a field's byte offset within its containing type, stabilized for checking a layout claim without hand computation.
- **Compile-time layout assertion**: a `const _: () = assert!(...)` (or equivalent) that fails the build itself the moment an assumed size, alignment, or offset stops holding, rather than failing only at run time or never.
- **Undefined behaviour from padding**: reading a struct's padding bytes as part of a value (e.g. by reinterpreting the whole struct as a byte array through `transmute` or a pointer cast) is undefined behaviour whenever those bytes are not guaranteed initialized, because the compiler never promises anything is written there.
- **`FromBytes`/`IntoBytes`** (`zerocopy`) or the equivalent `Pod`/`NoUninit` traits (`bytemuck`): derive-checked marker traits that only compile for a type the derive can prove has a fixed layout with no uninitialized padding in play, replacing a hand-rolled `transmute` with a guarantee checked once, at compile time, instead of trusted by convention everywhere it's used.

Narration words (continuing the convention: no digits, no code-style names spoken): "how many bytes a value takes up" for size, "the boundary a value's address must land on" for alignment, "the gap the compiler leaves to keep things aligned" for padding, "the order fields are actually laid out in memory" vs "the order they're written in" for field order under `repr(Rust)`, "a layout the compiler is free to change on you" for `repr(Rust)`, "a layout pinned down, field by field" for `repr(C)`, "a check the compiler runs on its own claim" for a compile-time layout assertion, "reading a gap that was never written" for padding UB, "a reader the compiler checks before it's allowed to compile" for a derive-checked byte view.
