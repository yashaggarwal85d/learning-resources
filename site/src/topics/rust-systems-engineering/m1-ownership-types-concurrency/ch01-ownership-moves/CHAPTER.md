## Part A — The chapter

### A.1 The problem it solves

The learner is a senior engineer who already ships systems in C/C++, Go, Java or Python, and has read the Book through ch. 10. They can make the borrow checker go quiet. What they don't yet have is the *model* the checker enforces, so they still fight it, and when they lose they reach for `.clone()` or `Arc<Mutex<T>>` and get code that compiles but allocates, copies and serialises where it shouldn't.

Each home language answers "who frees this buffer, and when?" differently: C by convention and discipline (and the bugs that follow), C++ with RAII plus move constructors that leave a moved-from object behind (for standard-library types, in a "valid but unspecified" state) whose destructor still runs, Go/Java/Python with a garbage collector at run time and `defer`/`try-with-resources`/`with` for everything that isn't memory. Rust answers it **statically**: every value has exactly one owner, the owner's end of scope is where it is destroyed, and the compiler tracks every handover. The chapter line in the syllabus is the thesis: *ownership as a static model of who destroys what, and therefore who may touch what.*

By the end of the chapter the learner can: predict what a move costs in bytes and allocations, read E0382/E0505/E0507/E0509 as statements about ownership rather than noise, place every destructor on a timeline, write a RAII guard that is correct even if it is leaked, move fields out of structs and out of `&mut` without cloning, and choose an ownership *shape* for a whole subsystem before reaching for shared mutability.

### A.2 The order of ideas, and why

1. **Single ownership and move semantics** — who owns, what a handover costs, how the compiler tracks it, and how signatures publish it. Everything else assumes "exactly one owner, moves are cheap and statically checked".
2. **RAII, drop order, and leak safety** — the other half of ownership: the owner's end is destruction. Needs (1): a drop happens where the *last* owner's scope ends, which only makes sense once moves are understood. Ends with the counter-intuitive rule that destruction is *not guaranteed*.
3. **Partial moves and destructuring as transfer** — ownership at field granularity. Needs (1) for moves and (2) for `Drop`, because the central rule ("you cannot move a field out of a type that implements `Drop`", E0509) and its fix (`Option::take`/`mem::take`/`mem::replace`) only make sense once drop glue and drop flags are known.
4. **Ownership topology over shared mutability** — ownership at program scale. Needs (1)–(3): a topology is a choice of who owns whom, how values move between owners, and how a guard returns them; it opens on the limit topic 3's guard leaves (one guard at a time). It ends where Chapter 2 begins: every topology still *lends* things out, which is what the borrow checker's aliasing rule governs.

The order goes from one value, to its end, to its parts, to the whole program. The running example grows along the same path (A.3).

### A.3 The running example: a byte pipeline with a pool and a counting allocator

All four topics use one example, the chapter Lab from the syllabus: a **3-stage byte pipeline** (allocate once → borrow to inspect headers → own the buffer and return it to a pool), instrumented with a **counting `#[global_allocator]`**, plus drop-order tracing through nested structs. Use these names, types and constants **exactly** (on screen, in `examples.py`, in the Deep dive). A topic may add private helpers, but it must not rename, re-type or redefine anything below.

```rust
// ---- the instrument (topic 1 introduces it; topics 2–4 copy it verbatim) ----
use std::alloc::{GlobalAlloc, Layout, System};
use std::sync::atomic::{AtomicUsize, Ordering::Relaxed};

pub struct CountingAlloc;
pub static ALLOCS: AtomicUsize = AtomicUsize::new(0);
pub static DEALLOCS: AtomicUsize = AtomicUsize::new(0);
pub static BYTES: AtomicUsize = AtomicUsize::new(0); // bytes requested by alloc

unsafe impl GlobalAlloc for CountingAlloc {
    unsafe fn alloc(&self, layout: Layout) -> *mut u8 {
        ALLOCS.fetch_add(1, Relaxed);
        BYTES.fetch_add(layout.size(), Relaxed);
        unsafe { System.alloc(layout) }
    }
    unsafe fn dealloc(&self, ptr: *mut u8, layout: Layout) {
        DEALLOCS.fetch_add(1, Relaxed);
        unsafe { System.dealloc(ptr, layout) }
    }
}
#[global_allocator]
static ALLOC: CountingAlloc = CountingAlloc;
pub fn allocs() -> usize { ALLOCS.load(Relaxed) }

// ---- the pipeline's data ----
pub const BUF_CAP: usize = 64 * 1024; // 65,536 bytes ("64 KiB" on screen)
pub const POOL_SLOTS: usize = 8;      // free-list capacity, reserved in Pool::new

#[derive(Clone)]                       // Clone, never Copy: cloning is the visible, costly act
pub struct Buf { pub id: u32, pub bytes: Vec<u8> }   // no Drop impl (so topic 3 can partially move it)

#[derive(Clone, Copy, Debug, PartialEq)]
pub struct Header { pub kind: u8, pub len: u32 }     // bytes[0], then bytes[1..5] little-endian

pub struct Pool { free: Vec<Buf>, next_id: u32 }
impl Pool {
    pub fn new() -> Pool { Pool { free: Vec::with_capacity(POOL_SLOTS), next_id: 0 } }
    pub fn get(&mut self) -> Buf {                   // the only place a buffer is allocated
        match self.free.pop() {                      // a `match`, not `unwrap_or_else(|| ..)`: closures are Book ch. 13, past the baseline
            Some(buf) => buf,
            None => {
                self.next_id += 1;
                Buf { id: self.next_id, bytes: Vec::with_capacity(BUF_CAP) }
            }
        }
    }
    pub fn put(&mut self, mut buf: Buf) { buf.bytes.clear(); self.free.push(buf); } // takes ownership back
}

// ---- the three stages: one of each ownership contract ----
pub fn fill(buf: &mut Buf, src: &[u8]) { buf.bytes.clear(); buf.bytes.extend_from_slice(src); } // &mut T: exclusive loan
pub fn inspect(buf: &Buf) -> Header {                                                            // &T: shared loan, returns a Copy value
    let b = &buf.bytes;
    Header { kind: b[0], len: u32::from_le_bytes([b[1], b[2], b[3], b[4]]) }
}
pub fn consume(buf: Buf) -> Buf { /* write the payload out */ buf }                             // T in, T out: takes, then hands back
```

The planner compiled this sketch on rustc 1.97.0 (the plan review recompiled it as written here), `--edition 2024 -O`, x86-64 Linux: one loop of 1,000 messages `get → fill → inspect → consume → put` made **1** allocation after `Pool::new()`; the same loop with one `buf.clone()` per message made **1,000**; `size_of::<Buf>()` was 32, `size_of::<Vec<u8>>()` 24, `size_of::<Header>()` 8. These are **orientation only**: every number a topic shows must come from its own executed `examples.py` on the current stable toolchain (Rust 1.99 is the syllabus baseline; record the version actually used). Two traps the planner hit, which topics must handle correctly: `Vec::clone` allocates for the *length*, not the capacity (a 261-byte message in a 64 KiB buffer clones 261 bytes; this is the implementation's behaviour, not a documented guarantee, so assert it rather than cite it), and anything that prints or formats inside a measured region can allocate (measure deltas around a region with no I/O inside it).

### A.4 Terms and notation (one vocabulary for the whole chapter)

Use these words with these meanings, in captions, narration and the Deep dive:

- **owner**: the binding, field, collection slot or stack frame that holds a value and is responsible for destroying it. "The owner of the buffer", never "the buffer's reference".
- **handle** and **payload**: for a heap-backed value, the handle is the fixed-size part that lives in the owner (for `Vec<u8>`: pointer, capacity, length; the `Vec` docs guarantee it is that triplet and say the field order is unspecified) and the payload is the heap bytes. "A move copies the handle; the payload stays put." (Chapter-local teaching words: say once that they are not Rust Reference terms; "handle" here is unrelated to topic 4's arena `Handle`, which the chapter always writes in code style.)
- **move**: a transfer of ownership; mechanically a bitwise copy of the value's bytes (which the optimiser may elide), after which the source is **moved-from**: statically dead until reassigned. Never "shallow copy" without the second half.
- **copy** (lower case) is what happens to a `Copy` type: the same bitwise copy, but the source stays usable. **clone** is the explicit `.clone()` call, which may allocate and deep-copy.
- **borrow** / **loan**: `&T` is a **shared borrow**, `&mut T` an **exclusive borrow**. rustc's diagnostics and the Book say "immutable"/"mutable" borrow; say once, where the first such diagnostic appears, that "mutable" there means exclusive. Chapter 1 uses borrows only as *ownership contracts* plus the Book's rule (one `&mut` or any number of `&`, declared knowledge); the model behind the rule belongs to Ch.2.
- **destructor** (as in the Rust Reference): `Drop::drop` if the type implements `Drop`, then the destructors of its fields; the compiler-generated part is called **drop glue**. **drop** (verb and noun): running a value's destructor at the end of its life. **drop scope**, **temporary scope** as in the Rust Reference.
- **leak**: a value whose destructor never runs. **Leak-safe** API: one whose soundness does not depend on a destructor running.
- **guard**: a value whose only job is to do something in `Drop` (`PooledBuf`, `MutexGuard`).
- **topology**: the shape of the owns-graph of a program (tree, arena with handles, owner with messages, shared owners).
- **E-codes** are written `E0382` on screen and linked to the error index in the Deep dive. Diagnostics shown on screen are copied from real compiler output captured by `examples.py` (wording changes between releases).

Code notation: types and functions in code style (`Buf`, `Pool::get`); signatures written in full the first time (`fn consume(buf: Buf) -> Buf`). Sizes: binary units throughout, "64 KiB" for 65,536 bytes, "62.5 MiB" for 1,000 × 64 KiB (never a decimal "MB" beside a "KiB"), "24 bytes" for the `Vec` handle (on 64-bit targets; say so). `size_of` values are shown as measured facts of the target, never as layout rules (those are Ch.5). Edition: every example compiles with `--edition 2024` unless it is deliberately comparing editions.

**Narration** (plan, Narration section; the build forbids digits, symbols and code-style names in narration lines; never edit `voice.json`): say "the use-after-move error" and "the move-while-borrowed error" (show `E0382`/`E0505` only on screen); "vector" or "byte vector" for `Vec<u8>`; "box", "arc", "mutex", "arc of mutex" for `Box`, `Arc`, `Mutex`, `Arc<Mutex<T>>`; "mem take", "mem replace", "option take" for the idioms; "drop" for the trait and the act; "sixty-four K" for 64 KiB, chapter-wide (never "kibibytes"); "a counting allocator"; "the pool"; "the guard". Say type names as plain words, never as code: "the buffer" for `Buf`, "the header" for `Header`, "the pool" for `Pool`, "the pooled buffer guard" for `PooledBuf`, "the spill file" for `SpillFile`, "the arena" and "a handle" for `Arena`/`Handle`, "a node" for `Node`, "the frame" for `Frame`, "the stage" for `Stage`, "a trace probe" for `Trace`, "a message" for `Msg`.

### A.5 One visual language for the chapter's reels

Every reel of the chapter draws ownership with the same marks, built from `site/src/reels/kit.tsx` (`Stack`, `Svg` on the 600-unit canvas, `T`, `Bar`, colour tokens `C`, `Code`) and `anim.ts` (`seg`, `easeOut`, `easeOutBack`, `lerp`, `fmt`). Each topic still finds its *own* picture for its idea (DESIGN.md "Its own idea"); this grammar only makes the marks mean the same thing in every reel.

- **Two regions.** Owners on the left (a column of slots: binding name in `C.crema`, slot outline `C.mocha` on `C.cocoa`), heap on the right (payloads as `Bar`s in `C.latte`; a full 64 KiB buffer is a long bar). In portrait the heap sits *below* the owners instead of to the right. Keep clear of the right 64 px on desktop.
- **The handle** is three small cells `ptr · cap · len` inside the owner slot (a drawing order, not the memory order, which is unspecified). **A move is the handle sliding** from one slot to another while the heap bar stays still; the source slot's outline then fades to `C.taupe` and the slot shows the word `moved` in `C.latte` at full opacity, at least 13 units (never deleted from the drawing, so the learner sees the dead binding; taupe is not used for small text).
- **Edges.** Owner edge: solid `C.caramel`, ending in an arrowhead at the payload it owns, exactly one per payload (single ownership is visible as "one caramel arrow"). Shared borrow `&T`: dashed `C.latte`. Exclusive borrow `&mut T`: dashed `C.cinnamon`. Borrow edges end in an open dot on the value they borrow, never an arrowhead, so "arrow = owns" reads at a glance.
- **Clone** is a second payload bar growing in beside the first, with the allocation counter ticking.
- **Allocation counter**: top-right of the drawing, `allocs N` (and `freed N` when deallocations matter), the changing digit in the serif face (the step's one serif element). Same position in every reel.
- **Drop**: the value's slot and payload collapse (scale and opacity to zero, `easeOut`) and leave a small numbered badge (`1`, `2`, `3` in circles, `C.crema` on `C.mocha`) giving the order destructors ran. A drop timeline, when used, runs left to right along the bottom.
- **Errors**: the offending edge or slot turns `C.cherry` (fill only); the code `E0382` in `C.cherryText` beside it. An error frame never uses `caramel` for anything else, so "red = rejected by the compiler" stays unambiguous.
- **Accents**: at most two per step (DESIGN.md). Default pair: `caramel` (ownership, the thing to look at) plus either `cinnamon` (exclusive borrow) or `cherry` (error). Shared borrows and quiet structure use `latte`/`taupe`, which are not accents.
- **Signatures** appear as `Code` panels of at most 8 lines when a drawing sits under them; on portrait, swap the code for the drawing (`portrait` in the step context) instead of shrinking both.

### Topic 1 — Single ownership and move semantics

- **Id / folder / title:** `rust.single-ownership-move-semantics` · `single-ownership-move-semantics` · "Single ownership and move semantics" (registry `title` may be shortened; `syllabusTitle` exactly as here).
- **Kind:** full.
- **Syllabus line, clause by clause, and where each lands:**
  1. "one live owner is responsible for destruction" → here: the owner model, owners of every kind (binding, field, `Vec` slot, frame), "live" meaning not moved-from. *When* and *in what order* destruction runs → topic 2.
  2. "A move is a shallow bitwise copy that statically invalidates the source binding, with no implicit deep copy" → here, in full: the handle/payload picture, the bitwise copy that the optimiser may elide (std `Copy` docs), static deinitialisation (Reference `[expr.move.deinitialization]`), reinitialising a moved-from `let mut` binding, every move site (assignment, argument, return, struct field init, `push`, by-value `for` via implicit `into_iter`), conditional moves (moved in one branch → unusable after the `if`). Contrast with C++ (`std::move` leaves a valid-but-unspecified object whose destructor still runs; no move constructors in Rust, so a move is always the plain copy) and with GC languages (aliasing instead of transfer). That a value which points into itself would be broken by a move, because moves are plain copies (why safe Rust gives you no way to build one that can still be moved): one forward-pointing line to Ch.2 section 2.2 / Ch.8 (`Pin`), only if verified against the `std::pin` docs. The *drop flags* behind conditional moves → topic 2. Moving *fields* → topic 3.
  3. "`Copy` vs `Clone` marks where the cost is" → here: `Copy` is the implicit bitwise duplicate for types whose fields are all `Copy` and that manage no resource beyond their own bytes; `Clone` is explicit and may allocate (measured with the counting allocator: `buf.clone()` = 1 allocation of `len` bytes); `Copy` requires `Clone` (supertrait); `#[derive(Copy)]` on a type with a non-`Copy` field fails (E0204); `Copy` and `Drop` are mutually exclusive (E0184) is stated in one line (`Drop` glossed on the spot as "a user-written destructor, next topic"), with the reason left to topic 2. `Header` is the chapter's `Copy` type, `Buf` its non-`Copy` one. Precision an expert will check: a move and a copy are the *same* bitwise copy of `size_of::<T>()` bytes (unless the optimiser elides it); `Copy` decides only whether the source stays usable, not the cost. So a `[u8; 4096]` costs a 4 KiB copy per move or copy whether or not it is `Copy`, while a `Buf` costs 32 bytes however big its payload: the cost that `Copy` vs `Clone` marks is the *hidden deep* copy, which Rust never does implicitly. Any byte-cost claim about large values needs a measurement or a source.
  4. "Signatures act as ownership contracts (`T` takes, `&T` borrows, `&mut T` borrows exclusively, returning `T` hands ownership back)" → here: the four contracts shown by the pipeline's own signatures (`Pool::put(buf: Buf)`, `inspect(&Buf)`, `fill(&mut Buf, &[u8])`, `consume(Buf) -> Buf`), method receivers (`self`/`&self`/`&mut self`), the API Guidelines' C-CALLER-CONTROL ("take ownership rather than borrowing and cloning") and C-CONV (`as_`/`to_`/`into_`). The *rules* that make `&mut T` exclusive, reborrowing and two-phase borrows → Ch.2 ("Aliasing XOR mutability"); not taught here.

"Reading E0382 (use after move) and E0505 (move while borrowed)" → here: real diagnostics captured from rustc, label by label ("move occurs because … does not implement the `Copy` trait", "value moved here", "value borrowed here after move", the loop variant "value moved here, in previous iteration of loop", the implicit `into_iter` note), and E0505 from a header *view* (`&buf.bytes[..5]`) held across `consume(buf)`. ### Topic 4 — Ownership topology over shared mutability

- **Id / folder / title:** `rust.ownership-topology-over-shared` · `ownership-topology-over-shared` · "Ownership topology over shared mutability".
- **Kind:** full.
- **Syllabus line, clause by clause, and where each lands:**
  1. "the anti-pattern of reaching for `Arc<Mutex<T>>` when the real problem is the wrong ownership topology" → here, at the *design* level: how the reflex arises (a value that two places want to mutate, E0499/E0502 (read with the Book's rule, declared knowledge; the model behind it is Ch.2) or E0505 or a `'static` error, then `Arc<Mutex<_>>` until it compiles; `Rc<RefCell<_>>` as the single-threaded twin), what it costs in *design* terms (ownership becomes "everyone and no one", invariants spread across every lock holder, lock order becomes global, the shape of the data is hidden). `Arc` (shared ownership by an atomic reference count) and `Mutex` (a lock whose guard gives `&mut` access) are explained in one line each on the spot.   2. "tree-shaped ownership" → here: parents own children, work is lent down (`&`/`&mut`) and results returned up; the pipeline driver owning the `Pool` and all stages, with stages as functions taking and returning `Buf` (topic 1's contracts) as the simplest correct topology; why most "shared" state is really a tree once the owner is named.
  3. "an owner task fed by messages (→ Ch.4, Ch.6)" → here: the pool owned by one thread, stages as threads connected by `std::sync::mpsc` channels, `Buf`s sent as owned values (a send is a move: the sender's binding is moved-from, E0382 if reused) and returned on a back channel; "Do not communicate by sharing memory; instead, share memory by communicating" (the Book ch. 16.2, quoting Go's documentation). `thread::spawn(move || …)` with `move` closures explained here (`move-closures`); the `'static` requirement and `Send` are named and left to Ch.2 section 2.2 and Ch.6.
