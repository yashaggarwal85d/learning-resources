## Learning outcomes ("After this topic you can")

1. **Recognise the `Arc<Mutex<T>>` reflex** in a design or a pull request (the chain of compiler errors that leads to it, `E0499` → `E0373` → `E0382` → `E0596` → `Arc<Mutex<_>>`, and its single-threaded twin `Rc<RefCell<_>>`), **name the topology it hides**, and count what it costs in code: owners of one value (3 for the reviewed `Pool`), lock acquisitions per message (5), invariants spread across every lock holder, and a buffer count nobody bounds.
2. **Restructure shared mutable state** into a **tree** (one owner lends down, results come back up), an **arena with generational handles** (one owner for every node of a graph), or an **owner thread fed by messages** (one owner, everyone else sends it owned values), and **pick between them** by the shape of the data (hierarchy, graph with cycles and removal, concurrent users) and the access pattern; and say when `Arc<Mutex<T>>` (or plain `Arc<T>`) really is the right shape.
3. **Implement a minimal generational arena** (`Arena<T>`, `Handle { index, generation }`, about 30 lines, the idea behind the `slotmap` crate) and explain how the generation turns a stale handle into `None` instead of a silent hit on a reused slot.
4. **Move owned buffers between threads through channels** (`std::sync::mpsc`, `thread::spawn(move || …)`) and **account for every buffer's owner at every moment**: a send is a move (`E0382` if the binding is reused, `E0505` if it is still borrowed), `SendError` hands the value back, the owner checks each buffer that comes home (it must be the oldest one out, because channels are FIFO) and keeps `in the pool + out in the ring == every buffer ever made`, and the number of buffers is bounded by the topology (3), not by luck.

2. **`## Into the internals`**
   - **`### How the reflex happens: four errors, four patches`** — the ladder in full with each real diagnostic (E1): `E0499` (the error index: "A variable was borrowed as mutable more than once"; the Book's rule, declared, read as an ownership statement: two stages both want to be the pool's exclusive borrower), `E0373` and its `move` help (`thread::spawn` requires `F: FnOnce() -> T + Send + 'static`; the docs: "threads can outlive the lifetime they have been created in"), `E0382` in its loop form ("value moved into closure here, in previous iteration of loop") with the note offering `Clone` (if `Pool` derived `Clone` (A.3 forbids changing it), the program would compile and be wrong: three independent free lists, and a buffer put into one never comes out of another; one sentence), `E0596` ("cannot borrow data in an `Arc` as mutable"; the `Arc` docs: "you cannot generally obtain a mutable reference to something inside an `Arc`"), then `Mutex`. The single-threaded twin: `Rc<RefCell<Pool>>`, and why it stops at the thread boundary (`E0277`, "`Rc<RefCell<Pool>>` cannot be sent between threads safely", measured E10; `Send` named, Chapter 6). The Book's ch. 16.3 walks the same road for a counter (`Rc` → `E0277` → `Arc`) and is right for a counter; the point here is that a pool of buffers isn't a counter. The same move one level out: the Rust 2024 edition makes references to `static mut` a deny-by-default error (`static_mut_refs`; measured E12: "creating a shared reference to mutable static"; the Edition Guide: "upholding mutability XOR aliasing for a `static mut` requires reasoning about your code globally") — global mutable state is the far end of the same spectrum, and the Edition Guide's alternatives (atomics, `Mutex`, `OnceLock`, "don't use globals") are the same menu as this topic's.
   - **`### What an Arc of Mutex is, exactly`** — `Arc<T>`: "provides shared ownership of a value of type T, allocated in the heap"; `Arc::clone` "points to the same allocation on the heap as the source Arc, while increasing a reference count" (measured E2b: 0 allocations; `Arc::new(Mutex::new(Pool::new()))` 2 allocations; `size_of` 8 bytes on this target); "Arc<T> makes it thread safe to have multiple ownership of the same data, but it doesn't add thread safety to its data"; the last `Arc` dropped drops the value; `Arc::try_unwrap`/`into_inner`/`get_mut` as the ways back to single ownership (named; Chapter 4). `Mutex<T>`: owns its data, accessible only "through the RAII guards returned from lock and try_lock"; `MutexGuard` "When this structure is dropped (falls out of scope), the lock will be unlocked" (topic 2's guard pattern); `get_mut(&mut self)` needs no locking ("the mutable borrow statically guarantees no new locks can be acquired while this reference exists"; measured E2b: compiles, the counting `lock` helper is never called; `get_mut` still returns a `LockResult`, because poisoning is still reported) and `into_inner(self)` consumes the mutex — the two places where the type itself says that if you own it, you don't need the lock. Locking twice in one thread "will not return" (it "might panic or deadlock"). Poisoning: named in one line ("a mutex becomes poisoned if it recognizes that the thread holding it has panicked"), Chapter 6. Data races vs race conditions: safe Rust rules out data races "mostly through Rust's ownership system alone" (Nomicon), not deadlocks ("it is considered “safe” for Rust to get deadlocked"); the Book: "Mutex<T> comes with the risk of creating deadlocks".
   - **`### Tree-shaped ownership`** — the owns-graph as a tree: one root (a `main`, a request, a pipeline run), parents own children, work is lent down as `&T`/`&mut T`, results return up as owned values or `Copy` values (`Header`); `fn` signatures from topic 1 are the edges (`fill(&mut Buf, &[u8])`, `inspect(&Buf) -> Header`, `consume(Buf) -> Buf`, `Pool::put(&mut self, Buf)`). Why most "shared" state is a tree once the owner is named: per-stage counters owned by each stage and summed by the parent (no `Arc<Mutex<Stats>>`); a pool owned by the driver; read-only config is the real exception (`Arc<T>` without a lock). Trees across threads: a parent can lend each child thread a disjoint `&mut` if the threads are joined before the parent continues — that is `std::thread::scope` (stable 1.63; "scoped threads can borrow non-'static data, as the scope guarantees all threads will be joined at the end of the scope"), taught in Chapter 2 section 2.2; one sentence here. Back-pointers to a parent: `Weak` (the std docs: "a tree could have strong Rc pointers from parent nodes to children, and Weak pointers from children back to their parents"), Chapter 4.
   - **`### Graphs: why single ownership can't hold a cycle`** — a graph with a cycle has no root, so "each node owns its successors" makes a ring of owners that keeps itself alive: the Book's ch. 15.6 ("the reference count of each item in the cycle will never reach 0, and the values will never be dropped"; "you can't rely on Rust to catch them"; leaks are memory-safe), measured E5 (4 live allocations after the ring's last outside handle is dropped, 0 for the arena). The Book's own remedy, "reorganizing your data structures so that some references express ownership and some references don't", has two forms: `Weak` back-edges (Chapter 4) and handles into an arena that owns everything (here). Indices into `Vec`s as the everyday form, and why they need generations once anything is removed.
   - **`### A generational arena in thirty lines`** — the full `Arena<T>` from `examples/arena.rs` (insert reusing the free list, `remove` with `take()` and `wrapping_add`, `get`/`get_mut` checking the generation; `Option::as_ref`/`as_mut` glossed in one line: they turn `&Option<T>` into `Option<&T>`), the invariant (a handle `(i, g)` is live iff `slots[i].generation == g` and `slots[i].value` is `Some`), the `Node { name, outputs: Vec<Handle> }` stage graph, stale handles after hot-swapping a stage (E4), and plain indices returning the wrong node (E4). Costs: one bounds check and one compare per access; slots are never shrunk (the `slotmap` docs say the same of `SlotMap`: "It can never shrink the size of its underlying storage, because it must remember for each storage slot what the latest stored version was"); generations wrap (ours: 2^32 removals of one slot; slotmap: 2^31, "in all circumstances is the behavior safe"); a handle from another arena is not caught (slotmap: "it's an error to use the key of one slot map on another slot map. The result is safe, but unspecified"; its `new_key_type!` makes a distinct key type per map). The production crate (`slotmap` 1.1.1): `SlotMap` and `DenseSlotMap` and when to choose each (`HopSlotMap`, which the crate page's prose still describes, is "Deprecated since 1.1.0: Use SlotMap or DenseSlotMap instead, the HopSlotMap is no longer maintained and will be removed in 2.0.": name it only as deprecated); `SecondaryMap` for side data keyed by the same keys ("simply a Vec of slots like slot map is"); per-slot memory "4 + max(sizeof(T), 4) rounded up to the alignment of T". The general ABA problem in lock-free code: Chapter 7.
   - **`### Owner thread fed by messages`** — `std::sync::mpsc` semantics as the docs state them: FIFO ("in the same order as it was sent"); `channel()` never blocks the sender ("infinite buffer") while `sync_channel(n)` blocks when full and `sync_channel(0)` is a rendezvous; `Sender::send(&self, t: T)` takes the value by move and "returning it back if it could not be sent" (`SendError<T>(pub T)`, measured E8: `send failed; got buffer 1 back`); `recv` blocks while a sender exists and, after disconnect, "messages sent before the disconnect will still be properly received"; the receiver "can only be owned by one thread"; `Sender` is `Send` when `T: Send`. `move` closures (the Reference: "A closure can be forced to capture its environment by copying or moving values by prefixing it with the move keyword. This is often used to ensure that the closure's lifetime is 'static"; the Book ch. 16.1: "The move keyword overrides Rust's conservative default of borrowing; it doesn't let us violate the ownership rules"). The ring in full (`examples/ring.rs`): the `Owner` struct (the owner's state is a plain struct with plain `&mut self` methods: no lock because no one else can reach it), the stage functions, `Msg::{Data, Stop}`, the accounting (the owner keeps a FIFO queue of the ids it sent out and asserts that each buffer coming home is the oldest one, then that pool plus queue equals every buffer made; the plan's first `home + (sent − back) == made` was an identity that could not fail, see FACT-CHECK.md), `join()` handing the `Owner` (and its pool) back to `main` ("A thread can also return a value through its JoinHandle"). Shutting down a cycle: in a ring each stage waits for its upstream to hang up, and Ryhl warns that in a cycle "the last sender is never dropped, preventing shutdown": hence the explicit `Stop` behind the last buffer (alternatively the owner can drop its `Sender` first, since it is the one place that knows the work is done). Bounded channels: our ring's channels are unbounded but can never hold more than the 3 buffers plus the one `Stop` (4 messages; the fact-check observed 4 queued for `fill` by pausing it before its 998th receive), because only 3 buffers exist; and the ring is a cycle of channels, which Ryhl warns must not be built from bounded ones: "To avoid such a deadlock, you must make sure that there are no cycles of channels with bounded capacity" (unbounded sends "always return immediately", so they can't deadlock; here the 3 buffers are the bound instead); in an open pipeline use `sync_channel` ("use a bounded channel so that the number of messages waiting in the channel don't grow without bound"); policy and sizing are Chapter 10. Async owner tasks (`tokio::spawn`, `tokio::sync::mpsc`/`oneshot`): M2.
   - **`### A guard that sends its buffer home`** — topic 3's `PooledBuf<'p>` holds `&'p mut Pool`, so one guard at a time. Replace the borrow with a way home: `HomeBuf { buf: Option<Buf>, home: Sender<Msg> }`, whose `Drop` does `if let Some(buf) = self.buf.take() { let _ = self.home.send(Msg::Data(buf)); }` (topic 3's idiom).
