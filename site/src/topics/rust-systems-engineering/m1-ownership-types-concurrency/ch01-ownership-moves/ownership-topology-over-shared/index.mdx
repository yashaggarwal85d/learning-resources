<section data-section="outcomes">

## After this topic you can

- **Recognise the `Arc<Mutex<T>>` reflex** in a design or a pull request: the chain of compiler errors that leads to it (`E0499`, `E0373`, `E0382`, `E0596`, then `Arc<Mutex<_>>`, with `Rc<RefCell<_>>` as its single-threaded twin), **name the topology it hides**, and count what it costs in code: owners of one value (3 for the reviewed `Pool`), lock acquisitions per message (5), invariants spread across every lock holder, and a buffer count nobody bounds.
- **Restructure shared mutable state** into a **tree** (one owner lends down, results come back up), an **arena with generational handles** (one owner for every node of a graph), or an **owner thread fed by messages** (one owner, everyone else sends it owned values); **pick between them** by the shape of the data and the access pattern; and say when `Arc<Mutex<T>>`, or plain `Arc<T>`, really is the right shape.
- **Implement a minimal generational arena** (`Arena<T>`, `Handle { index, generation }`, about thirty lines, the idea behind the `slotmap` crate) and explain how the generation turns a stale handle into `None` instead of a silent hit on a reused slot.
- **Move owned buffers between threads through channels** (`std::sync::mpsc`, `thread::spawn(move || …)`) and **account for every buffer's owner at every moment**: a send is a move (`E0382` if the binding is reused, `E0505` if it is still borrowed), `SendError` hands the value back, the owner checks that each buffer that comes home is the oldest one out (channels are first-in, first-out) and that the pool plus the buffers out in the ring equals every buffer ever made, and the number of buffers is bounded by the topology (3), not by luck.

## Into the internals

Everything measured here was run with rustc 1.97.0 (2d8144b78 2026-07-07), edition 2024, on x86_64 Linux; the std documentation quoted is version 1.99.0 (the current stable at the time of writing; its release notes list no change to the diagnostics, `mpsc`, `Mutex`, `Arc` or closure capture shown here). The programs are in `examples/*.rs` and are compiled, run and asserted by `examples.py`. No timing is measured or claimed anywhere in this topic: every number is a count (owners, locks, allocations, buffers). Sizes are facts of this target, not layout rules (those are Chapter 5).

The running example is the chapter's byte pipeline: `Pool::get(&mut self) -> Buf` hands out a buffer, `Pool::put(&mut self, buf: Buf)` takes it back, `fill(&mut Buf, &[u8])` writes into it, `inspect(&Buf) -> Header` reads a small `Copy` summary, and `consume(Buf) -> Buf` takes it and hands it back. Three stages need buffers at once, and the guard from the previous topic, `PooledBuf<'p> { buf: Option<Buf>, pool: &'p mut Pool }`, allows one at a time.

### How the reflex happens: four errors, four patches

Start from the guard and give each stage a thread. Every error below is real compiler output (measured in `examples.py`), and every patch is local.

1. **`E0499`.** Two `PooledBuf::new(&mut pool)` alive at once: "cannot borrow `pool` as mutable more than once at a time". The error index states the rule: "A variable was borrowed as mutable more than once." Read as an ownership statement, two stages both want to be the pool's exclusive borrower. The patch that suggests itself: give each stage its own thread.
2. **`E0373`.** `thread::spawn` requires `F: FnOnce() -> T + Send + 'static`, and the docs explain why: "threads can outlive the lifetime they have been created in". A closure that calls `pool.get()` needs only `&mut pool`, so it captures `pool` by borrow, and rustc refuses: "closure may outlive the current function, but it borrows `pool`". Its help says to use the `move` keyword. The patch: add `move`.
3. **`E0382`.** Inside a loop that spawns one thread per stage, `move` moves `pool` into the first closure: "value moved into closure here, in previous iteration of loop". The note even offers a way out: "if `Pool` implemented `Clone`, you could clone the value". That would compile, and be wrong: three independent free lists, and a buffer put into one never comes out of another. The patch people reach for instead: `Arc`.
4. **`E0596`.** `Arc<T>` "provides shared ownership of a value of type T, allocated in the heap", but "you cannot generally obtain a mutable reference to something inside an Arc": "cannot borrow data in an `Arc` as mutable". The patch: put a `Mutex` inside.

```rust
let pool = Arc::new(Mutex::new(Pool::new()));
let buf = pool.lock().unwrap().get();
pool.lock().unwrap().put(buf);
```

It compiles and runs. Nobody asked who should own the pool. The single-threaded twin ends the same way, at `Rc<RefCell<Pool>>`, and stops at the thread boundary: `E0277`, "`Rc<RefCell<Pool>>` cannot be sent between threads safely" (`Send` is Chapter 6). The Book's chapter 16.3 walks the same road for a counter (`Rc`, then `E0277`, then `Arc`) and is right for a counter; the point here is that a pool of buffers is not a counter.

The same move one level out is global mutable state. In the 2024 edition, references to a `static mut` are a deny-by-default error (`static_mut_refs`; measured in `examples.py`: "creating a shared reference to mutable static"). The Edition Guide says why: "upholding mutability XOR aliasing for a `static mut` requires reasoning about your code globally", and its alternatives (atomics, `Mutex`, `OnceLock`, or don't use globals) are the same menu as this topic's.

### What an Arc of Mutex is, exactly

`Arc<T>` "provides shared ownership of a value of type T, allocated in the heap". `Arc::clone` "points to the same allocation on the heap as the source Arc, while increasing a reference count": measured, a clone makes 0 allocations, and `Arc::new(Mutex::new(Pool::new()))` makes 2 (the pool's free-list reservation and the `Arc`'s heap block); the pointer is 8 bytes on this target. "`Arc<T>` makes it thread safe to have multiple ownership of the same data, but it doesn't add thread safety to its data", so you "may need to pair `Arc<T>` with some sort of std::sync type, usually `Mutex<T>`". The last `Arc` dropped drops the value. The ways back to a single owner are `Arc::try_unwrap`, `Arc::into_inner` and `Arc::get_mut` (named here; Chapter 4).

`Mutex<T>` owns the data it protects, reachable only "through the RAII guards returned from lock and try_lock". The guard unlocks when dropped: that is the previous topic's guard pattern. Two methods say the quiet part out loud. `get_mut(&mut self)` takes no lock, because "the mutable borrow statically guarantees no new locks can be acquired while this reference exists" (measured: the counting `lock` helper is never called; it still returns a `LockResult`, because poisoning is still reported). `into_inner(self)` consumes the mutex. Both are the type itself saying: if you own it, you do not need the lock. Locking again in a thread that already holds the lock "will not return" (it "might panic or deadlock"), as Lab 5 shows. A mutex becomes poisoned when the thread holding it panics (named only; Chapter 6).

What `Mutex` does not do: Rust prevents data races, "mostly through Rust's ownership system alone" (the Rustonomicon), but "it is considered safe for Rust to get deadlocked", and the Book warns that "`Mutex<T>` comes with the risk of creating deadlocks". Shared ownership has a design cost too: "multiple ownership can add complexity because these different owners need managing". In the reviewed pipeline the pool has three owners and the counters four (`Arc::strong_count`, read while every thread is parked at a `Barrier`); every message takes 5 locks; an invariant like "every buffer is in the pool or in exactly one stage" lives in no single place, because each lock holder must keep it; and nothing bounds the number of buffers.

### Tree-shaped ownership

Draw the program as an owns-graph. If it is a tree, there is one root (a `main`, a request, a pipeline run), parents own children, work is lent down as `&T` or `&mut T`, and results return up as owned values or `Copy` values. The function signatures from the first topic are the edges: `fill(&mut Buf, &[u8])`, `inspect(&Buf) -> Header`, `consume(Buf) -> Buf`, `Pool::put(&mut self, Buf)`. The API Guidelines state the rule for each edge: take ownership "if a function requires ownership of an argument", borrow "if a function does not require ownership".

```rust
struct Pipeline { pool: Pool, counts: Counts }

impl Pipeline {
    fn run_one(&mut self, src: &[u8]) -> Header {
        let mut buf = self.pool.get();        // the driver takes a buffer from the pool it owns
        fill(&mut buf, src);                  // lends it exclusively
        self.counts.filled += 1;
        let h = inspect(&buf);                // lends it shared, gets a Copy result back
        self.counts.inspected += 1;
        let buf = consume(buf);               // hands it over, gets it back
        self.counts.consumed += 1;
        self.pool.put(buf);                   // and returns it
        h
    }
}
```

The driver owns the pool and each stage's counters; the three stages run one after another. Measured: 1,000 messages, 1 allocation, 1 buffer created, 0 locks, and the file contains no `Mutex`, `Arc` or `.lock(`. Most "shared" state is a tree once the owner is named: per-stage counters owned by each stage and summed by the parent need no `Arc<Mutex<Stats>>`. The real exception is read-only data: a config read by 8 threads for the whole run is an `Arc<Config>` with no lock (measured: 9 owners while running, 1 after the joins). Trees across threads are possible when the parent lends each child thread a disjoint `&mut` and joins them before it continues: that is `std::thread::scope` (stable since 1.63), whose "scoped threads can borrow non-'static data, as the scope guarantees all threads will be joined at the end of the scope". It belongs to Chapter 2. Back-pointers to a parent are `Weak` ("a tree could have strong Rc pointers from parent nodes to children, and Weak pointers from children back to their parents"), which is Chapter 4.

### Graphs: why single ownership can't hold a cycle

A graph with a cycle has no root. The pipeline is one: the pool feeds `fill`, and `consume` feeds the pool. Make each node own its successor and you get a ring of owners that keeps itself alive. The Book's chapter 15.6 says exactly this: "the reference count of each item in the cycle will never reach 0, and the values will never be dropped", and "you can't rely on Rust to catch them", because "memory leaks are memory safe in Rust". Measured with the counting allocator: building the ring of four `Rc<RefCell<RcNode>>` and dropping the program's own handles leaves 4 allocations live; the same ring in the arena below leaves 0.

The Book's own remedy is "reorganizing your data structures so that some references express ownership and some references don't". That has two forms. `Weak` back-edges (Chapter 4) keep the shape and make some edges non-owning. Handles into an arena, below, make every edge non-owning and give the nodes one owner. The everyday version of the second form is indices into a `Vec`, and it needs one more idea as soon as anything is removed.

### A generational arena in thirty lines

```rust
#[derive(Clone, Copy, Debug, PartialEq)]
pub struct Header { pub kind: u8, pub len: u32 }     // bytes[0], then bytes[1..5] little-endian

pub struct Pool { free: Vec<Buf>, next_id: u32 }
impl Pool {
    pub fn new() -> Pool { Pool { free: Vec::with_capacity(POOL_SLOTS), next_id: 0 } }
    pub fn get(&mut self) -> Buf {                   // the only place a buffer is allocated
        match self.free.pop() {                      // a `match`, not `unwrap_or_else(|| ..)`: closures are Book ch. 13, past the baseline
            Some(buf) => buf,
            None => {
                self.next_id += 1;
                Buf { id: self.next_id, bytes: Vec::with_capacity(BUF_CAP) }
            }
        }
    }
    pub fn put(&mut self, mut buf: Buf) { buf.bytes.clear(); self.free.push(buf); } // takes ownership back
}

// ---- the three stages: one of each ownership contract ----
pub fn fill(buf: &mut Buf, src: &[u8]) { buf.bytes.clear(); buf.bytes.extend_from_slice(src); } // &mut T: exclusive loan
pub fn inspect(buf: &Buf) -> Header {                                                            // &T: shared loan, returns a Copy value
    let b = &buf.bytes;
    Header { kind: b[0], len: u32::from_le_bytes([b[1], b[2], b[3], b[4]]) }
}
pub fn consume(buf: Buf) -> Buf { /* write the payload out */ buf }                             // T in, T out: takes, then hands back

// A generational arena, by hand (the idea behind the `slotmap` crate): one owner for
// every node of a graph; edges are Copy handles (index + generation), never references.
#[derive(Clone, Copy, Debug, PartialEq)]
pub struct Handle {
    index: u32,
    generation: u32,
}

struct Slot<T> { generation: u32, value: Option<T> }

pub struct Arena<T> { slots: Vec<Slot<T>>, free: Vec<u32> }

impl<T> Arena<T> {
    pub fn new() -> Arena<T> { Arena { slots: Vec::new(), free: Vec::new() } }

    pub fn insert(&mut self, value: T) -> Handle {
        match self.free.pop() {
            Some(index) => {                                   // reuse a freed slot
                let slot = &mut self.slots[index as usize];
                slot.value = Some(value);
                Handle { index, generation: slot.generation }
            }
            None => {
                self.slots.push(Slot { generation: 0, value: Some(value) });
                Handle { index: self.slots.len() as u32 - 1, generation: 0 }
            }
        }
    }

    pub fn remove(&mut self, h: Handle) -> Option<T> {
        let slot = self.slots.get_mut(h.index as usize)?;
        if slot.generation != h.generation {
            return None;                                       // stale: already removed
        }
        let value = slot.value.take()?;                        // move out of &mut, leave None
        slot.generation =
            slot.generation.wrapping_add(1);                   // every old handle is now stale
        self.free.push(h.index);
        Some(value)
    }

    pub fn get(&self, h: Handle) -> Option<&T> {
        let slot = self.slots.get(h.index as usize)?;
        if slot.generation != h.generation { return None; }
        slot.value.as_ref()
    }

    pub fn get_mut(&mut self, h: Handle) -> Option<&mut T> {
        let slot = self.slots.get_mut(h.index as usize)?;
        if slot.generation != h.generation { return None; }
        slot.value.as_mut()
    }
}

pub struct Node {
    name: &'static str,
    outputs: Vec<Handle>,
}
```

The invariant: a handle `(i, g)` is live if and only if `slots[i].generation == g` and `slots[i].value` is `Some`. `Option::as_ref` and `as_mut` turn `&Option<T>` into `Option<&T>`. `remove` uses `Option::take` (the previous topic's idiom): it moves the value out of the slot and leaves `None`. Measured in `examples.py`: the stage graph `pool → fill → inspect → consume → pool` is walked through handles; after `inspect` is removed and `audit` inserted, `audit` gets handle `Handle { index: 2, generation: 1 }`; the stale `Handle { index: 2, generation: 0 }` that `fill` still holds gives `None` from both `get` and `remove`; a plain `Vec` index in the same situation returns `audit`, the wrong node (what the `slotmap` docs call the ABA problem); `Handle` is 8 bytes and `Copy`; and `u32::MAX.wrapping_add(1)` is 0.

The costs: one bounds check and one compare per access; slots are never shrunk (the `slotmap` docs say the same of `SlotMap`: "It can never shrink the size of its underlying storage, because it must remember for each storage slot what the latest stored version was"); generations wrap (ours after 2^32 removals of one slot, `slotmap`'s after 2^31, and "in all circumstances is the behavior safe": a wrapped handle can again hit a reused slot, it just cannot corrupt memory); and a handle from another arena is not caught ("it's an error to use the key of one slot map on another slot map. The result is safe, but unspecified"; its `new_key_type!` makes a distinct key type per map).

The production crate is `slotmap` 1.1.1: `SlotMap` and `DenseSlotMap` (`HopSlotMap` is "Deprecated since 1.1.0: Use SlotMap or DenseSlotMap instead", so name it only as deprecated), and `SecondaryMap` for side data keyed by the same keys ("simply a Vec of slots like slot map is"); per-slot memory is "4 + max(sizeof(T), 4) rounded up to the alignment of T". This is not the same thing as an *allocation* arena (a bump allocator such as `bumpalo` that frees everything at once): that manages memory, this manages identity (Chapter 30, "Custom allocators and arenas"). The general ABA problem in lock-free code is Chapter 7.

### Owner thread fed by messages

When stages must run at the same time, a tree is not enough, because a borrow cannot be lent to a thread that may outlive it. Move the owner into a thread and send it owned values. The `std::sync::mpsc` semantics the topology relies on, as the docs state them: a channel is first-in, first-out ("in the same order as it was sent"); `channel()` never blocks the sender (an "infinite buffer") while `sync_channel(n)` blocks when full and `sync_channel(0)` is a rendezvous; `Sender::send(&self, t: T)` takes the value by move and returns it "back if it could not be sent" inside `SendError<T>` (measured: `send failed; got buffer 1 back`); `recv` blocks while a sender exists and, after disconnect, "messages sent before the disconnect will still be properly received"; the receiver can only be owned by one thread.

`move` closures (new here): the Reference says "a closure can be forced to capture its environment by copying or moving values by prefixing it with the move keyword", and the Book that `move` "overrides Rust's conservative default of borrowing; it doesn't let us violate the ownership rules". Without `move` the closure captures each variable as lightly as its body allows. A closure whose body only calls `pool.get()` borrows `pool`, and `thread::spawn` refuses it:

```rust
let h = thread::spawn(|| {
    let buf = pool.get();
    pool.put(buf);
});
```

With `move` it compiles, the thread owns the pool until it ends, and `join()` hands it back ("a thread can also return a value through its JoinHandle"); using `pool` after the spawn is `E0382`. The ring's stage closures pass their channels on by value, so they capture them by value even without `move` (measured: the ring compiles and prints the same output with `move` removed from every spawn); `move` just says so.

The ring itself (`examples/ring.rs`): one owner thread, three stage threads, four channels. The owner's state is a plain struct with plain `&mut self` methods; there is no lock because no one else can reach it.

```rust
pub enum Msg { Data(Buf), Stop }

fn fill_stage(rx: Receiver<Msg>, tx: Sender<Msg>, src: Vec<Vec<u8>>) -> Vec<u32> {
    let mut seen = Vec::new();
    for msg in rx {
        match msg {
            Msg::Data(mut buf) => {
                let s = &src[seen.len()];
                fill(&mut buf, s);
                seen.push(buf.id);
                tx.send(Msg::Data(buf)).unwrap();
            }
            Msg::Stop => { tx.send(Msg::Stop).unwrap(); break; }
        }
    }
    seen
}
```

```rust
struct Owner { pool: Pool, to_fill: Sender<Msg>, sent: u32, back: u32, out: VecDeque<u32>, checks: u32, ids: Vec<u32> }

impl Owner {
    fn dispatch(&mut self, buf: Buf) {
        self.ids.push(buf.id);
        self.out.push_back(buf.id);
        self.to_fill.send(Msg::Data(buf)).unwrap();
        self.sent += 1;
        if self.sent == MESSAGES { self.to_fill.send(Msg::Stop).unwrap(); }
    }
    fn home(&mut self, buf: Buf) {
        // the ring is FIFO: the oldest buffer out must be the one coming home
        let oldest = self.out.pop_front();
        assert_eq!(oldest, Some(buf.id));
        self.back += 1;
        if self.sent < MESSAGES { self.dispatch(buf); } else { self.pool.put(buf); }
        let made = self.pool.next_id as usize;
        let home = self.pool.free.len();
        assert_eq!(home + self.out.len(), made);
        self.checks += 1;
    }
}
```

Every buffer has exactly one owner at every instant: a stage, the owner, or the channel it is in. The owner keeps a first-in, first-out queue of the ids it has sent out and asserts that each buffer coming home is the oldest one, then that the pool plus the queue equals every buffer made. (A first version of this check, `home + (sent - back) == made`, was an identity of the owner's own counters that could never fail; the fix is that the check compares what actually arrives with what must arrive. A stage that clones one buffer, or loses one, now fails at the first wrong return: measured, both variants exit non-zero at the assertion.) `join()` hands the `Owner`, and its pool, back to `main`. Measured, identical in three runs: 1,000 messages, 3 buffers created and 3 home at the end, the ids going round `1, 2, 3, 1, 2, 3`, the buffers making 334, 333 and 333 trips, and 1,000 passed checks. The channels' own bookkeeping allocates, so buffers are counted with `Pool::next_id`, not with `ALLOCS`.

"0 locks" here means no `Mutex` acquisition in our code. A channel send and receive is itself a synchronisation point (std's `mpsc` uses atomics and blocking internally): the redesign removes shared ownership and its locks, not synchronisation. And the owner thread serialises access just as a lock does; its gains are one owner, one place for invariants, a closed message API and bounded resources, not speed.

The general recipe (Alice Ryhl, "Actors with Tokio", a secondary source): an owner task that exclusively owns a resource, a cloneable handle holding a `Sender`, a message enum as the API ("the ActorMessage enum defines the kind of messages we can send to the actor"), replies over a one-shot channel (with std, a fresh `mpsc::channel()` used once), `let _ =` on replies because "a send operation on a channel fails if the receiver has been dropped", and an owner that ends "when all senders to the receiver have been dropped". Async owner tasks (`tokio::spawn`, `tokio::sync::mpsc`, `oneshot`) are Milestone 2.

Shutting down a cycle is the subtle part. In a ring each stage waits for its upstream to hang up, and Ryhl warns that in a cycle "the last sender is never dropped, preventing shutdown": hence the explicit `Stop` behind the last buffer (the owner could also drop its `Sender` first, since it is the one place that knows the work is done). Bounded channels: the ring's channels are unbounded but can never hold more than the 3 buffers plus the one `Stop`, because only 3 buffers exist. The ring is a cycle of channels, and Ryhl warns that "you must make sure that there are no cycles of channels with bounded capacity" (unbounded sends "always return immediately", so they cannot deadlock; here the 3 buffers are the bound instead). In an open pipeline use `sync_channel`, "so that the number of messages waiting in the channel don't grow without bound"; policy and sizing are Chapter 10.

### A guard that sends its buffer home

The previous topic's `PooledBuf<'p>` holds `&'p mut Pool`, so one guard exists at a time. Replace the borrow with a way home.

```rust
pub struct HomeBuf { buf: Option<Buf>, home: Sender<Msg> }
impl HomeBuf {
    pub fn get_mut(&mut self) -> &mut Buf { self.buf.as_mut().unwrap() }
}
impl Drop for HomeBuf {
    fn drop(&mut self) {
        if let Some(buf) = self.buf.take() {
            let _ = self.home.send(Msg::Data(buf));   // owner gone? then the buffer is just freed
        }
    }
}
```

`Sender`s clone, so any number of guards live at once (measured: 3 alive at once; one stage panics, its guard still sends the buffer home during unwinding; all 3 home, 3 created). If the owner is gone, `send` fails and the buffer is simply dropped; if the owner goes after a successful send, the buffer is dropped with the channel (the `Sender` docs: "a return value of Ok does not mean that the data will be received"). That is leak-safe in the previous topic's sense: soundness never depends on the send.

### Choosing a topology

| | Locks per message | Buffers | Owners of the pool | When | Where it breaks |
|---|---|---|---|---|---|
| `Arc<Mutex<T>>` | 5 | not bounded by the design (1,000 when stage 3 stalls) | 3 | small, simple data touched briefly, truly shared | critical sections grow, two locks meet (order), a guard is held across I/O (Chapter 6) |
| Tree | 0 | 1 | 1 | data has a natural parent; stages run in turn | two parents need one child (a graph); children must run concurrently and the borrow cannot be scoped |
| Arena | n.a. | n.a. | 1 (of every node) | graphs, cycles, removal | handles leak across arenas, generations wrap (both safe, both silent) |
| Owner thread | 0 | 3 | 1 | many concurrent users of one piece of state | it becomes the bottleneck (every request serialises through one thread: the same serialisation as a lock, made explicit; Chapter 4 measures the trade) or request and reply round trips dominate |

The Tokio tutorial states the same menu independently: "Generally you want to use the first approach for simple data, and the second approach for things that require asynchronous work such as I/O primitives", and for contention: "Let a dedicated task manage state and use message passing.", "Shard the mutex.", "Restructure the code to avoid the mutex." It also says that "using a blocking mutex to guard short critical sections is an acceptable strategy when contention is minimal", so the anti-pattern is the reflex, not the type.

```text
buffer_bytes=196608 size_of_buf=32 size_of_msg=32
```

`buffer_bytes` is 3 times 64 KiB, 192 KiB. `examples/homebuf.rs` prints `alive_at_once=3 created=3` and, with one stage panicking, `panics=1 home=3 created=3`. `examples/ring_clone.rs` and `examples/ring_drop.rs` (a stage that clones one buffer, or loses one) exit non-zero at the owner's first-in, first-out check. `examples/ring_one.rs` is the ring with one buffer in flight: `buffers_created=1 home_at_end=1`, `first_ids=[1, 1, 1] trips=[1000]`.

### Lab 5 · Break it

- **Stall stage 3.** In the reviewed design (`examples/stall.rs`), `fill` calls `pool.get()` itself and its channel never pushes back, so while `consume` waits it makes a buffer for every message: `created=1000`, 65,536,000 bytes requested (62.5 MiB). The same stall in the ring (`examples/ring_stall.rs`) leaves `made_while_stalled=3` and `buffers_created=3`. Both stalls use channel signals, not sleeps.
- **Lock the same mutex twice in one statement.** `println!("{} {}", pool.lock().unwrap().next_id, pool.lock().unwrap().free.len());` never returns (`examples/selflock.rs` runs it as a child process killed after 5 seconds; the `try_lock` variant reports `second_lock_would_block=true`). The first guard is a temporary that lives to the end of the statement (the previous topic), and a `Mutex` locked again by its holder "will not return". The compiler does not catch it.
- **The compile-fail set,** each first line asserted: `E0499`, `E0373`, `E0382` (closure in a loop), `E0596`, `E0382` (use after send: "borrow of moved value: `buf`"), `E0505` (send while a view borrows), `E0277` (`Rc<RefCell<Pool>>` across threads), and the 2024 `static_mut_refs` error.
- **Clone a message buffer.** `Vec::clone` allocates for the length, not the capacity: cloning a `Buf` filled with a 261-byte message makes 1 allocation of 261 bytes, and cloning the empty buffer from `pool.get()` makes 0 (`examples/clonecost.rs`). That is an implementation behaviour, so it is asserted, not cited.

<section data-section="production">

## In production

- **The reflex's signature in a code review:** `Arc<Mutex<_>>` on state that only one component writes; `.lock()` calls in every stage of a pipeline; a struct full of `Arc<Mutex<…>>` fields "so it can be shared". The question to ask is the reel's: which of these really has many owners?
- **Hidden unbounded growth.** With a shared pool and unbounded channels, nothing bounds how many buffers exist: it varied from run to run in the unstalled lab (asserted only as "between 1 and 1,000") and reached 1,000 when stage 3 stalled (Lab 5). Ring topologies bound it by construction; open pipelines need bounded channels (Chapter 10).
- **Self-deadlock from guard temporaries** (Lab 5) and **lock order** across two mutexes ("two threads have each acquired one of the locks, causing them to wait for each other forever"): neither is caught by the compiler. For contention, a different problem, the Tokio tutorial's first listed option is a dedicated task, and switching to Tokio's own mutex is "rarely" the fix. A `std::sync::MutexGuard` held across `.await` makes the future non-`Send` ("the std::sync::MutexGuard type is not Send"); its rule of thumb: a synchronous mutex in async code "is fine as long as contention remains low and the lock is not held across calls to .await". Chapter 6 and Milestone 2.
- **Games and entity systems.** The long-form blog version of the RustConf 2018 closing keynote (a secondary source; its page shows no author byline in the text this topic fetched, so no name is given) asks "How do you structure something like a game without needing `Rc<RefCell>` and `Arc<Mutex>` everywhere?" and answers with indices into `Vec`s and generational indices ("Generational indexes are never re-used because the generation will always increment", true until the counter wraps), naming `slotmap` as the crate built on the idea.
- No public post-mortem of an `Arc<Mutex<_>>` redesign is cited: none was found that could be opened and checked, and this topic would rather say so than invent one.

</section>

<section data-section="frontier">

## The frontier

- **A stale handle is caught, not prevented.** The arena trades compile-time lifetimes for run-time generation checks. Tying a handle to one arena at the type level, so that a wrong-arena or stale handle fails to compile, is a direction people keep exploring; no specific scheme is claimed here.
- **Wrong-map keys.** `slotmap` documents the limit and answers it at the type level: a key used on the wrong map "can not be detected at runtime", but "if you use a new key type for each slot map you create you can entirely prevent using the wrong key on the wrong slot map" (`new_key_type!`).
- **Async owner tasks and structured concurrency.** This topology lives in modern services as tasks with bounded queues, cancellation and orderly shutdown: Chapter 10's "Bounded channels and backpressure" and "Structured shutdown with tokens and trackers".
- **The language steers too.** The 2024 edition denies references to `static mut` by default ("There is no automatic migration to fix these references to static mut"), pushing global shared mutation towards owned or synchronised alternatives.

</section>

<section data-section="prove">

## Prove it

Answer first, then check. Each was compiled and run in `examples.py`.

**1. Debug this (reel).** A stage keeps `let view = &buf.bytes[..5];`, sends `buf`, then prints `view`. *`E0505`: cannot move out of `buf` because it is borrowed.* The fix that clones nothing: `let h = inspect(&buf);` returns a `Copy` `Header`, then send.

**2. Point to the line (reel).** Stage 3 stalls; where does stage 1 block? *At `for msg in rx`.* It can only work on a buffer someone sends it, and only the owner sends buffers, three in all; its sends never block because the channel is unbounded, which is safe here only because the ring holds 3 buffers.

**3. Defend a design (reel).** A job scheduler on one thread: jobs depend on jobs, and finished jobs are removed while others still list them. *An arena with handles.* `Rc<RefCell<Job>>` keeps a finished job alive through its dependents; `Arc<Mutex<Job>>` locks on one thread; a `Box` tree cannot give one job two dependents.

**4. Predict the outcome.** The ring with `IN_FLIGHT = 1`: how many buffers, what id order? *One buffer; ids `1, 1, 1, …`; one trip count of 1,000* (measured: `buffers_created=1 home_at_end=1`, `first_ids=[1, 1, 1] trips=[1000]`, `buffer_bytes=65536`). The ring is then sequential, one stage at a time.

**5. Debug this.** `println!("{} {}", pool.lock().unwrap().next_id, pool.lock().unwrap().free.len());` hangs. Why, and give two fixes. *The first guard is a temporary that lives to the end of the statement, so the second `lock()` waits for it.* Bind the value first (`let n = pool.lock().unwrap().next_id;`), or take one guard and read both fields from it.

**6. Estimate the cost (counts, no time).** A service has 8 worker threads and handles 10,000 requests per batch; each request touches the shared `Arc<Mutex<Stats>>` twice and the pool twice (a get and a put). Lock acquisitions per batch? *10,000 times 4 is 40,000.* After moving the stats into each worker and the pool into an owner thread: 0 mutex acquisitions, but a get becomes a request plus a reply and a put one message home, 3 messages per request, 30,000 per batch. A channel hop is itself a synchronisation; Chapter 4 measures it.

**7. Defend a design.** A teammate argues the owner thread is "just a mutex with extra steps". *It serialises like a mutex, but* the state has one owner, the invariant is checked in one place, the API is a closed message enum, no caller can hold the state across a slow operation, and backpressure is a property of the topology; it costs a thread and a channel hop per request.
