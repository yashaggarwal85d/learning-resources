## Outcomes

- State what `Send` and `Sync` each mean in one sentence, and name a real `std` type that is one but not the other (`Cell`/`RefCell`: `Send`, not `Sync`; `MutexGuard`: `Sync`, not `Send`; `Rc`: neither).
- Explain why `unsafe impl Send`/`Sync` is a real, unchecked proof obligation, and read `PhantomData<*const T>` as the mechanism that opts a generic type out of an auto-trait it would otherwise get.
- State that a spawned future must itself be `Send`, and that a `!Send` value only breaks that if it is still alive across an `.await` point.

## Internals

`Send` and `Sync` are both declared as `pub unsafe auto trait` — an *auto-trait*, which means the compiler derives it structurally rather than requiring a hand-written `impl` in the ordinary case. The Rustonomicon states the rule plainly: "if a type is composed entirely of Send or Sync types, then it is Send or Sync." That rule applies field by field, recursively, all the way down to the type's primitives — which is also why the check is cheap: `Send`/`Sync` have no methods, so there's nothing to vtable-dispatch or monomorphize, only a yes/no fact to propagate through a type's layout at compile time.

The same structural rule applies somewhere less visible: a compiler-generated future. An `async fn` or `async {}` block compiles to an anonymous type with one field for everything that needs to survive across an `.await` point — effectively a hand-rolled state machine, generated by the compiler. That generated type is `Send` by the same field-by-field rule as any other: it's `Send` exactly when everything live across its `.await` points is `Send`. This is why holding an `Rc` live across one `.await` makes the *whole future* `!Send`, even though nothing else about the function changed — the `Rc` became one of that invisible type's fields the moment it had to survive a suspension point.

## In production

The error this topic's step 8 produces verbatim — `future cannot be sent between threads safely` — is one of the most common async-Rust compiler errors in real codebases, and it is almost always this exact shape: some ordinary-looking value (an `Rc`, a `RefCell`, occasionally a borrowed `MutexGuard`) ends up alive across an `.await` inside code meant to run on a multi-threaded executor. `tokio::spawn`'s own `Send + 'static` bound exists for a concrete operational reason, not an abstract one: a multi-threaded runtime may migrate a suspended task to a different worker thread between `.await` points, so anything still alive at that moment genuinely does cross threads, even though the code never wrote `thread::spawn` anywhere. `rayon`'s closures carry the identical `Send` bound for the same underlying reason — work handed to a thread pool has to be able to actually run on any of its threads.

## The frontier

`unsafe impl Send`/`Sync` and `PhantomData`-based opt-outs are both stable, everyday tools. A third option exists only on nightly: `#![feature(negative_impls)]` lets a type write `impl !Send for T {}` directly, rather than achieving the same effect indirectly through a `PhantomData<*const T>` field — the Rustonomicon calls reaching for it "the incredibly rare case." Separately, exactly which auto-traits leak through an `impl Trait` return type (including `impl Future`) remains an area of ongoing language work, since a caller sometimes needs to know a hidden future is `Send` without the function's signature naming every type involved.

## Where this goes next

Knowing which types the compiler lets across a thread boundary at all says nothing yet about what happens once several threads actually hold the same one — `Arc` alone was never the whole answer in Chapter 4, and the next topic can finally say why: `Arc` and `Mutex` are two separate tools doing two separate jobs, and conflating them is a real, common mistake.
